# 学员作业反馈报告模板与要求

版本：1.0  
整理日期：2026-11-07  
用途：将详细评测结果整理为可直接发给学员的简明反馈报告。

## 一、报告结构

报告包含学员编号和以下四项内容：

1. 作业等级。
2. 作业优点。
3. 作业不足。
4. 改进方案。

报告应基于实际评测结果生成。详细评分表、测试日志和复现步骤可另存为评测附件，简明报告只挑重点说明。

## 二、作业等级

| 等级 | 分数范围 |
| --- | --- |
| 优秀 | 80 分及以上 |
| 良好 | 60 分及以上、低于 80 分 |
| 不及格 | 低于 60 分 |

边界约定：80 分归为优秀，60 分归为良好，避免区间重叠。

展示格式：`作业等级：良好（79分）`。

等级按总分确定。若仍有核心功能未完成，应在“作业不足”和“改进方案”中明确说明，不自行改变等级规则。

## 三、内容与格式要求

### 1. 作业优点

- 列出 **3–5 条**。
- 本节总字数不超过 **500 字**。
- 优先说明核心功能、实现质量、工程交付或验证结果中最突出的优点。
- 使用具体事实，避免“做得很好”“功能完善”等缺少依据的评价。
- 测试通过应说明范围，不把离线测试通过等同于全部功能或真实调用均已通过。

### 2. 作业不足

- 列出 **3–5 条**。
- 本节总字数不超过 **500 字**。
- 优先说明缺失的核心要求、影响功能正确性的问题和关键验证缺口。
- 描述实际问题及影响，不以个人技术偏好代替评分依据。
- 区分“已验证存在缺陷”和“缺少证据、尚未验证”，不把推测写成事实。

### 3. 改进方案

- 列出 **3–5 条**。
- 本节总字数不超过 **500 字**。
- 对应前面指出的不足，按影响程度和修复优先级排列。
- 每条尽量写清“需要做什么”和“如何验证完成”。
- 建议应符合当前作业范围，不无故增加额外技术或基础设施要求。

### 4. 排版与表达

- 作业优点、不足、改进方案均采用 Markdown 列表。
- **每条列表单独换行**，不能把多条内容挤在同一行。
- 小标题与列表之间保留空行。
- 每条围绕一个重点，尽量用一至两句话说清楚。
- 语言简洁、客观，面向学员说明问题与下一步行动。

如果实际独立问题或优点不足 3 条，以事实为准；可以拆分确有区别的方面，不编造内容或重复凑数。

## 四、可复用 Markdown 模板

复制以下模板，将占位内容替换为实际评测结果。每节默认 4 条，可按实际情况调整为 3–5 条。

```markdown
# 第【周次】周作业反馈

学员：【学员编号】

**1. 作业等级：【优秀 / 良好 / 不及格】（【得分】分）**

**2. 作业优点**

- 【优点一：已验证的核心功能及表现。】
- 【优点二：架构、抽象或实现质量。】
- 【优点三：可观测性、异常处理或其他重要能力。】
- 【优点四：文档、测试或工程交付。】

**3. 作业不足**

- 【不足一：尚未完成的核心要求及影响。】
- 【不足二：实际验证发现的功能问题。】
- 【不足三：另一项重要缺陷或能力限制。】
- 【不足四：必要验证或交付物的缺口。】

**4. 改进方案**

- 【优先改进一：具体行动及验收方式。】
- 【优先改进二：具体行动及验收方式。】
- 【优先改进三：具体行动及验收方式。】
- 【优先改进四：补充验证、文档或重新验收的要求。】
```

## 五、出具报告前检查

- 等级与总分符合分段规则，80 分归优秀、60 分归良好。
- 优点、不足、改进方案原则上各 3–5 条，各节不超过 500 字。
- 所有列表均逐条换行，小标题后有空行。
- 每项评价有详细评测结果支撑，没有将未验证事项写成已通过或已失败。
- 改进方案回应主要不足，并提供可执行的完成标准。
- 没有为了凑条数重复问题、虚构缺陷或堆砌空泛评价。
- 已删除模板占位内容及任何密钥、凭据等敏感信息。
