### 3.2 扣分原则

- 同一根因不重复扣分。例如未注册工具导致五个测试失败，主要扣工具注册对应子项，不能再按每个失败测试机械扣分。
- 一个子项最多扣至零分，总分最低为零、最高为 100。只有独立缺陷才能分别扣分。
- 每次扣分记录触发条件、预期结果、实际结果、证据位置、所属子项和分值。
- 业务行为缺陷扣对应任务；验收入口、固定框架或展示本身缺失，才扣“治理链路接入与验收展示”。不能因业务失败再次扣展示分。
- 修改 `PermissionEngine.decide()` 即违反明确限制，对应“固定权限引擎保持原样”不得分；若还造成独立业务缺陷，再扣相应任务分。验收结论为未通过，不自动把总分清零。
- 放宽 `extra="forbid"` 扣参数模型相应子项；直接调用 handler 的测试扣统一调用入口相应子项。不得再以同一违规重复处罚。
- 测试少、没有额外测试、未采用参考答案的函数写法或目录组织，本身不是扣分理由。超出范围的完善只作为亮点或建议，不追加分数。

## 5. 关键判分口径

### 5.1 金额与业务预检

- `(50000, 80000]` 是教学拦截区间，不是“所有超过 50000 都拒绝”。将其改为真实业务风格的单笔限额，会使超时演示无法执行，应扣相应分数。
- `amount > 80000` 仍需余额充足及匹配审批，不能为了进入 sleep 跳过预检、权限或审批。
- 账户查询必须使用 `context.tenant_id`。租户身份不能从模型参数读取，也不能靠账号中的 A/B 字母推断。
- 转出账户不存在时，附件未规定专门错误码。按零余额返回 `INSUFFICIENT_BALANCE` 或明确的账户不存在拒绝均可；不能抛出未处理异常或访问其他租户。转入账户不存在的错误码和消息则已有明确要求。
- 预检只能判断，不得预扣款、预加款或预先消费审批；审批由固定权限引擎处理。

### 5.2 审批与权限

- 未审批应返回 `DecisionAction.CONFIRM`，实际序列化值为小写 `confirm`；不因大小写展示形式与题目描述不同扣分。
- 匹配审批才可执行；金额或账户被更改后不能沿用原审批；成功审批只能消费一次。不能仅检查 `approval_id` 是否非空。
- 缺权限、缺执行白名单及 plan 模式不能被审批或 bypass 覆盖。不得向固定引擎增加转账特例。
- 审批摘要由 `_approval_digest()` 绑定工具和规范化参数，审批记录另绑定用户与租户。`canonical_target` 的编码不要求与参考答案一致，只需确定、能区分完整业务参数组合。
- 原框架会将参数中的整数金额规范化为 float。测试或演示创建审批时可使用校验后的 `TransferArgs`，避免直接审批原始整数映射造成摘要不同；不要求修改框架来统一所有数值表示。
- 离线演示允许模拟已取得人工确认并调用 `ApprovalStore.approve()`；应说明模拟含义，不要求实现真实审批页面。真实应用不得自动把模型生成的 `approved` 当作用户确认。

### 5.3 副作用、超时与重试

- 转入不存在时必须在扣款前拒绝，不能先扣后报错而不恢复。
- `amount > 80000` 应先 `await asyncio.sleep(3.0)`，Runtime 超时必须小于三秒。两秒是可接受配置，不要求只能为两秒，但须足以让正常的小额流程稳定完成。
- 超时路径应实际进入 handler 并等待；在预检里直接返回超时码，或直接从 handler 返回 `TIMEOUT_UNKNOWN`，不算完成超时模拟。
- 非幂等写超时返回 `TIMEOUT_UNKNOWN`，不能声称已确定失败或安全重试。此次可取消的本地 sleep 在扣款之前，所以本题验收可断言余额不变；不能据此推断真实远端转账超时也一定没有执行。
- 工具应配置 `idempotent=False`、`max_retries=0`，防止转账副作用被自动重试。不能靠把转账声明为只读或幂等来改变超时结果。
- `txn_id` 可用调用 ID 后六位，也可采用其他合理生成方式；题目措辞为“可用”，不能仅因未截取后六位扣分。原始测试对此固定断言为后六位：若仅该断言因合理生成方式而失败，教师应保留原测试结果，另行验证交易标识及完整成功路径；复核成立时记录为“标识断言等效满足”，不修改原测试文件，可视为满足该项验收。附件注释及验收测试期望 `status="accepted"`。
- 同账户转账未规定必须拒绝或成功；明确拒绝，或成功且余额净变化为零均可。不要求数据库级并发控制，但学员新增的部分写入、错误余额更新应按任务 4 判分。

### 5.4 脱敏与审计展示

- 账号脱敏示例 `ACC-A-123456 → ACC-A-****3456` 使用四个星号并保留末四位；不是简单地把前两位替换为两个星号。
- 应对当前工具输出中的两个账号生效，并保留既有邮箱及敏感键脱敏；不要求必须使用某一种 `re.sub` 写法。
- 附件的 `AuditRecord` 只记录参数字段名、决策及关联标识，不存账号值。因此接受“工具结果展示脱敏账号，同时打印关联审计记录”，不要求为满足“日志看到脱敏账号”而把账号新增进审计结构。
- 可在测试、原离线演示或独立演示中打印上述信息；文件名不限。使用 pytest 时可加 `-s` 显示打印内容。
- 核查 `tool_call_id`、`trace_id`、决策阶段和执行阶段可关联。失败或拒绝也应有对应记录；沿用附件行为即可，不要求新增数据库或审计字段。

每次评测记录学生版本、评测日期、Python 与主要依赖版本、实际导入路径、执行命令、退出码及测试摘要。每个扣分点记录最小复现与对应子项。

1. **固定对象**：记录仓库、分支、提交号或提交包，不直接修改学员业务代码。
2. **准备环境**：确认依赖和导入路径，保留必要环境差异；环境问题与实现缺陷分开记录。
3. **核查限制**：对比固定权限引擎、严格参数配置、业务测试入口和原始测试断言。
4. **运行原始五测**：保存真实结果，区分通过、失败、跳过和未验证。
5. **逐项核查六任务**：结合第 4.2 节补足边界、账户数据和注册策略检查。
6. **运行展示与必要补测**：确认审批、脱敏、审计及异常路径；只对疑点补测。
7. **按根因评分**：使用第 3 节逐项计分，避免重复扣分；给出验收结论及待修复要求。
8. **留存附件并出具反馈**：完整证据保存在内部，给学员的报告按统一模板提炼重点。

测试前后应恢复 `ACCOUNTS`，每个独立用例重新创建 Runtime、审批存储和审计容器，或保证等效隔离。避免前一用例扣款、审批已消费或审计残留导致误判。原始五测已有余额恢复 fixture，教师补测也应保留隔离。

不需要为了验收运行可选真实模型模式。日志与示例不得包含真实凭据；模拟账号按题目使用即可。

## 7. 扣分示例

| 问题 | 建议处理 |
| --- | --- |
| 将所有大于 50000 的金额都拒绝 | 从预检“教学区间”扣分；90000 超时测试因此失败不再重复扣 handler 超时分，需静态或独立证据确认 handler 是否实现。 |
| 使用 `balance <= amount` 导致无法转出全部余额 | 从余额比较子项部分扣分；不再因相同根因扣余额更新分。 |
| 转入账号不存在时已经扣款 | 从任务 4 的“扣款前拒绝”子项扣分；若同一语句顺序是唯一根因，不再重复扣“无部分写入”。 |
| 去掉 `extra="forbid"`，模型可提交 `approved` | 参数模型对应 5 分子项不得分，验收结论未通过；不额外清零总分。 |
| 转账逻辑正确，但只在测试中直接调用 handler | 扣统一入口相应子项；直接 handler 测试不能证明治理链路通过，须补跑可信五测。 |
| 小额转账成功，但工具被声明为幂等，超时返回 `TIMEOUT` | 从注册策略对应子项扣分；不要再把同一错误策略作为独立超时实现缺陷扣分。 |
| 修改固定权限引擎来给 transfer 放行 | 固定引擎保持原样的 3 分不得分，验收结论未通过；若另外跳过审批，按独立缺陷追溯对应策略或接入问题。 |
| 五测通过，但没有打印确认、脱敏结果与关联审计的入口 | 从验收展示的 3 分子项按缺失范围扣分，不否认已验证的业务能力。 |
| 审计不存账号，只打印脱敏工具结果和关联审计 | 满足展示口径，不扣分。 |
| 没有真实模型、Docker、数据库、Decimal 或额外测试 | 原题未要求，不扣分。 |

示例用于统一尺度，实际扣分以证据和子项上限为准，不能机械叠加。

### 8.2 发给学员的反馈报告

按[学员作业反馈报告模板与要求](../学员作业反馈报告模板与要求.md)的结构、条数、字数和排版要求出具，并通过其第五节检查。

- **等级**：按总分确定，与评测附件一致，示例为 `作业等级：良好（79分）`；暂评分应明确标注。
- **优点**：选取已验证的核心实现与运行事实。本周离线验收足以证明作业链路，不必要求真实模型证据；不要将内存模拟说成真实支付系统验证。
- **不足**：按影响排序，合并同一根因；明确区分缺陷与未验证事项。没有足够独立问题时不凑数。
- **改进方案**：与不足对应，写明修复动作和复验条件。题目外的生产化建议注明不影响得分，并排在必须修复事项之后。
- **内部留存**：详细评分表、验收结论标签、测试日志和复现命令保留在评测附件，不放入简明学员反馈。
