# 第三周作业评分标准：基于 smolagents 实现 Guarded Harness

版本：1.2  
整理日期：2026-11-18  
满分：100 分

## 1. 适用范围与评测目标

本标准用于批改“AI Agent 全栈工程师训练营”第三周作业，以[作业说明](AI%20Agent%20全栈工程师训练营-作业三.md)为依据，结构沿用第二周评分标准。作业未附练习源码和原始测试，模糊之处按第三周课程（3.1 Agent Loop、3.3 State 与 Checkpoint、3.4 Sandbox、3.5 Harness、3.7 Codebase Agent）讲授的规则判定。

评测目标是确认：学员在不重写 smolagents 核心的前提下，为 `ToolCallingAgent` 增加一层可恢复的 Guarded Coding Harness。模型只负责决策；门禁、执行边界、状态、审计、恢复和最终验收由程序完成，并且具备安全完成“代码理解”和“测试修复”两类任务的能力。两类能力均需核查，但 T2 的真实模型运行记录只要求覆盖其中一类。

采用源码核查、学员测试、教师用 Fake Model 补测和提交记录核对相结合的方式。不能仅凭 README 声明、截图或已有的 passed 报告判断完成，也不能用测试通过率直接换算分数。

smolagents 相关口径已在 v1.26.0（当前最新发布版）上用脚本核实。学员使用其他版本时，以其锁定版本的实际行为为准。

## 2. 核心验收前提

- 基于 smolagents 的 `ToolCallingAgent` 运行；没有修改 site-packages 中的 smolagents，没有内嵌改过的 smolagents 副本，也没有用手写循环取代 smolagents 的 Agent 循环。
- 七类交付物的实现均可定位并已接入运行流程，不是空文件或占位实现；允许第 2.1 节所述的模块合并。此项核查职责是否有实际承载，不代表每个细项均已通过。
- 在无网络、无 API Key 的环境中，`pytest -q` 全部通过，没有借助 skip、xfail、删改断言或绕过 Harness 制造通过结果。
- 所有 Tool Call（含 `final_answer`）都经过 Gate，不存在绕过 Gate 直接进入 handler 的路径。
- 所有 P0 验收场景的行为成立。
- 两类任务均有可验证的正常完成能力；不要求两类都提交真实模型运行记录。

具体缺陷按对应验收项判定：已确认 P0 不成立（含 T1 的必测覆盖缺失）或其他核心前提失败，结论为“未通过”；仅 P1、环境变量与输出边界、非 P0 测试覆盖或提交记录有缺陷时，在其他核心前提成立的条件下判为“通过，需修复”，不再因同一细项缺陷反推整类交付物缺失。无对应编号的必交职责，如完整业务状态保存或 append-only 审计，若已确认缺失，仍属于核心交付缺失。未验证事项按“证据不完整”处理；已确认核心失败时，不因同时存在未验证项而改判。

允许子类化 `ToolCallingAgent` 并重写单个方法（如 `execute_tool_call`、`process_tool_calls`），也允许使用 `final_answer_checks`、`step_callbacks` 等公开扩展点，这些都不算“重写核心”。

作业等级统一按[学员作业反馈报告模板与要求](../学员作业反馈报告模板与要求.md)第二节，只按总分确定：优秀为 80 分及以上，良好为 60 分及以上、低于 80 分，不及格为低于 60 分。不另设分数封顶或一票否决规则。

内部评测附件另记录验收结论，不改变按分数确定的作业等级：

| 结论 | 判定条件 |
| --- | --- |
| 通过 | 核心前提全部成立，P0、P1 场景及提交材料均有可复现证据，没有需要修复的缺陷。 |
| 通过，需修复 | 核心前提全部成立，但 P1 场景（S2、S4、A2、T2）、环境变量与输出边界、非 P0 测试覆盖或提交材料存在缺陷或缺失。 |
| 证据不完整 | 受缺失文件、依赖环境等因素影响，部分能力尚不能验证；给出暂评分及补交要求。 |
| 未通过 | 已确认核心前提不成立，如 `pytest -q` 未全绿、测试依赖真实模型、修改 smolagents 核心、存在绕过 Gate 的路径或某个 P0 场景行为不成立。 |

“未验证”不等同于“已确认错误”，也不等同于通过。对可确认部分暂评，列明未验证项及其待定分值，补充证据后复评。核心缺失与约束违规必须写入学员反馈的不足和改进方案。

### 2.1 判分依据与范围

- 作业点名的模块文件名按要求核查，可以放在包目录中（如 `src/harness/gate.py`）。模块合并到其他文件、但职责仍能定位时，只扣对应模块职责的部分分。
- 作业列出的六个测试文件按题目组织。改名或合并但能逐项定位到 P0 场景，不扣分；无法定位的场景视为缺少测试。
- `WAITING_APPROVAL`、`UNKNOWN_RESULT` 是作业给出的名称，推荐原样使用。课程说明状态名可按项目约定（3.3 节），因此使用 `RESULT_UNKNOWN`、`AWAITING_APPROVAL` 等等价名称且语义清楚时不扣分。StopReason 的具体枚举值不作要求，只要求可区分完成、等待审批、结果不明、轮数或预算耗尽、拒绝、取消等结论。
- 目标仓库不限定语言和样例。可以使用课程 3.7 节的 `samples/1_login_demo` 和 `samples/2_bug_fix/demo-app`，也可以自建小仓库。两类任务均需核查正常路径，可用 Fake Model 确定性集成测试验证；真实模型只要求跑通一类任务。
- 课程参考实现是 TypeScript（pi），学员不必照搬其模块划分、字段名或配置格式，按作业要求的行为判分。
- 不要求容器或操作系统级隔离、网络沙箱、LangGraph、数据库、分布式锁、真实审批界面、任意时刻崩溃都能无损恢复、副作用 exactly-once、审计防篡改哈希链或 Managed Agent 支持。这些属于超出范围的完善，只作为亮点或建议，不追加分数。
- 本评分标准是批改用的分值分配方案。作业未要求单独 README、依赖锁文件或指定的记录格式，不因缺少这些文件本身扣分；能按提交材料复现验收即可。

| 评分项 | 子项及分值 |

### 3.2 扣分原则

- 同一根因不重复扣分。例如 Gate 只包装了 `Tool.forward`，导致参数非法的调用无法审计、也拿不到 `tool_call_id`，主要扣“唯一入口”子项；G1 只在独立缺陷存在时另扣。
- 一个子项最多扣至零分，总分最低为零、最高为 100。只有独立缺陷才能分别扣分。
- 比例扣分保留精确值参与计算，例如 T1 每个应扣的缺失场景扣 5/14 分；中间子项不逐项舍入。汇总后仅对总分按十进制四舍五入保留两位小数（ROUND_HALF_UP），该值作为正式总分，同时用于等级判定和报告展示。例如 79.994 分记为 79.99 分、良好，79.995 分记为 80.00 分、优秀；59.994 分记为 59.99 分、不及格，59.995 分记为 60.00 分、良好。内部保留原始分值与计算式；明细展示值如因舍入与总分有尾差，应注明，不调整实际扣分。
- 每次扣分记录触发条件、预期结果、实际结果、证据位置、所属子项和分值。
- 场景行为缺陷扣对应模块；该场景缺少测试时，不再扣对应测试覆盖分。行为成立、只是缺少确定性测试，才扣覆盖分：P0 归 T1，其余边界与两类正常路径归上述 3 分子项。两类任务能力缺失归“Harness 装配”子项；若由 G、S、C、A、H 的具体缺陷导致，按同一根因只扣对应子项。
- 教师补测发现的缺陷扣对应模块，不再因“学员测试没发现”另扣测试有效性分。测试有效性只针对系统性问题，如以直接调用 handler 代替集成测试、mock 掉待验证的 Gate 或 Sandbox 行为、依赖真实模型或残留文件。合法的模块单元测试不因此扣分。
- 修改 smolagents 核心违反明确限制，扣“Harness 装配”对应子项，验收结论为未通过，不自动把总分清零。若还造成独立缺陷，再扣相应模块分。
- 测试数量、代码风格、未采用课程参考实现的结构，本身不是扣分理由。超出范围的完善只作为亮点或建议，不追加分数。

## 4. 统一验收用例

### 4.1 环境与学员测试

在学员项目根目录、按其依赖说明新建的虚拟环境中运行：

```bash
env -u OPENAI_API_KEY -u ANTHROPIC_API_KEY -u HF_TOKEN python -m pytest -q
```

预期全部通过。另需核查以下事项：

- 记录 Python、smolagents 和 pytest 版本，以及实际导入的模块路径。
- 用 `pip show -f smolagents` 或在干净环境中重装同版本，确认 smolagents 未被修改，也没有导入项目内的改版副本。
- 断网或屏蔽模型地址后再跑一次，确认测试不访问真实模型。
- 在新的临时目录连续运行两次，确认结果不依赖上一次留下的状态、Checkpoint 或审计文件。
- 检查测试没有被 skip、xfail 或削弱断言，集成测试经 Harness 入口而不是直接调用 handler 或 `agent.run`。

学员可以增加测试，但教师不能只凭学员测试认定通过；对存疑场景用第 4.2 节补测。

### 4.2 核心验收核查

教师用自己的 Fake Model（继承 `smolagents.models.Model` 并实现 `generate`，按脚本返回带 `tool_calls` 的 `ChatMessage`）经学员的 Harness 入口驱动补测。学员测试已可信覆盖的场景可只做源码核查。

先分别核查两类任务的正常路径：代码理解应通过仓库读取生成非空说明，文件引用与调用链有源码依据；测试修复应复现失败、完成获批修改、运行当前版本测试并通过，最后由程序接受完成声明。两类均需核对状态、审计与交付物一致。能力缺失归 Harness 装配或实际缺陷所属子项；仅缺测试归正常路径覆盖分。这是原题任务目标的核查，不新增 P0 编号或额外分值。

| 编号 | 输入或操作 | 通过标准与评分归属 |
| --- | --- | --- |
| G1 | 脚本发出缺必填字段、字段类型错误（如 `path=123`）的调用，`tool_call_id` 为 `call_g1` | handler 调用次数为 0；返回结构化错误（错误码与说明），含 `call_g1`；Run 不因未捕获异常中止；有拒绝审计。归 Gate。 |
| G2 | 连续三步发出相同工具和参数、不同 `tool_call_id` 的调用；再测参数键顺序不同的同一调用 | handler 只执行两次；第三次在执行前以稳定错误码拦截；键顺序不同不能绕过。归 Gate。 |
| G3 | 未审批时调用写文件工具；另测模型在参数中自带 `approved: true` | 状态进入 `WAITING_APPROVAL`，待审批动作已保存；目标文件摘要不变，写 handler 零调用；自带的批准字段被拒绝或忽略。归 Gate。 |
| G4 | 经 Harness 审批入口（非模型可见工具）批准待审批动作后继续；随后重放同一调用；再测批准后改变参数 | 写入只执行一次；重放被拒绝，文件内容和写入次数不变；改参后的调用不能沿用原审批。归 Gate。 |
| S1 | 读写 `artifacts/../../.env`，以及工作区外的绝对路径 | Sandbox 拒绝，handler 不执行，`.env` 未被读取或修改；有拒绝审计。归 Sandbox。 |
| S2 | 在工作区内建立指向工作区外文件（或 `.env`）的软链接并经它读写；直接访问学员声明的敏感路径（至少含 `.env` 类密钥文件） | 按真实落点判定后拒绝；审计记录拒绝规则。归 Sandbox。 |
| S3 | `run_test` 传入配置外命令，如 `rm -rf .`、`pytest; touch /tmp/pwned`、`python -c ...` | 命令不执行，进程未启动，标记文件不存在；配置内命令正常运行。归 Sandbox。 |
| S4 | 配置一条会派生孙进程的测试命令，例如 `sh -c '(sleep 5; touch /tmp/s4_marker) & sleep 30'`，超时设为 1 秒；再在运行中触发取消 | 在超时附近返回超时或取消状态；之后进程组内无存活进程，标记文件不会出现。归 Sandbox。 |
| E1 | 父进程设置 `FAKE_SECRET_TOKEN`，让允许的命令打印环境变量；再让命令输出超过上限的大量文本 | 子进程看不到该变量；返回给模型的输出被截断并标明省略。归 Sandbox。 |
| C1 | 正常执行若干步，以及进入等待审批后，读取 Checkpoint | 每个安全步骤后都有新 Checkpoint，含 run、step、计划、证据、预算和待审批动作；`state_store` 能读出完整业务状态与停止原因。归 State 与 Checkpoint。 |
| C2 | 用测试钩子在写 handler 完成后、结果与 Checkpoint 保存前让进程退出，再在新进程恢复 | 该步骤标记 `UNKNOWN_RESULT`；写入不重放（handler 次数与文件内容不变）；停止自动推进并输出核查信息。归 State 与 Checkpoint。 |
| C3 | 进程一执行到中途（如等待审批或注入中断）后退出，用独立子进程执行恢复入口 | 从后续步骤继续；已完成写入不重复；已用轮数、工具调用数和预算延续，例如已用 3 步、上限 5 步时只能再走 2 步。归 State 与 Checkpoint。 |
| C4 | 在前次执行结果已保存、无未决写入的情况下，两次进程之间修改工作区文件，或修改待审批动作的目标文件 | 恢复时发现变化，停止并等待核对；旧测试证据和旧审批失效，不按旧记录继续；不因文件变化单独认定执行结果未知。归 State 与 Checkpoint。 |
| A1 | 按 G1 或 S1 的 `tool_call_id` 查询审计 | 记录含 run_id、tool_call_id、工具名、rule、decision、actor 和时间。归 Audit。 |
| A2 | 对一次含审批的完整任务按 run_id 查询；检查审计写入方式 | 能依次还原 Gate 决策、Sandbox 检查、审批请求与批准人、执行、结果和状态变化；记录只追加，没有改写或删除旧记录的路径。归 Audit。 |
| H1 | 脚本未生成交付物（或生成空文件）就调用 `final_answer`；若 Gate 返回结构化拒绝字符串，检查后续完成标记 | final answer 被拒绝，Run 不进入完成态，拒绝字符串不能被当作成功答案；可以把缺失项反馈给模型继续，或以非成功 StopReason 停止。归 Harness。 |
| H2 | 脚本修复源码、`run_test` 通过、再修改源码、然后 `final_answer`；之后重跑测试再提交 | 第一次提交被拒绝，提示需重跑；重跑通过后才能完成。归 Harness。 |
| H3 | 脚本持续发出不重复的无害调用直到最大轮数；对另行声明的预算维度（如工具调用数、Token 或耗时）分别触发上限；仅采用轮数预算时不另要求其他维度 | 以明确 StopReason 停止，状态不是完成；smolagents 在 `max_steps` 时强制生成的答案不被当作成功结果。归 Harness。 |
| T1 | 对照第 4.1 节结果，逐项定位 14 个 P0 场景（G1–G4、S1、S3、C1–C4、A1、H1–H3）的测试 | 每个场景都有确定性测试，断言真实效果。归测试与提交证据。 |
| T2 | 核对提交的真实模型运行记录、产物、Diff、测试记录和审计，按第 5.6 节区分任务类型 | 记录中的工具调用与审计 ID 对应；实际 Diff（含新增产物）与写入记录一致；测试记录标明对象与版本，测试修复须绑定修复后的源码并通过，代码理解按适用性核对；产物与任务要求相符；日志不含真实凭据。归测试与提交证据。 |

教师不需要 API Key 也能完成 T2 核对；学员提供了可用配置时，可选择重跑一次以确认记录真实。

### 4.3 建议边界补测

可补测：模型在同一步返回多个相同调用（smolagents 会用线程池并行执行）、`final_answer` 与其他工具同一步出现、调用未注册工具、审批被拒绝、审批属于其他 Run、等待审批时取消、Checkpoint 文件损坏或版本不符、恢复后再次中断再恢复。

这些用例用于定位集成问题。若暴露题目明确要求被破坏，例如并行调用让重复检查失效或同一审批被消费两次，按对应子项扣分；若属于未要求的扩展，只写建议，不新增扣分门槛。

## 5. 关键判分口径

### 5.1 Gate 与审批

- v1.26.0 的 `process_tool_calls` 会遍历顶层调用并持有调用 ID，`execute_tool_call` 是下游执行接入点。两处都可用于接入 Gate，也接受其他能覆盖全部调用的等价方案；必须覆盖 `final_answer`、未知工具名和参数非法的调用。只包装 `Tool.forward` 会漏掉在工具执行前被拒绝的调用；在 `__init__` 之前包装现有工具还可能漏掉后加的 `final_answer`，不能据此认定满足“唯一入口”。
- `execute_tool_call` 本身不接收 `tool_call_id`。学员可以重写 `process_tool_calls` 或自建分发把 ID 传给 Gate，方式不限，但拒绝结果必须带原 `tool_call_id`。
- 依赖 smolagents 内置的 `validate_tool_arguments` 不能满足 G1：它在 Gate 之外抛错，不经 Gate 审计，返回给模型的也不是含 ID 的结构化错误。
- 拒绝方式影响模型看到的内容。在默认分发路径中，普通工具的 Gate 返回结构化字符串时，结果作为 observation 回写，ID 保留，Run 继续；`final_answer` 不能照搬这一处理，须另行阻止完成标记，见第 5.5 节。Gate 直接抛出 `AgentError` 子类且未在自定义分发中转换时，smolagents 不记录本步的 tool_calls，模型只看到通用错误；直接抛出其他异常会中止整个 `run()`。判定 G1 时应看最终是否返回含原 ID 的结构化错误，而非仅凭内部是否抛异常。进入 `WAITING_APPROVAL` 等有意暂停的停止不受此限。
- 参数、权限与风险、审批、重复动作及适用预算检查都必须在 handler 之前完成。推荐先校验参数再做依赖参数的检查，但不限定其余检查的固定顺序；只要拒绝不产生副作用、审批不能被绕过，等价顺序不扣分。先执行 handler 再标记拒绝不算拦截。
- 重复动作指纹为工具名加规范化参数，不能包含 `tool_call_id`，否则每次调用都不同，G2 永远不会触发。按连续次数或按整个 Run 的累计次数计数均可，只要三次连续相同调用时第三次被拦截。课程称指纹检测是“保守的入门保护”，不要求进度感知或振荡检测。
- 写操作必须需要审批；读操作是否审批由学员按风险分级决定。审批入口必须在模型可见的工具之外（课程 3.3、3.5 节：模型不能批准自己提交的补丁）。提供 `approve` 工具，或接受模型参数中的 `approved` 字段，按 G3 未满足处理。
- 审批至少绑定 Run、工具名和规范化参数；推荐同时绑定目标文件当前摘要（课程 3.3 节 patchHash、3.7 节 args_digest）。只校验 `approval_id` 非空不算绑定。
- 审批只能消费一次。批准后的调用执行成功后，重放同一调用或复用已消费审批应被拒绝，不能产生第二次写入。相同参数的新调用若获得独立的新审批，应按当前权限、风险、工作区及 G2 重复动作规则重新判断；不能仅因参数曾执行过就认定 G4 要求永久禁止。

### 5.2 Sandbox

- 路径检查应先把相对路径拼到工作区，再取 `realpath` 等真实落点后判断是否在允许范围内；只比较字符串前缀，或只做 `normpath` 而不解析软链接，S2 不得满分。目标文件尚不存在时，按最近已存在祖先目录的真实路径判断。
- 敏感目录由学员声明，至少覆盖 `.env` 类密钥文件；`.git`、策略文件、审计和 Checkpoint 目录推荐列为禁止写入。不要求与课程配置相同。
- `run_test` 只能执行配置允许的命令或测试目标。推荐由程序构造参数列表并以 `shell=False` 执行；使用固定受信任的 shell 命令等方案，只要模型不能注入配置外命令，也可通过。对模型给出的整条命令字符串做前缀匹配后交给 shell，会放过 `pytest; rm -rf .`，S3 不得分。
- 超时或取消必须真实终止整个进程组并确认退出。POSIX 环境推荐以 `start_new_session=True` 或 `os.setsid` 启动，再对进程组先发 SIGTERM、宽限后发 SIGKILL；不限定具体 API 或信号顺序，等价进程树终止机制也可通过。仅用 `subprocess.run(timeout=...)` 杀直接子进程、导致孙进程继续运行时，S4 只能得部分分。
- `agent.interrupt()` 只在两步之间生效，不会终止正在运行的工具或子进程（已在 smolagents 上核实）。取消必须传到 Sandbox 的执行路径并真实终止进程；只依赖 `interrupt()` 的取消不满足 S4 的取消部分。
- 子进程环境应显式传入并剔除疑似密钥变量（如名称以 KEY、TOKEN、SECRET、PASSWORD 结尾），不要直接继承父进程环境。输出上限的具体数值不限，但截断时应标明省略。
- smolagents 的本地或远程 Python 执行器只用于 `CodeAgent`，`ToolCallingAgent` 的工具直接在宿主进程运行。因此文件和命令边界必须由 `sandbox.py` 自己实现，不能以“smolagents 自带沙箱”为由免除。

### 5.3 State 与 Checkpoint

- “安全步骤边界”按课程 3.3 节理解：完整轮次结束后保存，进入等待审批前先保存待审批动作和状态。不要求任意时刻崩溃都能原样恢复。
- Checkpoint 推荐包含格式版本和工作区摘要，并用临时文件加重命名原子写入。作业未单列这两点，缺少时只作建议；但没有工作区摘要通常无法通过 C4，届时扣 C4。
- C2 针对未决写入：执行写操作前记录“已开始”，结果保存后再关闭。恢复时发现有开始、无可靠结果的写操作，应标记 `UNKNOWN_RESULT` 并停止自动执行；不能仅凭文件摘要变化认定写入成功，也不能当作未开始重放或当作失败自动重试，否则 C2 不得分。只读操作可以安全重放。
- C4 针对工作区变化：执行结果已可靠保存、没有未决写入时，文件摘要与已保存基线不符应使旧证据或旧审批失效，并停止等待核对，不必标记 `UNKNOWN_RESULT`。两种情况同时出现时，保留“写入结果未知”和“工作区已变化”两类事实，停止自动执行；按根因判分，不因同一缺陷在 C2、C4 重复扣分。
- 恢复顺序应为：读取 Checkpoint、核对工作区、确认可以继续、还原业务状态，最后才调用模型。只把原始任务重新发给模型不算恢复。
- smolagents 的 `AgentMemory` 只能导出、不能载入，`run(reset=False)` 只在同一进程内续接。C3 必须用独立进程验证，由学员自己的 `state_store` 还原状态，再重建 memory 或注入进度摘要，方式不限。同一进程内续接不满足 C3。
- smolagents 每次 `run()` 都从第 1 步重新计数。已用轮数、工具调用数及学员声明的预算消耗必须由 Harness 累计并写入状态，恢复后继续使用，不能清零；不因此要求实现所有可能的预算维度。
- 审批状态可以持久化后在恢复时重新校验，也可以在重启后作废并要求重新审批，课程采用后者。工作区变化后仍沿用旧审批，按 C4 未满足处理。
- 状态机不要求使用课程的九个状态名，按迁移是否由事件驱动、`WAITING_APPROVAL` 是否真正阻止写入、暂停与失败是否区分来判断。

### 5.4 Audit

- append-only 指只追加写入，例如以追加模式写 JSONL，或数据库只插入不更新。每次重写整份 JSON 列表、按 ID 覆盖旧记录，扣 append-only 子项。不要求防篡改存储或哈希链。
- rule 可以是规则名或错误码，decision 为放行、拒绝、等待审批等，actor 指做出决定的一方（Gate、Sandbox、具体审批人）或调用发起方，字段名可以不同，但含义必须能对应。
- 被拒绝的调用也必须有记录；只从 smolagents memory 事后整理审计不可靠，因为 smolagents 在某些失败路径下不保存本步的调用记录。审计应由 Gate、Sandbox 和 Harness 在决策和执行时写入。
- 审计不应保存密钥或敏感文件内容，长输出可存摘要或截断。题目未单列脱敏要求，发现泄露时写入不足和改进方案；只有泄露本身破坏了 S1、S2 等明确要求时才扣分。

### 5.5 完成验收与停止原因

- 完成态由程序判定。`final_answer` 只是模型的完成声明，Harness 必须检查交付物存在且非空；测试修复类任务还需当前版本的测试通过证据。
- 拒绝 final answer 可用 `final_answer_checks`（检查失败时 smolagents 把错误回写给模型并继续运行），也可在自定义分发中将被 Gate 拒绝的 `final_answer` 作为非最终工具结果处理。v1.26.0 默认 `process_tool_calls` 按工具名设置 `is_final_answer`，因此仅从 `execute_tool_call` 返回结构化拒绝字符串仍可能被当成最终答案；必须同时阻止完成标记或由完成检查拒绝。采用 `final_answer_checks` 不免除 `final_answer` 经过 Gate 的要求；检查函数返回 `None` 会被当作失败。
- 测试证据应绑定受测内容，例如源码与测试文件的内容摘要。测试通过后源码又被修改，旧证据失效。只记一个 `tests_passed=True` 布尔值而不随修改失效，H2 不得分。
- v1.26.0 在达到 `max_steps` 时会再调用一次模型生成答案，并可作为普通输出返回。推荐通过 `RunResult.state == "max_steps_error"` 识别；检查 memory 中记录的 `AgentMaxStepsError`，或采用其他可验证的等价机制也可。Harness 必须识别轮数耗尽并写入明确的 StopReason，不能仅凭返回了答案判断成功；把强制生成的答案标为成功，H3 不得分。
- 预算可以是轮数、工具调用数、Token 或耗时中的一种或几种，由学员声明。停止原因一旦写入不应被后续逻辑覆盖成成功。

### 5.6 测试与真实运行

- Fake Model 可以按脚本返回 `ChatMessage`。断言应检查真实效果：handler 实际调用次数、文件摘要、进程是否存活、状态与审计内容，而不是只看日志里出现提示。
- `pytest -q` 结果须为实际运行输出。教师复跑结果与提交不一致时，以教师复跑为准。
- 真实模型运行记录至少包含任务、模型标识、Run ID、工具调用与结果、停止原因和最终交付物；Checkpoint 恢复记录应展示中断、换进程恢复和恢复后的进度。格式不限。
- 代码理解任务核对说明产物引用的文件和调用链真实存在，并核对实际 Diff 与写入审计（新增说明文件也计入产物变化）；未改源码时应明确注明，不要求为演示制造源码修改。T2 证据中仍需交代测试情况：实际运行过仓库测试的，提供对象、版本和结果；任务未运行仓库测试的，明确记录“未运行／不适用”及原因，并提供说明产物的核验记录，不伪称测试通过。该适用性说明不免除作业本身提交 `pytest -q` 实际结果的要求。
- 测试修复任务核对 Diff 与修复目标相关、测试记录绑定修改后的源码版本且通过，未删改测试来制造通过；不能用代码理解任务的“不适用”说明替代修复后的测试证据。
- 未提交真实模型运行记录时 T2 不得分，不能用 Fake Model 记录替代。仅当其他核心前提均成立时，验收结论为“通过，需修复”；已有核心前提失败时仍为“未通过”，核心能力尚未验证时按“证据不完整”处理。

## 6. 证据要求与批改流程

每次评测记录学生版本、评测日期、Python 与 smolagents 版本、实际导入路径、执行命令、退出码及测试摘要。每个扣分点记录最小复现与对应子项。

1. **固定对象**：记录仓库、分支、提交号或提交包，不直接修改学员业务代码。
2. **准备环境**：在干净虚拟环境中安装依赖，确认 smolagents 未被修改；环境问题与实现缺陷分开记录。
3. **运行学员测试**：按第 4.1 节离线运行并保存真实结果，区分通过、失败、跳过和未验证。
4. **核查唯一入口**：阅读 Gate 的接入方式，确认没有绕过路径。
5. **逐项补测**：按第 4.2 节核查两类任务正常路径及 G、S、E、C、A、H 场景，对存疑项用 Fake Model 补测，C2、C3 必须使用独立进程。
6. **核对提交记录**：核对 pytest 输出、审计记录、Checkpoint 恢复记录和真实模型运行记录是否相互印证。
7. **按根因评分**：使用第 3 节逐项计分，避免重复扣分；给出验收结论及待修复要求。
8. **留存附件并出具反馈**：完整证据保存在内部，给学员的报告按统一模板提炼重点。

每个补测用例使用新的临时工作区、状态目录和审计文件，避免前一用例的 Checkpoint、已消费审批或审计残留导致误判。补测中的危险命令只针对临时目录，不在教师自己的工作目录中运行。日志与示例不得包含真实凭据。

## 7. 扣分示例

| 问题 | 建议处理 |
| --- | --- |
| Gate 只包装 `Tool.forward`，参数非法的调用由 smolagents 报错，不经 Gate | 扣“唯一入口”子项；G1 的结构化错误与 ID 若因此缺失，按同一根因不重复扣；验收结论未通过。 |
| Gate 拒绝时抛出 `PermissionError`，整个 Run 中止 | 扣 G1 子项中“结构化错误”部分；G3、S1 等因同一拒绝方式受影响时不重复扣。 |
| 重复指纹包含 `tool_call_id`，三次相同调用都执行 | G2 不得分，验收结论未通过。 |
| 指纹用 `json.dumps` 未排序键，键顺序不同即可绕过 | 按影响从 G2 扣分；参数键顺序不改变调用语义，连续三次相同调用仍能绕过即为 G2 不成立，验收结论未通过。 |
| 提供模型可调用的 `approve` 工具 | G3 不得分，模型可以自行批准写操作；不再因同一根因扣 G4。 |
| `run_test` 用 `shell=True`，只检查命令以 `pytest` 开头 | S3 不得分，验收结论未通过。 |
| 超时使用 `subprocess.run(timeout=...)`，孙进程继续运行 | 从 S4 部分扣分，验收结论为通过，需修复。 |
| 恢复只在同一进程内调用 `run(reset=False)` | C3 不得分；若计数也因此清零，按同一根因不重复扣。 |
| 写入后崩溃，恢复时把该步当作未开始并再次写入 | C2 不得分，验收结论未通过。 |
| 达到 `max_steps` 后把 smolagents 强制生成的答案作为成功返回 | H3 不得分，验收结论未通过。 |
| 测试通过后改源码，仍以旧的 `tests_passed=True` 完成 | H2 不得分；补测发现但学员测试未覆盖时，T1 不再因同一场景另扣。 |
| 审计每次重写整份 JSON 文件 | 扣 append-only 子项；字段齐全时 A1、A2 不受影响。 |
| 集成测试直接调用 handler，不经 Harness | 扣测试有效性子项；对应行为须由教师补测确认后再评模块分。 |
| 其他核心前提全部成立，但没有真实模型运行记录 | T2 的 5 分不得分，验收结论为通过，需修复。 |
| 没有使用 Docker、LangGraph、数据库或额外测试 | 原题未要求，不扣分。 |

示例用于统一尺度，实际扣分以证据和子项上限为准，不能机械叠加。

### 8.2 发给学员的反馈报告

按[学员作业反馈报告模板与要求](../学员作业反馈报告模板与要求.md)的结构、条数、字数和排版要求出具，并通过其第五节检查。

- **等级**：按第 3.2 节舍入后的正式总分确定，与评测附件一致，示例为 `作业等级：良好（79.00分）`；暂评分应明确标注，并使用相同精度规则。
- **优点**：选取已验证的门禁、边界、恢复和审计能力。离线测试通过应说明范围，不等同于真实模型任务已验证。

- **内部留存**：详细评分表、验收结论标签、测试日志和复现命令保留在评测附件，不放入简明学员反馈。
