# 第一周作业评分标准：LLM 统一模型调用服务

版本：1.1  
整理日期：2026-11-07  
满分：100 分

## 1. 适用范围与评测目标

本标准用于批改“AI Agent 全栈工程师训练营”第一周作业。

评测目标是确认：学生实现了统一模型调用服务，通过适配器封装至少两种不同 API 协议，并使流式输出、结构化输出、提示词版本管理、可观测性、重试和按模型独立限流具备可验证的运行证据。

采用以下方式评测：

1. 阅读源码、配置、README 和学生提交的证据。
2. 使用教师统一验收脚本运行正常流程与异常流程。
3. 使用真实模型调用证明协议接入，使用受控模拟证明重试、限流等异常处理。
4. 人工检查关键实现，并将每次扣分关联到可复现的用例。

本标准不限定开发语言、框架、数据库或具体模型品牌。推荐模型组合是参考方案，学生可使用其他模型，但必须满足两种不同 API 协议的训练目标。

## 2. 核心验收前提

作业已经公布，学生已按作业原文提交。评分以作业原文为准，以下前提由作业的“交付物”和“验收标准”直接推出：

- 项目能够按照 README 启动。
- 两个模型都至少完成一次真实调用。
- 两个适配器使用的底层 API 协议确实不同。
- 六项功能都有可执行的验证入口和对应证据。

作业原文没有写明的事项，按第 2.1 节的口径判分：学生文档明确、实现一致即可，不额外设置扣分门槛；更完善的做法可写入评语建议。

协议差异应通过实际请求路径与请求体结构、响应及流事件解析确认；鉴权方式不同可作为补充证据，但不是必要条件。不能仅凭模型名称、类名或配置标签判断。

课程逐字稿讲授的双协议组合是 Chat Completions 与 Responses（1.2 节）；作业推荐的 Anthropic Messages 课程未展开。以下组合均视为满足“两种不同 API 协议”：Chat Completions + Responses、Responses + Anthropic Messages、Chat Completions + Anthropic Messages。同一供应商的两种协议即使共用鉴权和 Base URL，只要请求路径与请求体结构不同，也视为不同协议。

允许使用兼容网关，但应能确认学生实现的两个适配器分别发送了两种不同协议的请求。模型别名应记录其实际映射的上游模型。

仅有 Mock 不能证明真实模型接入。仅有截图、README 描述或已有的 passed 报告，也不能替代可复现的运行证据。

如果缺少凭据或上游暂时不可用，应将真实调用标记为“未验证”，说明原因并给出暂评分，不把环境阻塞直接认定为代码缺陷，也不声称真实验收通过。

作业等级统一按 `hw-guide/学员作业反馈报告模板与要求.md` 第二节，只按总分确定：优秀为 80 分及以上，良好为 60 分及以上、低于 80 分，不及格为低于 60 分。本标准不另设分数线，也不因核心前提缺失而改变等级。

验收结论记录在内部评测附件中（见 9.1），不改变作业等级，也不在学员反馈报告中单列：

| 结论 | 判定条件 |
| --- | --- |
| 通过 | 核心前提全部成立，六项功能均有可复现证据，没有需要修复的缺陷。 |
| 通过，需修复 | 核心前提全部成立，六项功能基本可用，但存在需要修复的缺陷。 |
| 证据不完整 | 实现可能存在，但缺少真实调用或某项功能的可复现证据，包括凭据缺失、上游不可用等环境阻塞。给出暂评分和补交要求。 |
| 未通过 | 核心前提不成立，如无法按 README 启动、只实现一种协议或某项功能完全缺失。 |

核心前提缺失或功能未完成时，应在学员反馈报告的“作业不足”中明确说明，并把补交要求写进“改进方案”。作业未公布分数封顶或一票否决规则，本次评分不采用。

### 2.1 作业原文未写明事项的判分口径

以下事项作业原文没有写明或存在多种理解。评分时按下列口径执行，不把作业未要求的做法当作扣分门槛：

- **真实调用证据**：作业验收标准要求“两个模型调用均可正常工作”，因此需要真实调用证据；仅有 Mock、截图或已有测试报告不能替代。
- **“最多 3 次”**：作业未定义是总尝试次数还是重试次数。“总共尝试 3 次”和“首次加重试 3 次”均接受，只要文档明确、实现一致；实际调用超过首次加 3 次（含 SDK 内置重试叠加）才扣分（见 5.4）。
- **按模型限流**：作业原文已明确要求。照搬课程按调用方 API Key 限流的实现不满足本项（见 5.5）。
- **response_format**：作业要求“支持 response_format 约束返回合法 JSON”。这里指统一入口的请求字段，由适配器映射到各协议的实际写法（见 5.2）。
- **缺失模板、版本或变量**：作业未规定具体行为。返回明确错误，或采用文档写明的默认行为均可；只有把未替换的占位符发给模型，或导致未处理的 500 时才扣分。
- **配额恢复**：限流的基本属性，按学生声明的窗口或令牌补充规则检查。
- **失败调用记录**：作业要求“记录每次调用”，失败调用也包括在内。
- **未知 model**：作业要求根据 model 字段路由；静默调用默认模型属于路由错误。
- **截断、incomplete、空正文**：作业未单独要求。仅在结构化输出中把非法、空或截断的 JSON 当作成功返回时扣分（作业要求“合法 JSON”）；其他场景作为评语建议，不扣分。
- **验证脚本**：作业要求“覆盖全部功能点”，按覆盖范围和断言是否有效判分；失败时返回非零退出码作为建议，不单独扣分。

### 3.2 扣分原则

- 对同一根因不重复扣分。一个问题在两个协议、三个输入上复现，不能直接按六个独立缺陷扣分。
- 每次扣分应写明：触发条件、预期结果、实际结果、证据位置和所属评分项。
- 根据影响范围扣分。核心流程不可用的扣分应高于边界输入处理不完善。
- 测试数量不是得分依据。重点检查断言是否验证了行为，而非只验证状态码或函数被调用。
- 不因未采用个人偏好的框架、设计风格或基础设施扣分。
- 超出题目范围的功能可以作为评语中的亮点，不挤占核心要求，也不自动追加分数。
- 测试覆盖不足只有在验证脚本确实缺少必要功能验证时单独扣分；不要因同一业务缺陷缺少回归测试再次机械扣分。

### 4.3 建议边界补测

| 编号 | 输入或场景 | 检查点 |
| --- | --- | --- |
| B01 | 模型内容包含 NaN、Infinity、-Infinity | 提示项：严格 JSON 应拒绝这些非标准常量。课程示例使用的 `json.loads` 和 Pydantic 默认接受它们，课程也未讲授，因此仅写入评语，不扣分；学生明确声明“严格 JSON 校验”时才按声明检查。 |

## 5. 关键判分口径

### 5.1 流式输出

- Content-Type 为 text/event-stream 只能证明格式，不能单独证明增量下发。
- 生成全部完成后再一次性输出多个 SSE 事件，不算完整的流式实现。
- 首内容接收时间小于最终读取完成时间，也不足以单独排除客户端或服务端缓冲。
- 推荐使用门控模拟：先发送内容块，暂不发送终态，确认下游已收到内容后再释放终态。
- 正常结束和异常结束应能区分。传输结束标记不应掩盖此前发生的错误。
- 建议把因长度上限截断（如 `finish_reason=length`、Responses `status=incomplete`、Anthropic `stop_reason=max_tokens`）与正常结束区分开。作业未单独要求，普通流式场景不单独扣分，可写入评语；结构化输出场景按 5.2 处理。

### 5.2 结构化输出

- response_format 指统一入口的请求字段，不要求各协议上游都有同名字段。适配器负责映射：Chat Completions 使用 `response_format`，Responses 使用 `text.format`，Anthropic Messages 等无原生字段的协议可使用提示约束加本地校验。按最终结果判分。
- 上游能力存在差异。例如 DeepSeek Chat Completions 只支持 `json_object`，传入 `json_schema` 会返回 400。上游不支持所请求的格式时，应以统一错误结构返回明确的 4xx（在入口拦截或包装上游 400 均可），或降级为 `json_object` 加本地 Schema 校验；不能绕过统一错误封装直接透传上游响应，也不能变成 500。
- 应检查模型内容本身，而非只检查外层 HTTP 响应是否为 JSON。仅在 Prompt 中要求“返回 JSON”而不做解析校验，不足以证明结构化输出完成；提示约束加本地校验和修复是可接受的实现，最终成功结果必须满足声明的格式。
- 非标准常量（NaN、Infinity）的严格拒绝不作为扣分项，见 B01。
- JSON Schema 不是原题强制要求；学生声明支持时，应验证其承诺的 Schema 能力。原生 Schema 约束与“`json_object` + 本地 Schema 校验”均视为支持。
- 题目没有强制 stream 与 response_format 组合；组合不支持但明确报错，不单独扣分。

### 5.3 Token 与延迟

- 至少记录输入、输出、总 Token；缓存、推理等分类按上游实际提供能力记录。
- 分类可能是总量的子集，不能机械地将所有分类再次相加。
- 流式用量可能是累计快照，不能把每次快照当作新增量累加。
- 不可获得的值应明确表示未知：用 null 表示，或在文档中写明 0 表示“未提供”，二者均可接受（课程 1.6 节示例对流式 Token 暂记为 0）。只有把估算值或 0 当作真实用量呈现时才扣分；估算值应标注为估算。
- 多次尝试产生的已知用量应按声明口径记录；无法确认的失败尝试应标明计量不完整。
- 首 Token 延迟应测到第一个非空有效内容块，不能用连接建立或心跳事件替代。
- 开启 thinking 的模型会先输出推理增量，作业未规定此时的首 Token 口径。以第一个非空正文增量或第一个非空推理增量为准均接受，只要文档写明并保持一致；推荐以正文为准，并另行记录推理首 Token 延迟。
- 非流式通常无法从完整响应反推出首 Token 延迟，允许记录为空。
- 总延迟应覆盖实际请求处理过程，明确是否包含重试等待。
- 不按偶然一次真实调用的速度对学生排名。

### 5.4 重试

- “最多 3 次”可能指总共尝试 3 次，也可能指首次调用外额外重试 3 次。作业未定义口径，两种解释均接受，只要文档明确、实现一致，且实际调用不超过首次加 3 次。课程示例采用总共尝试 3 次（1.2 节“最多三次的临时错误重试”，1.7 节 `max_attempts=3`），可在评语中作为参考。
- 实际调用次数按上游实际收到的请求计算。SDK 内置重试与外层重试叠加（如 OpenAI SDK 默认 `max_retries=2`）导致实际调用超过首次加 3 次时，按次数上限扣分；未超过时可在评语中建议只保留一个重试所有者。
- 实现 fallback 时，次数上限按单个上游计算；跨上游的全局上限建议在文档中写明。
- 可重试范围应合理，例如网络故障、部分上游 5xx 或上游限流；参数错误、鉴权错误通常不应重复请求。
- 指数退避允许抖动和等待上限，应通过可控时间或等待记录验证。课程示例使用全抖动（`random.uniform(0, cap)`），单次等待不一定逐次变长；验证时检查第 n 次重试前的等待不超过 min(cap, base·2^(n-1))，或由学生固定随机种子、注入时钟后验证。
- 收到有效 Retry-After 时，建议尊重该提示；这作为完善程度检查，不临时扩展为原题未公布的强制门槛。
- 已向客户端输出流式内容后，若没有明确恢复机制，不应自动重新生成并造成重复内容。

### 5.5 限流与实现范围

- 必须按公开模型分别计数，不能仅用一个全局桶替代模型限流。课程示例按调用方 API Key 限流，照搬不满足本项；按“调用方 + 模型”组合计数满足要求。
- 本地超限应返回 HTTP 429，而不仅是在 HTTP 200 的正文里写错误。
- F10 只检查网关本地限流。上游返回的 429 可映射为 429 或 503（课程 1.7 节示例映射为 503），只要统一错误结构中的错误码能区分“本地限流”和“上游限流”即可。
- 窗口或令牌应能够恢复，阈值应便于配置和验证。
- 单进程内存限流、文件模板或 SQLite 存储均可满足本周作业。
- 不强制 Redis、分布式限流、独立监控平台、多副本部署或 Docker，除非课程另有明确要求。

## 6. 证据要求

每个功能点建议附以下信息：

```text
功能点：
验证命令或脚本入口：
前置配置：
预期结果：
实际结果：
证据位置：日志 / 脱敏请求响应 / 测试报告
请求关联标识（如有）：
验证方式：真实调用 / 受控模拟
```

真实调用报告应记录模型别名、上游模型、所用协议、请求标识、状态、用量及延迟。

模拟报告应明确标注模拟范围。重试和限流不需要通过压测或故意耗尽真实上游额度来验证。

所有证据应去除 API Key 等凭据。测试报告应能区分“通过”“失败”“跳过”和“未验证”，不能把跳过或缺少密钥视为通过。

## 7. 建议批改流程

1. **固定评测对象**：记录仓库、分支、提交号和评测时间；检查当前修改，避免评测过程中变更学生源码。
2. **验证可启动性**：按 README 准备环境，使用独立配置、数据库和端口；记录必要的环境差异。
3. **运行提交方脚本**：保存退出码及输出，确认断言的实际内容。
4. **运行统一验收**：双模型真实调用验证正常流程；受控模拟验证失败、重试、限流和异常输出。
5. **检查关键源码**：核对协议转换、路由、JSON 校验、Token 口径、重试预算及限流状态。
6. **补充边界验证**：对可疑行为新增最小复现；同一问题确认后，不为增加测试数量重复执行。
7. **按表评分**：为每次扣分写明证据，不用测试通过率直接换算总分。
8. **留存评测附件**：按 9.1 模板记录总分、作业等级、验收结论、已通过项、失败用例、扣分原因和补交要求。
9. **出具学员反馈报告**：按 9.2 从评测附件中挑选重点，生成发给学员的简明报告。

可通过配置降低限流阈值和测试重试等待时间，但不得修改业务逻辑来制造通过结果。正常真实调用宜使用短 Prompt 和合理输出上限，避免不必要的费用。

## 8. 扣分示例

| 问题 | 建议处理 |
| --- | --- |
| 双协议普通调用可用，但模型返回非法 JSON 或截断内容时仍以成功返回 | 从“成功前 JSON 解析校验”子项扣分；例如扣 3 分。 |
| 对 NaN、Infinity 等非标准常量返回成功 | 未声明严格 JSON 校验时不扣分，在评语中提示。 |
| 上游不支持 json_schema，网关未经统一错误封装直接透传上游 400 | 从统一错误处理部分扣分；例如扣 1 分。 |
| SDK 内置重试与外层重试叠加，实际调用超过首次加 3 次 | 从“次数上限与实际尝试计数”扣分；例如扣 2 分。 |
| 已声明支持 Schema，但无法解析的本地引用导致内部 500 | 从统一错误处理部分部分扣分；例如扣 1 分，不再次按同一根因扣结构化输出分。 |
| SSE 事件格式正确，但生成完成后才一次性下发 | 扣除真实增量下发对应分值；保留确已实现的格式、结束等部分分数。 |
| 一个模型触发本地限流后，另一个模型也被同一桶拒绝（含照搬课程按调用方限流的实现） | 按模型独立计数未满足，扣除对应分值。 |
| 没有真实模型证据，只有 Mock 通过 | 标记真实接入未验证；按可确认内容暂评，并要求补交真实调用证据。 |
| 未采用 Redis、JSON Schema 或流式与结构化组合 | 若题目未要求、学生未承诺，不扣分。 |

上述扣分为示例。实际应根据功能影响和作业原文判定，不能机械叠加。

### 9.2 学员反馈报告

发给学员的评语必须按 `hw-guide/学员作业反馈报告模板与要求.md` 的结构、条数、字数和排版要求出具，并通过其第五节的检查。该文件是格式的唯一来源，本节只说明如何从评测附件取材：

- **学员编号与作业等级**：等级按总分确定（见第 2 节），格式为 `作业等级：良好（79分）`。分数与评测附件的合计一致。
- **作业优点**：从评测附件的已通过项中选取，优先选核心功能、真实调用和有效验证。测试通过要写明范围，例如“离线测试通过”不能写成“全部功能通过”。超出作业范围的亮点可以写在这里，但不加分。
- **作业不足**：从待修复问题中按扣分影响排序选取。同一根因合并为一条，与 3.2 的扣分原则一致。验收结论为“证据不完整”或“未通过”时，第一条写明原因。区分“已验证存在缺陷”和“缺少证据、尚未验证”。
- **改进方案**：与不足一一对应，按优先级排列，每条写清要做什么和如何验证完成。补交要求写在这里。
- **评语建议**：本标准中“写入评语”“评语建议”“在评语中提示”等不扣分的事项，只在条数和字数还有余量时，以建议的口吻写进“作业不足”或“改进方案”，排在扣分问题之后，并注明不影响得分。
- **不写入报告的内容**：评分明细表、验收结论标签、测试日志、复现命令、内部判分口径和任何凭据。这些内容留在评测附件中。
