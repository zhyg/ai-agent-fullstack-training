# 第一周作业评分标准：LLM 统一模型调用服务

版本：1.0  
整理日期：2026-11-07  
满分：100 分

## 1. 适用范围与评测目标

本标准用于批改“AI Agent 全栈工程师训练营”第一周作业。

评测目标是确认：学生实现了统一模型调用服务，通过适配器封装至少两种不同 API 协议，并使流式输出、结构化输出、提示词版本管理、可观测性、重试和按模型独立限流具备可验证的运行证据。

采用以下方式评测：

1. 阅读源码、配置、README 和学生提交的证据。
2. 使用教师统一验收脚本运行正常流程与异常流程。
3. 使用真实模型调用证明协议接入，使用受控模拟证明重试、限流等异常处理。
4. 人工检查关键实现，并将每次扣分关联到可复现的用例。

本标准不限定开发语言、框架、数据库或具体模型品牌。推荐模型组合是参考方案，学生可使用其他模型，但必须满足两种不同 API 协议的训练目标。

## 2. 核心验收前提

以下内容应在布置作业时提前向学生公布：

- 项目能够按照 README 启动。
- 两个模型都至少完成一次真实调用。
- 两个适配器使用的底层 API 协议确实不同。
- 六项功能都有可执行的验证入口和对应证据。

协议差异应通过实际请求路径、鉴权、请求体与响应解析确认。不能仅凭模型名称、类名或配置标签判断。

允许使用兼容网关，但应能确认学生实现的两个适配器分别发送了两种不同协议的请求。模型别名应记录其实际映射的上游模型。

仅有 Mock 不能证明真实模型接入。仅有截图、README 描述或已有的 passed 报告，也不能替代可复现的运行证据。

如果缺少凭据或上游暂时不可用，应将真实调用标记为“未验证”，说明原因并给出暂评分，不把环境阻塞直接认定为代码缺陷，也不声称真实验收通过。

若核心前提成立、六项功能基本可用，但存在边界缺陷，可以判为“通过，需修复”。核心前提缺失时，应标记“证据不完整”或“未通过”，并列出补交要求。本标准不额外规定分数封顶或一票否决规则；课程如需采用，应提前公布。

### 3.2 扣分原则

- 对同一根因不重复扣分。一个问题在两个协议、三个输入上复现，不能直接按六个独立缺陷扣分。
- 每次扣分应写明：触发条件、预期结果、实际结果、证据位置和所属评分项。
- 根据影响范围扣分。核心流程不可用的扣分应高于边界输入处理不完善。
- 测试数量不是得分依据。重点检查断言是否验证了行为，而非只验证状态码或函数被调用。
- 不因未采用个人偏好的框架、设计风格或基础设施扣分。
- 超出题目范围的功能可以作为评语中的亮点，不挤占核心要求，也不自动追加分数。
- 测试覆盖不足只有在验证脚本确实缺少必要功能验证时单独扣分；不要因同一业务缺陷缺少回归测试再次机械扣分。

## 4. 统一验收用例

### 4.1 启动与双协议接入

| 编号 | 操作 | 通过标准 |
| --- | --- | --- |
| A01 | 从干净环境按 README 安装依赖、配置和启动 | 服务可启动；不依赖学生本机隐藏文件或未说明的配置。 |
| A02 | 同一接口分别传入两个模型 | 两个模型均完成真实调用，响应符合统一结构。 |
| A03 | 检查两个适配器的上游请求 | 路径、鉴权、请求体和响应解析能够证明两种协议确实不同。 |
| A04 | 传入不存在的 model | 返回明确的统一错误，不静默调用默认模型。 |

### 4.2 六项功能

| 编号 | 功能 | 操作 | 通过标准 |
| --- | --- | --- | --- |
| F01 | 流式 | 两个模型分别请求 stream=true，记录接收时间 | 以 SSE 返回有效内容块，内容在生成结束前到达，有明确结束信号。 |
| F02 | 流式 | 模拟文本输出后的断流或错误事件 | 客户端能识别失败；不会从头重试而重复已输出内容。 |
| F03 | 结构化 | 两个模型分别请求 JSON，严格解析模型内容 | 输出为合法 JSON；若声明支持 Schema，再验证字段与类型。 |
| F04 | 结构化 | 模拟非法 JSON、格式不符和修复后仍不合法 | 不以成功结果返回非法内容；允许修复，但修复后必须重新校验。 |
| F05 | 模板 | 同一模板发布 v1、v2，分别渲染并显式引用 | 变量替换正确；更新后仍可引用 v1；指定版本实际进入模型请求。 |
| F06 | 模板 | 引用不存在的模板或版本，遗漏必要变量 | 返回明确错误，不将未替换的占位符直接发送给模型。 |
| F07 | 可观测 | 执行普通、流式及失败调用，查询日志或账本 | 可关联请求；状态、用量和延迟准确；失败也有记录。 |
| F08 | 重试 | 模拟上游前两次可重试失败，随后成功 | 调用次数符合配置，等待时间符合指数退避，最终成功。 |
| F09 | 重试 | 模拟持续失败和不可重试错误 | 持续失败达到次数上限后停止；不可重试错误不重复请求。 |
| F10 | 限流 | 降低模型 A 配额并耗尽，再调用模型 B | A 返回 HTTP 429；B 仍有独立配额并能正常调用。 |
| F11 | 限流 | 等待限流窗口或令牌补充后再次调用 | 配额按实现声明恢复，请求可重新通过。 |
| F12 | 验证脚本 | 运行学生提交的验证脚本，并制造一项失败 | 脚本覆盖全部功能；失败有清晰输出并返回非零退出码。 |

### 4.3 建议边界补测

| 编号 | 输入或场景 | 检查点 |
| --- | --- | --- |
| B01 | 模型内容包含 NaN、Infinity、-Infinity | 严格 JSON 校验应拒绝这些非标准常量，不能返回成功。 |
| B02 | Schema 本地引用指向不存在的定义 | 如声明支持 Schema，应尽早返回明确的入参错误，避免误报 500。 |
| B03 | 正常的 Schema 本地引用 | 作为 B02 的对照，避免通过禁用所有本地引用绕过问题。 |
| B04 | SSE 心跳、元数据、空增量、UTF-8 跨块分片 | 不把心跳当首 Token；文本完整；分片不导致解码错误。 |
| B05 | SSE 没有成功终态、被截断或客户端断开 | 正确记录失败或取消，并释放上游连接。 |
| B06 | 重试和结构修复组合 | 实际尝试次数不绕过文档声明的全局调用预算。 |
| B07 | 上游缺失用量或只提供部分分类 | 不编造数据；明确未知值或不完整状态。 |

边界用例用于验证已承诺的能力。题目没有要求且学生也未声明支持的扩展能力，不因该扩展缺失扣分。

## 5. 关键判分口径

### 5.1 流式输出

- Content-Type 为 text/event-stream 只能证明格式，不能单独证明增量下发。
- 生成全部完成后再一次性输出多个 SSE 事件，不算完整的流式实现。
- 首内容接收时间小于最终读取完成时间，也不足以单独排除客户端或服务端缓冲。
- 推荐使用门控模拟：先发送内容块，暂不发送终态，确认下游已收到内容后再释放终态。
- 正常结束和异常结束应能区分。传输结束标记不应掩盖此前发生的错误。

### 5.2 结构化输出

- 只在 Prompt 中写“请返回 JSON”不足以证明结构化输出完成。
- 应检查模型内容本身，而非只检查外层 HTTP 响应是否为 JSON。
- 可以使用上游原生约束，也可以结合提示约束、本地校验和修复；最终成功结果必须满足声明的格式。
- 解析器应采用严格 JSON 口径；特别检查某些语言默认接受的非标准数字常量。
- JSON Schema 不是原题强制要求；学生声明支持时，应验证其承诺的 Schema 能力。
- 题目没有强制 stream 与 response_format 组合；组合不支持但明确报错，不单独扣分。

### 5.3 Token 与延迟

- 至少记录输入、输出、总 Token；缓存、推理等分类按上游实际提供能力记录。
- 分类可能是总量的子集，不能机械地将所有分类再次相加。
- 流式用量可能是累计快照，不能把每次快照当作新增量累加。
- 不可获得的值应明确表示未知；估算值应标注为估算，不得冒充真实用量。
- 多次尝试产生的已知用量应按声明口径记录；无法确认的失败尝试应标明计量不完整。
- 首 Token 延迟应测到第一个非空有效内容块，不能用连接建立或心跳事件替代。
- 非流式通常无法从完整响应反推出首 Token 延迟，允许记录为空。
- 总延迟应覆盖实际请求处理过程，明确是否包含重试等待。
- 不按偶然一次真实调用的速度对学生排名。

### 5.4 重试

- “最多 3 次”可能指总共尝试 3 次，也可能指首次调用外额外重试 3 次。
- 课程应提前统一口径。未提前说明时，接受学生文档明确、实现一致且不超过首次加 3 次的解释。
- 可重试范围应合理，例如网络故障、部分上游 5xx 或上游限流；参数错误、鉴权错误通常不应重复请求。
- 指数退避允许抖动和等待上限，应通过可控时间或等待记录验证。
- 收到有效 Retry-After 时，建议尊重该提示；这作为完善程度检查，不临时扩展为原题未公布的强制门槛。
- 已向客户端输出流式内容后，若没有明确恢复机制，不应自动重新生成并造成重复内容。

### 5.5 限流与实现范围

- 必须按公开模型分别计数，不能仅用一个全局桶替代模型限流。
- 超限应返回 HTTP 429，而不仅是在 HTTP 200 的正文里写错误。
- 窗口或令牌应能够恢复，阈值应便于配置和验证。
- 单进程内存限流、文件模板或 SQLite 存储均可满足本周作业。
- 不强制 Redis、分布式限流、独立监控平台、多副本部署或 Docker，除非课程另有明确要求。

每个功能点建议附以下信息：

```text

```

真实调用报告应记录模型别名、上游模型、所用协议、请求标识、状态、用量及延迟。

模拟报告应明确标注模拟范围。重试和限流不需要通过压测或故意耗尽真实上游额度来验证。

所有证据应去除 API Key 等凭据。测试报告应能区分“通过”“失败”“跳过”和“未验证”，不能把跳过或缺少密钥视为通过。

## 7. 建议批改流程

1. **固定评测对象**：记录仓库、分支、提交号和评测时间；检查当前修改，避免评测过程中变更学生源码。
2. **验证可启动性**：按 README 准备环境，使用独立配置、数据库和端口；记录必要的环境差异。
3. **运行提交方脚本**：保存退出码及输出，确认断言的实际内容。
4. **运行统一验收**：双模型真实调用验证正常流程；受控模拟验证失败、重试、限流和异常输出。
5. **检查关键源码**：核对协议转换、路由、JSON 校验、Token 口径、重试预算及限流状态。
6. **补充边界验证**：对可疑行为新增最小复现；同一问题确认后，不为增加测试数量重复执行。
7. **按表评分**：为每次扣分写明证据，不用测试通过率直接换算总分。
8. **输出反馈**：给出总分、验收结论、已通过项、失败用例、扣分原因和补交要求。

可通过配置降低限流阈值和测试重试等待时间，但不得修改业务逻辑来制造通过结果。正常真实调用宜使用短 Prompt 和合理输出上限，避免不必要的费用。

## 8. 扣分示例

| 问题 | 建议处理 |
| --- | --- |
| 双协议普通调用可用，但对非法 JSON 常量返回成功 | 从结构化输出的严格合法性部分扣分；例如扣 3 分。 |
| 已声明支持 Schema，但无法解析的本地引用导致内部 500 | 从统一错误处理部分部分扣分；例如扣 1 分，不再次按同一根因扣结构化输出分。 |
| SSE 事件格式正确，但生成完成后才一次性下发 | 扣除真实增量下发对应分值；保留确已实现的格式、结束等部分分数。 |
| 一个模型触发本地限流后，另一个模型也被同一桶拒绝 | 按模型独立计数未满足，扣除对应分值。 |
| 没有真实模型证据，只有 Mock 通过 | 标记真实接入未验证；按可确认内容暂评，并要求补交真实调用证据。 |
| 未采用 Redis、JSON Schema 或流式与结构化组合 | 若题目未要求、学生未承诺，不扣分。 |

上述扣分为示例。实际应根据功能影响和已公布的课程政策判定，不能机械叠加。
