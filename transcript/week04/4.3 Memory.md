# **4\.3 Memory 体系：从当前会话走向长期记忆 v2**

大家好。上一节，我们讲了工作记忆。



在“登录会话修复”这个任务里，Agent 先读源码，再修改比较条件，最后运行测试。**工作记忆**会把每一步的实际结果整理成当前记录，**每一轮，程序都会把这些记录交给上下文装配器。**这样，模型才知道：这一次，到底该改代码，还是该验证修改后的代码。



这一节，我们再把视角往后延伸一步：**任务结束以后，哪些信息还能在下次任务中继续使用？**



还是这个项目，几天以后，用户新开一个会话，要求 Agent 增加“退出登录”功能。



上次任务里的“正在准备补丁”，现在已经没用了。但会话模块在哪里、该运行哪个测试命令、项目要求怎么处理过期会话，这些信息仍然有用。**如果不保留，Agent 就得重新搜索，用户也可能需要再次说明项目要求。**



如果把这些信息按项目保存下来，新任务开始时，程序就能读取相关记录，加入模型输入。Agent 就能据此找到会话模块，核对当前代码，再按项目约定实现退出登录，最后运行记录里写明的测试命令。



**这种跨会话、跨任务保存并复用信息的能力，就是长期记忆。**



今天，我们沿着一条流程来讲：

1. 先选出值得保存的信息；

2. 再用 OKF 把知识组织成文件，用 pi\-okf  插件创建和维护这些文件；

3. 接着用 pi\-okf 演示模型怎样调用工具保存、召回和撤回记忆；

4. 最后讨论当前任务丢失上下文以后怎样恢复。



学完这一节，你至少应该能说明三件事：什么信息值得记；pi 怎样把它写成项目知识；下一次使用前，怎样判断这些知识是否仍然适用。



## 区分短期记忆和长期记忆

### 1\.1 当前任务需要什么，就放进短期记忆

先回到上一节的“登录会话修复”。



用户要求：会话恰好到期时，应该返回无效。Agent 跑边界测试，发现预期是 False，实际却是 True。于是它准备把 `now <= expires_at` 改成 `now < expires_at`。



在修复过程中，失败断言、补丁状态、待运行的测试，都得保留。否则下一轮只收到一句"继续"，模型根本不知道代码到底改了没有。



**这些围绕当前会话、当前任务保存的信息，就是短期记忆。**上一节讲的工作记忆，是其中按目标、进度、关键结果和未解决问题组织起来的部分。



注意，**这里的“短期”说的是使用范围**，不是说只能放在内存里。一个任务要做两天，程序也可以把工作记忆存进文件或数据库，第二天再读。它保存得久，但主要用途仍然是完成这一个任务。



### 1\.2 下次任务还需要什么，才考虑长期保存

现在假设修复已经结束。



我们回头检查这次任务产生的信息。会话模块在 `app/session.py`，下次增加退出登录功能还会用到；会话测试在 `tests/test_session.py`，验证相关功能时还会用到；项目约定“到期时刻必须视为无效”，实现其他接口时也要遵守。



**这三条信息，就可以进入长期记忆。**



但像“补丁准备到一半”“刚才搜索了三次”，通常不值得变成长期项目知识。它们可以留在执行日志里，用来排查这次任务，但不需要反复发给以后的任务。



我们可以用一张表，把区别看清楚。

短期记忆服务于当前任务，任务结束就不再需要；长期记忆服务于以后的任务，所以必须能核对来源。而同一个测试命令，可能两边都用：这一次跑它是为了验证补丁，下一次跑它是为了确认环境没变。



### 1\.3 长期保存不等于修改模型

所以我们说的，Agent “记住了项目”，并不是它修改了自己的模型参数。更准确地说，是程序把外部记录检索出来，再放进下一次模型输入。



这一点决定了后面所有事情的做法：既然记忆在模型外面，那它就得像代码一样被写、被读、被检查、被更新。接下来，我们就来判断：哪些信息，才值得长期保留。

## 长期记忆保存什么，怎样维护（生命周期）

**一次任务产生了很多信息。我们要选出以后有用的内容，保存下来；以后读取时判断能不能用；内容变化或出错后，再更新、停用或删除。**



所以，这一节的两个重点分别是：

- **保存什么**：决定哪些信息可以进入长期记忆，以及以什么性质保存。

- **怎样维护**：保证保存的内容在后续任务中仍然适用，避免错误或过期信息继续影响执行。

我将维护分成五个部分：筛选、记录、使用、冲突处理、失效处理，它们分别承担下面的作用。



### 2\.1 保存什么：筛选后续任务仍然有用的信息

假设这次会话修复，产生了三句话。

1. 第一句：“会话逻辑在 app/session\.py，对应测试在 tests/test\_session\.py。” \-\- 这条已经通过读取文件确认过，是一条以后仍然有用的项目事实。

2. 第二句：“我猜退出登录的问题，可能和缓存有关。”这只是模型的推断。\-\-以后可以拿它当检查线索，但不能把它存成"退出登录故障由缓存导致"。

3. 第三句：“这次为了排查问题，临时加了一个打印。”\-\- 这个打印已经删掉，也没有形成可复用的经验，不需要写入项目长期记忆。



所以，写入之前，先问三件事：**以后哪类任务会用到它？它的来源能不能核对？它在什么条件下会失效？**



三个问题都答得上来，再保存。答不上来，就先留在本次日志里。



另外，登录令牌、密码和完整用户请求载荷都不保存。这个案例真正值得留下的，是模块位置、项目规则和修复经验，不是任务里碰巧读到的凭证。



登录修复结束了，我们先选出后续任务还会使用的信息。这一步解决的是"长期记忆保存什么"。



### 2\.2 保存时记录什么：区分要求、事实和推断，附上来源

选出了内容，接下来给每条记录标明来源性质。这一节把信息分成四类。

- **要求**：项目或维护者明确规定的做法。比如"到期时刻必须视为无效"、"不要修改测试"。这类信息下一次要遵守。

- **事实**：实际读取或运行确认过的状态。比如"会话逻辑在 `app/session.py`，已打开文件确认过"。这类信息下一次可以直接用，但要标明是在哪个版本上确认的。

- **推断**：还没有验证的猜测。比如"退出登录失败可能和缓存有关"，或者用户说"文件应该在 session 目录"。这类信息只能当排查线索，用之前必须核对。

- **证据**：支撑上面三类判断的原始材料，比如测试回执、命令输出、文件哈希。



再比如，用户要求“不要修改测试”，这是约束；用户说“文件应该在 session 目录”，这仍然只是待核对的线索。



记录时还要说明适用项目、来源和检查时间。涉及执行事实时，补充代码版本或文件哈希，让下一次任务知道这条事实是在哪个现场验证的。



选出的内容不能只保存一句结论，还要说明它是要求、验证事实还是推断。这样，下一次读取时才能决定：应该遵守、重新核对，还是仅作为排查线索。



### 2\.3 保存后怎样使用和维护：让记忆持续服务后续任务

前面选出了值得保存的信息，也标明了它们的来源。接下来要解决的是：**怎样让这些信息在后续任务中找得到、用得上，并在内容变化以后得到修正。**



还是登录会话项目。修复完成以后，我们决定保留会话模块的位置和测试入口，因为以后修改登录相关功能，还需要找到代码并验证改动。



**输入**是这次修复留下的两条结论；

**动作**是把它们连同适用项目、来源和检查时间一起写入；

**结果**是知识文件里多了两条带来源的记录。

留下来的不仅是一个文件路径或一条命令，还有判断它是否适用所需要的信息。



几天后，用户要求增加退出登录功能。这个新任务需要知道：会话逻辑在哪里，修改以后怎样测试。



**输入**是"退出登录"这个新任务加上当前项目标识；

**动作**是程序按项目和任务检索相关记忆；

**结果**是模块位置和测试入口两条记录进入这一轮的模型输入。



模型拿到这两条，先打开 `app/session.py` 看比较运算符，再打开测试文件看边界用例有没有覆盖 `now == expires_at`，然后才开始实现功能。这时记忆才起作用：模型拿到的是能直接打开的文件路径和能直接运行的命令，而不是一段描述。用户也不用再重复说一遍测试命令是什么。



但项目会变化。假设会话测试已经从 `tests/test_session.py` 移到了 `tests/auth/test_session.py`，旧命令就不能继续作为当前入口。



这时，需要找到原来的测试入口记录，依据当前文件位置和实际运行结果，更新命令、来源和检查时间。否则，下一次任务读到的仍是旧命令，运行一个已经不存在的测试文件，命令直接报错，模型还得回头重新找。



如果某条记录本来就写错了，而且没有保留价值，就要删除。例如，Agent 曾把未经验证的判断写成"退出登录失败是缓存导致的"。后来调查证明原因不在缓存，就不能让这条错误结论继续作为排查依据。



更新和删除以前，都要确认记录属于当前项目，并定位到准确的记录 ID 或文件路径。搜索可以帮助找到候选，但不能因为两条内容相似，就直接覆盖或删除其中一条。



所以，这四个动作各管一段：**写入**，让有用信息留下来；**检索**，让它进入需要它的任务；**更新**，让它跟上项目变化；**删除**，让错误或不该保留的信息不再被读到。



长期记忆是否有用，要看下一次任务能否取得适用的信息，并根据它找到代码、遵守约定和完成验证。



### 2\.4 更新依据是什么：新旧记录冲突时，先核对范围，再核对来源

现在，让这个项目再发生一个变化。



旧记忆写着："会话测试使用 `pytest tests/test_session.py -q`。"新工程的说明要求使用 `python -m pytest tests/test_session.py -q`。



两条命令都可能有效，只是入口约定发生了变化。我们要读取当前项目说明，核对这次任务使用的环境，再决定把哪一条设为当前项目的测试入口。



不能因为新消息时间更晚，就自动删除旧记录。新消息可能只是模型建议，也可能针对另一个分支。



我们的处理顺序是：先确认是不是同一项目、同一规则、同一环境；再比较来源；最后更新当前记录。如果两个来源同样可靠，内容却互相矛盾，那就先查配置，或者询问维护者，不能替用户编一个结论。



对于编码规范这类要求，维护者明确发布的新规定，可以替换旧规定。对于"命令运行成功"这类事实，新版本的真实执行结果，更有说服力。



**一句话：要求，要看谁有权提出；事实，要看证据是否适用。**



更新经常会遇到新旧内容不一致。先核对适用范围和来源，再决定替换哪部分，避免把错误信息写成当前结论。



### 2\.5 失效以后怎样处理：过期、废弃和删除，解决不同问题

再看历史故障经验。



我们保存这样一条："旧版本的到期判断使用了小于等于，导致到期时仍然有效；修复为小于以后，相关边界测试通过。"



这个经验，依然有教学和排查价值。但其中"当前代码使用小于等于"这个状态，已经不能用于新版本。



所以，可以保留历史经验，同时明确适用版本；把旧代码状态标记为历史信息。过期，意味着不能再作为当前事实使用，不一定意味着必须把历史记录全部删除。



删除，则是移除记录。删除接口处理对应的活动记忆，缓存与备份如何清除，还要另行定义。



内容不再适用以后，判断它还有没有历史价值。有价值就保留并明确失效范围；不该保留就删除，防止它继续进入后续任务的输入。



到这里，我们已经知道什么值得记录，也知道如何判断一条记录是否可用。接下来，讨论存储与检索如何组织这些记录。

## 用 OKF 组织项目知识，用 pi 插件维护和复用

### 3\.1 为什么要约定统一格式

假设我们把登录规则写在一个笔记里，把测试入口写在另一个临时文件里，历史修复经验又藏在聊天记录中。



下一次任务开始时，Agent 打开这个项目，不知道一共有哪些记录，也不知道哪一条是当前规则、哪一条是旧判断。它只能重新翻一遍这些文件，或者干脆问用户。



OKF，也就是 Open Knowledge Format，提供一组文件组织约定：知识正文使用 Markdown，文件顶部使用 YAML 记录元数据，相关知识通过链接连接。



官方 v0\.2 规范把一个知识包定义为 Markdown 目录树。每个概念文件有 YAML 头信息，`type` 是始终必填的字段；`index.md` 和 `log.md` 分别用于目录与更新历史。



课堂统一把知识包放在项目的 `~/.pi/agent/okf-memory` 下。这是我们的路径约定，OKF 不强制所有项目使用这个名字。





这样组织以后，工作的顺序就变成：先读目录，知道有哪些记录；再打开当前任务需要的那几个文件。不用把整套知识一次性塞进模型输入。



### 3\.2 为什么长期记忆不等于向量数据库

前面说长期记忆要保存后续任务仍然有用的信息，还要说明来源和适用范围。现在来看 pi\-okf\-memory 在实际会话中生成的一份文件。



这份记忆记录了两项内容：会话判断在哪里实现，以及教学项目要求怎样处理到期边界。下一次修改登录功能时，Agent 可以先从这里找到源码入口，再核对实现是否满足规则。



看这份文件时，重点观察三处：顶部记录了什么元数据；正文保存了哪些可复用信息；哪些内容仍然需要核对。

```YAML
---
type: Fact
title: "登录会话模块：会话判断位置与到期边界规则"
description: "- 会话判断（会话有效性校验）的实现在 `app/session.py`。"
tags: [session, auth, 登录, 边界条件, 教学示例]
timestamp: 2026-10-06T07:48:49.407Z
source: session
---

# 位置

- 会话判断（会话有效性校验）的实现在 `app/session.py`。
- 使用者给出的记忆入口路径为 `../../app/session.py`（相对当前工作目录 `okf-memory/fact` 解析后未找到该文件，故实际路径以项目根目录下的 `app/session.py` 为准）。
- 使用前必须核对当前源码，不要凭记忆推断实现细节。

# 到期边界规则

- 项目（教学任务）规则：**`now == expires_at` 时，会话必须无效**。
- 即边界取闭区间失效：`now >= expires_at` → 无效；有效条件应写作 `now < expires_at`。
- 这条规则的适用范围仅限**本节登录示例**，不要推广到其他模块或全局。

# 核对清单

1. 打开 `app/session.py`，确认判断条件的比较运算符（`<` 还是 `<=`）。
2. 确认边界测试是否覆盖 `now == expires_at` 这一用例。
3. 如果模块路径或实现描述已经变化，核对后更新记忆；如果当前实现不满足“恰好到期时无效”的项目要求，先用边界测试确认问题，再修复代码。只有项目要求正式变更，才更新对应规则。
```



先看顶部。

`type: Fact` 表示插件把它归为事实类记忆；`title` 和 `description` 帮助 Agent 判断这条记录是否与当前任务有关；`tags` 提供检索线索；`timestamp` 记录时间；`source: session` 表示内容来自会话。

**这些字段说明记录怎样被组织，但不能单独证明内容已经验证。**例如，`source: session` 没有告诉我们模块位置是用户提供的，还是 Agent 读取源码后确认的；时间戳也不能当成测试执行时间。

这里还有一处需要留意：`description` 直接写"实现在 `app/session.py`"，语气是确定的。但正文承认按相对路径没有找到文件。同一份文件里，摘要比正文更肯定——这是元数据和正文不一致的信号。遇到这种情况，以正文的核对清单为准，把摘要当成线索。



再看正文。

"位置"这一部分，给下一次任务提供了源码入口。不过，文件里也明确写着：按给出的相对路径没有找到源码。因此，这里的 `app/session.py` 应先作为待核对的定位线索，不能因为已经写进记忆，就认定文件一定存在。

"到期边界规则"这一部分，保存的是教学任务的要求：恰好到期时，会话必须无效。它还限定了适用范围，避免后续 Agent 把这条要求推广到其他模块。

所以，虽然整份文件被标为 Fact，正文实际上包含了不同性质的信息：模块位置需要核对，到期规则属于项目要求。使用时，仍然要分别判断。



最后看核对清单。前两项把后续动作写得很具体：读取源码，检查比较条件，再检查边界测试。



回到"增加退出登录"任务，这份记忆的作用就清楚了：先帮助 Agent 找到会话代码和边界要求，再指导它读取源码、检查测试。它保存了可复用的知识和核对步骤，但没有证明当前实现正确，也没有证明测试已经通过。



### 3\.3 安装与命令：终端和 pi 会话要分清楚

先说一个容易踩的坑：插件的安装和知识库的创建，发生在两个不同的地方。

`pi install` 是给 pi 这个程序装能力，必须在终端里执行，此时还没有会话，所以不能用斜杠命令。`/okf-init` 是在会话里让模型读源码、建知识文件。分清楚这一点，后面的命令才不会敲错地方。

先在终端装插件：

```Shell
pi install npm:pi-okf@0.4.0
```

### 3\.4 演示一：建立知识，再从新会话读取

**输入**是当前项目文件夹。这个项目的登录代码统一放在 `login_demo` 文件夹。

在 pi 会话里输入：

```Shell

/okf-init
```

执行结束后，先看文件清单。打开根目录索引，再打开会话和测试相关概念。如果实际文件名与讲义不同，就记下真实路径，后续使用这些路径。



接着运行：

```Shell

```

这条命令的回执会列出检查结果。有错误就修正文档，再校验一次。回执里没有格式错误，说明知识包的结构满足检查要求。



现在关闭这个 pi 会话，再在同一个项目启动新会话，输入：

```Shell

```

我们要看实际读取过程，不能只看回答中出现了熟悉的文件名。

### 3\.6 手动与自动修改记忆

手动修改的话，可以通过斜杠命令实现：



日常对话由模型调用下面六个工具。它们是工具名称，不是让用户在终端输入的命令。



**"自动记住"具体怎样发生呢？**这里先把“自动”说清楚。



适配层在会话启动时准备记忆库和目录摘要，在 `before_agent_start` 时把记忆纪律、目录摘要和读取指引加入系统提示。



模型看到这些指引，再结合用户消息决定是否调用工具。遇到新背景、稳定偏好、明确决策或用户纠正时，指引要求它先搜索，避免重复，然后调用 `okf_remember`。



用户下一次提出相关问题，模型再调用 `okf_search` 找候选，用 `okf_read` 读全文。知识通过工具结果进入模型上下文。



所以，它能减少用户手动输入维护命令，但不是后台把每轮对话无条件保存，也不是每次任务都确定性地注入全部记忆。是否实际调用工具，要看执行记录。



还有一点：返回摘要也不等于已经读取全文。重要规则不能只靠模型自觉搜索，正式 Harness 仍然要精确加载必要约束。



如何直观看到当前的记录呢？运行：

```Plain Text
/okf graph
```

在 macOS 上，这条命令执行完会自动用系统的 `open` 命令打开生成的 HTML。如果你在 Windows 或 Linux 上，终端不会自动弹窗，这时候去看命令回执里给出的路径，手动打开那个文件。



需要建立关联时，让 Agent 使用实际概念 ID 填入 `related`，再检查图谱边。图谱显示关联，不代表关联已证明因果。



最后记住三个边界：两套插件当前声明的 OKF 版本不同，不直接混写；项目隔离依靠正确根目录，不只靠标签；自动记忆仍受模型调用、去重和文件读写结果影响，必须核对回执。



到这里，我们完成了跨任务知识复用。讲完了怎么保存和复用，下一个问题是：这些做法各自要付什么代价、该选哪一种。

## 记忆策略怎样比较：成功率、成本与延迟

### 4\.1 四种策略，解决的问题不一样

我们仍然用“退出登录”这个任务，来做比较。

4. **第一种，无记忆。**新任务只收到当前要求，Agent 重新搜索目录、检查配置、询问约定。实现最简单，也没有记忆检索成本，但可能增加重复的工具调用。

5. **第二种，完整历史。**把之前的消息全部发送给模型。它保留了很多细节，但也包含旧计划、失败尝试，以及已经失效的状态。历史越长，输入越多，还可能超过上下文预算。

6. **第三种，摘要记忆。**用一小段文字，交接目标、约束和进度。输入更集中，但摘要如果漏掉"不得修改测试"，后续模型就可能失去这条限制，直接改动测试文件来让结果通过。

7. **第四种，按需检索。**先根据当前任务，查询相关项目知识，再把少量结果加入输入。它可以控制输入规模，但要支付查询和维护成本，也可能漏掉某条本来该用的规则，模型就按默认做法执行了。

这四种都是可能出现的效果，不是这个项目已经测出的结果。不能看到使用 pi\-okf，就提前宣布成功率一定提高、延迟一定降低。



这张表里没有"哪个最好"。选哪种，取决于你的任务更怕什么：怕重复搜索，就用检索；怕丢约束，就别用纯摘要。



### 4\.2 本项目先使用组合方案

对这个 Codebase Agent，我会先采用组合方案。



当前任务的目标、约束、进度，通过结构化工作记忆和 Checkpoint 精确恢复。必须遵守的项目约定，按项目读取，并交给执行层检查。模块线索和历史故障经验，通过 pi\-okf 按需检索。



完整工具日志，留在执行记录里。模型需要查看堆栈或补丁细节时，再通过引用读取。



这样做的原因是：任务状态要求精确，相关经验允许先返回候选，原始日志又需要能够追溯。



分开做以后，三种信息各有各的入口：任务状态走 Checkpoint——程序知道第 3 步做完了、第 4 步没做；经验走检索——允许先返回候选，模型再核对；原始日志走引用——需要看堆栈时才读。三种信息混在一起检索，模型就分不清哪条是必须遵守的约束、哪条只是可以试试的线索。

## 小结：把有用的信息留下，把当前状态核对清楚

这节课，我们把任务中的信息分成了两种用途。



目标、进度和执行回执，帮助完成这一次任务。模块位置、项目规则和经过核验的经验，帮助以后相关任务减少重复调查——不用再搜索一遍目录，也不用再问用户测试命令是什么。



OKF 把后一类信息组织成可以阅读和修改的文件。pi\-okf 帮助 pi 根据项目证据创建和维护这些文件；pi\-okf\-memory 让模型在对话里通过工具保存和召回记忆。新任务还需要实际读取，并核对当前源码。



当前任务失去上下文时，摘要帮助模型理解进度；Checkpoint 和工具回执帮助程序判断动作是否完成；当前现场决定旧结果是否仍然有效。



下一节讲 RAG。我们会在知识来源清楚的基础上，进一步讨论资料变多以后怎样检索、怎样选择证据，以及怎样检查回答是否受到证据支持。
