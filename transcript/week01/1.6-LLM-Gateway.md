# 1.6 LLM Gateway：把模型调用收口成 Agent 的统一入口

## 一、学习目标

完成本节后，学员应当能够：

1. 说明 Agent 项目为什么需要独立的 LLM Gateway；
2. 使用 FastAPI 和 Pydantic 定义统一的模型调用入口与出口；
3. 使用 Provider Adapter 隔离 OpenAI Compatible 模型的地址、认证和调用细节；
4. 在 Gateway 中统一处理 Prompt 模板、Structured Output 和 Streaming；
5. 区分可重试错误与不可重试错误，实现有限重试和备用模型 fallback；
6. 记录模型、Prompt 版本、Token、Cost、Latency 和调用状态。

本节不要求从零搭建完整模型中台，而是围绕一个可以运行的 `gateway.py`，理解 Agent 开发工程师需要亲自确定的服务边界。

---

## 二、前面已经学会调用模型，为什么还要增加 LLM Gateway？

前面几节已经解决了单次模型调用中的关键问题：Streaming 让用户提前看到结果；Prompt Engineering 约束模型行为；Structured Output 把模型输出变成可以校验的对象。

但在真实 Agent 项目里，模型调用不会只出现一次：Planning 调用模型拆解任务，Agent Loop 调用模型决定下一步动作，RAG 调用模型整理检索结果，Eval 还会再次调用模型评价任务结果。

如果每个组件都直接调用模型，就要分别管理 API Key、Base URL、请求格式、流式响应、重试和日志。切换模型时，修改会扩散到整个项目。

所以这一节先给出结论：

> LLM Gateway 的价值不是多转发一次 HTTP，而是把模型调用规则集中到一个可治理的边界中。

在当前实现中，完整链路是：

```text
Agent / RAG / Planning
        ↓ 统一请求
FastAPI LLM Gateway
        ├─ Pydantic 入口校验
        ├─ Prompt 模板渲染
        ├─ 模型白名单与能力校验
        ├─ OpenAI Compatible Provider
        ├─ 重试与备用模型 fallback
        ├─ Structured Output 出口校验
        └─ Token / Cost / Latency Trace
```

模型只负责生成候选结果。工程师必须亲自决定：允许哪些模型、请求协议是什么、模板怎样发布、哪些错误可以重试、备用模型是否能力等价、失败后向上层返回什么。

|角色|负责什么|不负责什么|
|---|---|---|
|模型|根据输入生成文本或 JSON|决定平台的重试与成本预算|
|LLM Gateway|统一调用、校验、重试、fallback 和留痕|规划整个 Agent 任务|
|Agent Loop / Harness|维护任务状态、调用工具、判断终止|适配供应商 SDK 和 API Key|

明确职责以后，先从 Gateway 对外暴露的协议开始。

---

## 三、为什么 Gateway 要先定义自己的请求协议？

不同模型服务的字段看起来相似，却不一定完全一致。如果上层直接传供应商的原始请求，Gateway 只是一个透明代理，模型差异仍然会泄漏到 Agent 中。

当前代码先用 Pydantic 定义平台自己的消息、Prompt 选择和模型请求。

### 3.1 怎样定义统一的消息与 Prompt 选择？

```Python
class Message(BaseModel):
    model_config = ConfigDict(extra="forbid")

    role: Literal["system", "user", "assistant"]
    content: str = Field(min_length=1, max_length=20_000)


class PromptSelection(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str = Field(min_length=1, max_length=100)
    version: str = Field(min_length=1, max_length=50)
    variables: dict[str, str] = Field(default_factory=dict)
```

`Message` 只保留当前业务真正使用的三种角色和文本内容。`extra="forbid"` 会拒绝未声明字段，避免调用方把某家供应商的私有参数偷偷带进平台协议。

`PromptSelection` 不接收完整 System Prompt，而是接收模板名、版本和变量。模板正文由 Gateway 发布，调用方只能选择已经存在的版本。

这正是需要工程师完成的第一项工作：不是照搬供应商请求，而是根据平台需要设计一份最小、稳定的内部协议。

### 3.2 为什么要在入口拒绝暂不支持的能力组合？

```Python
class LLMRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")

    model: str = Field(min_length=1, max_length=100)
    messages: list[Message] = Field(min_length=1, max_length=100)
    stream: bool = False
    response_schema: dict[str, Any] | None = None
    timeout_seconds: float = Field(default=30, gt=0, le=120)
    prompt: PromptSelection | None = None

    @model_validator(mode="after")
    def check_supported_combination(self) -> "LLMRequest":
        if self.stream and self.response_schema is not None:
            raise ValueError("stream 与 response_schema 不能同时使用")
        return self
```

这份请求包含六项信息：平台模型名、消息、是否流式、输出 Schema、超时和 Prompt 模板选择。

当前实现明确禁止同时启用 `stream` 与 `response_schema`。Structured Output 需要拿到完整 JSON 后统一解析和校验，而当前流式路径只逐块转发文本，没有实现增量 JSON 解析。

模型不会主动替平台缩小边界。工程师必须明确当前版本支持什么，并让不支持的组合在入口立刻失败。

### 3.3 为什么响应出口也要有统一类型？

```Python
class Usage(BaseModel):
    model_config = ConfigDict(extra="forbid")

    input_tokens: int = Field(ge=0)
    output_tokens: int = Field(ge=0)


class LLMResponse(BaseModel):
    model_config = ConfigDict(extra="forbid")

    request_id: str
    model: str
    content: str
    parsed: dict[str, Any] | list[Any] | None = None
    usage: Usage
    latency_ms: int = Field(ge=0)
    attempts: int = Field(ge=1)
```

上层不应该有时读取 `choices[0].message.content`，有时又解析其他供应商字段。Gateway 统一返回文本、结构化对象、Token、耗时和尝试次数。

其中 `model` 是实际成功返回的模型。发生 fallback 时，它可能和请求中的模型不同；`attempts` 表示这次 Gateway 调用一共向模型服务发起了多少次请求。

入口和出口已经稳定，下一步才是把平台模型映射到实际供应商。

## 四、为什么 OpenAI Compatible 接口仍然需要 Provider Adapter？

当前项目的主模型和备用模型都使用 OpenAI Compatible Chat Completions 接口。兼容协议减少了适配成本，但 Base URL、模型名、API Key 和 Structured Output 能力仍然需要统一管理。

### 4.1 怎样集中管理模型配置？

```Python
@dataclass(frozen=True)
class ModelConfig:
    provider_model: str
    base_url: str
    api_key_env: str
    supports_structured_output: bool
    structured_output_mode: Literal[
        "json_schema", "json_object"
    ] = "json_schema"


MODEL_CONFIGS = {
    "general-primary": ModelConfig(
        provider_model=os.getenv(
            "PRIMARY_PROVIDER_MODEL", "deepseek-v4-flash"
        ),
        base_url=os.getenv(
            "PRIMARY_BASE_URL", "https://api.deepseek.com"
        ),
        api_key_env="DEEPSEEK_API_KEY",
        supports_structured_output=True,
        structured_output_mode="json_object",
    ),
    "general-backup": ModelConfig(
        provider_model=os.getenv(
            "BACKUP_PROVIDER_MODEL", "deepseek-chat"
        ),
        base_url=os.getenv(
            "BACKUP_BASE_URL", "https://api.deepseek.com"
        ),
        api_key_env="DEEPSEEK_BACKUP_API_KEY",
        supports_structured_output=True,
        structured_output_mode="json_object",
    ),
}
```

上层只使用 `general-primary` 和 `general-backup`，不会接触真实模型名、地址和环境变量名。部署时可以通过环境变量替换模型与地址，而不修改 Agent 代码。

`supports_structured_output` 用于 fallback 前的能力检查。`structured_output_mode` 说明模型使用原生 `json_schema`，还是只支持 `json_object`。

主模型与备用模型当前都配置为 `json_object`。Schema 不能直接作为原生约束交给接口，Gateway 还要把 Schema 写进提示信息，并在返回后自行校验。这一差异必须由 Gateway 吸收。

### 4.2 为什么要定义 Provider Protocol？

```Python
class Provider(Protocol):
    async def complete(
        self,
        config: ModelConfig,
        messages: list[Message],
        timeout_seconds: float,
        response_schema: dict[str, Any] | None,
    ) -> tuple[str, Usage]: ...

    async def stream(
        self,
        config: ModelConfig,
        messages: list[Message],
        timeout_seconds: float,
    ) -> AsyncIterator[str]: ...
```

`Provider` 规定两种统一能力：普通调用返回完整文本与 Usage，流式调用逐块产生文本。业务流程依赖这份接口，不依赖 `AsyncOpenAI`。

当前只有 `OpenAICompatibleProvider` 一个实现，但提前定义 Protocol 仍然有价值：以后接入非兼容接口时，可以增加另一个 Provider，而不是修改重试、日志和 FastAPI 路由。

这一步体现了 Codex 等生产级 Harness 常见的设计思想：供应商通信细节停留在 Adapter 中，Loop 和上层服务只依赖稳定能力。不过，本章以你的实际实现为准，只演示当前已经使用的 Chat Completions Compatible 路径。

### 4.3 怎样让 SDK 只负责一次请求？

```Python
class OpenAICompatibleProvider:
    def create_client(self, config: ModelConfig) -> AsyncOpenAI:
        api_key = os.getenv(config.api_key_env)
        if not api_key:
            raise GatewayError(
                "gateway_misconfigured",
                "Gateway 模型凭据未配置",
                503,
            )

        return AsyncOpenAI(
            api_key=api_key,
            base_url=config.base_url,
            max_retries=0,
        )
```

API Key 只在 Gateway 内部读取。Planning、RAG 和业务 Agent 不需要保存外部密钥。

`max_retries=0` 关闭 SDK 内置重试。当前项目已经在 Gateway 层实现显式重试，如果 SDK 内部再自动重试，就无法准确统计尝试次数，也可能放大调用量。

Provider 边界建立以后，先看普通模型调用怎样完成协议转换。

## 五、怎样把统一请求转换成真实模型调用？

### 5.1 普通文本调用怎样完成？

```Python
async def complete(
    self,
    config: ModelConfig,
    messages: list[Message],
    timeout_seconds: float,
    response_schema: dict[str, Any] | None,
) -> tuple[str, Usage]:
    request_data: dict[str, Any] = {
        "model": config.provider_model,
        "messages": [
            message.model_dump() for message in messages
        ],
        "timeout": timeout_seconds,
    }

    completion = await self.create_client(
        config
    ).chat.completions.create(**request_data)

    content = completion.choices[0].message.content or ""
    usage = completion.usage

    return content, Usage(
        input_tokens=usage.prompt_tokens if usage else 0,
        output_tokens=usage.completion_tokens if usage else 0,
    )
```

Provider 把 Pydantic `Message` 转为普通字典，再调用 OpenAI Compatible Chat Completions。响应回来后，只提取完整文本与输入、输出 Token。

SDK 的 `completion` 对象不会离开 Provider。Gateway 的其他部分只消费 `str` 和 `Usage`，因此不会和供应商响应类型耦合。

### 5.2 为什么 Structured Output 需要在 Provider 中处理模式差异？

当请求带有 `response_schema` 时，Provider 会根据模型配置选择两条路径：

```Python
if response_schema is not None:
    if config.structured_output_mode == "json_schema":
        request_data["response_format"] = {
            "type": "json_schema",
            "json_schema": {
                "name": "agent_response",
                "strict": True,
                "schema": response_schema,
            },
        }
    else:
        request_data["response_format"] = {
            "type": "json_object"
        }
        request_data["messages"] = [
            {
                "role": "system",
                "content": (
                    "只返回一个合法 JSON 对象，必须严格符合下列 JSON Schema，"
                    "不要返回 Markdown 或额外文字："
                    f"{json.dumps(response_schema, ensure_ascii=False)}"
                ),
            },
            *request_data["messages"],
        ]
```

原生 `json_schema` 模式会把 Schema 放进 `response_format`；当前 DeepSeek 配置走 `json_object`，因此 Gateway 要求模型输出 JSON，并把 Schema 作为系统消息加入上下文。

`json_object` 主要保证输出是 JSON，不代表一定满足业务 Schema。提示信息只是提高合规率，真正的验收仍然发生在模型返回以后。

### 5.3 为什么模型返回后还要再次校验？

```Python
parsed: dict[str, Any] | list[Any] | None = None

if request.response_schema is not None:
    try:
        parsed = json.loads(content)
        validate(
            instance=parsed,
            schema=request.response_schema,
        )
    except json.JSONDecodeError as exc:
        raise GatewayError(
            "invalid_json",
            "模型没有返回合法 JSON",
        ) from exc
    except JsonSchemaError as exc:
        raise GatewayError(
            "schema_validation_failed",
            "模型结果不符合 response_schema",
        ) from exc
```

当前代码执行两层校验：`json.loads()` 检查 JSON 语法；`jsonschema.validate()` 检查字段、类型、必填项和其他 Schema 约束。

只有两层都通过，`parsed` 才会进入 `LLMResponse`。错误 JSON 不会被拼成半成品，也不会被 Agent Loop 当作合法动作执行。

当前 Gateway 只负责检测并返回稳定错误码，没有在内部实现 Structured Output 纠错循环。把错误反喂模型修复属于上一节的 Harness 策略；是否在 Gateway 中集中实现，可以在后续演进时再决定。

普通请求到这里已经闭合。下一步处理另一种响应形态：Streaming。

## 六、为什么 Streaming 必须边接收边转发？

如果 Gateway 等待完整答案再返回，用户仍然要经历完整生成时间。真正的流式代理应该收到一个增量块，就立即向下游发送一个增量块。

### 6.1 Provider 怎样读取上游流？

```Python
async def stream(
    self,
    config: ModelConfig,
    messages: list[Message],
    timeout_seconds: float,
) -> AsyncIterator[str]:
    response = await self.create_client(
        config
    ).chat.completions.create(
        model=config.provider_model,
        messages=[message.model_dump() for message in messages],
        stream=True,
        timeout=timeout_seconds,
    )

    async for chunk in response:
        choice = chunk.choices[0] if chunk.choices else None
        if choice and choice.delta.content:
            yield choice.delta.content
```

Provider 只提取增量文本，不把供应商 chunk 对象暴露给 Gateway。这样下游不需要知道 `choices[0].delta.content` 的具体结构。

### 6.2 Gateway 怎样统一 SSE 事件？

```Python
def encode_sse(event: dict[str, Any]) -> str:
    return (
        f"data: {json.dumps(event, ensure_ascii=False)}\n\n"
    )
```

当前 Gateway 使用三种事件：

|事件|含义|
|---|---|
|`content.delta`|一段新的文本|
|`response.completed`|流正常结束，并给出实际模型|
|`response.failed`|流中发生错误|

前端、CLI 或 Harness 只需要理解这三种内部事件，不再直接处理不同模型的流式格式。

### 6.3 为什么只能在首块输出前 fallback？

```Python
async def stream_with_fallback(
    request: LLMRequest,
) -> AsyncIterator[str]:
    messages = build_messages(request)
    started = time.perf_counter()
    attempts = 0
    emitted = False
    last_error: Exception | None = None

    for model_name in dict.fromkeys(
        [request.model, "general-backup"]
    ):
        try:
            config = validate_model(model_name, None)
            attempts += 1

            async for delta in provider.stream(
                config,
                messages,
                request.timeout_seconds,
            ):
                emitted = True
                yield encode_sse(
                    {"type": "content.delta", "delta": delta}
                )

            yield encode_sse(
                {
                    "type": "response.completed",
                    "model": model_name,
                }
            )
            return

        except Exception as exc:
            last_error = exc
            if emitted or not is_retryable(exc):
                break

    yield encode_sse(
        {
            "type": "response.failed",
            "error": "upstream_stream_failed",
        }
    )
```

`emitted` 是流式路径最重要的状态。首块产生以前，调用方还没有看到任何模型内容，因此临时故障可以切换备用模型；一旦已经发送文本，再从另一个模型重新生成，用户就可能看到重复或互相矛盾的内容。

所以当前实现选择：首块前允许 fallback，首块后失败就发送 `response.failed` 并停止。

还要注意一个当前实现边界：流式调用没有请求 Usage，因此 Trace 中的流式 Token 暂时记录为零。后续可以通过供应商支持的 Usage 事件或流式 Usage 选项补齐。

如果要补齐当前 Chat Completions 流的 Token Usage，数据仍然应该在 Provider 层取得。DeepSeek 的兼容接口支持在流式请求中启用 `stream_options.include_usage`；启用后，结束标记之前会额外返回一个 Usage chunk，该 chunk 的 `choices` 为空，`usage` 保存整次请求的 Token 统计。需要注意，当前 `Provider.stream()` 只产出字符串，Usage chunk 没有文本，直接套入现有判断会被跳过。因此后续演进时，应让 Provider 流同时表达“文本增量”和“调用完成及 Usage”，再由 `stream_with_fallback()` 在完成事件到达时调用 `record_trace()`。Usage 的提取仍然不应该放进 FastAPI 路由或 Agent Loop，因为它属于供应商响应适配。

如果以后接入 Responses API，事件解析也应加载在 Provider Adapter 与 Gateway 内部事件之间，而不是散落到前端。可以在 `OpenAICompatibleProvider` 旁新增 Responses Provider，负责把上游的 `response.output_text.delta`、`response.completed`、`response.failed` 和 `response.incomplete` 转换成 Gateway 内部事件。`stream_with_fallback()` 只消费内部事件：文本事件继续向下游发送，完成事件读取 Response ID 和 Usage，失败或未完成事件进入统一错误路径。Codex `v0.146.1` 中可参考 `codex-rs/codex-api/src/sse/responses.rs` 的分层：SSE 解析发生在 API 适配层，核心 Loop 消费的是类型化 `ResponseEvent`。OpenAI 的 Responses 流中，`response.completed` 携带完整 Response 对象，其中包含最终 Usage，因此它也是最合适的完成与计费边界。

Streaming 已经统一，接下来处理 Gateway 中另一项需要集中治理的资产：Prompt 模板。

## 七、为什么 Prompt 模板要由 Gateway 管理？

如果每个业务 Agent 都传入完整 System Prompt，同一份提示词会散落在多个服务中。模板修改以后，很难确认哪些调用已经升级，也无法从日志判断一次调用用了哪个版本。

### 7.1 怎样定义受控模板库？

```Python
class PromptTemplate(BaseModel):
    model_config = ConfigDict(extra="forbid")

    name: str
    version: str
    system_template: str


PROMPT_TEMPLATES = {
    ("knowledge_decision", "v1"): PromptTemplate(
        name="knowledge_decision",
        version="v1",
        system_template=(
            "你是${product_name}的知识库决策器。"
            "资料不足时搜索，资料充分时结束回答。"
            "不得编造制度内容。"
        ),
    )
}
```

模板通过 `(name, version)` 唯一确定。修改模板时发布新版本，而不是直接覆盖旧内容，已有调用和历史 Trace 才能被准确复现。

### 7.2 为什么调用方只能传变量，不能覆盖模板正文？

```Python
def render_prompt(selection: PromptSelection) -> Message:
    template = PROMPT_TEMPLATES.get(
        (selection.name, selection.version)
    )
    if template is None:
        raise GatewayError(
            "unknown_prompt_template",
            "Prompt 模板不存在",
            400,
        )

    try:
        content = Template(
            template.system_template
        ).substitute(selection.variables)
    except KeyError as exc:
        raise GatewayError(
            "missing_prompt_variable",
            f"缺少 Prompt 变量: {exc.args[0]}",
            400,
        ) from exc

    return Message(role="system", content=content)


def build_messages(request: LLMRequest) -> list[Message]:
    if request.prompt is None:
        return request.messages
    return [render_prompt(request.prompt), *request.messages]
```

模板不存在或变量缺失时，Gateway 直接返回客户端错误，不会带着残缺 Prompt 调用模型。

调用方仍然可以在 `messages` 中传普通消息，但不能通过 `PromptSelection` 修改模板正文。Gateway 负责模板发布、版本和渲染；Agent Harness 仍然负责选择当前任务应该使用哪个模板。

受控模板并不等于自动消除 Prompt 注入。变量仍可能来自不可信输入，是否允许变量进入 System Prompt、是否需要长度和内容限制，仍要按上一节的输入边界处理。本节只解决模板资产不被调用方任意覆盖的问题。

Prompt 模板把请求内容收口，下一步还要把模型故障的处理方式收口。

---

## 八、为什么重试必须由 Gateway 明确控制？

如果 SDK、Gateway 和 Agent Loop 都自动重试，一次任务可能产生远超预期的模型调用。当前代码关闭 SDK 重试，只在 Gateway 中保留明确、可统计的两次尝试。

### 8.1 哪些错误当前会被重试？

```Python
def is_retryable(exc: Exception) -> bool:
    return isinstance(
        exc,
        (
            APIConnectionError,
            APITimeoutError,
            RateLimitError,
            TimeoutError,
            ConnectionError,
        ),
    )
```

当前实现只重试连接、超时和限流类错误。认证失败、请求参数错误、JSON 解析失败和 Schema 校验失败都不会进入网络重试。

这段代码没有把所有异常都标记为可重试，也没有覆盖所有 5xx。如果后续希望对服务过载或部分 5xx 重试，需要先补充明确的异常分类和测试。

### 8.2 怎样实现有限重试与备用模型 fallback？

```Python
async def call_with_fallback(
    request: LLMRequest,
) -> LLMResponse:
    requested_model = request.model
    request_id = str(uuid4())
    started = time.perf_counter()
    attempts = 0
    last_error: Exception | None = None
    messages = build_messages(request)

    for model_name in dict.fromkeys(
        [requested_model, "general-backup"]
    ):
        try:
            config = validate_model(
                model_name,
                request.response_schema,
            )
        except GatewayError as exc:
            if model_name == requested_model:
                raise exc
            last_error = exc
            continue

        for retry_number in range(2):
            attempts += 1
            try:
                content, usage = await provider.complete(
                    config,
                    messages,
                    request.timeout_seconds,
                    request.response_schema,
                )

                parsed = None
                if request.response_schema is not None:
                    parsed = json.loads(content)
                    validate(
                        instance=parsed,
                        schema=request.response_schema,
                    )

                return LLMResponse(
                    request_id=request_id,
                    model=model_name,
                    content=content,
                    parsed=parsed,
                    usage=usage,
                    latency_ms=int(
                        (time.perf_counter() - started) * 1000
                    ),
                    attempts=attempts,
                )

            except GatewayError:
                raise
            except Exception as exc:
                last_error = exc
                if is_retryable(exc) and retry_number == 0:
                    await asyncio.sleep(0.1)
                    continue
                break

    raise GatewayError(
        "model_unavailable",
        "主模型和备用模型均不可用",
    ) from last_error
```

为了突出控制流，片段省略了前面已经讲过的 Schema 校验和 Trace 调用，完整代码仍保留它们。

每个候选模型最多尝试两次。第一次遇到可重试错误，等待 `0.1` 秒再试；第二次仍失败，才切换备用模型。`attempts` 统计跨主模型和备用模型的全部请求次数。

如果要增加 Provider 级指数退避，策略应该加载在模型配置与 `call_with_fallback()` 的内层重试循环之间。配置层负责声明每个 Provider 的最大尝试次数、基础等待时间，以及是否重试 429、5xx 和传输错误；执行层在确认错误可重试以后，根据当前 attempt 计算等待时间。常见做法是让等待时间按 `base_delay × 2^(attempt-1)` 增长，并加入小幅随机抖动，避免大量失败请求在同一时刻再次访问上游。如果响应带有可信的 `Retry-After`，应优先服从供应商给出的等待时间。这个策略不应放在 `Provider.complete()` 内部，否则普通调用和流式调用容易形成两套重试逻辑，也会重新出现 SDK 重试与 Gateway 重试叠加的问题。

Provider 级策略还要与 fallback 分开理解：指数退避解决“同一个 Provider 是否值得再试一次”，fallback 解决“当前 Provider 耗尽预算后是否切换能力等价的模型”。因此正确顺序仍然是先耗尽当前 Provider 的有限预算，再校验备用模型能力，最后切换；不能每次短暂超时都立即跨 Provider 跳转。

fallback 前，`validate_model()` 会检查模型白名单和 Structured Output 能力：

```Python
def validate_model(
    model: str,
    response_schema: dict[str, Any] | None,
) -> ModelConfig:
    config = MODEL_CONFIGS.get(model)
    if config is None:
        raise GatewayError(
            "unknown_model",
            "模型不在 Gateway 允许列表中",
            400,
        )

    if (
        response_schema is not None
        and not config.supports_structured_output
    ):
        raise GatewayError(
            "structured_output_unsupported",
            "模型不支持 Structured Output",
            400,
        )

    return config
```

这是工程师必须亲自决定的能力等价关系。模型不会替平台判断“备用模型能否完成同一种协议”。

### 8.3 Gateway 重试和 Agent Loop 重试有什么区别？

Gateway 重试的是同一次模型调用，输入和目标保持不变；Agent Loop 重试的是任务步骤，可能会补充上下文、修改计划或重新调用工具。

当前 Gateway 最多可能调用主模型两次、备用模型两次。如果外层 Loop 还要重试，必须把 `attempts` 纳入任务预算，否则调用量会成倍增加。

重试解决了临时故障，但如果调用完成后没有留下记录，团队仍然无法解释成本和延迟。因此最后还要加入统一 Trace。

## 九、为什么模型调用必须留下 Token、Cost 和 Latency？

模型调用除了状态和耗时，还要关注 Token。Token 同时影响成本、上下文窗口和输出长度。

### 9.1 当前 Trace 记录哪些字段？

```Python
class CallTrace(BaseModel):
    model_config = ConfigDict(extra="forbid")

    request_id: str
    timestamp: datetime
    requested_model: str
    actual_model: str | None = None
    prompt_name: str | None = None
    prompt_version: str | None = None
    input_tokens: int = Field(ge=0)
    output_tokens: int = Field(ge=0)
    cost_usd: float = Field(ge=0)
    latency_ms: int = Field(ge=0)
    attempts: int = Field(ge=0)
    status: Literal["success", "failed"]
    error_code: str | None = None
```

`requested_model` 是调用方选择的模型，`actual_model` 是最终实际返回的模型。发生 fallback 时，两者不同。

Prompt 名称和版本一起记录，方便比较模板变更前后的成功率、长度和成本。Trace 默认不保存完整输入与输出，减少敏感内容进入日志的风险。

### 9.2 怎样计算成本并写入 Trace？

```Python
PRICE_PER_MILLION = {
    "general-primary": {"input": 1.0, "output": 4.0},
    "general-backup": {"input": 0.8, "output": 3.2},
}


def calculate_cost(model: str, usage: Usage) -> float:
    price = PRICE_PER_MILLION[model]
    return (
        usage.input_tokens * price["input"]
        + usage.output_tokens * price["output"]
    ) / 1_000_000
```

价格只是课程演示值，不代表供应商真实报价。上线时必须按实际模型版本维护价格表。

```Python
CALL_TRACES: list[CallTrace] = []


def record_trace(
    request_id: str,
    requested_model: str,
    actual_model: str | None,
    prompt: PromptSelection | None,
    usage: Usage,
    latency_ms: int,
    attempts: int,
    status: Literal["success", "failed"],
    error_code: str | None = None,
) -> None:
    trace = CallTrace(
        request_id=request_id,
        timestamp=datetime.now(timezone.utc),
        requested_model=requested_model,
        actual_model=actual_model,
        prompt_name=prompt.name if prompt else None,
        prompt_version=prompt.version if prompt else None,
        input_tokens=usage.input_tokens,
        output_tokens=usage.output_tokens,
        cost_usd=(
            calculate_cost(actual_model, usage)
            if actual_model
            else 0
        ),
        latency_ms=latency_ms,
        attempts=attempts,
        status=status,
        error_code=error_code,
    )
    CALL_TRACES.append(trace)
    logger.info(
        "llm_call_trace=%s",
        trace.model_dump_json(),
    )
```

成功和失败都要留下 Trace。失败调用的 Token 当前记为零，因为异常路径没有可靠 Usage；成功调用按实际模型计算成本。

`CALL_TRACES` 是内存列表，只适合课程演示。服务重启后数据会丢失，多进程实例之间也不共享。生产环境应写入日志平台、数据库或可观测系统，但本节不扩展存储架构。

如果要把 Trace 落到数据库，替换点应该是 `record_trace()`，而不是三个 FastAPI 路由。可以把当前的 `CALL_TRACES.append()` 抽象成 Trace Repository，由 Repository 负责写入 PostgreSQL、ClickHouse 或其他存储；普通调用、Streaming 和失败路径仍然只调用同一个记录接口。表结构至少保留 `request_id`、请求模型、实际模型、Prompt 名称与版本、输入输出 Token、成本、延迟、attempts、状态、错误码和时间戳，并为时间、模型、Prompt 版本和状态建立常用查询索引。这样路由协议不变，后续也可以把写库改为异步队列，避免数据库延迟阻塞模型响应。

`/v1/traces` 也不应该继续直接返回进程内列表。数据库落地后，这个接口应经过 Repository 查询，并补充分页、时间范围、模型与状态过滤以及访问控制。Trace 可能暴露模型选择、错误和成本信息，即使不保存 Prompt 正文，也不应作为无权限的公开接口。

当前非流式调用已经能从 `completion.usage` 取得输入与输出 Token。若要增加细分 Token，扩展位置有三处：Provider 层从供应商 Usage 中提取缓存命中 Token、推理 Token等明细；统一 `Usage` 模型增加对应字段；`CallTrace` 与 `calculate_cost()` 使用细分字段计算和存储。三处必须一起修改，不能只扩展日志字段，否则上游数据仍然没有进入系统。

细分 Token 的字段不能假设所有供应商完全一致。某些模型区分缓存读取、缓存写入和推理 Token，另一些模型只返回输入与输出总量。Provider 应负责把可获得的字段映射到统一 Usage，缺失字段使用明确的零值或空值；成本计算则按实际模型版本读取价格规则。这样上层看到的是稳定口径，同时不会把“供应商未提供”误解为“确实没有消耗”。

现在，统一协议、Provider、Prompt、Structured Output、Streaming、重试和 Trace 都已经完成。最后把它们收回 FastAPI 路由。

## 十、怎样用 FastAPI 暴露统一入口？

### 10.1 为什么普通响应和 Streaming 使用两个入口？

```Python
app = FastAPI(
    title="Agent LLM Gateway",
    version="0.0.1",
)


@app.post("/v1/llm", response_model=LLMResponse)
async def create_llm_response(
    request: LLMRequest,
) -> LLMResponse:
    if request.stream:
        raise HTTPException(
            status_code=400,
            detail={
                "code": "use_stream_endpoint",
                "message": "流式请求请使用 /v1/llm/stream",
            },
        )

    try:
        return await call_with_fallback(request)
    except GatewayError as exc:
        raise HTTPException(
            status_code=exc.status_code,
            detail={"code": exc.code, "message": exc.message},
        ) from exc
```

普通入口使用 `response_model=LLMResponse`。FastAPI 在请求进入时按 `LLMRequest` 校验，在结果离开时按 `LLMResponse` 再校验一次。

`GatewayError` 会被转换为稳定的 HTTP 错误。上层只依赖 `code` 和 `message`，不用识别 OpenAI SDK 异常。

```Python
@app.post("/v1/llm/stream")
async def create_stream(
    request: LLMRequest,
) -> StreamingResponse:
    if request.response_schema is not None:
        raise HTTPException(
            status_code=400,
            detail={
                "code": "unsupported_combination",
                "message": "流式输出不支持 response_schema",
            },
        )

    try:
        validate_model(request.model, None)
        build_messages(request)
    except GatewayError as exc:
        raise HTTPException(
            status_code=exc.status_code,
            detail={"code": exc.code, "message": exc.message},
        ) from exc

    return StreamingResponse(
        stream_with_fallback(request),
        media_type="text/event-stream",
    )
```

流式入口在响应开始前先校验模型和 Prompt。真正进入流以后，HTTP 状态码已经不能随意修改，因此后续故障通过 `response.failed` 事件返回。

两个入口是在协议层明确区分“完整对象响应”和“持续事件流”。

### 10.2 为什么还提供 Trace 查询入口？

```Python
@app.get("/v1/traces", response_model=list[CallTrace])
async def list_traces() -> list[CallTrace]:
    return CALL_TRACES
```

这个接口方便课堂观察一次调用使用了哪个模型、是否 fallback、调用几次、消耗多少 Token 和多长时间。

它不是完整审计系统。当前接口没有分页、持久化和访问控制，只用于演示 Gateway 为什么必须保存结构化调用记录。

### 10.3 Agent 现在怎样调用 Gateway？

```Python
import httpx


async def decide_through_gateway(
    task: str,
) -> AgentDecision:
    payload = {
        "model": "general-primary",
        "messages": [
            {"role": "user", "content": task},
        ],
        "prompt": {
            "name": "knowledge_decision",
            "version": "v1",
            "variables": {
                "product_name": "差旅助手",
            },
        },
        "response_schema": (
            AgentDecision.model_json_schema()
        ),
    }

    async with httpx.AsyncClient() as client:
        response = await client.post(
            "http://llm-gateway:8000/v1/llm",
            json=payload,
            timeout=35,
        )
        response.raise_for_status()
        result = LLMResponse.model_validate(response.json())

    if result.parsed is None:
        raise RuntimeError("Gateway 未返回结构化结果")

    return AgentDecision.model_validate(result.parsed)
```

Agent 不再保存 DeepSeek API Key，不再拼接 Base URL，也不再编写供应商重试。它只提交平台模型名、模板选择、消息和业务 Schema。

最后仍然用 `AgentDecision.model_validate()` 执行业务类型校验。Gateway 负责通用 JSON Schema，业务 Agent 负责自己的跨字段规则，两层职责不同。

## 十一、课堂练习与验收

基于 `gateway.py` 完成一次知识库 Agent 调用，并验证下面这些场景：

1. 正常文本请求返回 `LLMResponse`；
2. 未知模型返回 `unknown_model`；
3. 模板版本不存在时返回 `unknown_prompt_template`；
4. 模板变量缺失时返回 `missing_prompt_variable`；
5. 合法 JSON 但不符合 Schema 时返回 `schema_validation_failed`；
6. 主模型连接失败时进行一次重试，再 fallback 到备用模型；
7. 流式请求逐块产生 `content.delta`；
8. 流开始后失败时产生 `response.failed`，不能静默换模型重写；
9. 成功和失败调用都能在 Trace 中找到；
10. 业务 Agent 的代码中不出现供应商 API Key 和 Base URL。

验收时重点检查三条不变量：

> 未通过 Schema 校验的输出不能进入 Agent Loop。

> 流已经输出首块以后，不能切换模型重新生成。

> 无论最终使用主模型还是备用模型，上层只依赖同一份请求、响应和错误协议。

如果这三条成立，Gateway 才真正成为 Harness 与模型服务之间的稳定边界。

## 十二、本节小结

上一节 Structured Output 解决的是“怎样把模型结果变成可验证对象”；本节 LLM Gateway 进一步解决“怎样让整个平台用同一种方式调用模型”。

当前 `gateway.py` 已经完成以下闭环：

1. FastAPI 提供普通调用、Streaming 和 Trace 查询入口；
2. Pydantic 在请求入口与响应出口执行协议校验；
3. `ModelConfig` 和 Provider 隔离模型名、地址、密钥与兼容接口；
4. Prompt 模板由 Gateway 按名称和版本渲染；
5. Structured Output 根据模型能力选择 `json_schema` 或 `json_object`，返回后统一执行 Schema 校验；
6. Gateway 关闭 SDK 隐式重试，明确控制重试次数和备用模型 fallback；
7. 每次调用记录模型、Prompt 版本、Token、Cost、Latency、尝试次数和状态。

同时也要准确认识当前实现边界：

- 目前只实现 OpenAI Compatible Chat Completions Provider；
- 重试等待是固定 `0.1` 秒，没有指数退避和 `Retry-After`；
- 当前可重试异常不包含所有服务端 5xx；
- Structured Output 校验失败后直接返回错误，没有内部纠错循环；
- Streaming 暂未记录真实 Token Usage；
- Trace 暂存在进程内存中，没有持久化和访问控制。

这些不是讲义需要隐藏的问题，而是下一阶段工程演进的起点。

真正需要 Agent 开发工程师掌握的，不是记住某个 SDK 方法，而是做出平台决策：哪些字段进入统一协议、哪些差异停留在 Provider、哪些能力组合被允许、哪些错误值得重试、fallback 是否等价、失败怎样返回、调用必须留下哪些证据。

模型可以辅助编写代码，但不能替团队决定这些系统边界。能够把边界写成协议、校验、状态和失败路径，才是 LLM Gateway 对 Agent Harness 的真正价值。
