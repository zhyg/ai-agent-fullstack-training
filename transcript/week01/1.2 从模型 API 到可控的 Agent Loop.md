## **二、目标拆解：为什么 Agent 开发要深入学习输入与输出**



很多传统开发工程师第一次接触 Agent，会产生一个非常合理的疑问：模型已经会写代码了，为什么“怎么调用模型、怎么组织输入、怎么解析输出”还要由开发者深入学习？这部分工作继续交给 AI 写，不可以吗？



答案是：**编码过程可以大量交给 AI，但上下文、目标、协议和失败边界不能交给 AI 自己定义。**



AI 可以替我们生成一段 SDK 调用代码，却不知道这次任务的真实业务边界。例如，我们让模型“分析线上告警并决定是否回滚”。模型可以生成一个看起来合理的 JSON，但它不知道：



- 回滚只能发生在指定环境；

- `service_name` 必须来自服务注册中心；

- 生产回滚必须经过人工审批；

- 没有足够证据时应该终止，而不是猜测；

- 同一个回滚动作不能因为网络重试而执行两次；

- 响应被截断时，半段 JSON 绝不能进入执行器。

这些不是语言生成问题，而是工程责任问题。



传统函数通常具有相对稳定的契约：输入类型正确，函数沿着开发者写好的路径执行，再返回约定类型。模型调用不同。它的输入是一个由目标、指令、历史消息、工具定义、检索结果和运行状态共同构成的上下文；它的输出则是带有概率性、版本差异和失败可能性的候选结果。



所以，Agent 系统中的职责边界应该这样划分：



|责任|应由谁负责|原因|
|---|---|---|
|目标是什么、什么算完成|开发者 / 产品 /业务规则|模型无法替业务承担责任|
|本轮给模型看什么上下文|Harness / Context Manager|上下文有成本、权限和信息边界|
|模型如何生成候选答案或动作|模型|这是模型擅长的概率生成工作|
|输出必须符合什么结构|开发者定义 Schema|下游程序需要稳定契约|
|工具能不能执行|Harness / Policy|Prompt 不能代替权限系统|
|失败能否重试、何时停止|Loop / Retry Policy|模型不能自行决定无限消耗预算|
|任务是否真的完成|Validator / Verifier|“模型说完成”不等于事实完成|



这就是本节六个目标的关系：



1. API 协议解决“数据怎样进出模型”；

2. 生成参数解决“输出怎样被采样、怎样限制长度”；

3. Token 与 Context Window 解决“本轮究竟能给模型看多少信息”；

4. Structured Output 解决“模型结果怎样进入确定性程序”；

5. 异常策略解决“外部服务和概率输出失败时，系统怎样收敛”；

6. Model Adapter 解决“如何更换模型而不重写 Agent Loop”。



请记住一句贯穿整个训练营的话：



**AI 可以写实现代码，但开发者必须指定目标、上下文、契约、权限与完成条件。**



如果这些内容没有被明确定义，AI 生成再多代码，也只是在更快地实现一个边界模糊的系统。

## **三、目标一：Chat Completions 与 Responses API**



### **3\.1 它们是什么，从哪里来**



在大模型 API 的早期，开发者常见的是 Completion 风格接口：给模型一段 prompt，模型续写一段文本。这种接口接近“文本补全”，但不擅长表达多轮对话中的角色、工具调用和工具结果。



Chat Completions 把上下文组织成按顺序排列的 `messages`。每条消息有角色和内容，例如 `system`、`user`、`assistant`、`tool`。它让对话历史、函数调用和多轮交互有了相对稳定的协议，并逐渐成为许多供应商支持的事实兼容基线。



Responses API 是在 Agent 应用需求增长后形成的更通用抽象。它不再假设模型只返回“一条 assistant 消息”，而是把输入和输出表示为不同类型的 item：消息、推理、函数调用、函数结果、内置工具调用等。流式响应也不再只是文本块，而是带明确类型的语义事件。



OpenAI 在 2025 年 3 月推出 Responses API，目标是把文本生成、内置工具、多模态输入和 Agent 工作流统一到一个 API 中。OpenAI 当前仍支持 Chat Completions，但建议新项目优先使用 Responses。DeepSeek V4 则同时提供 OpenAI 兼容的 Chat Completions；截至本节编写日期，其 Responses API 当前支持 `deepseek-v4-flash`。



### **3\.2 主流应该用哪个**



不要把答案背成“旧项目用 Chat，新项目一律用 Responses”。工程上要先看边界：



|场景|建议起点|原因|
|---|---|---|
|需要最大化跨供应商兼容|Chat Completions|支持范围广，很多供应商提供兼容端点|
|新建 OpenAI Agent 应用|Responses|OpenAI 推荐方向，item、工具和流式事件更适合 Agent|
|新建 DeepSeek V4 Flash / Codex 风格应用|Responses|官方已提供 Responses 兼容接口|
|使用暂不支持 Responses 的模型|Chat Completions|能力可用性优先于接口偏好|
|维护已有稳定系统|不为“追新”强迁移|迁移必须由工具能力、观测或成本收益驱动|



因此，本节两个都学。



学习 Chat Completions，是为了理解当前最广泛的跨供应商协议基线，以及消息、tool call、tool result 怎样组成多轮上下文。学习 Responses，是为了理解 Agent API 正在走向哪里：类型化 item、明确的生命周期事件、内置工具和更丰富的响应状态。



真正的工程结论不是把 Loop 绑定到其中一个，而是让 Adapter 消化协议差异，让 Loop 只认识内部统一类型。



### **3\.3 Chat Completions 的请求与返回**



先安装依赖：



```Bash
pip install "openai>=2" "pydantic>=2"
export DEEPSEEK_API_KEY="你的 API Key"
```



第一个例子使用 `deepseek-v4-flash` 的 Chat Completions 接口：



```Python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
    timeout=30.0,
    max_retries=0,  # 本节由应用层统一管理重试，避免双重重试
)

messages = [
    {
        "role": "system",
        "content": (
            "你是代码审查助手。只指出会影响正确性的问题，"
            "没有证据时不要猜测。"
        ),
    },
    {
        "role": "user",
        "content": "审查：def divide(a, b): return a / b",
    },
]

completion = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=messages,
    max_tokens=512,
    extra_body={"thinking": {"type": "disabled"}},
)

choice = completion.choices[0]
print(choice.message.content)
print("finish_reason:", choice.finish_reason)
print("usage:", completion.usage)
```



阅读这段代码时，不要只看到 `create()`。要能指出输入输出契约：



- `model` 决定具体模型和能力集合；

- `messages` 是本轮完整上下文，不是服务器替我们保管的“聊天窗口”；

- 消息顺序属于协议的一部分；

- `max_tokens` 是输出上限，不是期望输出长度；

- `choices[0].message` 是本轮 assistant 消息；

- `finish_reason` 决定输出是正常结束、长度截断还是工具调用；

- `usage` 是成本、限额和上下文治理的真实依据。

Chat Completions 的典型返回可以抽象为：



```JSON
{
  "id": "chatcmpl_xxx",
  "model": "deepseek-v4-flash",
  "choices": [
    {
      "index": 0,
      "message": {
        "role": "assistant",
        "content": "...",
        "tool_calls": null
      },
      "finish_reason": "stop"
    }
  ],
  "usage": {
    "prompt_tokens": 50,
    "completion_tokens": 80,
    "total_tokens": 130
  }
}
```



在 Agent Loop 中，如果返回了 `tool_calls`，当前 turn 还没有结束。Harness 要校验工具名和参数，执行工具，再把带有对应 `tool_call_id` 的 `tool` 消息追加到历史中，然后再次调用模型。



### **3\.4 Responses API 的请求与返回**



同一个模型可以通过 Responses API 调用：



```Python
import os
from openai import OpenAI

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
    timeout=30.0,
    max_retries=0,
)

response = client.responses.create(
    model="deepseek-v4-flash",
    instructions=(
        "你是代码审查助手。只指出会影响正确性的问题，"
        "没有证据时不要猜测。"
    ),
    input="审查：def divide(a, b): return a / b",
    max_output_tokens=512,
    reasoning={"effort": "none"},
)

print(response.output_text)
print("status:", response.status)
print("usage:", response.usage)

for item in response.output:
    print("item type:", item.type)
```



这里最重要的变化不是 `messages` 改名为 `input`，而是返回值从“choice 中的一条 message”变成“由多个类型化 item 组成的 output”。模型可以先产生 reasoning item，再产生 message 或 function call item。流式接口则会给出 `response.output_text.delta`、`response.function_call_arguments.done`、`response.completed`、`response.incomplete`、`response.failed` 等语义事件。



这对 Agent Loop 很重要：Loop 不必猜一段文本到底是普通回答、工具参数还是结束信号；协议已经提供类型和生命周期。



### **3\.5 两种 API 的关键映射**



|关注点|Chat Completions|Responses|
|---|---|---|
|主要输入|`messages`|`instructions` \+ `input` / items|
|主要输出|`choices[].message`|`output[]` items|
|文本便捷读取|`choices[0].message.content`|`response.output_text`|
|输出上限|`max_tokens`|`max_output_tokens`|
|工具动作|message 中的 `tool_calls`|独立 `function_call` item|
|流式结束|chunk / finish reason|`completed`、`incomplete`、`failed` 事件|
|多轮状态|应用重传消息历史|取决于供应商能力；不可假定均支持服务端状态|



注意，**API 格式兼容不等于能力完全兼容**。DeepSeek 的 Responses 兼容层当前不支持 \`previous\_response\_id\`、\`conversation\`、\`store\` 和 \`background\` 等部分 OpenAI 语义。Adapter 必须维护能力矩阵，不能看到相同 SDK 方法名就假设行为完全相同。

## **四、目标二：模型参数不是“质量旋钮”**



### **4\.1\`temperature\` 是什么**



模型每生成一个 token，都会对候选 token 产生一组分数。`temperature` 会改变这些分数经过 softmax 后的概率分布。简化表达为：



$P_i = \frac{e^{z_i/T}}{\sum_j e^{z_j/T}}$



其中 $z_i$ 是候选 token 的 logit，$T$ 是 temperature。



- 较低的 temperature 会让高概率候选更集中，输出通常更稳定；

- 较高的 temperature 会让分布更平，低概率候选更有机会被选中，输出通常更多样；

- temperature 改变的是采样分布，不会给模型补充缺失知识，也不会修复错误上下文。

“temperature 低，所以答案一定正确”是错误理解。低 temperature 只能让模型更稳定地沿着当前概率分布生成。如果 prompt 给错了文件、检索结果过期、Schema 定义错误，模型只会更稳定地输出错误结果。



同样，temperature 设为 0 也不应被宣传为绝对确定。供应商实现、并行计算、模型版本、系统路由和后端更新都可能导致差异。需要可回归性时，要固定模型快照、参数、输入和工具结果，并通过 Eval 测量，而不是依赖“0 等于绝对一致”。



### **4\.2\`top\_p\` 是什么**



`top_p` 又叫 核采样（nucleus sampling）。它先按概率从高到低选择最小候选集合，使集合累计概率达到阈值 $p$，再从这个集合中采样。



例如，候选概率为：



|Token|原概率|
|---|---|
|`inspect`|0\.50|
|`test`|0\.25|
|`edit`|0\.15|
|`delete`|0\.06|
|其他|0\.04|



当 `top_p=0.8` 时，采样集合大致只需包含前三个 token，因为累计概率已经达到 0\.90。尾部低概率候选被排除。



temperature 是重塑整个概率分布，top\_p 是裁剪候选集合。两者都影响采样随机性，因此一次对照实验中通常只改变一个，另一个保持默认。否则输出变化后，我们无法判断是哪个参数造成的。



### **4\.3\`max\_tokens\` / \`max\_output\_tokens\` 是什么**



它们表示本次调用最多允许生成多少输出 token：



- Chat Completions 常用 `max_tokens`；

- Responses 使用 `max_output_tokens`；

- 达到上限时，输出可能在句子、JSON 字符串或工具参数中间被截断；

- 它不保证模型一定输出这么长；

- 它也不是成本的唯一上限，因为输入、推理 token、工具调用和重试同样会消耗预算。

在 Agent 系统里，输出截断不是“答案短一点”，而是一种必须进入状态机的失败状态。自然语言可以提示用户内容不完整；结构化对象和工具参数则必须禁止执行。



```Python
def assert_complete(status: str, finish_reason: str | None) -> None:
    incomplete_reasons = {"length", "max_tokens", "max_output_tokens"}
    if status == "incomplete" or finish_reason in incomplete_reasons:
        raise RuntimeError("MODEL_OUTPUT_TRUNCATED")
```



### **4\.4 为什么不能随意调参**



|错误做法|为什么无效或危险|正确动作|
|---|---|---|
|答错了就调高 temperature|随机性不等于推理质量|检查目标、上下文、模型能力和 Eval 失败样本|
|JSON 不合法就把 temperature 设为 0|不能替代 Schema 约束和本地校验|使用 Structured Output \+ Pydantic|
|回答不完整就无限增大 max tokens|可能推高延迟和成本，仍可能偏题|设计合适输出契约、拆分任务、预留预算|
|同时修改 temperature 和 top\_p|无法归因|单变量实验并固定测试集|
|所有模型复制同一组参数|模型支持范围和语义不同|Adapter 做能力校验和参数映射|



DeepSeek V4 还有一个非常值得记住的工程细节：**\*\*thinking 模式下不支持 \`temperature\` 和 \`top\_p\`；为兼容客户端，即使传入也不会报错，只是没有效果。\*\*** 如果系统日志只记录“发送了 temperature=0\.2”，却不记录模型和 thinking 模式，调试人员会误以为参数已经生效。



因此，参数记录至少包含：供应商、模型实际版本、模式、请求参数、实际生效参数和被忽略参数。



### **4\.5 基于 DeepSeek V4 Flash 的对照实验**



这个实验必须显式关闭 thinking，否则 temperature 和 top\_p 不生效：



```Python
import os
from collections import Counter
from openai import OpenAI

MODEL = "deepseek-v4-flash"
TRIALS = int(os.getenv("TRIALS", "3"))
PROMPT = (
    "为一个“把模型错误统一归一化”的 Python 函数起更短的名字。"
    "允许使用缩写、同义词或不同动词形式。"
    "只输出 1 个 snake_case 名称，不要解释。"
)

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
    timeout=30.0,
    max_retries=0,
)

def sample(*, temperature: float, top_p: float) -> str:
    response = client.chat.completions.create(
        model=MODEL,
        messages=[{"role": "user", "content": PROMPT}],
        temperature=temperature,
        top_p=top_p,
        max_tokens=16,
        extra_body={"thinking": {"type": "disabled"}},
    )
    return response.choices[0].message.content.strip()

def run_case(*, label: str, temperature: float, top_p: float) -> None:
    values = [sample(temperature=temperature, top_p=top_p) for _ in range(TRIALS)]
    counts = Counter(values)

    print(f"\n[{label}] temperature={temperature}, top_p={top_p}")
    print(f"样本: {values}")
    print(f"去重数: {len(counts)}/{TRIALS}")
    print("Top 频次:", counts.most_common(5))

def main() -> None:
    print("=== 固定 top_p=1.0，只观察 temperature ===")
    for temperature in [0.0, 0.3, 0.8, 1.3]:
        run_case(
            label="temperature 对照组",
            temperature=temperature,
            top_p=1.0,
        )

    print("\n=== 固定 temperature=1.0，只观察 top_p ===")
    for top_p in [1.0, 0.7, 0.3, 0.1]:
        run_case(
            label="top_p 对照组",
            temperature=1.0,
            top_p=top_p,
        )

if __name__ == "__main__":
    main()

```



实验观察的不是“哪个名字最好”，而是：重复率、格式合规率、响应长度、任务成功率是否变化。参数选择必须与评测指标绑定。



推荐的初始工程策略是：



- 抽取、路由、工具选择、结构化计划：优先稳定设置，并由 Eval 决定是否调整；

- 创意候选生成：可以提高多样性，但候选仍需排序和验证；

- thinking 模型：先查文档和能力矩阵，确认哪些采样参数实际生效；

- `max_tokens`：根据输出 Schema 和历史 usage 的分位数设置，同时保留截断处理。

## **五、目标三：Token 与 Context Window**



### **5\.1 Token 是什么**



模型不是按字符或“字数”读取内容，而是先通过 tokenizer 把文本切分为 token。中文、英文、代码、缩进、标点和长标识符的 token 比例不同，所以不能用 `len(text)` 直接代替 token 数量。



一次调用的 token 通常至少包含：



- 输入 token：指令、用户内容、历史消息、工具定义、工具结果、Schema；

- 输出 token：模型最终文本、结构化输出、工具参数；

- 缓存输入 token：供应商命中 prompt/context cache 的输入部分；

- 某些模型还会区分推理 token，但字段和计费方式由供应商定义。

### **5\.2 Context Window 是什么**



Context Window 是单次模型请求可处理的总上下文容量。对 Agent 来说，它不是“用户可以输入多少字”，而是本轮所有输入、协议开销和输出预留的共同上限。



可以用下面的预算式理解：



```Plain Text
可用业务输入
= Context Window
- 系统 / developer 指令
- 工具定义与 JSON Schema
- 历史消息
- 历史工具结果
- 预留输出 token
- 安全余量
```



Agent Loop 会不断把工具结果追加进上下文。如果没有预算管理，运行通常不会在第一轮失败，而会在第 8、20 或 50 轮突然超出窗口。更隐蔽的情况是：框架静默截断前面的消息，把最初目标或安全约束丢掉，模型仍然继续运行，却已经不再解决原任务。



### **5\.3 为什么这部分不能交给模型自己管理**



模型只能看到最终发送给它的上下文。被截掉的目标，它不知道；没有传入的错误日志，它也无法主动找回；被摘要器错误压缩的数字，它可能当成事实继续使用。



所以 Context Manager 必须由 Harness 控制，并把内容分为三类：



1. 必须保留：用户目标、硬约束、当前状态、未完成的 tool call、最近错误、完成条件；

2. 可以摘要：已完成步骤、重复解释、较早的对话和冗长日志；

3. 可以外部化：完整文件、全量测试日志、二进制内容和可重新读取的数据。

### **5\.4 一个可执行的预算器**



```Python
"""一个可执行的上下文预算器示例。

这段代码把“大模型上下文预算”这个抽象概念，落成了可以直接运行、
可以被单元测试、也可以被业务代码复用的预算规则对象。
"""

from dataclasses import dataclass

@dataclass(frozen=True)
class ContextBudget:
    """用不可变数据对象描述一次请求的上下文预算配置。

    1. 制定一个预算参数的数据模型，便于传递和复用。
    2. `frozen=True` 表示预算配置创建后不再被随意修改，减少运行时状态污染。
    3. 这也是把“配置”和“决策逻辑”分离开的一个基础动作。
    """

    context_window: int
    reserve_output: int
    protocol_overhead: int
    safety_margin: int

    @property
    def max_business_input(self) -> int:
        """计算真正可分配给业务输入的 token 上限。

        1. 总窗口并不等于都能拿来放用户输入，还要扣掉输出预留、协议开销和安全余量。
        2. 这里把“预算计算公式”收口成一个可复用属性，调用方不需要重复手写。
        3. 主动校验 `value <= 0`，是在用代码保护配置正确性，避免错误预算进入后续流程。
        """

        value = (
            self.context_window
            - self.reserve_output
            - self.protocol_overhead
            - self.safety_margin
        )
        if value <= 0:
            raise ValueError("上下文预算配置无效")
        return value

def choose_context_action(estimated_input: int, budget: ContextBudget) -> str:
    """根据预计输入规模，返回当前请求应该采取的上下文处理策略。

    1. 这一步把“容量判断”翻译成“业务动作”，让预算器真正可以执行决策。
    2. 用比例阈值而不是写死某个 token 数，说明规则可以跟随不同模型窗口一起伸缩。
    3. 返回的是策略名而不是直接执行动作，方便上层系统继续编排 summarize、reject 等流程。
    """

    ratio = estimated_input / budget.max_business_input
    if ratio <= 0.75:
        return "keep"
    if ratio <= 1.0:
        return "summarize_old_tool_results"
    return "externalize_or_reject"

# 这里给出一组可直接运行的示例预算配置，方便把抽象规则变成具体数字。
budget = ContextBudget(
    context_window=1_000_000,
    reserve_output=16_000,
    protocol_overhead=8_000,
    safety_margin=32_000,
)

```



DeepSeek V4 官方当前标注 1M context 和最高 384K 输出，但这不意味着每次请求都应该使用接近上限的内容。长上下文会增加延迟、成本和注意力稀释风险。生产预算应由真实任务分布决定，而不是由模型规格上限决定。



请求前使用供应商 tokenizer、计数接口或保守估算做准入检查；请求后必须记录服务端返回的真实 usage。估算用于保护，真实 usage 用于计费、复盘和后续校准。



### **课堂练习**



借助大模型生成一段用户目标、三份源文件、一次 30,000 token 的测试日志和五轮历史对话。要求你给每部分标注“保留、摘要、外部化”，并说明如果预算仍然不足，应当终止还是继续压缩。



判断标准不是“尽量都塞进去”，而是最小充分上下文：让模型看到完成当前决策必需的事实，同时保留可追溯的外部原文。

## **六、目标四：Structured Output——模型输出与程序世界的边界**



### **6\.1 它是什么**



Structured Output 是让模型按照预先定义的结构返回数据，使下游程序能够解析、校验并据此执行。常见手段有三种：



1. Prompt 约定：“请返回 JSON”；

2. JSON mode：API 保证返回合法 JSON；

3. 原生 Structured Output：API 接收 JSON Schema，并约束输出符合 Schema。

Pydantic 则位于应用侧：我们用 Python 类型定义领域对象，对模型返回的数据做解析、类型校验和业务校验，也可以从模型生成 JSON Schema。



这几种能力不能混为一谈。“合法 JSON”只说明花括号和引号可解析，不代表字段齐全、类型正确，更不代表业务动作安全。



### **6\.2 为什么 Agent 不能依赖自然语言解析**



假设模型返回：



```Plain Text
我建议先执行测试。命令是 pytest，风险不高，可以直接运行。
```



人能看懂，但程序面临一连串歧义：命令是 `pytest` 还是一整句话？工作目录在哪里？超时多久？“风险不高”对应哪个枚举？是否需要审批？



如果用字符串查找或正则表达式解析自然语言，一旦模型改变措辞、语言或换行，执行路径就可能改变。这不是一个稳定协议。



所以我们把输出定义为领域对象：



```JSON
{
  "action": "run_tests",
  "command": ["pytest", "-q"],
  "reason": "验证现有失败",
  "risk": "execute",
  "requires_approval": false
}
```



### **6\.3 AI 为什么不能替开发者定义 Schema**



AI 可以根据自然语言草拟 Schema，但最终 Schema 必须由开发者审查，因为它编码了业务协议和安全边界。



模型不知道：



- `command` 应该是字符串还是参数数组；

- 路径是否允许绝对路径或 `..`；

- `risk` 有哪些合法枚举；

- 哪些字段必须存在；

- 未知字段应该忽略还是拒绝；

- Schema v1 升级到 v2 时，旧消费者怎样兼容；

- 这个动作能否在生产环境执行。

如果让模型同时决定输出、定义校验规则、判断自己是否合格，就等于让被校验者制定并执行自己的考试标准。



### **6\.4 三层校验**



模型输出进入 Loop 前必须经过：



|层次|解决的问题|不能解决的问题|
|---|---|---|
|JSON 语法校验|是否能解析|字段和业务含义是否正确|
|Schema / Pydantic 校验|类型、必填、枚举、额外字段|路径权限、资源存在性、业务状态|
|业务校验|是否满足当前环境和领域规则|最终操作是否成功，仍需执行后验证|



### **6\.5 使用 Pydantic 定义协议**



```Python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field, model_validator

class AgentAction(BaseModel):
    model_config = ConfigDict(extra="forbid")

    action: Literal["inspect", "edit", "run_tests", "finish"]
    reason: str = Field(min_length=1, max_length=500)
    path: str | None = None
    command: list[str] | None = None

    @model_validator(mode="after")
    def validate_action_fields(self) -> "AgentAction":
        if self.action in {"inspect", "edit"} and not self.path:
            raise ValueError("inspect/edit 必须提供 path")
        if self.action == "run_tests" and not self.command:
            raise ValueError("run_tests 必须提供 command")
        return self
```



这段模型完成两件事：生成机器可读的 JSON Schema，以及在本地建立信任边界。`extra="forbid"` 很重要，因为模型多返回一个看似合理的 `shell=true` 字段，不应该被悄悄忽略。



### **6\.6 DeepSeek V4 Flash：JSON mode \+ Pydantic**



Chat Completions 的 JSON mode 保证合法 JSON，但仍要本地校验字段：



```Python
import json
import os
from openai import OpenAI
from typing import Literal

from pydantic import BaseModel, Field, ValidationError

class AgentAction(BaseModel):
    # 概念：先用 Pydantic 定义“期望输出结构”，把输出格式从“自然语言约定”
    # 升级成“代码里的显式契约”。这样既方便人阅读，也方便程序做自动校验。
    step: Literal["inspect_logs", "run_tests", "read_code", "ask_user"] = Field(
        description="Agent 下一步要执行的动作"
    )
    reason: str = Field(description="选择这个动作的原因")
    needs_user_input: bool = Field(description="是否需要向用户补充提问")
    confidence: float = Field(ge=0, le=1, description="当前判断的置信度，范围 0 到 1")

client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
    max_retries=0,
)

# Pydantic 可以直接把模型转成 JSON Schema，避免我们手写字段说明。
# 好处是：提示词、数据结构、校验规则三者共用一份定义，不容易随着迭代逐渐漂移。
schema = AgentAction.model_json_schema()

response = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=[
        {
            "role": "system",
            "content": (
                "你是 Agent 决策器。必须输出 json。"
                "输出必须符合以下 JSON Schema：\n"
                f"{json.dumps(schema, ensure_ascii=False)}"
            ),
        },
        {
            "role": "user",
            "content": "目标：检查 tests/test_api.py 为什么失败。当前还没有测试日志。",
        },
    ],
    # JSON mode 的价值：强约束模型返回合法 JSON，减少多余解释、Markdown 包裹、
    # 漏括号等格式问题，让下游代码更容易稳定解析。
    response_format={"type": "json_object"},
    max_tokens=1024,
    extra_body={"thinking": {"type": "disabled"}},
)

raw_text = response.choices[0].message.content
if not raw_text:
    raise RuntimeError("MODEL_EMPTY_RESPONSE: 模型没有返回任何内容")

try:
    # Pydantic 的价值：JSON mode 只能尽量保证“像 JSON”，但不能保证字段名、枚举值、
    # 类型和数值范围都完全符合业务要求；这里再做一次模型校验，才能把输出真正变成
    # “可直接进入业务逻辑”的结构化数据。
    action = AgentAction.model_validate_json(raw_text)
except ValidationError as exc:
    raise RuntimeError(f"MODEL_SCHEMA_INVALID: {exc}") from exc

print(action)

```



DeepSeek 官方特别提示：JSON mode 要在 prompt 中包含 `json`，合理设置 `max_tokens` 以避免截断，而且可能偶发空内容。工程代码不能只调用 `json.loads()` 然后假定成功。



### **6\.7 DeepSeek Responses：原生 JSON Schema**



DeepSeek 当前的 Responses 兼容文档标明 `text.format` 受支持，因此可以把 Schema 直接交给 API：



```Python
response = client.responses.create(
    model="deepseek-v4-flash",
    instructions="你是 Agent 决策器。输出下一步动作。",
    input="目标：检查 tests/test_api.py 为什么失败。当前还没有测试日志。",
    reasoning={"effort": "none"},
    max_output_tokens=1024,
    text={
        "format": {
            "type": "json_schema",
            "name": "agent_action",
            "strict": True,
            "schema": AgentAction.model_json_schema(),
        }
    },
)

if response.status != "completed":
    raise RuntimeError(f"MODEL_NOT_COMPLETED: {response.status}")

action = AgentAction.model_validate_json(response.output_text)
```



即使 API 宣称严格遵守 Schema，本地 Pydantic 校验仍然保留，原因有四个：供应商实现可能不同；模型或 API 版本会变化；缓存和历史数据可能来自旧 Schema；业务校验不属于模型原生 Structured Output 的职责。



### **6\.8 业务校验不能省略**



```Python
from pathlib import Path

def validate_business_rules(action: AgentAction, workspace: Path) -> AgentAction:
    if action.path:
        resolved = (workspace / action.path).resolve()
        if workspace.resolve() not in resolved.parents and resolved != workspace.resolve():
            raise ValueError("路径逃逸工作区")

    if action.command and action.command[0] not in {"pytest", "ruff", "mypy"}:
        raise ValueError("命令不在允许列表")

    return action
```



Schema 证明 `command` 是字符串数组，业务校验才证明第一个命令位于允许列表；真正执行后，还要用退出码和测试报告证明动作成功。



### **输出失败的处理边界**



- 空输出：视为格式失败，可在预算内重试一次；

- JSON 语法错误：记录原始脱敏摘要，可请求一次格式修复；

- Schema 错误：把精简后的校验错误反馈给模型，不回传整段堆栈；

- 业务规则失败：不要让模型通过改写 JSON 绕过权限，直接拒绝或请求人工确认；

- 截断：禁止解析和执行，增大合理输出预算或缩小任务；

- 拒答：进入 refusal 分支，不当成 JSON 错误无限修复。

## **七、目标五：错误分类、重试、退避、降级与终止**



### **7\.1 错误发生在什么时候**



一次模型调用至少经过六个阶段，每个阶段的失败性质不同：



1. 请求构造：参数、Schema 或消息格式错误；

2. 鉴权与准入：API Key 无效、余额不足、权限不足；

3. 网络传输：DNS、连接中断、连接超时；

4. 服务调度：限流、并发超限、服务过载、内部错误；

5. 模型生成：内容拒答、达到输出上限、响应不完整；

6. 应用解析：空输出、JSON 错误、Schema 错误、业务校验失败。

如果把所有失败都写成 `except Exception: retry()`，系统会产生三类严重问题：对永久错误无意义重试；重试风暴进一步压垮服务；同一个 Agent turn 重复扣费，甚至间接触发重复工具动作。



### **7\.2 分类与策略表**



|类型|常见时机 / 信号|主要问题|默认策略|
|---|---|---|---|
|认证失败|HTTP 401|Key 错误或无权限，不会自行恢复|立即终止，提示检查凭证；绝不 fallback 泄露请求|
|参数/请求错误|HTTP 400/422|协议、模型名、Schema 或上下文错误|立即终止或修正请求；不做同参重试|
|余额不足|HTTP 402|账户资源不足|终止或按明确策略切换已授权供应商|
|限流|HTTP 429|QPS/并发/配额超限|尊重 `Retry-After`，指数退避 \+ jitter，有限重试|
|服务端错误|HTTP 500|临时内部故障|有限重试，持续失败后降级|
|服务过载|HTTP 503|当前容量不足|更长退避或切换备用模型/供应商|
|连接/读取超时|timeout / connection error|结果状态不确定|幂等模型请求可有限重试；记录 attempt|
|内容拒答|200 响应中的 refusal / content filter|安全策略或内容边界|不机械重试；改写合法目标、解释或终止|
|输出截断|`finish_reason=length` / `status=incomplete`|JSON/工具参数可能不完整|禁止执行；缩短输入或合理提高输出预算|
|输出格式错误|JSON/Pydantic 校验失败|下游无法安全消费|最多一次定向修复，之后降级或终止|



DeepSeek 当前公开错误码包含 400、401、402、422、429、500 和 503。生产 Adapter 应优先根据 HTTP 状态、SDK 异常类型和响应状态归一化，而不是依赖错误消息字符串。



### **7\.3 有边界的策略是什么**



一个合格的重试策略至少有六条边界：



1. 只重试明确的临时错误；

2. 有最大尝试次数；

3. 有指数退避和随机抖动；

4. 尊重服务端 `Retry-After`；

5. 每次尝试都计入时间、token 和费用预算；

6. 重试耗尽后有明确的 fallback 或终止状态。

退避可以写成：



$delay = \min(cap, base \times 2^{attempt-1}) + jitter$



jitter 用来避免大量实例在同一时间再次请求，形成“惊群”。



### **7\.4 Python 错误归一化**



```Python
from dataclasses import dataclass
from typing import Literal

from openai import (
    APIConnectionError,
    APITimeoutError,
    AuthenticationError,
    BadRequestError,
    InternalServerError,
    RateLimitError,
)
from pydantic import ValidationError

ErrorCode = Literal[
    "authentication",
    "invalid_request",
    "rate_limited",
    "overloaded",
    "timeout",
    "network",
    "refusal",
    "truncated",
    "schema_invalid",
    "unknown",
]

@dataclass
class ModelCallError(Exception):
    code: ErrorCode
    message: str
    retryable: bool
    status_code: int | None = None
    request_id: str | None = None


def normalize_exception(exc: Exception) -> ModelCallError:
    if isinstance(exc, AuthenticationError):
        return ModelCallError("authentication", str(exc), False, 401)

    if isinstance(exc, BadRequestError):
        return ModelCallError(
            "invalid_request",
            str(exc),
            False,
            getattr(exc, "status_code", None),
        )

    if isinstance(exc, RateLimitError):
        return ModelCallError("rate_limited", str(exc), True, 429)

    if isinstance(exc, APITimeoutError):
        return ModelCallError("timeout", str(exc), True)

    if isinstance(exc, APIConnectionError):
        return ModelCallError("network", str(exc), True)

    if isinstance(exc, InternalServerError):
        status = getattr(exc, "status_code", None)
        code: ErrorCode = "overloaded" if status == 503 else "unknown"
        return ModelCallError(code, str(exc), True, status)

    if isinstance(exc, ValidationError):
        return ModelCallError("schema_invalid", str(exc), False)

    return ModelCallError("unknown", str(exc), False)
```



注意：不同 SDK 版本可能调整异常层次。Adapter 应通过契约测试验证映射，并始终为未知错误保留兜底分支和请求 ID。



### **7\.5 Python 有限重试与退避**



```Python
import random
import time
from collections.abc import Callable
from typing import TypeVar

T = TypeVar("T")

def call_with_retry(
    operation: Callable[[], T],
    *,
    max_attempts: int = 3,
    base_delay: float = 0.5,
    max_delay: float = 8.0,
    total_deadline: float = 20.0,
) -> T:
    started = time.monotonic()
    last_error: ModelCallError | None = None

    for attempt in range(1, max_attempts + 1):
        try:
            return operation()
        except Exception as raw_exc:
            error = normalize_exception(raw_exc)
            last_error = error

            deadline_exceeded = time.monotonic() - started >= total_deadline
            if not error.retryable or attempt == max_attempts or deadline_exceeded:
                raise error from raw_exc

            exponential = min(max_delay, base_delay * 2 ** (attempt - 1))
            jitter = random.uniform(0, exponential * 0.25)
            time.sleep(exponential + jitter)

    assert last_error is not None
    raise last_error
```



示例调用：



```Python
def request_once():
    return client.responses.create(
        model="deepseek-v4-flash",
        input="把错误日志归类为 network、timeout、rate_limit 或 application。",
        max_output_tokens=256,
        reasoning={"effort": "none"},
    )

response = call_with_retry(request_once)
```



这里将 SDK 的 `max_retries` 设为 0，是为了避免 SDK 内部重试 3 次、外层再重试 3 次，最终变成最多 9 次而团队毫不知情。也可以选择完全使用 SDK 重试，但全系统必须只有一个清晰的重试所有者。



### **7\.6 内容拒答与格式错误不是一回事**



模型调用 HTTP 200，不代表业务成功。Responses 可能以 item 或 incomplete reason 表达拒答/内容过滤；Chat Completions 也可能在消息或 finish reason 中表达安全终止。



处理顺序应该是：



```Python
def parse_response(response) -> AgentAction:
    if response.status == "incomplete":
        reason = getattr(response.incomplete_details, "reason", "unknown")
        if reason == "content_filter":
            raise ModelCallError("refusal", "内容被安全策略拒绝", False)
        raise ModelCallError("truncated", f"输出不完整: {reason}", False)

    if response.status == "failed":
        raise ModelCallError("unknown", str(response.error), True)

    if not response.output_text:
        raise ModelCallError("schema_invalid", "模型返回空内容", False)

    try:
        return AgentAction.model_validate_json(response.output_text)
    except ValidationError as exc:
        raise ModelCallError("schema_invalid", str(exc), False) from exc
```



对 Schema 错误可以设计一次“定向修复”：只把 Schema 名称、缺失字段和枚举错误反馈给模型，并要求重发完整对象。但最多修复一次或两次；持续失败说明模型能力、Schema 复杂度或上下文存在系统性问题，不应无限循环。



### **7\.7 降级怎么设计**



降级不是“主模型失败就随便换一个便宜模型”。首先定义等价能力：



- 是否支持目标上下文长度；

- 是否支持严格结构化输出；

- 是否支持工具调用；

- 是否支持当前输入模态；

- 是否满足数据合规和区域要求；

- 是否允许执行当前风险级别的任务。

推荐策略：



```Plain Text
临时错误
  → 同模型有限重试
  → 同供应商等价模型
  → 已授权的备用供应商
  → 人工接管或终止
```



认证失败、非法请求、业务校验失败默认不走这条链路。每次 fallback 必须记录原模型、错误类型、替代模型、能力差异和最终状态。



最后再强调一次：模型请求通常是只读生成，但模型结果可能驱动有副作用的工具。**模型调用的重试与工具执行的重试必须分开。** 付款、发消息、创建工单、运行迁移等动作要使用幂等键、执行日志和审批，不能因为上游超时就盲目重复。

## **八、目标六：Model Adapter 与多模型切换**



### **8\.1 为什么不能在 Loop 里直接调用 SDK**



最容易写出的 Agent Loop 往往长这样：



```Python
response = openai_client.responses.create(...)
if response.output[0].type == "function_call":
    ...
```



它能运行，但 Loop 已经绑定了供应商 SDK、Responses 数据结构、错误类型和参数命名。换成另一个只支持 Chat Completions 的模型时，Loop 中会迅速出现：



```Python
if provider == "openai":
    ...
elif provider == "deepseek":
    ...
```



再加入第三家后，业务 Loop 就变成供应商兼容层。此时没有任何人敢改重试、工具调用或完成逻辑，因为每一个分支都可能只对某个模型有效。



Model Adapter 的价值，是把“供应商怎样表达请求和响应”与“Agent 怎样推进任务”分开。



它带来五个直接好处：



1. 可替换：配置切换模型，不修改 Loop；

2. 可测试：用 Fake Adapter 独立测试 Loop 的状态机；

3. 可观测：统一记录 usage、错误、请求 ID 和 finish reason；

4. 可治理：集中处理参数映射、能力校验、超时和凭证；

5. 可演进：供应商 API 变化时，只修改 Adapter 和契约测试。

但“统一”不等于抹平差异。Adapter 必须暴露能力，而不是假装每个模型都支持相同的 Structured Output、工具、上下文和参数。



### **8\.2 定义内部协议**



```Python
from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from typing import Any, Literal

ResultKind = Literal["text", "structured", "tool_calls", "refusal"]

@dataclass(frozen=True)
class ModelCapabilities:
    chat_completions: bool
    responses: bool
    structured_output: Literal["native_schema", "json_mode", "prompt_only"]
    tool_calling: bool
    supports_temperature: bool
    supports_top_p: bool

@dataclass(frozen=True)
class ModelRequest:
    system: str
    user: str
    max_output_tokens: int = 1024
    temperature: float | None = None
    top_p: float | None = None
    output_schema: dict[str, Any] | None = None

@dataclass
class ModelResult:
    kind: ResultKind
    text: str | None = None
    data: dict[str, Any] | None = None
    tool_calls: list[dict[str, Any]] = field(default_factory=list)
    finish_reason: str | None = None
    input_tokens: int = 0
    output_tokens: int = 0
    request_id: str | None = None

class ModelAdapter(ABC):
    name: str
    capabilities: ModelCapabilities

    @abstractmethod
    def generate(self, request: ModelRequest) -> ModelResult:
        raise NotImplementedError
```



### **8\.3 DeepSeek Chat Completions Adapter**



```Python
import json
from openai import OpenAI

class DeepSeekChatAdapter(ModelAdapter):
    name = "deepseek-v4-flash-chat"
    capabilities = ModelCapabilities(
        chat_completions=True,
        responses=False,
        structured_output="json_mode",
        tool_calling=True,
        supports_temperature=True,  # 仅 non-thinking 生效
        supports_top_p=True,         # 仅 non-thinking 生效
    )

    def __init__(self, api_key: str) -> None:
        self.client = OpenAI(
            api_key=api_key,
            base_url="https://api.deepseek.com",
            timeout=30.0,
            max_retries=0,
        )

    def generate(self, request: ModelRequest) -> ModelResult:
        system = request.system
        kwargs: dict[str, Any] = {}

        if request.output_schema:
            system += (
                "\n必须输出 json，并符合此 JSON Schema：\n"
                + json.dumps(request.output_schema, ensure_ascii=False)
            )
            kwargs["response_format"] = {"type": "json_object"}

        if request.temperature is not None:
            kwargs["temperature"] = request.temperature
        if request.top_p is not None:
            kwargs["top_p"] = request.top_p

        raw = self.client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=[
                {"role": "system", "content": system},
                {"role": "user", "content": request.user},
            ],
            max_tokens=request.max_output_tokens,
            extra_body={"thinking": {"type": "disabled"}},
            **kwargs,
        )

        choice = raw.choices[0]
        text = choice.message.content or ""
        usage = raw.usage

        data = json.loads(text) if request.output_schema else None
        return ModelResult(
            kind="structured" if data is not None else "text",
            text=text,
            data=data,
            finish_reason=choice.finish_reason,
            input_tokens=getattr(usage, "prompt_tokens", 0) if usage else 0,
            output_tokens=getattr(usage, "completion_tokens", 0) if usage else 0,
            request_id=raw.id,
        )
```



真实项目还应在 Adapter 内补上：异常归一化、拒答判断、截断判断、工具调用映射和原始响应脱敏。这里先保留主干，让学员看清协议转换发生在哪里。



### **8\.4 OpenAI Responses Adapter**



第二个 Adapter 使用另一个供应商和 Responses 协议。模型名称通过配置传入，不写死在 Loop：



```Python
class OpenAIResponsesAdapter(ModelAdapter):
    name = "openai-responses"
    capabilities = ModelCapabilities(
        chat_completions=False,
        responses=True,
        structured_output="native_schema",
        tool_calling=True,
        supports_temperature=True,
        supports_top_p=True,
    )

    def __init__(self, api_key: str, model: str) -> None:
        self.model = model
        self.client = OpenAI(
            api_key=api_key,
            timeout=30.0,
            max_retries=0,
        )

    def generate(self, request: ModelRequest) -> ModelResult:
        kwargs: dict[str, Any] = {}

        if request.output_schema:
            kwargs["text"] = {
                "format": {
                    "type": "json_schema",
                    "name": "agent_result",
                    "strict": True,
                    "schema": request.output_schema,
                }
            }

        if request.temperature is not None:
            kwargs["temperature"] = request.temperature
        if request.top_p is not None:
            kwargs["top_p"] = request.top_p

        raw = self.client.responses.create(
            model=self.model,
            instructions=request.system,
            input=request.user,
            max_output_tokens=request.max_output_tokens,
            **kwargs,
        )

        if raw.status != "completed":
            raise RuntimeError(f"MODEL_NOT_COMPLETED: {raw.status}")

        text = raw.output_text or ""
        data = json.loads(text) if request.output_schema else None
        usage = raw.usage

        return ModelResult(
            kind="structured" if data is not None else "text",
            text=text,
            data=data,
            finish_reason=raw.status,
            input_tokens=getattr(usage, "input_tokens", 0) if usage else 0,
            output_tokens=getattr(usage, "output_tokens", 0) if usage else 0,
            request_id=raw.id,
        )
```



`supports_temperature=True` 只是示意能力，生产实现要细化到具体模型和模式；某些推理模型可能不支持或忽略这些参数。能力矩阵应该由 `(provider, model, mode)` 决定，而不只是供应商名称。



### **8\.5 Loop 不感知供应商**



```Python
class OneTurnLoop:
    def __init__(self, model: ModelAdapter) -> None:
        self.model = model

    def run(self, goal: str) -> AgentAction:
        request = ModelRequest(
            system=(
                "你是编码 Agent 的决策器。根据目标选择 inspect、edit、"
                "run_tests 或 finish。不要声称执行了尚未执行的动作。"
            ),
            user=goal,
            max_output_tokens=1024,
            output_schema=AgentAction.model_json_schema(),
        )

        result = self.model.generate(request)
        if result.kind != "structured" or result.data is None:
            raise RuntimeError("模型没有返回结构化动作")

        # Adapter 负责协议归一化，Loop 仍负责领域对象校验。
        return AgentAction.model_validate(result.data)
```



切换模型时只改变装配代码：



```Python
import os

provider = os.getenv("MODEL_PROVIDER", "deepseek")

if provider == "deepseek":
    adapter: ModelAdapter = DeepSeekChatAdapter(
        api_key=os.environ["DEEPSEEK_API_KEY"]
    )
elif provider == "openai":
    adapter = OpenAIResponsesAdapter(
        api_key=os.environ["OPENAI_API_KEY"],
        model=os.getenv("OPENAI_MODEL", "gpt-5.6"),
    )
else:
    raise ValueError(f"未知 MODEL_PROVIDER: {provider}")

loop = OneTurnLoop(adapter)
action = loop.run("检查 tests/test_api.py 失败原因，当前尚未运行测试。")
print(action)
```



请观察：`OneTurnLoop.run()` 没有任何 `if provider == ...`，也没有读取 `choices` 或 `output`。Loop 只认识 `ModelRequest`、`ModelResult` 和 `AgentAction`。



### **8\.6 Adapter 的测试重点**



每个 Adapter 至少要有以下契约测试：



- 相同内部请求能映射为供应商合法请求；

- 正常文本归一化为 `kind="text"`；

- 结构化结果归一化为 `kind="structured"`；

- 工具名、调用 ID 和参数不会丢失；

- usage 字段映射正确；

- 截断、拒答和失败状态不会伪装成正常文本；

- 不支持的参数会明确报错或记录为 ignored，而不是静默假装生效；

- 供应商异常能归一化为统一错误类型。

多模型的价值不是为了在架构图上多画两个方框，而是避免业务被一家供应商的协议锁死，并允许系统依据能力、成本、延迟和可用性做可审计选择。

## **九、练习：把六个目标接入最小 Agent Loop**

实现一个只做“下一步决策”的 Mini Coding Agent：输入一个代码任务和当前事实，输出一个经过 Pydantic 校验的 `AgentAction`。它暂不直接修改文件，只建立后续 Tool Runtime 所需的模型边界。



### **实现顺序**

1. 用 DeepSeek V4 Flash 的 Chat Completions 跑通一次文本调用；

2. 改用 JSON mode，并用 `AgentAction` 校验；

3. 加入输出截断、空内容和拒答分支；

4. 加入统一错误类型和最多三次的临时错误重试；

5. 实现 DeepSeek Chat Adapter 与另一个供应商的 Responses Adapter；

6. 用同一个 `OneTurnLoop` 切换两个 Adapter，确保 Loop 代码不变。



### **必须记录的 Trace 字段**

```JSON
{
  "run_id": "...",
  "turn": 1,
  "provider": "deepseek",
  "model": "deepseek-v4-flash",
  "api_style": "chat_completions",
  "mode": "non-thinking",
  "requested_parameters": {},
  "effective_parameters": {},
  "ignored_parameters": [],
  "input_tokens": 0,
  "output_tokens": 0,
  "latency_ms": 0,
  "attempt": 1,
  "finish_reason": "stop",
  "result_kind": "structured",
  "error_code": null,
  "request_id": "..."
}
```



Trace 不保存明文 API Key；生产环境中的 prompt、代码和模型原始响应也要根据数据分级做脱敏或关闭记录。



### **常见的面试题**



1. 为什么 Chat Completions 仍是重要的跨供应商基线，而新 Agent 应用又要研究 Responses？

2. 为什么 `temperature=0` 不等于事实正确，也不应承诺绝对确定？

3. 为什么 DeepSeek thinking 模式下记录了 `temperature`，也不代表它实际生效？

4. 为什么 `max_tokens` 过小在 Agent 中可能成为安全问题？

5. “JSON 可解析”“符合 Schema”“业务允许执行”分别由谁保证？

6. 为什么认证失败不能重试，429 可以有限重试，内容拒答不能机械重试？

7. 为什么模型调用重试与工具执行重试必须分开？

8. Model Adapter 应该统一什么，又必须保留哪些模型差异？
