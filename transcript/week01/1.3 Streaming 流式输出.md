## **二、目标拆解：为什么 Agent 开发工程师不能只会“打字机效果”**



传统 HTTP 接口通常在业务逻辑全部执行完成后返回一个完整 JSON。这个模型适合耗时较短、结果相对确定的请求：调用方发起请求，服务端计算，最后一次性返回结果。



LLM 和 Agent 任务不同。



一次模型生成可能持续数秒甚至数十秒；一次 Agent 运行还可能包含多轮模型推理、文件检索、命令执行、工具审批和结果校验。如果整个过程只在最后返回一个 JSON，用户在几十秒内无法判断系统究竟是：



- 正在排队；

- 正在生成；

- 正在调用工具；

- 卡在外部服务；

- 已经偏离目标；

- 还是早已失败但没有及时返回。

因此，Streaming 在 Agent 系统中不只是 UI 层的“逐字显示”，而是一条从 Agent Runtime 到交互层的**事件通道**。



这条通道至少要承载三类信息：



|类别|典型事件|作用|
|---|---|---|
|内容事件|`text.delta`、`message.completed`|增量展示模型输出|
|过程事件|`tool.started`、`tool.completed`、`run.retrying`|暴露 Loop 当前状态|
|控制事件|`run.cancelled`、`run.failed`、`run.completed`|让客户端知道运行如何终止|



很多开发者第一次实现 Streaming，会直接把模型 SDK 返回的 chunk 原样转发到浏览器。这种代码能演示，但不能成为 Harness 的稳定边界。



原因是模型供应商的流式协议并不相同：



- 有的接口返回 `choices[0].delta.content`；

- 有的接口返回带类型的 `response.output_text.delta`；

- 工具调用参数可能被拆成多个增量片段；

- usage 可能只在最后一个事件出现；

- 正常结束、内容拒答和长度截断使用不同字段表达；

- SDK 升级后事件类型和对象结构也可能变化。

如果浏览器直接依赖供应商事件，模型切换会同时影响前端、CLI、日志、Trace 和恢复逻辑。正确的分层应当是：



```Plain Text
模型供应商流
    ↓
Model Adapter：解析供应商 chunk
    ↓
Harness Event：统一的内部事件
    ↓
Event Store：持久化与排序
    ↓
SSE Gateway：编码为传输协议
    ↓
Web / CLI / IDE：按事件类型消费
```



这一节的六个目标分别解决：



1. 延迟指标解决“为什么要流、流能带来什么”；

2. SSE 与事件协议解决“流在网络上怎样表达”；

3. 模型转发解决“供应商 chunk 怎样进入 Harness”；

4. 客户端消费解决“网络字节怎样还原成业务事件”；

5. 取消传播解决“怎样真正停止成本，而不只是停止显示”；

6. 重试与 checkpoint 解决“流中断后怎样保证不重复、不丢失、不无限重来”。



请记住本节的核心结论：

**文本 delta 是 Streaming 的数据面；状态、取消、错误和恢复才是 Agent Streaming 的控制面。**

## **三、目标一：为什么 LLM 应用需要 Streaming**



### **3\.1 三种延迟必须分开测量**



假设模型在收到请求 2\.4 秒后产生第一个 Token，之后用 9\.6 秒生成完整答案。非流式接口会让用户等待约 12 秒后一次性看到结果；流式接口能让用户在约 2\.4 秒时开始看到内容。



这里有三个不同指标：

|指标|含义|主要受什么影响|
|---|---|---|
|TTFT|请求发出到首个可用 Token 的时间|排队、输入长度、模型调度、Prefill|
|Generation Time|首 Token 到生成结束的时间|输出长度、解码速度、推理强度|
|End\-to\-End Latency|用户操作到任务最终完成的时间|网络、模型、多轮 Loop、工具、持久化|



Streaming 可以降低“第一次看到结果”的等待，但不会自动减少模型推理耗时，也不会自动缩短工具执行时间。



因此，下面的说法是错误的：



> 开启 `stream=True` 后，模型会生成得更快。
> 
> 



更准确的说法是：



> 开启流式返回后，应用可以在模型尚未生成完整结果时消费已产生的增量，因此改善感知延迟，并获得提前取消的机会。
> 
> 



### **3\.2 为什么 Agent 比普通聊天更需要流**



普通聊天的主要输出是文本。Agent Loop 的输出是不断变化的运行状态：



```Plain Text
接收任务
→ 模型判断需要搜索代码
→ 工具开始执行
→ 工具返回结果
→ 模型继续分析
→ 修改文件
→ 运行测试
→ 校验完成
```



如果系统只流式输出模型文本，却不输出工具状态，用户会在工具执行期间看到界面停止更新，误以为系统卡死。因此生产级 Agent 应流式传输**语义事件**，而不是只传输字符。



### **3\.3 Streaming 能解决什么，不能解决什么**



Streaming 能解决：

- 尽早展示已生成内容；

- 展示长任务进度；

- 允许用户提前发现方向错误；

- 允许用户取消后续生成和工具调用；

- 增量记录一次 Run 的事实轨迹；

- 为 Web、CLI、IDE 提供同一条运行事件流。



Streaming 不能解决：

- 模型本身推理慢；

- TTFT 过高；

- 工具阻塞且没有进度事件；

- Prompt 过长导致 Prefill 昂贵；

- 事件没有落库导致进程崩溃后丢失；

- 客户端断线后后台任务仍继续消耗资源。



### **3\.4 建立最小延迟观测**



不要只记录一个 `latency_ms`。至少要记录：

```Python
from dataclasses import dataclass
from time import perf_counter


@dataclass
class StreamMetrics:
    started_at: float
    first_token_at: float | None = None
    completed_at: float | None = None

    def mark_first_token(self) -> None:
        if self.first_token_at is None:
            self.first_token_at = perf_counter()

    def mark_completed(self) -> None:
        self.completed_at = perf_counter()

    def snapshot(self) -> dict[str, float | None]:
        ttft = None
        generation = None
        total = None

        if self.first_token_at is not None:
            ttft = self.first_token_at - self.started_at
        if self.first_token_at is not None and self.completed_at is not None:
            generation = self.completed_at - self.first_token_at
        if self.completed_at is not None:
            total = self.completed_at - self.started_at

        return {
            "ttft_seconds": ttft,
            "generation_seconds": generation,
            "total_seconds": total,
        }
```



工程上要特别注意：首个供应商事件未必包含可显示文本。只有收到第一个非空 `text.delta` 时，才应记录用户可感知的 TTFT。



### **课堂练习**



分别对同一个 Prompt 发起非流式和流式请求，记录：

1. 请求开始时间；

2. 首个非空文本 delta 时间；

3. 完整输出时间；

4. 最终输出 Token 数；

5. 用户在第 100 个字符时取消可节省多少输出。

解释：为什么总耗时可能没有明显下降，但交互体验仍然改善。

## **四、目标二：SSE 与类型化事件协议**



### **4\.1 HTTP 流式响应到底是什么**



HTTP 响应并不要求服务端一次性准备好全部 Body。服务端可以在保持连接的情况下逐块写出字节，客户端也可以在响应尚未结束时持续读取。



需要区分三个层次：



1\. **HTTP 传输层**负责把响应 Body 分批送到客户端；

2\. **SSE 帧协议**规定事件如何用文本行表达；

3\. **Harness 事件协议**规定 \`text\.delta\`、\`tool\.started\` 等业务含义。



网络 chunk 不是 SSE event，SSE event 也不等于模型 Token。



一次 `read()` 可能只读到半个 SSE 事件，也可能同时读到三个事件。一个模型 delta 也可能包含多个 Token，甚至是空字符串。任何把“一次网络读取”当作“一条完整业务消息”的实现都存在边界错误。



### **4\.2 SSE 是什么**



Server\-Sent Events 是一种基于 HTTP 长连接的服务端单向事件协议。服务端使用 `text/event-stream` 返回一系列 UTF\-8 文本帧。



一条完整事件如下：



```Plain Text
id: 17
event: text.delta
data: {"run_id":"run_123","seq":17,"delta":"正在分析"}
```



最后的空行表示这条事件结束。



SSE 常用字段：

|字段|含义|
|---|---|
|`event`|事件类型；客户端可按类型注册处理器|
|`data`|事件数据；复杂负载通常使用 JSON|
|`id`|事件 ID；浏览器重连时可通过 `Last-Event-ID` 发送|
|`retry`|建议客户端重连等待时间，单位毫秒|



以冒号开头的行是注释，可用作心跳：



```Plain Text
: heartbeat
```



心跳用于防止反向代理或负载均衡器把长时间没有数据的连接判断为空闲连接。



### **4\.3 SSE、WebSocket 与普通 JSON 怎么选**



|方案|方向|适合场景|主要代价|
|---|---|---|---|
|普通 JSON|请求后一次返回|短请求、完整结果|不能展示增量|
|SSE|服务端到客户端|模型输出、Run 状态、日志流|客户端上行控制需另走 HTTP|
|WebSocket|双向|高频双向协作、实时语音、多人编辑|连接治理和扩缩容更复杂|



LLM 文本生成通常是“客户端提交任务，服务端持续返回事件”，SSE 的语义与基础设施兼容性都很合适。取消可以使用独立的 `POST /runs/{run_id}/cancel`，没有必要仅仅为了一个停止按钮引入 WebSocket。



### **4\.4 为什么不应直接暴露供应商 chunk**



下面是一个错误的网关设计：



```Python
# 错误示例：前端被迫依赖具体供应商的数据结构
async for chunk in deepseek_stream:
    yield chunk.model_dump_json() + "\n"
```



它带来四个问题：



1. 前端必须理解供应商 SDK；

2. 更换模型会修改所有消费端；

3. 工具、取消和 checkpoint 没有统一事件类型；

4. 原始对象可能包含不应发送给用户的字段。

Harness 应定义自己的内部事件：



```Python
from __future__ import annotations

from datetime import datetime, timezone
from typing import Any, Literal
from pydantic import BaseModel, Field


EventType = Literal[
    "run.started",
    "text.delta",
    "tool.started",
    "tool.completed",
    "run.retrying",
    "run.completed",
    "run.failed",
    "run.cancelled",
]


class RunEvent(BaseModel):
    schema_version: Literal["1"] = "1"
    run_id: str
    seq: int = Field(ge=0)
    type: EventType
    created_at: datetime = Field(
        default_factory=lambda: datetime.now(timezone.utc)
    )
    data: dict[str, Any] = Field(default_factory=dict)
```



`run_id + seq` 构成一条 Run 内稳定的事件位置。消费端使用它去重，事件存储使用它排序，断线重连使用它确定从哪里继续。



### **4\.5 SSE 编码器**



```Python
import json


def encode_sse(event: RunEvent) -> bytes:
    payload = event.model_dump(mode="json")
    lines = [
        f"id: {event.seq}",
        f"event: {event.type}",
        "data: " + json.dumps(payload, ensure_ascii=False),
        "",
        "",
    ]
    return "\n".join(lines).encode("utf-8")


def encode_heartbeat() -> bytes:
    return b": heartbeat\n\n"
```



编码器是协议边界，应做单元测试：中文、换行、引号、空字符串和较大 payload 都必须能被客户端正确还原。



**课堂练习**



为 `RunEvent` 增加 `message.completed` 和 `approval.required` 两种事件，要求：

- 不把供应商对象放进 `data`；

- `approval.required` 只包含允许暴露给用户的工具名、参数摘要和审批 ID；

- 老客户端遇到未知事件时可以忽略，而不是崩溃。

## **五、目标三：DeepSeek V4 Flash 与 FastAPI 流式转发**



### **5\.1 先直接消费模型流**



安装依赖：



```Bash
pip install "openai>=2" "fastapi>=0.115" "uvicorn[standard]>=0.34" \
  "pydantic>=2" "httpx>=0.28"

export DEEPSEEK_API_KEY="你的 API Key"
```



DeepSeek 提供 OpenAI 兼容接口，因此可以使用 OpenAI Python SDK。下面先绕过 Web 层，观察 Chat Completions 的原始增量：



```Python
import os
from openai import AsyncOpenAI


client = AsyncOpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
    timeout=60.0,
    max_retries=0,
)


async def stream_deepseek(prompt: str):
    stream = await client.chat.completions.create(
        model="deepseek-v4-flash",
        messages=[
            {
                "role": "system",
                "content": "你是代码审查助手，只报告有证据的问题。",
            },
            {"role": "user", "content": prompt},
        ],
        stream=True,
        max_tokens=1024,
        extra_body={"thinking": {"type": "disabled"}},
        stream_options={"include_usage": True},
    )

    async for chunk in stream:
        choice = chunk.choices[0] if chunk.choices else None
        delta = choice.delta.content if choice else None

        if delta:
            yield {"type": "text.delta", "delta": delta}

        if choice and choice.finish_reason:
            yield {
                "type": "model.finished",
                "finish_reason": choice.finish_reason,
            }

        if chunk.usage is not None:
            yield {
                "type": "model.usage",
                "usage": {
                    "input_tokens": chunk.usage.prompt_tokens,
                    "output_tokens": chunk.usage.completion_tokens,
                    "total_tokens": chunk.usage.total_tokens,
                },
            }
```



阅读代码时要注意：



- `stream=True` 返回异步流，不再直接返回完整 `ChatCompletion`；

- chunk 可以没有 `choices`；

- `delta.content` 可以是 `None` 或空字符串；

- `finish_reason` 和 usage 可能出现在不同 chunk；

- 文本结束不等于业务任务完成，Harness 仍需检查结束原因和验证结果。



### **5\.2 把供应商流适配为内部协议**



Model Adapter 不应该产生 SSE 字符串，因为 SSE 是 Gateway 的职责。Adapter 只产生统一事件数据：



```Python
from collections.abc import AsyncIterator
from dataclasses import dataclass
from typing import Any, Protocol


@dataclass(frozen=True)
class ModelStreamEvent:
    type: str
    data: dict[str, Any]


class StreamingModel(Protocol):
    async def stream(
        self,
        messages: list[dict[str, str]],
    ) -> AsyncIterator[ModelStreamEvent]: ...


class DeepSeekChatAdapter:
    def __init__(self, client: AsyncOpenAI, model: str):
        self.client = client
        self.model = model

    async def stream(
        self,
        messages: list[dict[str, str]],
    ) -> AsyncIterator[ModelStreamEvent]:
        response = await self.client.chat.completions.create(
            model=self.model,
            messages=messages,
            stream=True,
            max_tokens=1024,
            stream_options={"include_usage": True},
            extra_body={"thinking": {"type": "disabled"}},
        )

        async for chunk in response:
            choice = chunk.choices[0] if chunk.choices else None

            if choice and choice.delta.content:
                yield ModelStreamEvent(
                    type="text.delta",
                    data={"delta": choice.delta.content},
                )

            if choice and choice.finish_reason:
                yield ModelStreamEvent(
                    type="model.finished",
                    data={"finish_reason": choice.finish_reason},
                )

            if chunk.usage:
                yield ModelStreamEvent(
                    type="model.usage",
                    data={
                        "input_tokens": chunk.usage.prompt_tokens,
                        "output_tokens": chunk.usage.completion_tokens,
                    },
                )
```



未来切换到 Responses API 时，只需增加另一个 Adapter，把 `response.output_text.delta` 等事件映射为相同的 `ModelStreamEvent`。Agent Loop 和客户端不需要理解供应商差异。



### **5\.3 一个可运行的 Run Store**



为了演示取消、重连和 checkpoint，不能把所有状态都放在请求 generator 的局部变量中。先定义一个最小内存存储；生产环境可替换成 PostgreSQL \+ Redis Stream。



```Python
import asyncio
from dataclasses import dataclass, field


@dataclass
class RunState:
    run_id: str
    status: str = "created"
    next_seq: int = 0
    events: list[RunEvent] = field(default_factory=list)
    cancel_event: asyncio.Event = field(default_factory=asyncio.Event)
    changed: asyncio.Condition = field(default_factory=asyncio.Condition)

    async def append(self, event_type: EventType, data: dict) -> RunEvent:
        async with self.changed:
            event = RunEvent(
                run_id=self.run_id,
                seq=self.next_seq,
                type=event_type,
                data=data,
            )
            self.next_seq += 1
            self.events.append(event)
            self.changed.notify_all()
            return event


RUNS: dict[str, RunState] = {}
RUN_TASKS: dict[str, asyncio.Task] = {}
```



这里的内存实现只用于课堂：



- 进程重启后数据会丢失；

- 多 Worker 之间不共享状态；

- 事件列表没有容量上限；

- 没有数据库唯一约束保护 `(run_id, seq)`。

但它能让我们先看清协议，再替换基础设施。



### **5\.4 Agent Loop 负责生产事件**



```Python
async def execute_run(
    state: RunState,
    model: StreamingModel,
    messages: list[dict[str, str]],
) -> None:
    state.status = "running"
    await state.append("run.started", {"status": state.status})

    text_parts: list[str] = []
    usage: dict = {}
    finish_reason: str | None = None

    try:
        async for model_event in model.stream(messages):
            if state.cancel_event.is_set():
                state.status = "cancelled"
                await state.append(
                    "run.cancelled",
                    {"reason": "user_requested", "partial_text": "".join(text_parts)},
                )
                return

            if model_event.type == "text.delta":
                delta = model_event.data["delta"]
                text_parts.append(delta)
                await state.append("text.delta", {"delta": delta})

            elif model_event.type == "model.usage":
                usage = model_event.data

            elif model_event.type == "model.finished":
                finish_reason = model_event.data["finish_reason"]

        if finish_reason == "length":
            state.status = "failed"
            await state.append(
                "run.failed",
                {
                    "code": "OUTPUT_TRUNCATED",
                    "retryable": False,
                    "partial_text": "".join(text_parts),
                },
            )
            return

        state.status = "completed"
        await state.append(
            "run.completed",
            {
                "text": "".join(text_parts),
                "usage": usage,
                "finish_reason": finish_reason,
            },
        )

    except asyncio.CancelledError:
        state.status = "cancelled"
        if not state.events or state.events[-1].type != "run.cancelled":
            await state.append(
                "run.cancelled",
                {"reason": "task_cancelled", "partial_text": "".join(text_parts)},
            )
        raise

    except Exception as exc:
        state.status = "failed"
        # 原始异常写服务端日志；对客户端只暴露稳定错误码。
        await state.append(
            "run.failed",
            {
                "code": "MODEL_STREAM_FAILED",
                "retryable": True,
                "partial_text": "".join(text_parts),
            },
        )
```



这段 Loop 做了三个重要区分：



1. 模型事件不等于 Run 事件；

2. 模型流结束不等于一定成功，`finish_reason == "length"` 必须单独处理；

3. `CancelledError` 是控制信号，不应被普通异常处理吞掉。



### **5\.5 FastAPI 创建 Run、订阅事件与取消**



```Python
import uuid
from fastapi import FastAPI, Header, HTTPException, Request
from fastapi.responses import StreamingResponse
from pydantic import BaseModel


app = FastAPI()


class CreateRunRequest(BaseModel):
    prompt: str


@app.post("/v1/runs")
async def create_run(body: CreateRunRequest):
    run_id = f"run_{uuid.uuid4().hex}"
    state = RunState(run_id=run_id)
    RUNS[run_id] = state

    messages = [{"role": "user", "content": body.prompt}]
    task = asyncio.create_task(execute_run(state, model, messages))
    RUN_TASKS[run_id] = task
    task.add_done_callback(lambda _: RUN_TASKS.pop(run_id, None))

    return {"run_id": run_id, "status": state.status}


async def subscribe(
    request: Request,
    state: RunState,
    after_seq: int,
):
    cursor = after_seq + 1

    while True:
        while cursor < len(state.events):
            event = state.events[cursor]
            cursor += 1
            yield encode_sse(event)

            if event.type in {"run.completed", "run.failed", "run.cancelled"}:
                return

        if await request.is_disconnected():
            # 这里只停止订阅，不直接取消 Run。
            # 用户刷新页面后仍可从 last seq 继续订阅。
            return

        try:
            async with state.changed:
                await asyncio.wait_for(state.changed.wait(), timeout=15.0)
        except TimeoutError:
            yield encode_heartbeat()


@app.get("/v1/runs/{run_id}/events")
async def stream_events(
    run_id: str,
    request: Request,
    last_event_id: str | None = Header(default=None, alias="Last-Event-ID"),
):
    state = RUNS.get(run_id)
    if state is None:
        raise HTTPException(status_code=404, detail="run not found")

    after_seq = int(last_event_id) if last_event_id is not None else -1
    return StreamingResponse(
        subscribe(request, state, after_seq),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache, no-transform",
            "X-Accel-Buffering": "no",
            "Connection": "keep-alive",
        },
    )


@app.post("/v1/runs/{run_id}/cancel")
async def cancel_run(run_id: str):
    state = RUNS.get(run_id)
    if state is None:
        raise HTTPException(status_code=404, detail="run not found")

    if state.status in {"completed", "failed", "cancelled"}:
        return {"run_id": run_id, "status": state.status}

    state.cancel_event.set()
    task = RUN_TASKS.get(run_id)
    if task is not None:
        task.cancel()

    return {"run_id": run_id, "status": "cancelling"}
```



启动服务：



```Bash
uvicorn app:app --reload --port 8000
```



这里把“创建 Run”和“订阅 Run”拆成两个接口，具有三个优势：



- `EventSource` 可以通过 GET 原生订阅；

- 浏览器刷新不会自动创建第二次模型调用；

- 客户端断线不等于业务取消，可重新连接已有 Run。



### **5\.6 低延迟转发的常见陷阱**



**陷阱一：先收集完整文本再 yield**

```Python
# 错误：名字叫 streaming，实际仍等待完整结果
text = ""
async for chunk in model.stream(messages):
    text += chunk
yield text
```



**陷阱二：同步 SDK 阻塞事件循环**

在 `async def` 中调用同步迭代器，会阻塞同一 Worker 的其他连接。优先使用异步 SDK；无法替换时，把阻塞部分放入受控线程池，并限制并发。



**陷阱三：反向代理缓冲**

应用已经逐块 `yield`，但 Nginx、网关或 CDN 仍可能聚合响应。需要关闭代理缓冲，并检查 idle timeout、压缩和缓存策略。



**陷阱四：每个 delta 同步写数据库**

模型可能产生大量很小的 delta。每个 delta 一次事务会制造 I/O 放大。生产环境通常：



- 终态、工具调用、审批等关键事件立即持久化；

- 文本 delta 按 50～200 ms 或一定字节数批量落库；

- 同时保证最终聚合文本可重建。



**陷阱五：把断开订阅等同于取消任**

移动网络切换、页面刷新都可能造成短暂断线。如果一断线就取消，用户无法恢复任务。如果任何断线都不取消，后台又可能产生孤儿任务。



工程上应明确产品策略：



- 显式点击停止：立即发取消请求；

- 短暂断线：Run 继续，允许重连；

- 长时间无人订阅：由租约或后台清理任务决定是否取消。

### **6\.1 EventSource：创建与订阅分离**



```TypeScript
type RunEvent = {
  schema_version: "1";
  run_id: string;
  seq: number;
  type: string;
  created_at: string;
  data: Record<string, unknown>;
};

async function createRun(prompt: string): Promise<string> {
  const response = await fetch("/v1/runs", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ prompt }),
  });

  if (!response.ok) {
    throw new Error(`create run failed: ${response.status}`);
  }

  const body = await response.json();
  return body.run_id;
}

function subscribeRun(runId: string) {
  const source = new EventSource(`/v1/runs/${runId}/events`);
  let text = "";
  let lastSeq = -1;

  source.addEventListener("text.delta", (raw) => {
    const event = JSON.parse((raw as MessageEvent).data) as RunEvent;

    // EventSource 可能重连；按 seq 去重。
    if (event.seq <= lastSeq) return;
    lastSeq = event.seq;

    text += String(event.data.delta ?? "");
    scheduleRender(text);
  });

  source.addEventListener("run.completed", (raw) => {
    const event = JSON.parse((raw as MessageEvent).data) as RunEvent;
    lastSeq = Math.max(lastSeq, event.seq);
    source.close();
    showCompleted(event.data);
  });

  source.addEventListener("run.failed", (raw) => {
    const event = JSON.parse((raw as MessageEvent).data) as RunEvent;
    source.close();
    showFailure(event.data);
  });

  source.addEventListener("run.cancelled", () => {
    source.close();
    showCancelled();
  });

  source.onerror = () => {
    // EventSource 会自动重连。不要在这里立即创建新 Run。
    showReconnecting();
  };

  return source;
}
```



`EventSource` 会自动维护 `Last-Event-ID`。但它有两个常见限制：只支持 GET，不方便携带自定义 Authorization Header。常见解决方式是使用同站 Cookie，或创建短期订阅令牌。不要把长期 API Key 放在 URL 查询参数中。



### **6\.2 为什么要做渲染节流**



每收到一个很小的 delta 就触发完整 Markdown 渲染，会导致浏览器频繁布局和重复解析。可以用 `requestAnimationFrame` 合并更新：



```TypeScript
let pendingText = "";
let renderScheduled = false;

function scheduleRender(text: string) {
  pendingText = text;
  if (renderScheduled) return;

  renderScheduled = true;
  requestAnimationFrame(() => {
    renderScheduled = false;
    renderText(pendingText);
  });
}
```



对于 Markdown 代码块，还要考虑尚未闭合的反引号。流式阶段可以使用容错渲染，终态到达后再进行完整渲染和语法高亮。



### **6\.3 fetch \+ ReadableStream：同一个 POST 中读取 SSE**



如果业务要求使用 Bearer Token，并希望在同一个 POST 请求中直接读取响应，可以使用 `fetch`。但必须自己解析 SSE 帧。



```TypeScript
async function streamWithFetch(prompt: string, signal: AbortSignal) {
  const response = await fetch("/v1/chat/stream", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      Authorization: `Bearer ${getAccessToken()}`,
    },
    body: JSON.stringify({ prompt }),
    signal,
  });

  if (!response.ok || !response.body) {
    throw new Error(`stream failed: ${response.status}`);
  }

  const reader = response.body.getReader();
  const decoder = new TextDecoder("utf-8");
  let buffer = "";

  while (true) {
    const { value, done } = await reader.read();
    buffer += decoder.decode(value, { stream: !done });

    let boundary: number;
    while ((boundary = buffer.indexOf("\n\n")) >= 0) {
      const frame = buffer.slice(0, boundary);
      buffer = buffer.slice(boundary + 2);
      handleSseFrame(frame);
    }

    if (done) break;
  }
}

function handleSseFrame(frame: string) {
  let eventType = "message";
  let eventId: string | undefined;
  const dataLines: string[] = [];

  for (const line of frame.split("\n")) {
    if (line.startsWith(":")) continue;
    if (line.startsWith("event:")) eventType = line.slice(6).trimStart();
    if (line.startsWith("id:")) eventId = line.slice(3).trimStart();
    if (line.startsWith("data:")) dataLines.push(line.slice(5).trimStart());
  }

  if (dataLines.length === 0) return;
  const data = JSON.parse(dataLines.join("\n"));
  dispatchRunEvent(eventType, eventId, data);
}
```



这里有三个不能省略的细节：



- `TextDecoder(..., {stream: true})` 处理一个 UTF\-8 字符被拆到两个网络 chunk 的情况；

- `buffer` 处理一个 SSE event 被拆包或多个 event 粘在一起；

- 多个 `data:` 行要用换行拼接。

生产项目可使用经过验证的 SSE parser，不要在多个客户端各自维护一份不完整解析器。



### **6\.4 Python CLI 消费 SSE**



```Python
import json
import sys
import httpx


def consume_run(base_url: str, run_id: str) -> None:
    last_seq = -1

    with httpx.Client(timeout=None) as client:
        with client.stream(
            "GET",

                        seq = payload["seq"]

                            last_seq = seq
                            if event_type == "text.delta":
                                sys.stdout.write(payload["data"]["delta"])

                            elif event_type in {
                                "run.completed",
                                "run.failed",

                            }:
                                print()
                                return

                    event_type = "message"
                    data_lines = []
                    continue

                if line.startswith(":"):
                    continue
                if line.startswith("event:"):
```

## **七、目标五：中断与取消必须贯穿整个 Agent Harness**



### **7\.1 “关闭连接”为什么不等于“停止生成”**



浏览器关闭连接后，可能发生：



- Gateway 的响应 generator 被取消；

- Agent Loop 已经在独立后台任务中继续运行；

- 模型供应商仍在生成；

- 已启动的 shell 命令或数据库查询仍在执行；

- 工具执行完成后仍可能产生外部副作用。

因此，取消不是一个 UI 状态，而是一个端到端控制协议：



```Plain Text
用户点击停止
→ Client 停止渲染并调用 Cancel API
→ Run Store 将状态改为 cancelling
→ Loop 在安全点检查取消信号
→ Model Adapter 关闭模型流
→ Tool Runtime 终止可取消工具
→ Checkpoint 保存部分结果
→ Run Store 写入 cancelled 终态
→ 订阅者收到 run.cancelled
```



### **7\.2 Cooperative Cancellation 与强制终止**



协作式取消要求运行代码在安全点主动检查 `cancel_event`：



```Python
async def cancellable_loop(state: RunState):
    for step in range(100):
        if state.cancel_event.is_set():
            raise asyncio.CancelledError
        await execute_one_step(step)
```



优点是可以在退出前保存状态和释放资源。缺点是如果某个工具长期阻塞且不检查信号，取消不会及时生效。



强制取消使用 `task.cancel()` 向 asyncio Task 注入 `CancelledError`。它更及时，但仍取决于被调用代码是否在可取消的 await 点，以及底层 SDK 是否会关闭网络请求。



生产实现通常两者结合：



1. 设置共享取消状态；

2. 给组件一个短暂清理窗口；

3. 取消仍未退出的 Task；

4. 对外部进程发送终止信号；

5. 达到强制终止超时后记录为 `cancel_timeout`。

### **7\.3 工具取消比模型取消更复杂**



工具分为三类：



|类型|示例|取消策略|
|---|---|---|
|只读、可重试|搜索、读取文件|停止等待，必要时重新执行|
|长运行、可终止|shell、构建、测试|保存进程句柄，发送终止信号|
|有副作用、不可逆|发邮件、付款、发布|取消不能假设动作未发生，必须查询结果|



对于有副作用的工具，网络断开时最危险的状态是“执行结果未知”。此时不能简单重试，否则可能重复付款、重复发信或重复发布。



必须使用：



- 幂等键；

- 工具调用 ID；

- 外部系统状态查询；

- `started / succeeded / failed / unknown` 状态机；

- 必要的人工确认。



### **7\.4 取消状态机**



Run 状态不应从 `running` 直接在 UI 中改成 `cancelled`。更合理的是：



```Plain Text
created → running → cancelling → cancelled
                  ↘ completed
                  ↘ failed
```



`cancelling` 表示已经接受取消请求，但底层资源尚未确认释放。只有 Loop 完成清理并写入终态后，才是 `cancelled`。



状态更新应使用比较并交换或数据库条件更新，避免“完成”和“取消”同时到达时覆盖终态：



```SQL
UPDATE agent_runs
SET status = 'cancelling'
WHERE run_id = :run_id
  AND status IN ('created', 'running');
```



如果更新行数为 0，应读取当前终态并原样返回，而不是强行覆盖。



### **7\.5 取消后的部分输出怎样处理**



取消不代表已经生成的内容必须丢弃。建议同时保存：



- `partial_text`：用户已经看到的文本；

- `last_seq`：最后持久化事件位置；

- `loop_step`：当前位于模型还是工具步骤；

- `tool_calls`：已开始和已完成的调用；

- `usage_so_far`：已知的 Token 用量；

- `cancel_reason`：用户取消、超时、预算或管理员终止。

但部分输出不应自动作为最终业务结果。例如一段被截断的 JSON、半条 SQL 或未闭合的补丁，都不能直接进入下游执行器。

## **八、目标六：流式异常、重试、断线续传与 Checkpoint**



### **8\.1 错误发生在什么时候**



流式请求不是一次成功或失败，而是分阶段的：



```Plain Text
创建连接 → 收到响应头 → 收到首事件 → 持续接收 → 收到终态
```



不同阶段的失败具有不同重试风险。



|阶段|例子|是否可能安全重试|
|---|---|---|
|建立流之前|DNS、连接超时、429、503|通常可以有限重试|
|已连接但无任何业务事件|服务端提前关闭|可按策略有限重试|
|已收到文本 delta|网络中断|不能盲目重跑并拼接|
|工具调用已开始|连接中断|必须先查询工具状态|
|已收到终态但客户端未确认|ACK 丢失|从事件存储重放，不重新执行|



### **8\.2 为什么流中失败不能简单重试模型**



假设第一次已经输出：



```Plain Text
修复方案包括两个步骤：第一，修改缓存键；第二，
```



网络中断后，如果使用原 Prompt 重新请求，模型可能输出另一种表述：



```Plain Text
建议先增加数据库索引，然后调整缓存策略……
```



把两段直接拼接会得到逻辑冲突的答案。即使温度为 0，供应商调度、模型版本或隐藏状态也可能让结果不同。



因此，必须区分：



\- **Transport Resume**：同一个 Run 从已持久化事件继续传给客户端；

\- **Model Retry**：重新发起一次模型推理；

\- **Task Resume**：从 Agent checkpoint 开始下一步运行。



它们不是同一件事。



### **8\.3 有边界的连接重试**



流建立前可以使用指数退避和抖动：



```Python
import asyncio
import random
from collections.abc import AsyncIterator, Callable


class RetryableStreamError(Exception):
    pass


async def open_stream_with_retry(
    open_stream: Callable[[], AsyncIterator[ModelStreamEvent]],
    *,
    max_attempts: int = 3,
) -> AsyncIterator[ModelStreamEvent]:
    emitted_business_event = False

    for attempt in range(1, max_attempts + 1):
        try:
            async for event in open_stream():
                emitted_business_event = True
                yield event
            return

        except RetryableStreamError:
            # 已向下游发过内容后，不自动重新生成。
            if emitted_business_event or attempt == max_attempts:
                raise

            base = min(0.5 * (2 ** (attempt - 1)), 4.0)
            delay = random.uniform(0, base)
            await asyncio.sleep(delay)
```



重试策略必须有：



- 最大尝试次数；

- 最大累计时间；

- 可重试错误白名单；

- 退避和 jitter；

- Run 预算；

- Trace 记录；

- 一旦产生不可重复的业务事件就停止自动重试。

认证失败、参数错误、内容拒答和 Schema 错误通常不应按网络故障重试。



### **8\.4 断线续传的核心是事件重放**



可靠恢复不是要求模型供应商从第 183 个 Token 继续，而是让客户端从 Harness 已持久化的第 183 条事件继续读取。



最小事件表：



```SQL
CREATE TABLE run_events (
    run_id         TEXT        NOT NULL,
    seq            BIGINT      NOT NULL,
    event_type     TEXT        NOT NULL,
    payload        JSONB       NOT NULL,
    created_at     TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (run_id, seq)
);

CREATE INDEX idx_run_events_created_at
ON run_events (run_id, created_at);
```



客户端重连时发送 `Last-Event-ID: 182`，服务端查询：



```SQL
SELECT seq, event_type, payload, created_at
FROM run_events
WHERE run_id = :run_id
  AND seq > :last_seq
ORDER BY seq ASC;
```



这样重连只重放已经发生的事实，不会创建新的模型调用。



### **8\.5 Event Store 与实时通知如何配合**



PostgreSQL 适合保存事实，Redis Stream 或 Pub/Sub 适合低延迟通知。常见流程是：



1. Loop 把事件写入 PostgreSQL；

2. 事务成功后发布“有新事件”通知；

3. SSE Gateway 收到通知后从数据库读取缺失事件；

4. 客户端按 `seq` 去重。

不要只依赖 Pub/Sub，因为订阅者断线期间的消息可能丢失。通知可以丢，事实事件不能丢。



### **8\.6 长文本为什么需要 checkpoint**



“长文本输出超出 Context Window”并不是网络 Streaming 能直接解决的问题。Context Window 限制的是模型本轮能够处理的输入与输出总量；SSE 只是把已生成内容逐步传出来。



如果任务需要生成超过单次输出上限的报告，应该把任务拆成多个有边界的步骤：



```Plain Text
生成大纲
→ 保存 outline checkpoint
→ 分节生成 section_1..N
→ 每节完成后校验并保存
→ 汇总一致性检查
→ 生成最终文档
```



每个 checkpoint 应保存：



```Python
from pydantic import BaseModel


class RunCheckpoint(BaseModel):
    run_id: str
    checkpoint_version: int
    loop_step: str
    completed_sections: list[str]
    current_section: str | None
    artifact_refs: list[str]
    last_event_seq: int
    context_summary: str
    pending_tool_calls: list[dict]
```



Checkpoint 保存的是可恢复状态，不是把全部历史原样塞回下一次 Prompt。恢复时由 Context Manager 根据任务状态重建必要上下文。



### **8\.7 会话断开与进程崩溃是两种问题**



|故障|Run 是否仍在执行|恢复方式|
|---|---|---|
|浏览器断线|通常是|重新订阅并重放事件|
|Gateway 重启|可能是|Gateway 无状态化，从 Store 恢复订阅|
|Loop Worker 崩溃|否|从 checkpoint 领取任务并恢复|
|模型供应商流中断|不确定|记录部分结果，由策略决定重试或终止|
|工具执行器失联|不确定|用 call\_id 查询外部状态，禁止盲目重放副作用|



### **8\.8 错误事件不能泄露内部异常**



对客户端返回稳定错误协议：



```JSON
{
  "schema_version": "1",
  "run_id": "run_123",
  "seq": 31,
  "type": "run.failed",
  "data": {
    "code": "UPSTREAM_STREAM_INTERRUPTED",
    "message": "模型连接中断，请稍后重试",
    "retryable": true,
    "resume_mode": "replay_only"
  }
}
```



服务端日志另外记录：



- 原始异常类型；

- HTTP 状态码；

- 供应商 request ID；

- Run ID 与 Trace ID；

- 已发出事件数；

- 已知 usage；

- 本轮是否已产生工具副作用。

不要把 API Key、完整 Prompt、内部堆栈或供应商原始响应直接发送给浏览器。

## **九、把 Streaming 接入最小 Agent Loop**



### **9\.1 Loop 不应该直接操作 HTTP**



错误的 Loop 会同时调用模型、拼 SSE、写数据库和判断客户端连接：



```Python
# 错误边界：业务循环被 HTTP 传输绑死
async def agent_loop(request):
    async for chunk in client.chat.completions.create(...):
        if await request.is_disconnected():
            break
        yield f"data: {chunk.model_dump_json()}\n\n"
```



正确的 Loop 只发布内部事件：



```Python
class EventSink(Protocol):
    async def publish(self, event: RunEvent) -> None: ...


class CancellationToken(Protocol):
    def is_cancelled(self) -> bool: ...
    async def checkpoint(self) -> None: ...


async def agent_loop(
    task: str,
    model: StreamingModel,
    tools: ToolRuntime,
    events: EventSink,
    cancellation: CancellationToken,
) -> AgentResult:
    # Loop 只依赖内部抽象，不依赖 FastAPI、EventSource 或具体 SDK。
    ...
```



这使同一个 Loop 可以运行在：



- FastAPI 请求；

- 后台 Worker；

- CLI；

- IDE 插件；

- 单元测试；

- Multi\-Agent 子任务。



### **9\.2 Harness 中各层的责任**



|组件|责任|不应承担的责任|
|---|---|---|
|Model Adapter|解析供应商流、归一化错误|拼接 SSE、渲染 UI|
|Agent Loop|驱动模型与工具、检查取消与预算|依赖 HTTP Request|
|Tool Runtime|执行工具、记录 call\_id、处理超时|决定页面展示|
|Event Store|持久化、排序、重放事件|重新执行模型|
|SSE Gateway|订阅事件、编码、心跳|决定任务是否完成|
|Client Renderer|展示、去重、触发取消|直接解析供应商 chunk|



### **9\.3 必须记录的 Trace 字段**



一次 Streaming Run 至少记录：



- `trace_id`、`run_id`、`session_id`；

- 模型、供应商、Prompt 版本；

- 请求开始、首文本 delta、模型完成、Run 完成时间；

- 输入和输出 Token；

- 每类事件数量与最后 `seq`；

- 客户端重连次数；

- 模型重试次数与原因；

- 取消来源、取消延迟；

- 工具调用及其幂等键；

- checkpoint 版本；

- 最终状态和稳定错误码。



### **9\.4 测试不能只看“浏览器会打字”**



至少完成以下测试：



1\. **SSE 编码测试**：中文、换行和引号可正确解析；

2\. **拆包测试**：一个事件被拆成任意字节块后仍能恢复；

3\. **粘包测试**：一次读取多个事件时不会漏事件；

4\. **顺序测试**：同一 Run 的 \`seq\` 单调递增；

5\. **去重测试**：重放重复事件不会重复渲染；

6\. **断线测试**：重连后从 \`Last\-Event\-ID\` 继续；

7\. **取消测试**：取消能到达模型和工具任务；

8\. **竞态测试**：完成与取消同时发生时只有一个终态；

9\. **失败测试**：首事件前失败可以有限重试，首事件后失败不盲目重跑；

10\. **恢复测试**：Worker 崩溃后能从 checkpoint 继续下一步骤。

## **十、项目实战：Streaming Agent Gateway**



### **项目背景**



在 1\.2 中，我们已经把不同模型接口封装到 Model Adapter，并建立了输入、输出、错误和重试边界。本节继续把同步模型网关升级为 Streaming Agent Gateway。



最终系统应支持：



- 创建一个独立 Run；

- 使用 DeepSeek V4 Flash 流式生成；

- 把供应商流转换成统一 Harness Event；

- 使用 SSE 向 Web 和 CLI 推送；

- 用户主动取消；

- 浏览器断线后从最后事件继续；

- 模型流中断后输出明确终态；

- 保存部分文本、事件和 checkpoint；

- 统计 TTFT、总耗时和取消延迟。

### **验收标准**

- 首个文本 delta 到达后立即显示，不等待完整回答；

- 用户取消后，后台模型任务停止，Run 最终进入 `cancelled`；

- 长文本按章节 checkpoint，而不是突破单轮 Context Window；

- Trace 中可以计算 TTFT、总耗时、取消延迟和重连次数。

## **十一、本节小结**



完成本节后，不应只得到一个会逐字显示文本的 Demo，而应形成下面这套工程认识：



1. Streaming 改善的是可感知延迟和过程可见性，不会自动降低模型推理时间；

2. SSE 是传输协议，Harness Event 才是 Agent Runtime 的稳定业务协议；

3. Model Adapter 消化供应商 chunk 差异，Loop 不依赖具体 SDK；

4. 客户端必须正确处理字节边界、SSE 帧、事件顺序、重复和渲染压力；

5. 取消必须传播到模型与工具，并经过 `cancelling` 到达唯一终态；

6. 流建立前可以有限重试，产生业务事件后不能盲目重新生成；

7. 断线续传依赖事件持久化与重放，长任务恢复依赖 checkpoint；

8. Streaming 的最终目标不是“打字机效果”，而是让 Agent Loop 可观察、可中断、可恢复、可审计。

下一节进入 Prompt Engineering 时，要继续沿用同一责任边界：Prompt 决定模型本轮怎样理解任务；Harness 负责上下文、事件、权限、失败和完成条件。模型输出得再流畅，也不能替代这些工程约束。
