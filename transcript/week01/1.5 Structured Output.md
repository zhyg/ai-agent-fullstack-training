## **二、Prompt 已经规定了输出格式，为什么还需要 Structured Output？**

03

上一节我们学习了 Prompt Engineering。System Prompt 可以要求模型：

> 判断下一步应该搜索资料还是结束回答，并返回 JSON。
> 
> 

但 Prompt 只能表达期望，不能替程序验收结果。模型可能输出解释文字、缺少字段的 JSON，或者一个字段齐全但组合错误的对象。

在聊天场景中，这通常只是表达差异；在 Agent 中，它会改变控制流。知识库 Agent 每一轮都要根据模型输出决定：

```Plain Text
search_docs → 调用搜索工具 → 把资料送回下一轮
finish      → 结束 Loop → 返回最终答案
```

因此，Agent 开发工程师不能只写一句“请返回 JSON”，还必须亲自完成四件事：

|工程工作|需要人决定什么|
|---|---|
|定义协议|允许哪些动作，每个动作需要哪些字段|
|实现校验|什么结果可以进入 Loop，什么结果必须拒绝|
|设计修复|哪些错误可以让模型重写，最多重写几次|
|处理失败|何时停止，何时降级，何时允许读取缓存|

模型负责生成候选结果；Harness 负责验证、拒绝和恢复。Structured Output 就是两者之间的接口边界。

本节统一使用一个知识库 Agent，完整走通下面这条链路：

```Plain Text
定义协议 → 生成结构化结果 → Pydantic 校验
                           ├─ 通过 → 进入 Agent Loop
                           └─ 失败 → 纠错 → 降级或停止
```

先从链路的第一个问题开始：为什么不能直接解析模型说的话？

---

## **三、为什么 Agent 不能依赖自然语言解析？**

04

用户问“公司差旅报销需要哪些材料”，模型可能回答“建议先查差旅制度”，也可能回答“调用 search\_docs”。人能理解两句话意思相近，程序拿到的却是两个不同字符串。

最初的实现可能使用关键词：

```Plain Text
def parse_action(text: str) -> str:
    if "搜索" in text or "search_docs" in text:
        return "search_docs"
    return "finish"
```

这段代码的问题不只是容易报错，更危险的是它可能不报错却选错动作。“不需要搜索”仍包含“搜索”，模型改写成“查询资料”又无法命中；即使动作判断正确，程序仍然拿不到类型稳定的查询参数。

要求“只返回 JSON”也不能解决全部问题，因为下面两份内容都是合法 JSON：

```Plain Text
{"action": "search_docs", "query": "差旅报销材料"}
```

```Plain Text
{"action": "search", "query": 123}
```

JSON 只证明文本可以解析，不证明字段、类型和动作符合业务约定。Agent 真正需要的不是“一个 JSON”，而是“一个符合指定协议的 JSON”。这就自然引出了 JSON Schema。

## **四、怎样用 JSON Schema 说清楚输出结构？**

JSON Schema 用统一格式声明字段名、字段类型、必填项、枚举值和额外字段规则。知识库 Agent 只允许 search\_docs 与 finish 两种动作，可以定义为：

```Plain Text
{
  "type": "object",
  "properties": {
    "action": {
      "type": "string",
      "enum": ["search_docs", "finish"]
    },
    "query": {
      "type": ["string", "null"]
    },
    "answer": {
      "type": ["string", "null"]
    }
  },
  "required": ["action", "query", "answer"],
  "additionalProperties": false
}
```

这份 Schema 只做四件事：规定最外层是对象；限制动作范围；要求三个字段都出现；拒绝未声明字段。query 和 answer 允许为 null，使两种动作共用一个稳定结构。

不过，Schema 仍可能接受下面这类业务冲突：

```Plain Text
{
  "action": "finish",
  "query": "继续搜索差旅制度",
  "answer": null
}
```

字段与类型没有越界，但 finish 不应该携带查询词，而且必须有答案。由此可见，JSON Schema 负责描述外形，跨字段的业务关系还要落进程序。Python Agent 项目中，最常用的承载方式就是 Pydantic Model。

## **五、怎样用 Pydantic 把 Schema 变成可执行的 Python 协议？**

05

如果团队分别维护 JSON Schema、Python 类和解析代码，三者迟早会不一致。Pydantic 的核心价值，是让同一个 Model 同时承担四项职责：

|职责|在 Agent 中的作用|
|---|---|
|定义类型|明确 Loop 最终接收什么对象|
|生成 Schema|把同一份结构提供给模型 API|
|校验输出|拦截字段、类型和业务组合错误|
|反序列化|把 JSON 转为可直接使用的 Python 对象|

### **5\.1 怎样定义字段规则和跨字段规则？**

fieldrule\.py

```Plain Text
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, model_validator


class AgentDecision(BaseModel):
    model_config = ConfigDict(
        extra="forbid",
        strict=True,
    )

    action: Literal["search_docs", "finish"] = Field(
        description="下一步是搜索资料还是结束回答"
    )
    query: str | None = Field(
        ...,
        min_length=1,
        max_length=200,
        description="搜索时使用；结束时为 null",
    )
    answer: str | None = Field(
        ...,
        min_length=1,
        max_length=4000,
        description="结束时使用；搜索时为 null",
    )

    @model_validator(mode="after")
    def check_action_fields(self) -> "AgentDecision":
        if self.action == "search_docs":
            if not self.query or self.answer is not None:
                raise ValueError(
                    "search_docs requires query and answer must be null"
                )

        if self.action == "finish":
            if not self.answer or self.query is not None:
                raise ValueError(
                    "finish requires answer and query must be null"
                )

        return self
```

这段代码包含三层约束。

第一层是字段类型。Literal 把动作限制在两个已知值中，str \| None 明确字段可以是字符串或空值。

第二层是字段自身规则。Field 限制查询词和答案的长度；extra="forbid" 拒绝模型临时添加字段；strict=True 避免把错误类型静默转换成正确类型。

第三层是字段之间的业务关系。单看 answer，它允许为空；但当 action="finish" 时，它又必须有值。这个条件只能由 model\_validator 表达。

这正是 Agent 工程师必须亲自写的部分：Pydantic 能执行规则，却不知道公司的业务规则是什么。

### **5\.2 怎样从同一个 Model 生成 Schema？**

```Plain Text
decision_schema = AgentDecision.model_json_schema()
```

model\_json\_schema\(\) 会把动作枚举、可空类型、长度限制、字段描述和额外字段规则转换为 JSON Schema。于是同一个类可以同时用于生成端和接收端：

```Plain Text
AgentDecision
   ├─ model_json_schema()   → 传给模型 API
   └─ model_validate_json() → 校验模型返回
```

这样做的意义不是少写一份配置，而是避免协议漂移。修改 AgentDecision 后，模型看到的 Schema 与服务端使用的类型会一起变化。

### **5\.3 怎样校验 JSON 并得到 Python 对象？**

```Plain Text
raw_output = """
{
  "action": "search_docs",
  "query": "差旅报销所需材料",
  "answer": null
}
"""

decision = AgentDecision.model_validate_json(raw_output)

print(decision.action)
print(decision.query)
print(decision.model_dump())
```

model\_validate\_json\(\) 一次完成三步：解析 JSON、执行全部规则、创建 AgentDecision。校验通过以后，Loop 读取的是 decision\.action 与 decision\.query，而不是一个字段可能缺失、类型可能变化的任意字典。

model\_dump\(\) 可以把对象转回普通字典，供日志、缓存或 API 响应使用。于是模型输出进入 Pydantic 之前是不可信数据，离开 Pydantic 之后才是程序可以消费的类型对象。

### **5\.4 怎样获得可诊断的校验错误？**

validation\.py

```Plain Text
from pydantic import ValidationError


invalid_output = """
{
  "action": "finish",
  "query": null,
  "answer": null
}
"""

try:
    AgentDecision.model_validate_json(invalid_output)
except ValidationError as exc:
    for item in exc.errors(
        include_url=False,
        include_input=False,
    ):
        print(item["loc"], item["type"], item["msg"])
```

每条错误都会说明位置、类型和原因。它不再只是“解析失败”四个字，而能告诉我们是字段缺失、动作越界、类型错误，还是 finish 没有答案。

到这里，协议已经能被 Python 定义和验证。下一步不是删除服务端校验，而是尽量让模型第一次就生成符合这份协议的结果。

## **六、模型原生 Structured Output 解决了什么？**

06

Prompt 只是要求模型返回 JSON；JSON mode 主要保证结果是合法 JSON；模型原生 Structured Output 则在 API 层接收 Schema，并约束正常生成结果符合这份结构。



下面使用 Responses API 演示把 Pydantic Model 直接传给模型：

textformat\.py

```Plain Text
from openai import OpenAI


client = OpenAI()

response = client.responses.parse(
    model="gpt-5.6",
    input=[
        {
            "role": "system",
            "content": (
                "你是知识库 Agent 的决策器。"
                "资料不足时继续搜索，资料充分时结束并回答。"
            ),
        },
        {
            "role": "user",
            "content": "公司差旅报销需要哪些材料？",
        },
    ],
    text_format=AgentDecision,
)

decision = response.output_parsed
```

text\_format=AgentDecision 让 SDK 根据 Pydantic Model 提供 Schema，并把正常结果解析成类型对象。官方文档同时提醒：拒答或输出达到长度上限时，仍可能得不到可用的解析对象。因此调用方还要检查请求是否正常完成，以及 output\_parsed 是否存在。

原生 Structured Output 提高第一次生成的结构合规率；它没有替业务判断答案是否真实，也没有替 Harness 决定当前动作是否允许执行。既然不同模型和异常状态最终都会汇入服务端，下一步就需要一道统一校验门。

## **七、怎样把校验放在模型返回与 Agent Loop 之间？**

07

Agent 平台可能同时接入原生 Structured Output、JSON mode 和兼容接口。无论输出来自哪一种模型，都应先经过同一个服务端边界：

```Plain Text
模型返回 → Pydantic 校验 → AgentDecision → Agent Loop
                    └─ 失败 → 纠错或失败处理
```

### **7\.1 怎样把错误保存成程序可以处理的数据？**

validationIssue\.py

```Plain Text
class ValidationIssue(BaseModel):
    path: str
    code: str
    message: str


class DecisionValidation(BaseModel):
    valid: bool
    decision: AgentDecision | None = None
    issues: list[ValidationIssue] = Field(default_factory=list)


def validate_decision(raw_output: str) -> DecisionValidation:
    try:
        decision = AgentDecision.model_validate_json(raw_output)
        return DecisionValidation(
            valid=True,
            decision=decision,
        )
    except ValidationError as exc:
        issues = [
            ValidationIssue(
                path=".".join(str(part) for part in item["loc"]),
                code=item["type"],
                message=item["msg"],
            )
            for item in exc.errors(
                include_url=False,
                include_input=False,
            )
        ]
        return DecisionValidation(
            valid=False,
            issues=issues,
        )
```

校验成功时，函数返回完整的 AgentDecision；校验失败时，decision 保持为空，issues 保存错误位置、类型和说明。

这个包装很重要。日志可以统计哪些错误最常见，repair loop 也能把相同的错误准确反馈给模型。如果这里只抛出一句“格式错误”，后续既无法诊断，也不知道应该修什么。

### **7\.2 一次校验具体检查什么？**

validate\_decision\.py

```Plain Text
samples = {
    "invalid_json": '{"action": "finish"',
    "missing_field": '{"action": "finish", "query": null}',
    "invalid_combination": (
        '{"action": "finish", "query": null, "answer": null}'
    ),
    "valid": (
        '{"action": "finish", "query": null, "answer": "需要发票。"}'
    ),
}

for name, raw_output in samples.items():
    result = validate_decision(raw_output)
    print(name, result.valid, result.issues)
```

这组输入依次覆盖三层边界：

|校验层|典型问题|结果|
|---|---|---|
|JSON 语法|引号或括号没有闭合|无法解析|
|字段结构|字段缺失、类型错误、未知动作|无法构造对象|
|业务组合|finish 没有答案|业务校验拒绝|

不同错误最后都不能进入 Loop，但保留失败层次以后，系统才能选择正确的处理方式。

### **7\.3 为什么校验必须“全有或全无”？**

不要从错误输出中挑出看似可用的字段继续执行：

```Plain Text
def accept_decision(raw_output: str) -> AgentDecision:
    validation = validate_decision(raw_output)

    if not validation.valid:
        raise ValueError(validation.issues)

    decision = validation.decision
    assert decision is not None
    return decision
```

如果 action 缺失，程序不能默认使用 finish；如果对象中混入未知字段，也不能删除后继续执行。那样做等于由 Harness 猜出一份模型从未作出的决策。

只有完整通过校验的 AgentDecision 才能离开这一层。至于用户是否有权限执行查询，属于后续业务与权限校验；本节先守住“输出对象完整合法”这道边界。

现在，系统已经能把错误准确识别为数据。下一步才有条件让模型针对这些错误进行修复。

## **八、怎样把校验错误反喂给模型，并限制重试次数？**

08

第一次输出失败，常常只是漏字段、类型错误或字段组合冲突。Pydantic 已经给出了准确原因，Harness 可以把原因反馈给模型，让它修正上一份结果。

### **8\.1 怎样构造明确的纠错消息？**

repair\.py

```Plain Text
import json


def build_repair_message(
    issues: list[ValidationIssue],
) -> str:
    details = [issue.model_dump() for issue in issues]

    return (
        "上一份输出未通过 AgentDecision 校验。\n"
        f"校验错误：{json.dumps(details, ensure_ascii=False)}\n"
        "请保持原任务含义不变，只修正 JSON 语法、字段、"
        "类型或字段组合。只返回修正后的 JSON。"
    )
```

有效的纠错反馈必须回答三个问题：哪里错了、为什么错、允许修改什么。笼统地说“格式不对，请重试”，模型只能重新猜测；传入结构化错误后，它可以针对具体字段修复。

同时要限制修复范围。这里要求保持原任务含义不变，避免模型借“修格式”重新选择动作；要求只返回 JSON，避免修复结果再次夹带解释文字。

### **8\.2 怎样实现一个有上限的 repair loop？**

repairloop\.py

```Plain Text
from collections.abc import Callable


ModelCall = Callable[
    [list[dict[str, str]], dict[str, object]],
    str,
]


class RepairAttempt(BaseModel):
    attempt: int
    output_preview: str
    issues: list[ValidationIssue]


class StructuredOutputFailure(RuntimeError):
    def __init__(self, attempts: list[RepairAttempt]):
        super().__init__(
            f"structured output failed after {len(attempts)} calls"
        )
        self.attempts = attempts


def decide_with_repair(
    task: str,
    call_model: ModelCall,
    max_repairs: int = 2,
) -> AgentDecision:
    messages = [
        {
            "role": "system",
            "content": "根据 AgentDecision 协议决定搜索或结束。",
        },
        {"role": "user", "content": task},
    ]
    attempts: list[RepairAttempt] = []

    for call_index in range(max_repairs + 1):
        raw_output = call_model(
            messages,
            AgentDecision.model_json_schema(),
        )

        validation = validate_decision(raw_output)
        if validation.valid:
            assert validation.decision is not None
            return validation.decision

        attempts.append(
            RepairAttempt(
                attempt=call_index + 1,
                output_preview=raw_output[:500],
                issues=validation.issues,
            )
        )

        if call_index == max_repairs:
            raise StructuredOutputFailure(attempts)

        messages.extend(
            [
                {"role": "assistant", "content": raw_output[:2000]},
                {
                    "role": "user",
                    "content": build_repair_message(
                        validation.issues
                    ),
                },
            ]
        )

    raise AssertionError("unreachable")
```

这段代码形成一个完整的小循环：模型生成结果，Pydantic 校验；失败后记录输出和错误；还有预算就把上一份结果与错误放回上下文；预算用完则抛出带完整尝试记录的异常。

max\_repairs=2 表示第一次生成以后最多修复两次，所以总调用次数最多是三次。代码必须把“修复次数”和“调用次数”区分清楚，否则线上预算很容易多执行一轮。

RepairAttempt 记录每次失败，方便判断模型是在逐步接近正确格式，还是连续犯同一种错误。示例只保留截断后的输出预览，避免日志默认保存过多原始内容。

repair loop 还要守住一个关键边界：它只重新生成决策，不执行任何工具。只有某次结果完整通过校验，外层 Agent Loop 才能读取动作。因此三次生成失败不会造成三次业务副作用。

### **8\.3 哪些错误不应该反喂给模型？**

|失败类型|正确处理|
|---|---|
|字段缺失、类型错误、组合冲突|反馈校验错误，让模型修复|
|网络超时、限流|由模型调用层按退避策略重试|
|权限不足|立即拒绝或请求授权|
|知识库不可用|停止、切换服务或转人工|

模型只能修复“它重新组织输出就能解决”的问题。网络、权限和外部服务故障不会因为 JSON 改写而消失，因此不能使用 except Exception 把所有错误都塞进 repair loop。

当格式修复预算也耗尽时，继续调用只是碰运气。系统需要从“尝试修好”转入“安全结束”。

## **九、多次修复仍然失败，Harness 应该怎样处理？**

09

失败处理需要给调用方一个稳定、可识别的结果，而不是返回最后一份错误 JSON。

### **9\.1 怎样明确区分成功、降级和失败？**

decisionResult\.py

```Plain Text
class DecisionResult(BaseModel):
    status: Literal["ok", "degraded", "failed"]
    source: Literal["model", "cache", "none"]
    decision: AgentDecision | None
    message: str | None
    repair_attempts: int = 0


def failed_result(attempts: int) -> DecisionResult:
    return DecisionResult(
        status="failed",
        source="none",
        decision=None,
        message="模型未能生成可验证的决策，请稍后重试。",
        repair_attempts=attempts,
    )
```

ok 表示模型给出了合法决策；degraded 表示模型失败，但系统找到了满足条件的替代结果；failed 表示没有任何结果可以安全使用。

最关键的设计是：failed 时 decision=None。系统不能为了让流程继续而伪造一个 finish，也不能把错误输出拼成半成品。

### **9\.2 缓存什么时候才是合法的降级结果？**

缓存不是“出错后随便找一条旧答案”。当前知识库 Agent 只允许回退到同一问题近期成功生成的只读答案，并检查任务键、协议版本和有效期。

cache\.py

```Plain Text
from datetime import datetime, timedelta, timezone
from hashlib import sha256


SCHEMA_VERSION = "agent-decision-v1"


class CachedAnswer(BaseModel):
    task_key: str
    answer: str = Field(min_length=1, max_length=4000)
    created_at: datetime
    schema_version: str


def make_task_key(task: str) -> str:
    normalized = " ".join(task.split()).strip().lower()
    return sha256(normalized.encode("utf-8")).hexdigest()


def use_cache_if_fresh(
    cached: CachedAnswer | None,
    task: str,
    max_age: timedelta = timedelta(minutes=5),
) -> AgentDecision | None:
    if cached is None:
        return None
    if cached.task_key != make_task_key(task):
        return None
    if cached.schema_version != SCHEMA_VERSION:
        return None
    if cached.created_at.tzinfo is None:
        return None

    age = datetime.now(timezone.utc) - cached.created_at
    if age < timedelta(0) or age > max_age:
        return None

    return AgentDecision(
        action="finish",
        query=None,
        answer=cached.answer,
    )
```

任务键避免把相似问题当成同一问题；协议版本避免旧缓存与新代码不兼容；有效期避免返回已经过期的数据。全部通过后，缓存仍要重新构造 AgentDecision，因此不能绕开当前 Pydantic 规则。

是否允许缓存回退必须由业务决定。订单状态、价格、权限等快速变化的数据，即使格式正确，也可能已经失效；写入、发送、支付等副作用动作更不能从缓存恢复。

### **9\.3 怎样把修复、缓存和最终失败串起来？**

all\.py

```Plain Text
def safe_decide(
    task: str,
    call_model: ModelCall,
    cached: CachedAnswer | None,
) -> DecisionResult:
    try:
        decision = decide_with_repair(
            task=task,
            call_model=call_model,
            max_repairs=2,
        )
        return DecisionResult(
            status="ok",
            source="model",
            decision=decision,
            message=None,
        )
    except StructuredOutputFailure as exc:
        cached_decision = use_cache_if_fresh(cached, task)

        if cached_decision is not None:
            return DecisionResult(
                status="degraded",
                source="cache",
                decision=cached_decision,
                message="模型输出异常，当前结果来自有效缓存。",
                repair_attempts=len(exc.attempts),
            )

        return failed_result(len(exc.attempts))
```

处理顺序现在非常明确：先有限修复；修不好再检查合格缓存；缓存也不可用就返回失败。这里只捕获 StructuredOutputFailure，不会把数据库故障或程序 Bug 伪装成模型格式问题。

走完这条路径，我们也能看清 Structured Output 的本质：它不是一段写在 Prompt 后面的格式说明，而是一份贯穿生成、校验、恢复和调用方处理的业务接口。

## **十、怎样把输出格式设计成稳定的业务协议？**

10

设计 Schema 之前，先回答五个业务问题：谁消费输出、输出决定什么、允许哪些动作、每种动作需要哪些数据、失败后怎样处理。知识库 Agent 的答案分别是：Agent Loop；决定搜索或结束；只允许 search\_docs 与 finish；分别需要 query 与 answer；最多修复两次，之后读取合格缓存或失败。

这些答案确定以后，字段设计就不需要追求复杂。action、query、answer 直接描述下游程序消费的数据，已经足够；model\_thought、大段推理文字或未被程序使用的置信度，只会增加误用和维护成本。

还要始终区分两件事：结构正确表示字段、类型和组合符合协议；内容正确表示答案真实、查询合理、当前用户有权执行。Structured Output 解决前者，并让后者有一个稳定对象可以继续检查。它的目标不是让模型永远正确，而是让错误可发现、可分类，并在进入下一步之前被拦截。

协议、校验和失败路径现在已经闭合，最后把它们放回一个最小 Agent Loop，检查这套边界是否真正有效。

## **十一、怎样把 Structured Output 接入最小 Agent Loop？**

loop1\.py

```Plain Text
MAX_STEPS = 4


def run_knowledge_agent(
    task: str,
    call_model: ModelCall,
    search_docs: Callable[[str], str],
    cached: CachedAnswer | None = None,
) -> str:
    observations: list[str] = []

    for _ in range(MAX_STEPS):
        context = task
        if observations:
            context += "\n\n已获得资料：\n" + "\n".join(observations)

        result = safe_decide(
            task=context,
            call_model=call_model,
            cached=cached if not observations else None,
        )

        if result.status == "failed":
            raise RuntimeError(result.message)

        decision = result.decision
        assert decision is not None

        if decision.action == "finish":
            assert decision.answer is not None
            return decision.answer

        assert decision.query is not None
        observations.append(search_docs(decision.query))

    raise RuntimeError("agent exceeded maximum steps")
```

这段 Loop 只消费 safe\_decide\(\) 返回的合法对象。模型原始文本、校验错误和修复过程都停留在 Harness 内部；failed 没有决策对象，无法触发搜索；search\_docs 的结果进入下一轮；finish 才结束任务。外层再用 MAX\_STEPS 防止每轮结构都合法、但模型始终不结束的循环。

最关键的测试不是“模型回答得像不像”，而是非法输出是否产生了副作用：

loop1\.py

```Plain Text
def test_invalid_output_never_calls_tool():
    calls = 0

    def invalid_model(_messages, _schema):
        return '{"action": "delete_docs"}'

    def search_docs(_query):
        nonlocal calls
        calls += 1
        return "不应执行"

    try:
        run_knowledge_agent(
            task="查询差旅报销材料",
            call_model=invalid_model,
            search_docs=search_docs,
        )
    except RuntimeError:
        pass

    assert calls == 0
```

连续失败时，safe\_decide\(\) 最终返回 failed，Loop 在工具调用前终止，所以 calls 必须保持为零。这条不变量准确体现了 Harness 的责任：模型可以犯错，但错误不能越过执行边界。

## **十二、课堂练习与验收**

为“工单分类 Agent”定义结构化输出。它只能执行两种动作：route\_to\_team 表示转交指定团队，ask\_user 表示信息不足并向用户追问。

要求：

1. 使用 Pydantic 定义 action、team 和 question；

2. 转交时必须有 team，追问时必须有 question；

3. 禁止额外字段；

4. 使用 model\_validate\_json\(\) 校验模型输出；

5. 把校验错误反喂给模型，最多修复两次；

6. 连续失败后返回 failed，不能猜测一个团队继续执行。

完成后，学员应能解释并实现：

- 合法 JSON 与符合业务协议的 JSON 有什么区别；

- Pydantic 如何同时生成 Schema、校验数据和创建 Python 对象；

- 原生 Structured Output 为什么仍需处理拒答、截断和业务错误；

- 为什么格式错误、网络错误和权限错误不能共用一种重试；

- 怎样保证未通过校验的输出不会触发工具调用。

## **十三、本节小结**

11

上一节的 Prompt 负责告诉模型“应该怎样决策”；本节的 Structured Output 进一步判断“系统实际收到了什么决策”。

完整链路可以收束为四步：用 Pydantic 定义业务协议，并生成 Schema；模型按 Schema 生成候选对象；Harness 在进入 Loop 前再次校验；失败时有限修复，仍失败则降级或停止。

其中真正需要 Agent 开发工程师完成的，不是让模型输出一段看起来像 JSON 的文本，而是确定动作和字段、写出业务规则、划定重试预算、设计失败结果，并验证非法输出永远不会产生工具副作用。

下一节进入 LLM Gateway 后，我们会把 Prompt、Schema、Pydantic 校验、错误处理和模型调用封装成统一入口，让上层 Agent 不必分别适配每一家模型供应商。
