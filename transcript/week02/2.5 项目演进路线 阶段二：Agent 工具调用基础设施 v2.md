```TypeScript
const output = await runWithDeadline(

    toolCallId: prepared.toolCallId,
```

然后看到 deadline 的实际实现：

```TypeScript
const deadline = new Promise<never>((_resolve, reject) => {
  timeout = setTimeout(() => {
    controller.abort();
    reject(new ToolRuntimeError("TOOL_TIMEOUT", "工具执行超时", true));
  }, timeoutMs);
});
return await Promise.race([work(), deadline]);
```

到这里，Agent 已经可以回答第一个问题。真正保证 Runtime 按时返回的是 `Promise.race`。

`controller.abort()` 负责通知合作式 handler 停止；deadline Promise 的主动 reject 负责对付不合作的 handler。两者要一起存在。只有 AbortController，没有竞速等待，handler 如果不监听信号，Runtime 还是会一直卡住。



但任务还要求解释重试和 fallback，所以 Agent 继续沿调用方往下读。

它会指出：捕获错误以后，只有 `ToolRuntimeError.retryable` 为真，且工具声明 `idempotent`，才进入下一次尝试；尝试耗尽后，有 `fallbackHandler` 才执行降级。

```TypeScript
const maxAttempts = tool.metadata.idempotent
  ? tool.metadata.maxRetries + 1
  : 1;

const retryable = lastError instanceof ToolRuntimeError
  && lastError.retryable;
```

注意这个结论不是从 `TOOL_TIMEOUT` 一行猜出来的，而是把错误对象、重试资格和 Tool Metadata 串成一条调用链。这就是 Coding Agent 做代码理解时应有的粒度。


这时 Agent 才给最终解释。它的答案应该包括四个结论：

第一，`runWithDeadline` 的 `Promise.race` 保证本地调用及时结束；`AbortController` 负责把取消继续传到下游。

第二，`TOOL_TIMEOUT` 被标成 retryable，但是否真的重试还要同时看工具的幂等声明和 `maxRetries`，模型不能自行扩大次数。

第三，fallback 也经过同一个 deadline helper，避免主调用超时以后又永远卡在降级路径。

第四，测试用一个忽略 signal 的慢 handler 证明硬超时成立，而不是只检查“signal 是否被触发”。



Agent 还应该指出一个生产风险：本地 Promise 已经超时，不代表远端副作用一定停止。HTTP 或 MCP 客户端必须真正接收同一个 signal；对于写操作，即使客户端取消，也可能出现“请求已送达、结果未知”。因此高风险工具不能因为超时就自动重试，而要进入状态核对或人工处理。

刚才我们演示的是一个只读的代码分析任务。

接下来要做的，是把这条执行链拆开，看看它在工程上是怎样实现的。

我们会从模型入口开始，一直讲到工具注册、参数校验、权限控制、人工审批、超时重试、MCP 接入和 Trace 记录。

这一部分大家可以按照一条主线来理解：模型提出动作，pi 推进动作，Runtime 判断动作，工具执行动作，最后系统记录动作。



后面的内容一共分成几个层次。

第一层，是把阶段一的统一模型调用服务接入 pi。这里会看到，Coding Agent 不直接连接 DeepSeek，而是通过 LiteLLM Gateway 统一处理模型路由、流式响应、Prompt、Token、成本和错误。

第二层，是工具本身的工程化。我们会把 Python 函数或者 MCP 工具包装成带有名称、Schema、风险、权限、超时和重试配置的标准工具，并通过 Registry 统一管理。

第三层，是执行前的控制。模型返回 Tool Call 以后，Runtime 会重新校验参数，检查角色权限、租户范围、Agent 白名单和运行模式。对于写操作和高风险操作，还要暂停等待人确认。

第四层，是执行过程中的可靠性。我们会实现真正的硬超时、有限重试、幂等键和降级结果，同时区分哪些错误可以交给模型恢复，哪些错误必须直接终止。

第五层，是外部工具接入。我们会把指定的瑞幸 `my-coffee` MCP Server 接入 Registry，让远端工具和本地工具经过完全相同的治理链。

最后，是工程验收。我们会把 Audit、Trace、LoopGuard 和 TDD 连接起来，明确哪些工作由模型完成，哪些工作必须由程序员设计和验证。



我们先来看第一节，我们先处理模型入口：怎样把阶段一的统一 Gateway 接到 pi，让 Coding Agent 使用受控的模型调用链。

## 一、先把阶段一 Gateway 接到 pi，而不是让 Agent 直连模型（约 3 分钟）



刚才 pi 能完成搜索和解释，第一步是拿到模型。这里不再介绍 Gateway 的作用，直接看接法。



Agent 侧只注册一个平台模型 `agent-default`，Base URL 指向阶段一的 `/v1`。供应商 Key 不进入 Node 进程，Node 只持有 Gateway Key。



agent\-tool\-runtime\-pi\-v2/config/platform\.yaml

```TypeScript
const model: Model<"openai-completions"> = {
  id: "agent-default",
  provider: "phase-gateway",
  api: "openai-completions",
  baseUrl: config.gateway.baseUrl,
  contextWindow: 1_000_000,
  maxTokens: 4096,
};
```

程序员在这里要控制两件事。

第一，平台模型名和供应商模型名分开。Prompt、Agent 配置和业务代码只引用 `agent-default`，这样 Gateway 把 Flash 换成 Pro 时，不需要改 Agent。

第二，价格配置要使用预算上界，而不是最乐观的缓存命中价格。LoopGuard 判断是否超预算时宁可提前停，也不能等账单出来才发现成本失控。



Gateway 内部由 FastAPI 嵌入 LiteLLM SDK。

正常路由先尝试 `deepseek-v4-flash`，有限重试仍失败再进入 `deepseek-v4-pro`：

agent\-tool\-runtime\-pi\-v2/gateway/app/service\.py  line 84、137

```Python
response = await litellm.acompletion(
    model=target.litellm_model,
    api_base=target.api_base,
    api_key=api_key,
    messages=request.messages,
    tools=request.tools,
    stream=request.stream,
    max_retries=0,
)
```

这里把 LiteLLM 的 `max_retries` 设置为零，是一个很重要的工程选择。因为重试策略应该只有一个负责方。如果 LiteLLM 自己重试，Gateway 再重试，工具 Runtime 还继续重试，最后一次用户请求可能变成多次下游调用，成本和副作用都会失控。

所以本项目规定：模型调用的重试由 Gateway 负责，工具调用的重试由 ToolRuntime 负责，两边分别计数，分别记录 Trace。

Streaming 也要在 Gateway 这一层处理。普通响应可以在模型失败以后切换备用模型，但流式响应一旦已经把第一段内容发给用户，就不能再无痕切换。否则用户收到的前半段可能来自 Flash，后半段可能来自 Pro，最终很难解释。



因此流式处理遵循一个简单规则：第一段内容发出之前允许切换；第一段内容发出之后，如果连接中断，返回 `STREAM_INTERRUPTED`，由上层重新发起一轮完整请求，而不是拼接两个模型的输出。



除了返回结果，Gateway 还要记录模型调用本身：

agent\-tool\-runtime\-pi\-v2/gateway/app/service\.py line 93

```Plain Text
self.repository.add_call(
    request_id=request_id, requested_model=request.model, actual_model=target.name,
    status="success", attempts=attempts, input_tokens=input_tokens,
    output_tokens=output_tokens, cost_usd=self._cost(target, input_tokens, output_tokens),
    latency_ms=int((time.monotonic() - started) * 1000),
    metadata={"stream": False},
)
```

这条记录里不保存完整 Prompt 和完整响应，而是保存实际模型、Token、成本、延迟和尝试次数。这样做的好处是，后面的 Agent Trace 可以和阶段一的 LLM Call 关联起来，但不会把大量敏感上下文复制到日志系统。



Prompt 也从 Gateway 统一管理。Coding Agent 请求 Prompt 时，只能提交模板名称、版本和变量：

agent\-tool\-runtime\-pi\-v2/runtime/src/pi/prompt\-client\.ts line 12

```JavaScript

    method: "POST",
    headers: { "content-type": "application/json", authorization: `Bearer ${apiKey}` },
```

到这里，第一节的实现链路就完整了：

pi 注册 `agent-default` Provider；Provider 把请求发送到 FastAPI Gateway；Gateway 使用 LiteLLM 路由到 DeepSeek；Gateway 负责重试、Streaming、Prompt、Token、Cost 和 Latency；最后 pi 得到统一的模型响应，并继续推进 Agent Loop。

## 二、注册工具时，同时完成命名投影和能力快照（约 3\.5 分钟）

第一节我们已经把模型入口接通了：pi 使用 `agent-default`，请求进入 LiteLLM Gateway，再由 Gateway 路由到 DeepSeek。模型现在能够正常工作，但它还不知道自己可以调用哪些工具。



接下来要完成的是工具接入。这里的“接入”是指把本地函数、Python 服务和 MCP 工具，统一导入 ToolRegistry，再从 Registry 生成当前 Agent 本轮可以看到的工具快照。



实现 Registry 时，不要只写一个 `Map<string, handler>`。注册动作至少要完成内部身份、模型名称和治理元数据三件事。



agent\-tool\-runtime\-pi\-v2/runtime/src/domain\.ts line17

```TypeScript
interface ToolMetadata {
  internalName: string;
  parameters: TSchema;
  risk: "read" | "write" | "high";
  permissions: string[];
  requiresConfirmation: boolean;
  timeoutMs: number;
  maxRetries: number;
  idempotent: boolean;
  source: "local" | "python" | "mcp";
}
```

内部名称保留领域语义，例如 `order.get_status`、`ticket.create`、`mcp.my-coffee.<tool>`。DeepSeek 的工具名不接受点号，所以向模型投影时改成 `order__get_status`。



接下来把它注册到 Registry：

agent\-tool\-runtime\-pi\-v2/runtime/src/registry\.ts line 5

```TypeScript
export class ToolRegistry {
  private readonly byInternalName = new Map<string, RegisteredTool>();
  private readonly byModelName = new Map<string, RegisteredTool>();

  register(tool: ManagedTool): RegisteredTool {
    const internalName = tool.metadata.internalName;
    if (this.byInternalName.has(internalName)) {
      throw new Error(`Tool already registered: ${internalName}`);
    }
    const modelName = toModelToolName(internalName);
    if (this.byModelName.has(modelName)) {
      throw new Error(`Model tool-name collision: ${modelName}`);
    }
    const registered = { ...tool, modelName };
    this.byInternalName.set(internalName, registered);
    this.byModelName.set(modelName, registered);
    return registered;
  }
```



`internalName` 是系统内部使用的稳定名称，使用领域前缀，便于排查和版本管理。

`description` 会提供给模型。

`parameters` 描述参数结构。

`risk`、`permissions`、`timeoutMs`、`maxRetries` 和 `idempotent`，则是 Runtime 后续执行治理所需要的控制信息。



代码里有一个程序员很容易忽略的点：系统同时维护两个索引。

第一个索引使用内部名称，例如 `order.get_status`，供 Runtime、审计和配置使用。

第二个索引使用模型名称，例如 `order__get_status`，供 DeepSeek 的 Function Calling 使用。



为什么要在注册阶段就检查名称冲突？因为 DeepSeek 的工具名不能包含点号，所以我们会把点号转换成双下划线。如果两个内部名称转换后得到同一个模型名称，模型返回 Tool Call 时就无法知道应该执行哪一个 handler。

这种问题不能等线上调用时再处理。注册阶段直接失败，启动阶段就能发现，定位成本最低。



名称映射代码保持简单，而且必须是可逆、可预测的：

agent\-tool\-runtime\-pi\-v2/runtime/src/name\-mapping\.ts

```TypeScript
const modelName = toModelToolName(internalName);
if (byInternalName.has(internalName)) throw new Error("duplicate tool");
if (byModelName.has(modelName)) throw new Error("model-name collision");
```

这里不要做复杂的自动修复。

工具名如果超过长度，或者包含无法安全转换的字符，直接拒绝注册。自动截断可能造成两个工具映射成同一个名称，最后形成更难发现的执行错误。



工具注册完成以后，还不能把 Registry 中的所有工具全部发送给模型。

我们要根据当前用户、Agent 类型、租户和运行模式生成一个快照。

agent\-tool\-runtime\-pi\-v2/runtime/src/registry\.ts

```Plain Text
snapshot(context: ExecutionContext, policy: PolicyEngine): RegisteredTool[] {
    return this.list().filter((tool) => policy.isVisible(context, tool.metadata.internalName));
  }
```

在 `session_start` 时，Coding Agent Extension 会生成这个快照：先按 Agent 白名单过滤，再向 pi 转成 `AgentTool`。



在 `pi-coding-agent` 入口中，Extension 在 `session_start` 读取用户、租户、角色和模式，再动态注册快照中的工具：

```TypeScript
for (const tool of registry.snapshot(context, policy)) {
  pi.registerTool({
    name: tool.modelName,
    label: tool.metadata.internalName,
    description: tool.metadata.description,
    parameters: tool.metadata.parameters,
    execute: (toolCallId, params) =>
      runtime.invoke({ context, toolCallId, modelName: tool.modelName, args: params }),
  });
}
```

里最关键的是 `execute` 里面没有直接调用 `tool.handler`，而是调用 `runtime.invoke()`。



这保证了不同入口使用同一条执行路径：

- headless `pi-agent-core` 进入 Runtime；

- `pi-coding-agent` Extension 进入 Runtime；

- CLI 进入 Runtime；

- 审批恢复执行也进入 Runtime。



这样做的好处是，工具不管从哪里被调用，都必须经过参数校验、权限判断、确认、超时、重试、审计和 Trace。



到这里，工具已经被导入 Registry，也被投影成模型可见的 Function Calling 定义。

但这时还有一个问题：模型传过来的参数，到底由谁定义，怎么保证和业务服务完全一致？

这就进入第三节：从 Python 的 Pydantic 模型导出 JSON Schema，并让同一份契约同时服务于 pi 和业务接口。

---

## 三、执行前控制，让 Pydantic 成为 Schema 源头，在两个信任边界执行校验（约 3\.5 分钟）

在 Python 业务服务中，我们用 Pydantic 定义输入模型，作为所有校验的单一事实来源：

```Python
class OrderStatusInput(BaseModel):
    model_config = ConfigDict(extra="forbid")
    order_id: str = Field(pattern=r"^ORD-[A-Z]-[0-9]{4,12}$")
```

然后通过 `model_json_schema()` 导出 JSON Schema，供 Node 侧直接读取并交给 PI（Plugin Interface）。**绝对不要**手工维护一份 Pydantic 和一份 TypeScript 的 Schema 副本——两份独立维护的契约，几个月后必然产生偏差。CI 流程应自动重新导出 Schema 并检查 Git diff，若有未提交的变化则直接构建失败。



### 两个边界，两道校验

**第一道：PI 层校验**  

负责尽早拦截模型生成的非法 Tool Call，避免无效请求发往业务服务，节省网络开销。

**第二道：Python 接口层校验**  

再次使用 Pydantic 完整校验，保护业务服务不信任任何调用方。即便未来有其他客户端绕过当前 Agent 直接调用，业务接口仍然安全可靠。



### `extra="forbid"` 不可省略

模型若传入额外字段，例如：

```JSON
{"order_id": "ORD-A-1001", "approved": true}
```

系统必须**整体拒绝**，而不能静默忽略 `approved` 后继续执行。  

原因有二：

- 静默丢弃会让模型误以为“越权参数”生效，产生错误的意图反馈；

- 审计日志中的“模型意图”与“实际执行参数”将无法对齐，造成安全隐患和排查困难。

    

### 特别注意 PI 的验证接缝

PI 0\.83\.0 在 `beforeToolCall` 或 Coding Agent 的 `tool_call` Hook 中修改参数后，**不会自动重新校验**。因此，在真正进入业务 handler 之前，Runtime 必须使用同一份 Pydantic Schema **再次执行校验**。  

即使框架已经做了一次校验，后续代码也绝不可取消这道防线——它守护的是最终执行的参数合法性。



### 结构校验 ≠ 权限校验

参数格式通过校验，只说明它“长得像一个合法的订单号”，**并不代表**当前用户有权查看该订单。  

因此，在结构校验通过之后，业务层仍需执行独立的权限校验（例如判断用户与订单的归属关系），才能继续执行后续逻辑。两者缺一不可，不可混淆。



这一步是最后一道输入防线。只要参数经过了 Hook、适配器或者审批恢复，就不能因为“前面已经校验过”而跳过最终校验。

到这里，工具已经完成了三次关键转换：

第一，从 Python 函数和 Pydantic 模型导出业务 Schema。

第二，Node Runtime 导入 Schema 并注册到 ToolRegistry。

第三，Registry 把内部工具投影成 pi 和 DeepSeek 能理解的模型工具。



下一节就可以进入真正的执行阶段：模型返回 Tool Call 以后，Runtime 怎样按固定顺序完成权限校验、租户校验和人工审批，并保证任何副作用都发生在这些检查之后。

---

## 四、把策略判断排在副作用之前，并固定判断顺序（约 3\.5 分钟）

第三节完成以后，工具已经有了稳定的参数契约。模型传入的 JSON 会先经过 pi 和 Runtime 的 Schema 校验，Python 业务服务还会再校验一次。

但参数合法，只说明它“可以被解析”，还不能说明“允许执行”。比如 `ORD-A-1001` 是合法订单号，但当前用户可能属于 `tenant_b`；又或者当前 Agent 处于只读的 `plan` 模式，模型却请求创建工单。

所以第四节要把校验结果继续送入 Policy。Runtime 的执行顺序必须固定下来：

查工具、校验参数、检查工具可见性、检查角色权限、检查运行模式、检查资源范围，最后判断是否需要人工确认。



我们先看执行上下文。权限判断不能只接收一个用户 ID，至少要把这些信息一起带进来：

```Go
interface ExecutionContext {
  traceId: string;
  requestId: string;
  userId: string;
  tenantId: string;
  roles: string[];
  agentName: string;
  mode: "plan" | "execute";
}
```

这些字段分别解决不同问题。

`userId` 用来确认是谁发起了请求；`tenantId` 用来限制资源范围；`roles` 用来计算权限；`agentName` 用来确定当前 Agent 能看到哪些工具；`mode` 用来区分规划阶段和实际执行阶段。

`traceId` 和 `requestId` 则负责把这次策略判断和后面的 Audit、Trace 关联起来。

执行上下文不能由模型生成。模型可以在文本中说“我是管理员”，但系统只能信任来自认证层和业务请求上下文的身份信息。



Runtime 的准备阶段按固定顺序执行：查找工具、校验参数、检查 Agent 可见性、检查角色权限、检查运行模式、检查租户资源范围，最后判断是否需要人工确认。



顺序固定有两个好处。第一，任何拒绝都发生在 handler 前。第二，相同输入始终得到相同的主错误码，测试和告警不会因为规则遍历顺序变化而抖动。

配置文件里，人写角色和白名单，接下来定义角色权限：：

```YAML
role_permissions:
  supervisor:
    - order:read
    - ticket:create
    - coffee:order

agent_tool_allowlist:
  support-agent:
    - order.get_status
    - ticket.create
    - mcp.my-coffee.*
```

代码读取角色后，合并出当前用户的权限集合：

```TypeScript
permissionsFor(context: ExecutionContext): Set<string> {
  return new Set(
    context.roles.flatMap(
      (role) => this.config.rolePermissions[role] ?? [],
    ),
  );
}
```

这里使用集合而不是数组，是因为一个用户可能有多个角色。比如用户同时拥有 `support` 和 `supervisor`，最终权限应该是两个角色权限的并集。



但角色权限只是第一层。还要限制当前 Agent 可以看到哪些工具：

```Plain Text
agent_tool_allowlist:
  support-agent:
    - order.get_status
    - ticket.create
    - mcp.my-coffee.*
```

Policy 中的白名单判断支持精确匹配和命名空间匹配：

```TypeScript
isVisible(
  context: ExecutionContext,
  internalName: string,
): boolean {
  return (
    this.config.agentToolAllowlist[context.agentName] ?? []
  ).some((pattern) =>
    pattern.endsWith("*")
      ? internalName.startsWith(pattern.slice(0, -1))
      : internalName === pattern,
  );
}
```

为什么需要 Agent 白名单？因为用户权限和 Agent 能力不是一回事。

一个运维用户可能拥有重启服务的权限，但客服 Agent 不应该因此自动看到 `ops.restart_service`。权限判断回答的是“用户有没有权限”，白名单判断回答的是“当前 Agent 是否允许接触这个能力”。



然后进入策略判断主流程：

agent\-tool\-runtime\-pi\-v2/runtime/src/policy\.ts

```TypeScript
evaluate(
  context: ExecutionContext,
  tool: RegisteredTool,
  args: Record<string, unknown>,
): PolicyDecision {
  if (!this.isVisible(context, tool.metadata.internalName)) {
    return {
      action: "deny",
      code: "TOOL_NOT_VISIBLE",
      reason: "工具不在当前 Agent 白名单中",
    };
  }

  const permissions = this.permissionsFor(context);
  const missing = tool.metadata.permissions.filter(
    (permission) => !permissions.has(permission),
  );

  if (missing.length > 0) {
    return {
      action: "deny",
      code: "RBAC_DENIED",
      reason: `缺少权限: ${missing.join(", ")}`,
    };
  }

  if (
    context.mode === "plan" &&
    tool.metadata.risk !== "read"
  ) {
    return {
      action: "deny",
      code: "PLAN_MODE_DENIED",
      reason: "plan 模式禁止写操作",
    };
  }

  return {
    action: "allow",
    code: "OK",
    reason: "策略检查通过",
  };
}
```

这段代码有一个程序员应该坚持的习惯：拒绝要尽可能早。

工具不在白名单，直接拒绝；权限不够，直接拒绝；规划模式调用写工具，直接拒绝。只有通过这些条件以后，才有机会进入确认或执行阶段。

不要把所有判断写成一个很长的布尔表达式，例如：

```Plain Text
if (visible && hasPermission && !plan && inTenant && confirmed) {
  execute();
}
```

这种写法的问题是，出了问题以后很难知道究竟是哪一条规则拒绝了调用，也很难给模型返回可恢复的错误码。

工程实现中，每个拒绝分支都应该有稳定的 `code` 和可读的 `reason`。模型拿到 `RBAC_DENIED`，可以解释权限不足；拿到 `RESOURCE_SCOPE_DENIED`，可以提示用户检查订单所属租户；拿到 `PLAN_MODE_DENIED`，可以继续规划但不能执行写入。



除了角色权限，还需要做资源范围判断。比如当前租户只能访问自己的订单：

```JavaScript
const orderId = args.order_id;

if (typeof orderId === "string") {
  const prefixes =
    this.config.resourceTenantPrefixes[context.tenantId] ?? [];

  if (
    !prefixes.some((prefix) =>
      orderId.startsWith(prefix),
    )
  ) {
    return {
      action: "deny",
      code: "RESOURCE_SCOPE_DENIED",
      reason: "目标订单不属于当前租户",
    };
  }
}
```

教学项目用订单号前缀表示租户范围，真实系统一般会调用统一的资源授权服务。但代码结构应该保持一致：把用户、租户、资源和动作一起交给策略层判断。

拥有 `order:read`，不代表可以读取所有订单；拥有 `database:read`，也不代表可以查询所有租户、所有表和所有字段。

这里还要区分 `plan` 和 `execute`。

`plan` 模式允许 Agent 搜索代码、读取文件、查询只读数据，但禁止产生写入副作用。`execute` 模式才允许继续进入写操作流程。



所以刚才的 Coding Agent 演示使用 `plan` 模式，即使模型调用了 `ticket.create`，也会在 Runtime 这里被拒绝。这个限制不能只写在 System Prompt 中，因为 Prompt 只能提醒模型，不能约束模型。



策略判断通过以后，仍然不能直接调用 handler。接下来还要判断工具是否需要确认：

```Plain Text
if (
  tool.metadata.requiresConfirmation &&
  !approvalSatisfied
) {
  return {
    action: "confirm",
    code: "APPROVAL_REQUIRED",
    reason: "该动作必须绑定参数后由人确认",
  };
}
```

`read` 工具通常可以自动执行，例如查询订单状态、搜索知识库或者读取服务健康信息。

`write` 工具，例如创建工单、修改订单备注，需要根据业务策略决定是否确认。

`high` 风险工具，例如下单、退款、删除数据、执行生产命令，必须人工确认。

特别是 `my-coffee` MCP。我们可以确定它的服务器地址，但在没有 Token 完成工具发现之前，不能假设远端暴露了哪些具体工具，也不能假设某个工具只是查询。项目因此把远端工具默认注册为 `high` 风险，并要求 `coffee:order` 权限和人工确认。

一旦策略返回 `confirm`，Runtime 不应该在当前进程里阻塞等待输入，也不能让模型自己回复一句“已确认”。正确做法是创建一条持久化审批记录，返回 `approval_id`，然后由 Harness 停止当前 Loop。



下一节我们来学习如何把一次人工确认保存成可恢复、可验证、不可篡改参数的执行状态。

---

## 五、把人工审批设计成可恢复状态，而不是一轮对话（约 3\.5 分钟）

第四节最后，Policy 返回了 `confirm`。这意味着工具本身没有被拒绝，用户也具备相应权限，但系统不能让模型直接执行，需要先把这次调用保存成一条等待人工处理的状态。

接下来进入第五节：人工审批怎样设计成一个可恢复的执行流程。

这里有一个实现原则：审批不能只是当前对话里的一个布尔值，不能让模型在参数里传入 `"approved": true`，也不能只保存在内存里。审批必须是一条持久化记录，并且要和这次调用的具体参数绑定。



先看审批摘要是怎样生成的：

```TypeScript
const digest = sha256(canonicalJson({
  trace_id,
  tool_call_id,
  tool_name,
  user_id,
  tenant_id,
  args,
}));
```

Runtime 返回 `APPROVAL_REQUIRED` 和 `approval_id`。`LoopGuard` 发现当前 Trace 有待审批记录，在这一轮结束后停止。模型不能通过再调用一次，或者在参数里补一个 `approved: true` 来绕过它。



这里没有直接对普通 JSON 字符串做哈希，而是先经过 `canonicalJson`。

原因是对象字段的顺序不应该影响摘要。下面两个对象，业务含义相同：

```Plain Text
{"order_id":"ORD-A-1001","title":"Need help"}
```

```Plain Text
{"title":"Need help","order_id":"ORD-A-1001"}
```

如果直接对字符串哈希，两个结果会不同；规范化以后，字段按固定顺序排列，摘要才能稳定。



审批记录至少要保存这些字段：

```Plain Text
interface ApprovalRecord {
  id: string;
  trace_id: string;
  tool_call_id: string;
  tool_name: string;
  context_json: string;
  args_json: string;
  args_digest: string;
  status: string;
  expires_at: string;
  decided_by: string | null;
  created_at: string;
}
```

`trace_id` 用来关联整次 Agent Run；`tool_call_id` 用来关联模型提出的那一次调用；`tool_name` 和 `args_digest` 用来确认批准的究竟是哪一个动作；`expires_at` 防止一条旧审批无限期有效。

当 Policy 判断需要确认时，Runtime 创建记录：

```Plain Text
const approval = store.createApproval({
  context: request.context,
  toolCallId: request.toolCallId,
  toolName: request.modelName,
  args: validatedArgs,
});
```

然后返回：

```Plain Text
{
  ok: false,
  action: "confirm",
  code: "APPROVAL_REQUIRED",
  content: "该动作必须绑定参数后由人确认",
  approvalId: approval.id
}
```

这里的 `ok: false` 不代表工具执行失败，而是表示当前调用还没有完成。`action: "confirm"` 比单纯返回一个错误字符串更重要，因为上层 Harness 要根据这个状态停止 Loop，而不是把它当成普通异常继续重试。

在 `pi-agent-core` 中，我们通过 `shouldStopAfterTurn` 读取当前 Trace 是否存在待审批记录：

```Plain Text
shouldStopAfterTurn: async () => {
  const pending = runtime.pendingApproval(traceId);
  return guard.shouldStop(pending).stop;
}
```

如果存在 `pendingApproval`，Loop 返回 `AWAITING_APPROVAL`。模型不会继续下一轮，也不会自己决定是否批准。



这时由人通过 CLI 或审批 API 处理：

```Plain Text
npm run cli -- approvals list
```

返回待审批记录以后，操作人查看工具名称、风险等级、参数摘要和影响范围，再执行批准或拒绝：

```Plain Text
npm run cli -- approvals decide <approval-id> \
  --decision approve \
  --actor teacher
```

这里的 `actor` 必须来自真实操作人身份。在生产系统中，它应该由登录态或企业身份系统提供，不应该允许调用方随便传一个字符串就完成审批。教学项目使用命令行参数，是为了把状态流转过程展示出来。

审批 API 提供同样的能力：

```Plain Text
POST /approvals/{approval-id}/decision
Authorization: Bearer <approval-api-key>
Content-Type: application/json

{
  "decision": "approve",
  "actor": "teacher"
}
```

API 只负责记录审批结果，不直接把一个 `"approved": true` 传回模型上下文。审批结果写入 SQLite，状态从 `pending` 变为 `approved` 或 `rejected`。

接下来是执行阶段：

```Plain Text
npm run cli -- approvals execute <approval-id>
```

执行审批时，Runtime 不能只查询状态，然后直接调用原来的 handler。它要重新执行完整校验流程：

agent\-tool\-runtime\-pi\-v2/runtime/src/runtime\.ts

```JavaScript
const approval = store.getApproval(id);

if (!approval || approval.status !== "approved") {
  return failure(
    "APPROVAL_NOT_EXECUTABLE",
    "审批不存在、已过期或已被消费",
  );
}

const context =
  JSON.parse(approval.context_json);

const storedArgs =
  JSON.parse(approval.args_json);

const currentDigest = approvalDigest({
  traceId: approval.trace_id,
  toolCallId: approval.tool_call_id,
  toolName: approval.tool_name,
  context,
  args: storedArgs,
});

if (currentDigest !== approval.args_digest) {
  return failure(
    "APPROVAL_BINDING_MISMATCH",
    "工具参数已变化，旧审批失效",
  );
}
```

这里要特别注意，审批执行不是对初次调用的简单续接，而是一次新的安全边界检查。

执行前至少重新确认四件事：

第一，工具还存在，模型名称映射没有变化。

第二，参数仍然符合当前版本的 Schema。

第三，用户权限和租户范围没有变化。

第四，当前参数摘要和批准时完全一致。

例如，第一次请求是：

```Plain Text
{
  "order_id": "ORD-A-1001",
  "title": "支付状态异常"
}
```

操作人批准以后，如果有人把参数替换成：

```Plain Text
{
  "order_id": "ORD-A-1001",
  "title": "删除订单"
}
```

即使审批状态已经是 `approved`，摘要也不一致，Runtime 必须返回：

```Plain Text
APPROVAL_BINDING_MISMATCH
```

不能因为“这个审批已经批准过”就继续执行。

重新校验通过以后，还要原子领取审批：

agent\-tool\-runtime\-pi\-v2/runtime/src/store\.ts line 254

```Plain Text
claimApproval(id: string): boolean {
  const result = db
    .prepare(
      `UPDATE approvals
       SET status = 'executing'
       WHERE id = ?
         AND status = 'approved'
         AND expires_at > ?`,
    )
    .run(
      id,
      new Date().toISOString(),
    );

  return Number(result.changes) === 1;
}
```

这段 SQL 解决的是并发问题。

如果两个 Worker 同时执行同一个审批，只有一个 Worker 能把状态从 `approved` 更新为 `executing`。另一个 Worker 更新行数为零，直接返回 `APPROVAL_NOT_EXECUTABLE`。

不要用进程内的 boolean 或 Map 来做这个控制。单进程时看起来没问题，但服务一旦重启或者扩容到多个实例，内存状态就无法保证一致性。

工具完成以后，再把审批状态更新为 `consumed`：

```Plain Text
const result = await executePrepared(prepared);

store.finishApproval(
  id,
  result.ok ? "consumed" : "failed",
  result.ok ? undefined : result.code,
);
```

一个审批只能有这样的状态流转：

```Plain Text
pending
  → approved
  → executing
  → consumed
```

或者：

```Plain Text
pending
  → rejected
```

如果执行失败，也应该进入 `failed`，而不是回到 `approved` 后让系统自动重放。尤其是远端写操作，失败并不一定代表没有副作用。



举个例子，Runtime 调用瑞幸 `my-coffee` 工具时，HTTP 请求已经发到服务器，但本地在等待响应时超时。此时我们不知道订单是否已经创建成功。如果直接把审批恢复成 `approved`，再自动执行一次，可能产生重复订单。

所以高风险工具的超时处理应该是：

```Plain Text
请求超时
→ 标记结果未知
→ 保留 Trace 和审批记录
→ 查询下游状态或交给人工核对
→ 不自动重放
```

审批摘要也不能只绑定参数。还要绑定用户、租户、工具名和 Tool Call ID。否则同一个参数可能被另一个用户、另一个租户或者另一条 Agent Run 重用。

最后看一下人工审批和模型的职责边界。

模型可以告诉用户：“这个动作需要确认”，也可以解释它准备调用什么工具；但模型不能产生有效审批。

人要决定：

- 这次动作是否真的符合业务意图；

- 参数是否正确；

- 影响范围是否可以接受；

- 当前环境是否允许执行；

- 是否需要补充人工核对。

程序要保证：

- 审批记录持久化；

- 参数摘要不可篡改；

- 审批过期；

- 角色权限重新校验；

- 批准只能消费一次；

- 执行结果完整记录。

这样，人工确认才不只是对话中的一句“同意”，而是一条可以恢复、可以审计、可以追责的执行状态。



到这里，我们已经解决了“能不能执行”的问题。下一节继续处理“开始执行以后如何可靠结束”：工具超时怎么办，哪些错误可以重试，哪些错误必须停止，以及降级结果怎样避免被模型误解成真实成功。



---

## 六、实现真正的硬超时，并让重试只有一个 owner（约 3\.5 分钟）



第五节我们把人工审批设计成了一个可恢复状态：调用先暂停，参数和上下文被持久化，审批通过后重新校验并原子执行。

现在进入第六节。审批通过并不代表工具一定能成功。网络会抖动，下游会限流，服务会超时，甚至可能出现“请求已经发出，但结果没有回来”的情况。

这一节重点处理三件事：硬超时、有限重试和受控降级。



先看 Runtime 的执行入口：

```Plain Text
const output = await runWithDeadline(
  () =>
    tool.handler({
      toolCallId: prepared.toolCallId,
      args: prepared.validatedArgs,
      context: prepared.context,
      signal: timeoutController.signal,
    }),
  tool.metadata.timeoutMs,
  timeoutController,
);
```

这里没有直接写：

```Plain Text
await tool.handler(...);
```

而是统一包了一层 `runWithDeadline`。

```Plain Text
async function runWithDeadline<T>(
  work: () => Promise<T>,
  timeoutMs: number,
  controller: AbortController,
): Promise<T> {
  let timeout: ReturnType<typeof setTimeout> | undefined;

  const deadline = new Promise<never>((_resolve, reject) => {
    timeout = setTimeout(() => {
      controller.abort();

      reject(
        new ToolRuntimeError(
          "TOOL_TIMEOUT",
          "工具执行超时",
          true,
        ),
      );
    }, timeoutMs);
  });

  try {
    return await Promise.race([
      work(),
      deadline,
    ]);
  } finally {
    if (timeout) {
      clearTimeout(timeout);
    }
  }
}
```

这里有两个动作必须同时存在。

第一个动作是 `controller.abort()`。它把取消信号传给 handler，让支持取消的 HTTP 请求、数据库查询或者 MCP 请求主动停止。

第二个动作是 `Promise.race()`。它保证即使 handler 不监听 `AbortSignal`，Runtime 也不会一直等下去。

这两个动作解决的问题不同。



如果只有 `AbortController`，不合作的 handler 仍然可能继续运行，Runtime 也会继续等待。

如果只有 `Promise.race`，Runtime 虽然能及时返回，但下游请求可能还在后台执行，尤其是写操作，可能已经产生副作用。

所以硬超时的语义应该是：

```Plain Text
本地 Runtime 到时间必须返回
同时尽可能取消下游请求
如果副作用状态不确定，不自动重放
```

项目里专门写了一个测试，验证 handler 忽略取消信号时，超时仍然生效：

```Plain Text
async handler() {
  await new Promise((resolve) =>
    setTimeout(resolve, 250),
  );

  return { status: "too-late" };
}
```

这个工具的超时时间只有 15 毫秒：

```Plain Text
timeoutMs: 15,
maxRetries: 0,
idempotent: true,
```

测试断言的是实际行为：

```Plain Text
expect(result).toMatchObject({
  ok: false,
  code: "TOOL_TIMEOUT",
});

expect(Date.now() - started)
  .toBeLessThan(150);
```

这里不要只断言 `AbortSignal.aborted === true`。那只能说明发出了取消信号，不能说明调用真的及时结束。生产测试应该断言错误码、返回时间和是否产生副作用。

接下来是重试。

重试不能写成：

```Plain Text
catch {
  return executeAgain();
}
```

因为不是所有工具都可以安全重复调用。

Runtime 根据工具元数据计算最大尝试次数：

```Plain Text
const maxAttempts =
  tool.metadata.idempotent
    ? tool.metadata.maxRetries + 1
    : 1;
```

这段代码表达了一个硬规则：

只有幂等工具，才允许按照 `maxRetries` 重试。

读取订单状态通常是幂等的，同样的订单号查两次，不会创建新的业务对象。

创建工单、提交订单、发起退款，即使接口看起来支持重试，也必须先证明下游有幂等机制。否则网络超时以后，第一次请求可能已经成功，第二次请求就会创建重复工单或重复订单。

错误还要分成可重试和不可重试。

```Plain Text
const retryable =
  lastError instanceof ToolRuntimeError &&
  lastError.retryable;

if (
  !retryable ||
  attempt >= maxAttempts
) {
  break;
}
```

适合重试的错误通常包括：

```Plain Text
HTTP 502、503、504
临时网络断开
连接池暂时不可用
可恢复的 429 限流
```

不适合重试的错误包括：

```Plain Text
参数格式错误
权限拒绝
租户范围错误
资源不存在
策略拦截
非幂等写操作
```

工程上不要只根据 HTTP 状态码判断。比如一个接口返回 500，可能是业务已经写入成功，只是响应生成失败。对于写操作，是否能重试应该由下游接口的幂等契约决定，而不是由 Runtime 猜测。

重试之间要增加退避时间：

```Plain Text
await new Promise((resolve) =>
  setTimeout(
    resolve,
    Math.min(
      25 * 2 ** (attempt - 1),
      100,
    ),
  ),
);
```

示例中的等待时间比较短，是为了课堂测试快速完成。生产环境通常会使用指数退避加随机抖动，避免大量请求在同一时间再次打到已经不稳定的服务。

重试次数还必须进入 Trace。我们需要知道：

```Plain Text
这次 Tool Call 一共尝试了几次
每次失败的错误码是什么
最终是成功、降级还是失败
```

不能只在最后记录“成功”，否则线上排查时看不出系统是否一直在反复撞击下游。

下面看降级。

降级不是伪造一个正常结果，而是返回明确的不确定性：

```Plain Text
async fallbackHandler({ args }) {
  return {
    order_id: args.order_id,
    status: "unknown",
    source: "fallback-cache",
    warning: "实时订单服务不可用，请人工核实",
  };
}
```

这里不能返回：

```Plain Text
{
  "status": "shipped"
}
```

因为实时查询失败时，我们没有证据证明订单就是 shipped。模型拿到降级结果以后，可以向用户解释“当前无法确认实时状态”，但不能把 `unknown` 改写成确定状态。

Runtime 只在最后一次尝试失败，并且错误仍然是 retryable 时，才进入 fallback：

```Plain Text
if (
  tool.fallbackHandler &&
  lastError instanceof ToolRuntimeError &&
  lastError.retryable
) {
  const output = await runWithDeadline(
    () => tool.fallbackHandler!(input),
    tool.metadata.timeoutMs,
    fallbackController,
  );

  return this.success(
    prepared,
    output,
    attemptsUsed,
    latencyMs,
    "FALLBACK_OK",
  );
}
```

注意，fallback 也使用同一个硬超时控制。不能因为主服务超时，就让降级服务无限等待。

另外，fallback 的成功码不能伪装成普通成功。示例使用 `FALLBACK_OK`，审计和 Trace 中可以清楚区分：

```Plain Text
OK          实时调用成功
FALLBACK_OK 使用了降级结果
TOOL_TIMEOUT 工具超时
```

这样模型、调用方和监控系统都能知道这不是正常实时结果。

还要特别区分模型调用重试和工具调用重试。

模型调用由 LiteLLM Gateway 负责：

```Plain Text
agent-default
→ deepseek-v4-flash
→ 有限重试
→ deepseek-v4-pro
```

工具调用由 ToolRuntime 负责：

```Plain Text
order.get_status
→ 校验幂等性
→ 判断错误是否 retryable
→ 有限重试
→ 必要时 fallback
```

这两层不能共用一个模糊的“重试次数”。模型重试不会自动允许工具重试，工具重试也不应该重新触发一整轮模型请求。

最后看一个最容易出事故的场景：写操作超时。

例如 `my-coffee` MCP 的下单请求已经发到远端，但本地等待响应时超时。此时系统无法确定订单是否已经创建。

正确处理不是：

```Plain Text
超时
→ 自动重试
→ 再下一单
```

而是：

```Plain Text
超时
→ 返回状态未知
→ 保留原始 Trace
→ 使用幂等键查询下游状态
→ 无法确认时交给人工处理
```

所以高风险工具通常应该满足三个条件：

第一，有稳定的幂等键。

第二，有查询执行结果的接口。

第三，超时以后能够进入人工核对流程。

这也是为什么前面审批、超时、重试和 Trace 必须放在同一个 Runtime 里。它们不是互相独立的工具函数，而是一次受治理执行的连续状态。

到这里，我们已经解决了本地工具和 Python 工具的失败恢复。下一节继续把远端工具接入进来：使用指定的 `my-coffee` MCP Server，完成工具发现、Schema 转换和统一执行，同时保证 MCP 工具不能绕过当前 Runtime 的权限、审批和审计链。



---

## 七、接入指定 MCP 时，先包成内部工具，再进入治理链（约 3\.5 分钟）



第六节解决的是工具执行过程中的失败问题：怎样硬超时，怎样控制重试，怎样返回明确的降级结果。

现在这些工具主要还是本地工具或者 Python 服务。下一步我们要把外部工具接进来。这里使用的是指定的瑞幸 `my-coffee` MCP Server。



接入 MCP 时，最重要的是连接以后，远端工具能不能和本地工具走完全相同的治理链。

正式配置如下：

```Plain Text
mcp_servers:
  - id: my-coffee
    type: streamablehttp
    url: https://gwmcp.lkcoffee.com/order/user/mcp
    headers:
      Authorization: Bearer ${LUCKIN_MCP_TOKEN}
    trust: trusted
    default_risk: high
    permissions:
      - coffee:order
```

这里有一个明确的安全边界：配置文件里不保存真实 Token，只保存环境变量占位符。

运行前由操作人设置：

```Plain Text
export LUCKIN_MCP_TOKEN="<登录后复制的 Token>"
```

适配器在连接时展开这个变量：

```Plain Text
function resolveHeaders(
  headers: Record<string, string>,
): Record<string, string> {
  return Object.fromEntries(
    Object.entries(headers).map(([name, template]) => [
      name,
      template.replace(
        /\$\{([A-Z][A-Z0-9_]*)\}/g,
        (_match, envName: string) => {
          const value = process.env[envName];

          if (!value) {
            throw new Error(
              `MCP_AUTH_MISSING: 请设置环境变量 ${envName}`,
            );
          }

          return value;
        },
      ),
    ]),
  );
}
```

如果 Token 没有配置，适配器直接失败，不会把空 Token 发给服务器，也不会自动切换到其他 MCP Server。

然后创建 Streamable HTTP Transport：

```Plain Text
const transport =
  new StreamableHTTPClientTransport(
    new URL(server.url),
    {
      requestInit: {
        headers: resolveHeaders(server.headers),
      },
    },
  );
```

建立连接：

```Plain Text
const client = new Client(
  {
    name: "agent-tool-runtime",
    version: "2.0.0",
  },
  {
    capabilities: {},
  },
);

await client.connect(transport);
```

连接成功以后，第一步不是直接调用工具，而是先发现工具：

```Plain Text
const discovered =
  await client.listTools();
```

MCP Server 返回的工具定义中，通常包含工具名称、描述和输入 Schema。我们要把每个远端工具转换成内部的 `ManagedTool`。

agent\-tool\-runtime\-pi\-v2/runtime/src/mcp/adapter\.ts

```Plain Text
for (const remoteTool of discovered.tools) {
  const internalName =
    `mcp.${server.id}.${remoteTool.name}`;

  registry.register({
    metadata: {
      internalName,
      description:
        remoteTool.description ??
        `MCP tool ${remoteTool.name}`,
      version: "mcp",
      parameters:
        remoteTool.inputSchema as TSchema,
      risk: server.defaultRisk,
      permissions: server.permissions,
      requiresConfirmation:
        server.defaultRisk !== "read",
      timeoutMs: 10_000,
      maxRetries:
        server.defaultRisk === "read" ? 1 : 0,
      idempotent:
        server.defaultRisk === "read",
      source: "mcp",
    },

    async handler({ args, signal }) {
      const result = await client.callTool(
        {
          name: remoteTool.name,
          arguments: args,
        },
        undefined,
        {
          signal,
          timeout: 10_000,
        },
      );

      if (result.isError) {
        throw new ToolRuntimeError(
          "MCP_TOOL_ERROR",
          normalizeMcpText(result.content),
          false,
        );
      }

      if (
        "structuredContent" in result &&
        result.structuredContent
      ) {
        return result.structuredContent;
      }

      return {
        content: normalizeMcpText(result.content),
        server_id: server.id,
      };
    },
  });
}
```

这里做了几个转换。

远端名称会加上 `mcp.my-coffee.` 前缀。例如远端工具叫 `create_order`，内部名称就是：

```Plain Text
mcp.my-coffee.create_order
```

之后再映射成模型名称：

```Plain Text
mcp__my-coffee__create_order
```

这样可以在 Trace 和审计里区分工具来源，也可以通过命名空间白名单控制整组 MCP 工具。

远端 Schema 直接进入内部 Registry，但不会绕过本地 Runtime。模型生成调用以后，仍然经过：

```Plain Text
模型 Tool Call
→ pi 参数校验
→ Runtime 再校验
→ Agent 白名单
→ RBAC
→ 租户与资源策略
→ 风险确认
→ MCP client.callTool
→ 输出校验
→ Audit
→ Trace
```

也就是说，MCP 只是工具的传输和发现协议，不是权限系统。

`my-coffee` 的工具默认按高风险处理，是因为我们在没有实际发现清单之前，不能假设每个工具都是只读操作。远端工具可能包含查询门店、查看订单，也可能包含创建订单、修改订单等有副作用的动作。

因此默认配置是：

```Plain Text
default_risk: high
permissions:
  - coffee:order
```

这样模型即使发现了远端工具，也不能直接执行。必须同时满足：

```Plain Text
当前 Agent 白名单允许
用户拥有 coffee:order
当前模式不是 plan
审批记录已批准
审批参数摘要一致
```

如果拿到真实工具清单以后，确认某个工具只是查询，可以由人单独配置成 `read`。这个动作应该经过代码评审，不能让模型根据工具描述自行降低风险。

MCP 调用还要把 Runtime 的取消信号继续传给 SDK：

```Plain Text
await client.callTool(
  {
    name: remoteTool.name,
    arguments: args,
  },
  undefined,
  {
    signal,
    timeout: 10_000,
  },
);
```

这样 Runtime 的硬超时触发以后，MCP 请求也会收到取消通知。

但需要注意，取消请求不等于远端副作用已经回滚。

对于查询工具，超时以后可以有限重试。

对于下单工具，即使本地超时，也可能已经在服务器端创建成功。这时不能自动再调用一次。正确流程应该是：

```Plain Text
MCP 请求超时
→ 标记执行结果未知
→ 保留 trace_id 和 tool_call_id
→ 使用幂等键或查询接口确认状态
→ 无法确认时交给人工处理
```

MCP 输出也不能直接完整塞回模型。首先要处理文本、结构化内容和错误内容：

```Plain Text
function normalizeMcpText(
  content: unknown,
): string {
  if (!Array.isArray(content)) {
    return JSON.stringify(content);
  }

  return content
    .map((item) => {
      if (
        item &&
        typeof item === "object" &&
        "text" in item
      ) {
        return String(item.text);
      }

      return JSON.stringify(item);
    })
    .join("\n");
}
```

生产环境还要对输出做大小限制和敏感字段脱敏，防止 MCP Server 把过大的内容或者内部凭据直接放进模型上下文。

另外，远端工具定义可能发生变化。今天的 `inputSchema` 和明天的 `inputSchema` 不一定相同，所以发现工具时应该记录：

```Plain Text
server_id
remote_tool_name
schema_hash
discovered_at
server_version
```

如果 Schema 哈希变化，至少要告警；对于高风险工具，建议暂停使用，重新进行人工确认。

测试分成两种。

本地 MCP 测试使用 stdio Server，只验证适配器公共接口：

```Plain Text
npm run test:mcp
```

它验证的是：

```Plain Text
发现工具
→ 注册 Registry
→ Runtime 执行
→ Audit
→ Trace
```

正式服务器使用真实 Streamable HTTP 连接：

```Plain Text
export LUCKIN_MCP_TOKEN="<登录后复制的 Token>"
npm run test:mcp:live
```

这个测试只负责连接和发现工具，不会擅自调用下单操作。

如果没有 `LUCKIN_MCP_TOKEN`，测试必须以 `LIVE_MCP_CREDENTIAL_MISSING` 失败；如果服务器没有返回任何工具，也必须失败。不能用本地演示工具伪造正式服务器已经接入。

到这里，远端 MCP 工具已经被转换成了内部工具，但还没有完成一次完整的可观测闭环。下一节我们继续看 Audit 和 Trace：怎样记录这次 MCP 调用是谁发起的、经过了哪些策略、最终调用了哪个远端工具，以及出现问题以后怎样把完整链路还原出来。

---

## 八、用 Audit 记录责任，用 Trace 还原执行链（约 2\.5 分钟）

第七节完成了 MCP 接入。远端工具已经被转换成内部工具，并且和本地工具一样，经过 Registry、Schema、Policy、Approval 和 Runtime 执行。

但是工具执行完成以后，我们还需要回答一个问题：这次调用到底发生了什么？

谁发起的？调用了哪个工具？参数是什么？有没有经过审批？调用耗时多久？失败发生在模型、Runtime、MCP，还是下游业务服务？

这就是第八节要解决的问题：Audit 和 Trace。



先看一次完整的 Agent Run。

```Plain Text
用户请求
└── Agent Run
    ├── LLM Call
    ├── Tool Call: order.get_status
    ├── LLM Call
    ├── Tool Call: mcp.my-coffee.query_order
    └── Final Answer
```

这条链路中，模型调用和工具调用可能来自不同模块、不同服务，甚至不同进程。如果没有统一的 Trace ID，最后只能看到一堆相互独立的日志。

所以在 Agent Run 开始时，先创建一个 Trace：

```Plain Text
const traceId = randomUUID();

const context = executionContext({
  traceId,
  requestId: randomUUID(),
  userId,
  tenantId,
  roles,
  agentName,
  mode,
});
```

之后所有事件都携带这个 `traceId`。

工具调用还要有独立的 `toolCallId`：

```Plain Text
{
  traceId: "trace-123",
  toolCallId: "call-456",
  toolName: "order__get_status"
}
```

`traceId` 表示一次完整任务，`toolCallId` 表示任务中的某一次工具调用。

如果模型在一轮中调用三个工具，就会有三个不同的 `toolCallId`，但它们共享同一个 `traceId`。

### 先实现 Audit Record

Audit 关注的是责任和合规，核心问题是：

```Plain Text
谁在什么时间，对哪个资源，执行了什么动作？
```

示例结构：

```Plain Text
interface ToolAuditRecord {
  trace_id: string;
  tool_call_id: string;
  tool_name: string;
  tool_version: string;

  user_id: string;
  tenant_id: string;
  agent_name: string;

  risk_level: string;
  status: string;
  code: string;

  started_at: string;
  finished_at: string;
  latency_ms: number;

  input_redacted: unknown;
  output_redacted?: unknown;
  error_code?: string;
}
```

在 Runtime 中，策略拒绝也要记录：

```Plain Text
store.addAudit({
  eventType: "policy_decision",
  context,
  toolCallId,
  toolName,
  status: "deny",
  code: "RBAC_DENIED",
  input: redact(args),
});
```

工具成功执行也要记录：

```Plain Text
store.addAudit({
  eventType: "tool_execution",
  context,
  toolCallId,
  toolName: tool.metadata.internalName,
  status: "success",
  code: "OK",
  input: redact(validatedArgs),
  output: redact(output),
  latencyMs,
});
```

工具失败同样要记录：

```Plain Text
store.addAudit({
  eventType: "tool_execution",
  context,
  toolCallId,
  toolName: tool.metadata.internalName,
  status: "error",
  code,
  input: redact(validatedArgs),
  output: { message },
  latencyMs,
});
```

这里不能只记录成功。实际生产问题经常发生在失败、拒绝和待审批状态中。如果只保留成功日志，最重要的安全事件反而会丢失。

### 脱敏必须发生在写日志之前

不要先把完整输入写入数据库，再在查询时脱敏。这样数据库、备份、日志采集器和调试工具里都可能已经存在明文。

正确方式是进入 Audit 之前就脱敏：

```Plain Text
export function redact(
  value: unknown,
  configured: string[] = [],
): unknown {
  const sensitive =
    new Set(
      configured.map((item) =>
        item.toLowerCase(),
      ),
    );

  if (
    value &&
    typeof value === "object"
  ) {
    return Object.fromEntries(
      Object.entries(
        value as Record<string, unknown>,
      ).map(([key, item]) => [
        key,
        sensitive.has(key.toLowerCase()) ||
        GENERIC_SENSITIVE_KEYS.test(key)
          ? "***"
          : redact(item, configured),
      ]),
    );
  }

  return value;
}
```

工具可以在 Schema 或 Metadata 中声明敏感字段：

```Plain Text
sensitiveFields: [
  "customer_email",
  "access_token",
]
```

同时使用通用规则识别：

```Plain Text
const GENERIC_SENSITIVE_KEYS =
  /(?:token|secret|password|api[_-]?key|authorization)/i;
```

这样即使某个工具忘记配置 `access_token`，通用规则也能提供第二层保护。

审计日志中应该看到：

```Plain Text
{
  "customer_email": "***",
  "access_token": "***"
}
```

而不是：

```Plain Text
{
  "customer_email": "alice@example.com",
  "access_token": "sk-live-..."
}
```

需要特别注意，脱敏不仅处理输入，也处理输出。很多敏感字段不是模型传进来的，而是工具响应带出来的。

### Trace 关注调用过程

Audit 记录责任，Trace 记录过程。

pi 会产生多个事件：

```Plain Text
if (
  event.type === "message_end" &&
  event.message.role === "assistant"
) {
  guard.observeAssistantUsage({
    totalTokens:
      event.message.usage.totalTokens,
    costUsd:
      event.message.usage.cost.total,
  });
}

if (event.type === "turn_end") {
  guard.observeTurn();
}
```

工具开始和结束时，写入对应 Trace：

```Plain Text
if (
  event.type === "tool_execution_start" ||
  event.type === "tool_execution_end"
) {
  store.addTrace({
    traceId: context.traceId,
    eventType: `pi.${event.type}`,
    payload: {
      tool_call_id: event.toolCallId,
      tool_name: event.toolName,
      is_error:
        "isError" in event
          ? event.isError
          : false,
    },
  });
}
```

Runtime 自己也要写事件：

```Plain Text
store.addTrace({
  traceId: context.traceId,
  eventType: "tool.approval_requested",
  payload: {
    tool_call_id: toolCallId,
    tool_name: modelName,
    approval_id: approval.id,
  },
});
```

完整 Trace 可能是：

```Plain Text
pi.message_end
pi.turn_end
tool.approval_requested
pi.tool_execution_end
tool.completed
pi.message_end
```

在调试时，我们可以通过 Trace ID 查询整条链：

```Plain Text
npm run cli -- trace <trace-id>
```

它可以帮助我们回答：

```Plain Text
模型在第几轮调用了工具？
工具是否在可见白名单中？
参数在哪一步被拒绝？
有没有创建审批？
谁批准了这次调用？
远端 MCP 是否返回错误？
最终答案使用了哪次工具结果？
```

### Audit 和 Trace 不要互相替代

有些团队会把所有信息都写到一张日志表里，短期看起来简单，长期会出现两个问题。

第一个问题是责任信息和调试信息混在一起。合规人员想查“谁执行了写操作”，却需要扫描大量模型事件。

第二个问题是数据保留周期不同。Trace 可能只保留七天，Audit 可能要保留一年甚至更久。

所以项目中使用两个表：

```Plain Text
audit_records
trace_events
```

Audit 面向安全追责，Trace 面向调试和性能分析。

模型调用还可以额外记录到 Gateway 的 `llm_calls`：

```Plain Text
llm_calls
tool_audit_records
trace_events
```

三个层次通过 `request_id`、`trace_id` 和 `tool_call_id` 关联。

### 观察 pi 的即时失败事件

还有一个工程细节：不是所有失败都会进入 `afterToolCall`。

例如工具不存在、Schema 校验失败，或者 `beforeToolCall` 直接阻止时，pi 可能只产生 `tool_execution_end`，而不会触发正常的 `afterToolCall`。

所以我们在事件观察器中补一层：

```Plain Text
if (
  event.type === "tool_execution_end" &&
  event.isError &&
  !runtime.wasAudited(event.toolCallId)
) {
  runtime.recordPiImmediateFailure({
    context,
    toolCallId: event.toolCallId,
    modelName: event.toolName,
    args: {},
    message: event.result.content
      .map((part) =>
        part.type === "text"
          ? part.text
          : "[image]",
      )
      .join("\n"),
  });
}
```

这里使用 `wasAudited()` 防止重复记录。

如果 Runtime 已经记录过审批或执行失败，pi 的事件观察器就不再重复写一条；如果是 pi 自己在执行前失败，观察器负责补上最小审计记录。

### 审计失败不能覆盖业务结果

假设工具已经成功创建工单：

```Plain Text
下游服务：创建成功
Runtime：拿到成功响应
Audit 写入：数据库暂时不可用
```

这时不能把最终结果改成工具失败。否则模型可能再次调用 `ticket.create`，造成重复工单。

正确做法是把两个结果分开：

```Plain Text
业务执行结果：成功
审计写入结果：失败，需要告警和补偿
```

生产环境中，Audit 最好写入独立的可靠队列，或者使用本地 Outbox 表，确保审计失败不会改变业务执行语义。

### 这一节的验收方式

我们要验证的不是“数据库里有几行记录”，而是记录和真实执行行为一致。

至少检查以下场景：

```Plain Text
参数错误
→ 有拒绝 Audit
→ 没有 handler 副作用

权限拒绝
→ 有 RBAC_DENIED
→ 有对应 Trace

高风险调用
→ 有 approval_requested
→ 没有提前执行

批准执行
→ 有 approved、executing、consumed 状态
→ 有成功 Audit

工具超时
→ 有 TOOL_TIMEOUT
→ 有失败 Trace
→ attempts 数量正确

MCP 调用
→ 工具来源是 mcp
→ tool_name 包含 my-coffee
→ 输入输出已脱敏
```

最后回到开场的 Coding Agent 演示。

它调用 `grep` 和 `read` 时，虽然使用的是 pi 自带的代码工具，但 Extension 仍然把工具结果写入 Trace。之后如果它调用 `order__get_status` 或 `mcp__my-coffee__...`，就会进入 Runtime 的完整 Audit 和 Trace 链。

这样我们不只知道 Agent 最终说了什么，还能知道它是怎样搜索、怎样判断、怎样调用工具，以及最终答案依赖了哪些证据。

下一节我们继续看 LoopGuard 和 TDD：怎样给整个 Agent Run 设置预算和终止条件，以及如何用测试证明这个 Loop 不会无限循环、不会无限重试，也不会在缺少真实凭据时伪造成功。

## 九、TDD 只测公开行为，真实模型与确定性治理分开（约 3\.5 分钟）

第八节我们已经把执行过程记录下来了。现在可以看到，Agent 的每一步都有 Trace，但“有记录”不等于“执行一定会停”。

如果模型不断重复调用同一个工具，或者每一轮都要求继续，系统可能一直运行下去。更麻烦的是，模型调用次数增加以后，Token、成本和下游请求也会一起增加。

所以第九节要在整个 Agent Run 外面加一层 LoopGuard，并用 TDD 验证它的终止条件。



先看预算配置：

```Plain Text
runtime:
  max_turns: 8
  max_tool_calls: 12
  max_repeated_call: 2
  max_total_tokens: 30000
  max_cost_usd: 0.25
  max_duration_ms: 120000
```

这些值不是模型参数，而是 Harness 的运行边界。

`max_turns` 限制模型最多进行多少轮对话；`max_tool_calls` 限制一次任务最多执行多少个工具；`max_repeated_call` 限制完全相同的工具和参数最多出现几次；`max_total_tokens` 和 `max_cost_usd` 控制模型预算；`max_duration_ms` 控制整次任务最长运行时间。

LoopGuard 不应该等到最后一轮才检查，而是要在工具调用前和每轮结束后都检查。

先看工具调用前的重复检测：

```Plain Text
beforeToolCall(
  toolName: string,
  args: Record<string, unknown>,
): GuardDecision {
  if (
    Date.now() - this.startedAt >=
    this.budget.maxDurationMs
  ) {
    return deny(
      "MAX_DURATION",
      "Agent Run 已超过总时限",
    );
  }

  if (
    this.toolCalls >=
    this.budget.maxToolCalls
  ) {
    return deny(
      "MAX_TOOL_CALLS",
      "工具调用预算已耗尽",
    );
  }

  const signature =
    `${toolName}:${canonicalJson(args)}`;

  const count =
    (this.repeatedCalls.get(signature) ?? 0) + 1;

  if (
    count >
    this.budget.maxRepeatedCall
  ) {
    return deny(
      "REPEATED_TOOL_CALL",
      "检测到相同工具与参数的重复调用",
    );
  }

  this.repeatedCalls.set(signature, count);
  this.toolCalls += 1;

  return {
    allow: true,
    code: "OK",
    reason: "Loop 工具预算通过",
  };
}
```

这里用 `canonicalJson(args)` 生成调用签名。

这样下面两个调用会被认为是相同调用：

```Plain Text
{
  "order_id": "ORD-A-1001",
  "include_history": true
}
```

```Plain Text
{
  "include_history": true,
  "order_id": "ORD-A-1001"
}
```

字段顺序不同，但业务参数相同，不能因为 JSON 排列变化就绕过重复调用检测。

这个检测要放在工具执行之前。如果放到 handler 执行以后，重复调用已经产生副作用，再拒绝就晚了。

接下来是每轮结束后的停止判断：

```Plain Text
shouldStop(
  pendingApprovalId?: string,
): StopDecision {
  if (pendingApprovalId) {
    return stop(
      "AWAITING_APPROVAL",
      "工具调用正在等待人工审批",
    );
  }

  if (
    this.turns >=
    this.budget.maxTurns
  ) {
    return stop(
      "MAX_TURNS",
      "Agent Loop 已达到最大轮数",
    );
  }

  if (
    this.toolCalls >=
    this.budget.maxToolCalls
  ) {
    return stop(
      "MAX_TOOL_CALLS",
      "工具调用预算已耗尽",
    );
  }

  if (
    this.totalTokens >=
    this.budget.maxTotalTokens
  ) {
    return stop(
      "MAX_TOKENS",
      "Token 预算已耗尽",
    );
  }

  if (
    this.costUsd >=
    this.budget.maxCostUsd
  ) {
    return stop(
      "MAX_COST",
      "Cost 预算已耗尽",
    );
  }

  if (
    Date.now() - this.startedAt >=
    this.budget.maxDurationMs
  ) {
    return stop(
      "MAX_DURATION",
      "Agent Run 已超过总时限",
    );
  }

  return {
    stop: false,
    code: "CONTINUE",
    reason: "预算允许继续",
  };
}
```

这里把待审批判断放在最前面，是因为等待审批不是普通预算耗尽。

如果工具需要人工确认，Loop 应该进入暂停状态，而不是继续执行下一轮。否则模型可能在等待审批期间继续提出其他写操作。

然后把 LoopGuard 接入 pi：

```Plain Text
beforeToolCall: async ({
  toolCall,
  args,
}) => {
  const decision =
    guard.beforeToolCall(
      toolCall.name,
      args,
    );

  if (!decision.allow) {
    return {
      block: true,
      reason: decision.reason,
    };
  }

  return undefined;
},

shouldStopAfterTurn: async () => {
  return guard.shouldStop(
    runtime.pendingApproval(traceId),
  ).stop;
},
```

这段代码体现了两个职责边界。

pi 负责在合适的生命周期节点调用 Hook；LoopGuard 负责决定是否允许继续。我们不修改 pi 的循环实现，而是使用它公开的 Hook 接缝加上项目自己的边界策略。

需要注意，工具预算、模型预算和总时长要分别记录。

例如：

```Plain Text
guard.observeAssistantUsage({
  totalTokens:
    event.message.usage.totalTokens,
  costUsd:
    event.message.usage.cost.total,
});
```

这里统计的是模型消耗。

工具调用则在 `beforeToolCall` 中统计。

如果只统计模型 Token，不统计工具次数，Agent 可能一次模型响应里并发调用大量工具；如果只统计工具次数，不统计模型成本，模型可能因为工具结果过大而反复消耗 Token。

下面进入 TDD。

这一节测试的不是某个私有方法有没有被调用，而是 Agent Run 是否遵守公开行为。

第一类测试是最大轮数：

```Plain Text

  maxTurns: 2,
  maxToolCalls: 12,
  maxRepeatedCall: 2,
  maxTotalTokens: 30000,
  maxCostUsd: 1,
  maxDurationMs: 120000,
});

guard.observeTurn();

expect(guard.shouldStop()).toMatchObject({
  stop: true,
  code: "MAX_TURNS",
});
```

第二类测试是重复调用：

```Plain Text

  "order__get_status",

const second = guard.beforeToolCall(
  "order__get_status",
  { order_id: "ORD-A-1001" },
);

const third = guard.beforeToolCall(
  "order__get_status",
  { order_id: "ORD-A-1001" },
);
```

如果配置 `max_repeated_call: 2`，前两次允许，第三次应该被拒绝：

```Plain Text
expect(third).toMatchObject({
  allow: false,
  code: "REPEATED_TOOL_CALL",
});
```

第三类测试是待审批停止：

```Plain Text
const decision =
  guard.shouldStop("approval-123");

expect(decision).toEqual({
  stop: true,
  code: "AWAITING_APPROVAL",
  reason: "工具调用正在等待人工审批",
});
```

这类测试很重要，因为它证明人工确认会改变 Loop 状态，而不是只生成一条日志。

第四类测试是模型成本预算：

```Plain Text
guard.observeAssistantUsage({
  totalTokens: 29000,
  costUsd: 0.24,
});

const next =
  guard.shouldStop();

expect(next.stop).toBe(false);

guard.observeAssistantUsage({
  totalTokens: 2000,
  costUsd: 0.02,
});

expect(
  guard.shouldStop().code,
).toBe("MAX_TOKENS");
```

测试要覆盖边界值。预算 30000 时，29999 和 30000 的行为应该明确，不能依赖某个浮点数比较的偶然结果。

真实 Agent Loop 测试则必须连接真实 DeepSeek：

```Plain Text
export DEEPSEEK_API_KEY="..."
export GATEWAY_API_KEY="..."

npm run test:live
```

测试任务可以是：

```Plain Text
查询订单 ORD-A-1001 的状态，
并说明实际调用了哪个工具。
```

断言至少包括：

```Plain Text

确实产生了 order.get_status 的 Audit
Agent Run 有 Trace
没有使用 Fake Provider
```

没有 `DEEPSEEK_API_KEY` 时，测试应该明确失败：

```Plain Text

```

不能用一个预先写好的模型回复替代真实测试。否则只能证明测试代码能运行，不能证明 Agent 会正确选择工具。

到这里，需要把三类参与者的职责再固定下来。

人负责定义：

```Plain Text

工具预算
Token 和 Cost 预算
重复调用规则
终止条件
人工审批条件
工具白名单
测试断言
```

模型负责：

```Plain Text

npm run cli -- approvals execute <id>
```

最后查看 Trace：

```Plain Text
npm run cli -- trace <trace-id>
```

验收时要看完整链路，而不是只看最后答案：

```Plain Text
模型请求是否经过 Gateway
工具是否来自当前快照
参数是否经过双层校验
权限是否在 handler 前判断
高风险工具是否暂停审批
超时是否真正及时返回
写操作是否避免自动重试
MCP 是否使用 my-coffee
敏感信息是否脱敏
Loop 是否在预算耗尽时停止
Trace 是否能还原全过程
```

如果这些问题都能够用代码、测试和 Trace 证据回答，才说明我们完成了阶段二。

到这里，阶段一提供了统一的模型调用入口，阶段二在这个入口上增加了工具发现、受控执行、人工介入、失败恢复和可观测性。后续进入 Planner、Memory、Workflow 或 Coding Agent 的复杂任务时，仍然复用这套 Loop 和 Harness 边界，而不是重新写一套无法审计的执行逻辑。

## 十、把演示里的调用链收回来（约 2 分钟）



第九节我们已经用 LoopGuard 和 TDD 把 Agent 的运行边界固定下来了：模型可以继续思考和调用工具，但不能无限循环、无限重试，也不能在缺少真实凭据时伪造成功。

现在进入第十节，做一次完整收束。我们把前面所有模块重新放回同一条执行链，并完成最终验收。



先看一次完整任务：

```Plain Text
用户：
查询 ORD-A-1001 的状态。
如果订单异常，搜索对应处理流程；
如果仍然找不到，再创建客服工单。
```

这个任务不是一次模型调用就能完成的。它至少可能经历以下过程：

```Plain Text
用户请求
→ Agent Loop
→ LiteLLM Gateway
→ DeepSeek
→ Tool Call: order.get_status
→ Tool Runtime
→ Schema 校验
→ 权限与租户校验
→ 订单服务
→ Tool Result
→ 下一轮模型调用
→ Tool Call: knowledge.search
→ Tool Runtime
→ 知识库结果
→ 下一轮模型调用
→ Tool Call: ticket.create
→ 人工审批
→ Tool Runtime 执行
→ 最终答案
```

每一层都有自己的职责，不能让一个模块承担所有工作。

Gateway 只负责模型调用，包括模型路由、Streaming、Prompt、Token、Cost、Latency 和模型级重试。

pi 负责 Agent Loop，包括消息上下文、Tool Call、Tool Result 和下一轮模型调用。

Registry 负责工具身份、工具命名、工具快照和模型可见工具列表。

Schema 负责参数结构。

Policy 负责白名单、RBAC、租户范围和运行模式。

Approval 负责高风险动作的人机确认。

Runtime 负责真正的工具执行、超时、重试、降级、Audit 和 Trace。

LoopGuard 负责整次任务的预算和停止条件。

MCP Adapter 负责把远端工具转换成内部工具，但不能绕过 Runtime。

所以最终主链可以概括成：

```Plain Text
模型提出动作
→ pi 接收动作
→ Registry 找到工具
→ Schema 验证参数
→ Policy 判断是否允许
→ Approval 判断是否需要人确认
→ Runtime 控制执行
→ Audit 和 Trace 留证
→ 结果回到模型
```

这条链最重要的不是模块数量，而是执行顺序不能乱。

如果先执行后鉴权，权限就失去意义。

如果先批准后重新校验，批准可能绑定到旧参数。

如果超时后直接重试写操作，可能产生重复副作用。

如果 MCP 工具绕过 Registry，远端工具就不会受到本地白名单和审计约束。

接下来做最终验收。

第一步，验证阶段一 Gateway。

```Plain Text
cd gateway

../.venv/bin/python -m pytest
```

然后检查服务接口：

```Plain Text
curl http://127.0.0.1:8000/health

curl \
  -H "Authorization: Bearer $GATEWAY_API_KEY" \
  http://127.0.0.1:8000/v1/models
```

这里重点看三件事：

第一，模型调用是否只使用平台别名 `agent-default`。

第二，供应商 Key 是否只存在于 Gateway 进程。

第三，模型失败时是否按照配置执行有限重试和降级。

第二步，验证工具 Registry 和参数校验：

```Plain Text
cd runtime

npm run cli -- tools --without-mcp

npm run cli -- invoke \
  order__get_status \
  '{"order_id":"bad"}'
```

非法订单号应该返回：

```Plain Text
INVALID_ARGUMENT
```

而且不能调用订单服务。

再测试跨租户访问：

```Plain Text
npm run cli -- invoke \
  order__get_status \
  '{"order_id":"ORD-B-1001"}'
```

如果当前上下文是 `tenant_a`，应该返回：

```Plain Text

```

这两个测试验证的是不同层次：

`INVALID_ARGUMENT` 说明结构校验生效。

`RESOURCE_SCOPE_DENIED` 说明参数合法以后，资源权限校验仍然生效。

第三步，验证人工审批：

```Plain Text
npm run cli -- invoke \
  ticket__create \
  '{"order_id":"ORD-A-1001","title":"支付状态异常"}'
```

第一次执行不应该直接创建工单，而是返回：

```Plain Text
{
  "ok": false,
  "action": "confirm",
  "code": "APPROVAL_REQUIRED",
  "approvalId": "..."
}
```

然后查看审批：

```Plain Text

```

批准：

```Plain Text

  --decision approve \
  --actor teacher
```

最后执行：

```Plain Text

```

这一步要检查：

```Plain Text
第一次调用没有副作用
参数变化会导致审批失效
批准记录只能消费一次
执行结果进入 Audit
Trace 中有 approval_requested 和 tool.completed
```

第四步，验证超时和重试。

项目中的测试会使用一个故意忽略 `AbortSignal` 的慢 handler：

```Plain Text
async handler() {
  await new Promise((resolve) =>
    setTimeout(resolve, 250),
  );

  return { status: "too-late" };
}
```

工具配置的超时时间只有 15 毫秒。正确结果应该是：

```Plain Text

```

并且 Runtime 在预算时间内返回，而不是等待 250 毫秒以后才结束。

接着验证读工具重试：

```Plain Text
第一次调用返回临时错误

→ attempts 为 2
```

再验证写工具：

```Plain Text
第一次调用返回临时错误
→ 不自动重试
→ attempts 为 1
```

这一组测试验证的是“错误分类”和“幂等策略”，不是简单验证代码有没有 `for` 循环。

第五步，验证正式 MCP：

这个测试只做正式服务器连接和工具发现，不主动创建订单。

```Plain Text

```

```Plain Text

Agent 是否真的调用了 order.get_status
```

```Plain Text
LIVE_TEST_CREDENTIAL_MISSING: DEEPSEEK_API_KEY
```

这不是测试不完整，而是系统拒绝伪造模型成功。

到这里，再总结一次人、模型和框架的分工。

人负责定义业务规则：

```Plain Text
哪些工具可以暴露
哪些角色可以调用
哪些资源属于哪个租户
哪些动作必须审批
哪些错误可以重试
哪些结果可以降级
Loop 什么时候必须停止
测试要证明哪些不变量
```

模型负责处理概率性的任务决策：

```Plain Text
理解用户目标
选择工具
生成参数
读取结果
判断是否需要下一步
组织最终答案
```

pi 负责通用的 Agent 运行机制：

```Plain Text
维护消息
调用模型
接收流式事件
分发 Tool Call
回填 Tool Result
触发生命周期 Hook
```

Runtime 和 Harness 负责确定性的安全边界：

```Plain Text
参数校验
权限判断
审批
超时
重试
降级
审计
Trace
预算
终止
```

这就是 Agent 开发中最需要程序员参与的地方。

大模型可以帮你生成工具代码，也可以帮你补测试、找调用链、解释失败原因。但工具契约、权限模型、风险等级、审批语义和终止条件，不能让模型临时决定。

最后回到开场的 Coding Agent 演示。

它搜索了 `runWithDeadline`，读取了 Runtime 实现，又读取了硬超时测试，最后解释出：

```Plain Text
Promise.race 保证本地及时返回；
AbortController 尝试取消下游；
retryable 决定是否允许重试；
idempotent 决定是否可以重复；
测试证明 handler 忽略 signal 时仍然会超时；
远端副作用未知时不能自动重放。
```

这就是本阶段真正想训练的能力：不是背出几百行 pi 源码，而是能沿着工具调用链定位问题，知道哪一层应该负责，知道怎样写测试证明，知道哪些地方必须由人做判断。

阶段二完成以后，我们已经有了一个可复用的 Agent Tool Runtime。后续进入 Loop 深化、任务规划、状态机、Memory、Multi\-Agent 或 Coding Agent Harness 时，都会继续复用这套基础设施。

Agent 的复杂度可以继续增加，但工具必须始终经过同一条可验证、可审计、可恢复的执行链。

## 本章小结

这一章我们把阶段一的统一模型调用能力，进一步升级成了真正可执行的 Agent 工具基础设施。通过 LiteLLM 统一接入 DeepSeek，再结合 pi 的 Provider、Tool 注册和事件机制，模型不再只是生成文本，而是可以提出工具调用请求；系统则负责把本地函数和 MCP 远程工具统一纳入 `ToolRegistry`，通过 `ToolSchema` 描述工具名称、参数、风险和权限，让模型看到的是标准化能力，而不是内部实现细节。

在执行层面，关键工作集中在“调用前”和“调用中”。调用前，使用 Pydantic 和 JSON Schema 做参数校验，再依次完成用户身份、租户范围、角色权限、工具白名单和风险等级检查；高风险操作还要绑定人工确认，并通过参数摘要生成不可篡改的确认指纹。调用中，所有请求都经过统一 Runtime，执行过程具备超时、有限重试、幂等键和明确的降级策略。无论是本地工具，还是指定的 `my-coffee` MCP Server，都不能绕过这条治理链路直接执行。

最后，我们为每次模型调用和工具调用建立了完整的 Audit 与 Trace。审计记录回答“谁在什么时间执行了什么动作”，Trace 则把一次任务中的模型请求、工具调用和最终结果串联起来，同时在写入日志前完成敏感信息脱敏。这样，系统既能完成任务，也能在出现错误、越权或性能问题时定位原因。学完这一章，你掌握的就不只是 Function Calling 的使用方法，而是一套可以接入真实业务、接受安全审查并持续运维的 Agent 执行底座。
