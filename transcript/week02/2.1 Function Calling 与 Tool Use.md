## 一、学习目标

完成本节后，学员应当能够：

1. 说明 Function Calling 从模型生成工具调用到结果回传的完整工作机制；

2. 为工具定义清晰的名称、描述、参数 Schema、返回 Schema、错误 Schema、权限等级和风险等级；

3. 使用 Pydantic 分别定义并校验工具的输入、输出和错误协议；

4. 解释模型怎样选择工具，并实现一次“模型决策—工具执行—结果回传—模型继续回答”的最小循环；

5. 在 Tool Runtime 中统一处理参数校验、权限、审计、超时、重试、失败恢复和 Trace；

6. 参考 pi 0\.83\.0 与 DeepSeek Harness，用 Python 实现最小的工具注册与插件化边界。

本节建议讲授 40 分钟。内容只围绕一条主线展开：

```Plain Text
模型提出 Tool Call
        ↓
Runtime 校验、授权并执行
        ↓
结构化 Tool Result 返回模型
        ↓
模型继续决策或生成答案
```

其中，模型擅长理解用户意图和生成候选参数；Agent 开发工程师要亲自完成的，是工具协议、执行边界、权限规则、失败策略和运行记录。

## 二、模型已经能回答问题，为什么还需要 Tool Use？

上一节完成 LLM Gateway 后，Agent 已经有了统一的模型调用入口。可是模型调用解决的是“生成什么”，不能直接解决“系统里发生什么”。

比如用户问：“帮我查一下昨天创建、还没有支付的订单。”模型可以解释应该怎样查询，但它不知道业务数据库里的实时订单，也不能只凭一句自然语言直接访问数据库。

如果用户进一步说：“把这笔订单取消掉”，问题就更明显了。模型不仅缺少实时数据，也不应该拥有数据库连接、用户身份和取消订单的真实权限。

所以先给出本节的核心结论：

> Function Calling 不是让模型获得执行权限，而是让模型用结构化方式提出“我想调用哪个工具、参数是什么”。真正的执行必须交给 Tool Runtime。
> 
> 

一条可靠的职责边界是：

|角色|负责什么|不能替谁决定什么|
|---|---|---|
|模型|理解请求、选择候选工具、生成候选参数、阅读工具结果|不能决定自己是否有权限，也不能直接执行 Python 函数|
|工具函数|完成一项确定的业务能力|不能相信调用参数天然正确，也不负责整个 Agent Loop|
|Tool Runtime|查找工具、校验、鉴权、超时、重试、审计和结果归一化|不能替业务方定义权限和风险规则|
|Agent Loop / Harness|保存消息和状态，把 Tool Result 送回模型，决定继续或结束|不应绕过 Runtime 直接调用业务函数|

pi 0\.83\.0 的源码也是按照这条边界组织的：模型侧的 Tool 只包含名称、描述和参数 Schema；进入 Agent 层后，AgentTool 才增加 execute\(\)；Agent Loop 在执行前校验参数、运行 beforeToolCall，执行后运行 afterToolCall，最后产生与 toolCallId 对应的 toolResult。

下面把分散在三个源码文件中的关键类型和函数合并成一段教学代码。为了让读者先看清主流程，这里省略异常与分支处理；文件注释标明了对应定义在 pi 0\.83\.0 中的位置。

```Plain Text
// packages/ai/src/types.ts
type Tool = {
        name: string;
        description: string;
        parameters: Record<string, unknown>;
};

type ToolCall = {
        id: string;
        name: string;
        arguments: unknown;
};

type ToolResultMessage = {
        role: "toolResult";
        toolCallId: string;
        toolName: string;
        content: string;
};

// packages/agent/src/types.ts
type AgentTool = Tool & {
        execute(
                toolCallId: string,
                args: Record<string, unknown>,
                onUpdate: (content: string) => void,
        ): Promise<string>;
};

type Hooks = {
        beforeToolCall?(call: ToolCall, args: object): Promise<void>;
        afterToolCall?(call: ToolCall, result: string): Promise<string>;
};

// packages/ai/src/utils/validation.ts
function validateToolArguments(call: ToolCall) {
        return call.arguments as Record<string, unknown>;
}

// packages/agent/src/agent-loop.ts
async function prepareToolCall(
        tools: AgentTool[],
        call: ToolCall,
        hooks: Hooks,
) {
        const tool = tools.find(item => item.name === call.name)!;
        const args = validateToolArguments(call);
        await hooks.beforeToolCall?.(call, args);
        return { tool, call, args };
}

async function executePreparedToolCall(
        prepared: Awaited<ReturnType<typeof prepareToolCall>>,
) {
        return prepared.tool.execute(
                prepared.call.id,
                prepared.args,
                content => console.log({
                        type: "tool_execution_update",
                        toolCallId: prepared.call.id,
                        content,
                }),
        );
}

async function finalizeToolCall(
        call: ToolCall,
        result: string,
        hooks: Hooks,
) {
        return await hooks.afterToolCall?.(call, result) ?? result;
}

function createToolResultMessage(
        call: ToolCall,
        content: string,
): ToolResultMessage {
        return {
                role: "toolResult",
                toolCallId: call.id,
                toolName: call.name,
                content,
        };
}

async function runToolCall(
        tools: AgentTool[],
        call: ToolCall,
        hooks: Hooks,
) {
        const prepared = await prepareToolCall(tools, call, hooks);
        const executed = await executePreparedToolCall(prepared);
        const finalized = await finalizeToolCall(call, executed, hooks);
        return createToolResultMessage(call, finalized);
}
```

接下来，我们先把这条链路拆开，看一次 Function Calling 到底发生了什么。

## 2\.1 Function Calling 工作机制

### 为什么模型返回了 Tool Call，程序还不能直接执行？

先看结论：模型返回的 Tool Call 只是一个候选动作，它与用户输入一样，都属于不可信数据。Runtime 至少要确认工具存在、参数合法、用户有权调用、当前风险可以接受，才能进入真实执行。

一次完整调用通常包含六步：

1. 应用把用户消息和当前可用的工具 Schema 一起发送给模型；

2. 模型决定直接回答，或者返回一个或多个 Tool Call；

3. 每个 Tool Call 携带调用 ID、工具名称和 JSON 参数；

4. Tool Runtime 校验工具、参数、权限和风险，再执行真实函数；

5. Runtime 把成功结果或结构化错误作为 Tool Result 写回消息历史；

6. 模型读取结果，继续调用工具、向用户追问，或者生成最终答案。

这条链路可以压缩成：

```Plain Text
User Message
    ↓
LLM：直接回答，或生成 Tool Call
    ↓
Tool Runtime：validate → authorize → execute → observe
    ↓
Tool Result：必须带回原来的 tool_call_id
    ↓
LLM：继续决策或完成回答
```

这里最容易被忽略的是 tool\_call\_id。模型一次可能提出多个调用，Runtime 必须把每份结果与原调用准确关联。只返回“订单查询成功”，却不保留调用 ID，模型和 Trace 都无法知道这是谁的结果。

### tool\_call\_id 到底解决了什么问题？

先给出结论：tool\_call\_id 是一次“模型提出的工具调用”的关联键。它把 Assistant Message 中的 Tool Call、Runtime 中的执行过程，以及随后写回的 Tool Result 串成同一条记录。

它不是订单 ID，也不是用户 ID，更不是整个 Agent 任务的 Trace ID。三类 ID 的职责要分开：

|ID|标识什么|生命周期|
|---|---|---|
|trace\_id|一次 Agent 任务或请求|贯穿多轮模型调用和多次工具执行|
|tool\_call\_id|模型在某一轮提出的一次具体工具调用|从 Tool Call 产生，到对应 Tool Result 写回|
|order\_id 等业务 ID|工具正在操作的真实业务对象|由业务系统定义，可能跨越很多 Agent 任务|

假设用户说：“查询 ord\_123 和 ord\_456 的状态。”模型可能在同一条 Assistant Message 中提出两个调用：

```Plain Text
{
  "role": "assistant",
  "tool_calls": [
    {
      "id": "call_A",
      "function": {
        "name": "get_order",
        "arguments": "{\"order_id\":\"ord_123\"}"
      }
    },
    {
      "id": "call_B",
      "function": {
        "name": "get_order",
        "arguments": "{\"order_id\":\"ord_456\"}"
      }
    }
  ]
}
```

两个调用的工具名称完全相同，区别只在参数和调用 ID。如果 Runtime 只记录工具名，就无法稳定区分两次执行。

而且并行执行时，完成顺序不一定等于生成顺序。ord\_456 可能先从数据库返回，ord\_123 反而超时。Runtime 可以先后得到下面两份结果：

```Plain Text
{
  "role": "tool",
  "tool_call_id": "call_B",
  "content": "{\"order_id\":\"ord_456\",\"status\":\"paid\"}"
}
```

```Plain Text
{
  "role": "tool",
  "tool_call_id": "call_A",
  "content": "{\"error\":{\"code\":\"TIMEOUT\"}}"
}
```

虽然结果顺序发生了变化，模型仍然可以通过 call\_B 知道 paid 属于 ord\_456，通过 call\_A 知道 ord\_123 查询超时。如果没有 tool\_call\_id，模型只能看到“一次成功、一次超时”，却无法判断哪笔订单成功、哪笔订单需要重试。

所以，tool\_call\_id 至少解决四个问题。

第一，解决消息协议的对应关系。Assistant Message 提出了哪些 Tool Call，后续就要为每个调用写回对应的 Tool Result。结果不能只依赖数组位置，也不能只依赖工具名称。

第二，解除生成顺序与完成顺序的耦合。只读工具可以并行执行，谁先完成就先产生执行事件；最终无论怎样排序，都能通过调用 ID 找回来源。

第三，区分成功和失败的恢复对象。同一批调用中，一个可能成功，一个可能参数错误，另一个可能超时。Agent Loop 必须知道应该修正或重试哪一个调用，不能把整批结果统一当成成功或失败。

第四，建立 Trace 的父子关系。日志可以使用 trace\_id 找到整个任务，再使用 tool\_call\_id 定位某次工具调用的参数摘要、权限判断、重试次数、耗时和最终结果。

Runtime 在并行执行时，应当让调用 ID 跟随调用对象进入每个异步任务，而不是等工具完成后再按返回顺序猜测：

tool\_batch\.py

```Plain Text
import asyncio


async def execute_bound(
    call: ToolCall,
    runtime: "ToolRuntime",
    ctx: "ExecutionContext",
) -> tuple[str, ToolResultMessage]:
    result = await runtime.execute(call, ctx)
    return call.id, result


async def execute_batch(
    calls: list[ToolCall],
    runtime: "ToolRuntime",
    ctx: "ExecutionContext",
) -> list[ToolResultMessage]:
    tasks = [
        asyncio.create_task(execute_bound(call, runtime, ctx))
        for call in calls
    ]

    results: list[ToolResultMessage] = []
    for task in asyncio.as_completed(tasks):
        call_id, result = await task
        assert result.tool_call_id == call_id
        results.append(result)

    return results
```

这段代码演示 Harness 怎样安全执行一批可以并行的 Tool Call。execute\_batch\(\) 为每个调用创建独立任务，execute\_bound\(\) 则把调用 ID 与 Runtime 返回结果绑定在同一个协程返回值中。

演示时重点看 asyncio\.as\_completed\(\) 和后面的 assert。as\_completed\(\) 故意按完成顺序取结果，证明 Runtime 不能依赖数组位置维持对应关系；assert result\.tool\_call\_id == call\_id 则把“结果必须属于原调用”写成可验证的不变量。

放回 Harness 后，这个机制允许执行事件按真实完成顺序流向 UI，同时仍可在持久化时按 Assistant Message 中的调用顺序整理 Tool Result。并发调度与消息协议因此解耦：谁先完成不重要，关联 ID 始终不能丢。

一个可靠的 Tool Runtime 至少要保证：

1. 每个 Tool Call 最终只产生一份权威 Tool Result；

2. 成功、参数错误、权限拒绝和执行异常都必须保留原 tool\_call\_id；

3. 同一批调用的结果可以乱序完成，但不能错配或遗漏；

4. tool\_execution\_start、进度更新、重试记录和最终结果使用同一个调用 ID。

还要注意，tool\_call\_id 主要用于协议关联，不应直接代替业务幂等键。模型重新决策后可能生成新的调用 ID，即使它仍然请求执行同一笔业务操作。涉及支付、发送或取消等副作用时，Runtime 还要根据业务对象、动作和参数生成或传递独立的幂等键，防止“新的 Tool Call 重复执行旧动作”。

前面展示的 pi 源码正是这样处理的：execute\(\) 接收 prepared\.toolCall\.id，执行进度继续携带该 ID，createToolResultMessage\(\) 最后把 finalized\.toolCall\.id 写入 toolCallId。调用从开始到结束始终使用同一个关联键。

先定义模型调用与工具结果在 Python 中的最小结构：

tool\_messages\.py

```Plain Text
from typing import Any, Literal

from pydantic import BaseModel, ConfigDict, Field


class ToolCall(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)

    id: str = Field(min_length=1)
    name: str = Field(min_length=1, max_length=100)
    arguments_json: str


class ToolResultMessage(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)

    role: Literal["tool"] = "tool"
    tool_call_id: str
    name: str
    content: str
    is_error: bool = False

    def to_model_message(self) -> dict[str, str]:
        return {
            "role": self.role,
            "tool_call_id": self.tool_call_id,
            "content": self.content,
        }
```

这段代码定义 Harness 内部的 Tool Call 与 Tool Result 消息协议。它不执行工具，而是把供应商返回的数据先收口成稳定的 Python 对象，让后续校验、执行、Trace 和消息回传都使用同一组字段。

演示时重点看三个设计。第一，arguments\_json 保留原始 JSON 字符串，说明“模型已经生成参数”不等于“参数已经可信”；只有 Runtime 调用具体工具的 input\_model 后，才能得到可执行对象。第二，ToolResultMessage 强制携带 tool\_call\_id，使成功、拒绝和异常都能与原调用关联。第三，to\_model\_message\(\) 是一个明确的协议投影：Harness 内部保留 name 和 is\_error 供 Trace、UI 与恢复逻辑使用，发送给 OpenAI Compatible API 时只输出对方真正接受的字段。

这段代码值得展示，是因为成熟 Harness 通常不会让 Provider SDK 对象直接穿透整个 Agent Loop。内部消息协议与供应商协议分离以后，切换 Chat Completions、Responses API 或其他模型时，只需要修改适配层；Tool Runtime 和 Loop 仍然消费同一个 ToolCall 与 ToolResultMessage。

还要注意，Tool Result 不等于最终答案。它只是新的 observation。模型读完以后，才决定下一步做什么。这就是后续 Agent Loop 的基本循环：

```Plain Text
模型决策 → 工具执行 → 获得观察 → 模型再次决策
```

理解完调用过程，为什么还要专门学习工具定义？因为模型不会读取 Python 函数的真实用途，它选择工具时主要依赖名称、描述和参数 Schema。如果定义含糊，即使 Runtime 完全没有 Bug，模型仍可能选错工具、漏填参数，或者把只读请求交给写操作工具。

这项工作也不能直接交给模型。模型可以帮助生成一份 Schema 草稿，却不知道公司的真实业务边界：哪些字段来自用户，哪些字段必须从登录态注入；查询和修改是否应该拆开；什么动作需要审批；哪些错误允许重试。只有工程师结合业务系统、权限模型和失败成本，才能把一个普通函数定义成可交给 Agent 使用的工具。

所以，学习工具定义不是为了记住一段 JSON 格式，而是为了掌握一项 Agent 开发的核心能力：把业务能力翻译成模型能正确选择、Runtime 能安全执行的协议。明确这一点以后，下一个问题才是：模型看到的“工具”到底应该怎样定义？

### 本小节结论

Function Calling 只负责把模型的动作意图变成结构化 Tool Call；Tool Runtime 才负责把候选动作变成受控执行；Agent Loop 再把 Tool Result 变成下一轮上下文。三者不能合并成一次普通函数调用。

## 2\.2 工具定义：名称、描述、Schema、权限与风险

### 为什么不能把一个普通 Python 函数直接暴露给模型？

普通函数签名只告诉 Python 怎样传参，却没有完整回答模型和 Runtime 需要的问题：模型什么时候应该调用它？什么时候不应该调用？返回什么？失败怎样表达？谁可以调用？它会不会产生副作用？

所以，Agent 中的工具不是一个裸函数，而是一份“模型可理解、Runtime 可执行、平台可治理”的业务协议。

每个工具至少要有以下信息：

|字段|解决的问题|示例|
|---|---|---|
|name|稳定、唯一地标识工具|search\_orders|
|description|告诉模型何时使用、边界是什么|“查询当前用户的订单，不修改订单”|
|input\_model|调用需要哪些参数|状态、开始日期、数量上限|
|output\_model|成功后返回什么事实|订单列表、总数|
|error\_model|失败后怎样分类和恢复|参数错误、拒绝、超时、上游失败|
|permission|调用者需要什么权限|order:read|
|risk|调用前需要怎样的控制|low、medium、high|
|timeout\_seconds|最多等待多久|5 秒|
|max\_retries|临时失败最多重试几次|2 次|
|idempotent|重复执行是否会产生额外副作用|查询为 True，取消订单通常为 False|

下面用 Python 定义统一的工具元数据。它参考 pi 中“Tool 元数据与 AgentTool 执行函数分离”的思路，同时增加课程当前需要的输出、错误、权限和风险字段。

tool\_definition\.py

```Plain Text
from collections.abc import Awaitable, Callable
from dataclasses import dataclass
from typing import Literal

from pydantic import BaseModel


Permission = Literal["order:read", "order:write"]
RiskLevel = Literal["low", "medium", "high"]
ToolHandler = Callable[
    [BaseModel, "ExecutionContext"],
    Awaitable[BaseModel],
]


@dataclass(frozen=True)
class ToolDefinition:
    name: str
    description: str
    input_model: type[BaseModel]
    output_model: type[BaseModel]
    error_model: type[BaseModel]
    permission: Permission
    risk: RiskLevel
    timeout_seconds: float
    max_retries: int
    idempotent: bool
    handler: ToolHandler

    def to_model_tool(self) -> dict:
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.input_model.model_json_schema(),
            },
        }
```

这段代码定义平台内部完整的 ToolDefinition。它把一项工具拆成三组信息：模型选择需要的名称、描述和输入 Schema；Runtime 治理需要的输出类型、错误类型、权限、风险、超时、重试和幂等性；真正完成业务操作的 handler。to\_model\_tool\(\) 的作用，是从这份完整定义中投影出模型 API 所需的公开部分。

演示时重点关注四个位置。

第一，input\_model 同时服务两条路径：调用模型前，model\_json\_schema\(\) 生成参数 Schema；模型返回后，Runtime 使用同一个 Pydantic Model 校验参数。这样可以避免“模型看到一份 Schema，服务端执行另一套规则”的协议漂移。

第二，output\_model 和 error\_model 没有进入 to\_model\_tool\(\)。模型选择工具时不需要获得平台全部治理信息，但 Runtime 必须用它们校验成功结果、归一化失败，并决定下一轮是重试、追问还是停止。

第三，permission、risk、timeout\_seconds、max\_retries 和 idempotent 都是 Harness 的执行策略，不是模型可以声明或修改的参数。否则模型只要生成 permission="admin" 或 idempotent=true，就可能绕过真实安全边界。

第四，handler 与 to\_model\_tool\(\) 明确分离。模型只得到可序列化的 JSON Schema，真实函数只保存在 Tool Registry 中。收到 Tool Call 后，Runtime 必须重新按名称找到同一份 ToolDefinition，校验 input\_model，检查权限和风险，最后才能调用 handler。

因此，这段代码不是为了演示如何拼一段 tools JSON，而是在建立 Harness 的工具单一事实源：

```Plain Text
注册阶段：ToolDefinition 进入 Tool Registry
模型阶段：to_model_tool() 只投影模型可见协议
执行阶段：Runtime 找回完整定义并执行治理链
Loop 阶段：只接收校验后的 Output 或结构化 Error
```

这套机制值得学习，因为它同时解决了工具发现、协议一致性、权限隔离和插件注册问题。后面新增工具插件时，只需要贡献新的 ToolDefinition；模型调用、Runtime 治理和 Agent Loop 不需要为每个工具重新写一套分支。

工具名称和描述需要工程师亲自设计，不能让模型随意生成。一个可用的描述至少要回答三件事：

```Plain Text
它做什么？
什么时候应该使用？
它不会做什么？
```

例如：

```Plain Text
名称：search_orders
描述：按当前用户、订单状态和创建日期查询订单；只读取订单，不能取消、退款或修改订单。
```

而下面这种描述几乎没有选择价值：

```Plain Text
名称：query_data
描述：查询数据。
```

模型不知道查询哪类数据，也不知道它与其他查询工具的区别。工具选择不稳定时，第一检查项通常不是继续增加 Prompt，而是检查名称、描述和工具粒度。

权限等级与风险等级也不能混为一谈。permission 回答“调用者有没有资格”；risk 回答“即使有资格，这次调用是否仍需确认或审批”。一个用户可能拥有 order:write，但批量取消订单仍然是高风险动作。

### 本小节结论

工具定义不是函数注释，而是跨越模型、Runtime 和业务系统的执行协议。工程师必须确定工具粒度、用途边界、数据结构、权限、风险和失败策略；模型只能在这份协议内提出调用。

有了工具的整体定义，为什么还要继续学习 Input、Output 和 Error Schema？因为上一节定义的元数据只是说明“这个工具应该有什么”，还没有形成 Runtime 可以强制执行的验收规则。没有可执行 Schema，参数错了只能等业务函数报错，返回值变了只能等 Agent 解析失败，工具失败后也不知道应该重试、追问还是停止。

这部分同样需要工程师决定。模型可以生成字段，却不能替业务系统确定必填条件、跨字段关系、稳定返回值和错误恢复语义。所以下一步不是继续增加工具描述，而是把输入、输出和错误写成真正可以校验的类型。

## 2\.3 Input Schema、Output Schema 与 Error Schema

### 为什么只校验输入还不够？

输入校验只能阻止模型把错误参数送进业务函数，却不能保证业务函数返回了可用结果，也不能告诉 Agent 失败后应该怎样继续。

因此要把工具边界拆成三份 Schema：

|Schema|保护哪一侧|核心问题|
|---|---|---|
|Input Schema|模型到 Runtime|参数是否完整、类型是否正确、范围是否合理|
|Output Schema|业务系统到 Agent|成功结果是否稳定、后续 Loop 能否直接消费|
|Error Schema|失败到恢复逻辑|失败属于哪一类、能否重试、下一步是什么|

我们继续使用订单查询工具：

order\_schemas\.py

```Plain Text
from datetime import date
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, model_validator


class StrictModel(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)


class SearchOrdersInput(StrictModel):
    status: Literal["pending", "paid", "shipped", "cancelled"] | None = None
    created_from: date | None = None
    limit: int = Field(default=10, ge=1, le=50)

    @model_validator(mode="after")
    def require_filter(self) -> "SearchOrdersInput":
        if self.status is None and self.created_from is None:
            raise ValueError("status 与 created_from 至少提供一个")
        return self


class OrderSummary(StrictModel):
    order_id: str
    status: Literal["pending", "paid", "shipped", "cancelled"]
    created_at: str
    amount_cents: int = Field(ge=0)


class SearchOrdersOutput(StrictModel):
    orders: list[OrderSummary]
    total: int = Field(ge=0)


class ToolError(StrictModel):
    code: Literal[
        "INVALID_ARGUMENT",
        "TOOL_NOT_FOUND",
        "PERMISSION_DENIED",
        "APPROVAL_REQUIRED",
        "TIMEOUT",
        "UPSTREAM_ERROR",
        "INVALID_OUTPUT",
    ]
    message: str
    retryable: bool = False
```

这段代码一次定义了工具边界上的三份可执行协议。SearchOrdersInput 验收模型参数，SearchOrdersOutput 验收业务函数返回值，ToolError 统一表达失败。三者都继承 StrictModel，从默认行为上拒绝额外字段和隐式类型转换。

演示 Input Schema 时重点看三层约束。Literal 把订单状态限制在业务允许的枚举内；Field 把查询数量控制在 1—50；model\_validator 表达“至少提供一个过滤条件”的跨字段规则。这里最值得学的不是 Pydantic 语法，而是 Harness 在进入工具函数前拥有一扇确定的校验门。模型可以生成候选参数，却不知道业务系统是否允许无条件扫全表，这条规则必须由工程师写。

演示 Output Schema 时重点看它返回的是订单 ID、状态、时间和金额，而不是“查询成功，共找到三笔订单”的自然语言。Agent Loop 后续可能需要判断候选数量、继续查询详情或请求用户选择；结构化事实可以被程序和模型同时消费，也可以在进入下一轮前再次校验。

演示 Error Schema 时重点看 code 与 retryable 的分工。code 告诉 Harness 失败属于参数、权限、审批、超时还是实现问题；retryable 提供恢复建议，但 Runtime 还要结合幂等性和预算作最终决定。例如：

- INVALID\_ARGUMENT：模型可以修正参数后再次调用；

- PERMISSION\_DENIED：不能重试同一调用，应停止或提示用户切换身份；

- APPROVAL\_REQUIRED：需要进入人工确认流程；

- TIMEOUT、UPSTREAM\_ERROR：只有满足幂等条件时，Runtime 才可以有限重试；

- INVALID\_OUTPUT：说明工具实现违反了自己的返回协议，应记录工程故障，而不是让模型猜测缺失字段。

retryable 只是错误携带的建议，最终是否重试仍由 Runtime 结合工具的 idempotent、当前尝试次数和总预算决定。模型不能通过返回或修改 retryable=true 获得重试权。

把这段代码放回 Loop，可以看到三份 Schema 分别卡在不同位置：Input 位于 Tool Call 与 handler 之间；Output 位于 handler 与 Tool Result 之间；Error 位于失败与下一轮决策之间。它们不是三个孤立的数据类，而是 Harness 控制流的三个关口。

现在把 Schema 与真实工具函数装配起来：

search\_orders\_tool\.py

```Plain Text
async def search_orders(
    args: SearchOrdersInput,
    ctx: "ExecutionContext",
) -> SearchOrdersOutput:
    rows = await ctx.order_service.search(
        user_id=ctx.user_id,
        status=args.status,
        created_from=args.created_from,
        limit=args.limit,
    )

    return SearchOrdersOutput(
        orders=[OrderSummary.model_validate(row) for row in rows],
        total=len(rows),
    )


SEARCH_ORDERS = ToolDefinition(
    name="search_orders",
    description=(
        "按当前用户、订单状态和创建日期查询订单。"
        "只读取订单；不能取消、退款或修改订单。"
    ),
    input_model=SearchOrdersInput,
    output_model=SearchOrdersOutput,
    error_model=ToolError,
    permission="order:read",
    risk="low",
    timeout_seconds=5,
    max_retries=2,
    idempotent=True,
    handler=search_orders,
)
```

这段代码完成两件事：search\_orders\(\) 实现真实业务查询；SEARCH\_ORDERS 再把 handler 与前面定义的 Schema、权限和执行策略装配成一个可注册工具。单独存在的异步函数还不是 Agent Tool，只有进入 ToolDefinition 后，Harness 才知道怎样向模型公开、怎样校验以及怎样治理它。

演示 handler 时重点看参数来源被分成两类。status、created\_from 和 limit 来自已经通过 Input Schema 的 args；user\_id 来自可信的 ExecutionContext，而不是让模型填写。身份、租户、Trace ID 和审批凭证都属于 Runtime 上下文，不能混入模型可控参数。

演示装配对象时重点看 input\_model、output\_model 与 handler 的闭环。Runtime 用 input\_model 验收调用，用 handler 获得真实结果，再用 output\_model 验收返回值；permission、risk、超时、重试和幂等性则决定 handler 能否执行以及失败后怎样处理。

放回 Harness 后，Tool Registry 保存的是 SEARCH\_ORDERS，而不是只保存 search\_orders 函数。Agent Loop 不需要理解订单业务，只需要把 Tool Call 交给 Runtime，再接收标准 Tool Result。这也是输入 Schema 设计中的关键原则：

> 模型只填写完成任务所需的业务参数；身份和权限由 Runtime 从可信上下文注入。
> 
> 

### 本小节结论

Input Schema 拦截错误调用，Output Schema 固定成功事实，Error Schema 驱动失败恢复。三者共同构成工具协议；缺少任何一份，Agent Loop 都会被迫解析自然语言或猜测下一步。

协议准备好以后，为什么还要学习工具选择？因为 Schema 只能约束“选中以后参数怎样写”，不能保证模型一定选对工具。工具选错了，问题可能来自名称与描述重叠、暴露的工具过多、上下文缺少关键信息，也可能是模型本身没有识别出调用条件。

Agent 开发工程师必须能区分这些原因，否则每次选错工具都只能继续修改 Prompt。接下来要观察模型到底看到了什么、依据什么选择，以及工程师怎样控制当前可见的工具集合。

## 2\.4 工具选择：模型怎样选择工具并生成参数？

### 模型是怎样知道该调用 search\_orders，而不是直接回答？

模型没有读取 Python 源码。它只看到当前消息，以及 Runtime 暴露的工具名称、描述和参数 Schema。模型根据这些信息生成三类结果之一：

1. 不需要外部能力，直接返回文本；

2. 信息不足，先向用户追问；

3. 需要外部能力，返回一个或多个 Tool Call。

因此，工具选择质量主要受四个因素影响：

|因素|工程师需要控制什么|
|---|---|
|工具集合|当前请求真正允许模型看到哪些工具|
|名称与描述|每个工具的用途、适用条件和禁止边界|
|参数 Schema|字段含义、枚举、必填项和范围|
|上下文|用户目标、已获得的 Tool Result 和当前状态|

不要把所有平台工具都暴露给每一轮模型。权限过滤得越晚，模型越可能选择一个最后必然被拒绝的工具。更好的做法是：Runtime 先根据用户、租户、Agent 角色和当前模式筛出可见工具，再把这份最小集合传给模型；真正执行前仍要再次鉴权。

下面使用 DeepSeek V4 Flash 和 OpenAI Compatible Chat Completions 演示一次工具选择。为了让代码集中在 Function Calling，本例关闭 thinking mode。

model\_select\.py

```Plain Text
import os

from openai import OpenAI


client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
)

        "role": "system",
        "content": (
            "你是订单助手。需要实时订单数据时调用工具；"
            "不要编造订单，修改订单前必须先获得明确目标。"
```

这段代码只演示 Function Calling 的“模型决策半程”：组装消息和工具 Schema，调用 DeepSeek V4 Flash，然后读取模型返回的 Tool Call。它没有执行 search\_orders\(\)，目的是把“模型提出动作”与“Runtime 执行动作”清楚分开。

演示时重点看四处。tools=\[SEARCH\_ORDERS\.to\_model\_tool\(\)\] 证明发送给模型的是公开 Schema，而不是 Python 函数；tool\_choice="auto" 允许模型根据任务选择直接回答或调用工具；assistant\.tool\_calls 可能为空、一个或多个，所以 Harness 不能假设每轮必定执行工具；call\.function\.arguments 仍然是模型生成的 JSON 字符串，打印出来只能用于观察，不能直接展开调用 handler。

这段代码在 Harness 中通常位于 LLM Adapter 或 Agent Loop 的模型请求阶段。它的输出不是最终答案，而是下一步控制流的输入：没有 Tool Call，Loop 可以结束；存在 Tool Call，Loop 必须转交 Tool Runtime 校验和执行。extra\_body 属于 DeepSeek Provider 差异，真实项目应由上一节的 LLM Gateway 统一处理，而不是复制进每个 Agent。

即使模型生成：

```Plain Text
{
  "status": "pending",
  "created_from": "2026-08-16",
  "limit": 10
}
```

程序也不能直接执行 search\_orders\(\*\*arguments\)。下一步必须交给 Runtime 做 Pydantic 校验和权限检查。

把模型决策、工具结果和下一次模型调用串起来，可以得到最小 Tool Loop：

minimal\_tool\_loop\.py

```Plain Text
MAX_STEPS = 4


async def run_order_agent(
    user_text: str,
    runtime: "ToolRuntime",
    ctx: "ExecutionContext",
) -> str:
    messages = [
        {"role": "system", "content": "你是订单助手，不得编造订单。"},
        {"role": "user", "content": user_text},
    ]

    for _ in range(MAX_STEPS):
        visible_tools = runtime.model_tools(ctx)
        response = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=messages,
            tools=visible_tools,
            tool_choice="auto",
            extra_body={"thinking": {"type": "disabled"}},
        )

        assistant = response.choices[0].message
        messages.append(assistant.model_dump(exclude_none=True))
        tool_calls = assistant.tool_calls or []

        if not tool_calls:
            return assistant.content or ""

        for raw_call in tool_calls:
            call = ToolCall(
                id=raw_call.id,
                name=raw_call.function.name,
                arguments_json=raw_call.function.arguments,
            )
            result = await runtime.execute(call, ctx)
            messages.append(result.to_model_message())

    raise RuntimeError("agent exceeded maximum steps")
```

这段代码第一次把模型调用和 Tool Runtime 组成最小 Agent Loop。它接收用户目标，持续执行“请求模型—检查 Tool Call—执行工具—写回结果”，直到模型不再调用工具并返回最终文本。

演示时建议按控制流看五个位置。

第一，runtime\.model\_tools\(ctx\) 在每一轮重新计算可见工具，而不是启动时固定一次。这样权限、模式或动态插件变化可以在下一轮生效。

第二，Assistant Message 必须先完整加入 messages，随后才能追加对应 Tool Result。模型下一轮既要看到“自己提出了什么调用”，也要看到“每个调用返回了什么”。只写 Tool Result 会破坏消息配对。

第三，assistant\.tool\_calls or \[\] 是 Loop 的分支条件：为空表示本轮没有待执行动作，可以结束；非空表示必须把每个候选调用转成内部 ToolCall，交给 Runtime，而不是在 Loop 中直接分派业务函数。

第四，result\.to\_model\_message\(\) 只负责把 Runtime 的权威结果投影回模型协议。权限拒绝、参数错误和工具异常也走这条路径，因此模型能获得新的 observation，Loop 不会因为一次工具失败就失去消息结构。

第五，MAX\_STEPS 是 Harness 强制执行的终止预算。模型可能每轮调用都合法，却始终不结束；Loop 不能把是否停止完全交给模型。真实 Harness 还会限制总耗时、工具次数和成本，本节先保留最小边界。

这段代码值得展示，是因为它划清了 Loop 与 Runtime：Loop 维护消息、轮次和终止条件；Runtime 维护工具查找、校验、权限和执行。业务工具增加以后，Loop 的主体不应出现新的 if tool\_name == \.\.\.。

如果 DeepSeek thinking mode 开启，包含 Tool Call 的中间 assistant 消息还需要按照官方协议完整回传 reasoning\_content。这属于 Provider 消息适配责任，应由上一节的 Gateway 或模型适配层统一处理，不应散落在每个工具里。

### 本小节结论

模型根据“当前上下文 \+ 当前可见工具 Schema”选择候选工具并生成参数。工具描述影响选择，Schema 影响参数，但两者都不能替代 Runtime 校验和授权。Tool Call 是提议，不是执行许可。

现在最小循环已经能跑起来，为什么还要专门学习工具治理？因为“模型选对了工具”只说明决策看起来合理，不代表这次调用有权限、参数安全、执行不会超时，也不代表失败后可以放心重试。只要工具连接数据库、文件系统或外部 API，Tool Call 就从内容生成跨入了真实副作用边界。

模型不能给自己授权，也不能根据一句“请求超时”判断写操作是否已经生效。这些规则必须由 Runtime 强制执行。因此下一步要解决的不是让模型更聪明，而是让每一次执行都可控、可恢复、可追踪。

---

## 2\.5 工具治理：校验、权限、审计、超时、重试、恢复与 Trace

### 为什么“工具成功调用一次”不等于 Tool Runtime 已经完成？

因为生产环境中的失败不只来自模型。参数可能不合法；用户可能没有权限；高风险动作可能缺少确认；数据库可能超时；上游服务可能短暂不可用；工具函数也可能返回不符合 Output Schema 的数据。

这一节先给出统一执行顺序：

```Plain Text
查找工具
  → Input Schema 校验
  → 权限与风险检查
  → 记录调用开始
  → 在超时边界内执行
  → Output Schema 校验
  → 记录成功或结构化错误
  → 返回 Tool Result
```

这个顺序不是装饰。权限检查必须发生在业务函数之前；Output Schema 校验必须发生在结果进入 Agent Loop 之前；审计要覆盖成功、拒绝和失败，而不只是成功调用。

### 2\.5\.1 怎样定义可信的执行上下文？

execution\_context\.py

```Plain Text
from dataclasses import dataclass, field


@dataclass(frozen=True)
class ExecutionContext:
    user_id: str
    tenant_id: str
    permissions: frozenset[str]
    approved_call_ids: frozenset[str] = field(default_factory=frozenset)
    trace_id: str = ""
    order_service: object | None = None
```

这段代码定义一次工具执行使用的可信上下文。它不属于模型消息，也不从 Tool Call 参数中解析，而是由 Harness 根据登录态、租户、审批状态和当前 Trace 在执行前创建，再传给 Runtime 与 handler。

演示时重点看 frozen=True 和字段来源。冻结对象可以避免某个工具在执行过程中修改用户身份或权限，影响同一批中的其他调用；user\_id、tenant\_id 和 permissions 来自登录态或服务间身份，不允许模型填写；order\_service 是 Harness 注入的业务依赖，工具不需要自己读取全局连接或密钥。

approved\_call\_ids 体现了 Human\-in\-the\-loop 与 Tool Runtime 的连接点。为什么要绑定调用 ID？因为用户确认“取消 ord\_123”之后，模型不能把参数改成“取消 ord\_456”并复用同一次确认。确认必须绑定具体动作和参数，课程代码用调用 ID 表达最小边界，生产系统还应同时保存工具名与参数摘要。

放回 Agent Loop 后，模型只负责产生候选 Tool Call；Loop 在需要确认时暂停；用户批准后，Harness 更新可信上下文并恢复执行。批准信息不会被拼进模型可自由改写的业务参数中。

### 2\.5\.2 怎样把失败统一成 Tool Result？

tool\_result\.py

```Plain Text
import json


def success_message(
    call: ToolCall,
    output: BaseModel,
) -> ToolResultMessage:
    return ToolResultMessage(
        tool_call_id=call.id,
        name=call.name,
        content=output.model_dump_json(),
        is_error=False,
    )


def error_message(
    call: ToolCall,
    error: ToolError,
) -> ToolResultMessage:
    return ToolResultMessage(
        tool_call_id=call.id,
        name=call.name,
        content=json.dumps(
            {"error": error.model_dump()},
            ensure_ascii=False,
        ),
        is_error=True,
    )
```

这段代码把 Runtime 内部的 Pydantic 结果转换成统一的 Tool Result 消息。success\_message\(\) 序列化通过 Output Schema 的对象；error\_message\(\) 把 ToolError 包装在固定的 error 字段下；两条路径都保留原始 tool\_call\_id 和工具名称。

演示时重点关注“成功与失败使用同一种消息外壳”。如果失败只抛 Python 异常，Agent Loop 会在消息历史中留下一个没有对应结果的 Tool Call；现在无论成功、超时还是权限拒绝，Loop 都能得到一份可持久化、可回传的 observation。is\_error 留给 Harness 判断状态，content 则按照模型协议序列化为字符串。

这里还体现了内部诊断与模型可见错误的分离。模型不需要阅读 Python 堆栈，也不能看到数据库连接串、Token 或内部文件路径。Runtime 只返回足够指导下一步的错误码和安全说明，详细异常、重试记录和参数摘要保留在内部 Trace 中。

### 2\.5\.3 怎样实现统一执行链路？

tool\_runtime\.py

```Plain Text
import asyncio
import json
from collections.abc import Awaitable, Callable
from time import perf_counter

from pydantic import ValidationError


TraceWriter = Callable[[dict], Awaitable[None]]


class TransientToolError(Exception):
    """上游临时故障，只有幂等工具才允许重试。"""


class ToolRuntime:
    def __init__(self, trace_writer: TraceWriter):
        self._tools: dict[str, ToolDefinition] = {}
        self._trace_writer = trace_writer

    def register(self, tool: ToolDefinition) -> Callable[[], None]:
        if tool.name in self._tools:
            raise ValueError(f"duplicate tool: {tool.name}")
        self._tools[tool.name] = tool

        def dispose() -> None:
            self._tools.pop(tool.name, None)

        return dispose

    def model_tools(self, ctx: ExecutionContext) -> list[dict]:
        return [
            tool.to_model_tool()
            for tool in self._tools.values()
            if tool.permission in ctx.permissions
        ]

    async def execute(
        self,
        call: ToolCall,
        ctx: ExecutionContext,
    ) -> ToolResultMessage:
        started = perf_counter()
        tool = self._tools.get(call.name)

        if tool is None:
            return await self._finish_error(
                call,
                ctx,
                started,
                ToolError(
                    code="TOOL_NOT_FOUND",
                    message="工具不存在或当前不可用",
                ),
            )

        try:
            args = tool.input_model.model_validate_json(
                call.arguments_json
            )
        except ValidationError as exc:
            issues = [
                {
                    "path": ".".join(str(part) for part in item["loc"]),
                    "message": item["msg"],
                }
                for item in exc.errors(
                    include_url=False,
                    include_input=False,
                )
            ]
            return await self._finish_error(
                call,
                ctx,
                started,
                ToolError(
                    code="INVALID_ARGUMENT",
                    message=json.dumps(issues, ensure_ascii=False),
                ),
            )

        if tool.permission not in ctx.permissions:
            return await self._finish_error(
                call,
                ctx,
                started,
                ToolError(
                    code="PERMISSION_DENIED",
                    message="当前身份没有调用该工具的权限",
                ),
            )

        if tool.risk == "high" and call.id not in ctx.approved_call_ids:
            return await self._finish_error(
                call,
                ctx,
                started,
                ToolError(
                    code="APPROVAL_REQUIRED",
                    message="该调用需要用户确认",
                ),
            )

        for attempt in range(1, tool.max_retries + 2):
            try:
                async with asyncio.timeout(tool.timeout_seconds):
                    raw_output = await tool.handler(args, ctx)

                output = tool.output_model.model_validate(raw_output)
                await self._write_trace(
                    call=call,
                    ctx=ctx,
                    started=started,
                    status="success",
                    attempt=attempt,
                )
                return success_message(call, output)

            except TimeoutError:
                error = ToolError(
                    code="TIMEOUT",
                    message="工具执行超时",
                    retryable=tool.idempotent,
                )
            except TransientToolError:
                error = ToolError(
                    code="UPSTREAM_ERROR",
                    message="上游服务暂时不可用",
                    retryable=tool.idempotent,
                )
            except ValidationError:
                error = ToolError(
                    code="INVALID_OUTPUT",
                    message="工具返回结果不符合 Output Schema",
                )
            except Exception:
                error = ToolError(
                    code="UPSTREAM_ERROR",
                    message="工具执行失败",
                )

            can_retry = (
                error.retryable
                and tool.idempotent
                and attempt <= tool.max_retries
            )
            if not can_retry:
                return await self._finish_error(
                    call,
                    ctx,
                    started,
                    error,
                    attempt=attempt,
                )

            await asyncio.sleep(min(0.25 * 2 ** (attempt - 1), 2.0))

        raise AssertionError("unreachable")

    async def _finish_error(
        self,
        call: ToolCall,
        ctx: ExecutionContext,
        started: float,
        error: ToolError,
        attempt: int = 0,
    ) -> ToolResultMessage:
        await self._write_trace(
            call=call,
            ctx=ctx,
            started=started,
            status="error",
            attempt=attempt,
            error_code=error.code,
        )
        return error_message(call, error)

    async def _write_trace(
        self,
        *,
        call: ToolCall,
        ctx: ExecutionContext,
        started: float,
        status: str,
        attempt: int,
        error_code: str | None = None,
    ) -> None:
        await self._trace_writer({
            "trace_id": ctx.trace_id,
            "tool_call_id": call.id,
            "tool_name": call.name,
            "user_id": ctx.user_id,
            "tenant_id": ctx.tenant_id,
            "status": status,
            "attempt": attempt,
            "latency_ms": int((perf_counter() - started) * 1000),
            "error_code": error_code,
        })
```

这段代码是本节 Python 实现的执行核心：它把 Tool Registry、模型可见工具投影和单次工具执行流水线收口到一个 Runtime。Agent Loop 只调用 model\_tools\(\) 和 execute\(\)，不需要知道某个工具怎样校验、需要什么权限或如何重试。

演示时不要逐行朗读，重点沿着一次 Tool Call 的生命周期看七个机制。

第一，register\(\) 拒绝重名工具，并返回 dispose\(\)。返回卸载函数看似简单，却是后面插件热卸载和测试隔离的基础。

第二，model\_tools\(\) 先根据权限缩小模型可见工具集合。不过执行时仍然再次检查权限，因为用户身份或运行状态可能在模型决策后发生变化。

第三，model\_validate\_json\(\) 在业务函数之前校验原始参数。校验失败时，handler 根本不会运行；返回模型的错误只保留字段路径和安全说明，不包含原始输入。

第四，高风险调用检查与 call\.id 绑定的审批记录。模型不能通过参数自我批准。

第五，asyncio\.timeout\(\) 给每次执行设置上限。超时会向协程传播取消，工具实现还必须正确响应取消，并把取消信号继续传给 HTTP、数据库或子进程；只包一层超时但让后台工作继续运行，不算真正取消。

第六，只有“错误可重试、工具幂等、次数未超限”三个条件同时成立，Runtime 才执行指数退避。写操作不能因为网络超时就盲目重放，否则第一次其实已经成功，第二次可能重复扣款或重复发送。

第七，Output Schema 在结果进入模型之前再次校验。工具代码同样会犯错，不能因为它是内部函数就无条件信任。\_finish\_error\(\) 和 \_write\_trace\(\) 则保证拒绝、失败与成功都走同一条留痕路径。

把这七点放回 Harness，可以得到一条稳定流水线：Registry 决定工具是否存在；可见性投影决定模型本轮能选择什么；execute\(\) 再执行参数校验、二次鉴权、审批、超时和重试；最后只向 Loop 返回标准 Tool Result。新增工具时只需注册新的 ToolDefinition，治理顺序和 Loop 主体都不改变。

这段代码尤其值得学习“可见性不是授权”这一机制。model\_tools\(\) 提前隐藏无权限工具，可以减少模型误选和无效 Token；execute\(\) 仍然再次检查权限，防止模型决策后身份变化、伪造 Tool Call 或绕过模型层直接调用 Runtime。两道检查用途不同，不能因为前面过滤过就删除执行边界。

课程代码为了突出执行顺序，没有记录原始参数。真实系统可以记录经过脱敏的参数摘要或哈希，但不应把密码、Token、身份证号和完整订单隐私写进 Trace。

Trace 至少要回答：谁在什么任务中，以什么身份，调用了哪个工具，尝试了几次，耗时多久，最终成功、拒绝还是失败。只有这样，Agent 出错时才能还原轨迹，而不是只看到最后一句“抱歉，处理失败”。

还要区分 Runtime 重试和 Agent Loop 重试：

|重试位置|适合处理什么|示例|
|---|---|---|
|Tool Runtime|同一个合法调用的瞬时基础设施故障|幂等查询遇到 502，原参数退避重试|
|Agent Loop|需要模型重新决策或修改参数|订单 ID 不存在，模型先查询候选订单|

Runtime 重试不改变动作语义；Agent Loop 重试会产生新的决策。两者如果混在一起，很容易出现重复执行和无限循环。

### 本小节结论

Tool Runtime 的价值不是统一写一行 await handler\(\)，而是保证每个工具都经过相同的校验、授权、风险控制、超时、有限重试、结果校验和 Trace。模型可以提出错误动作，但错误动作不能越过执行边界。

完成统一治理以后，为什么还要学习工具插件化？少量工具可以直接写进一个 Registry，但随着业务增加，每新增一个工具都修改 Runtime，权限、Trace 和超时逻辑也会逐渐散落在工具函数中。最终任何一次加载、替换或下线都可能影响整个 Harness。

Agent 开发工程师不仅要让一个工具调用成功，还要让能力可以独立注册、测试、卸载和替换，让治理规则覆盖一类工具而不是复制到每个函数。于是最后一个问题是：当工具越来越多，怎样避免注册、治理和生命周期代码全部堆进 Runtime？

## 2\.6 DeepSeek Harness 的工具插件化设计

### 2\.6\.1 DeepSeek Harness 是什么？

先不要急着理解 Plugin、Service 和 Registry，先回答最基本的问题：DeepSeek Harness 到底是什么？

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 是 DeepSeek AI 开源的一套 Agent Harness，目前处于 developer preview。它不是一个新模型，也不是 Function Calling API，而是运行 Agent 的工程框架。模型只负责生成文本和 Tool Call；Harness 负责把模型、Agent Loop、工具、上下文、会话、权限、取消和事件组织成一个可以持续运行的系统。

可以先把 Harness 理解成 Agent 的“运行外壳”：

```Plain Text
模型：决定下一步想做什么
Harness：提供当前能做什么，并控制这一步怎样执行
```

前面课程编写的 Tool Runtime、ExecutionContext、Trace 和最小 Agent Loop，其实都属于 Harness 的组成部分。DeepSeek Harness 的特别之处，不是又实现了一遍这些组件，而是使用 Cordis 的插件体系组织它们，提出“Everything is a Plugin”：工具、模型适配器、事件监听器和其他运行能力，都尽量通过插件和 Service 装配到系统中。

这里先管理好学习预期。本小节不要求学员掌握 Cordis 的完整 API，也不讨论插件打包、前端扩展和热更新实现。我们只回答三个与 Agent 开发岗位直接相关的问题：

1. 一个工具能力怎样在不修改 Agent Loop 的情况下加入 Harness；

2. 插件怎样声明依赖，并在依赖就绪后安全加载；

3. 插件卸载时，工具注册、事件监听和外部资源怎样一起清理。

掌握这三个问题以后，即使项目最终不用 DeepSeek Harness，也能把相同边界迁移到 Python Agent 平台中。

### 2\.6\.2 它与 pi 和常见 Agent Harness 有什么区别？

这一章把 pi 0\.83\.0 作为主要源码参考，因为它的 Tool 与 Agent Loop 链路直接、紧凑，适合看清“模型请求—参数校验—执行前钩子—工具执行—执行后钩子—结果回传”。DeepSeek Harness 更值得参考的，则是能力怎样在一个更大的运行平台中装配和管理。

可以用下面这张表建立区别：

|比较维度|pi 0\.83\.0|DeepSeek Harness|常见的应用级 Agent 框架|
|---|---|---|---|
|主要关注点|轻量、可组合的模型调用与 Agent Loop|插件优先的 Agent 运行平台|快速搭建固定 Workflow 或 Agent 应用|
|工具扩展|registerTool\(\) 注册工具，使用执行前后事件扩展行为|插件通过 ctx\.tools Service 注册工具|通常在初始化时传入工具列表或节点|
|核心 Loop|源码集中，适合直接理解调用和回传顺序|运行能力通过插件与事件协作，强调可替换和装配|Loop 或 Workflow 通常由框架预先定义|
|依赖处理|扩展使用宿主提供的 API 和上下文|插件声明所需 Service，依赖未就绪时等待加载|多由应用启动代码手工保证初始化顺序|
|卸载与清理|扩展跟随会话或宿主生命周期管理|注册行为归属插件 Fiber，卸载时自动撤销|经常只考虑启动和注册，较少讨论动态卸载|
|最值得学习的部分|Agent Loop、Tool Call、Tool Result 和 Hook 顺序|Service、依赖、生命周期和可撤销注册|业务流程建模与快速交付|

这不是在判断哪一个框架更好，而是在说明它们适合提供不同的学习视角。

从 pi 中，我们重点学习一条调用怎样进入 Loop、怎样执行、怎样形成 Tool Result；从 DeepSeek Harness 中，我们重点学习当工具、模型适配器和治理能力越来越多时，Harness 怎样避免所有组件直接依赖核心 Loop。

### 2\.6\.3 为什么 DeepSeek Harness 的可插拔设计值得学习？

先用一个具体问题理解“可插拔”。假设订单 Agent 最初只有 search\_orders，后来又加入支付工具、审批工具、审计模块和 Sandbox。如果每增加一个能力，都直接修改 Agent Loop：

```Plain Text
if tool_name == "search_orders":
    ...
elif tool_name == "cancel_order":
    ...
elif tool_name == "refund_order":
    ...
```

短期看很直接，长期却会出现三个问题：新增业务工具必须修改核心循环；权限、超时和 Trace 逻辑容易复制到每个分支；删除一个工具时，也很难确认它留下的监听器、连接和后台任务是否已经清理。

可插拔设计希望建立相反的关系：Agent Loop 只认识稳定的 Tool Call 与 Tool Result 协议；新能力通过统一接口注册进来；不用时再完整撤销。Loop 不需要知道当前安装的是订单工具还是代码工具。

要理解 DeepSeek Harness 的设计，先解释四个新概念：

|概念|先把它理解成什么|解决什么问题|
|---|---|---|
|Registry|按名称保存工具定义的索引|Tool Call 到来时，Runtime 到哪里寻找工具|
|Plugin|向 Harness 贡献一种能力的自包含模块|新增工具或治理能力时，怎样避免修改核心 Loop|
|Service|Harness 提供给插件使用的具名运行能力|插件怎样获得 Tool Runtime、LLM 或 Agent 能力|
|Lifecycle|插件从等待、加载、运行到卸载的过程|依赖未就绪怎么办，卸载时由谁清理资源|

现在再看 Registry 与插件化的区别就容易理解了。

Registry 只解决“已经注册的工具放在哪里、怎样按名称找到”。它通常就是 dict\[str, ToolDefinition\]。但 Registry 不知道是谁注册了这个工具，不知道插件依赖的数据库或 Tool Runtime 是否已经就绪，也不知道插件卸载时还要撤销哪些事件监听和连接。

插件体系在 Registry 外增加了装配和生命周期：

```Plain Text
Plugin 声明需要 tools Service
        ↓
依赖就绪后，Plugin 注册 ToolDefinition
        ↓
工具调用继续经过统一 Tool Runtime
        ↓
Plugin 卸载时，撤销工具、监听器和自有资源
```

在 DeepSeek Harness 的 [Services and dependencies](https://deepseek-harness.github.io/deepseek-harness/en/develop/framework/service) 设计中，tools、llm 和 agents 都可以作为挂载在 Context 上的 Service。工具插件声明依赖 tools，框架会等 Tool Runtime 就绪后再运行插件；如果依赖消失，相关插件会退出活动状态，并在服务恢复后重新加载。注册工具、注册事件监听器和自定义清理函数都归属于[插件生命周期](https://deepseek-harness.github.io/deepseek-harness/en/develop/framework/)。

这套设计对 Agent 工程尤其重要，因为 Agent 不是一次请求结束就销毁的普通函数。它可能运行很久，动态增加工具，等待人工审批，切换模型 Provider，或者在开发期热替换能力。如果只解决“注册”，却没有“依赖”和“卸载”，运行时间越长，残留状态和行为冲突就越难诊断。

因此，本节真正要学习的不是 Cordis 语法，而是四个 Harness 机制：

1. 工具定义与 Agent Loop 分离，新增工具不修改循环；

2. 插件通过 Service 获取能力，不直接访问 Harness 内部实现；

3. 注册行为必须可撤销，谁注册就由谁负责清理；

4. 权限、Sandbox、超时和 Trace 通过稳定扩展点覆盖多类工具。

带着这四个目标，下面再用 Python 表达最小插件边界。这不是 DeepSeek Harness 的官方 Python API，而是按照相同职责关系重建的教学实现。

plugins\.py

```Plain Text
from collections.abc import Callable
from dataclasses import dataclass
from typing import Protocol


Dispose = Callable[[], None]


@dataclass(frozen=True)
class PluginContext:
    tools: ToolRuntime

    def register_tool(self, tool: ToolDefinition) -> Dispose:
        return self.tools.register(tool)


class ToolPlugin(Protocol):
    name: str
    requires: frozenset[str]

    def apply(self, ctx: PluginContext) -> list[Dispose]: ...


class OrderToolsPlugin:
    name = "order-tools"
    requires = frozenset({"tools"})

    def apply(self, ctx: PluginContext) -> list[Dispose]:
        return [ctx.register_tool(SEARCH_ORDERS)]


class PluginManager:
    def __init__(self, ctx: PluginContext):
        self._ctx = ctx
        self._loaded: dict[str, list[Dispose]] = {}

    def load(self, plugin: ToolPlugin) -> None:
        available = frozenset({"tools"})
        missing = plugin.requires - available
        if missing:
            raise RuntimeError(f"missing services: {sorted(missing)}")
        if plugin.name in self._loaded:
            raise ValueError(f"duplicate plugin: {plugin.name}")
        self._loaded[plugin.name] = plugin.apply(self._ctx)

    def unload(self, plugin_name: str) -> None:
        disposers = self._loaded.pop(plugin_name, [])
        for dispose in reversed(disposers):
            dispose()
```

这段代码用 Python 重建最小插件生命周期。OrderToolsPlugin 不修改 Agent Loop，只在加载时向 Tool Runtime 注册 SEARCH\_ORDERS；PluginManager 负责检查依赖、保存清理函数，并在卸载时撤销插件产生的注册。

演示时重点看三个位置。requires=\{"tools"\} 表示插件只有在 Tool Runtime Service 就绪后才能加载；apply\(\) 负责装配能力而不是启动新的 Loop；register\_tool\(\) 返回 Dispose，使一次注册拥有明确的撤销动作。卸载时逆序执行 disposer，可以按照资源创建的相反顺序清理依赖。

这段代码值得展示，是因为插件化真正解决的不是“把类放进另一个文件”，而是能力生命周期。没有 disposer，重载插件可能留下两个同名工具；没有依赖检查，插件可能在 Runtime 尚未就绪时注册失败；如果插件直接修改 Loop，新增和下线工具都可能破坏核心控制流。

放回 Harness 后，工具插件只贡献 ToolDefinition，权限、超时和 Trace 插件可以挂在统一执行扩展点上，Agent Loop 继续只处理 Tool Call 和 Tool Result。这样工具能力、治理规则和循环机制才能独立演进。

生产级 DeepSeek Harness 还提供更细的工具执行扩展点。理解它们时不需要记住所有 API，只要看清职责：

|扩展位置|适合放什么|为什么不写进每个工具|
|---|---|---|
|执行前|权限、审批、Sandbox、参数策略|同一规则需要覆盖多类工具|
|执行包裹层|超时、重试、Metrics|需要覆盖完整执行时长|
|执行后|结果转换、敏感信息拦截|业务结果产生后才能判断|
|最终结果观察|审计、Trace、统计|只观察权威结果，不再改变它|

这与 pi 的 beforeToolCall、execute、afterToolCall 和 Tool Result 事件虽然 API 不同，但工程目标一致：让 Agent Loop 保持稳定，把可替换的工具能力和治理规则装配到 Harness 上。

插件化也不代表“安装后默认可信”。pi 文档明确提醒扩展拥有宿主进程权限；DeepSeek Harness 当前也处于 developer preview。工程师仍然要审核来源、锁定版本、限制权限，并用集成测试验证插件卸载、重名冲突和治理钩子是否生效。

### 本小节结论

插件化不是为了把文件拆得更多，而是让工具、治理和 Agent Loop 各自演进：工具插件贡献能力，治理插件约束执行，Runtime 保证统一协议，Loop 只处理 Tool Call 与 Tool Result。Python 实现不必复制 Cordis，但应保留依赖、可撤销注册和稳定扩展点这三个核心边界。

## 三、本节小结

上一节的 LLM Gateway 统一了“怎样调用模型”；本节继续向前一步，解决“模型怎样请求外部能力，以及程序怎样安全执行”。

完整链路可以收束为四层：

```Plain Text
模型：根据上下文和工具 Schema 提出 Tool Call
协议：用 Input、Output、Error Schema 定义边界
Runtime：校验、授权、执行、超时、重试、审计和 Trace
Harness：保存 Tool Result，推动下一轮模型决策
```

其中真正需要 Agent 开发工程师完成的，不是教模型输出一个函数名，而是：

- 把业务能力拆成边界清楚的工具；

- 写出模型能理解、程序能校验的协议；

- 从可信上下文注入身份和权限；

- 区分可重试错误与不可重复的副作用；

- 保证非法、越权和未审批调用永远不会执行；

- 让每次调用都能通过 Tool Result 和 Trace 被恢复、解释与审计；

- 用插件化方式装配工具和治理能力，同时保持 Agent Loop 稳定。

下一节进入 Tool Runtime 设计后，会在本节最小实现上继续补充 Tool Registry、工具发现、版本、并发控制和更完整的执行基础设施。

## 四、课堂练习与验收

为“订单运营 Agent”补充一个 cancel\_order 工具。要求：

1. Input Schema 包含 order\_id 和 reason，禁止额外字段；

2. Output Schema 返回 order\_id、取消后的状态和业务操作编号；

3. Error Schema 复用本节的 ToolError；

4. 权限设为 order:write，风险设为 high，工具设为非幂等；

5. 模型能看见 Schema，但用户身份和审批记录不能由模型填写；

6. 非法参数、无权限或未确认时，业务函数调用次数必须为零；

7. 超时后不能自动重试取消动作；

8. 每次成功、拒绝和失败都可以通过 trace\_id 与 tool\_call\_id 定位。

完成后，学员应能解释：

- Function Calling 为什么是候选动作，而不是函数执行；

- 为什么工具描述、输入 Schema 和权限检查分别解决不同问题；

- 为什么 Tool Result 必须保留 tool\_call\_id；

- 为什么权限信息不能从模型参数中读取；

- 为什么只有幂等工具的临时错误适合 Runtime 重试；

- pi 和 DeepSeek Harness 的插件机制怎样避免把治理逻辑写进每个工具。
