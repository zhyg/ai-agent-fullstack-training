# 2.1 Function Calling 与 Tool Use：让模型提出动作，让 Runtime 安全执行

## 一、先回答学习预期：不能脱离 AI 手写完整工具调用框架，算没有掌握吗？

### 学完以后，必须默写整套 Function Calling 代码吗？

先给结论：不需要。

真实工作中，你完全可以让 AI 帮你生成 Pydantic Model、Provider 调用样板、异常分支和测试代码。本节也不要求你记住某家模型 API 的全部字段，更不要求你脱离文档复刻一个成熟 Harness。

但是，AI 能写出“可以运行的代码”，不等于它能替你决定“这段代码是否可以执行真实业务动作”。工具应该怎样拆分、哪些参数允许模型填写、用户身份从哪里来、哪些错误可以重试、什么结果可以进入模型上下文，这些都依赖业务事实和风险判断，必须由工程师负责。

因此，本节真正训练的不是代码记忆，而是四项能力。

1. **构建与验证工具调用闭环的能力**

   能把 Tool Schema、Tool Call、Runtime 执行、Tool Result 和模型下一轮决策串成完整链路；还能用测试证明参数非法、权限不足或缺少确认时，handler 没有执行。

2. **软件工程判断能力**

   能区分模型协议、业务函数、Tool Runtime 和 Agent Loop 的职责；能识别不可信输入、可信上下文、副作用边界和失败语义，而不是把所有逻辑都塞进一个函数。

3. **与 AI 协作开发的能力**

   能先定义工具边界、Schema 和验收条件，再让 AI 补实现；拿到 AI 代码后，能审查是否绕过校验、相信模型提供的身份、丢失 `tool_call_id`，或者对非幂等写操作盲目重试。

4. **迁移与应用能力**

   能把同一套方法从订单查询迁移到工单、知识库、文件系统或企业 API，而不是只会复现课堂里的 `search_orders`。

### 本节怎样才算真正掌握？

不要用“能不能背出全部代码”验收自己。完成本节后，你应当能够做到三件事：

- 不看代码，用两分钟讲清“模型提出动作，Runtime 受控执行，Loop 回写结果”的主链；
- 面对一段 AI 生成的工具调用代码，指出协议、权限、重试和结果关联上的关键问题；
- 为一个新业务动作写出最小工具定义，能构造 Tool Call，并生成与调用 ID 正确配对的 Tool Result。

如果暂时写不出完整 Runtime，但能做出这些判断，并能借助 AI 实现后验证结果，说明你已经掌握了本节的核心能力。

### 本节围绕哪条主线展开？

本节建议讲授 40 分钟，只回答 Function Calling 的六个基础问题，不提前展开下一节完整的 Tool Registry、Snapshot、并发调度和生产级治理平台。

|小节|本节要回答的问题|
|---|---|
|1.1|模型怎样提出 Tool Call，结果又怎样回到模型？|
|1.2|一个业务函数怎样定义成模型可选择、Runtime 可治理的工具？|
|1.3|Input、Output 和 Error Schema 分别保护哪一段边界？|
|1.4|模型依据什么选择工具，最小 Agent Loop 怎样继续下一轮？|
|1.5|为什么 Tool Call 不能直接执行，治理边界至少要检查什么？|
|1.6|为什么工具能力要与 Agent Loop 解耦，插件化需要保留哪些接口？|

六个问题最终收束到一条主线：

```text
模型提出 Tool Call
  → Runtime 校验、授权并执行
  → 生成带原始 tool_call_id 的 Tool Result
  → Agent Loop 写回结果
  → 模型继续决策或完成回答
```

在这条链路里，模型擅长理解意图、选择候选工具和生成候选参数；工程师负责定义协议、可信边界、权限风险、失败恢复和验收标准。
## 二、先划清边界：模型已经能回答问题，为什么还需要 Tool Use？

上一节完成 LLM Gateway 后，Agent 已经有了统一的模型调用入口。可是模型调用解决的是“生成什么”，不能直接解决“系统里发生什么”。

比如用户问：“帮我查一下昨天创建、还没有支付的订单。”模型可以解释应该怎样查询，但它不知道业务数据库里的实时订单，也不能只凭一句自然语言直接访问数据库。

如果用户进一步说：“把这笔订单取消掉”，问题就更明显了。模型不仅缺少实时数据，也不应该拥有数据库连接、用户身份和取消订单的真实权限。

所以先给出本节的核心结论：

> Function Calling 不是让模型获得执行权限，而是让模型用结构化方式提出“我想调用哪个工具、参数是什么”。真正的执行必须交给 Tool Runtime。

一条可靠的职责边界是：

|角色|负责什么|不能替谁决定什么|
|---|---|---|
|模型|理解请求、选择候选工具、生成候选参数、阅读工具结果|不能决定自己是否有权限，也不能直接执行 Python 函数|
|工具函数|完成一项确定的业务能力|不能相信调用参数天然正确，也不负责整个 Agent Loop|
|Tool Runtime|查找工具、校验、鉴权、超时、重试、审计和结果归一化|不能替业务方定义权限和风险规则|
|Agent Loop / Harness|保存消息和状态，把 Tool Result 送回模型，决定继续或结束|不应绕过 Runtime 直接调用业务函数|

`pi 0.83.0` 的源码也是按照这条边界组织的：模型侧的 `Tool` 只包含名称、描述和参数 Schema；进入 Agent 层后，`AgentTool` 才增加 `execute()`；Agent Loop 在执行前校验参数、运行 `beforeToolCall`，执行后运行 `afterToolCall`，最后产生与 `toolCallId` 对应的 `toolResult`。

下面把分散在三个源码文件中的关键类型和函数合并成一段教学代码。为了让读者先看清主流程，这里省略异常与分支处理；文件注释标明了对应定义在 `pi 0.83.0` 中的位置。

```typescript
// packages/ai/src/types.ts
type Tool = {
	name: string;
	description: string;
	parameters: Record<string, unknown>;
};

type ToolCall = {
	id: string;
	name: string;
	arguments: unknown;
};

type ToolResultMessage = {
	role: "toolResult";
	toolCallId: string;
	toolName: string;
	content: string;
};

// packages/agent/src/types.ts
type AgentTool = Tool & {
	execute(
		toolCallId: string,
		args: Record<string, unknown>,
		onUpdate: (content: string) => void,
	): Promise<string>;
};

type Hooks = {
	beforeToolCall?(call: ToolCall, args: object): Promise<void>;
	afterToolCall?(call: ToolCall, result: string): Promise<string>;
};

// packages/ai/src/utils/validation.ts
function validateToolArguments(call: ToolCall) {
	return call.arguments as Record<string, unknown>;
}

// packages/agent/src/agent-loop.ts
async function prepareToolCall(
	tools: AgentTool[],
	call: ToolCall,
	hooks: Hooks,
) {
	const tool = tools.find(item => item.name === call.name)!;
	const args = validateToolArguments(call);
	await hooks.beforeToolCall?.(call, args);
	return { tool, call, args };
}

async function executePreparedToolCall(
	prepared: Awaited<ReturnType<typeof prepareToolCall>>,
) {
	return prepared.tool.execute(
		prepared.call.id,
		prepared.args,
		content => console.log({
			type: "tool_execution_update",
			toolCallId: prepared.call.id,
			content,
		}),
	);
}

async function finalizeToolCall(
	call: ToolCall,
	result: string,
	hooks: Hooks,
) {
	return await hooks.afterToolCall?.(call, result) ?? result;
}

function createToolResultMessage(
	call: ToolCall,
	content: string,
): ToolResultMessage {
	return {
		role: "toolResult",
		toolCallId: call.id,
		toolName: call.name,
		content,
	};
}

async function runToolCall(
	tools: AgentTool[],
	call: ToolCall,
	hooks: Hooks,
) {
	const prepared = await prepareToolCall(tools, call, hooks);
	const executed = await executePreparedToolCall(prepared);
	const finalized = await finalizeToolCall(call, executed, hooks);
	return createToolResultMessage(call, finalized);
}
```

这段代码不是让大家记住 TypeScript 语法，而是把分散在 `pi 0.83.0` 三个文件中的职责合并到一张“流程图”里。它从模型侧的 `Tool` 开始，经过 Runtime 侧的 `AgentTool`，最后进入 Agent Loop 的准备、执行、收口和结果回写。

演示时只需要抓住三个位置。

第一，`Tool` 没有 `execute()`。模型能看到的只有名称、描述和参数 Schema，因此它只能提出候选动作，拿不到宿主进程中的函数引用。

第二，`prepareToolCall()` 先调用 `validateToolArguments()`，再运行 `beforeToolCall`。这说明参数校验、权限和确认必须发生在真实业务函数之前；任何拒绝路径都应该保证 handler 调用次数为零。

第三，`executePreparedToolCall()`、`finalizeToolCall()` 和 `createToolResultMessage()` 始终沿用同一个调用 ID。执行进度、执行后处理和最终结果因此能够回到原始 Tool Call，即使多个工具并行完成也不会错配。

这正是值得从 Harness 和 Agent Loop 中学习的机制：Loop 只推动“模型决策—工具结果—再次决策”，Runtime 负责把候选动作变成受控执行。以后用 Python 实现时，不需要复制这些 TypeScript 类型，但必须保留这条职责链和 `tool_call_id` 不丢失的协议不变量。

接下来，我们先把这条链路拆开，看一次 Function Calling 到底发生了什么。

## 1.1 Function Calling 工作机制

### 为什么模型返回了 Tool Call，程序还不能直接执行？

先看结论：模型返回的 Tool Call 只是一个候选动作，它与用户输入一样，都属于不可信数据。Runtime 至少要确认工具存在、参数合法、用户有权调用、当前风险可以接受，才能进入真实执行。

一次完整调用通常包含六步：

1. 应用把用户消息和当前可用的工具 Schema 一起发送给模型；
2. 模型决定直接回答，或者返回一个或多个 Tool Call；
3. 每个 Tool Call 携带调用 ID、工具名称和 JSON 参数；
4. Tool Runtime 校验工具、参数、权限和风险，再执行真实函数；
5. Runtime 把成功结果或结构化错误作为 Tool Result 写回消息历史；
6. 模型读取结果，继续调用工具、向用户追问，或者生成最终答案。

这条链路可以压缩成：

```text
User Message
    ↓
LLM：直接回答，或生成 Tool Call
    ↓
Tool Runtime：validate → authorize → execute → observe
    ↓
Tool Result：必须带回原来的 tool_call_id
    ↓
LLM：继续决策或完成回答
```

这里最容易被忽略的是 `tool_call_id`。模型一次可能提出多个调用，Runtime 必须把每份结果与原调用准确关联。只返回“订单查询成功”，却不保留调用 ID，模型和 Trace 都无法知道这是谁的结果。

### `tool_call_id` 到底解决了什么问题？

先给出结论：`tool_call_id` 是一次“模型提出的工具调用”的关联键。它把 Assistant Message 中的 Tool Call、Runtime 中的执行过程，以及随后写回的 Tool Result 串成同一条记录。

它不是订单 ID，也不是用户 ID，更不是整个 Agent 任务的 Trace ID。三类 ID 的职责要分开：

|ID|标识什么|生命周期|
|---|---|---|
|`trace_id`|一次 Agent 任务或请求|贯穿多轮模型调用和多次工具执行|
|`tool_call_id`|模型在某一轮提出的一次具体工具调用|从 Tool Call 产生，到对应 Tool Result 写回|
|`order_id` 等业务 ID|工具正在操作的真实业务对象|由业务系统定义，可能跨越很多 Agent 任务|

假设用户说：“查询 ord_123 和 ord_456 的状态。”模型可能在同一条 Assistant Message 中提出两个调用：

```json
{
  "role": "assistant",
  "tool_calls": [
    {
      "id": "call_A",
      "function": {
        "name": "get_order",
        "arguments": "{\"order_id\":\"ord_123\"}"
      }
    },
    {
      "id": "call_B",
      "function": {
        "name": "get_order",
        "arguments": "{\"order_id\":\"ord_456\"}"
      }
    }
  ]
}
```

两个调用的工具名称完全相同，区别只在参数和调用 ID。如果 Runtime 只记录工具名，就无法稳定区分两次执行。

而且并行执行时，完成顺序不一定等于生成顺序。`ord_456` 可能先从数据库返回，`ord_123` 反而超时。Runtime 可以先后得到下面两份结果：

```json
{
  "role": "tool",
  "tool_call_id": "call_B",
  "content": "{\"order_id\":\"ord_456\",\"status\":\"paid\"}"
}
```

```json
{
  "role": "tool",
  "tool_call_id": "call_A",
  "content": "{\"error\":{\"code\":\"TIMEOUT\"}}"
}
```

虽然结果顺序发生了变化，模型仍然可以通过 `call_B` 知道 paid 属于 `ord_456`，通过 `call_A` 知道 `ord_123` 查询超时。如果没有 `tool_call_id`，模型只能看到“一次成功、一次超时”，却无法判断哪笔订单成功、哪笔订单需要重试。

所以，`tool_call_id` 至少解决四个问题。

第一，解决消息协议的对应关系。Assistant Message 提出了哪些 Tool Call，后续就要为每个调用写回对应的 Tool Result。结果不能只依赖数组位置，也不能只依赖工具名称。

第二，解除生成顺序与完成顺序的耦合。只读工具可以并行执行，谁先完成就先产生执行事件；最终无论怎样排序，都能通过调用 ID 找回来源。

第三，区分成功和失败的恢复对象。同一批调用中，一个可能成功，一个可能参数错误，另一个可能超时。Agent Loop 必须知道应该修正或重试哪一个调用，不能把整批结果统一当成成功或失败。

第四，建立 Trace 的父子关系。日志可以使用 `trace_id` 找到整个任务，再使用 `tool_call_id` 定位某次工具调用的参数摘要、权限判断、重试次数、耗时和最终结果。

Runtime 在并行执行时，应当让调用 ID 跟随调用对象进入每个异步任务，而不是等工具完成后再按返回顺序猜测：

tool_batch.py

```python
import asyncio


async def execute_bound(
    call: ToolCall,
    runtime: "ToolRuntime",
    ctx: "ExecutionContext",
) -> tuple[str, ToolResultMessage]:
    result = await runtime.execute(call, ctx)
    return call.id, result


async def execute_batch(
    calls: list[ToolCall],
    runtime: "ToolRuntime",
    ctx: "ExecutionContext",
) -> list[ToolResultMessage]:
    tasks = [
        asyncio.create_task(execute_bound(call, runtime, ctx))
        for call in calls
    ]

    results: list[ToolResultMessage] = []
    for task in asyncio.as_completed(tasks):
        call_id, result = await task
        assert result.tool_call_id == call_id
        results.append(result)

    return results
```

这段代码演示 Harness 怎样安全执行一批可以并行的 Tool Call。`execute_batch()` 为每个调用创建独立任务，`execute_bound()` 则把调用 ID 与 Runtime 返回结果绑定在同一个协程返回值中。

演示时重点看 `asyncio.as_completed()` 和后面的 `assert`。`as_completed()` 故意按完成顺序取结果，证明 Runtime 不能依赖数组位置维持对应关系；`assert result.tool_call_id == call_id` 则把“结果必须属于原调用”写成可验证的不变量。

放回 Harness 后，这个机制允许执行事件按真实完成顺序流向 UI，同时仍可在持久化时按 Assistant Message 中的调用顺序整理 Tool Result。并发调度与消息协议因此解耦：谁先完成不重要，关联 ID 始终不能丢。

一个可靠的 Tool Runtime 至少要保证：

1. 每个 Tool Call 最终只产生一份权威 Tool Result；
2. 成功、参数错误、权限拒绝和执行异常都必须保留原 `tool_call_id`；
3. 同一批调用的结果可以乱序完成，但不能错配或遗漏；
4. `tool_execution_start`、进度更新、重试记录和最终结果使用同一个调用 ID。

还要注意，`tool_call_id` 主要用于协议关联，不应直接代替业务幂等键。模型重新决策后可能生成新的调用 ID，即使它仍然请求执行同一笔业务操作。涉及支付、发送或取消等副作用时，Runtime 还要根据业务对象、动作和参数生成或传递独立的幂等键，防止“新的 Tool Call 重复执行旧动作”。

前面展示的 `pi` 源码正是这样处理的：`execute()` 接收 `prepared.toolCall.id`，执行进度继续携带该 ID，`createToolResultMessage()` 最后把 `finalized.toolCall.id` 写入 `toolCallId`。调用从开始到结束始终使用同一个关联键。

先定义模型调用与工具结果在 Python 中的最小结构：

tool_messages.py

```python
from typing import Any, Literal

from pydantic import BaseModel, ConfigDict, Field


class ToolCall(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)

    id: str = Field(min_length=1)
    name: str = Field(min_length=1, max_length=100)
    arguments_json: str


class ToolResultMessage(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)

    role: Literal["tool"] = "tool"
    tool_call_id: str
    name: str
    content: str
    is_error: bool = False

    def to_model_message(self) -> dict[str, str]:
        return {
            "role": self.role,
            "tool_call_id": self.tool_call_id,
            "content": self.content,
        }
```

这段代码定义 Harness 内部的 Tool Call 与 Tool Result 消息协议。它不执行工具，而是把供应商返回的数据先收口成稳定的 Python 对象，让后续校验、执行、Trace 和消息回传都使用同一组字段。

演示时重点看三个设计。第一，`arguments_json` 保留原始 JSON 字符串，说明“模型已经生成参数”不等于“参数已经可信”；只有 Runtime 调用具体工具的 `input_model` 后，才能得到可执行对象。第二，`ToolResultMessage` 强制携带 `tool_call_id`，使成功、拒绝和异常都能与原调用关联。第三，`to_model_message()` 是一个明确的协议投影：Harness 内部保留 `name` 和 `is_error` 供 Trace、UI 与恢复逻辑使用，发送给 OpenAI Compatible API 时只输出对方真正接受的字段。

这段代码值得展示，是因为成熟 Harness 通常不会让 Provider SDK 对象直接穿透整个 Agent Loop。内部消息协议与供应商协议分离以后，切换 Chat Completions、Responses API 或其他模型时，只需要修改适配层；Tool Runtime 和 Loop 仍然消费同一个 `ToolCall` 与 `ToolResultMessage`。

还要注意，Tool Result 不等于最终答案。它只是新的 observation。模型读完以后，才决定下一步做什么。这就是后续 Agent Loop 的基本循环：

```text
模型决策 → 工具执行 → 获得观察 → 模型再次决策
```

理解完调用过程，为什么还要专门学习工具定义？因为模型不会读取 Python 函数的真实用途，它选择工具时主要依赖名称、描述和参数 Schema。如果定义含糊，即使 Runtime 完全没有 Bug，模型仍可能选错工具、漏填参数，或者把只读请求交给写操作工具。

这项工作也不能直接交给模型。模型可以帮助生成一份 Schema 草稿，却不知道公司的真实业务边界：哪些字段来自用户，哪些字段必须从登录态注入；查询和修改是否应该拆开；什么动作需要审批；哪些错误允许重试。只有工程师结合业务系统、权限模型和失败成本，才能把一个普通函数定义成可交给 Agent 使用的工具。

所以，学习工具定义不是为了记住一段 JSON 格式，而是为了掌握一项 Agent 开发的核心能力：把业务能力翻译成模型能正确选择、Runtime 能安全执行的协议。明确这一点以后，下一个问题才是：模型看到的“工具”到底应该怎样定义？

### 本小节结论

Function Calling 只负责把模型的动作意图变成结构化 Tool Call；Tool Runtime 才负责把候选动作变成受控执行；Agent Loop 再把 Tool Result 变成下一轮上下文。三者不能合并成一次普通函数调用。

---

## 1.2 工具定义：名称、描述、Schema、权限与风险

### 为什么不能把一个普通 Python 函数直接暴露给模型？

普通函数签名只告诉 Python 怎样传参，却没有完整回答模型和 Runtime 需要的问题：模型什么时候应该调用它？什么时候不应该调用？返回什么？失败怎样表达？谁可以调用？它会不会产生副作用？

所以，Agent 中的工具不是一个裸函数，而是一份“模型可理解、Runtime 可执行、平台可治理”的业务协议。

每个工具至少要有以下信息：

|字段|解决的问题|示例|
|---|---|---|
|`name`|稳定、唯一地标识工具|`search_orders`|
|`description`|告诉模型何时使用、边界是什么|“查询当前用户的订单，不修改订单”|
|`input_model`|调用需要哪些参数|状态、开始日期、数量上限|
|`output_model`|成功后返回什么事实|订单列表、总数|
|`error_model`|失败后怎样分类和恢复|参数错误、拒绝、超时、上游失败|
|`permission`|调用者需要什么权限|`order:read`|
|`risk`|调用前需要怎样的控制|`low`、`medium`、`high`|

下面用 Python 定义统一的工具元数据。它参考 `pi` 中“Tool 元数据与 AgentTool 执行函数分离”的思路，同时增加课程当前需要的输出、错误、权限和风险字段。

tool_definition.py

```python
from collections.abc import Awaitable, Callable
from dataclasses import dataclass
from typing import Literal

from pydantic import BaseModel


Permission = Literal["order:read", "order:write"]
RiskLevel = Literal["low", "medium", "high"]
ToolHandler = Callable[
    [BaseModel, "ExecutionContext"],
    Awaitable[BaseModel],
]


@dataclass(frozen=True)
class ToolDefinition:
    name: str
    description: str
    input_model: type[BaseModel]
    output_model: type[BaseModel]
    error_model: type[BaseModel]
    permission: Permission
    risk: RiskLevel
    handler: ToolHandler

    def to_model_tool(self) -> dict:
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.input_model.model_json_schema(),
            },
        }
```

这段代码定义工具的最小完整契约：模型选择需要的名称、描述和输入 Schema；应用侧需要的输出、错误、权限和风险；真正完成业务操作的 `handler`。超时、重试、版本和依赖等运行策略会在 2.2 的 Tool Runtime 中继续补充。

演示时重点关注三个位置。

第一，`input_model` 同时服务两条路径：调用模型前，`model_json_schema()` 生成参数 Schema；模型返回后，Runtime 使用同一个 Pydantic Model 校验参数。这样可以避免“模型看到一份 Schema，服务端执行另一套规则”的协议漂移。

第二，`output_model`、`error_model`、`permission` 和 `risk` 没有进入 `to_model_tool()`。模型选择工具时只需要申请格式，不能读取或修改运行策略。

第三，`handler` 与 `to_model_tool()` 明确分离。模型只得到可序列化的 JSON Schema，真实函数保留在应用进程中。Tool Call 到达以后，应用仍要查找完整定义、校验参数并检查权限，才能调用 `handler`。

因此，这段代码展示的是“完整定义”到“模型可见 Tool”的单向投影。Registry 怎样保存完整定义、怎样处理版本和本轮快照，留到下一节。

工具名称和描述需要工程师亲自设计，不能让模型随意生成。一个可用的描述至少要回答三件事：

```text
它做什么？
什么时候应该使用？
它不会做什么？
```

例如：

```text
名称：search_orders
描述：按当前用户、订单状态和创建日期查询订单；只读取订单，不能取消、退款或修改订单。
```

而下面这种描述几乎没有选择价值：

```text
名称：query_data
描述：查询数据。
```

模型不知道查询哪类数据，也不知道它与其他查询工具的区别。工具选择不稳定时，第一检查项通常不是继续增加 Prompt，而是检查名称、描述和工具粒度。

权限等级与风险等级也不能混为一谈。`permission` 回答“调用者有没有资格”；`risk` 回答“即使有资格，这次调用是否仍需确认或审批”。一个用户可能拥有 `order:write`，但批量取消订单仍然是高风险动作。

### 本小节结论

工具定义不是函数注释，而是跨越模型、Runtime 和业务系统的执行协议。工程师必须确定工具粒度、用途边界、数据结构、权限、风险和失败策略；模型只能在这份协议内提出调用。

有了工具的整体定义，为什么还要继续学习 Input、Output 和 Error Schema？因为上一节定义的元数据只是说明“这个工具应该有什么”，还没有形成 Runtime 可以强制执行的验收规则。没有可执行 Schema，参数错了只能等业务函数报错，返回值变了只能等 Agent 解析失败，工具失败后也不知道应该重试、追问还是停止。

这部分同样需要工程师决定。模型可以生成字段，却不能替业务系统确定必填条件、跨字段关系、稳定返回值和错误恢复语义。所以下一步不是继续增加工具描述，而是把输入、输出和错误写成真正可以校验的类型。

---

## 1.3 Input Schema、Output Schema 与 Error Schema

### 为什么只校验输入还不够？

输入校验只能阻止模型把错误参数送进业务函数，却不能保证业务函数返回了可用结果，也不能告诉 Agent 失败后应该怎样继续。

因此要把工具边界拆成三份 Schema：

|Schema|保护哪一侧|核心问题|
|---|---|---|
|Input Schema|模型到 Runtime|参数是否完整、类型是否正确、范围是否合理|
|Output Schema|业务系统到 Agent|成功结果是否稳定、后续 Loop 能否直接消费|
|Error Schema|失败到恢复逻辑|失败属于哪一类、能否重试、下一步是什么|

我们继续使用订单查询工具：

order_schemas.py

```python
from datetime import date
from typing import Literal

from pydantic import BaseModel, ConfigDict, Field, model_validator


class StrictModel(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)


class SearchOrdersInput(StrictModel):
    status: Literal["pending", "paid", "shipped", "cancelled"] | None = None
    created_from: date | None = None
    limit: int = Field(default=10, ge=1, le=50)

    @model_validator(mode="after")
    def require_filter(self) -> "SearchOrdersInput":
        if self.status is None and self.created_from is None:
            raise ValueError("status 与 created_from 至少提供一个")
        return self


class OrderSummary(StrictModel):
    order_id: str
    status: Literal["pending", "paid", "shipped", "cancelled"]
    created_at: str
    amount_cents: int = Field(ge=0)


class SearchOrdersOutput(StrictModel):
    orders: list[OrderSummary]
    total: int = Field(ge=0)


class ToolError(StrictModel):
    code: Literal[
        "INVALID_ARGUMENT",
        "TOOL_NOT_FOUND",
        "PERMISSION_DENIED",
        "APPROVAL_REQUIRED",
        "TIMEOUT",
        "UPSTREAM_ERROR",
        "INVALID_OUTPUT",
    ]
    message: str
    retryable: bool = False
```

这段代码一次定义了工具边界上的三份可执行协议。`SearchOrdersInput` 验收模型参数，`SearchOrdersOutput` 验收业务函数返回值，`ToolError` 统一表达失败。三者都继承 `StrictModel`，从默认行为上拒绝额外字段和隐式类型转换。

演示 Input Schema 时重点看三层约束。`Literal` 把订单状态限制在业务允许的枚举内；`Field` 把查询数量控制在 1—50；`model_validator` 表达“至少提供一个过滤条件”的跨字段规则。这里最值得学的不是 Pydantic 语法，而是 Harness 在进入工具函数前拥有一扇确定的校验门。模型可以生成候选参数，却不知道业务系统是否允许无条件扫全表，这条规则必须由工程师写。

演示 Output Schema 时重点看它返回的是订单 ID、状态、时间和金额，而不是“查询成功，共找到三笔订单”的自然语言。Agent Loop 后续可能需要判断候选数量、继续查询详情或请求用户选择；结构化事实可以被程序和模型同时消费，也可以在进入下一轮前再次校验。

演示 Error Schema 时重点看 `code` 与 `retryable` 的分工。`code` 告诉 Harness 失败属于参数、权限、审批、超时还是实现问题；`retryable` 提供恢复建议，但 Runtime 还要结合幂等性和预算作最终决定。例如：

- `INVALID_ARGUMENT`：模型可以修正参数后再次调用；
- `PERMISSION_DENIED`：不能重试同一调用，应停止或提示用户切换身份；
- `APPROVAL_REQUIRED`：需要进入人工确认流程；
- `TIMEOUT`、`UPSTREAM_ERROR`：只有满足幂等条件时，Runtime 才可以有限重试；
- `INVALID_OUTPUT`：说明工具实现违反了自己的返回协议，应记录工程故障，而不是让模型猜测缺失字段。

`retryable` 只是错误携带的建议，最终是否重试仍由 Runtime 结合工具的 `idempotent`、当前尝试次数和总预算决定。模型不能通过返回或修改 `retryable=true` 获得重试权。

把这段代码放回 Loop，可以看到三份 Schema 分别卡在不同位置：Input 位于 Tool Call 与 handler 之间；Output 位于 handler 与 Tool Result 之间；Error 位于失败与下一轮决策之间。它们不是三个孤立的数据类，而是 Harness 控制流的三个关口。

现在把 Schema 与真实工具函数装配起来：

search_orders_tool.py

```python
async def search_orders(
    args: SearchOrdersInput,
    ctx: "ExecutionContext",
) -> SearchOrdersOutput:
    rows = await ctx.order_service.search(
        user_id=ctx.user_id,
        status=args.status,
        created_from=args.created_from,
        limit=args.limit,
    )

    return SearchOrdersOutput(
        orders=[OrderSummary.model_validate(row) for row in rows],
        total=len(rows),
    )


SEARCH_ORDERS = ToolDefinition(
    name="search_orders",
    description=(
        "按当前用户、订单状态和创建日期查询订单。"
        "只读取订单；不能取消、退款或修改订单。"
    ),
    input_model=SearchOrdersInput,
    output_model=SearchOrdersOutput,
    error_model=ToolError,
    permission="order:read",
    risk="low",
    handler=search_orders,
)
```

这段代码完成两件事：`search_orders()` 实现真实业务查询；`SEARCH_ORDERS` 再把 handler 与前面定义的 Schema、权限和风险装配成 Agent Tool。单独存在的异步函数还不是模型可以使用的工具，应用还需要为它提供稳定协议。

演示 handler 时重点看参数来源被分成两类。`status`、`created_from` 和 `limit` 来自已经通过 Input Schema 的 `args`；`user_id` 来自可信的 `ExecutionContext`，而不是让模型填写。身份、租户、Trace ID 和审批凭证都属于 Runtime 上下文，不能混入模型可控参数。

演示装配对象时重点看 `input_model`、`output_model` 与 `handler` 的闭环。应用用 `input_model` 验收调用，用 `handler` 获得真实结果，再用 `output_model` 验收返回值；`permission` 与 `risk` 只声明治理要求，具体怎样执行由下一节的 Tool Runtime 负责。

放回 Harness 后，Tool Registry 保存的是 `SEARCH_ORDERS`，而不是只保存 `search_orders` 函数。Agent Loop 不需要理解订单业务，只需要把 Tool Call 交给 Runtime，再接收标准 Tool Result。这也是输入 Schema 设计中的关键原则：

> 模型只填写完成任务所需的业务参数；身份和权限由 Runtime 从可信上下文注入。

### 本小节结论

Input Schema 拦截错误调用，Output Schema 固定成功事实，Error Schema 驱动失败恢复。三者共同构成工具协议；缺少任何一份，Agent Loop 都会被迫解析自然语言或猜测下一步。

协议准备好以后，为什么还要学习工具选择？因为 Schema 只能约束“选中以后参数怎样写”，不能保证模型一定选对工具。工具选错了，问题可能来自名称与描述重叠、暴露的工具过多、上下文缺少关键信息，也可能是模型本身没有识别出调用条件。

Agent 开发工程师必须能区分这些原因，否则每次选错工具都只能继续修改 Prompt。接下来要观察模型到底看到了什么、依据什么选择，以及工程师怎样控制当前可见的工具集合。

---

## 1.4 工具选择：模型怎样选择工具并生成参数？

### 模型是怎样知道该调用 `search_orders`，而不是直接回答？

模型没有读取 Python 源码。它只看到当前消息，以及 Runtime 暴露的工具名称、描述和参数 Schema。模型根据这些信息生成三类结果之一：

1. 不需要外部能力，直接返回文本；
2. 信息不足，先向用户追问；
3. 需要外部能力，返回一个或多个 Tool Call。

因此，工具选择质量主要受四个因素影响：

|因素|工程师需要控制什么|
|---|---|
|工具集合|当前请求真正允许模型看到哪些工具|
|名称与描述|每个工具的用途、适用条件和禁止边界|
|参数 Schema|字段含义、枚举、必填项和范围|
|上下文|用户目标、已获得的 Tool Result 和当前状态|

不要把所有平台工具都暴露给每一轮模型。权限过滤得越晚，模型越可能选择一个最后必然被拒绝的工具。更好的做法是：Runtime 先根据用户、租户、Agent 角色和当前模式筛出可见工具，再把这份最小集合传给模型；真正执行前仍要再次鉴权。

下面使用 DeepSeek V4 Flash 和 OpenAI Compatible Chat Completions 演示一次工具选择。为了让代码集中在 Function Calling，本例关闭 thinking mode。

model_select.py

```python
import os

from openai import OpenAI


client = OpenAI(
    api_key=os.environ["DEEPSEEK_API_KEY"],
    base_url="https://api.deepseek.com",
)

messages = [
    {
        "role": "system",
        "content": (
            "你是订单助手。需要实时订单数据时调用工具；"
            "不要编造订单，修改订单前必须先获得明确目标。"
        ),
    },
    {
        "role": "user",
        "content": "查一下我昨天创建、还没有支付的订单。",
    },
]

response = client.chat.completions.create(
    model="deepseek-v4-flash",
    messages=messages,
    tools=[SEARCH_ORDERS.to_model_tool()],
    tool_choice="auto",
    extra_body={"thinking": {"type": "disabled"}},
)

assistant = response.choices[0].message

for call in assistant.tool_calls or []:
    print(call.id)
    print(call.function.name)
    print(call.function.arguments)
```

这段代码只演示 Function Calling 的“模型决策半程”：组装消息和工具 Schema，调用 DeepSeek V4 Flash，然后读取模型返回的 Tool Call。它没有执行 `search_orders()`，目的是把“模型提出动作”与“Runtime 执行动作”清楚分开。

演示时重点看四处。`tools=[SEARCH_ORDERS.to_model_tool()]` 证明发送给模型的是公开 Schema，而不是 Python 函数；`tool_choice="auto"` 允许模型根据任务选择直接回答或调用工具；`assistant.tool_calls` 可能为空、一个或多个，所以 Harness 不能假设每轮必定执行工具；`call.function.arguments` 仍然是模型生成的 JSON 字符串，打印出来只能用于观察，不能直接展开调用 handler。

这段代码在 Harness 中通常位于 LLM Adapter 或 Agent Loop 的模型请求阶段。它的输出不是最终答案，而是下一步控制流的输入：没有 Tool Call，Loop 可以结束；存在 Tool Call，Loop 必须转交 Tool Runtime 校验和执行。`extra_body` 属于 DeepSeek Provider 差异，真实项目应由上一节的 LLM Gateway 统一处理，而不是复制进每个 Agent。

即使模型生成：

```json
{
  "status": "pending",
  "created_from": "2026-08-16",
  "limit": 10
}
```

程序也不能直接执行 `search_orders(**arguments)`。下一步必须交给 Runtime 做 Pydantic 校验和权限检查。

把模型决策、工具结果和下一次模型调用串起来，可以得到最小 Tool Loop：

minimal_tool_loop.py

```python
MAX_STEPS = 4


async def run_order_agent(
    user_text: str,
    runtime: "ToolRuntime",
    ctx: "ExecutionContext",
) -> str:
    messages = [
        {"role": "system", "content": "你是订单助手，不得编造订单。"},
        {"role": "user", "content": user_text},
    ]

    for _ in range(MAX_STEPS):
        visible_tools = runtime.model_tools(ctx)
        response = client.chat.completions.create(
            model="deepseek-v4-flash",
            messages=messages,
            tools=visible_tools,
            tool_choice="auto",
            extra_body={"thinking": {"type": "disabled"}},
        )

        assistant = response.choices[0].message
        messages.append(assistant.model_dump(exclude_none=True))
        tool_calls = assistant.tool_calls or []

        if not tool_calls:
            return assistant.content or ""

        for raw_call in tool_calls:
            call = ToolCall(
                id=raw_call.id,
                name=raw_call.function.name,
                arguments_json=raw_call.function.arguments,
            )
            result = await runtime.execute(call, ctx)
            messages.append(result.to_model_message())

    raise RuntimeError("agent exceeded maximum steps")
```

这段代码第一次把模型调用和 Tool Runtime 组成最小 Agent Loop。它接收用户目标，持续执行“请求模型—检查 Tool Call—执行工具—写回结果”，直到模型不再调用工具并返回最终文本。

演示时建议按控制流看五个位置。

第一，`runtime.model_tools(ctx)` 在每一轮重新计算可见工具，而不是启动时固定一次。这样权限、模式或动态插件变化可以在下一轮生效。

第二，Assistant Message 必须先完整加入 `messages`，随后才能追加对应 Tool Result。模型下一轮既要看到“自己提出了什么调用”，也要看到“每个调用返回了什么”。只写 Tool Result 会破坏消息配对。

第三，`assistant.tool_calls or []` 是 Loop 的分支条件：为空表示本轮没有待执行动作，可以结束；非空表示必须把每个候选调用转成内部 `ToolCall`，交给 Runtime，而不是在 Loop 中直接分派业务函数。

第四，`result.to_model_message()` 只负责把 Runtime 的权威结果投影回模型协议。权限拒绝、参数错误和工具异常也走这条路径，因此模型能获得新的 observation，Loop 不会因为一次工具失败就失去消息结构。

第五，`MAX_STEPS` 是 Harness 强制执行的终止预算。模型可能每轮调用都合法，却始终不结束；Loop 不能把是否停止完全交给模型。真实 Harness 还会限制总耗时、工具次数和成本，本节先保留最小边界。

这段代码值得展示，是因为它划清了 Loop 与 Runtime：Loop 维护消息、轮次和终止条件；Runtime 维护工具查找、校验、权限和执行。业务工具增加以后，Loop 的主体不应出现新的 `if tool_name == ...`。

如果 DeepSeek thinking mode 开启，包含 Tool Call 的中间 assistant 消息还需要按照官方协议完整回传 `reasoning_content`。这属于 Provider 消息适配责任，应由上一节的 Gateway 或模型适配层统一处理，不应散落在每个工具里。

### 本小节结论

模型根据“当前上下文 + 当前可见工具 Schema”选择候选工具并生成参数。工具描述影响选择，Schema 影响参数，但两者都不能替代 Runtime 校验和授权。Tool Call 是提议，不是执行许可。

现在最小循环已经能跑起来，为什么还要专门学习工具治理？因为“模型选对了工具”只说明决策看起来合理，不代表这次调用有权限、参数安全、执行不会超时，也不代表失败后可以放心重试。只要工具连接数据库、文件系统或外部 API，Tool Call 就从内容生成跨入了真实副作用边界。

模型不能给自己授权，也不能根据一句“请求超时”判断写操作是否已经生效。这些规则必须由 Runtime 强制执行。因此下一步要解决的不是让模型更聪明，而是让每一次执行都可控、可恢复、可追踪。

## 1.5 工具治理：本节需要先建立哪些执行边界？

### 为什么模型已经选对工具，程序仍然不能直接执行？

先给结论：Tool Call 与用户输入一样，都是不可信数据。模型选对工具，只说明它提出了一个看起来合理的动作，不代表参数合法、用户有权限，也不代表失败以后可以安全重试。

这一小节只建立治理边界，不实现完整 Tool Runtime。学完以后，你需要知道一次调用必须经过哪些检查、这些检查为什么有先后顺序；Registry、Snapshot、统一 `invoke()`、并发和完整重试实现留到 2.2。

最小执行顺序是：

```text
接收 Tool Call
  → 校验工具名称和 Input Schema
  → 从可信上下文读取身份、权限和审批
  → 判断风险、超时与重试边界
  → 执行 handler
  → 校验 Output 或构造 Error
  → 生成带原始 tool_call_id 的 Tool Result
  → 写入 Trace，再交回 Agent Loop
```

顺序不能随意调整。权限检查如果发生在 handler 之后，越权副作用已经产生；Output Schema 如果在结果进入模型以后才校验，不稳定数据已经污染上下文；失败结果如果丢失 `tool_call_id`，Agent Loop 就无法判断它对应哪次调用。

### 1.5.1 哪些信息来自模型，哪些信息必须由 Harness 注入？

模型只应该填写完成业务动作所需的参数。例如查询订单时，它可以填写状态和日期；不能填写“我是管理员”“本次已经审批”或者“把风险改成 low”。

可以把两类数据明确分开：

|数据来源|典型字段|是否可信|
|---|---|---|
|Tool Call|订单号、查询条件、用户描述|不可信，必须经过 Input Schema 和业务规则校验|
|Execution Context|用户、租户、权限、审批记录、Trace ID|由登录态或服务间身份生成，Runtime 可以据此判断|
|Tool Definition|权限要求、风险等级、超时、是否允许重试|由工程师配置，模型不能修改|
|handler 结果|数据库或外部 API 返回的数据|仍需经过 Output Schema，不能直接进入模型|

最小可信上下文可以这样表达：

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class ExecutionContext:
    user_id: str
    tenant_id: str
    permissions: frozenset[str]
    trace_id: str
```

这段代码不负责鉴权，而是明确权限事实的来源。演示时重点看 `frozen=True`：上下文由 Harness 在调用前创建，工具只能读取，不能在执行过程中把自己升级成更高权限。

这里最重要的验收不只是“返回了权限错误”，而是证明权限不足时 handler 调用次数为零。只有这样，才能确认拒绝发生在副作用之前。

### 1.5.2 超时以后，为什么不能统一重试？

因为超时只表示调用方没有及时拿到结果，不代表业务动作一定失败。

|场景|本节先记住的处理边界|
|---|---|
|查询订单遇到连接抖动|只读且参数不变，可以在预算内有限重试|
|取消订单请求超时|可能已经取消，不能直接再执行一次|
|参数校验失败|不应由 Runtime 原参数重试，应把安全错误返回 Agent Loop|
|权限或审批不足|必须停止，不能靠重试绕过|
|handler 返回结构错误|转成稳定错误，不能把原始对象直接交给模型|

所以要区分两种“再试一次”：

```text
Runtime 重试：工具和参数不变，只恢复明确的瞬时故障
Agent Loop 修正：模型阅读 Tool Result 后，重新选工具、改参数或询问用户
```

2.1 只要求理解这条边界。下一节会把幂等性、超时、取消、重试预算和状态未知接入统一 Runtime。

### 1.5.3 审计和 Trace 在本节要掌握到什么程度？

本节不实现审计数据库，只要求知道一次工具调用至少要能够回答：

- 属于哪个 `trace_id`；
- 对应哪个 `tool_call_id`；
- 调用了哪个工具；
- 最终是成功、拒绝还是失败；
- 失败发生在参数、权限还是执行阶段；
- 耗时多久，是否发生重试。

Trace 用来还原 Agent 任务的运行过程；审计用来回答谁以什么身份触发了什么动作；Tool Result 用来把结果送回模型。三者可以关联，但不能混成一份把原始参数、敏感结果和 Python 堆栈全部复制进去的日志。

### 本小节结论

2.1 的重点不是实现 Tool Runtime，而是先建立执行不变量：模型参数不可信，身份权限来自 Harness，拒绝必须发生在 handler 之前，写操作不能因超时盲目重试，所有结果必须保留原始 `tool_call_id`。

下一节会把这些不变量实现为 ToolDefinition、Registry、Snapshot 和统一 Runtime。本节最后只再看一个更高层的问题：为什么工具能力不应该直接写进 Agent Loop？
## 1.6 DeepSeek Harness 的工具插件化设计

### 1.6.1 DeepSeek Harness 是什么，本节为什么要看它？

[DeepSeek Harness](https://github.com/deepseek-ai/deepseek-harness) 是一套用于组织模型、Agent Loop、工具、上下文和运行能力的 Agent Harness。模型负责提出下一步动作，Harness 负责提供当前能力、维护状态并控制动作怎样执行。

这一小节不学习 Cordis 的完整 API，也不实现插件管理器。这里只回答一个与 Function Calling 直接相关的问题：

> 当工具越来越多时，怎样新增或移除工具，而不修改 Agent Loop 的主体？

如果 Loop 中不断出现下面的分支：

```python
if tool_name == "search_orders":
    ...
elif tool_name == "cancel_order":
    ...
```

那么每增加一个业务能力，都要修改核心循环。工具定义、业务执行和循环控制会逐渐耦合，测试与下线也越来越困难。

插件化希望保持相反的关系：

```text
工具插件贡献 ToolDefinition
  → Runtime 负责注册和受控执行
  → Agent Loop 只处理 Tool Call 与 Tool Result
```

### 1.6.2 它与 `pi` 分别提供了什么学习视角？

|参考|本节重点学习什么|本节不展开什么|
|---|---|---|
|`pi 0.83.0`|Tool、AgentTool、before/after Hook、Tool Result 与 Agent Loop 顺序|完整 Coding Agent 和扩展生态|
|DeepSeek Harness|Service、插件依赖、生命周期和可撤销注册|Cordis API、打包、热更新与前端插件|
|本课程 Python 实现|保留相同职责边界，并与后续 Tool Runtime 连接|逐行翻译 TypeScript|

从 `pi` 中，我们看清一次 Tool Call 怎样进入 Loop、执行并回写；从 DeepSeek Harness 中，我们看清工具能力怎样装配到一个长期运行的 Harness，而不让插件直接修改 Loop。

### 1.6.3 一个最小工具插件需要表达什么？

先解释四个概念：

|概念|解决的问题|
|---|---|
|Registry|已经装配的工具到哪里查找|
|Plugin|谁向 Harness 贡献这项能力|
|Service|插件依赖 Tool Runtime、LLM 等什么运行能力|
|Dispose|插件卸载时怎样撤销注册和清理资源|

用 Python 表达最小接口，可以压缩成下面这段代码：

```python
from collections.abc import Callable
from dataclasses import dataclass
from typing import Protocol


Dispose = Callable[[], None]


@dataclass(frozen=True)
class PluginContext:
    register_tool: Callable[[ToolDefinition], Dispose]


class ToolPlugin(Protocol):
    name: str
    requires: frozenset[str]

    def setup(self, ctx: PluginContext) -> list[Dispose]: ...


class OrderToolsPlugin:
    name = "order-tools"
    requires = frozenset({"tools"})

    def setup(self, ctx: PluginContext) -> list[Dispose]:
        return [ctx.register_tool(SEARCH_ORDERS)]
```

这段代码只描述插件与 Harness 的边界，不实现 Registry。演示时重点看三个位置。

第一，`requires={"tools"}` 表示插件依赖 Tool Runtime Service，只有依赖就绪以后才能加载。

第二，`setup()` 只贡献工具，不启动新的 Agent Loop。新增订单工具不会改变循环如何处理 Tool Call 和 Tool Result。

第三，`register_tool()` 返回 `Dispose`。谁注册能力，谁就保存撤销动作；卸载插件时可以删除工具、事件监听器或其他资源，避免重载后留下重复注册。

插件化真正解决的不是“把代码拆成多个文件”，而是依赖和生命周期：

```text
等待依赖
  → 加载插件
  → 注册工具
  → 工具仍经过统一 Runtime
  → 卸载时执行 Dispose
```

Registry 怎样拒绝重名、怎样管理版本和生成本轮快照，属于 2.2；权限、超时和 Trace 怎样覆盖所有插件工具，也由统一 Runtime 处理。2.1 只保留一个原则：工具可以插拔，执行入口不能分叉。

### 本小节结论

插件贡献能力，Runtime 约束执行，Agent Loop 推动状态。三者分离以后，新增和下线工具不需要修改核心循环；插件也不能因为完成了注册，就绕过参数校验、权限和结果回写。
## 三、本节总结：Function Calling 最终解决了什么问题？

Function Calling 把模型的自然语言决策变成结构化候选动作。它没有让模型获得函数、数据库或系统权限，只建立了下面这条协议闭环：

```text
工程师定义 Tool
  → 模型看到名称、描述和 Input Schema
  → 模型生成带 ID 的 Tool Call
  → 应用校验并调用工具
  → 应用生成带原始 tool_call_id 的 Tool Result
  → Agent Loop 把结果交给模型继续决策
```

本节需要真正掌握五个判断：

1. Tool Call 是不可信的动作提议，不是执行许可；
2. 名称和描述影响模型是否选对工具，Input Schema 约束模型可以填写什么；
3. Output Schema 和 Error Schema让结果成为稳定协议，而不是随意字典；
4. 模型可见 Tool 与 Runtime 可执行 AgentTool 必须分离，handler 不会暴露给模型；
5. 无论成功还是失败，Tool Result 都必须保留原始 `tool_call_id`。

工程师负责工具粒度、字段语义、可信数据来源、风险等级和结果协议；AI 可以生成 Schema、数据类和适配代码，但不能替业务系统决定这些边界。

到这里，2.1 已经完成“模型怎样申请工具调用”的协议基础。下一节才进入 Tool Runtime：工具怎样注册、发现和冻结版本，所有调用怎样经过统一 `invoke()`，以及参数、权限、超时、重试、审计和 Trace 怎样真正落地。

## 四、课堂练习与验收：怎样证明自己掌握了 Function Calling？

### 4.1 口头验收：能不能两分钟讲清协议闭环？

不看代码，回答下面五个问题：

1. Function Calling 与普通函数调用有什么区别？
2. 模型侧 Tool 为什么没有 `execute()`？
3. Input、Output 和 Error Schema 分别约束什么？
4. 为什么权限和审批不能作为模型参数？
5. 两个同名工具调用乱序完成时，`tool_call_id` 怎样防止结果错配？

### 4.2 代码验收：能不能完成一次最小调用？

为 `search_orders` 完成下面四步：

1. 定义名称、描述和 Input Schema；
2. 生成模型可见的 Tool JSON，确认其中没有 handler、权限和内部依赖；
3. 构造两条不同 `tool_call_id` 的 Tool Call；
4. 分别生成 Tool Result，并断言结果 ID 与原调用一致。

练习只需要使用模拟订单数据，不要求实现 Registry、Snapshot、完整权限系统或重试框架。

### 4.3 审查验收：能不能发现协议错误？

检查一段 AI 生成的 Function Calling 代码，至少识别下面四类问题：

- 把 `user_id`、`role` 或 `approved` 放入 Input Schema，让模型自己填写；
- 把完整 ToolDefinition 或 handler 信息发送给模型；
- 直接相信参数 JSON，没有经过 Pydantic 校验；
- Tool Result 只返回内容，没有原始 `tool_call_id`。

发现以后，要说明错误会影响模型选择、可信边界还是结果关联，并给出相应测试。

### 4.4 迁移验收：能不能定义一个新工具？

把 `search_orders` 换成 `get_service_status`。只允许查询 `api`、`worker` 和 `scheduler`，不允许模型生成任意 Shell 命令。

你需要重新设计工具名称、描述、Input Schema、Output Schema 和 Error Schema，并说明它是只读还是写操作、需要什么权限和风险等级。做到这里即可，Registry、Snapshot 和完整 Runtime 实现留到下一节。
