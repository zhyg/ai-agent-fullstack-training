# 2\.4 工具治理和安全边界：用 Python 把 AI 的动作申请变成可控执行

> 核心路线：运行结果 → 权限状态机 → Python Runtime → 四项核心测试 → 验收
贯穿案例：订单售后 Agent 查询订单，并在用户确认后发起退款



## 一、导论

### 1\.1 承接上一节：MCP 已经接通，为什么工具仍然不能直接执行？

先给结论：**MCP 解决的是“能力如何被标准化发现与调用”，而工具治理解决的是“当前这一次调用，有没有资格进入真实世界”。协议连通，不等于安全边界已经建立**



当远端工具接入订单 MCP Server 后，通常会同时暴露以下能力：

- `get_order`：查询订单

- `create_refund`：创建退款

- `export_customer_data`：导出客户资料

- `run_sql`：执行分析 SQL

- `run_shell`：处理运维任务



从 MCP 协议视角看，这些只是名称、描述、参数 Schema 和返回结果。协议本身天然不具备以下判断能力：

- 当前 Agent 是只读客服，还是财务 Agent？

- 当前登录用户属于哪个租户？

- 用户是否已明确确认了 399 元这笔退款？



MCP Server 可以提供自身鉴权，但 Host 侧仍然必须基于本轮任务上下文、当前身份和业务状态，对能力进行二次收紧。



如果省略这一层治理，最常见的四类故障便会发生：

1. 权限逃逸：一个只读客服 Agent 因模型发现了 `create_refund` 工具，被 Prompt 注入诱导发起了非授权退款。

2. 参数篡改：用户确认退款 100 元，下一轮模型将参数悄悄改成 399 元，而旧的 `approved=true` 审批状态仍被系统接受。

3. 幂等缺失：支付接口已完成退款，但响应超时，Runtime 自动重试导致重复退款。

4. 绕过规则：调试人员开启 `bypass` 模式后，宽泛放行规则覆盖了原本不可绕过的删除规则，造成误删。

这些问题的共同本质是：**模型只产生了“候选动作”，系统却错误地将候选动作当成了“执行许可证”。**



### 1\.2 治理流程：从候选动作到可控执行

本节从上一节的终点继续推进：

```Plaintext
MCP / 本地 Tool 已接入
        ↓
Harness 根据任务上下文收敛模型可见的工具集
        ↓
模型提出 Tool Call（此时仍为“候选动作”）
        ↓
ToolRuntime 进行综合决策：参数校验、身份确认、权限判定、审批状态、风险等级
        ↓
仅当决策结果为 allow 时，才进入 Handler 执行
        ↓
执行结果经脱敏与审计后，输出为 Tool Result
        ↓
Agent Loop 根据结果决定下一步：继续 / 暂停 / 修正参数 / 人工接管
```

这个流程的核心在于：**在执行前插入一道强制检查点**，将模型的“意图”与系统的“行动”彻底解耦。



### 1\.3 本节的学习边界：不做大而全，做最小可用的治理骨架

需要提前管理好学习预期：本节不是要再造一套 IAM 权限平台，也不要求实现生产级容器沙箱。

我们的目标是掌握一套**最小而完整的治理骨架**——你只需要搞清楚：

- **策略放在哪里**（规则定义的位置）

- **可信事实从哪里来**（身份、租户、审批状态等上下文）

- **拒绝发生在哪个时机**（执行前拦截，而非执行后补救）

- **结果回写到何处**（审计日志、状态回滚、Loop 决策）

并且，能够用测试明确验证副作用的边界。



上一节回答了 “**能力怎么进来**”（MCP 接入与 Harness 收敛）；

这一节回答 “**动作怎么出去**”（Runtime 裁决与安全执行）。



接下来我们先不讲抽象术语，直接运行最终演示——让大家先看见一个“被治理过的 Agent”应该表现成什么样，再深入拆解每一块实现细节。

## 二、先看演示结果：什么叫“可控执行”？

先给结论：工具治理的目标，**不是让所有调用都成功，而是让应该执行的动作成功，让不该执行的动作在副作用发生之前停下来**，并给 Agent Loop 返回一个稳定、可解释、可追踪的结果。

完整工程位于 `python-tool-governance-v11` 目录。默认运行离线演示，无需模型 API，不连接真实支付系统，也不会启动真实 Shell：

```Bash
cd python-tool-governance-v11
python -m pip install -r requirements.txt
python tool_governance_demo.py
python -m pytest -q
```



运行 `python tool_governance_demo.py` 会得到六次调用和一条副作用统计，输出如下：

```JSON
{"tool_call_id":"call_01","tool_name":"get_order","ok":true,"action":"allow","code":"OK","content":{"status":"paid","refundable":399.0,"customer_email":"***@***","access_token":"***"}}
{"tool_call_id":"call_02","tool_name":"create_refund","ok":false,"action":"confirm","code":"APPROVAL_REQUIRED","content":"需要确认本次具体动作"}
{"tool_call_id":"call_03","tool_name":"create_refund","ok":true,"action":"allow","code":"OK","content":{"refund_id":"ref_9001","idempotency_key":"call_03","tenant_id":"tenant_a","order_id":"ord_1001","amount":399.0,"status":"accepted"}}
{"tool_call_id":"call_04","tool_name":"create_refund","ok":false,"action":"deny","code":"INVALID_ARGUMENT","content":[{"path":"user_id","message":"Extra inputs are not permitted"},{"path":"approved","message":"Extra inputs are not permitted"}]}
{"tool_call_id":"call_05","tool_name":"run_shell","ok":false,"action":"deny","code":"DENY_RULE","content":"命中 deny 规则"}
{"tool_call_id":"call_06","tool_name":"create_refund","ok":false,"action":"deny","code":"PLAN_MODE_DENIED","content":"plan 模式禁止写操作和 Shell"}
{"side_effects":{"refund_executions":1,"shell_executions":0},"audit_records":8}
```

下面逐条解释这六条结果各自证明了什么。

### 2\.1 六条结果逐条解读

第一条（查询订单成功）

`get_order` 返回 `allow`，但注意：结果中的邮箱变成了 *`@`*，Token 变成了 `***`。
这证明了一个关键原则：Handler 成功取得完整数据，和这些数据可以进入模型上下文，是两件不同的事。 Runtime 必须为模型、用户、日志和审计分别定义不同的结果视图，不能把原始对象一份多发。



第二条（退款申请 — 需人工确认）

`create_refund` 返回 `confirm`，而非 `allow`。订单存在、金额合法、用户也有 `refund:create` 权限，但退款 Handler 此时并未执行。
这说明：权限只回答“有没有资格申请”，人工确认回答“是否同意这一笔具体动作”——两者不能合并。



第三条（退款执行成功）

使用服务端生成的审批记录，绑定了用户、租户、工具名、规范化参数摘要、过期时间和一次性状态。所有字段与当前退款完全一致，Runtime 才执行 Handler。
副作用统计显示 `refund_executions=1`，证明真实退款只发生了一次。



第四条（参数伪造被拒绝）

模型尝试伪造 `user_id="admin"` 和 `approved=true`。Pydantic Schema 使用 `extra="forbid"`，两个未知字段在进入权限判断之前就被拒绝。
这里的意义在于：阻止模型把授权事实伪装成普通业务参数，而非仅仅追求 JSON 格式的“美观”。



第五条（Bypass 模式下仍被拒绝）

在 `bypassPermissions` 模式下尝试执行 `rm -rf /tmp/demo`，依然命中 `DENY_RULE`，且 `shell_executions=0`。
这证明：Deny 规则必须拥有比调试便利模式更高的优先级。否则一旦开发者为了联调打开 Bypass，所有所谓的“硬边界”都会沦为一纸空文。



第六条（Plan 模式下写操作被拒绝）

用户权限和退款参数均未变化，仅将执行模式切换为 `plan`。Runtime 在审批和普通 allow 规则之前便拒绝了写操作。
这证明：Plan 模式不能只写在 System Prompt 里要求模型“请不要修改”，而必须成为执行层可验证的只读契约。



### 2\.2 副作用统计：评估治理效果的双重证据

最后的副作用统计是整个演示最重要的结果：

```Markdown
{"side_effects":{"refund_executions":1,"shell_executions":0},"audit_records":8}
```



很多不安全实现也能打印 `PERMISSION_DENIED`，但可能在打印错误之前已经调用了支付接口。课程验收必须同时看两类证据：

只有两类证据一致，才能证明**拒绝发生在正确的位置**——在副作用产生之前，而非之后。



### 2\.3 从六条结果反推 Runtime 契约

观察上述结果，可以反推出 Runtime 至少需要一份稳定的 ToolResult 契约，而不能让每个 Handler 自由返回字符串、字典或异常：

```Python
@dataclass(frozen=True, slots=True)
class ToolResult:
    tool_call_id: str
    tool_name: str
    ok: bool
    action: DecisionAction
    code: str
    content: Any
    retryable: bool = False
```

各字段的设计考量：

- **`ok`**** 与 ****`action`**** 不可合并**
`ok` 表示工具是否成功完成，`action` 表示治理层的决策（`allow` / `deny` / `confirm`）。例如 `confirm` 不是执行失败，而是尚未获得执行许可；`TIMEOUT_UNKNOWN` 也不能简单视为失败，因为真实支付可能已经成功。

- **`code`**** 给程序，****`content`**** 给模型或用户**
程序根据 `APPROVAL_REQUIRED` 暂停并打开确认界面，而不是从“需要确认本次具体动作”这句话里猜测语义。文案可以变化，错误码保持稳定。

- **`retryable`**** 不由模型判断**
它应来自工具策略和失败类型：只读瞬时失败可能为真，权限拒绝、参数错误和非幂等写超时必须为假。即便字段为真，Agent Loop 仍需受最大轮数、总 Deadline 和预算约束，不能无限重试。

- **`tool_call_id`**** 是关键协议关联键**
它不仅是日志追踪字段，更是 Provider Tool Call 与 Tool Result 的关联键。模型同一轮并行发起多个调用时，Runtime 必须将每条结果返还给正确的调用；审批、审计和幂等也围绕此 ID 建立关联。



### 2\.4 为什么先运行离线治理，再连接真实模型？

治理层的输入和输出是确定的：给定 Tool Call、`ExecutionContext`、策略和业务状态，应当得到确定决策。因此最有效的开发顺序是：

1. 离线构造测试用例，直接观察 Runtime 行为，而非先调用模型再在一长串对话中猜测权限是否生效。

2. 离线模式可稳定复现越权、参数伪造、审批改参、Plan 和 Bypass 等边界场景。

3. 真实模型模式用于验证 Provider 格式、上下文回填和多轮 Loop。

两种模式共用同一个 `ToolRuntime.invoke()`，才能同时获得确定性测试与真实集成可信度。

> 如果一开始就依赖模型，测试结果会混入模型选择差异、网络延迟、限流和输出波动。一次退款没有发生——究竟是权限系统拦截成功，还是模型压根没选择退款工具？离线测试把这些变量剥离，让我们能明确证明治理逻辑；随后真实 Provider 验收再证明集成没有旁路。
> 
> 



### 2\.5 模型视角 vs 开发者视角

|对比维度|模型视角（AI 消费）|开发者视角（工程师排障）|
|---|---|---|
|**看到什么**|结构化 JSON，仅含决策所需的最小必要字段（状态、金额、错误码）|完整 Trace、决策链路、规则命中记录、原始入参与出参|
|**看不到什么**|租户 ID、用户 ID、Token、PII（邮箱/手机号）、权限元数据、审计日志|—（所有数据可见，但需独立鉴权）|
|**数据用途**|决定下一步调用什么工具、填什么参数、是否向用户追问|排障定位、审计追溯、性能分析、策略调优|
|**可以外包给 AI**|工具选择、参数填充、错误码→重试策略、结果语义理解|日志摘要生成、异常模式初步分类、关联 Trace 的排查建议|
|**必须工程师掌控**|—（模型不应触碰的已在上方“看不到”列）|审计记录写入、决策最终归因、Runtime 契约变更、敏感数据访问权限|
|**数据结构特征**|稳定、版本化、向后兼容，字段增删不影响模型|可扩展、可关联、保留原始上下文，字段增删不影响线上模型协议|
|**交付给谁**|Agent Loop / LLM 上下文|监控面板、日志系统、工程师终端|



**核心原则**：

> 模型只消费“经过治理的结果”，开发者看到“完整的决策过程”。  
> 
> 两者的数据管道必须隔离——**同一个 ToolResult，派生两种视图，而非共享一份原始对象。**
>

## 三、学完以后有什么用？先把人的责任和掌握标准说清楚

**先给结论：**学完本节，你应该能把一个“模型会选择工具”的 Demo，升级成一个 “**动作有边界、失败有语义、结果有证据”的业务 Agent**。你不需要比 AI 更快地默写几百行 Runtime，但必须能**决定边界、审查实现、设计验收**。



传统应用里，前端按钮、后端路由和权限中间件通常预先限定了用户能做什么。Agent 应用多了一层不确定性：模型会根据自然语言动态选择工具、生成参数、连续调用多个动作，还可能受到 Prompt 注入影响。



因此，**Agent 开发工程师的价值，不是把函数注册给模型，而是把不确定的动作申请压进确定的工程边界。**



### 3\.1 交付能力：五类可验收的产出

本节的目标，不是让你知道“工具调用有风险”，而是让你能交付一套可运行、可测试、可审计的工具治理机制。

完成本节后，你应能交付以下五类结果：

|交付能力|具体产物|验收证据|
|---|---|---|
|工具风险建模|`ToolPolicy`、读写分类、风险等级、权限与审批要求|策略表与代码一致，边界案例有说明|
|可信上下文设计|`ExecutionContext`、身份透传、租户与权限来源|模型参数无法伪造身份，跨租户测试被拒绝|
|确定性执行治理|唯一 `ToolRuntime.invoke()`、三态决策和固定优先级|deny、plan、白名单、RBAC 和审批顺序可测试|
|副作用与恢复控制|超时、重试、幂等键、队列和人工兜底|写操作不盲重试，未知状态可追踪|
|结果与证据治理|Tool Result、脱敏、稳定错误码和审计记录|敏感信息零泄漏，Trace 与 Tool Call 可关联|

这些产物解决的是岗位中的真实问题：

- 拿到一个新工具时，你要判断它究竟是只读还是会改变外部状态；

- 拿到一个 AI 生成的 Hook 时，你要发现权限判断是否放在 Handler 之后；

- 业务提出“确认一次就别再弹窗”时，你要判断这是低风险会话白名单，还是会把退款审批变成永久通行证；

- 支付请求超时时，你要知道应该查状态还是重放。



工具治理不是给每个工具加几个 `if`，而是建立一条完整调用链：

text

```Plain Text
可信身份与租户上下文
        ↓
策略判断
        ↓
统一执行与副作用控制
        ↓
结果脱敏与审计证据
```

其中，业务策略会变化；但统一入口、执行顺序、恢复机制和审计链路应保持稳定。



### 3\.2 AI 的边界：哪些可以辅助，哪些必须人决定

上一节讲的是：工程师要交付哪些机制。
这一节讲的是：这些机制中的规则，谁有权定义和承担责任。

AI 可以根据已经确认的规则生成代码、补充测试、修复局部实现和重构重复逻辑；但它不能替组织决定权限、风险阈值、确认范围或数据边界。

可以这样理解三者分工：

```Plain Text
业务 / 产品 / 法务 / 安全
定义规则、阈值、责任与边界
        ↓
工程师
将规则实现为可测试、可恢复、可审计的系统
        ↓
AI
在明确规则内协助生成和维护代码
```

因此，正确的提示不是：请根据上下文判断这笔退款是否需要审批。

而是：当策略规定该操作需要审批时，
系统进入 PLAN 状态，等待具备审批权限的用户确认。



前者把风险判断交给模型；后者让系统执行已被人确认的规则。

人决定规则和责任，工程保证规则被稳定执行，AI 在边界内提高实现效率。

## 四、第一阶段：工具分级与权限模型——先决定谁可以申请什么动作

先给结论：（别等事情已经做了一半，才想起来问‘这人有没有资格做’。要在动手干真事之前，就先把门关好。）

权限治理不是在 Handler 执行失败后返回“无权限”，而是在**任何真实副作用发生之前**，根据服务端可信身份、工具策略和本次业务事实，返回 `allow`、`deny` 或 `confirm`。



本阶段结束时，学员应能完成三件事：

1. 为工具写出最小策略表；

2. 把模型参数与可信身份分离；

3. 把白名单、RBAC、审批和权限模式组合成有固定优先级的状态机。



### 4\.1 为什么必须先给工具分级？

工具分级的目的是让不同风险的动作走不同的执行路径。天气查询、读取订单、导出客户数据、创建退款和删除生产文件都是 Tool，但它们的副作用、敏感度、可逆性和恢复成本完全不同。



最小策略表至少回答七个问题：

1. 工具是否改变外部状态？

2. 它读取的数据是否敏感，即使只读是否仍然高风险？

3. 当前身份需要哪项业务权限？

4. 影响范围是单条资源、一个租户，还是整个环境？

5. 失败后能否安全重放，是否真正幂等？

6. 是否必须由用户或审批人确认具体参数？

7. 运行时使用什么超时、并发和审计策略？



设计工具之前，我会指定这样一张规格表，订单案例可以先写成一张最小规格表：

|工具|副作用|数据敏感度|风险|权限|人工确认|自动重试|
|---|---|---|---|---|---|---|
|`get_order`|只读|中，含客户信息|中|`order:read`|否|瞬时失败可有限重试|
|`create_refund`|写，产生资金变化|中|高|`refund:create`|必须绑定订单与金额|非幂等时禁止盲重试|
|`run_shell`|取决于命令，影响面可能很大|高|中到极高|`shell:run`|危险动作确认或直接拒绝|默认不重试|

风险判断应基于真实副作用和数据价值，而非函数名、HTTP 方法或模型描述。



Python 中，策略被写进不可变对象：

tool\_governance\_demo\.py line 86

```Python
@dataclass(frozen=True, slots=True)
class ToolPolicy:
    effect: Effect
    risk: Risk
    permission: Permission
    requires_approval: bool
    timeout_seconds: float
    max_retries: int
    idempotent: bool
```

策略要靠近代码，因为运行时真正读取的是这些字段。单独的 Word 或 Spec 如果没有测试约束，很容易与实现漂移。必须始终成立的规则。



### 4\.2 白名单、RBAC 和人工确认为什么不能合成一个判断？

先给结论：

白名单、RBAC 和人工确认必须连续执行，但不能合并成一个 `is_allowed`。它们分别控制 Agent 的能力范围、当前主体的业务资格和这一次具体副作用。

|机制|判断对象|可信输入|订单案例|失败后的动作|
|---|---|---|---|---|
|工具白名单|Agent 本轮能力面|Agent 配置、租户策略、任务策略|只读客服看不到退款工具|本轮不应继续尝试|
|RBAC|当前主体资格|鉴权系统生成的角色与权限|普通客服没有 `refund:create`|换有权限主体或结束|
|人工确认|一次具体动作|服务端审批记录|用户确认 `ord_1001` 退款 399 元|暂停并进入确认流程|

管理员拥有退款权限，不代表所有 Agent 都应该看到退款工具；退款工具在白名单里，不代表当前客服有权限；客服有权限，也不代表 Runtime 可以未经确认直接调用支付接口。



#### 4\.2\.1 工具白名单：先限制 Agent 本轮拥有什么能力

白名单是一组由 Harness 根据 Agent 配置、租户策略、当前任务和运行环境计算出的工具名称。它控制的是能力面，不是用户身份。

例如，同一用户进入“订单查询助手”和“售后退款助手”，身份权限不变，但两个 Agent 的工具集合不同。

如果把 Registry 中所有工具都交给模型，再期待 RBAC 最后拦截，虽然部分越权调用仍会被拒绝，但模型的候选动作空间已被扩大——Prompt 注入可不断诱导危险工具，工具 Schema 占用 Context，模型也更容易误选。

白名单必须出现两次。

第一次发生在模型调用前，称为**发现期白名单**。发现期白名单（模型调用前）：Harness 只把必要的工具 Schema 放进模型上下文：

```Python
def model_tools(self, context: ExecutionContext) -> list[dict[str, Any]]:
    return [
        tool.to_model_tool()
        for tool in self._tools.values()
            if tool.name in context.allowed_tools
    ]
```

这一步的结果可以直接验收：当 `allowed_tools={"get_order"}` 时，传给 DeepSeek 的 tools 列表中不应出现 `create_refund`。

第二次发生在 `ToolRuntime.invoke()` 内，称为**执行期白名单**：执行期白名单（`ToolRuntime.invoke()` 内）：即使模型曾经看到过该工具，执行时也要重新授权

```Python
if tool.name not in context.allowed_tools:
    return PermissionDecision(
        DecisionAction.DENY,
        "TOOL_NOT_ALLOWED",
        "工具不在本轮执行白名单",
        "whitelist",
    )
```

只做发现期过滤，无法阻止旁路和过期调用；只做执行期检查，会把不必要的危险工具暴露给模型。正确关系是：**发现时收敛能力，执行时重新授权。**

白名单不要写死在 Prompt 中，也不要由模型自行选择。它应由 Harness 使用可信配置计算，并把同一结果同时用于模型投影和 Runtime Context。



#### 4\.2\.2 RBAC：再判断当前主体有没有业务资格

RBAC 把组织中的岗位映射成权限集合。客服角色可能拥有 `order:read`，高级售后拥有 `refund:create`，运维拥有受限的 `shell:run`。



角色属于组织管理概念，工具属于执行概念。角色名称、继承关系和人员归属可能经常变化，而 `refund:create` 这样的业务能力相对稳定。



Runtime 不直接判断角色名称，而是让认证层把角色展开成细粒度权限：

```Python
# 不推荐：角色名称渗透到每个工具。
if context.role in {"admin", "senior_support"}:
    ...
```

更稳定的做法是让认证与授权层把角色展开成细粒度权限，Runtime 只检查工具声明的权限：

```Python
if tool.policy.permission not in context.permissions:
    return PermissionDecision(
        DecisionAction.DENY,
        "PERMISSION_DENIED",
        f"缺少业务权限 {tool.policy.permission}",
        "rbac",
    )
```

Web 鉴权中间件先验证 JWT/Session/API Key，从 IAM 获取权限，再创建不可由模型修改的 `ExecutionContext`。



> RBAC 只完成粗粒度资格判断。拥有 `refund:create` 不代表能退任意租户、任意金额、任意状态的订单——资源归属、额度和状态属于后续业务 precheck。
> 
> 



#### 4\.2\.3 人工确认：最后确认这一笔具体副作用

人工确认不是“是否继续”的通用按钮，而是让用户确认工具、业务对象、关键参数和影响范围：

```Plaintext
工具：create_refund
订单：ord_1001
金额：399 元
原因：商品存在质量问题
结果：提交后将创建真实退款
```

模型可能误解用户意图，也可能在多轮上下文中改变参数。即使当前用户有退款权限，系统仍然需要证明用户同意的是这一笔动作，而不是抽象的“允许退款”。



PermissionEngine 返回 `confirm + APPROVAL_REQUIRED`，Runtime 保证 handler 零调用；Agent Loop 暂停，把待确认动作交给 Web、CLI 或审批工作台；确认服务根据已认证用户生成 `approval_id`；下一次进入 Runtime 时重新校验用户、租户、工具、参数摘要、过期时间和一次性状态。

```Plaintext
Tool Call
→ PermissionEngine 返回 confirm
→ Agent Loop 暂停
→ 可信界面展示动作
→ 用户确认并生成 approval_id
→ 原参数重新进入 Runtime
→ 审批完全匹配才 allow
```

模型不能生成 `approved=true`，也不能把一句“用户已经确认”当成事实。非交互 `dontAsk` 模式遇到强制确认时必须拒绝；高风险审批不能被普通 allow、会话白名单或 bypass 跳过。测试要覆盖参数变化、跨用户、跨租户、过期和重放。



这里先讲清人工确认在完整授权链中的位置。4\.5 还会继续深入一个更具体的实现问题：确认记录为什么必须绑定规范化参数，而不能只保存一个布尔值。



到这里，三层准入关系已经完整：白名单收敛 Agent 能力，RBAC验证主体资格，人工确认绑定一次具体动作。三层都依赖可信上下文，因此下一节要回答这些用户、租户、权限与审批 ID究竟从哪里来，哪些值绝对不能相信模型。



### 4\.3 身份透传时，哪些信息可以相信？

模型可以提供订单号、退款金额和退款原因——它们是**业务候选参数**。

模型不能提供用户 ID、租户 ID、角色、权限和审批状态——它们是**授权事实**。

可信上下文应由 Web 鉴权中间件在验证 JWT/Session/API Key 后创建：

```Python
@dataclass(frozen=True, slots=True)
class ExecutionContext:
    trace_id: str
    user_id: str
    tenant_id: str
    mode: PermissionMode
    permissions: frozenset[Permission]
    allowed_tools: frozenset[str]
    approval_id: str | None = None
```

`ExecutionContext` 与工具参数分离有三个收益：

1. **模型无法伪造身份**：Schema 中没有 `user_id` 和 `tenant_id`，即使模型生成未知字段，Pydantic 也会在 Handler 前拒绝。

2. **结构上防止跨租户**：Handler 查询资源时强制使用 `context.tenant_id`。

3. **测试可独立替换 Context**：构造“同一 Tool Call、不同用户权限”的场景。



常见错误：

```Python
# 错误示意：模型能够伪造授权事实。
class RefundArgs(BaseModel):
    order_id: str
    amount: float
    user_id: str
    tenant_id: str
    approved: bool
```

这种代码即使 Schema 校验全部通过，仍然不安全，**因为 Schema 只能证明值的形状，不能证明值来自可信来源。**`user_id` 是字符串并不等于它属于当前登录用户，`approved=True` 是布尔值也不等于真实用户完成了确认。



这一节把“信任谁”讲清楚了：模型只提交候选参数，认证层和审批系统提供授权事实。但这些对象如果只是散落在函数参数里，仍然容易被不同入口绕开。下一节把它们装进 Python Harness，让模型侧协议、运行侧策略和唯一执行入口形成结构化边界。



### 4\.4 怎样把策略接入 Python Harness？

本节我们参考 Pi 的生命周期顺序，在 Python 中建立同构对象：

- `ToolDefinition`：工具契约、Pydantic 参数模型、策略、handler 和业务预检查；

- `ExecutionContext`：服务端可信身份与本轮能力；

- `PermissionEngine`：返回 allow、deny 或 confirm；

- `ToolRuntime.invoke()`：唯一执行入口；

- `AuditSink`：保存决策和执行证据。



这组对象不要让 AI 凭空设计。工程师先写出对象关系和硬性要求，再用下面的局部提示词生成样板：

```Markdown
请只生成 Python 数据模型与接口，不实现业务 handler：

1. 使用 Python 3.12、`dataclass(frozen=True, slots=True)` 和 Pydantic 2；
2. `ToolDefinition` 包含 name、description、Pydantic 参数模型、ToolPolicy、handler、precheck 和 canonical_target；
3. `ExecutionContext` 包含服务端可信的 trace_id、user_id、tenant_id、permissions、allowed_tools、mode 和 approval_id；
4. `to_model_tool()` 只能返回名称、描述和 JSON Schema，禁止暴露 handler、权限和审批；
5. 给出类型注解，不要实现 PermissionEngine 和 ToolRuntime；
6. 最后解释模型侧对象与运行侧对象的边界。
```

这个提示词只生成当前层需要的对象，不让 AI 一次跨到权限、执行和测试。生成后先检查字段归属，再进入下面的投影代码。



投影边界：`to_model_tool()` 只返回名称、描述和 JSON Schema，禁止暴露 Handler、权限和审批：

```Python
@dataclass(frozen=True, slots=True)
class ToolDefinition:
    name: str
    description: str
    parameters_model: type[StrictArgs]
    policy: ToolPolicy
    handler: Handler
    canonical_target: CanonicalTarget
    precheck: Precheck | None = None

    def to_model_tool(self) -> dict[str, Any]:
        return {
            "type": "function",
            "function": {
                "name": self.name,
                "description": self.description,
                "parameters": self.parameters_model.model_json_schema(),
            },
        }
```

> 模型侧：只有名称、描述和 JSON Schema；运行侧：持有 Handler、超时、重试、权限、风险和审批策略。
> 
> 



所有调用必须经过同一入口：

```Python
result = await runtime.invoke(
    ToolCall("call_01", "get_order", {"order_id": "ord_1001"}),
    context,
)
```

未来无论 Tool Call 来自 DeepSeek、测试、CLI、定时任务还是 MCP Adapter，都调用这一个 `invoke()`。

如果不同入口复制自己的鉴权和分发逻辑，规则迟早会漂移：模型入口检查 RBAC，CLI 忘了审批；测试入口做脱敏，真实 Provider 直接回写原始结果。

到这里，策略已经拥有结构化落点，但人工确认仍然只是一个概念。下一节深入审批数据本身：系统怎样证明用户确认的是当前订单、当前金额，而不是曾经确认过某个相似动作。



### 4\.5 为什么有效审批必须绑定参数摘要？

用户确认的是**一个具体动作**，不是一个长期布尔开关。假设用户确认“为 `ord_1001` 退款 100 元”，模型下一轮却把金额改成 399 元。如果审批记录只有 `approved=True`，Runtime 无法识别动作已经变化。



**有效审批至少绑定六项事实：**

```Plaintext
user_id
+ tenant_id
+ tool_name
+ canonical(arguments) 的摘要
+ expires_at
+ used
```

参数摘要不能直接依赖普通字典的临时字符串表现。代码先递归排序对象字段，再用稳定 JSON 序列化，最后计算 SHA\-256：

```Python
def _approval_digest(tool_name: str, arguments: ArgsModel | Mapping[str, Any]) -> str:
    canonical = json.dumps(
        _stable_value(arguments),
        ensure_ascii=False,
        separators=(",", ":"),
    )
    return hashlib.sha256(f"{tool_name}:{canonical}".encode()).hexdigest()
```

Runtime 消费审批时**同时比较**用户、租户、工具和参数摘要，并检查过期时间与一次性状态。



只要金额、订单号或原因发生变化，旧审批就不再匹配；审批成功使用一次以后标记 `used=True`，同一个 ID 不能重放。



这里还要区分低风险会话白名单与高风险业务审批。Coding Agent 中，用户可能愿意在本会话反复允许读取同一目录或运行 `pytest`，减少重复确认；但退款、删除、发布等高风险写操作不能因为“刚才确认过一次”就永久放行。本节参考权限流程的思想，但对业务 Agent 做了更严格的调整：普通 allow 或 bypass 都不能跳过强制审批。



审批绑定解决的是“确认了什么”，但系统仍然需要决定各种运行模式能否改变检查顺序。下一节把 default、plan、bypass 和 dontAsk 放进同一张优先级表，避免便捷模式无意中覆盖硬边界。



### 4\.6 deny、plan、bypass 和 dontAsk 为什么必须有固定优先级？

权限模式的目的，是描述当前会话采用什么交互策略，而不是授予无限权限：

|模式|业务语义|仍然不可跳过的边界|
|---|---|---|
|`default`|普通交互，必要时返回 confirm|deny、白名单、RBAC、业务检查、审批|
|`plan`|只允许分析和读取，不允许真实写入|所有写操作与 Shell 都被执行层拒绝|
|`bypassPermissions`|跳过普通低风险确认，便于受控环境自动化|deny、plan、白名单、RBAC、业务检查、强制审批|
|`dontAsk`|无法与用户交互|需要确认的动作直接 deny，不得偷偷执行|

正确顺序：

硬拒绝\(deny\) → plan → 白名单 → RBAC → 业务预检查 → 强制审批 → bypass → 普通 allow



顺序一旦交换，会出现具体故障：

- `bypass` 在 `deny` 之前：调试模式可删除受保护路径；

- `allow` 在 `plan` 之前：白名单里的退款工具在只读模式仍可执行；

- 审批在业务检查之前：用户会确认一个不属于当前租户或已退款的订单；

- `dontAsk` 把 `confirm` 当 `allow`：后台任务无人确认时自动执行高风险动作。



这台状态机目前完成了 Agent 级与主体级准入，但 RBAC 仍然是粗粒度判断。下一节继续向业务资源深入：同样拥有退款权限的人，为什么仍然不能修改所有租户、所有金额和所有订单。



### 4\.7 RBAC 通过以后，为什么还可能发生资源级越权？

RBAC 适合回答“当前主体是否拥有退款能力”，但**不一定能回答“是否能操作这一张订单”**。两个客服都拥有 `order:read`，但一个负责华东租户，另一个负责海外租户。

权限判断通常要组合三种范围：



前两项可以由白名单与 RBAC 快速拒绝，第三项需要业务 precheck 或策略服务读取实时资源。不能为了追求“统一权限中间件”，把所有业务条件硬塞进角色名称，例如创建 `east_china_refund_under_500_role`。角色爆炸会让策略难以维护，也无法表达订单状态等动态条件。



反过来，也不能只做资源查询而跳过 RBAC。否则攻击者可以用大量不存在的订单号探测资源，或者利用业务接口的错误差异推断其他租户数据。通常先做粗粒度主体资格，再查询当前租户内资源，最后判断细粒度业务条件。



资源级判断让当前时刻的动作合法，但 Agent Loop 是一个持续过程，策略和资源都可能在模型思考或用户确认期间变化。所以下一节继续回答时间维度的问题：曾经允许，是否等于现在仍然允许。



### 4\.8 策略在调用期间变化怎么办？

Agent Loop 可能持续数十秒甚至更久。模型看到工具以后，管理员可能撤销权限；用户等待确认时，订单可能已经退款；MCP Server 可能下线；租户策略也可能收紧。这就是为什么发现期 Schema 和先前审批不能成为永久执行许可证。



执行前应重新读取或校验关键事实：本轮白名单仍然包含工具、权限版本仍然有效、审批没有过期、资源状态仍然允许。对于高价值写操作，还要在最终存储事务中再次保护硬性要求。



并不是所有配置都要每毫秒远程读取。工程师需要在一致性、延迟和可用性之间取舍：低风险工具可以使用短 TTL 策略缓存；高风险权限撤销可以通过版本号、事件通知或在线授权服务快速生效；审批记录应在消费时强一致更新 `used` 状态。



这类取舍也是人的业务能力。AI 可以写缓存代码，但无法替你决定“权限撤销最多允许延迟多少秒”以及“授权服务不可用时退款应该 fail\-open 还是 fail\-closed”。



权限策略还需要明确变更责任。工具开发者负责声明副作用与所需权限，业务负责人决定角色和额度，安全负责人定义硬拒绝与高风险确认，平台负责提供一致执行点。若所有字段都由写 handler 的同一个人随手决定，代码评审很难发现策略是否过宽。把责任写进评审清单，比增加更多枚举更能减少错误授权。



策略上线也应像代码一样灰度与回归。先在测试租户运行固定 Tool Call 集合，比较 allow、deny、confirm 分布和副作用；再扩大范围。权限规则不是普通 Prompt 文案，顺序变化可能直接改变真实执行路径。



最小策略表也要包含默认行为。新工具尚未完成风险分类时，应默认不进入生产白名单，而不是继承一个宽泛 allow；新权限尚未配置时，Runtime 应返回明确拒绝。安全默认值让遗漏表现为“功能暂不可用”，而不是“未知能力自动开放”。



经过能力、主体、资源和时间四层检查，第一阶段才真正闭合。下面的小结不再罗列名词，而是把它们重新串回一次 Tool Call，确认学员知道每一层的输入、输出和验收证据。



### 4\.9 本阶段小结：人的能力不是会写几个 if

第一阶段真正训练的是四项判断能力：

到这里，我们只证明了“谁有资格申请什么动作”。即使权限全部通过，参数仍可能不符合协议，订单状态可能已变化，SQL 和 Shell 可能拥有过大的解释能力，超时也可能导致重复副作用。**下一阶段继续回答：允许执行以后，怎样保证一次调用不会失控。**

## 五、第二阶段：调用期安全与韧性——允许执行以后，怎样避免失控？

先给结论：调用期安全的目标，不是保证工具永远不失败，而是**保证非法输入进不去、危险能力被收窄、失败不会被错误重放、敏感结果不会继续扩散。**



上一阶段回答了“谁有资格申请”。本阶段沿着一次调用继续深入：把模型生成的字典转为可信业务对象 → 检查实时业务状态 → 进入 Handler → 超时或失败时按副作用语义恢复 → 结果治理后回到 Agent Loop。



这一阶段集中解决五类运行期问题：

|运行期问题|本阶段的控制点|如果不处理会发生什么|
|---|---|---|
|模型参数结构合法但业务含义非法|Schema 校验 \+ 业务预检查|非法金额、跨租户资源或过期状态进入 handler|
|SQL / Shell 的表达能力远大于业务需要|能力收窄 \+ 参数化 \+ 隔离|一条工具调用变成任意数据库或系统权限|
|下游超时、限流或断连|按副作用和幂等语义恢复|重复退款、无限重试或把未知状态当失败|
|工具原始结果包含敏感数据和内部异常|结果投影、脱敏、限长和错误归一化|Token、个人信息和堆栈进入模型或日志|
|Prompt 注入诱导模型调用危险工具|Prompt 降概率 \+ Runtime 硬边界|模型把外部数据中的指令变成真实副作用|

**什么时候需要本阶段？** 只要 Tool 能访问真实数据、调用网络、写数据库、发消息、执行命令或产生费用，就必须在第一次接入时设计调用期边界。即使是 Demo，参数校验和稳定 Tool Result 也不应省略——否则 Demo 无法平滑迁移到业务项目。



**本阶段的顺序不能调换**：先判断参数能否成为业务对象 → 再读取动态业务事实 → 确定“调用什么”后，才讨论 SQL/Shell 的能力范围 → 进入执行阶段后，才讨论超时恢复 → 最后，所有结果离开 Runtime 前统一收口。



### 5\.1 参数校验为什么不只是检查 JSON 能不能解析？

JSON 能解析，只说明括号和引号符合语法。它不能证明字段属于工具协议、数值在业务范围内、身份来源可信。

以下几段参数都是合法 JSON，**但都不应进入退款 Handler**：

```JSON
{"order_id":"ord_1001","amount":-1,"reason":"退款"}
{"order_id":"../../etc/passwd","amount":399,"reason":"商品存在质量问题"}
{"order_id":"ord_1001","amount":99999999,"reason":"商品存在质量问题"}
{"order_id":"ord_1001","amount":399,"reason":"商品存在质量问题","user_id":"admin","approved":true}
```

- 金额为负 / 原因过短

- 订单号不符合业务标识格式

- 金额超过工具上限

- 身份和审批事实混入参数

Pydantic Model 的作用，是把“不可信字典”转换成“Handler 可依赖的业务对象”：

```Python
class StrictArgs(BaseModel):
    model_config = ConfigDict(extra="forbid", strict=True)


class CreateRefundArgs(StrictArgs):
    order_id: str = Field(pattern=r"^ord_[0-9]{4}$")
    amount: float = Field(gt=0, le=10_000)
    reason: str = Field(min_length=4, max_length=200)
```

每一项对应一个确定边界：

- `extra="forbid"`：禁止模型偷偷增加 `user_id`、`approved` 等字段

- `strict=True`：避免字符串/布尔值被过度自动转换

- `pattern`：订单号必须符合格式

- `gt`/`le`：金额必须为正且不超过上限

- `min_length`/`max_length`：避免空洞原因，也限制 Context 污染

Runtime 在进入权限引擎之前执行校验：

```Python
try:
    arguments = tool.parameters_model.model_validate(call.arguments)
except ValidationError as error:
    return ToolResult(
        tool_call_id=call.tool_call_id,
        tool_name=call.name,
        ok=False,
        action=DecisionAction.DENY,
        code="INVALID_ARGUMENT",
        content=normalize_validation_errors(error),
    )
```

为什么校验失败仍要保留 `tool_call_id`？因为 Agent Loop 必须知道这条 Tool Result 对应哪一次 Tool Call，模型下一轮才能根据字段错误重新生成参数。如果 Runtime 抛出 Python traceback 或丢掉 ID，Provider 层可能无法构造合法工具消息，多轮上下文也会失去关联。



参数校验以后，handler 收到的是 `CreateRefundArgs`，而不是任意字典。这会显著降低内部代码的分支数量，但它仍然没有证明订单属于当前租户、处于可退款状态或拥有足够余额。结构正确以后还需要业务校验。



因此，5\.1 的结论范围有限——它只说明“参数格式合法、值域合规”，不等于“可以执行”。真正的执行许可，还要经过业务预检查、权限和审批。



### 5\.2 Schema 正确以后，为什么还要做业务预检查？

Schema 验证静态形状，业务预检查验证动态事实。两者不可混淆。两者经常被错误地写在一起，导致开发者误以为“Pydantic 通过就能执行”。

可以把四层判断明确分开：

|层次|判断内容|数据来源|失败示例|
|---|---|---|---|
|Schema|字段、类型、格式和范围|ToolDefinition|金额为负、未知字段、订单号格式错误|
|业务预检查|资源归属、当前状态、额度和依赖事实|Repository / 业务 API|订单不属于租户、已退款、可退金额不足|
|权限|当前主体是否有资格申请|ExecutionContext / IAM|普通客服没有退款权限|
|审批|用户是否确认当前具体动作|审批服务|金额改变、审批过期、审批已使用|

退款业务预检查使用服务端 `tenant_id` 查询订单：

```Python
async def refund_precheck(arguments: ArgsModel, context: ExecutionContext) -> None:
    assert isinstance(arguments, CreateRefundArgs)
    order = ORDERS.get((context.tenant_id, arguments.order_id))

    if not order or order["status"] != "paid":
        raise PolicyDenied("BUSINESS_RULE_DENIED", "订单不存在或状态不可退款")

    if arguments.amount > float(order["refundable"]):
        raise PolicyDenied("BUSINESS_RULE_DENIED", "退款金额超过可退金额")
```

这段代码必须放在 Handler 之前。否则支付接口可能已经执行，Runtime 才发现状态不合法——即使返回 `BUSINESS_RULE_DENIED`，也无法撤销已发生的外部副作用。



竞态问题：两次并发退款都在预检查时看到可退金额 399 元，然后同时请求退款。单靠前置检查不够，最终写入还需数据库条件更新、唯一约束、版本号或下游幂等键。治理层负责尽早拒绝明显非法动作，业务存储层负责最终一致性——两者不能互相替代。



> 这里训练的是识别状态所有权的能力：哪些规则仅靠 Schema，哪些必须读取实时业务事实，哪些还需要原子性。AI 可以生成检查分支，但不知道“订单已发货是否还能全额退款”这类业务规则。
> 
> 



### 5\.3 SQL 和 Shell 为什么不能原样交给模型？

通用 SQL 与 Shell 的风险在于把解释器级能力交给了概率系统。命令字符串可包含重定向、管道、子进程、文件遍历；SQL 可包含多语句、锁、高成本查询。关键词黑名单很难覆盖所有等价表达。



**更安全的第一选择是把能力收窄成业务工具。**不要给模型：

```Python
run_sql({"sql": "模型生成的任意 SQL"})
run_shell({"command": "模型生成的任意命令"})
```

如果真实需求只是查询订单，就把表、列、租户条件和排序固定在代码中：

```Python
async def search_orders(
    pool: DatabasePool,
    context: ExecutionContext,
    status: Literal["paid", "shipped", "refunded"],
    limit: int,
) -> list[dict[str, Any]]:
    safe_limit = max(1, min(limit, 50))
    return await pool.fetch(
        """
        SELECT order_id, status, total_amount
        FROM orders
        WHERE tenant_id = $1 AND status = $2
        ORDER BY created_at DESC
        LIMIT $3
        """,
        context.tenant_id,
        status,
        safe_limit,
    )
```

模型只能选择业务状态和数量；租户来自可信 Context；SQL 结构由工程师持有；结果只返回必要列。

Shell 同理——固定可执行文件和参数数组：

```Python
async def inspect_service_logs(service: str, requested_lines: int) -> str:
    service_units = {"api": "my-api.service", "worker": "my-worker.service"}
    unit = service_units[service]
    lines = max(1, min(requested_lines, 200))
    process = await asyncio.create_subprocess_exec(
        "journalctl",
        "--unit",
        unit,
        "--lines",
        str(lines),
        "--no-pager",
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE,
    )
    stdout, _ = await asyncio.wait_for(process.communicate(), timeout=5)
    return stdout.decode(errors="replace")[:20_000]
```

这里没有 `shell=True`，也没有让模型拼接任意命令；服务名来自白名单，行数有上限，输出有限长，进程有超时。部署层还要配合低权限账户、固定工作目录、只读文件系统、网络策略和容器。



配套演示仍然保留一个“模拟 `run_shell`”，用于讲解 deny\-first 和 bypass 顺序，但它不会创建真实子进程。危险正则只是一条教学兜底。参考权限实现也明确指出，真实 Coding Agent 需要 AST、沙箱和多层防御；生产中应在解析失败时 fail\-closed，而不是把正则当成完整安全方案。



到这里，输入和能力范围都已经收窄，handler 才具备执行资格。可是“允许开始”不等于“必然得到确定结果”：网络可能在请求送达以后断开，下游可能成功却没有返回响应。于是下一小节必须先区分到底是谁在重试，再决定工具能不能重放。



### 5\.4 超时以后为什么不能统一重试三次？

“请求失败就重试”在只读 API 中很常见，但工具治理必须先问：失败发生时，真实副作用是否可能已经完成？

首先区分三个容易混淆的机制：

|机制|发生位置|是否产生新的模型决策|是否重放同一业务动作|典型场景|
|---|---|---|---|---|
|Provider / 大模型请求重试|调用 LLM API 时|否，通常还是同一请求|尚未进入 handler|429、连接失败、模型服务 5xx|
|Agent 重新规划|Tool Result 回填后的下一轮|是，会生成新的 Tool Call|不一定，参数和工具都可能变化|`INVALID_ARGUMENT` 后模型修正金额|
|Tool Runtime 重试|`execute` 阶段|否，沿用同一 Tool Call|是，因此必须判断幂等性|只读查询遇到瞬时数据库断连|
|业务状态恢复|结果未知或长流程中断后|不一定|原则上先查状态，不直接重放|支付请求超时后查询退款单|

本节的工具重试发生在模型已决定、Runtime 已批准、Handler 已开始之后。重放可能再次扣款、再次发邮件或再次删除文件——风险完全不同。



恢复策略应由副作用和幂等语义决定：

|失败|工具属性|推荐动作|禁止动作|
|---|---|---|---|
|参数错误|任意|返回 `INVALID_ARGUMENT`，允许模型修参|用原参数重试|
|权限或 deny 拒绝|任意|结束、换主体或人工处理|让模型改写提示词绕过|
|只读瞬时失败|read|总 deadline 内指数退避、有限重试|无限重试占满资源|
|幂等写失败|write \+ 真实幂等|使用同一幂等键有限重试|每次生成新幂等键|
|非幂等写超时|write|返回 `TIMEOUT_UNKNOWN`，查询真实状态|直接重放|
|依赖持续不可用|任意|缓存、只读降级或人工兜底|伪造成功结果|

Python Runtime 先计算允许重试的次数：

```Python
retries = (
    tool.policy.max_retries
    if tool.policy.effect is Effect.READ or tool.policy.idempotent
    else 0
)
```

随后使用 `asyncio.timeout()` 包住 handler：

```Python
for attempt in range(retries + 1):
    try:
        async with asyncio.timeout(tool.policy.timeout_seconds):
            return await tool.handler(tool_call_id, arguments, context)
    except TransientToolError:
        if attempt == retries:
            raise
        await asyncio.sleep(min(0.05 * (2**attempt), 0.2))
```

> 超时需向下游传播：HTTP 客户端、数据库驱动、子进程都要响应取消。只停止外层等待，不代表支付请求真的停止。
> 
> 



判断顺序：先确认失败发生在哪一层 → 再判断副作用是否可能发生 → 最后选择重试、查状态、降级或人工接管。不能仅根据异常类名决定重试，更不能把“模型再想一次”与“支付再执行一次”混为一谈。



### 5\.5 原始结果：不能同时发给模型、用户和日志



一次工具执行通常产生多个出口：模型上下文需要足够的信息继续推理，用户界面需要可理解的结果，审计需要决策证据，调试日志需要排障信息。四个出口的最小必要数据并不相同。

|视图|目的|可以包含|不应默认包含|
|---|---|---|---|
|handler 原始结果|内部业务处理|下游完整对象|不直接传播|
|模型视图|支撑下一步推理|状态、可退金额、业务 ID|Token、密码、内部堆栈、无关个人信息|
|用户视图|告知结果与下一步|用户有权查看的字段|内部权限规则与系统实现细节|
|审计视图|证明决策与执行|Trace、Tool Call、主体、错误码、摘要|完整 Prompt、原始客户资料、密钥|



配套代码使用递归脱敏作为最后一道防线：

```Python
def _redact(value: Any) -> Any:
    if isinstance(value, Mapping):
        return {
            key: "***"
            if re.search(r"token|secret|password|authorization", key, re.I)
            else _redact(item)
            for key, item in value.items()
        }
    if isinstance(value, str):
        return re.sub(EMAIL_PATTERN, "***@***", value)
    return value
```

> 生产中不能只依赖“先查询全量数据，再用正则清理”。更稳妥的顺序是：下游查询只选必要字段 → Handler 只返回业务需要字段 → 模型视图做显式投影 → 统一脱敏作为兜底。
> 
> 

错误结果同样需要治理：返回 `TOOL_ERROR`、`TIMEOUT_UNKNOWN` 等稳定错误码和有限安全说明，不能把 Python traceback 原样交给模型。内部堆栈可进入受保护的诊断系统，但必须与模型消息分离。



下一小节处理一种更隐蔽的风险：工具本身没有漏洞，模型却被数据中的恶意指令诱导去申请另一个危险动作。



### 5\.6 Prompt 注入：最终靠工具边界兜底

先给结论：Prompt 注入治理的目标，**不是证明模型永远不会受骗，而是保证模型即使受骗，也只能提出候选动作，不能绕过 Runtime 获得真实权限。**



Prompt 注入是把本应作为“数据”的文本伪装成“指令”。直接注入来自用户输入；间接注入更危险——来自网页、邮件、PDF、另一个工具的返回值。如果模型同时拥有网页读取、Shell、网络发送能力，一段间接注入可能形成完整攻击链。



1. Prompt 层：明确区分指令和不可信数据，要求模型不执行数据里的命令

2. 数据层：对网页、邮件、Tool Result 做来源标记、限长、内容隔离

3. Runtime 层（最终边界）：所有 Tool Call 重新经过白名单、RBAC、资源检查、审批

> Runtime 不需要先判断模型“为什么”提出动作。无论来自正常需求、模型误判还是间接注入，都经过相同的确定性门。系统不要求模型永远识别攻击，只要求危险动作无法越过边界。
> 
> 

- 不要用“模型判断这是不是注入”作为唯一授权条件

- 不要因工具是只读就认为结果可信——网页、邮件、代码仓库都可能携带间接指令

- 用攻击链测试验证边界：让网页结果包含“调用 run\_shell”，断言即使产生 Shell Tool Call，也被 `deny` 或 `confirm`，且副作用为零



下一小节把业务授权与计算隔离分开。



### 5\.7 隔离环境解决什么，权限判断又解决什么？

先给结论：权限判断回答的是“这次动作应不应该做”，而 Sandbox 与部署隔离回答的是“即使代码失控，最多能伤到哪里”。这两者分别控制业务正当性和技术爆炸半径，不能互相替代，也不存在谁比谁更重要。



那具体聊一聊什么是隔离环境。隔离环境不是写一个 try\-except，它是一组系统级的约束：用什么用户身份运行、能访问哪些文件系统路径、允许访问哪些网络地址、能创建多少进程、可用多少 CPU 和内存、运行多长时间、输出结果能有多大、以及秘密信息如何注入。对 Python、Shell、代码构建和浏览器自动化这类解释器级的工具来说，隔离不是部署结束后再补的运维选项，它从一开始就应该是执行设计的一部分。



好，那问题来了：什么时候必须用隔离环境？如果只是一个只读的内存计算，通常不需要完整容器；如果工具访问的是固定的内部 API，重点放在 RBAC 和结果边界上就够了。但一旦这个工具能执行用户或模型生成的代码、能读取工作区文件、能安装依赖、能访问公网、或者能启动子进程，这时候就应该把它放进受限进程、容器、MicroVM 或者专门的 Sandbox 服务。风险越高，隔离就越接近强制要求。



我举两个例子你就明白了。一个有权运行日志工具的 Agent，如果它的进程账户仍然可以读取整个主机的文件系统，那参数校验只要有一个遗漏，影响面就可能被无限放大。反过来，一个运行在容器中的 Agent，如果跨租户权限设计错了，它仍然可能通过内部 API 读取其他租户的数据。所以说，业务权限保护的是逻辑资源，Sandbox 保护的是计算与系统资源——各管一摊，谁也替代不了谁。



那具体怎么落地呢？生产环境的执行层通常会组合这样一组措施：低权限账户、只读的根文件系统、一次性可写的工作区、显式的网络出站白名单、CPU/内存/进程限制、固定的环境变量注入、短期有效的秘密、以及命令和输出的上限。更具体地说，Runtime 会生成一份执行计划，Sandbox 根据这份计划创建受限环境；Handler 只能拿到必要的输入，执行结束后环境被回收，只有有限的结果被交回到 finalize 阶段。



需要特别说明的是，这节课不会在课堂进程中真的执行任意 Shell。因为“为了演示安全而运行真实危险命令”这件事本身就是错误的教学方式。配套的 run\_shell 只模拟调用次数，用来证明 deny\-first 和 plan 模式的优先级。真实项目如果必须运行命令，应该使用参数数组、固定可执行文件、受限工作目录和独立的 Sandbox；解析失败、Sandbox 不可用或策略服务超时的时候，对高风险动作要默认 fail\-closed。



这里还要提醒一点：不要把所有的安全检查都堆进一个前置函数里。Schema 校验、授权、业务状态、执行隔离和结果治理，它们的数据来源不同，失败语义也不同。分阶段实现，既便于测试，也能在 Trace 里快速定位到底是哪一层拒绝了调用。所谓纵深防御，不是把同一个正则表达式重复五遍，而是每一层控制不同类型的风险，并且后一层不假设前一层永远正确。



最后说一个实践上的关键点：要把隔离参数也当成 ToolPolicy 的一部分。最大运行时间、网络范围、文件系统挂载、输出上限，这些都应该可审查、可测试、可审计。不要让 Handler 自己临时决定“这次多开放一个目录”，也不要把宿主机的长期凭据直接放进环境变量。权限允许之后仍然使用最小能力——这才是真正的纵深防御。



好了，回顾一下。这一阶段我们从输入参数出发，一路走过了业务状态检查、危险能力收窄、失败恢复、结果传播、Prompt 注入，一直推进到系统隔离。这些内容看似分散，但实际上都围绕同一个目标：让一次已经获得批准的调用，在确定的边界内完成，并且留下可恢复的结果。



### 5\.8 本阶段小结：韧性不是多重试几次

这一阶段我们扩展了四项工程判断能力。

第一，能够区分 JSON 可解析、Schema 合法、业务合法、权限允许和用户确认——这五个层次不是一回事，不能混在一起判断。

第二，优先把 SQL 和 Shell 收窄成具体的业务能力，然后再用 AST、沙箱和最小权限来防御剩余的风险。

第三，根据只读、幂等和真实的副作用来选择重试、查状态、降级还是人工接管——而不是一律重试三次。

第四，在数据进入模型、用户界面和审计之前，先控制好结果的视图。



如果用四个视角来收一下这一阶段：从 What 看，我们建立的是一次调用从参数到结果的安全执行管道。从 Why 看，它避免了“权限通过”被误解为“可以无条件运行”。从 How 看，我们依次使用了 Schema、业务预检查、能力收窄、副作用驱动的恢复、结果投影和系统隔离。而从 Know\-how 看，真正困难的地方在于识别状态归属、失败层级、幂等事实和不同出口的最小数据——而不是多写几个异常分支。



工程师完成这一阶段之后，应该具备这样的能力：拿到一个新工具，先列出它的输入硬性要求和下游副作用，然后决定是否允许重试、需不需要 Sandbox、结果能进入哪些出口，并且能写出“失败时副作用为零”或“未知状态禁止重放”的测试。AI 可以帮你补 Pydantic Model、超时包装和脱敏样板，但这些策略层面的决定，必须由懂业务的人来定义。



现在，单次 Tool Call 已经有了明确的边界。但模型可能在同一轮里提出多个调用：同时查订单和物流，先查余额再退款，甚至对同一个订单发起两次写操作。下一节我们要讨论的是队列与编排——重点不是一上来就建 DAG，而是先识别哪些调用是独立的、哪些有依赖关系、哪些会争抢同一份资源。

## 六、第三阶段：调用编排与队列——多个工具应该并行、串行还是按资源排队？

先给结论：**工具队列不是默认必建的通用平台。正确的做法是，先判断调用是否独立、是否存在数据依赖、是否争用同一业务资源，再选择有限并行、显式串行或按资源键排队。**



这一节在课程里属于 P2 了解级，所以不用写得像前面那么细。但为什么还得讲？因为真实事故经常来自调度语义与业务语义不一致——两条查询被无意义地串行导致延迟翻倍，两条针对同一订单的退款被并行执行导致重复扣款。



第三阶段解决的核心问题是：多条已经分别合法的 Tool Call 放在一起时，怎样保持顺序、依赖、资源一致性和结果关联？



### 6\.1 先识别三种关系

编排前的第一件事不是选队列产品，而是给调用分类。三种关系对应三种策略：

相互独立不等于无限并行。 模型一次生成 100 个查询，全启动可能拖垮数据库。并发控制至少要三层：全局上限、按工具上限、按租户配额。生产中还要把排队时间纳入总 deadline，超时就返回 `QUEUE_TIMEOUT`。

数据依赖不能靠模型在自然语言里“记住顺序”。 如果退款金额必须来自最新订单状态，要么把前一步结果回填到下一轮 Context，要么把两步封装成一个业务工具——后一种方式把关键硬性要求收回到确定性代码里。

资源冲突最容易被忽略。 两个退款调用参数都合法，但改的是同一张订单。单进程可以按 `tenant_id:order_id` 加锁，生产环境还得靠数据库唯一约束、条件更新或下游幂等键。队列控制顺序，存储层保证数据最终一致，两层不能互相替代。



### 6\.2 结果完成顺序和消息顺序为什么要分开？

并行执行时，后发起的调用可能先完成。Runtime 可以按完成顺序收结果，但回写 Agent Loop 时必须按 `tool_call_id` 关联，不能按数组位置猜。

```Python
async def invoke_many(calls, context):
    tasks = {
        asyncio.create_task(runtime.invoke(call, context)): call.tool_call_id
        for call in calls
    }
    by_id = {}
    for task in asyncio.as_completed(tasks):
        result = await task
        by_id[result.tool_call_id] = result
    return [by_id[call.tool_call_id] for call in calls]
```

两个硬性要求：每个结果携带自己的 ID；聚合器不用“第几个完成”猜“第几个调用”。部分失败也一样——失败结果保留 ID 和错误码，独立调用继续完成。

有些 Provider 要求 Tool Call 和 Tool Result 顺序严格对应，内部可以乱序完成，协议输出要按 ID 排好。这也是为什么 `tool_call_id` 不是可选字段——它同时服务模型协议、审计关联、并行聚合和幂等语义。

### 6\.3 什么时候才需要 DAG 或工作流引擎？

只有业务出现稳定的多步依赖、条件分支、长时间等待和补偿，才值得升级为显式 Graph。

比如：查库存 → 锁库存 → 创建支付 → 等待回调，失败则释放库存。这种流程需要持久化状态和补偿，超出了简单队列。反过来，两条独立查询就上 DAG，增加了复杂度却没带来可靠性收益。

选择标准不是“步骤超过三步”，而是是否需要持久化进度、跨故障恢复和补偿语义。

设计时每个节点仍然调用同一个 `ToolRuntime.invoke()`，Graph 管调度，Runtime 管执行。节点要保存输入摘要、`tool_call_id`、业务 ID 和幂等键，重启后才能区分恢复与重复执行。

还有一个关键点：补偿不等于回滚。 邮件发出去撤不回，转账只能冲正，删文件只能从备份恢复。画 DAG 之前，先写清楚每个节点的可逆性和兜底方案。

### 6\.4 本阶段小结

编排最终回答四个问题：哪些可以同时开始？哪些必须等前一步？哪些不能同时改同一资源？部分成功后怎么办？

asyncio 或 Pi 的并行配置只提供调度机制，具体关系得由工程师定义——模型能看见依赖，但它不拥有锁，也不承诺隔离性。

演进路径是：先限制并发，再处理显式依赖，再保护资源冲突。问题稳定复现以后，才考虑升级 Graph。asyncio 样板代码 AI 能写，但定义关系、一致性和恢复语义——这是工程师的事。

队列能控制“怎么跑”，却不能证明系统为什么允许、拒绝或失败。下一阶段用审计与可观测，把整条链串成证据。

## 七、第四阶段：审计与可观测——怎样证明系统为什么这样决定？

先给结论：**审计不是把 Prompt、参数和结果全部打印出来，而是在不扩大数据泄漏的前提下，记录足以重建一次治理决策和业务副作用的证据。**



普通 debug 日志回答的是“程序运行到哪一行了”，治理审计要回答的问题完全不同：谁以什么身份发起了哪个动作？系统依据什么规则允许、拒绝或要求确认？Handler 到底有没有真正执行？结果关联到哪个业务对象？敏感信息在进入模型之前有没有被处理掉？



这一阶段解决的是前三阶段共同留下的“证据问题”。权限系统返回 deny，并不自动证明 Handler 没有被调用。Tool Result 返回成功，也不自动证明真实支付系统真的创建了退款。调用超时了，更无法仅凭一条异常判断副作用到底有没有发生。没有审计与 Trace，系统只能描述结果，不能解释因果，也不能支持对账、人工接管和策略改进。



那什么时候必须用呢？只读内部 Demo 可以先使用内存记录。但任何涉及用户数据、写操作、费用、高风险工具、人工审批和跨系统调用的 Agent，都应该从第一天保留最小审计字段。审计不是“上线以后再补”的事，因为历史事件一旦没有记录，就无法事后补造可信证据。



这一阶段按证据形成的顺序来讲。先定义一条最小记录长什么样，再把决策与执行分开记录。然后用稳定错误码驱动恢复，用脱敏保护审计自身。最后把离散事件组织成时间线和指标。这样审计既服务于单次故障排查，也服务于长期的策略治理。



### 7\.1 一条最小审计记录应该包含什么？

What :最小审计记录不是完整请求快照，而是一份结构化事件：它能回答主体、工具、阶段、决定、错误码和关联 ID，同时默认不保存敏感参数值。



**生成本节审计对象的提示词：**

```Markdown
请只生成 Python 3.12 的 `AuditRecord` 数据类与内存 `AuditSink`，不要生成 Runtime。

要求：
1. 记录 `trace_id`、`tool_call_id`、`tool_name`、`user_id`、`tenant_id`；
2. `phase` 只能是 `decision` 或 `execution`；
3. 保存稳定 `decision`、`code`、参数键名和可选延迟，不默认保存参数值；
4. 对象不可变，适合 pytest 精确断言；
5. `AuditSink` 只提供追加与按 trace 查询，不打印 Prompt、Token、密码或原始异常；
6. 给出两个测试：被拒绝的调用只有 decision 记录，成功调用同时有 decision 与 execution 记录。

先输出接口说明，再输出最小代码；不得替我决定审计保留期限和敏感字段分类。
```

生成的代码大概是这样：

```Python
@dataclass(frozen=True, slots=True)
class AuditRecord:
    trace_id: str
    tool_call_id: str
    tool_name: str
    user_id: str
    tenant_id: str
    phase: Literal["decision", "execution"]
    decision: str
    code: str
    argument_keys: tuple[str, ...]
    latency_ms: int | None = None
```

这里有个设计上的关键点：只保存 argument\_keys，不默认保存全部参数值。订单号、金额或审批引用如果业务确实需要审计，可以经过数据分类后单独添加。但 Token、密码、完整客户资料和未经脱敏的 Prompt，不应该因为“方便排障”就进入永久日志。



还有三个标识必须分清。trace\_id 串起一次 Agent Run 的模型调用、工具决策、审批和失败事件。tool\_call\_id 关联一条模型 Tool Call 与对应的 Tool Result。业务 ID，比如订单号、退款单号、工单号，用来核对真实副作用。它们不能互相替代。一次 Trace 可能包含多个 Tool Call；一次 Tool Call 可能产生一个业务退款单；一个订单也可能在多个 Trace 中被查询。



这段代码位于 finalize 和拒绝返回的共同出口，解决的是“每次决策怎样留下稳定证据”。重点看三种 ID、phase 和只保存 argument\_keys。如果直接保存原始参数，审计会变成泄漏源；如果只保存 trace\_id，并行的 Tool Call 又无法准确关联。对象定义清楚以后，下一步要决定：为什么一条调用至少会产生决策与执行两类事件。



### 7\.2 为什么决策审计和执行审计要分开？

如果只在 Handler 完成以后写审计，被拒绝的调用就没有证据。如果只记录 allowed，又无法证明 Handler 最终是否真的成功了。

配套的 Runtime 记录两个阶段。第一个阶段是 decision，记录 allow、deny 或 confirm，以及规则来源和错误码。第二个阶段是 execution，记录 executed 或 failed，以及延迟和业务结果摘要。



举个例子。call\_02 退款未审批，只会有 decision=confirm，不会出现 execution=executed。而 call\_03 会先记录 APPROVED，再记录 execution=executed。审计记录与副作用计数结合起来，就能证明 Handler 到底有没有越过治理门。



审计本身也可能失败。生产中要根据业务风险决定：高风险写操作在审计系统不可用时是 fail\-closed，还是先写本地事务 Outbox 再异步投递。不能简单地把所有日志失败都忽略，也不能因为远端日志平台短暂不可用就让所有低风险查询瘫痪。



两阶段记录让我们知道“是否获准”和“是否完成”，但 Agent Loop 仍然需要机器可读的下一步。于是审计中的 code 不能只是任意文本，必须成为稳定的恢复协议。



### 7\.3 稳定错误码怎样驱动 Agent Loop？

模型、前端、Harness 和人工工作台不能靠解析中文说明决定下一步。错误码应该直接映射恢复动作：

|错误码|Agent Loop / Harness 动作|是否自动重试|
|---|---|---|
|`INVALID_ARGUMENT`|把字段错误回填模型，允许生成新的 Tool Call|不用原参数重试|
|`TOOL_NOT_ALLOWED`|当前轮不开放，结束该路径|否|
|`PERMISSION_DENIED`|当前身份无权限，换主体或结束|否|
|`APPROVAL_REQUIRED`|暂停 Loop，进入可信确认界面|否|
|`BUSINESS_RULE_DENIED`|业务状态不允许，重新规划或人工处理|通常否|
|`TIMEOUT`|只读或幂等工具按策略恢复|有条件|
|`TIMEOUT_UNKNOWN`|查询真实业务状态，禁止直接重放|否|
|`TOOL_ERROR`|记录内部诊断，给模型有限说明|按映射决定|

稳定错误码也是 TDD 的锚点。如果错误文本改变，测试不应该全部失效。但如果错误码语义改变了，那就属于需要评审的契约变化。



错误码让控制流可编程，但记录得越多，泄漏面也越大。所以下一节不是继续增加字段，而是回答：哪些数据根本不应该进入审计。



### 7\.4 审计怎样避免自己成为泄漏源？

工具结果已经对模型脱敏了，并不代表日志就安全。很多系统只处理 afterToolCall 的模型结果，却在前置 Hook 里打印完整参数，在异常处理中记录原始响应——最终日志成了更大的敏感数据集合。

建议统一一条数据出口规则。

第一，参数先按字段分类，默认只记键名和摘要。

第二，模型结果与审计结果复用同一套敏感字段识别规则。

第三，内部 traceback 进入受保护的诊断通道，不进入 Tool Result。

第四，审计存储设置访问控制、保留期限和不可篡改策略。

第五，高风险事件保留审批引用与业务 ID，而不是保存整个上下文。



审计最终服务于线上排障、权限复盘、安全调查、业务对账和 Agent Eval。它不是“多打一行日志”，而是对系统行为负责的证据层。



最小披露解决了单条记录的安全问题，但仍然不能解释多轮 Agent 中事件如何前后关联。所以下一节要把记录按时间和 ID 组织起来，让一次失败能够被完整复盘。



### 7\.5 怎样用一条事件时间线复盘工具调用？

单条日志很难解释多轮 Agent。更有效的方式是按 trace\_id 和时间把事件组织起来。比如这样一条时间线：

```Plaintext
10:00:00.120  model_tool_call   call_03 create_refund
10:00:00.123  schema_valid      call_03
10:00:00.127  policy_allow      call_03 code=APPROVED
10:00:00.130  tool_start        call_03
10:00:00.286  tool_end          call_03 refund_id=ref_9001
10:00:00.288  result_redacted   call_03
10:00:00.291  tool_message      call_03
```

如果调用被拒绝，时间线应该停在 policy\_deny，不应该再出现 tool\_start。如果 tool\_start 存在却没有 tool\_end，那就需要结合 timeout、取消和下游业务 ID 来判断结果是否未知。如果 tool\_end 成功了但没有 tool\_message，问题发生在 finalize 或 Provider 回填阶段，而不是支付系统本身。



这种事件序列让故障定位从“Agent 好像没有工作”变成“哪一个生命周期阶段中断了”。它也是后续 Trace Analysis 和 Eval 的数据基础。



时间线可以解释一笔事故，聚合后的大量时间线还可以发现系统性问题。下一节从单次追踪转向长期指标，但要注意：指标只能提供证据，不能代替业务取舍。



### 7\.6 审计指标怎样反过来改进治理策略？

治理不是写完规则就结束了。我们可以从审计中聚合出一些有价值的指标。



INVALID\_ARGUMENT 的比例，反映工具 Schema 是否难以被模型正确使用。TOOL\_NOT\_ALLOWED 的比例，看模型是否频繁选择本轮不可用的工具——可能是工具描述不清楚，也可能是任务装配有问题。APPROVAL\_REQUIRED 到实际批准的转化率，能判断确认流程是否过度、界面是否清晰。

PERMISSION\_DENIED 的分布，能看出角色配置是否与真实岗位不匹配。TIMEOUT\_UNKNOWN 的数量，反映写接口是否缺少状态查询和幂等设计。敏感字段命中次数，则说明下游接口是否返回了过多数据。



但指标不能机械优化。举个例子，为了降低确认率而把所有退款改成自动允许，数值确实更漂亮了，风险却上去了。工程师要把安全、用户体验、自动化率和业务损失放在一起评估。审计提供证据，决策仍然属于业务与工程负责人。



指标决定了“哪些规则值得调整”，保留和访问策略则决定了“这些证据能存在多久、谁有权查看”。没有最后这层治理，审计平台本身会积累成新的高价值攻击目标。



### 7\.7 审计数据保留多久、谁能查看？

审计越详细并不总是越好。保存完整 Prompt 和工具结果虽然方便复现，却可能积累大量个人信息、商业数据和密钥。系统需要给不同数据定义保留周期、访问角色和删除机制。



高风险写操作可以长期保留决策码、主体、审批引用和业务 ID。普通只读调用可以只保留聚合指标或短期诊断记录。敏感字段默认不采集。访问审计本身也应该被审计——避免排障平台成为新的数据出口。

这一部分通常需要和安全、合规、业务团队共同决定。课程只给出最小字段，不假设“一份日志满足所有行业”。



审计字段也要有版本意识。新增错误码、修改参数摘要算法或调整脱敏规则时，应该记录策略版本，让历史事件仍然可解释。否则三个月后看到同一个 DENY\_RULE，却不知道当时命中的是哪一版规则。最小实现可以暂不落库版本，但生产设计必须为它预留位置。



可观测性最后还要服务人工接管。TIMEOUT\_UNKNOWN 事件应该带上业务 ID 和查询入口，让值班人员能判断退款是否完成了。如果只有一句“工具超时”，业务根本无法恢复。审计是否有用，要看它能不能支持下一步行动，而不是字段数量。



### 7\.8 本阶段小结

回顾一下第四阶段的核心。

从 What 来看，审计与可观测是一条从模型申请、治理决策、Handler 执行到 Tool Result 回填的结构化证据链，不是未经筛选的日志副本。



从 Why 来看，它解决了三个问题：被拒绝的动作能不能证明副作用为零？成功或超时的动作能不能关联到真实业务结果？线上的策略能不能依据数据改进？没有这些，系统就无法对账，也无法判断治理代码是否真正有效。



从 How 来看，我们做了五件事：定义最小 AuditRecord，用 trace\_id、tool\_call\_id 和业务 ID 关联不同层次；把 decision 和 execution 分开记录；用稳定错误码驱动 Agent Loop；对参数、结果和异常执行最小披露；最后把事件组织成时间线、指标和人工恢复入口。



从 Know\-how 来看，审计本身也要有作用域思维——它同样需要权限、脱敏、保留期限和策略版本。真正有用的审计记录必须能支持下一步行动：TIMEOUT\_UNKNOWN 要能跳到状态查询，而不是只留下一句"发生错误"。



至此，四个阶段的链路已经完整了：权限模型决定能否申请，调用期安全控制如何执行，队列处理多调用关系，审计证明系统的依据和结果。



下一节，我们把四段压回一条 ToolRuntime\.invoke\(\)，并解释它和 Pi 生命周期的对应关系。

## 八、把四个阶段接回 Python Runtime：为什么所有入口必须共用 invoke\(\)？

先给结论：**治理代码只有放在所有调用方都无法绕过的唯一入口里，才是真正的安全边界。散落在 Agent Loop、CLI、Handler 和测试里的重复 if，只是多份迟早会漂移的约定。**



这一节要把前面分开学习的参数校验、权限判断、执行控制、恢复策略、结果治理和审计，重新组装成一个最小 Runtime。

为什么要重新组装？因为独立函数即使每一个都写对了，只要调用顺序不固定，或者某个入口能够绕过它们，这些函数就无法构成真正的安全边界。



怎么落地呢？核心是 prepare → execute → finalize 三阶段，加上唯一的 invoke\(\)。



而 Know\-how 在于：CLI、离线演示、pytest、Provider Adapter，还有未来的 HTTP 或 MCP Handler，全部都要走同一条路径。



那什么时候应该开始使用这套结构呢？答案是：从第一个真实 Tool 开始，而不是等工具数量多了再重构。工具只有两个的时候，最容易建立唯一入口。等工具增加到二十个以后再收口，往往已经出现了多处执行语义的漂移——Agent Loop 直调、定时任务旁路、测试用 Fake Runtime、运维脚本直接调 Handler——多份实现互相不认。



接下来我们看一下 Pi 0\.83\.0 的生命周期。它的真实流程是：工具查找与参数准备、TypeBox Schema 校验、beforeToolCall、AgentTool\.execute、afterToolCall、最后 Tool Result 回写。Python 版本不冒充 Pi SDK，而是把相同的责任映射成下面这样：

|Agent 生命周期|Python v11 对应|治理责任|
|---|---|---|
|Tool Schema 校验|Pydantic `model_validate()`|把不可信字典变成业务对象|
|`beforeToolCall`|`PermissionEngine.decide()`|白名单、RBAC、业务预检查、审批和风险|
|`AgentTool.execute`|`ToolDefinition.handler`|只实现已经通过治理的业务动作|
|执行模式与取消|`asyncio.timeout`、重试策略、队列|控制期限、重放和并发|
|`afterToolCall`|finalize 脱敏与 `AuditSink`|结果进入模型以前收口|
|Tool Result Message|`ToolResult.to_tool_message()`|保留 `tool_call_id` 回填 Agent Loop|

完整入口只保留三段：prepare、execute、finalize。



这里要特别说明一下，下面这段 Runtime 骨架不是通过一句“写一个安全执行器”就能生成的。需要先把前七节已经确定的对象、顺序和失败语义压缩成局部提示词，只让 AI 负责组装，不让它重新发明业务策略。



**生成 ****`ToolRuntime.invoke()`**** 骨架的提示词：**

```Markdown
请基于现有 Python 3.12 接口生成 `ToolRuntime.invoke()` 的最小骨架，严格分为 prepare、execute、finalize 三段。

现有对象：`ToolCall`、`ToolResult`、`ToolDefinition`、`ExecutionContext`、`PermissionEngine`、`AuditSink`。

硬约束：
1. 所有入口只能调用 `invoke()`，不得在 Agent Loop 中直接访问 handler；
2. prepare 顺序为：查找工具、Pydantic 校验、权限三态决策；
3. `DENY` 和 `CONFIRM` 必须立即返回结构化 ToolResult，handler 零调用；
4. execute 只接收已校验的 Pydantic 对象，超时与重试委托 `_execute_with_recovery()`；
5. finalize 对结果投影、脱敏、审计，并原样保留 `tool_call_id`；
6. Python 异常不得直接进入模型消息；
7. 只生成 Runtime 组装代码和三项最小测试，不修改 PermissionEngine 的业务规则。

输出后逐项说明每段位于生命周期哪里、交换顺序的具体后果。
```

生成的骨架大致是这样的：

```Python
async def invoke(self, call: ToolCall, context: ExecutionContext) -> ToolResult:
    # prepare：找工具、参数校验、权限三态决策
    tool = self._tools.get(call.name)
    arguments = tool.parameters_model.model_validate(call.arguments)
    decision = await self._permission_engine.decide(tool, arguments, context)
    if decision.action is not DecisionAction.ALLOW:
        return blocked_result(call, decision)

    # execute：按副作用、超时和幂等策略运行 handler
    raw = await self._execute_with_recovery(tool, call.tool_call_id, arguments, context)

    # finalize：投影、脱敏、审计，并保留 tool_call_id
    return ToolResult(
        tool_call_id=call.tool_call_id,
        tool_name=call.name,
        ok=True,
        action=DecisionAction.ALLOW,
        code="OK",
        content=redact(raw),
    )
```

模型模式的 Agent Loop 最终调用：

```Python
result = await runtime.invoke(
    ToolCall(
        tool_call_id=provider_call.id,
        name=provider_call.function.name,
        arguments=json.loads(provider_call.function.arguments),
    ),
    context,
)
messages.append(result.to_tool_message())
```

离线演示与 pytest 也调用同一个方法。这样有两个好处：第一，测试命中的就是生产执行路径，不需要相信一套 Fake Runtime；第二，未来把本地 Handler 替换成内部 HTTP 或 MCP Tool 时，prepare 与 finalize 不变，只替换 execute 的下游实现。



这段代码位于模型 Tool Call 与真实 Handler 之间。重点看几个关键点：model\_validate\(\)、三态提前返回、\_execute\_with\_recovery\(\) 和最终 tool\_call\_id。如果先 execute 再 decide，会产生越权副作用；如果先把原始结果回填再 finalize，敏感数据已经进入 Context；如果 Provider 自己分发 Handler，离线测试通过也不能证明生产路径安全。



Runtime 结构明确以后，接下来不能立刻让 AI 一次填满所有规则。需要用最小规格、Harness、TDD 和 Loop 来控制生成范围与验证节奏。



### 8\.1 最小规格、Harness、TDD 和 Loop 怎样组合？

这四个方法并非简单的并列口号，更不是可以按喜好随意剪裁的锦上添花，而是一条强依赖、严顺序、不能随意跳步的开发流水线。在构建 LLM Agent 时，最大的工程陷阱往往不是模型能力不足，而是开发者企图用一份万能提示词一次性覆盖所有治理逻辑。

它们分别承担从需求边界、运行隔离、正确性证明到增量演进的不同责任。上一阶段的产物，恰好是下一阶段能够运作的前提：没有最小规格，Harness 不知道拦什么；没有 Harness，测试无法稳定观测副作用；没有 TDD，Loop 每轮没有客观红绿信号；没有小步 Loop，几十条规则一起失败时根本没法定位。

我们先看最小规格。

#### 8\.1\.1 最小规格：只记录业务的硬性要求，不维护第二套实现

最小规格的落点是一张工具策略表、一组稳定错误码和一份验收清单。它的价值在于克制：只记录“必须不发生什么”和“必须留下什么”，不在代码外复制全部类、字段和算法。

以退款为例，最小规格只需要写四条硬性要求。

第一，普通客服没有 refund:create 权限时，支付 Handler 调用次数必须为 0。

第二，审批必须绑定用户、租户、工具和规范化参数，参数变化后旧审批失效。

第三，退款超时结果未知时不得自动重放，必须查询真实状态。

第四，客户邮箱和 Token 不能进入模型消息与普通审计日志。



这些硬性要求足以驱动代码和测试，却不会产生一份需要与源码双向同步的庞大 SDD 文档。索引文档告诉开发者策略和测试在哪里，代码与测试作为事实来源。



#### 8\.1\.2 Harness：把模型与真实世界隔开

Harness 在本节中的落点包括 ExecutionContext、发现期白名单、执行期 PermissionEngine、唯一 ToolRuntime\.invoke\(\)、超时与结果收口。它不是普通单元测试 fixture，而是包住 Agent Loop、模型和工具的控制框架。



模型发出 Tool Call 时，Harness 不盲目转发。它先把不可信字典变成 Pydantic 对象，再检查服务端身份、业务权限、资源状态和审批；Handler 执行以后，Harness 又把原始结果投影、脱敏和审计。模型可以提出动作，但无法决定可信身份、授权事实和最终执行顺序。



如果没有 Harness，同一条规则会散落在 Prompt、Handler 和前端确认代码里。模型换 Provider、CLI 直接调用或历史 Tool Call 重放时，就可能绕过其中一层。



#### 8\.1\.3 TDD：把“应该安全”变成可执行断言

这里的 TDD 不只是普通业务单元测试，而是安全属性和副作用测试。举个例子：

```Python
result = await runtime.invoke(refund_call, context_without_permission)

assert result.code == "PERMISSION_DENIED"
assert SIDE_EFFECTS["refund_executions"] == 0
```

第一条断言验证控制面语义，第二条断言验证真实副作用。只有错误码而没有副作用断言，测试无法发现“先退款、后报错”的错误顺序。



TDD 的作用是把自然语言承诺转换成二进制信号。AI 可以生成实现，但在实现诞生以前，工程师已经定义了什么叫安全、用什么证据判断。失败测试不是为了刁难 AI，而是限制概率生成的搜索空间。最后是 8\.1\.4，Loop。



#### 8\.1\.4 Loop：每次只接入一条规则

多条治理规则同时加入时，一旦测试失败，很难区分是 Schema、白名单、RBAC、审批摘要还是脱敏逻辑出了问题。Loop 要求每轮只引入一个可以独立验证的硬性要求，经历运行、故障注入、修复和回归，再进入下一轮。



推荐的实际步骤是这样：从最小规格摘出一条业务硬性要求，比如“模型不能伪造管理员身份”。然后在同一个 Runtime 测试路径中先写失败测试，断言 INVALID\_ARGUMENT 且 Handler 零调用。接着让 AI 只针对这一条测试补最小实现，比如给 Pydantic 基类增加 extra="forbid"。然后运行离线 Harness，观察错误码、副作用计数和审计记录是否一致。如果失败，判断问题发生在 prepare、permission、execute 还是 finalize，修复后全量回归已有用例。只有该轮全部变绿，才接入下一条规则。



这种推进节奏可以形成清晰的四轮。

第一轮是参数边界，增加 extra="forbid"，验证 user\_id 与 approved 无法混入 Tool Call。

第二轮是准入边界，增加双重白名单和 RBAC，验证过期 Tool Call 与越权用户都无法进入支付 Handler。

第三轮是审批边界，增加规范化摘要、过期和一次性消费，验证金额变化与重放都会失效。

第四轮是结果边界，增加字段投影、脱敏和审计，验证敏感字段零泄漏，同时保留 tool\_call\_id。



每轮都应该在十几分钟内得到明确红绿结果，而不是让 AI 一次生成半套治理平台，再面对数百行未知代码猜测哪里出错。



最终，最小规格提供边界，Harness 提供隔离，TDD 提供准绳，Loop 提供节奏。四者咬合，把模型不确定性限制在可观测、可回归的工程框架内。



### 8\.2 迁移到真实项目时需要替换什么？

演示代码为了离线运行，用了内存订单、内存审批和副作用计数。迁移的时候不是推翻 Runtime，而是逐个替换明确接口。：

|演示对象|生产替换|必须保留的硬性要求|
|---|---|---|
|`ORDERS` 字典|带 tenant 条件的 Repository 或业务 API|资源查询必须使用服务端租户|
|`ApprovalStore`|审批数据库、工作流服务或可信确认结果|绑定用户、租户、工具、参数、过期和一次性|
|`SIDE_EFFECTS` 计数|Mock 支付网关、测试数据库、消息记录|拒绝时真实副作用为零|
|`AuditSink.records`|append\-only 审计表、事件流或日志平台|决策与执行可关联，不泄漏敏感数据|
|模拟退款 handler|支付接口|幂等键、超时、状态查询和对账|
|递归正则脱敏|字段投影、数据分类、统一 Masking Middleware|进入模型和普通日志前已处理|
|本地函数 Tool|内部 HTTP 或 MCP Tool|所有执行仍走同一个 invoke|

我把对应关系列一下。ORDERS 字典要替换成带 tenant 条件的 Repository 或业务 API，必须保留的硬性要求是：资源查询必须使用服务端租户。ApprovalStore 要替换成审批数据库、工作流服务或可信确认结果，必须绑定用户、租户、工具、参数、过期和一次性。SIDE\_EFFECTS 计数要替换成 Mock 支付网关、测试数据库或消息记录，保证拒绝时真实副作用为零。AuditSink\.records 要替换成 append\-only 审计表、事件流或日志平台，决策与执行可关联，不泄漏敏感数据。模拟退款 Handler 要替换成真实支付接口，幂等键、超时、状态查询和对账必须保留。递归正则脱敏要替换成字段投影、数据分类和统一的 Masking Middleware，进入模型和普通日志前已处理。本地函数 Tool 可以替换成内部 HTTP 或 MCP Tool，但所有执行仍然要走同一个 invoke。



迁移时最危险的做法，是为了“方便”让真实 Agent Loop 直接调用新的 HTTP 客户端，而保留离线测试只测旧 Handler。正确的方式是把 HTTP 或 MCP 调用封装为新的 Handler，仍然由同一个 ToolDefinition、PermissionEngine 和 Runtime 管理。



### 8\.3 怎样证明唯一入口不是一句架构口号？

是什么？唯一入口不是类图上只有一个箭头，而是任何真实副作用都只能从 ToolRuntime\.invoke\(\) 到达 Handler。



要证明？因为最常见的旁路往往来自“临时”代码。CLI 为了方便直接调用函数，Provider Adapter 自己写工具分发，后台重放任务绕过审批，测试为了简单只测 Handler——这些都可能绕过唯一入口。



那怎么证明呢？可以用三类证据验收。

第一，静态搜索项目中 Handler 的引用，除注册和 Runtime 以外不得直接调用。用 grep 命令搜索 handler 的调用点，比如 `rg "\.handler\(|handlers\[|execute_refund\(" src tests`。

第二，给 Handler 加副作用计数，分别从 CLI、离线 Demo 和 Provider Adapter 发起拒绝调用，全部必须为零。运行 pytest 确认副作用计数符合预期。

第三，在 Runtime 入口记录 trace，所有真实执行都必须出现 prepare、decision、execute 和 finalize 四个阶段的事件。



Know\-how 是把旁路检查放入代码评审和 CI，而不是依赖团队记忆。新增 MCP、HTTP 或定时任务时，适配器只负责协议转换，不能复制权限逻辑。完整运行链可以替换 Provider 和下游实现，但 invoke\(\) 的不变量与安全测试必须保持稳定。



### 8\.4 本阶段小结

从 What 看，Runtime 是所有工具执行的控制平面。从 Why 看，它消除入口漂移和检查顺序漂移。从 How 看，用 prepare → execute → finalize 固定生命周期，并让所有调用方共用 invoke\(\)。从 Know\-how 看，要用静态引用、跨入口集成测试和 Trace 证明没有旁路，而不是只看代码结构。

## 九、怎样把权限流程图写成 Python 状态机？

先给结论：**先定义输入、三态输出、规则优先级和不可绕过的硬性要求，再把这条决策链接入 Runtime。**



### 9\.1 第一步：把权限结果从布尔值升级成三态协议

**如果 ****`check_permission()`**** 只返回 ****`True`**** 或 ****`False`****，系统无法表达“当前动作有资格，但必须暂停并等待用户确认”。开发者通常会用异常文本或额外布尔值弥补，最后让 Agent Loop 依赖字符串解析。**

**三态协议把控制意图写进类型：**

```Python
class DecisionAction(StrEnum):
    ALLOW = "allow"
    DENY = "deny"
    CONFIRM = "confirm"


@dataclass(frozen=True, slots=True)
class PermissionDecision:
    action: DecisionAction
    code: str
    reason: str
    source: Literal[
        "rule",
        "mode",
        "whitelist",
        "rbac",
        "business",
        "approval",
        "risk",
        "default",
    ]
```

三种状态分别驱动确定动作：

|决策|Runtime|Agent Loop|handler|
|---|---|---|---|
|`allow`|进入 execute|等待 Tool Result|可以执行|
|`deny`|形成稳定失败结果|修参、换方案、换主体或结束|必须零调用|
|`confirm`|保存待确认动作并返回审批要求|暂停，进入 Web/CLI/工作台|必须零调用|

这里要特别强调一点：CONFIRM 不是让模型再生成一句“用户已经确认”。真正的确认要离开模型上下文——界面向用户展示工具名、业务对象、金额和影响范围，服务端根据当前登录身份生成审批记录，下一次调用只携带可信的 approval\_id，由 Runtime 重新匹配完整参数。

source 字段也不是装饰品。它让审计和测试能够区分：同样的 DENY 到底来自显式规则、plan 模式、白名单、RBAC 还是业务状态。线上如果 PERMISSION\_DENIED 突然激增，排障方向跟 BUSINESS\_RULE\_DENIED 是完全不同的。

### 9\.2 第二步：先写决策表，再写代码

在动手写条件分支以前，先把优先级写成一张表。这张表是人和 AI 协作的接口——人定义顺序和业务语义，AI 根据表生成代码。

|优先级|检查|通过后去哪里|失败动作|为什么在这里|
|---|---|---|---|---|
|1|deny 规则|plan|deny|硬拒绝不能被任何便捷模式覆盖|
|2|plan 写/Shell|执行白名单|deny|只读契约优先于普通授权|
|3|执行期白名单|RBAC|deny|防止旧调用和旁路|
|4|RBAC|业务预检查|deny|主体无资格时不读取更多敏感业务状态|
|5|资源归属与状态|强制审批|deny|不确认本来就非法的动作|
|6|高风险参数绑定审批|bypass|allow / confirm / deny|高风险动作不能被普通 allow 跳过|
|7|bypass 模式|allow 规则|allow|只跳过普通确认|
|8|allow 规则|风险检查|allow|宽泛放行只能在硬边界后生效|
|9|通用危险模式|默认允许|confirm / deny|教学兜底，不能替代沙箱|
|10|默认策略|execute|allow|所有确定性检查通过|

这张表让代码评审有了客观依据。评审者不再只问“有没有做权限检查”，而是可以具体地问：deny 是否先于 bypass？高风险审批是否先于 allow？业务检查失败时 handler 是否零调用？

### 9\.3 第三步：实现不可交换的决策顺序

决策表是人的业务设计，下面的代码才适合交给 AI 实现。为了防止模型在生成过程中把安全优先级重新排序，提示词必须把顺序、输出和副作用约束逐条写死。

生成 PermissionEngine\.decide 的提示词可以这样写：

```Markdown
请根据下方决策表，只生成 Python 3.12 的 `PermissionEngine.decide()` 与对应 pytest；不要生成 Agent Loop，不要调用 handler。

输出必须是 `PermissionDecision(action, code, reason, source)`，其中 action 只有 allow、deny、confirm。

检查顺序不可交换：
1. 显式 deny；
2. plan 模式拒绝 write/shell；
3. 执行期工具白名单；
4. RBAC 权限；
5. 资源归属和业务状态 precheck；
6. 高风险或 requires_approval 的参数绑定审批；
7. bypass 只跳过普通确认；
8. 普通 allow 规则；
9. 危险模式兜底；
10. 显式默认策略。

硬约束：任何 deny/confirm 路径都不得调用 handler；身份、租户、权限和 approval_id 只从 ExecutionContext 读取；审批绑定用户、租户、工具、规范化参数、过期时间和一次性消费；每个分支返回稳定错误码和 source。测试必须证明 deny 优先于 bypass、高风险审批优先于 allow、RBAC 拒绝时副作用为零。

先复述你理解的不可交换顺序，再输出最小实现；不得用一个宽泛 try/except 把策略错误变成 allow。
```

完整 `PermissionEngine.decide()` 的核心如下：

```Python
async def decide(
    self,
    tool: ToolDefinition,
    arguments: ArgsModel,
    context: ExecutionContext,
) -> PermissionDecision:
    # 1. deny-first
    if any(
        rule.effect == "deny" and self._rule_matches(rule, tool, arguments)
        for rule in self._rules
    ):
        return PermissionDecision(
            DecisionAction.DENY, "DENY_RULE", "命中 deny 规则", "rule"
        )

    # 2. plan 是执行层只读契约
    if context.mode is PermissionMode.PLAN and tool.policy.effect is not Effect.READ:
        return PermissionDecision(
            DecisionAction.DENY,
            "PLAN_MODE_DENIED",
            "plan 模式禁止写操作和 Shell",
            "mode",
        )

    # 3. 执行期白名单
    if tool.name not in context.allowed_tools:
        return PermissionDecision(
            DecisionAction.DENY,
            "TOOL_NOT_ALLOWED",
            "工具不在本轮执行白名单",
            "whitelist",
        )

    # 4. RBAC
    if tool.policy.permission not in context.permissions:
        return PermissionDecision(
            DecisionAction.DENY,
            "PERMISSION_DENIED",
            f"缺少业务权限 {tool.policy.permission}",
            "rbac",
        )

    # 5. 业务预检查
    try:
        if tool.precheck:
            await tool.precheck(arguments, context)
    except PolicyDenied as error:
        return PermissionDecision(
            DecisionAction.DENY, error.code, str(error), "business"
        )

    # 6. 高风险或显式要求确认的工具
    if tool.policy.requires_approval or tool.policy.risk is Risk.HIGH:
        if self._approvals.consume(
            context.approval_id, context, tool.name, arguments
        ):
            return PermissionDecision(
                DecisionAction.ALLOW,
                "APPROVED",
                "审批与当前动作完全匹配",
                "approval",
            )
        if context.mode is PermissionMode.DONT_ASK:
            return PermissionDecision(
                DecisionAction.DENY,
                "APPROVAL_REQUIRED",
                "非交互模式无法完成高风险确认",
                "approval",
            )
        return PermissionDecision(
            DecisionAction.CONFIRM,
            "APPROVAL_REQUIRED",
            "需要确认本次具体动作",
            "approval",
        )

    # 7. bypass 只在硬边界之后生效
    if context.mode is PermissionMode.BYPASS_PERMISSIONS:
        return PermissionDecision(
            DecisionAction.ALLOW,
            "BYPASS_ALLOWED",
            "跳过普通确认",
            "mode",
        )

    # 8. 普通 allow 规则
    if any(
        rule.effect == "allow" and self._rule_matches(rule, tool, arguments)
        for rule in self._rules
    ):
        return PermissionDecision(
            DecisionAction.ALLOW, "ALLOW_RULE", "命中 allow 规则", "rule"
        )

    # 9. 通用危险模式兜底
    if tool.policy.effect is Effect.SHELL and _is_dangerous_shell(arguments.command):
        return PermissionDecision(
            DecisionAction.CONFIRM,
            "DANGEROUS_OPERATION",
            "危险 Shell 需要确认",
            "risk",
        )

    # 10. 默认允许
    return PermissionDecision(
        DecisionAction.ALLOW,
        "DEFAULT_ALLOWED",
        "所有确定性检查均已通过",
        "default",
    )
```

这段代码的重点不是 Python 语法，而是每一个 return 都在 handler 以前终止路径。PermissionEngine 不调用退款 API，也不修改数据库——它只做确定性决策。Runtime 只有收到 ALLOW 才进入 execute。



这段代码位于 Runtime 的 prepare 阶段，解决的是“这次候选动作应该 allow、deny 还是 confirm”这个问题。审查的时候重点要看 deny\-first、plan、双重白名单、RBAC、precheck、审批和 bypass 的相对位置。如果顺序写错了，代码即使类型正确、普通测试能跑通，仍然可能发生越权、无效确认或者审批绕过。AI 可以按决策表补分支，但定义优先级和每个失败的业务后果，这是人的责任。



### 9\.4 第四步：用具体故障解释为什么顺序不可交换

光说“顺序重要”太抽象，我们来看几种具体的错误顺序会导致什么后果。



第一种错误是先匹配 allow，再匹配 deny。假设规则允许 run\_shell 的 pytest 前缀，同时禁止受保护目录的删除操作。如果一个宽泛的 allow 规则先返回了，后面的 deny 就永远没有机会执行。修复的办法不是增加更多的正则表达式，而是从架构上保证 deny\-first。



第二种错误是把 bypass 当成“超级管理员”。bypass 的合理用途是在受控自动化环境里跳过低风险的重复确认，但它不能绕过组织权限、跨租户边界和硬拒绝。如果 bypass 写在 RBAC 以前，任何拿到模式开关的人都能越权操作。



第三种错误是先审批、后业务预检查。用户可能会被要求确认一个已经退款、金额超限或者属于其他租户的订单。即使最终没有执行，这种确认本身已经泄露了资源存在性，还造成了糟糕的用户体验。



第四种错误是会话白名单覆盖高风险业务动作。在 Coding Agent 里，“本会话允许重复读取这个目录”可能是合理的；但在业务 Agent 里，“本会话允许任意退款”几乎一定不合理。所以我们的实现把强制审批放在 bypass 和 allow 前面，并且使用一次性记录。



第五种错误是用 Prompt 来实现 plan 模式。模型大多数时候可能遵守“只分析不修改”的指令，但 Prompt 注入、模型幻觉或者历史 Tool Call 都可能产生写操作。plan 必须由 Runtime 检查 ToolPolicy\.effect，不能依赖模型自觉。



### 9\.5 第五步：把状态机接入唯一 Runtime，而不是散落在 Agent Loop

Agent Loop 和 Runtime 的职责边界要分清楚。Agent Loop 负责驱动多轮推理——解析 Provider 的 Tool Call，构造内部 ToolCall，然后交给 Runtime。

Runtime 负责执行工具——参数校验、权限决策、调用 Handler、结果治理，最后返回结构化的 ToolResult。Loop 只根据这个结果决定继续、暂停还是结束。



所有调用都必须经过同一个入口：

```Python
result = await runtime.invoke(
    ToolCall(
        tool_call_id=provider_call.id,
        name=provider_call.function.name,
        arguments=json.loads(provider_call.function.arguments),
    ),
    execution_context,
)
messages.append(result.to_tool_message())
```

Agent Loop 不感知每个工具的权限细节，不自己判断角色，也不决定哪个工具能执行。

这些事全部由 Runtime 的 prepare → execute → finalize 三阶段来处理。

这样 Loop 就不会随着业务规则增长变成一个臃肿的分发器，测试和 CLI 也能走完全相同的路径。



### 9\.6 本阶段小结

这一节我们从一张流程图出发，把它变成了一段可执行的 Python 代码。



回头看一下我们做了哪五步。

第一步，把权限结果从 True/False 升级成 ALLOW、DENY、CONFIRM 三态，让系统能够表达“有资格但需要确认”这个状态。

第二步，在写任何代码之前，先画决策表，把十个检查步骤的优先级定死——这张表是人和 AI 协作的接口。

第三步，用严格的提示词把决策表翻译成 PermissionEngine，每个 return 都卡在 handler 之前，顺序写死，不能交换。

第四步，用五个具体的故障案例解释为什么顺序不能乱——deny 必须在 bypass 前面，审批必须在业务检查后面。

第五步，把状态机接到唯一 Runtime 上，确保 Agent Loop 不自己做分发。



验收标准很简单：每一个 DENY 和 CONFIRM 分支，handler 调用次数都必须为零。能做到这一点，状态机就真正起作用了。

## 十、怎样让 AI 生成这套 Python 治理代码？

先给结论：**高质量提示词不是把“请写得安全一点”说得更客气，而是把对象边界、可信数据来源、执行顺序、失败语义和验收证据写成不可误解的工程约束。**



这一节不是要教一条“万能 Prompt”，而是展示怎样把人的业务判断转换成 AI 可以执行的工程任务。为什么要单独讲生成过程？因为前面章节的大段代码如果只给最终答案，学员只能复制粘贴。看到最小规格、局部提示词、失败测试和组装顺序之后，才具备迁移到自己项目里的能力。



完整工程不是一次生成的。我们推荐把代码分成五个可验证的产物，每个产物都需要明确分工：

|产物|生成前人必须决定|AI 适合补全|本轮验收|
|---|---|---|---|
|对象与 Schema|模型字段、可信字段、错误协议|数据类、Pydantic Model|伪造字段被拒绝|
|PermissionEngine|决策表、优先级、审批语义|分支与规则匹配样板|deny/confirm 副作用为零|
|ToolRuntime|prepare/execute/finalize 顺序|统一入口与异常映射|所有入口无法旁路|
|测试与故障注入|业务硬性要求、副作用证据|pytest 夹具与参数化|删除护栏时测试会红|
|Provider 组装|消息协议、Tool Call/Result 关联|DeepSeek Adapter 与流式解析|真实模型仍调用同一 invoke|

具体的操作顺序是“先局部、后组装”。4\.4 的提示词生成策略对象，7\.1 生成审计对象，第八节生成 Runtime 骨架，第九节生成权限状态机，第十一节先生成测试，最后才用完整提示词核对文件、依赖和 Agent Loop。每轮都限制可修改的文件范围，运行上一轮的全部测试，再进入下一轮。不要把下面整段提示词直接丢给 AI 然后接受第一版答案。

## 三、内部对象

必须实现：

实现三个工具：

- `get_order`：只读，权限 `order:read`，返回订单状态、可退金额、客户邮箱和模拟 access token；
- `create_refund`：高风险写操作，权限 `refund:create`，必须人工确认；
- `run_shell`：教学模拟 Shell，权限 `shell:run`，只增加计数，不启动真实子进程。

模型参数只能包含业务候选字段。`user_id`、`tenant_id`、角色、权限、`approved` 和 `approval_id` 不得出现在工具 Pydantic Model 中，只能来自服务端 `ExecutionContext`。

所有参数模型继承严格基类，使用 `extra="forbid"` 和严格类型。退款参数约束订单号格式、金额范围和原因长度。

## 五、权限三态与固定顺序

定义 `allow | deny | confirm`，每个决策包含稳定 `code`、安全 `reason` 和 `source`。必须严格按下列顺序实现，不得交换：

1. deny 规则；
2. plan 模式拒绝写操作和 Shell；
3. 执行期重新检查 `allowed_tools`；
4. RBAC 权限；
5. 租户资源归属、状态和额度等业务 precheck；
6. 高风险或 `requires_approval` 工具检查一次性参数绑定审批；
7. `bypassPermissions` 只跳过普通确认，不能跳过 1—6；
8. allow 规则；
9. 教学用危险 Shell 模式检测；
10. 默认允许。

deny 必须优先于 allow 和 bypass；plan 必须由执行层强制只读；高风险业务审批不能被 allow、bypass 或会话白名单跳过。

## 六、审批要求

审批记录必须绑定：

- `user_id`
- `tenant_id`
- `tool_name`
- 递归排序、稳定 JSON 序列化后的参数 SHA-256
- 过期时间
- 一次性 `used` 状态

批准 100 元后把金额改成 399 元，旧审批必须失效；同一个审批成功执行一次后不得重放。禁止使用 `approved=true`。

## 七、Runtime 执行要求

`ToolRuntime.invoke()` 严格分成：

1. prepare：查找工具、Pydantic 校验、权限三态决策；
2. execute：只有 allow 才调用 handler，根据只读/幂等属性选择超时与重试；
3. finalize：字段投影、递归脱敏、审计并生成 ToolResult。

任何 deny 或 confirm 都必须保证 handler 零调用。参数、权限、审批和 deny 失败不得自动重试。只读或真正幂等的工具才允许有限重试；非幂等写操作超时返回 `TIMEOUT_UNKNOWN`，禁止直接重放。

## 八、结果与审计

返回模型以前必须脱敏邮箱以及键名包含 token、secret、password、authorization 的字段。审计至少保存：

- `trace_id`
- `tool_call_id`
- 工具名
- 用户和租户
- decision / execution 阶段
- allow / deny / confirm / executed / failed
- 稳定错误码
- 参数键名
- 延迟

审计不得默认保存 Token、完整 Prompt、未经脱敏的客户资料和 Python traceback。ToolResult 必须保留原始 `tool_call_id`。

## 九、DeepSeek 可选模式

使用 `AsyncOpenAI`，从 `DEEPSEEK_API_KEY` 读取密钥；Base URL 默认 `https://api.deepseek.com`；模型从 `DEEPSEEK_MODEL` 读取，默认 `deepseek-v4-flash`；设置 `stream=True`，逐块输出文本并按 Tool Call index 累积流式名称与参数；通过 `extra_body={"thinking":{"type":"disabled"}}` 关闭思考输出。

Agent Loop 最多 8 轮。模型工具列表必须来自 Runtime 的发现期白名单；解析 Provider Tool Call 后调用同一个 `ToolRuntime.invoke()`；Tool Result 以 `role="tool"` 和原 `tool_call_id` 回填。不要在 Agent Loop 中用 if/else 分发 handler。

## 十、安全边界

- 不执行真实 Shell，不连接真实支付接口；
- 演示可以用最小危险命令正则，但注释必须说明生产环境优先使用窄工具、AST、沙箱、最小权限和 fail-closed；
- 不允许模型声明身份、租户、权限或审批；
- 不把 handler 暴露给模型；
- 不在 handler 以后才做权限判断；
- 不把原始异常堆栈交给模型；
- 不省略 `tool_call_id`；
- 不为离线测试另造一套 Fake Runtime。

## 十一、离线演示结果

至少输出：

1. 查询成功且邮箱、Token 已脱敏；
2. 未审批退款返回 `APPROVAL_REQUIRED` 和 confirm；
3. 参数绑定审批后退款成功；
4. 伪造 `user_id`、`approved` 被 Pydantic 拒绝；
5. bypass 模式下 deny 规则仍拒绝危险 Shell；
6. plan 模式拒绝退款；
7. 最终只有一次退款副作用，Shell 副作用为零，并打印审计数量。

## 十二、测试验收

至少实现八项测试：

1. deny-first：bypass 不能覆盖硬拒绝；
2. plan：写工具在审批与 allow 以前被拒绝；
3. Schema：模型不能伪造身份和确认；
4. RBAC：权限不足时 handler 零调用；
5. 审批改参：批准 100 元后改成 399 元，旧审批失效；
6. 结果边界：敏感字段脱敏，审计保留 tool_call_id；
7. 双重白名单：模型不可见，旧 Tool Call 在执行时也被拒绝；
8. 一次性审批：第一次执行成功，第二次重放返回 confirm，副作用总数为 1。

测试必须断言副作用计数，不得只断言中文错误文本。最后给出依赖说明、运行命令和预期输出摘要。
```

### 10\.1 这份提示词为什么比“帮我写个安全 Runtime”更有效？

因为它先定义人的决策，再要求 AI 写实现。它明确了：

1. 哪些对象存在，各自负责什么；

2. 哪些字段来自模型，哪些只能来自服务端；

3. 权限不是布尔，而是三态协议；

4. 十条决策顺序不可交换；

5. 高风险审批的业务语义；

6. Runtime 的唯一入口与三个阶段；

7. 超时和重试依据副作用，而不是错误字符串；

8. 模型、用户和审计看到不同结果；

9. 演示必须输出什么；

10. 测试必须用什么副作用证据验收。

AI 面对这种提示词时，不需要猜“安全”意味着什么，只需要在确定边界内补全代码。即便生成结果仍有问题，工程师也能逐项审查和运行测试，而不是阅读几百行代码凭感觉判断。



### 10\.2 AI 生成以后应该怎样审查？

第一轮看对象边界：handler 是否出现在模型工具描述里了？身份和审批字段有没有混入参数 Model？Agent Loop 有没有绕过 Runtime？

第二轮看执行顺序：Pydantic 校验是否在 handler 之前？deny 是否先于 bypass？plan 是否由执行层检查？审批是否绑定参数并且先于 allow？

第三轮看失败语义：写操作超时之后是不是盲目重试了？异常会不会泄漏 traceback？confirm 有没有被错误地当成 allow？

第四轮看证据：拒绝相关的测试是否断言了 handler 零调用？脱敏测试是否同时检查了模型结果和审计记录？一次性审批是否真的防重放？

只有审查和测试都通过了，AI 生成的代码才能从“候选实现”升级为可以进入项目的实现。



### 10\.3 为什么不建议一次让 AI 生成全部生产能力？

完整提示词是最终目标的规格说明，但不代表第一次对话就要让模型同时对接 IAM、审批中心、数据库、支付、沙箱和日志平台。一次性范围太大，AI 会在没有真实接口的地方自己假设，生成“看起来完整、实际上没法验证”的胶水代码。



更稳妥的方式是拿完整提示词当边界清单，然后分五轮执行。

```Plaintext
轮次 1：只生成对象模型、Pydantic Schema 与 ToolResult
轮次 2：加入 PermissionEngine 和拒绝路径测试
轮次 3：组装唯一 ToolRuntime 与离线调用骨架
轮次 4：加入审批、超时恢复、脱敏、审计和完整测试
轮次 5：接 DeepSeek Provider，并证明没有旁路 Runtime
```

每一轮都要求 AI 只修改明确指定的文件，输出变更说明和新增的测试。工程师运行上一轮的全部测试之后再继续。完整提示词管理总体边界，小提示词管理单轮变更，两者并不矛盾。



### 10\.4 怎样把测试失败有效地反馈给 AI？

不要只说“测试没过，继续修”。高质量的反馈应该包含：失败命令、最小错误输出、预期的硬性要求、允许修改的范围和禁止退化的条目。举个例子：

```Markdown
运行 `python -m pytest -q` 后，
`test_approval_is_bound_to_canonical_arguments` 失败：
第二次调用仍执行了退款，`refund_executions == 2`。

预期：审批一次性消费，第二次返回 `APPROVAL_REQUIRED`，副作用总数为 1。
只允许修改 `ApprovalStore.consume()` 和相关测试夹具；
不得删除参数摘要校验，不得把高风险工具改成无需审批。
请先解释根因，再给最小补丁。
```

这种反馈方式让 AI 围绕证据来修复，而不是通过删除断言、放宽规则或者改写测试来“制造绿色”。工程师还要检查修复是否只处理了当前样例——比如硬编码了一个 `approval_once`，而没有修复通用的一次性语义。



### 10\.5 怎样防止 AI 通过修改测试逃避约束？

在生成式开发里，有一个常见的反模式：测试失败之后，AI 同时修改实现和验收标准，最后把红线给删掉了。解决方法包括：

- 把业务硬性要求单独列在任务开头，声明未经批准不能改动；

- 单轮只允许修改实现文件，测试变更需要单独解释；

- 在 CI 里把关键安全测试保护起来，或者由独立的评审者审批；

- 检查断言是否仍然包含对真实副作用的验证，而不是只剩错误文本；

- 使用变异测试——故意注入错误，证明测试真的会红。

AI 可以优化测试结构，但不能自己降低验收标准。最终负责合并的人必须能解释每一条被修改的安全断言。

### 10\.6 生成代码时哪些上下文应该提供，哪些不应该？

应该提供的是最小真实接口：认证中间件怎么生成 Context、支付客户端是否支持幂等键、审批服务返回什么 ID、Repository 如何带租户条件。没有这些事实，AI 只能靠猜。

不应该提供的是生产密钥、完整客户数据、未经处理的内部日志和大段无关的仓库上下文。可以提供脱敏后的样例、接口 Protocol、测试夹具和错误契约。上下文越多不等于质量越高——跟当前硬性要求无关的代码反而会增加污染和误改的风险。

这正是 Harness 思维在 AI Coding 中的延伸：给模型足够完成局部任务的能力和上下文，但不授予不必要的真实世界权限。



最后，提示词本身也要版本化，但不需要维护一套庞大的 SDD。保留目标、硬性要求、运行命令和验收结果就够了，实现细节由代码来表达。每次修改提示词之后，用同一组测试和演示输出做回归，才能判断新提示词是真的提升了实现质量，还是只生成了更长的代码。

如果 AI 返回的代码用到了不存在的 Python Pi API、把 approved 放进了参数、或者省略了副作用测试，应该立即依据硬约束拒绝，而不是继续用补丁提示词在错误的架构上修修补补。架构边界错误的时候，重新生成通常比局部堆补丁更可靠。



### 10\.7 完整代码具体怎样分五轮生成？

第一轮只生成对象与 Schema。提示词只给 ToolCall、ToolResult、ExecutionContext 的字段表和两个工具的参数，不允许出现 handler 实现。运行 Schema 测试，确认 `user_id`、`tenant_id`、`approved` 等未知字段被拒绝。这样先固定住“模型候选数据”和“服务端事实”之间的边界。



第二轮生成 PermissionEngine。把 9\.2 的决策表和三项副作用测试交给 AI，只允许修改权限相关的文件。先故意运行失败测试，再让 AI 补上 deny\-first、plan、白名单、RBAC 和审批的逻辑。这个时候还没有 Provider、日志平台和真实支付接口，问题范围足够小。



第三轮生成 Runtime。提供已经通过测试的对象和 PermissionEngine 接口，要求组装 prepare、execute、finalize 三个阶段；handler 用内存计数器实现。运行 CLI、离线 Demo 和测试共用入口的检查，证明没有新的工具分发旁路出现。



第四轮生成恢复、脱敏、审计和完整测试。每次只增加一个硬性要求：只读瞬时失败有限重试；写超时返回未知状态；敏感结果进入 Context 前脱敏；decision 和 execution 都能按 ID 关联。每增加一项就回归前面的所有测试。



第五轮才接 DeepSeek。Provider Adapter 只负责把 SDK 的 Tool Call 转成内部的 ToolCall，把 `ToolResult.to_tool_message()` 回填到消息里；禁止复制权限逻辑和 handler 分发。这个时候即使网络或者模型行为不稳定，核心治理仍然可以离线确定性测试。



最后再用一条组装提示词核对完整文件：

```Markdown
请组装已经分别通过测试的四个文件：requirements.txt、pyproject.toml、tool_governance_demo.py、tests/test_tool_governance.py。

不要重写已经通过测试的业务决策。请完成以下工作：
1. 合并对象、PermissionEngine、ToolRuntime、AuditSink 与离线场景；
2. 添加可选 DeepSeek Adapter，Provider 只做协议转换；
3. 确认 CLI、离线 Demo、pytest、Provider 全部调用同一个 `ToolRuntime.invoke()`；
4. 输出完整文件，不使用省略号；
5. 给出 py_compile、离线运行和 pytest 命令；
6. 若接口冲突，先列出冲突，不得擅自放宽 deny、审批、脱敏或副作用断言。

组装后逐项对照八项测试，不得通过删除测试、修改错误码或把 handler 变成空函数制造通过。
```

这五轮的目的不是为了多和 AI 聊几次，而是为了让每一轮只有一个主要的失败来源。AI 输出的内容越大，人就越难审查。把生成分层以后，每一段代码都有上游规格、下游测试和明确的修改边界。



### 10\.8 本阶段小结

这一节讲的是提示词工程的实践——不是写得更客气，而是把人的判断翻译成机器可执行的约束。

从 What 看，提示词是把业务硬性要求、接口和验收翻译成 AI 编码任务的临时工程规格。从 Why 看，它减少了模型自行猜测身份来源、策略顺序和失败语义的空间。从 How 看，分五轮走：先对象、再决策、再 Runtime、再测试与治理、最后 Provider 组装。从 Know\-how 看，每一轮都要限制修改范围、运行红绿测试、检查副作用，并且防止 AI 把验收标准一起改了。



真正可复用的不是某一份很长的 Prompt，而是“最小规格 → 局部生成 → 失败测试 → 最小修复 → 全量回归 → 最终组装”这套方法。



下一节不再讨论代码看起来是否完整，而是用八项安全测试来证明它保护了哪些真实的业务边界。



---

## 十一、八项安全测试：它们分别训练人的什么业务能力？

先给结论：**安全测试不能只断言 Runtime 返回了某个错误码，还要证明不允许发生的真实副作用确实没有发生。测试的核心不是 AI 会不会写 assert，而是工程师能否定义有效证据。**



那这八项测试是什么呢？它们不是普通的“代码覆盖率用例”，而是八条可执行业务硬性要求：宽泛模式不能覆盖硬拒绝，只读模式不能产生写副作用，模型不能伪造身份，越权不能触达支付，审批不能改参或重放，敏感结果不能传播，过期的 Tool Call 不能执行。



那为什么必须先讲测试，再看完整代码呢？因为 AI 生成的实现可能结构很漂亮、类型也正确、成功路径能跑通，却可能把权限检查放在了 Handler 之后，或者把审批简化成了一个布尔值。只有测试提前定义好错误码、Handler 调用次数、数据库记录和消息内容，开发者才有客观的标准去判断代码到底能不能用。



那什么时候运行这些测试呢？每次 AI 补一条规则、每次调整策略顺序、每次替换真实下游、每次修改 Provider Adapter，都要先跑离线核心测试。接真实模型的集成测试可以单独运行，但不能让网络波动影响到安全相关的红绿信号。



先看一下生成这八项安全测试的提示词：

```Markdown
请只为现有 Python ToolRuntime 生成 pytest，不修改生产实现。

业务硬性要求：
1. deny-first：bypass 下危险 Shell 仍被拒绝，Shell handler 次数为 0；
2. plan：写工具在审批和 allow 以前被拒绝，退款次数为 0；
3. Schema：`user_id`、`tenant_id`、`approved` 等未知字段返回 INVALID_ARGUMENT；
4. RBAC：缺少 refund:create 时返回 PERMISSION_DENIED，退款次数为 0；
5. 审批改参：100 元审批不能执行 399 元退款；
6. 结果边界：邮箱和 Token 不进入 Tool Result，tool_call_id 与审计仍可关联；
7. 双重白名单：工具发现期不可见，历史 Tool Call 执行时仍被拒绝；
8. 一次性审批：第一次成功，第二次返回 confirm，副作用总数保持 1。

要求：每项测试同时断言稳定错误码或 action 与真实副作用；使用构造数据，不使用生产客户信息；不得 mock 掉 `ToolRuntime.invoke()`；不得通过修改实现、清空 handler 或放宽预期让测试通过。先输出测试设计表，再输出完整测试文件。
```

注意，这个提示词刻意要求“只生成测试”。工程师先审查这些测试是不是真正击中了业务红线，再允许 AI 补实现。如果 AI 同时改生产代码，红灯和修复会混在一次提交里，你就很难判断测试是否曾经真正失败过。

运行命令很简单：

```Bash
cd python-tool-governance-v11
python -m py_compile tool_governance_demo.py tests/test_tool_governance.py
python -m pytest -q
```

预期输出是八个点，全部通过。

```Plaintext
........                                                                 [100%]
8 passed
```

那这八项测试跟人的能力是怎么对应的呢？我们逐一来看。

第一项，deny\-first 对抗 bypass。它验证的是硬拒绝优先、Shell handler 零调用。训练的是人的什么能力？设计不可被宽泛模式覆盖的安全红线。

第二项，plan 拒绝写操作。它验证只读承诺由 Runtime 强制执行。训练的是把交互模式转成执行层契约的能力。

第三项，Schema 拒绝伪造字段。它验证模型不能声明自己是管理员或者自己批准自己。训练的是区分候选参数与可信事实的能力。

第四项，RBAC 拒绝副作用。它验证没有权限的时候退款次数为 0。训练的是用业务副作用来验证鉴权位置的能力。

第五项，审批参数变化失效。它验证 100 元的审批不能执行 399 元的退款。训练的是定义“用户究竟批准了什么”的能力。

第六项，脱敏与调用关联。它验证 Token 和邮箱不进模型，但 ID 仍然可追踪。训练的是平衡最小披露与可观测性的能力。

第七项，双重白名单。它验证工具对模型不可见，旧的调用也无法执行。训练的是区分“能力收敛”与“最终授权”的能力。

第八项，一次性审批防重放。它验证同一个审批只产生一次退款。训练的是对高风险动作建模时效和次数的能力。



好，这是总览。接下来我们深入几个关键问题。



### 11\.1 为什么错误码断言不够？

你看下面这个测试，看起来通过了，但它不能证明安全：

```Python
result = await runtime.invoke(refund_call, unauthorized_context)
assert result.code == "PERMISSION_DENIED"
```

问题在哪？如果错误实现是先调用退款 Handler，然后再检查权限、返回错误，这条测试仍然是绿的。所以必须增加一个断言：

```Python
assert SIDE_EFFECTS["refund_executions"] == 0
```

在真实项目里，这个计数器要替换成 Mock 支付网关的调用次数、测试数据库的记录、消息队列的事件、邮件发送记录、文件哈希或者子进程启动次数。选择哪种证据取决于具体的业务动作，而不是测试框架本身。

所以 11\.1 的核心就是建立“结果断言 \+ 副作用断言”的双重证据。



### 11\.2 为什么测试顺序本身也体现学习路径？

这八项测试的顺序是有讲究的，不是随便排的。



前两项先锁住规则优先级，确保便捷模式不能覆盖硬边界。第三、四项建立输入边界和身份边界。第五、第八项深入审批的语义。第六项控制结果的传播。第七项防止发现期和执行期的策略漂移。



这个顺序恰好对应了 Harness、TDD、Loop 的增量路径。每增加一条规则，就有一条明确失败的测试。修复以后全量回归，确保新的审批逻辑没有破坏旧的 RBAC，新的脱敏逻辑没有丢掉 tool\_call\_id。



这个顺序建立了学习和开发的节奏，但八项核心测试仍然只是最小基线。不同业务有不同的竞态、下游和恢复风险，生产项目需要根据自己的故障模型继续扩展。



### 11\.3 生产项目还应该增加哪些故障测试？

根据你的业务风险，至少还要考虑这些：

同一订单两次并发退款，有没有被资源锁、唯一约束或者幂等键保护？

只读的瞬时失败，是不是只重试了规定的次数，并且受到总 deadline 的限制？

非幂等的写操作超时，是不是返回 TIMEOUT\_UNKNOWN，而不是自动重放？

审批过期、跨用户、跨租户、跨工具，是不是全部失效？

审计系统不可用的时候，高风险动作是 fail\-closed 还是走事务 Outbox？

下游响应里如果包含嵌套的 Token、邮箱或者大段文本，模型和日志是不是都安全？

取消信号有没有真正传播到 HTTP 请求、数据库查询和子进程？

MCP Server 在等待确认期间下线了，或者策略收紧了，执行期会不会重新拒绝？



这些测试的价值在于把线上事故提前变成可重复的实验。

AI 可以帮你补测试夹具，但人必须决定哪些失败值得模拟、什么样的结果算安全。

故障场景列出来以后，还要验证测试本身是不是真的能捕获错误。下一节我们就来谈这个。

### 11\.4 怎样证明测试不是“碰巧通过”？

可以做一次最小的故障注入。临时把 PermissionEngine 里的 bypass 判断移到 deny 之前，test\_deny\_first\_beats\_bypass\_permissions 必须变红。把 extra="forbid" 改成允许未知字段，Schema 测试必须变红。删除审批的 used 更新，防重放测试必须变红。

这种方法接近轻量级的变异测试——主动植入一个已知错误，检查测试能不能捕获它。如果测试在安全规则被删除以后仍然全绿，说明断言没有覆盖真正的硬性要求。

还要检查失败信息能不能帮助定位问题。好的测试名称会直接描述属性，比如“deny\-first 在 bypass 下仍拒绝”，失败的时候同时显示错误码和副作用次数。烂的测试只叫 test\_case\_5，失败以后你得重新读一遍整个实现才能知道它在测什么。

变异验证证明了单个断言有捕获能力，但不同测试层回答的是不同的问题。接下来要区分函数级规则、Runtime 组合、真实下游和线上行为，不能拿一种测试替代全部证据。

### 11\.5 单元测试、集成测试和线上 Eval 分别证明什么？

单元测试适合固定 PermissionEngine 的规则顺序、审批摘要和脱敏函数。Runtime 集成测试证明 prepare、execute、finalize 组合以后，拒绝路径不产生副作用。真实 Provider 验收证明 DeepSeek 的 Tool Call 和 Tool Result 格式没有旁路。线上 Eval 则观察真实任务中的参数错误率、确认率、人工接管率和业务成功率。

这四层不能互相替代。单元测试全绿，不代表支付客户端的幂等键真的生效了。线上成功率高，也不代表没有敏感数据泄漏。安全属性需要确定性测试，业务效果需要 Trace 和 Eval，两者共同构成 Agent 的质量基线。

测试层次明确以后，最后还要治理测试数据和执行环境。否则为了验证隐私而复制真实隐私数据，或者让并行测试共享同一个租户，测试本身就会制造新的风险和不确定性。

### 11\.6 测试数据为什么也要遵守租户和隐私边界？

不要为了“更真实”就把生产订单、客户邮箱和访问令牌复制到测试夹具里。使用构造的订单号、假邮箱和显式的假 Token。测试脱敏的时候验证模式和字段，而不是依赖真实的个人信息。

集成测试要使用沙箱支付账户、隔离的数据库 Schema 和专用的租户。清理逻辑也要有边界，不能让测试结束命令去删除共享环境里的数据。测试本身也是 Harness 的一部分，同样需要最小权限和可恢复性。

这八项核心测试应该保持快速和确定，便于每次 AI 修改以后立即运行。涉及真实 Provider 的用例放到单独的集成层，避免网络波动让安全回归失去可信度。开发者要能在一分钟内得到红绿反馈，才能维持小步 Loop 的节奏——而不是等十分钟以后才发现最早的 RBAC 已经被破坏了。

### 11\.7 本阶段小结

回顾一下这一节。

从 What 看，安全测试是业务硬性要求的可执行证据，不是单纯为了覆盖 Python 分支。从 Why 看，它能发现“返回了正确的错误码，但副作用已经发生了”这类表面正确、实际危险的实现。从 How 看，每项测试同时检查控制结果、真实副作用和 ID/审计关联，并从单元、Runtime 集成、真实下游到线上 Eval 分层验证。

从 Know\-how 看，要先让测试变红再补实现；关键测试未经评审不能让 AI 删除或放宽；通过最小变异证明测试确实能捕获护栏缺失；测试数据使用构造租户和假敏感字段；离线核心保持快速确定，Provider 和下游故障的测试放在独立的集成层。

这八项测试训练的始终是人的业务能力：定义什么绝对不能发生、观察什么证据才能证明、失败以后哪条路径可以恢复。AI 能快速生成夹具和断言，但它不能替业务负责人决定——“重复退款”和“超时未知”这两个结果，哪个可以接受。

下一节，我们会把这些证据转成学员可以实际完成的四层验收标准。

## 十二、怎样才算学会？用口头、代码、审查和迁移四层验收

先给结论：**学会不是背下 700 行 Python，而是能解释主链、补关键骨架、审查错误实现、迁移业务策略，并用测试证明真实副作用边界。**

这一节把“听懂”拆解成可以验收的行为：能讲、能补、能审、能迁移、能接真实模型。



为什么要分层呢？因为只会复述概念，不代表能写出控制点；只会运行现成的 Demo，不代表能发现越权；只会复制退款案例，不代表能迁移到邮件、文件或者数据库的场景。



那什么时候用这套验收标准呢？课程结束时用来自测，团队引入新 Tool 时用来做评审清单，面试或者代码走查时用来判断工程师是否真正理解 Agent 的可信边界。验收的重点始终是人的判断和证据，而不是脱离 AI 去默写全部实现。



四层不是四选一。口头验收检查概念模型，代码验收检查主链位置，审查验收检查故障推理，迁移验收检查业务建模。最后再用项目验收证明真实 Provider 没有绕过这些边界。



### 12\.1 口头验收：两分钟讲清主链

不看稿画出：

```Plaintext
模型 Tool Call
→ Pydantic 参数对象
→ deny / plan / 白名单 / RBAC / 业务检查 / 审批
→ allow 才进入 handler
→ 超时与恢复
→ 投影、脱敏、审计
→ 带 tool_call_id 的 Tool Result
```

然后回答几个问题。为什么 Tool Call 不是执行许可证？为什么发现期和执行期都要检查白名单？为什么 `approved=true` 是无效的？为什么退款超时不能统一重试？



验收的时候不要求背类名，但要求每个箭头都能说清楚输入、输出和失败后果。比如 Pydantic 的输出是业务参数对象，不是最终授权；confirm 的输出是暂停协议，不是 Handler 成功了；Tool Result 里的 `tool_call_id` 是协议关联键，不是业务退款单号。



关键是用一个故障把主链串起来。比如：模型伪造了 `approved=true`，它会在哪一步被拒绝？Handler 的调用次数是多少？审计留下了什么？下一轮模型能做什么？能把一个故障从头到尾讲通，才说明不是机械背图。



口头模型建立以后，下一层要求在不看完整答案的情况下，补出关键控制点。



### 12\.2 代码验收：补出 Runtime 的关键检查点

给一个 `invoke()` 的空骨架，能够补出这几个关键步骤：根据工具名查找定义；Pydantic 校验并结构化错误；PermissionEngine 做三态决策；deny 和 confirm 时保证 Handler 零调用；根据只读和幂等属性驱动超时与重试；finalize 做脱敏与审计；返回结果保留原始的 `tool_call_id`。



不要求默写辅助函数，但必须知道每一步为什么放在这里，交换顺序会产生什么故障。



代码验收的时候，可以先把接口和失败测试给出来，让学员补最小实现。比如提供 `ToolCall`、`ToolDefinition` 和 `PermissionDecision`，把 `invoke()` 的实现藏起来。学员可以让 AI 生成 Pydantic 错误归一化的样板代码，但必须亲自决定校验、权限、execute 和 finalize 的顺序，然后让八项测试全部变绿。



关键是要限制修改范围：不能通过直接返回预期错误码、清空 Handler 或者修改测试来制造通过。补全以后，故意交换 RBAC 和 execute 的顺序，测试必须变红。



能补正确路径只是起点。下一层要能从一份“能够运行”的错误实现里，推导出真实的后果。



### 12\.3 审查验收：指出 AI 错误实现的后果

拿到一份可以运行的 AI 代码，要能找出这些问题：



`user_id`、`tenant_id`、`approved` 出现在了模型参数里；Agent Loop 直接调用了 `handlers[tool_name]`；allow 或 bypass 写在了 deny 前面；plan 只写在 System Prompt 里，没有在执行层落地；Pydantic 允许未知字段，或者校验放在了 Handler 之后；审批只绑定了工具名，没有绑定参数和一次性状态；所有异常统一重试三次；原始结果同时写入了模型上下文和日志；错误的 Tool Result 丢掉了 `tool_call_id`；测试只看错误文本，不看副作用。



不仅要指出“这样不安全”，还要说清楚具体的后果：跨租户读取、金额篡改、重复退款、日志泄密、Provider 消息关联失败。



审查的时候按四轮走：先看可信数据来源，再看权限与执行顺序，再看超时和结果传播，最后看测试是否证明了副作用。每个问题都要给出“触发输入 → 错误路径 → 真实副作用 → 应增加的测试”，不能只贴一个“安全风险”的标签。



优先发现架构级的旁路。Agent Loop 直接调 Handler、身份来自模型参数、审批不绑定参数——这些问题比某个正则表达式写得不完整要严重得多。在错误的架构上不断让 AI 打补丁，通常只会产生更多互相矛盾的分支。



能够审查以后，还要换一个业务场景，验证这些判断是否真的可以迁移。



### 12\.4 迁移验收：换业务以后重新做判断

把 `create_refund` 替换成其他工具，比如发邮件、改工单状态、读服务日志、删项目文件。

迁移的时候要重新填写 ToolPolicy，重新定义 Pydantic 参数、业务 precheck、审批摘要、恢复策略和审计证据。如果只是把 `refund:create` 改个名字就复制过去，那就没有真正掌握治理能力。

举个例子。迁移到 `send_customer_email`，读写分类的逻辑仍然适用，但资源键从订单变成了租户加收件人集合，幂等证据从退款单变成了发送记录，审批摘要需要绑定模板、收件人和附件，超时以后要查询消息服务状态而不是直接重发。

What 和 Why 的框架是相同的，但 How 和 Know\-how 必须根据新的副作用重新做。

迁移验收的通过标准不是代码行数，而是一张新的策略表、至少四条业务硬性要求，以及能捕获错误的测试。

完成离线迁移以后，最后才接真实 Provider，验证协议层没有形成新的旁路。



### 12\.5 项目验收：真实模型也不能绕开 Runtime

最后设置 `DEEPSEEK_API_KEY`，让模型产生真实的 Tool Call。验收的重点不是看模型是否聪明地选中了工具，而是确认这几件事：

模型可见的工具列表来自发现期白名单；Provider 的 Tool Call 被正确转换成内部对象；所有调用都进入了同一个 Runtime；Tool Result 保留了原始的 tool\_call\_id；模型连续修正参数的时候，拒绝路径仍然没有产生副作用。

验收的时候先跑离线八项测试，再启动真实模型。保存一条完整的 Trace，对照 `model_tool_call → schema → policy → tool_start/tool_end → result_redacted → tool_message` 这个顺序。然后主动构造伪造字段、无权限退款和需要确认的动作，确认 Provider 模式和离线模式得到的是相同的治理语义。

要把模型表现和 Runtime 安全分开评估。模型没选对工具，属于规划或工具描述的问题；模型选了危险工具但被稳定拒绝，说明治理边界工作正常；Tool Result 格式不符合 Provider 要求，属于协议适配的问题。不要因为最终答案不理想就随意放宽权限，也不要因为模型这次“很听话”就省略攻击测试。

完成这四层验收，才说明学员从“能运行 Demo”升级为“能对 Agent 行为负责”。



### 12\.6 本阶段小结

回顾一下验收标准。

从 What 看，掌握标准由口头、代码、审查、迁移和真实项目五类证据组成。从 Why 看，它防止把记忆 API、复制 Demo 或者一次成功运行误认为工程能力。从 How 看，先讲清主链，再补最小骨架，然后审查故障路径、迁移业务策略，最后接 Provider 验证唯一 Runtime。



从 Know\-how 看，每一层验收都必须落到可观察的证据上：顺序错误会造成什么副作用？哪条测试会变红？哪个 ID 能关联结果？超时以后怎么查询真实状态？



允许使用 AI 生成样板和修复候选，但学员必须能定义问题、限制实现、验证结果，并对业务损失负责。

到这里，整个课程已经从“为什么需要治理”推进到了“怎样设计、怎样生成、怎样测试、怎样验收”。最后一节，我们会把整条主线压缩成一个开发者面对任何新 Tool 都能复用的决策框架。

## 十三、本节总结：AI 生成动作，工程师定义真实世界的边界

回到开头。MCP 可以快速接入能力，模型可以快速选择工具，AI Coding 可以快速生成 Runtime 样板。但系统是否可靠，最终取决于开发者能不能回答六个问题：

1. 哪些工具应该对当前 Agent 和租户可见？

2. 当前登录主体是否拥有业务资格？

3. 用户确认的到底是哪一个具体动作？

4. 允许执行以后，怎样控制 SQL、Shell、超时、重试和并发？

5. 什么结果可以进入模型、用户界面和审计？

6. 用什么副作用证据证明规则真正生效？

技术主链可以压缩成一句话：

```Plaintext
不可信 Tool Call → Pydantic 与业务预检查 → deny-first、plan、双重白名单、RBAC 与参数绑定审批 → 按副作用、幂等和资源关系执行 → 投影、脱敏、审计和稳定错误码 → 可验证的 Tool Result
```

学习主链也可以压缩成一句话：

```Plaintext
人定义业务硬性要求 → 最小规格记录边界 → Harness 固化唯一执行路径 → TDD 证明副作用与结果边界 → Loop 每次增加一条规则 → AI 加速实现、修复和重构
```

所以，这一节不要求谁比 AI 更快地写完 Runtime。真正的岗位能力是：面对一个新业务动作，能够判断它是否应该成为 Tool，决定谁可以申请、什么时候确认、失败后怎样恢复、结果如何传播，并把这些决定写成确定性程序和可回归的测试。



还要看到一个更深层的变化：AI Coding 把大量编码工作外包给模型以后，开发者的价值并没有消失，而是从“亲手写出每个分支”前移到业务意图和风险建模，后移到测试、Trace、评测和生产责任。



以前评价一个工具实现，可能主要看代码结构、抽象和单元测试。现在还要评价模型能看见什么、Tool Call 能控制什么、可信 Context 来自哪里、失败是否会诱发下一轮错误动作。工具治理不是传统权限中间件的简单换名，而是把权限、上下文、执行和 Agent Loop 放到同一条因果链中观察。



开发者与 AI 的职责可以这样收口：



当 AI 生成一段代码时，最有价值的问题不再是“这段代码像不像资深工程师写的”，而是：它是否满足硬性要求？测试能否在删除护栏后变红？所有入口是否真的共用 Runtime？线上 Trace 能否解释一次决定？出现未知副作用时是否有恢复路径？



学完后可以做一次最终自检。 面对任何新 Tool，先回答这八个问题：

1. 它为什么必须成为 Tool，而不是普通应用逻辑？

2. 模型应该控制哪些参数，哪些事实必须由服务端注入？

3. 它的副作用、影响范围、可逆性和数据敏感度是什么？

4. 谁有资格申请，哪种情况必须确认或直接拒绝？

5. 超时和重复调用会造成什么真实后果？

6. 结果需要进入哪些出口，每个出口最少需要什么信息？

7. 哪一条测试可以证明拒绝时副作用为零？

8. 所有入口是否都经过同一个 Runtime？

如果这些问题没有答案，继续堆 Prompt 或让 AI 生成更多代码，只会放大不确定性。如果答案已经变成策略、Runtime 和测试，模型能力越强，工程杠杆就越大。



上一节 MCP 解决的是“能力怎样标准化接入”，这一节解决的是“接入以后怎样安全执行”。下一节，Agent Tool Runtime 会把 Registry、工具发现、Snapshot、治理策略、执行和 Agent Loop 收进完整基础设施。到那时，这一节的 PermissionEngine 与 finalize 不会消失，而是成为 Runtime 中不可绕过的治理阶段。

class ApprovalStore:
    def __init__(self) -> None:
        self._records: dict[str, ApprovalRecord] = {}

    def approve(
        self,
        approval_id: str,
        context: ExecutionContext,
        tool_name: str,
        arguments: ArgsModel | Mapping[str, Any],
        *,
        ttl_seconds: float = 300,
    ) -> None:
        self._records[approval_id] = ApprovalRecord(
            approval_id=approval_id,
            user_id=context.user_id,
            tenant_id=context.tenant_id,
            tool_name=tool_name,
            digest=_approval_digest(tool_name, arguments),
            expires_at=time.time() + ttl_seconds,
        )

    def consume(
        self,
        approval_id: str | None,
        context: ExecutionContext,
        tool_name: str,
        arguments: ArgsModel,
    ) -> bool:
        record = self._records.get(approval_id or "")
        valid = bool(
            record
            and not record.used
            and record.expires_at >= time.time()
            and record.user_id == context.user_id
            and record.tenant_id == context.tenant_id
            and record.tool_name == tool_name
            and record.digest == _approval_digest(tool_name, arguments)
        )
        if valid and record:
            record.used = True
        return valid

def _redact(value: Any) -> Any:
    if isinstance(value, Mapping):
        return {
            key: "***" if re.search(r"token|secret|password|authorization", key, re.I) else _redact(item)
            for key, item in value.items()
        }
    if isinstance(value, (list, tuple)):
        return [_redact(item) for item in value]
    if isinstance(value, str):
        return re.sub(r"[\w.+-]+@[\w.-]+\.[A-Za-z]{2,}", "***@***", value)
    return value


class PermissionEngine:
    """固定优先级的三态权限状态机。"""

    def __init__(self, rules: Sequence[PermissionRule], approvals: ApprovalStore) -> None:
        self._rules = tuple(rules)
        self._approvals = approvals

    def _rule_matches(self, rule: PermissionRule, tool: ToolDefinition, arguments: ArgsModel) -> bool:
        if rule.tool_name != tool.name:
            return False
        if rule.target_prefix is None:
            return True
        return tool.canonical_target(arguments).startswith(rule.target_prefix)

    async def decide(
        self,
        tool: ToolDefinition,
        arguments: ArgsModel,
        context: ExecutionContext,
    ) -> PermissionDecision:
        # 1. deny-first：硬拒绝不能被 allow 或 bypass 覆盖。
        if any(
            rule.effect == "deny" and self._rule_matches(rule, tool, arguments)
            for rule in self._rules
        ):
            return PermissionDecision(DecisionAction.DENY, "DENY_RULE", "命中 deny 规则", "rule")

        # 2. plan 是执行层只读契约，而不是一句系统提示词。
        if context.mode is PermissionMode.PLAN and tool.policy.effect is not Effect.READ:
            return PermissionDecision(
                DecisionAction.DENY,
                "PLAN_MODE_DENIED",
                "plan 模式禁止写操作和 Shell",
                "mode",
            )

        # 3. 发现阶段过滤后，执行阶段仍然要重新检查白名单。
        if tool.name not in context.allowed_tools:
            return PermissionDecision(
                DecisionAction.DENY,
                "TOOL_NOT_ALLOWED",
                "工具不在本轮执行白名单",
                "whitelist",
            )

        # 4. 只相信认证层生成的 ExecutionContext。
        if tool.policy.permission not in context.permissions:
            return PermissionDecision(
                DecisionAction.DENY,
                "PERMISSION_DENIED",
                f"缺少业务权限 {tool.policy.permission}",
                "rbac",
            )

        # 5. 资源归属、状态和额度在 handler 之前验证。
        try:
            if tool.precheck:
                await tool.precheck(arguments, context)
        except PolicyDenied as error:
            return PermissionDecision(DecisionAction.DENY, error.code, str(error), "business")

        # 6. 高风险业务写操作必须使用一次性、参数绑定审批。
        if tool.policy.requires_approval or tool.policy.risk is Risk.HIGH:
            if self._approvals.consume(context.approval_id, context, tool.name, arguments):
                return PermissionDecision(
                    DecisionAction.ALLOW,
                    "APPROVED",
                    "审批与当前用户、租户、工具和参数完全匹配",
                    "approval",
                )
            if context.mode is PermissionMode.DONT_ASK:
                return PermissionDecision(
                    DecisionAction.DENY,
                    "APPROVAL_REQUIRED",
                    "非交互模式无法完成高风险确认",
                    "approval",
                )
            return PermissionDecision(
                DecisionAction.CONFIRM,
                "APPROVAL_REQUIRED",
                "需要确认本次具体动作",
                "approval",
            )

        # 7. bypass 只能跳过普通确认，不能跳过前面的硬边界。
        if context.mode is PermissionMode.BYPASS_PERMISSIONS:
            return PermissionDecision(
                DecisionAction.ALLOW,
                "BYPASS_ALLOWED",
                "跳过普通确认，但硬边界已经全部通过",
                "mode",
            )

        # 8. allow 规则只在 deny、plan、白名单、RBAC 和审批以后生效。
        if any(
            rule.effect == "allow" and self._rule_matches(rule, tool, arguments)
            for rule in self._rules
        ):
            return PermissionDecision(DecisionAction.ALLOW, "ALLOW_RULE", "命中 allow 规则", "rule")

        # 9. 正则只是教学兜底，生产中必须配合窄工具、AST 与沙箱。
        if tool.policy.effect is Effect.SHELL and _is_dangerous_shell(
            str(getattr(arguments, "command", ""))
        ):
            if context.mode is PermissionMode.DONT_ASK:
                return PermissionDecision(
                    DecisionAction.DENY,
                    "DANGEROUS_OPERATION",
                    "危险 Shell 在非交互模式下被拒绝",
                    "risk",
                )
            return PermissionDecision(
                DecisionAction.CONFIRM,
                "DANGEROUS_OPERATION",
                "危险 Shell 需要用户确认",
                "risk",
            )

        return PermissionDecision(
            DecisionAction.ALLOW,
            "DEFAULT_ALLOWED",
            "所有确定性检查均已通过",
            "default",
        )


class ToolRuntime:
    """模型、CLI、测试与未来 Provider 共用的唯一工具执行入口。"""

    def __init__(
        self,
        tools: Sequence[ToolDefinition],
        permission_engine: PermissionEngine,
        audit_sink: AuditSink,
    ) -> None:
        self._tools = {tool.name: tool for tool in tools}
        self._permission_engine = permission_engine
        self._audit = audit_sink

    def model_tools(self, context: ExecutionContext) -> list[dict[str, Any]]:
        """发现期白名单：减少模型可见能力，不把 handler 暴露给模型。"""

        return [
            tool.to_model_tool()
            for tool in self._tools.values()
            if tool.name in context.allowed_tools
        ]

    async def invoke(self, call: ToolCall, context: ExecutionContext) -> ToolResult:
        started = time.perf_counter()
        tool = self._tools.get(call.name)
        if tool is None:
            return self._rejected(call, context, "TOOL_NOT_FOUND", "工具不存在")

        # prepare-1：Pydantic 把不可信字典转换成 handler 可接收的业务对象。
        try:
            arguments = tool.parameters_model.model_validate(call.arguments)
        except ValidationError as error:
            details = [
                {"path": ".".join(map(str, item["loc"])), "message": item["msg"]}
                for item in error.errors(include_url=False)
            ]
            return self._rejected(call, context, "INVALID_ARGUMENT", details)

        # prepare-2：执行期重新授权，返回 allow / deny / confirm。
        decision = await self._permission_engine.decide(tool, arguments, context)
        self._audit.append(
            AuditRecord(
                trace_id=context.trace_id,
                tool_call_id=call.tool_call_id,
                tool_name=call.name,
                user_id=context.user_id,
                tenant_id=context.tenant_id,
                phase="decision",
                decision=decision.action,
                code=decision.code,
                argument_keys=tuple(sorted(call.arguments)),
            )
        )
        if decision.action is not DecisionAction.ALLOW:
            return ToolResult(
                tool_call_id=call.tool_call_id,
                tool_name=call.name,
                ok=False,
                action=decision.action,
                code=decision.code,
                content=decision.reason,
            )

        # execute：只有通过全部确定性检查后，handler 才可能产生副作用。
        try:
            raw = await self._execute_with_recovery(tool, call.tool_call_id, arguments, context)
        except TimeoutError:
            code = "TIMEOUT" if tool.policy.effect is Effect.READ or tool.policy.idempotent else "TIMEOUT_UNKNOWN"
            return self._failed(call, context, started, code, "工具执行超时")
        except PolicyDenied as error:
            return self._failed(call, context, started, error.code, str(error))
        except Exception as error:  # 生产中映射异常类型，不把 traceback 交给模型。
            return self._failed(call, context, started, "TOOL_ERROR", str(error))

        # finalize：先投影与脱敏，再形成模型能看见的 ToolResult。
        safe_content = _redact(dict(raw))
        latency_ms = round((time.perf_counter() - started) * 1_000)
        self._audit.append(
            AuditRecord(
                trace_id=context.trace_id,
                tool_call_id=call.tool_call_id,
                tool_name=call.name,
                user_id=context.user_id,
                tenant_id=context.tenant_id,
                phase="execution",
                decision="executed",
                code="OK",
                argument_keys=tuple(sorted(call.arguments)),
                latency_ms=latency_ms,
            )
        )
        return ToolResult(call.tool_call_id, call.name, True, DecisionAction.ALLOW, "OK", safe_content)

    async def _execute_with_recovery(
        self,
        tool: ToolDefinition,
        tool_call_id: str,
        arguments: ArgsModel,
        context: ExecutionContext,
    ) -> Mapping[str, Any]:
        retries = tool.policy.max_retries if tool.policy.effect is Effect.READ or tool.policy.idempotent else 0
        for attempt in range(retries + 1):
            try:
                async with asyncio.timeout(tool.policy.timeout_seconds):
                    return await tool.handler(tool_call_id, arguments, context)
            except TransientToolError:
                if attempt == retries:
                    raise
                await asyncio.sleep(min(0.05 * (2**attempt), 0.2))
        raise AssertionError("unreachable")

    def _rejected(
        self,
        call: ToolCall,
        context: ExecutionContext,
        code: str,
        content: Any,
    ) -> ToolResult:
        self._audit.append(
            AuditRecord(
                trace_id=context.trace_id,
                tool_call_id=call.tool_call_id,
                tool_name=call.name,
                user_id=context.user_id,
                tenant_id=context.tenant_id,
                phase="decision",
                decision="deny",
                code=code,
                argument_keys=tuple(sorted(call.arguments)),
            )
        )
        return ToolResult(call.tool_call_id, call.name, False, DecisionAction.DENY, code, content)

    def _failed(
        self,
        call: ToolCall,
        context: ExecutionContext,
        started: float,
        code: str,
        content: Any,
    ) -> ToolResult:
        self._audit.append(
            AuditRecord(
                trace_id=context.trace_id,
                tool_call_id=call.tool_call_id,
                tool_name=call.name,
                user_id=context.user_id,
                tenant_id=context.tenant_id,
                phase="execution",
                decision="failed",
                code=code,
                argument_keys=tuple(sorted(call.arguments)),
                latency_ms=round((time.perf_counter() - started) * 1_000),
            )
        )
        return ToolResult(call.tool_call_id, call.name, False, DecisionAction.DENY, code, content)

def build_runtime(

async def run_deepseek_agent(user_input: str) -> None:
    """可选真实模型闭环；所有工具调用仍经过同一个 ToolRuntime.invoke。"""

    from openai import AsyncOpenAI

    api_key = os.environ.get("DEEPSEEK_API_KEY")
    if not api_key:
        raise RuntimeError("请先设置环境变量 DEEPSEEK_API_KEY")

    runtime, _, _ = build_runtime()
    context = base_context(allowed_tools=frozenset({"get_order"}))
    client = AsyncOpenAI(api_key=api_key, base_url=os.getenv("DEEPSEEK_BASE_URL", "https://api.deepseek.com"))
    model = os.getenv("DEEPSEEK_MODEL", "deepseek-v4-flash")
    messages: list[dict[str, Any]] = [
        {
            "role": "system",
            "content": "你是订单助手。只根据工具结果回答，不得伪造订单事实。",
        },
        {"role": "user", "content": user_input},
    ]

    for _round in range(8):
        stream = await client.chat.completions.create(
            model=model,
            messages=messages,
            tools=runtime.model_tools(context),
            stream=True,
            extra_body={"thinking": {"type": "disabled"}},
        )
        text_parts: list[str] = []
        pending_calls: dict[int, dict[str, Any]] = {}

        async for chunk in stream:
            if not chunk.choices:
                continue
            delta = chunk.choices[0].delta
            if delta.content:
                text_parts.append(delta.content)
                print(delta.content, end="", flush=True)
            for delta_call in delta.tool_calls or []:
                current = pending_calls.setdefault(
                    delta_call.index,
                    {"id": "", "type": "function", "function": {"name": "", "arguments": ""}},
                )
                if delta_call.id:
                    current["id"] = delta_call.id
                if delta_call.function:
                    if delta_call.function.name:
                        current["function"]["name"] += delta_call.function.name
                    if delta_call.function.arguments:
                        current["function"]["arguments"] += delta_call.function.arguments

        provider_calls = [pending_calls[index] for index in sorted(pending_calls)]
        assistant_message: dict[str, Any] = {"role": "assistant", "content": "".join(text_parts)}
        if provider_calls:
            assistant_message["tool_calls"] = provider_calls
        messages.append(assistant_message)

        if not provider_calls:
            print()
            return

        if text_parts:
            print()
        for provider_call in provider_calls:
            try:
                raw_arguments = json.loads(provider_call["function"]["arguments"])
            except json.JSONDecodeError:
                raw_arguments = {"_invalid_json": provider_call["function"]["arguments"]}
            result = await runtime.invoke(
                ToolCall(provider_call["id"], provider_call["function"]["name"], raw_arguments),
                context,
            )
            print(f"[tool_result] {result.tool_name} {result.code}")
            messages.append(result.to_tool_message())

    raise RuntimeError("Agent Loop 超过最大轮数 8")


def parse_args() -> argparse.Namespace:
    parser = argparse.ArgumentParser(description="Python 工具治理与权限状态机演示")
    parser.add_argument("--agent", action="store_true", help="使用 DeepSeek 运行真实 Agent Loop")
    parser.add_argument("--input", default="请查询订单 ord_1001 的状态和可退金额")
    return parser.parse_args()


if __name__ == "__main__":
    cli_args = parse_args()

## 附录 B：Pi 0\.83\.0 生命周期对应关系与参考边界

Python 实现没有调用 Pi API。下面的对应关系只用于确认生命周期责任，避免把课程自定义 Runtime 说成 Pi 内置的 RBAC 或审批能力：

|Python v11|Pi 0\.83\.0 参考位置|共同边界|
|---|---|---|
|Pydantic `model_validate()`|`packages/ai/src/utils/validation.ts`|参数在 Hook 与 handler 以前校验|
|`PermissionEngine.decide()`|`beforeToolCall` / `agent-loop.ts`|前置阶段可阻断，阻断后不进入 execute|
|`ToolDefinition.handler`|`AgentTool.execute`|只完成通过治理后的业务动作|
|`asyncio.timeout` 与重试|execute 接收的取消信号及工具执行策略|期限与取消应继续传向下游|
|finalize 脱敏与审计|`afterToolCall`|结果写回 Agent Context 以前可以治理|
|`ToolResult.to_tool_message()`|Tool Result Message|保留原始 Tool Call 关联|

需要特别区分“框架提供的位置”和“业务工程师提供的规则”。Pi 提供 Schema 校验、前后 Hook 和执行生命周期；工具白名单、tenant 级 RBAC、业务资源检查、审批摘要、错误码、脱敏字段与审计语义，都是本课程 Harness 增加的业务治理能力。

权限状态机参考：[Claude Code from Scratch：权限与安全](https://diwang.info/claude-code-from-scratch/#/docs/06-permissions)。本节继承 deny\-first、plan 只读、权限模式、危险操作检查和用户确认的思想；针对业务 Agent 增加双重白名单、RBAC、资源归属和不可被 bypass 跳过的一次性参数绑定审批。

读源码与参考实现的目的不是背文件路径，而是验证三个稳定边界：handler 以前必须可以拒绝；执行中必须根据副作用控制超时、重试和并发；结果进入模型以前必须可以投影、脱敏和审计。
