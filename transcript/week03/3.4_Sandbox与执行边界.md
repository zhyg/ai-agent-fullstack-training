# 3\.4 Sandbox 与执行边界

## 一、概念：**Loop 决定下一步，Sandbox 限定影响范围。**



大家好，欢迎来到第三章的第四节。

前面三节，我们已经让 Agent 能连续执行任务、调整计划，也能在中断以后核对现场、继续工作。接下来要解决的，是把这样的 Agent 放到真实项目里以后，它究竟可以动哪些东西。



先说结论：**Agent 的执行能力越完整，我们越需要提前限定它的影响范围。这个范围必须由程序和执行环境强制落实。**



举个例子。你让 Agent 修复登录问题，它要搜索代码、修改函数、运行测试。测试失败以后，它判断是环境问题，于是开始清理缓存、重装依赖。这时候，**如果清理目录算错了**，或者依赖脚本执行了额外操作，一次普通的修复任务，就可能影响其他项目，甚至读到不该读取的密钥等， 一次修复变成了灾难。



很多时候搞砸事情不是外部攻击或有意破坏。像是模型误解任务、代码有缺陷、工作目录不对，都可能造成不可恢复的后果。再加上 Agent 会持续循环，一次小错误的判断还可能被重复执行，循环放大。



所以，今天我们关注三个问题：**Agent 能碰哪里？越界以后谁拦？出了问题怎样查清楚？**



### 1\.1 从任务出发，先确定允许的副作用

我们沿用“修复登录问题”这个任务。先不讨论用什么沙箱，先写出任务需要的权限。

|能力|本次任务的边界|需要防住的问题|
|---|---|---|
|文件|项目源码可读，指定工作区可写，真实凭证不提供|改错仓库、读取密钥、覆盖其他任务产物|
|命令|允许受控测试与构建，高风险动作单独判断|清理越界、执行未知脚本、进程长期不退出|
|网络|无需要就关闭；有需要只开放指定目的地|数据外发、访问未授权内网或生产接口|
|资源|限制运行时间、CPU、内存和输出量|无限循环、资源耗尽、日志挤满上下文|

这张表的价值，是把“注意安全”变成了可以实现、可以验收的要求。



但大家可能会问：前面已经有 Runtime 和执行前的 pre 节点检查，为什么还需要 Sandbox？

**因为执行前检查决定“这个动作能不能开始”，Sandbox 限制“动作开始以后，最多能影响哪里”，两者需要配合。**



比如，pre 节点允许执行 `pytest`，但测试会运行项目代码，其中仍可能包含删除文件、读取凭证或访问网络的操作。我们很难在执行前穷尽这些行为，所以还需要 Sandbox 在运行过程中强制限制文件、网络和资源的访问范围。这样，即使前置判断有遗漏，或者被允许的程序出现意外，影响也能被限制在事先划定的边界内。



### 1\.2 怎样把执行前检查、沙箱和任务管理串起来？



明确了为什么需要 Sandbox，接下来就要看：它怎样与前面学过的 Runtime、Loop 和状态机配合？

**一次完整的工具执行，需要先判断能不能做，再限制执行范围，最后把结果和证据交回任务流程。这些能力由 Harness 统一组织。**



执行前，**Tool Runtime** 检查用户权限、参数和审批要求，决定是否放行。执行时，**Sandbox** 限制程序能访问的文件、网络和资源，把实际影响控制在授权范围内。执行结束或发生异常后，**Harness** 负责组织结果回写、审计记录和状态更新，让 pi 的 Loop 能据此继续、调整计划或等待人工处理。



这里要特别注意：**Harness 统筹整个过程，Runtime 和 Sandbox 是其中协同工作的组件。**

例如，一条命令超时，不能只向模型返回“执行失败”，还要终止实际执行、记录已有副作用；如果结果无法确认，就衔接上一节的恢复机制，先核对现场，再决定下一步。



这些连接代码可以让 AI 帮我们完成，但允许什么、拒绝什么，以及怎样证明边界生效，需要工程师确定。



下面通过两段演示把这条链路看清楚：先用 **pi\-sandbox** 观察本地工具如何被限制，再用独立 Python 程序调用 **OpenSandbox**，让任务代码在 Docker 容器中执行。重点看三个结果：**正常操作能完成，越界操作被阻止，执行结果能够核对。**

### 2\.2 写入配置，并检查实际生效范围

```JSON
{
  "enabled": true, // 启用沙箱
  "sandboxUserShell": true, // 在 pi 中手动输入的 !命令也要经过沙箱
  "permissionPromptTimeoutSeconds": 30, // 授权提示等待 30 秒，超时保持拒绝
  "allowBrowserProcess": false, // 不开启浏览器进程所需的额外权限
  "network": { // 网络访问规则
    "allowedDomains": [], // 本文件不添加允许访问的域名；未获授权的域名访问会触发提示
    "deniedDomains": [], // 本文件不添加硬性禁止的域名；不代表允许访问所有域名
    "allowLocalBinding": false, // 不允许在本地绑定监听端口，例如启动 HTTP 服务
    "allowAllUnixSockets": false, // 不全面放开 Unix Socket，避免扩大本机服务访问权限
    "allowUnauthenticatedSocksProxy": false // 不开启免认证的 SOCKS 代理访问
  },
  "filesystem": { // 文件系统访问规则
    "denyRead": ["/Users", "/home", "/root"], // 默认限制读取这些用户目录；明确的允许规则可覆盖它
    "allowRead": ["."], // 允许读取当前工作目录及其内容，也可覆盖上面的目录读取限制
    "allowWrite": ["./artifacts"], // 允许读写当前工作目录下的 artifacts 目录
    "denyWrite": [".env.demo", ".pi"] // 禁止修改这两个路径；优先于允许写入规则，不弹出放行提示
  }
}
```



我们让项目可读，产物目录可写，并保护演示配置和策略目录。为了让跨平台行为更容易核对，这里使用具体路径。



启动 pi，进入后输入：

```Plaintext
/sandbox
```

先确认沙箱处于启用状态，再检查显示的权限。项目配置会与全局配置合并，因此项目里写了空域名列表，不代表已有的全局域名授权自动被清掉。演示前要确认没有遗留的宽泛授权，尤其不能有允许全部域名的配置。



### 2\.3 顺序执行三个动作，观察实际结果

第一个动作，验证合法操作没有被误拦。把下面这句话发给 pi：

```Plaintext
使用 write 工具创建 artifacts/ok.txt，内容为 sandbox-ok。
完成后使用 read 工具回读，报告实际读到的内容。
```

预期是写入成功，也能回读。沙箱要保留完成任务所需的能力，否则只是把 Agent 关停了。



第二个动作，验证受保护文件不能被修改：

```Plaintext
这是一个仅含假数据的边界验收。
请使用 write 工具把 .env.demo 改为 DEMO_ONLY=changed。
若工具拒绝，报告拒绝原因，不申请修改策略，也不要换工具重试。
```

预期是工具拒绝写入。在另一个普通终端进入同一目录，检查：

```Bash
cat .env.demo
```

它应该仍然是 `DEMO_ONLY=original`。注意，验收证据是文件没变；如果模型只是口头说“我不能修改”，还没有验证到工具边界。



第三个动作，观察网络授权。在 pi 输入框中直接输入下面这条命令，开头的 `!` 也要保留：

```Plaintext
!curl --max-time 5 -I https://example.com
```

这能直接测试用户 Shell 入口。前面设置了 `sandboxUserShell: true`，所以这个入口也应受约束。



出现权限提示后，选择 **Abort，保持阻断**。这里要观察的是沙箱的拒绝信息，普通的连接超时不能单独证明策略生效。



如果想验证授权差异，可以再执行一次，仅选择本次会话放行，观察请求是否获得 HTTP 响应。不要为了让演示成功而扩大成全局放行。网络自身不可用时，批准以后仍可能失败，要把网络故障与权限拒绝分开判断。



### 2\.4 一个工程判断

刚才三次操作，分别回答了“该做的能不能做”“不该改的有没有改”“额外权限由谁决定”。我们已经从配置文件走到了行为证据。



这里有两点要注意。第一，`denyRead` 不是“任何情况下都不能读”：如果后面又给了读取权限，这些文件仍可能被读到。所以，真实密钥、生产配置这类敏感文件，最好不要放进 Agent 能接触的环境。第二，装了 pi\-sandbox，不代表自己新增的工具、接入的 MCP 服务也都受它限制，还要逐一确认这些工具在哪里执行、能访问什么。



本地沙箱用起来很方便，Agent 改完代码，你在编辑器里马上就能看到。但它改的也是你电脑上的真实文件，沙箱允许修改的地方，仍然可能被改坏。因此，遇到陌生仓库，或者要让 Agent 无人值守地批量执行任务时，更合适的做法是给它一个独立的工作环境，完成后再把需要的结果取回来。



下面看第二种方式：让任务代码在 Docker 容器里运行。



## 三、OpenSandbox：用独立 Python 程序驱动 Docker 沙箱

### 3\.1 准备环境

### 3\.3 保存并运行完整 Python 程序

把下面代码保存为 `sandbox_demo.py`。它做一个小型登录判断测试：测试代码在容器里执行，结果写入容器文件，再由宿主程序显式取回。

```Python
import asyncio
import json
import os
import sys
from datetime import timedelta
from pathlib import Path

from opensandbox import Sandbox
from opensandbox.config import ConnectionConfig
from opensandbox.models import WriteEntry


async def main():
    # 这份标记只创建在宿主工作区，不挂载进容器。
    marker = Path("host-only-marker.txt").resolve()
    marker.write_text("host-original", encoding="utf-8")
    connection = ConnectionConfig(
        domain="127.0.0.1:8080",
        protocol="http",
        api_key=os.environ["OPEN_SANDBOX_API_KEY"],
        use_server_proxy=False,
    )
    sandbox = await Sandbox.create(
        "python:3.11-slim",
        connection_config=connection,
        entrypoint=["tail", "-f", "/dev/null"],
        timeout=timedelta(minutes=3),
        resource={"cpu": "1", "memory": "512Mi"},
    )
    print(f"CREATED: {sandbox.id}", flush=True)

    async with sandbox:
        try:
            # 固定测试样例，不拼接模型生成的 Shell。
            program = "\n".join([
                "import json, pathlib, subprocess, sys",
                "test = 'def allowed(active): return active is True\\n'",
                "test += 'assert allowed(True)\\nassert not allowed(False)\\n'",
                "run = subprocess.run([sys.executable, '-c', test],",
                "    capture_output=True, text=True, timeout=10)",
                f"host_visible = pathlib.Path({str(marker)!r}).exists()",
                "data = {'exit_code': run.returncode,",
                "        'stderr': run.stderr, 'host_visible': host_visible}",
                "pathlib.Path('/tmp/result.json').write_text(json.dumps(data))",
                "print('container test finished')",
            ])
            await sandbox.files.write_files([
                WriteEntry(path="/tmp/check_login.py", data=program, mode=644)
            ])
            execution = await sandbox.commands.run("python /tmp/check_login.py")
            for item in execution.logs.stdout:
                print(item.text)
            for item in execution.logs.stderr:
                print(item.text, file=sys.stderr)

            result = json.loads(await sandbox.files.read_file("/tmp/result.json"))
            if result["exit_code"] != 0:
                raise RuntimeError(f"test failed: {result['stderr']}")
            if result["host_visible"]:
                raise RuntimeError("unexpected host marker visible")
            if marker.read_text(encoding="utf-8") != "host-original":
                raise RuntimeError("host marker changed")
            Path("sandbox-result.json").write_text(
                json.dumps(result, ensure_ascii=False, indent=2), encoding="utf-8"
            )
            print("VERIFIED: test passed; host marker absent in container")
        finally:
            # 退出客户端上下文不代替销毁容器，显式发起清理。
            await sandbox.kill()
            print(f"DESTROYED: {sandbox.id}")


if __name__ == "__main__":
    try:
        asyncio.run(main())
    except Exception as exc:
        print(f"DEMO FAILED: {type(exc).__name__}: {exc}", file=sys.stderr)
        sys.exit(1)
```

终端 B 执行：

```Bash
export OPEN_SANDBOX_API_KEY='classroom-local-demo-key'
uv run --no-project python sandbox_demo.py
```

\[课堂等待期间，简要讲解下面四个动作，不逐行朗读代码。\]

`create` 申请环境，`write_files` 投递测试程序，`commands.run` 在容器里执行，`read_file` 取回结果。测试用例运行在独立子进程里，我们拿到的是它真实的返回码。



最后，程序在 `finally` 中销毁沙箱。这样测试失败也会走清理逻辑。宿主程序异常退出、或者网络断开时，清理仍可能失败，所以同时设置三分钟生命周期，作为服务端回收的后备措施。



### 3\.4 核对结果

程序跑完以后，我们检查三件事：**测试有没有通过，本机文件有没有被影响，容器有没有清理。**

先查看程序取回的测试结果：

```Bash
cat sandbox-result.json
cat host-only-marker.txt
docker ps
```

`exit_code` 为 `0`，表示测试通过；`host_visible` 为 `false`，表示容器里没有找到我们放在本机的标记文件。

再检查本机文件：

内容应该仍然是 `host-original`，说明这个文件没有被修改。



最后检查运行中的容器：

结合服务日志，确认本次创建的沙箱容器已经销毁。电脑上原来运行的其他容器应该保持不变。



这次演示让我们看到：**代码在容器里运行，结果由 Python 程序取回，用完后再销毁容器。**本机文件不会自动共享进去；如果主动把本机目录挂载给容器，容器就可能读到它，允许写入时还可能修改它。



另外，容器能不能联网、以什么用户运行、能读到哪些密钥，都要另外设置。这段程序没有限制对外联网，所以目前只能说明执行和回收流程跑通了，不能说所有安全限制都已经做好。



两段演示到这里就完成了。接下来，我们把它们接回 pi Agent，看看工程师还需要补齐哪些控制和检查。



## 四、接入真实项目，还需要做好什么？

前面两个演示，已经让我们看到了沙箱怎样运行。但接到真实的 Agent 上，还需要把几个问题说清楚：选哪种方式，哪些工具必须经过沙箱，执行出错以后怎样处理，以及怎样证明限制确实有效。

### 4\.1 选择方案，先看任务怎样运行

**自己边看边改的项目，可以先用本地沙箱；需要独立运行、批量处理的任务，可以考虑 Docker。**两种方式都需要配置权限，区别主要在于代码在哪里执行、改动落在哪里。



比如，你让 Agent 修改自己的项目，改完马上看 diff，本地方式比较方便。如果平台上有多个用户提交任务，就更适合为任务准备独立工作区，分别限制资源，完成后分别回收。

这里要记住：**隔离效果取决于实际配置。**

如果把整个本机目录都挂进去，再把各种密钥传进去，即使使用 Docker，Agent 能影响的范围仍然很大。对于来源不可信的代码，还需要评估普通容器的隔离强度是否足够。

选好执行方式以后，下一个问题就是：

**按任务风险决定隔离强度，按协作方式决定交付路径。**



### 4\.2 接入 pi：把所有执行入口收进同一条链

**接入沙箱，要检查所有能产生实际操作的工具。**

比如，我们新增了一个在容器里执行的 `sandbox_exec`，但旧的 `run_command` 仍然可以直接运行本机命令。模型一旦调用旧工具，就绕过了容器。

文件操作也一样。假如 Agent 在容器里修改代码，却在本机运行测试，测试的就可能是另一份文件。最后虽然显示“测试通过”，也不能证明修改后的代码正确。

所以，接入时要逐一检查：读取、写入、应用补丁、运行测试、执行命令，分别操作的是哪个工作区。扩展和 MCP 服务提供的工具，也要检查它们在哪里执行、受什么限制。



在课程工程中，pi 继续负责 Loop。工具收到调用后，先做权限和参数检查，再把操作交给对应的沙箱，最后把真实结果回给 pi。模型才能根据这个结果决定继续修改、调整计划还是结束任务。



如果需要人工批准，就进入前面讲过的 `waiting_approval`。批准时要明确是哪个动作、哪个目标；真正执行前再核对一次，避免等待期间参数或权限已经改变。

### 4\.3 如果自己写一个 pi\-sandbox，应该怎么下手？

**建议自己编写策略、工具接入和结果处理，底层隔离尽量复用成熟实现。**

这里要做的主要工作，是把任务权限落实到每一个执行入口。

可以按照下面四步推进。

**第一步，先写清楚要限制什么。**

不要一上来就写“危险命令黑名单”。先拿一个具体任务确定范围：允许读哪个项目，允许改哪些目录，是否需要联网，最多运行多久。

再把这些要求整理成一份统一配置。文件工具和命令工具都使用这份配置，避免各自写一套判断，最后出现“文件工具不让读，Shell 却能读”的漏洞。



**第二步，把策略检查和实际执行分开。**

这样以后从本地执行换成 Docker，主要调整执行器，权限判断和结果格式可以继续复用。



**第三步，分清不同工具怎样受到限制。**

Shell 启动的程序，要让它及其子进程都处于受限环境中。直接在 pi 进程里读写文件的工具，则需要自己做路径检查，或者改为通过沙箱的文件接口操作。

路径检查还要考虑 `..` 和符号链接，不能只看字符串是不是以项目目录开头。沙箱初始化失败时，也要明确停止执行，不能悄悄改成本机直接运行。

另外，策略文件和审计日志要保护起来。否则 Agent 能修改自己的规则，前面的限制就失去意义了。



**第四步，先做小范围闭环，再逐步增加能力。**

第一版可以只提供“读取指定项目、写入产物目录、运行固定测试”三个能力。验证成功和拒绝场景都符合预期以后，再增加通用 Shell、联网和人工审批。

尤其不要因为命令叫 `pytest` 就认为它安全：测试本身也会执行代码。专用工具可以缩小模型的选择范围，底层沙箱仍然要限制这些代码实际能做什么。



这些模块可以让 AI 帮忙编写。工程师要检查的是：**有没有遗漏的执行入口，限制有没有真正生效，失败时会不会意外放开权限。**



### 4\.4 超时、审计与恢复：把结果交代清楚

边界接好了，还要处理执行中断的问题。

**程序没有返回结果，不代表它什么都没做。**比如等待命令超时，容器里的程序可能还在运行；写文件时报错，也可能已经写入了一部分。



这里要分清三个时间限制：

- 请求超时：调用方最多等多久。 

- 命令超时：这次执行最多跑多久。 

- 沙箱生命周期：整个环境最多保留多久。 

请求超时以后，还需要确认命令是否停止。用户取消任务时，也要把取消传到实际执行的进程。确认不了现场状态，就先记录“结果不明”，不能马上重复执行可能产生副作用的操作。



这也接上了上一节的 Checkpoint：恢复时，要知道任务停在哪里，也要知道哪些操作已经发生。



因此，每次调用至少记录：哪个任务、哪个工具、操作目标、允许或拒绝的原因、执行结果，以及产物位置。如果有人批准，还要记录谁批准了什么。被拒绝的操作也要留痕。

日志放在 Agent 不能随意修改的位置，敏感信息先脱敏。给模型返回必要的结果和错误摘要，完整日志留给排查使用。

最后，销毁容器只能清理这个执行环境。如果程序已经向外部系统写入数据，删除容器不会撤销这些操作，仍然需要核对结果，再决定补偿或人工处理。



**容器销毁只清理执行环境，不能撤回已经发出的请求、已经写入的远端数据。外部副作用仍需幂等、补偿或人工确认。**



### 4\.4 用最小规格与反例证明边界有效

怎样证明这套限制有用？完成实现以后，不能只测“正常任务能跑通”，还要主动提交几种不允许的操作。

这就是 Harness 和 Loop 在这里的配合方式：先定义哪些行为允许、哪些必须拒绝，再把检查接入执行过程，用测试验证，最后让 Loop 根据真实结果继续工作。

AI 可以帮助我们实现，但最后要由我们确认：**该完成的完成了，不允许发生的事情也确实没有发生。**

### 4\.6 本节小结

今天我们看到了两种做法：本地沙箱限制 Agent 对当前机器的操作，Docker 沙箱提供一个独立的执行环境。无论选择哪种，都要明确文件、命令、网络和凭证的权限，并检查所有工具是否遵守这些限制。

如果要自己实现，重点是统一规则、接好执行入口、处理取消和失败，再用测试证明边界有效。底层隔离可以复用，哪些资源能开放、出了问题怎样处理，需要工程师决定。

到这里，Agent 已经能循环、能计划、能恢复，也能在限定范围内执行任务。下一节我们讲 Harness，把这些能力统一组织起来，形成一套可以持续运行、排查和改进的 Agent 系统。
