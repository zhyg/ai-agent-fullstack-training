# 3\.7 项目演进路线 阶段三：Codebase Agent v3

## 开场：从学会机制，到交付项目

先回到第三章的项目目标。

我们要把 Agent 从“调用一次模型、执行一次工具”，升级成能连续思考、执行、观察结果、发现问题并继续纠错的系统。

最后要交付一个能在代码仓库里完成任务的 Codebase Agent：它能理解代码、修改文件、运行测试、根据失败日志修复问题，也能在需要时暂停下来等待人工确认。

本章前面几节已经逐步搭起了关键部件：3\.1 讲了 Agent Loop 和停止条件，3\.2 讲了 Planning，3\.3 讲了任务状态与 Checkpoint，3\.4 讲了 Sandbox，3\.5 把这些能力放进 Harness，3\.6 又演示了如何用 LangGraph 编排流程。现在我们手里已经有了不少机制和代码。

但“分别学过这些机制”，还不等于“已经交付完整项目”。

接下来要做的是项目分析与代码组合：先确认现有代码满足了哪些项目要求，再把缺失的部分补齐，最后把已有能力组合成一台能执行代码仓库任务的 Agent。

**这一节的重点，是把学过的机制变成可运行、可验证、可继续演进的项目。**

这个 Agent 要能使用十件仓库工具：`list_files`、`search_code`、`read_file`、`read_directory`、`write_file`、`apply_patch`、`run_test`、`run_command`、`git_diff` 和 `git_status`。我们会用两类任务检验它。

第一类是代码理解：找到项目中的登录逻辑，阅读相关路由、中间件、Service 和数据库代码，梳理调用链，并生成带文件路径的 Markdown 说明。

第二类是测试与修复：定位指定函数，补充测试，运行测试，根据失败日志修改测试或代码，再说明改动结果。

再看第二章。阶段二项目已经交付了一套 Agent Runtime 工具调用基础设施：通过 ToolRegistry 统一注册工具，用 ToolSchema 描述工具，结合 JSON Schema 或 Pydantic 校验参数，并把 Function Calling、权限控制、风险分级、调用审计、超时、重试、降级、MCP 接入和 Trace 记录纳入运行时。它解决的核心问题是：**模型提出工具调用后，系统如何受控地执行它。**

但阶段二的重点是工具调用基础设施，还没有把第三章的 Loop、规划、状态恢复、沙箱和编排整合成代码仓库任务 Agent。所以本节先做第一步：**对照第三章的项目目标，盘点哪些能力已经实现、哪些还需要补齐。**

## 一、项目目标盘点：我们已经有什么，还缺什么？

### 1\.1 把第三章目标拆成可验收能力

围绕开场定义的两类任务，可以拆成一组可检查的行为：

|能力|可验收表现|
|---|---|
|任务理解与规划|能把目标拆成有顺序、有完成条件的步骤|
|仓库探索|能列出文件、搜索代码、读取相关文件，并给出路径依据|
|文件修改|能按任务创建或修改文件，并通过差异确认改动范围|
|测试与纠错|能运行测试、读取失败结果，并据此决定下一步|
|Loop 与停止|能把工具结果带回下一轮；达到完成条件或预算时停止|
|人工确认|高风险操作前能暂停，让人查看操作内容后再继续|
|安全执行|文件访问和命令执行受工作区边界约束|
|状态保存与恢复|中断后能找回任务进度，并从可确认的位置继续|
|执行编排|能明确步骤的先后、分支、循环和责任组件|
|过程追踪|能查看工具调用、执行结果、任务状态和最终改动|

这里的验收重点是**系统行为**，也就是能看到它运行了什么测试、收到什么结果、做了什么修改，以及最终验证的证据。

### 1\.2 标出已实现、部分实现和待补齐

学过一种机制，不代表它已经接进当前项目。盘点时，要把“课程里学过”与“本项目中可运行”区分开来。

|项目能力|前面章节|目前基础|本项目状态与处理方式|
|---|---|---|---|
|连续思考、执行、观察与纠错|3\.1 Agent Loop|已有 Loop 的执行模型和停止控制思路|**部分实现**：需要接入代码仓库工具，并用两类任务验证闭环|
|任务拆解与步骤规划|3\.2 Planning|已有计划结构、依赖和偏差处理方法|**部分实现**：需要把计划用于代码理解和测试修复流程|
|任务状态与 Checkpoint|3\.3 State Machine 与 Checkpoint|已有状态设计、存档和恢复思路|**部分实现**：需要确认状态中保存了代码任务恢复所需的信息|
|文件与命令执行边界|3\.4 Sandbox|已有沙箱职责和边界设计|**部分实现**：需要核对项目工具是否都经过边界检查|
|执行流程与人工协作|3\.5 Harness|已有任务装配、执行、审查和异常处理方法|**部分实现**：需要把它们连接到本项目的完整任务路径|
|节点、分支、循环与恢复|3\.6 LangGraph|已有图式编排方法及其适用场景|**可复用的方法**：是否由 LangGraph 承担编排，要结合本项目结构判断|
|仓库工具|第三章项目目标|已明确需要十件工具|**需要补齐或接入**：文件列表、代码搜索、文件读写、补丁、测试、命令和 Git 状态等|
|两类典型任务|第三章项目目标|已明确代码理解、测试与修复的业务目标|**需要组合验收**：用真实样本仓库验证从输入到产出的完整过程|

### 1\.3 阶段二的 Runtime 能力如何被复用

阶段二的这些能力，在 Codebase Agent 中仍然适用，只是工具从客服业务工具变成了代码仓库工具。

|阶段二 Runtime 能力|在 Codebase Agent 中的对应方式|
|---|---|
|ToolRegistry 与工具定义|注册十件仓库工具，并描述工具用途和输入参数|
|JSON Schema / Pydantic 校验|检查工具参数格式，避免缺字段或类型错误进入执行函数|
|权限与风险分级|区分读取、修改文件、运行命令等不同风险的操作|
|人工确认|对需要审批的操作暂停执行，并提供可检查的信息|
|超时、重试与降级|为工具执行设置边界；根据错误类型决定是否重试或交由人工处理|
|审计与 Trace|记录谁发起了什么工具调用、参数是什么、结果如何|
|MCP 接入经验|复用统一接入和工具描述的设计思路；本节的重点则是本地仓库工具|

复用 Runtime，并不意味着把第二章的实现原封不动搬过来。

两类项目的任务不同：阶段二围绕客服下单，Codebase Agent 围绕仓库读取、修改和测试。我们要复用的是工具治理的边界与工程原则，再检查现有代码是否能承接新的工具和任务。

### 1\.4 本节的交付范围与验收标准

本节的交付目标，是把前面学过的机制和已有代码组合成一台**能执行、能检查、能说明结果**的 Codebase Agent。

开场列出的十件仓库工具全部可用，并用两类任务验收。

验收时，我们会同时看任务结果和执行过程：

- 目标产物是否生成，内容是否能对应到实际文件和代码。

- 工具参数是否经过校验，文件和命令是否受执行边界约束。

- 测试失败后，Agent 是否依据真实日志调整行动，而不是只重复原操作。

- 需要人确认时是否暂停，并在批准后才继续。

- 中断或失败后是否能识别当前状态，避免盲目重放写操作。

- Trace、状态记录和 Git 差异是否足以复核 Agent 做过什么。

- 两类任务是否都能按预期完成；若不能，失败是否清楚、可定位、可恢复。

**到这里，项目目标就从一句“做一个 Codebase Agent”，变成了一张能力清单和一组验收条件。下一步我们先检查现有工程：哪些能力已经在代码中实现，哪些只是前面课程里的机制，哪些还需要补齐。只有完成这次盘点，后面的组合和改造才有明确依据。**



## 二、先跑通基线：Agent 能不能完成两类仓库任务？

目标和验收条件明确以后，接下来先跑一次现有工程。

这一轮演示，我们要看清三件事：**任务怎样进入系统，工具怎样推进任务，最后拿什么证明任务完成。** 跑完以后，再根据实际表现决定后面需要补什么。

这里统一采用配套 README 中的 `project3/v2` 工程：TypeScript 承担 Agent 与工具运行时，Python 服务承担 LangGraph 审批流程。后面的目录和命令都按这一套展开。

### 2\.1 基线项目结构与运行方式

先认识几个运行时会用到的位置。

|路径|职责|代码作用|
|---|---|---|
|`v2/src/cli.ts`|命令行入口|提交任务、处理审批、查询审计|
|`v2/src/pi/provider.ts`|模型接入|本次任务是否连接了真实模型|
|`v2/config/platform.yaml`|平台配置|模型、预算、沙箱等公共约束|
|`v2/config/tasks.yaml`|任务配置|任务差异、审批方式与审批人角色|
|`v2/hitl/service.py`|LangGraph 审批服务|等待审批、接收决定并推动后续执行|
|`samples/1_login_demo`|代码理解样本|登录逻辑及生成的说明文档|
|`samples/2_bug_fix/demo-app`|测试修复样本|失败测试、源码改动与复测结果|
|`v2/data/platform.db`|本地运行账本|审批记录、审计与 Trace|

看目录时，先记住一个关系：**Agent 工程负责组织执行，样本仓库是它操作的对象。** 我们通过 `--dir` 指定工作仓库。

进入工程目录：

```Bash
cd project3/v2
```

以下命令以配套依赖已经安装、`DEEPSEEK_API_KEY` 已在当前终端配置为前提。启动时还要检查决策器标识，确认本次使用真实模型。

这是一个必须看清的细节：当前工程在缺少密钥时会降级到离线脚本，并在日志里说明。离线脚本可以检查工具和审批路径；**两类任务的模型能力验收，要以真实模型运行的结果为准。**

还有两个编号要提前分清：

- `trace_id`：标识本次运行，用来查询执行记录。

- 审批编号：标识某一次待批准的操作，用来批准或拒绝这次操作。

一个任务可能产生多次审批，因此这两个编号不能混用。

运行方式了解了，先从代码理解任务开始。它涉及读取和生成文档，比较容易看清整条调用链。

### 2\.2 任务一：理解登录逻辑并生成说明

现在假设你刚接手一个项目，需要知道登录请求从哪里进入，经过哪些检查，最后怎样完成认证。

把这个目标交给 Agent：

```Bash
node --import tsx src/cli.ts agent \
  "帮我找出该项目的登录逻辑，并生成 Markdown 说明文档。" \
  --dir ../samples/1_login_demo
```

任务开始以后，我们观察它如何缩小查找范围：先了解目录，再搜索登录与认证相关代码，读取入口文件，沿着调用关系继续查看相关实现。

这里的关键是**先取得代码依据，再形成说明**。如果 Agent 只读了一个路由文件，就开始描述完整的数据库认证流程，我们要继续检查这些描述有没有文件内容支撑。样本里不存在的层次，也不能为了凑齐“路由、中间件、Service、数据库”而编出来。

按照当前 README 的流程，生成文档时会触发写入审批。CLI 此时结束本轮运行，并返回 `pending_approval_id`。

为什么读代码也会遇到审批？因为前面的搜索和阅读是读取操作，而生成 Markdown 已经要向仓库写入文件。当前基线对这次写入保留了人工确认。

拿到审批编号后，先检查待写入的路径和内容，再批准：

```Bash
node --import tsx src/cli.ts approvals decide <pending_approval_id> \
  --decision approve \
  --actor trainer-1 \
  --roles maintainer \
  --task understand
```

然后执行这张已经批准的写入单：

```Bash
node --import tsx src/cli.ts approvals execute <pending_approval_id> \
  --task understand
```

这两步的职责不同：`decide` 记录审批决定，`execute` 才真正执行写入。**批准成功，只能说明操作获得授权；文件是否生成，还要检查执行结果。**

接下来查看产物和审计：

```Bash
cat ../samples/1_login_demo/artifacts/login-flow.md
```

```Bash
node --import tsx src/cli.ts audit --trace-id <trace_id>
```

验收时，把说明文档与实际代码对照起来：

|检查项|要确认什么|
|---|---|
|登录入口|能否指出真实的入口文件与处理位置|
|调用关系|说明中的调用顺序是否有代码依据|
|路径引用|引用的文件是否存在，是否与所述逻辑对应|
|文档落盘|Markdown 文件是否实际生成|
|修改范围|除预期文档外，是否出现无关改动|

这样我们就完成了第一类任务的检查：Agent 找到了什么、依据是什么、最终交付在哪里，都能复核。

接下来增加难度。第二类任务需要它根据执行失败继续行动。

### 2\.3 任务二：补测试、读失败日志并修复

本类任务的完整目标是“补充测试，并根据失败日志修复”。先说明当前基线的覆盖范围：**样本已经预置了失败测试，并且禁止修改 ****`tests/`**** 下的已有测试，所以本轮验证的是读取失败、修复源码和复测；需要新增测试时，只能写到受控目录 ****`tests/generated/`****。**

先把这一段修复闭环跑稳，再接入测试生成，验收会更清楚。

样本的缺陷位于 `src/auth/session-policy.ts`。根据配套 README，它在判断会话是否到期时只比较日期，没有完整比较时间。样本预置的测试用于暴露这个问题。

开工前，先检查测试基线：

```Bash
npm --prefix ../samples/2_bug_fix/demo-app test --silent
```

README 记录的初始结果为：

```Plaintext
ℹ tests 7
ℹ pass 4
ℹ fail 3
```

这三个失败给了我们一个明确起点：后面要解释它们为什么失败，以及什么改动使它们通过。

#### 先启动审批服务

本任务使用 LangGraph 审批服务。打开一个终端，在 `project3/v2` 下运行：

```Bash
HITL_API_KEY=demo-key HITL_DB=/tmp/hitl-demo.db \
  ../.venv/bin/python -u hitl/service.py
```

这里的 `demo-key` 是本地演示值，Agent 端和服务端需要保持一致。

可以通过健康检查确认服务已启动：

```Bash
curl -s \
  -H "Authorization: Bearer demo-key" \
  http://127.0.0.1:8383/health
```

#### 再提交修复任务

另开一个终端，同样进入 `project3/v2`，提交与本轮范围一致的任务：

```Bash
HITL_API_KEY=demo-key node --import tsx src/cli.ts agent \
  "读取登录会话模块的失败测试与日志，修复源码并复测，不修改现有测试。" \
  --task fix_tests \
  --dir ../samples/2_bug_fix/demo-app
```

这一轮要观察的流程是：

> 运行测试 → 读取失败日志与相关代码 → 提出修改 → 获批后执行 → 再次测试 → 汇总变更。

当前任务把 `run_test` 也放进了审批范围。原因是测试会执行仓库里的脚本，执行行为需要按任务策略检查。

出现待审批操作时，在另一个终端查询：

```Bash
HITL_API_KEY=demo-key node --import tsx src/cli.ts \
  approvals tickets --task fix_tests
```

检查操作内容后，使用返回的审批编号批准：

```Bash
HITL_API_KEY=demo-key node --import tsx src/cli.ts \
  approvals decide <ticketId> \
  --decision approve \
  --actor lead-1 \
  --roles tech_lead \
  --task fix_tests
```

在这条 HTTP 审批路径中，Agent 会等待审批结果，放行后继续执行。后续如果出现新的审批单，就检查对应的新操作。

#### 最后检查结果与改动

任务结束以后，先独立复跑测试：

```Bash
npm --prefix ../samples/2_bug_fix/demo-app test --silent
```

再查看实际差异：

```Bash
git -C ../samples/2_bug_fix/demo-app diff
```

```Bash
git -C ../samples/2_bug_fix/demo-app status --short
```

README 给出的修复样本结果是七条测试全部通过，源码中的日期比较被替换为时间戳比较。真实模型运行时，具体操作顺序可能不同，我们按验收条件检查结果：

- 原来的失败是否消失。

- 修改是否针对失败原因。

- 现有测试是否保持完整。

- 是否出现无关文件改动。

- 变更说明是否与实际差异一致。

这里尤其要区分“现有测试通过”和“完整目标达成”。当前演示能够检验修复闭环；新增测试可以通过受控目录写入，但“新用例能否暴露目标缺陷”仍需单独验收。

### 2\.4 观察基线：哪些能力已经就绪，哪些还不够？

两类任务跑过以后，我们就可以根据工程表现确定下一步。

先修正一个容易产生的判断：当前工程已经有 `tasks.yaml`，也已经接入真实模型和审批服务。因此，后续要检查配置是否完整、连接是否可靠，以及新增任务需要改哪些地方。

|观察点|当前基线表现|后续要补齐或验证什么|
|---|---|---|
|任务配置|已有任务配置与审批配置|查清计划、路径、命令是否仍有任务专用逻辑散落在代码中|
|工具参数契约|已有阶段二 Runtime 基础|核对十件仓库工具是否统一经过校验，失败信息是否进入下一轮|
|测试生成|当前样本预置测试，并禁止改动测试目录|增加受控的新测试写入范围，证明新测试能发现目标缺陷|
|上下文管理|搜索、源码和测试日志都会进入任务过程|检查输出过长时如何截断、保留证据并控制模型输入|
|人工确认|本地审批和 HTTP 审批的继续方式不同|明确批准后由谁执行、由谁继续任务，避免漏执行或重复执行|
|完成判定|模型可能先于实际执行宣布完成|以产物、测试、差异和审计记录核对完成状态|
|批量验收|当前 README 按两个样本分别运行|汇总两类任务的结果、停止原因、审批与产物，形成可复核报告|

“补测试”还有一条边界要提前定好：给新增测试指定允许写入的位置，同时检查 Agent 没有借机删除断言、跳过用例或降低原有标准。否则，新增测试和修复结果都失去了可信依据。

到这里，基线演示完成了它的任务：明确了哪些既有能力可以复用，也列出了后续要补齐的缺口。

## 接下来先回答一个问题：这些任务差异，写在哪里？

## 三、未来接入新任务，改动落在哪里？

刚才跑过的两类任务，共用一套工具运行时，执行要求却不同：代码理解要沿调用关系阅读源码并生成文档；测试修复要执行测试、分析失败、修改源码并复测。

真实岗位的任务会不断增加。这些差异写在哪里，决定了以后接入新任务的成本。

如果每加一个任务，都要在 Loop、工具函数和审批模块里改一遍代码，成本就太高了。合理的分工是：

|变化类型|改动位置|
|---|---|
|已有工具能完成的任务|任务配置 `config/tasks.yaml`|
|需要新工具或新验证方式的任务|扩展代码|

任务要交付什么、允许做什么，以及检查范围、搜索标记、输出路径、预算和审批要求这类差异，都写进配置。具体读取哪个文件、下一步做什么，仍由模型自行决定。

比如“检查 Markdown 文档里的 TODO”，用已有的搜索、读取和写入工具就能完成，应该通过配置接入；而“检查网页链接是否失效”需要网络访问能力，就要扩展代码。

判断方法也很直接。如果接入新任务时，必须在 Loop、工具函数和审批模块里分别追加：

```TypeScript
if (taskType === "docs_audit") {
  // 任务专用逻辑
}
```

就要回头检查：这是任务差异写错了位置，还是引擎确实缺少一种通用能力？

**任务差异进入配置，新能力扩展代码。** 有了这条边界，同一套执行框架就能承接更多任务。

任务越多，工具被调用的次数和形态也越多。在把它们组合成完整项目之前，还需要定清楚工具调用链路上的三条公共边界，接下来的三节分别处理其中一条：

- **四、工具调用有契约**：模型提出的参数要经过统一校验，不合法就不进入执行，错误要能准确回到下一轮。

- **五、上下文与预算受控**：源码、日志和搜索片段不断累积，哪些进入下一轮、哪些压缩留证，需要明确的规则。

- **六、人工确认按旅程安排**：哪些操作连续执行，哪些必须停下来等人决定，停下来时给人看什么证据。

这三条边界都围绕同一次工具调用（发生在 Harness 里）：参数能不能进、结果给多少、执行要不要批准。三项定清楚以后，下一节就把各模块连接起来，检查完整的运行闭环。

---

## 四、让工具调用有契约

任务配置确定了“做什么”和“允许做什么”，接下来要检查每次工具调用是否符合要求。

比如，模型决定读取登录入口，却传来了 `{"path": 42}`。这个参数应该在工具执行前被拦下，并把具体错误反馈给模型，让它修正后再提交。

第二章已经实现了 Runtime 参数校验。本节把这条执行路径接到十件仓库工具上：**工具向模型展示的参数要求，与 Runtime 执行前校验的要求，必须来自同一份定义。**

### 4\.1 十件仓库工具各自的输入与输出

先把十件工具的职责摆清楚。

下面是本项目应对齐的契约内容，字段名称可以沿用已有工程。重点是确认每件工具需要什么参数，以及返回什么信息才能支撑后续决策。

|工具|输入应说明什么|输出应包含什么|
|---|---|---|
|`list_files`|相对目录、匹配条件、数量上限|文件路径列表，是否截断|
|`search_code`|搜索内容、搜索范围、结果上限|命中文件、行号、片段，是否截断|
|`read_file`|文件路径、可选的起始行与读取范围|文件内容、实际行号范围，是否截断|
|`read_directory`|目录路径|当前目录的直接子项及类型|
|`write_file`|文件路径、写入内容、覆盖规则|写入路径、创建或覆盖结果|
|`apply_patch`|目标文件、补丁内容|应用结果、变更摘要；失败时说明匹配问题|
|`run_test`|允许的测试目标或配置标识|退出码、测试摘要、输出日志，是否超时|
|`run_command`|命令及参数、工作目录、超时|退出码、标准输出、标准错误，是否超时|
|`git_diff`|可选的路径范围|实际差异、涉及的文件，是否截断|
|`git_status`|可选的路径范围|已修改、未跟踪等文件状态|

这十件工具的实现集中在 `project3/v2/src/tools/` 目录。

有几个地方容易混淆。

`read_directory` 用来了解一层目录的组成，`list_files` 用来按约定范围查找文件。把边界写清楚，模型才能选择合适的工具。

`run_test` 应优先使用任务配置里允许的测试目标。模型提供的测试选择，要由程序解析成允许执行的命令。`run_command` 的能力更宽，需要单独检查命令、工作目录和审批要求。

输出也要有契约。比如，搜索结果为空，可能是确实没有匹配，也可能是搜索失败。两者必须区分，否则模型会在错误依据上继续推理。

同样，测试执行后应返回退出码和日志。即使测试工具成功启动并完成了进程管理，测试断言仍然可能失败。因此，**工具是否成功执行，与任务是否达到目标，要分别表达。**

这些输出最终有两个使用者：模型需要它们决定下一步，程序需要它们更新状态、记录审计和判断是否完成。

### 4\.2 用 JSON Schema 校验工具参数

输入输出明确后，把输入要求写成程序可以检查的 Schema。

以 `read_file` 为例，下面这份示例要求路径是非空字符串，行号和读取数量是正整数，并拒绝未定义字段：

```JSON
{
  "type": "object",
  "properties": {
    "path": {
      "type": "string",
      "minLength": 1,
      "description": "相对于当前工作仓库的文件路径"
    },
    "start_line": {
      "type": "integer",
      "minimum": 1
    },
    "max_lines": {
      "type": "integer",
      "minimum": 1,
      "maximum": 500
    }
  },
  "required": ["path"],
  "additionalProperties": false
}
```

这份 Schema 能拦住几类错误：

- 缺少 `path`。

- 把 `path` 写成数字。

- 把起始行写成负数。

- 一次要求读取超过约定上限的行数。

- 传入拼错或未定义的字段。

这里还要明确 Schema 的检查边界。

`{"path": "../../outside.txt"}` 在类型上仍然是一个非空字符串。它能通过上面的 Schema，但能否访问，要继续交给路径边界检查。文件是否存在，则需要在实际读取时确认。

|检查层|回答的问题|
|---|---|
|参数校验|字段、类型、范围是否符合工具契约|
|权限与审批|当前任务和用户是否允许执行这次操作|
|Sandbox|实际文件访问与进程执行是否受到边界约束|
|工具执行|文件是否存在、补丁是否匹配、命令能否完成|

这些检查沿用第二章的 Runtime 执行路径。

接入时，先找到已有的工具定义和校验入口，让仓库工具经过同一个入口。模型发现工具时使用本轮绑定的 Schema，执行时也使用与该定义一致的版本，避免模型看到一份要求，Runtime 却按另一份要求判断。

同时，参数错误应当显式返回。比如模型把路径传成数字 `42`，不要悄悄转换成字符串 `"42"` 再尝试读取。这样的转换掩盖了调用错误，也让后面的行为更难解释。

校验接好了，接下来还要让错误进入下一轮。

### 4\.3 校验失败后如何反馈、修正和重试

假设模型发出这次调用：

```JSON
{
  "path": 42
}
```

Runtime 检查后发现 `path` 类型错误。此时工具函数还没有执行，系统应生成结构化失败结果，再通过现有适配层回写给模型。

下面是建议表达的信息，具体字段与工程现有的错误结构对齐：

```JSON
{
  "ok": false,
  "error": {
    "code": "INVALID_ARGUMENT",
    "message": "path 必须是字符串，当前收到整数",
    "details": {
      "field": "path",
      "expected": "string",
      "received": "integer"
    }
  },
  "execution": {
    "started": false
  }
}
```

为什么要说明 `started: false`？因为后续处理需要知道这次操作有没有实际发生。参数校验失败时，我们能够明确说明：执行函数尚未进入。

这条失败结果还必须保留原工具调用的关联编号。沿用当前适配层的 `toolCallId` 或协议中的 `tool_call_id`，让模型知道是哪次调用失败。连续调用多个工具时，不能只往历史里追加一句没有归属的“参数错误”。

收到结果后，模型可以依据此前搜索到的路径重新提交：

```JSON
{
  "path": "src/routes/login.ts",
  "start_line": 1,
  "max_lines": 120
}
```

新的调用再次经过参数校验、权限检查和执行边界检查，通过后才读取文件。

这里有两个不同的动作：

|情况|应怎样处理|
|---|---|
|参数不合法，执行尚未开始|把错误交给模型，让它修正参数后重新提交|
|参数合法，但执行遇到临时故障|根据第二章的重试策略，判断是否允许有限重试|
|写操作发出后结果不明|先检查执行事实，确认是否已经产生修改|

参数错误通常不能靠原样重试解决。`path` 传成数字，重复十次仍然是数字。

即使模型已经修正参数，也要重新检查这次调用。尤其是写操作，参数变更以后，原审批不能自动授权新的写入内容。

最后，错误修正也要受循环预算和重复错误护栏约束。模型连续提交同样的无效参数时，系统应按既有规则停下，并留下最后一次错误。这样，反馈机制才能帮助任务推进，同时避免无效循环。

### 4\.4 验收：错误参数不能进入工具执行

现在怎样证明校验确实接在了执行之前？

验收要同时检查两件事：**错误结果是否正确，工具是否真的没有执行。**

可以先直接向 Runtime 提交错误参数，使用计数器记录 handler 是否被调用；再通过集成测试检查错误结果能否回到模型循环。

|验收场景|预期结果|必须检查的执行事实|
|---|---|---|
|`read_file` 缺少 `path`|返回参数错误，指出缺失字段|handler 调用次数为 0|
|`read_file` 的 `path` 为数字|返回类型错误|没有发生文件读取|
|`write_file` 缺少 `content`|返回参数错误|文件未创建，已有内容未改变|
|参数包含未定义字段|按严格契约拒绝|handler 未执行|
|模型修正参数后重新提交|新调用通过校验并执行|成功结果关联到新的调用编号|
|连续提交相同错误参数|达到既有护栏条件后停止|没有无限请求或工具执行|

再增加一条边界验证：

```JSON
{
  "path": "../../outside.txt"
}
```

这次参数类型正确，应该由工作区边界检查拒绝。验收时要确认错误来自正确的检查层，并且没有读取工作区外的内容。

修正流程也要单独验证。可以在测试中安排两次固定调用：第一次传错误参数，第二次传合法参数，检查：

1. 第一次调用返回 `INVALID_ARGUMENT`，没有进入 handler。

2. 错误结果携带原调用编号进入下一轮。

3. 第二次调用重新经过完整检查。

4. 合法调用只执行一次，并返回真实结果。

这项测试验证运行机制。随后再用真实模型完成仓库任务，检查它能否利用错误反馈继续推进。

如果让 AI 辅助接入这一层，可以把要求写得具体一些：

> 复用当前 Tool Runtime 的参数校验入口，为仓库工具补齐输入 Schema。模型发现与执行校验使用同一份工具定义。参数不合法时不得进入 handler；返回结构化错误并保留调用编号。增加验证，证明错误写入参数不会修改文件，修正后的调用会重新经过权限与审批检查。

工程师复核时，重点沿着这条链看：**定义从哪里来，校验在哪里发生，失败怎样回写，副作用是否被阻止。**

**这一层完成以后，工具调用就有了可检查的输入要求和失败反馈。下一步要处理执行过程中不断积累的内容：源码、搜索片段和测试日志越来越多，怎样让模型保留足够依据，同时控制上下文与预算。**

## 五、控制长任务的上下文与预算

工具调用有了契约，Agent 就能持续读取源码、执行测试、根据结果继续修复。但任务一长，另一个问题就出现了：每一步都会产生内容，这些内容不断进入历史，下一次请求模型时要带上多少？

先给结论：**完整执行记录留作追踪，模型每轮只接收经过选择的上下文。** 这样既能保存可复核的证据，又能控制单次工具结果和历史记录占用的空间。

本节落实两项机制：限制单次工具观察的长度，把较早的步骤压缩成保留关键事实的摘要。

### 5\.1 为什么代码任务更容易撑满上下文

代码任务有一个特点：用户输入很短，工具输出却可能很长。

“帮我修复登录问题”只有一句话，后面可能跟着几十条搜索结果、几百行源码、多轮测试日志，以及修改前后的差异。模型每执行一步，都可能增加一大段历史。

以测试修复为例：

|执行步骤|新增内容|后续真正需要的信息|
|---|---|---|
|搜索登录逻辑|多处命中及代码片段|相关文件和入口位置|
|阅读实现|整个文件的源码|与缺陷有关的函数和依赖|
|第一次测试|成功日志、失败堆栈、统计|失败用例、错误位置、预期与实际值|
|应用补丁|修改内容与执行结果|改了哪里、是否应用成功|
|第二次测试|又一份完整日志|当前是否通过、还有什么失败|

如果每轮都携带这些内容的全文，输入会持续增长；同一批旧日志还会被反复发送，既消耗 Token、拖慢请求，也让当前要处理的失败淹没在历史里。

因此，预算要分两层：

- **单次上下文预算**：这一轮最多给模型多少输入，还要为输出留出空间。

- **任务累计预算**：整个任务最多消耗多少 Token、费用、工具调用和运行时间。

压缩只减少后续请求的输入，已经发生的消耗仍然计入任务预算。另外，消息历史只是输入的一部分，系统提示词、工具定义和当前用户要求同样占空间，检查单次预算时要把它们一起算进去。

增长最快、也最好控制的，是单次工具输出，先从它动手。

### 5\.2 截断单次工具观察

一次 `run_test` 输出几千行日志，全部放进历史，即使前面没几步操作也可能占掉大量空间。所以工具执行完成后，Harness 要先整理结果，再交给模型。

要保留两份用途不同的内容：完整结果存进受控的运行产物；模型看到的是有长度限制、带定位信息的观察。审计只记录结果状态和产物引用，方便日后查回。

不同工具，保留内容的方式也应该不同。

|工具结果|优先保留|内容过长时怎样处理|
|---|---|---|
|文件列表|路径、数量、是否还有结果|限制条数，提示缩小目录或继续查询|
|搜索结果|命中文件、行号、相关片段|限制命中数，明确结果不完整|
|文件内容|请求范围内的源码与行号|分段读取，返回本次实际范围|
|测试日志|退出码、失败用例、关键堆栈、统计|完整日志落盘，提供可继续读取的引用|
|Git 差异|文件列表、变更统计、相关补丁|按文件读取，提示还有未展示的差异|

测试日志尤其不能只留前几百行——前面可能全是正常输出，真正的失败在中间或末尾。

更合适的顺序是：先保留退出码和超时状态，再提取可识别的失败信息，剩余空间展示日志片段；提取失败时保留有限的首尾片段，并提供完整日志的位置。

下面是建议的观察结构示例：

```JSON
{
  "exit_code": 1,
  "timed_out": false,
  "summary": "7 条测试，4 条通过，3 条失败",
  "failures": [
    {
      "test": "会话到期后应失效",
      "location": "tests/session-policy.test.ts:42",
      "message": "预期 false，实际 true"
    }
  ],
  "truncated": true,
  "output_ref": "artifacts/runs/run-001/test-01.log"
}
```

这不是当前工程的真实运行记录，而是接入时应表达的信息；`output_ref` 还要能通过已有的受控读取路径访问，模型才有办法补查细节。

模型看到 `truncated: true`，就知道观察不完整，需要时可以读取对应日志片段。**截断后要说明省略了什么，并留下继续查证的入口。**

单条观察有了上限，多轮积累仍会变长，接下来处理较早的历史步骤。

### 5\.3 压缩历史步骤，保留关键证据

假设 Agent 已经定位到会话判断函数，也读过几轮文件。准备修改代码时，最早那次目录列表还有必要完整携带吗？

通常不需要，只要保留它得出的结论：入口在哪、相关实现在哪、哪些位置已经查过。

上下文可以按用途分别处理：

|内容|处理方式|
|---|---|
|用户目标、禁止事项、完成标准|持续保留|
|当前计划与未完成步骤|保留最新状态|
|最近的工具调用和结果|在单条上限内保留必要细节|
|较早的探索步骤|压缩成结构化事实|
|完整源码、日志和差异|保存引用，需要时再读取|

压缩后的记录要回答四件事：做过什么、得到什么结果、依据在哪里、还有什么没确认。

例如，一段较早的历史可以整理为：

```Plaintext
目标：修复会话到期判断，保持现有测试不变。

已确认：
- 相关实现：src/auth/session-policy.ts
- 第一次测试：4 过、3 失败
- 日志：artifacts/runs/run-001/test-01.log

当前判断：
- 疑似与日期比较粒度有关，尚未通过修复验证。

下一步：
- 核对时间比较逻辑，提出补丁。
```

这里把“已确认”和“当前判断”分开。模型怀疑某行代码有问题时，摘要要保留“疑似”状态，避免后续轮次把推测当成结论。

有三类证据要格外保留。

**第一，尚未解决的失败。**
最近一次失败的关键信息是下一步修复的依据，压缩时保留错误位置、表现和日志引用。

**第二，操作是否真的发生。**
“补丁等待审批”“补丁已应用”“补丁应用结果不明”是三种不同状态，摘要必须准确表达，不能统一写成“补丁已处理”。

**第三，验证结果对应哪个版本。**
测试通过后代码又改了，旧结果只能说明修改前的状态。程序要把测试结果与当时的工作区版本或内容指纹关联起来，完成判定用对应当前内容的证据。

这些执行状态、审批记录和版本信息继续由程序管理。摘要给模型帮助决策，完成检查仍读取真实记录。

实现时先按结构化步骤生成确定性摘要，再考虑让模型参与——这样更容易保证退出码、路径、审批状态等关键字段被准确保留。

如果消息协议要求工具调用与结果配对，压缩时要保持配对完整：不能删掉调用、只留一个找不到编号的结果，未结束的工具交互也要完整保留。

完成压缩后，每次请求模型前重新检查输入预算。信息仍然放不下时，就停止本轮请求并说明原因。



### 5\.4 验收：上下文受控，任务仍能继续

怎样判断这一层做好了？两点：上下文大小受控，模型仍能拿到推进任务所需的证据。只验证“字符串变短了”，不足以证明任务能继续。

可以围绕下面几种场景验收：

|验收场景|要证明什么|
|---|---|
|测试输出大量日志|模型收到的观察有长度上限，完整日志仍可查回|
|失败信息出现在日志中间|关键失败被保留，或模型能通过引用补查|
|连续执行多轮搜索和读取|较早步骤被压缩，每轮组装后的输入受预算约束|
|压缩后继续修复|目标、限制、未解决错误和当前步骤仍然明确|
|测试通过后再次修改文件|旧测试结果不会被当作当前版本的完成证据|
|达到任务累计预算|系统按预算停止，并保留状态和停止原因|

每轮可以记录以下指标，帮助复核：

- 工具原始输出长度与实际送入模型的长度。

- 是否发生截断或历史压缩。

- 模型输入的 Token 估算值。

- 响应返回后的实际 Token 用量。

- 任务累计消耗与停止原因。

字符数可以用来限制单条文本，但不能当作精确 Token 数。请求前用估算值控制输入，响应后按实际用量更新账本，并为估算误差留余量。

如果让 AI 辅助实现，可以给出这样的最小规格：

> 在现有工具结果处理与模型请求组装位置接入上下文预算。长输出保存为受控产物，模型观察保留关键状态、截断标记和可读取引用。压缩较早步骤时，保留目标、限制、未解决失败、操作状态和证据引用，保持工具调用与结果配对完整。每次请求前检查整体输入预算，响应后累计实际用量。用长日志和多轮任务证明内容受控且证据可查。

最后再用真实模型跑一次测试修复任务：让输出足够长，触发截断或压缩，检查它是否仍能找到失败原因、取得细节并完成复测。工程机制和实际任务都通过，才算这一层有效。

到这里，工具结果既能留下完整证据，也能以受控的形式进入下一轮。接下来把人工确认放回完整的用户旅程：哪些操作可以连续执行，哪些必须停下来，以及停下来时应给人看什么。

## 六、按用户旅程安排人工确认

Agent 已经能连续搜索、读取、修改和测试，但也正因如此，更需要明确哪些操作必须先停下来。

第二章已经实现了审批机制，本节把它放进具体任务流程，回答三个问题：**哪里设确认点、确认时给人看什么、批准后由谁执行。** 下面依次看代码理解、文件修改与命令执行、评估报告三段。

### 6\.1 代码理解任务中，哪些操作不需要拦截

用户要求“帮我找出登录逻辑”，已经表达了读取代码的意图。只要在工作区内，搜索、列目录、读取源码都可以连续执行——每读一个文件都确认一次，用户反而看不出哪一步才需要决定。

|任务阶段|操作|本项目建议的确认方式|
|---|---|---|
|了解目录|`list_files`、`read_directory`|在授权范围内自动执行|
|查找入口|`search_code`|在授权范围内自动执行|
|阅读实现|`read_file`|在授权范围内自动执行，受敏感路径限制|
|生成说明|在指定产物目录创建新文档|满足预授权条件时自动执行|
|覆盖已有说明|修改已存在的文档|展示差异后确认|
|改动业务源码|超出代码理解任务的写入|按任务权限拒绝，需另行授权|

这里的“自动执行”仍然经过参数校验、权限检查和沙箱限制。

基线演示里，写文档会触发审批；这里做一项调整：允许代码理解任务在指定产物目录创建新报告，限制目标路径，并采用“文件已存在则拒绝覆盖”的写入方式。新文档自动生成，覆盖已有文件时才要求用户决定——这个条件要在实际写入时保证，不能只在执行前检查一次。

要注意：**不能仅按工具名称放行所有 ****`write_file`****。** 在产物目录新建报告和覆盖源码影响完全不同，审批策略要结合任务类型、目标路径和写入方式判断。



### 6\.2 文件修改与命令执行，分别怎样审批

测试修复任务会改变仓库状态，还会运行仓库里的程序，两类操作要看不同的信息。

**文件修改，重点确认具体变更。**

模型先提出补丁，系统暂存，审批人查看目标文件、差异和修改理由，批准后再应用。审批绑定本次任务、工作区、具体补丁和修改前的文件状态；补丁被改过，或等待期间文件被他人修改，都要重新核对。这也是“批准一次就永久放行”不适合当前演示的原因。

**命令执行，重点确认将运行什么，以及它能影响哪里。**

|操作|审批前展示|执行前再次检查|
|---|---|---|
|应用补丁|文件路径、完整差异、修改理由|补丁是否一致，目标文件是否变化|
|写入文件|路径、写入内容、创建或覆盖方式|是否仍在授权范围，覆盖条件是否满足|
|运行测试|实际测试命令、工作目录、超时|测试配置及相关脚本是否变化|
|运行通用命令|可执行程序、参数、工作目录、执行范围|命令是否允许，审批是否仍有效|

`run_test` 名字里虽有“测试”，实际执行的可能是仓库里的 npm script，审批人要看到最终解析出的命令，而不是一个工具名。

当前基线对测试执行保留审批；以后要让复测自动进行，可以预先授权一个范围明确的测试配置——命令、工作目录和相关脚本未变就按策略执行，变了就重新判断。这些条件由程序检查，不靠模型口头保证。

审批通过后，还要明确谁继续执行：

- 本地审批路径由显式的执行动作领取并执行获批操作。

- HTTP 审批路径由等待中的任务收到批准后继续。

同一张审批单只能被一条路径领取，重复点击或重复通知不能造成重复写入。拒绝、过期、服务不可达也要有明确结果：拒绝记录原因，过期重新申请，不可达时保留未执行状态。审批未完成时，工具不能产生副作用。

### 6\.3 审批时让人看什么证据

只显示“Agent 请求调用 `apply_patch`”，用户还得自己翻日志、找文件。审批单要把作出决定所需的信息组织好。

一次源码修复至少展示：

|信息|帮助审批人判断什么|
|---|---|
|用户目标|这次操作是否服务于当前任务|
|失败证据|为什么需要修改，依据是哪次测试或日志|
|目标文件与补丁|具体改了什么，是否超出范围|
|当前验证状态|哪些检查已完成，哪些要执行后才能验证|
|影响范围|是否涉及源码、测试、依赖或构建配置|
|操作编号与有效期|批准的是哪一次操作，授权何时失效|

比如，审批摘要可以这样表达：

> 当前任务是修复会话到期判断。已有测试出现三条失败，相关日志可展开查看。拟修改 `src/auth/session-policy.ts` 中的时间比较逻辑，现有测试保持不变。补丁尚未应用，应用后需要重新运行测试。

下面再附完整差异和日志引用供核对。这里要分清事实与推断：“三条测试失败”来自工具结果，“可能与日期比较粒度有关”是当前诊断，“补丁能修复问题”在复测前仍未验证。所以审批材料由程序记录和模型说明共同组成：退出码、差异、操作状态取自执行记录，模型负责解释理由。

审批人应该能给出具体反馈，比如“修改范围太大”“先补边界用例”；若策略允许改方案后继续，反馈进入下一轮，新补丁重新审批。

**批准只表示允许执行，执行后的验证才决定任务是否完成。**

到这里，一次人工确认的完整过程是：提出操作、展示依据、作出决定、执行获批内容、验证结果。下面把这些过程汇总起来检查。



### 6\.4 用两类任务生成自动评估报告

工程持续修改后，需要一份统一报告回答：两类任务是否仍然符合要求？这一步新增一个评估执行器，依次运行两类任务、收集证据并生成报告（配套工程已提供 `cli eval`）。

先把每个评估任务的条件固定下来：

|评估项|代码理解|测试修复|
|---|---|---|
|输入|登录逻辑分析要求|会话判断修复要求|
|初始环境|指定版本的干净样本|保留已知缺陷与失败测试的样本|
|预期产物|登录说明文档|源码差异、复测结果、变更说明|
|修改范围|指定报告文件|允许修改的源码|
|关键检查|引用路径有效，原文件未改|目标测试通过，现有测试未被削弱|
|人工确认|按报告创建或覆盖策略|按补丁与命令策略|
|当前覆盖限制|内容准确性需要进一步核对|新增测试的用例有效性需单独核对|

每次评估使用独立工作副本和独立运行记录，保证起点一致。遇到人工确认也要尊重真实状态：等待审批记为“待审批”，被拒绝记为“已拒绝”——自动生成报告不等于自动批准。

工程机制测试可以用明确标注的测试审批器，验证批准、拒绝和过期路径；真实任务报告记录实际审批来源，两者分开呈现。

报告至少包含：

|字段|用途|
|---|---|
|任务名称、Run ID、决策器来源|确认运行对象与执行方式|
|执行状态与停止原因|区分完成、失败、待审批、取消和预算耗尽|
|验收结果|区分程序结束与交付条件通过|
|工具调用与审批次数|观察执行过程和人工参与量|
|耗时、Token 与费用|观察资源消耗|
|产物、日志与差异引用|支持复核|
|未覆盖能力与待复核项|明确当前结论的范围|

关键是把“执行状态”和“验收结果”分开：Agent 正常结束但报告文件不存在，验收仍然失败；测试全通过但改了禁止改动的文件，也不能通过。代码理解同理：路径存在可以自动检查，解释是否准确要对照代码，不能仅凭“文档非空”判定。

如果让 AI 辅助实现，可以给出这样的要求：

> 新增两类任务的评估执行器，使用独立样本副本，沿用现有决策器、Runtime 与审批路径。根据真实产物、测试结果和文件差异生成验收结论，记录运行状态、停止原因、审批次数与资源消耗。待审批任务不得计为完成，测试审批与人工审批明确区分。报告附上证据引用，并列出新增测试等尚未覆盖的能力。

到这里，人的参与位置就清楚了：授权范围内连续探索，具体变更和命令按策略确认，最终结果用报告集中复核。

**接下来，把任务配置、决策器、Runtime、沙箱、状态与审批连接到一张完整的项目结构里，检查一次任务从进入系统到交付结果，是否都有明确的责任组件。**

## 七、组合完整项目：从模块到运行闭环

前面几节已经逐项明确了任务配置、工具契约、上下文预算和人工确认。现在把它们组合起来，检查一次任务能否从用户输入走到可复核的交付结果。

组合时，最重要的是把模块之间的交接说清楚：**谁提供输入，谁检查条件，谁真正执行，结果由谁保存，又怎样进入下一轮。**

### 7\.1 项目目录与模块职责

先沿用当前工程已有的入口：

|已有位置|职责|
|---|---|
|`src/cli.ts`|接收任务、处理命令行操作、查询结果|
|`src/pi/provider.ts`|连接模型|
|`src/pi/coding-agent-extension.ts`|从 pi 扩展入口接入受控工具能力|
|`config/platform.yaml`|平台级模型、预算和执行边界|
|`config/tasks.yaml`|各类任务的目标与执行策略|
|`hitl/service.py`|承担 LangGraph 审批流程|
|`data/platform.db`|保存本地审批、审计等运行记录|
|`../samples/`|存放被分析和修改的样本仓库|

这些路径能帮助我们找到入口。

继续阅读代码时，还要把下面几项职责对应到具体实现。

后续新增模块也按这些边界组织：

|模块职责|接收什么|交付什么|
|---|---|---|
|任务装配|用户目标、任务类型、工作区|本次任务的有效配置与运行上下文|
|计划管理|目标、执行观察、当前进度|当前计划、修订记录与待完成步骤|
|模型与决策适配|经过预算处理的上下文、工具定义|工具调用或结束建议|
|Tool Runtime|工具调用、用户身份、当前策略|校验、授权和执行后的结构化结果|
|仓库工具|已通过检查的参数|文件、命令和 Git 操作结果|
|上下文处理|历史步骤、原始工具结果|下一轮需要的观察、摘要和证据引用|
|状态与 Checkpoint|任务进度、待处理操作、执行记录|可恢复的任务状态|
|完成检查与评估|当前产物、测试结果、差异|验收结论与报告|

这张表描述的是职责边界，具体文件名可以沿用现有工程。

没有必要为了目录看起来整齐，把已有模块全部重命名。

这里还要明确 pi 与 LangGraph 的分工。**本项目继续由 pi 承担模型与工具循环，LangGraph 承担当前接入的审批流程。** 审批结果返回以后，由任务运行层决定继续、暂停或结束。



这样，我们能够沿着一条执行链定位问题：模型调用看 Provider，工具拒绝看 Runtime，等待审批看审批记录，恢复异常看任务状态和 Checkpoint。



### 7\.2 任务进入、计划执行、工具调用与状态更新

接下来用测试修复任务走一遍完整过程。

**第一步，接收任务并建立运行上下文。**

CLI 收到目标、任务类型和工作目录后，加载平台配置与任务配置，检查工作区，生成 Run ID，并确认本次动作来自离线脚本还是真实模型。

平台与任务约束共同形成这次运行的有效策略。预算、工具范围和读写权限都要在这里确定，后面各模块使用同一份运行上下文。

> **这一步的提示词**（整段复制到你的 AI 编辑器）：

```Markdown
任务：以 project3/v2 为基础，实现「接收任务并建立运行上下文」——一句话目标和任务类型进来，装配出这次运行的有效策略。

【涉及文件】
  src/cli.ts        入口：接收目标、--task、--dir 与权限参数
```

### 7\.3 沙箱、Checkpoint、审计和人工确认怎样协作

这四项能力在一次文件修改中会同时出现。它们分别回答不同的问题：

|能力|回答的问题|
|---|---|
|人工确认|这次具体操作是否获得授权？|
|Sandbox|操作实际发生时，能访问和影响哪些资源？|
|Checkpoint|任务暂停以后，继续执行需要哪些状态？|
|审计|刚才提出、批准和执行了什么，有什么结果？|

以一次补丁为例，先保存待修改路径、补丁内容、目标文件状态和审批编号，然后等待人工决定。

批准后，系统重新核对权限、补丁和目标文件状态，再通过沙箱边界执行。执行结果写入审计，并更新任务状态与 Checkpoint。

这一过程还需要统一关联信息：Run ID 标识任务，调用编号标识动作，审批编号标识授权，产物引用指向日志或差异。这样，从一条失败记录就能找到它所属的任务、操作和审批。

最容易出问题的是执行中断。恢复时，要根据已有证据决定下一步：

|中断位置|恢复时怎样处理|
|---|---|
|仍在等待审批|查询原审批状态，核对有效期和待执行内容|
|已批准，能够确认尚未开始执行|重新检查执行条件，再按既有领取机制执行|
|操作可能已经发出，结果未保存|先核对文件或进程现场，确认实际后果|
|结果已持久化，但计划未更新|根据已有结果补齐状态，避免再次执行|
|补丁已应用，但尚未复测|继续验证当前内容|

**Checkpoint 保存任务状态，不能撤销已经写入的文件。** 审批通过也不代表补丁已经成功应用。因此，恢复逻辑必须结合工作区现场和执行记录。

LangGraph 审批流程的 Checkpoint 同样有自己的范围：它可以恢复审批流程，但整个代码任务还需要保存计划、工具调用、工作区信息和验证证据。两者通过运行编号和审批编号连接。

如果补丁执行结果不明，就先检查文件内容是否符合预期，并确认是否存在其他改动。无法确认时，转人工处理。这比直接重放补丁更容易保持状态一致。

### 7\.4 运行两类任务并核对最终产物

模块连接完成以后，再从用户入口运行两类任务。这次重点检查完整交付。

运行前，确认真实模型配置、工作区初始状态和审批服务均已就绪。每次验收使用独立工作副本，避免上一轮产物影响结果。

#### 任务一：代码理解

沿用现有 CLI：

```Bash
node --import tsx src/cli.ts agent \
  "帮我找出该项目的登录逻辑，并生成 Markdown 说明文档。" \
  --task understand \
  --dir ../samples/1_login_demo
```

按当前生效的审批策略完成必要确认，然后检查：

|产物或记录|核对内容|
|---|---|
|登录说明文档|入口、调用关系和关键判断是否准确|
|路径引用|是否指向实际存在且相关的代码|
|Git 状态与差异|是否只产生允许的文档改动|
|Trace|文档中的关键结论是否有阅读依据|
|最终状态|文档是否实际落盘，是否仍有待执行操作|

文档存在只是第一步。还要把关键结论与对应源码对照，确认它能够帮助读者理解项目。

#### 任务二：测试修复

先运行目前已有的修复路径：

```Bash
HITL_API_KEY=demo-key node --import tsx src/cli.ts agent \
  "读取登录会话模块的失败测试与日志，修复源码并复测，不修改现有测试。" \
  --task fix_tests \
  --dir ../samples/2_bug_fix/demo-app
```

这里的 `demo-key` 沿用本地审批演示配置。执行过程中完成所需审批，结束后独立查看测试结果与 Git 差异。

|产物或记录|核对内容|
|---|---|
|初始失败日志|修复前的问题是否确实存在|
|源码差异|是否针对失败原因，是否存在无关修改|
|最终测试结果|是否对应修改后的当前内容|
|审批记录|实际执行内容是否与获批内容一致|
|变更说明|是否准确说明修改与验证结果|

最后，把两类任务的结果交给 6\.4 设计的评估模块，汇总产物、执行状态、验收结论、审批和资源消耗。

到这里，项目组合就有了明确的检查方式：从入口启动任务，沿执行链查看记录，最后用文件、测试和差异核对交付。下一节再主动制造失败和中断，验证这些连接在异常情况下是否仍然可靠。

```Markdown
  data/platform.db 三张表：audit_records（谁调了什么、结果与耗时）、trace_events（每轮上下文渲染等事件）、approvals（待批与已批的写操作）。

【验收 AC】
  AC-1 npm test 全绿：每件能力至少一份单测（契约 / 运行时 / 沙箱 / 工具 / 任务 / 审批 / 上下文 / 决策器 / 护栏 / 提示词）
  AC-2 任务一离线跑通：--decider mock 走 understand-login.yaml，停在写文件审批，批准并执行后生成 artifacts/login-flow.md
  AC-3 任务二离线跑通：run_test 第一步即被门口拦下（AWAITING_APPROVAL），批准后打补丁、复跑、git_diff
  AC-4 参数错误的调用不进入 handler；越界路径被沙箱拒绝
  AC-5 长输出被截断、旧步骤压成一行摘要，审计留全量哈希

【明确不做】
  - 不做跨任务批量评估入口（cli eval 留给后续）
  - 不接 MCP：十件工具走 pi 的 registerTool 扩展点
  - 不修改样本已有测试来让它变绿：tests/** 由沙箱拒绝写入
  - 不引入向量召回与长期记忆：短期记忆就是受预算约束的对话
```





## 八、验收与工程复盘

上一节把模块接成了完整执行链。现在回到第一节的项目目标，检查哪些已有证据支持，哪些还需补齐。

**验收要同时看交付结果和执行过程：** 文档要有代码依据，修复要有测试证据，权限和审批要落实到操作，中断后也要能说清任务停在哪里。下面先按目标逐项检查，再用几类失败场景验证关键边界。

### 8\.1 按项目目标逐项验收

先把验收清单摆出来。每一项都要能找到对应的文件、日志或测试记录。

|项目目标|验收动作|通过依据|
|---|---|---|
|Agent Loop|运行需要多次工具调用的任务|工具结果进入下一轮，任务能继续推进并正确停止|
|Planning|查看计划及执行中的修订|步骤有完成条件，进度与实际证据一致|
|搜索与读取|执行登录逻辑分析|能定位相关文件，说明中的引用真实有效|
|文件修改|执行受控写入和补丁操作|实际差异与任务要求、获批内容一致|
|测试与修复|从已知失败状态运行修复任务|保留修复前失败、源码差异及修复后通过结果|
|新增测试|为目标函数新增边界用例|新测试能暴露目标缺陷，修复后与原测试共同通过|
|人工确认|分别执行批准与拒绝场景|未批准不执行，批准只授权对应操作|
|Sandbox|尝试访问禁止路径或执行禁止操作|实际访问被阻止，拒绝原因可追踪|
|状态与 Checkpoint|在指定位置中断并恢复|找回进度，核对现场，避免重复写入|
|工具契约|提交缺字段、错类型等参数|handler 未执行，错误准确回写|
|上下文与预算|使用长日志和多轮任务|输入受控，关键证据可查，预算耗尽时停止|
|评估与追踪|汇总两类任务的执行记录|状态、验收结论、产物和消耗能够相互对应|

执行这张清单时，给每项标记“通过、失败、待验证或未覆盖”，并附上证据位置。例如，测试修复样本预置了失败用例，能验证修复流程，但还不能证明 Agent 会生成有效的新测试——在补齐之前，这一项就标“未覆盖”；一次运行还在等审批，即使前面已完成搜索和分析，也只能记录当前进度。

这张清单也帮我们判断何时收工：某项证据充分就查下一项，某项失败就定位缺口修复，避免反复跑成功路径却没有新增验证价值。

### 8\.2 失败案例：参数错误、测试失败、审批中断与恢复

成功路径跑通后，再主动制造几种失败。以下是建议执行的验收场景，实际结果由测试和运行记录填写。每次都按同一个顺序复盘：**看见了什么现象，操作有没有发生，哪条规则应该处理，怎样证明修复有效。**

#### 案例一：参数错误，工具有没有提前执行？

向 `write_file` 提交缺少 `content` 的参数。预期是 Runtime 返回参数错误、handler 不执行、目标文件保持原样，错误携带调用编号进入下一轮。如果日志显示“校验失败”而文件已经变化，就沿调用链检查：是否先进入 handler 再做校验，或某个入口绕过了 Runtime。

修复后同时验证两件事：

- 错误参数下，handler 调用次数为零。

- 修正参数后，调用重新经过完整检查，并正常执行。

这样才能证明校验位置正确，也没有误伤合法调用。

#### 案例二：测试失败，系统有没有把执行结束当成任务完成？

让 Agent 运行一个必然失败的测试。测试进程正常结束只说明取得了结果，失败退出码、断言信息和日志必须进入下一轮，任务状态不能直接变成“修复完成”。

如果 Agent 宣布完成，先检查失败发生在哪个连接上：

|观察到的现象|优先检查|
|---|---|
|模型没有看到失败日志|工具结果回写、截断和上下文组装|
|模型看到了失败，计划却标记完成|计划完成条件|
|模型提出结束，程序直接通过|完成检查|
|修改后沿用旧的通过结果|测试证据与工作区版本的关联|

修复这类问题要补上对应检查，并用同一失败场景复验——只改提示词要求“认真检查”，不足以证明完成条件已经生效。

#### 案例三：审批中断，恢复后会不会错用旧授权？

让任务停在补丁审批前，保存状态并中断进程。

恢复时要找回原待审批操作、查询审批状态，并核对补丁、目标文件和授权条件；等待期间文件发生变化，就重新核对方案，不能直接应用旧补丁。

还要测试两种操作：

- 重复提交批准决定。

- 批准后再次请求执行同一张审批单。

两种情况下都不能重复写入，审批记录要体现是否已被领取、是否完成和最终结果。

#### 案例四：文件已经修改，执行结果没有保存

这是恢复里最需要谨慎的一类：补丁可能已经应用，但进程在保存结果前退出，Checkpoint 里没有成功记录，不能据此认定“尚未执行”。恢复逻辑要读取当前文件，结合修改前状态和预期变更判断现场：

- 能确认补丁已应用，就核对并记录事实，再继续测试。

- 能确认尚未应用，就重新检查执行条件后处理。

- 存在其他改动，无法判断，就保留现场并转人工处理。

验收重点是证明系统没有盲目重放；即使无法自动恢复，也要把“不确定在哪里、需要检查什么”交代清楚。

这几类失败最终都指向同一个工程问题：**程序记录的状态，是否与实际执行事实一致。**

### 8\.3 本次实现的边界与已知限制

验收结束后，把能力范围写进交付说明。按当前基线及前面规划的改造内容，需要重点核对以下边界：

|边界|应怎样说明|
|---|---|
|样本覆盖|两类样本通过，只能证明对应任务与环境下的表现|
|新增测试|已放开受控写入（`tests/generated/`）；新用例是否有效仍需独立证据|
|配置化|已有工具能够承接的任务可以复用配置；新能力仍需扩展代码|
|模型输出|同一目标可能产生不同操作顺序和消耗，需要按结果与约束验收|
|上下文压缩|可能省略细节，必须保留关键事实和补查入口|
|中断恢复|对结果不明的写操作，需要核对现场，部分情况需人工接管|
|Sandbox|保护范围取决于实际执行机制，路径检查不能代替进程层隔离|
|自动评估|文件、测试和差异可自动核对（`cli eval` 已接入）；解释准确性仍需明确检查点或人工复核|

统一评估入口（`cli eval`）与受控新增测试（`allow_write_extra`）已经补齐；严格的真实模型模式与部分上下文管理规则仍属待接入设计，必须有代码和验收记录才能列入已完成能力。

真实模型的一次成功只是样本证据，不能推导稳定成功率；要讨论稳定性，需要固定任务集合、记录每次成败，再按数据判断。

这一版项目的价值，在于让任务、工具、状态、审批和证据之间形成可检查的连接。后续扩展仓库和任务时，可以沿这些连接定位差异与缺口。

### 8\.4 哪些问题由 AI 辅助，哪些必须由工程师把关

做完这一轮，回到课程最关心的问题：用 AI Coding，工程师需要掌握到什么程度？

AI 可以承担大量实现工作——补 Schema、写配置读取、整理工具适配、生成测试场景、连接日志与报告。工程师要能给出明确要求，并判断生成的代码是否满足要求。

|工作|AI 可以辅助|工程师必须把关|
|---|---|---|
|需求拆解|整理流程、提出任务与模块划分|交付目标、完成条件和范围是否正确|
|代码组合|查找接入点、生成适配代码|是否复用已有路径，是否绕过关键检查|
|工具契约|编写 Schema 和错误结构|输入输出是否足够明确，失败是否阻止执行|
|人工确认|实现审批流程与展示内容|授权绑定什么，何时失效，如何避免重复执行|
|状态恢复|编写存档和恢复分支|状态是否符合现场，写操作能否安全继续|
|测试验收|生成用例、执行命令、汇总记录|用例是否验证目标，结果是否足以支持结论|
|工程复盘|整理 Trace、提出原因假设|依据是否成立，修复是否处理了真正原因|

比如，你让 AI “加入断点恢复”，它可能生成一套能保存和读取 JSON 的代码。但你还要追问：补丁执行后、结果保存前崩溃怎么办？审批过期怎么办？恢复时文件被别人改了怎么办？这些问题决定恢复机制是否可用——把它们写成验收条件，再让 AI 实现并运行验证，才是完整的开发过程。

学到这里，可以用三个层次检查自己：

1. **能解释**：说明 Loop、Runtime、Harness、Sandbox 和 Checkpoint 各自负责什么。

2. **能追踪**：沿一次任务找到输入、决策、校验、执行、回写和完成检查。

3. **能修复并验证**：发现未校验执行、旧审批复用、错误结果丢失或写操作误重放，并用测试证明问题已经解决。

不要求脱离 AI 默写整套工程，但要看得懂关键连接，能指出错误会发生在哪里，并拿出证据确认修复有效。

这一轮验收与复盘完成后，项目就有了清楚的交付结论：哪些目标通过、依据在哪里、哪些能力仍待补齐，以及下一步从哪个模块继续演进。

## 九、本节小结：从机制学习走向项目交付

第二章阶段二建立了工具调用基础设施，让模型提出的工具请求能够经过注册、参数校验、权限检查、审批和审计，再进入实际执行。第三章在这套基础上，把能力延伸到持续推进的代码仓库任务：Loop 根据观察继续行动，Planning 组织步骤，状态与 Checkpoint 保存进度，Sandbox 限制执行范围，Harness 连接任务过程，LangGraph 承担明确的审批编排。**这些能力最终汇合到同一条任务链上：理解目标、执行操作、观察结果、处理偏差，并依据证据确认完成。**

本节用代码理解和测试修复两类任务，把这条链逐步展开。先盘点已有能力，再运行基线，随后检查任务配置、工具契约、上下文预算和人工确认，最后通过产物、测试、差异与执行记录核对结果。这个过程中，已经实现的能力继续复用，缺失的连接逐项补齐，尚未覆盖的目标明确记录。比如，利用预置失败测试完成修复，只能证明修复流程有效；要交付“新增测试”的能力，还需要证明新用例能够暴露目标缺陷。**项目完成度，要由验收证据支持。**

学完以后，面对一个新的岗位任务，你应当能够独立把交付目标拆成可验收行为，识别需要哪些工具、状态和流程，判断哪些模块可以复用、哪些需要扩展，再指导 AI 完成实现。代码生成以后，你要能沿调用链检查关键边界，通过失败场景验证参数校验、审批、恢复和完成判定，并根据结果决定下一步改造。掌握了这套项目分析、组合、验证和演进的方法，就能把前面学过的机制应用到新的业务中，逐步交付可运行、可检查、可维护的 Agent 系统。
