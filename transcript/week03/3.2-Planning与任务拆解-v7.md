# 3\.2 Planning 与任务拆解 v7

本节主线：先判断任务是否需要计划，再把任务拆成可验收的子目标，建立依赖和证据，最后用完成契约判断能不能交付。

贯穿案例：同一条提示词、同一个仓库，让 3\.1 的 Codebase Agent 和本节要做的 Planning Agent 各修一次同一个登录模块的会话过期边界问题。

## 序言

大家好，接着上一节。

上一节的 Codebase Agent 跑通了代码理解任务：搜索登录逻辑、读文件、写 `artifacts/login-flow.md`。这类任务的输入是明确的——找什么、写到哪，都说清楚了，做完就是做完了。

这一节把任务换成修复，输入还是只有一句话：

> 请修复登录模块的会话过期边界问题：先定位登录和会话相关代码，复现失败测试，分析根因，只修改必要源码，然后运行目标测试、边界测试和回归测试，最后把根因、改动和验证结果写入 artifacts/login\-fix\.md。

任务一换，性质就变了。

上一节是「执行一组已知步骤」，这一节是「在不知道答案的情况下找答案」。

提示词只说了是会话过期边界，没说错在哪一行：可能是日期粒度截断了时刻，可能是时区语义，也可能是边界该不该包含到期时刻。**而这三条里哪一条成立，只能靠工具结果去证实或推翻。**

于是 Loop 还能继续跑，只是会跑得很难看。

因为 Loop
里保存的是一条消息历史，它知道「模型读过什么、说过什么」，但不知道「任务还差哪几步」。

所以当工具结果推翻当前判断时，没有东西可以回答：哪一步的结论作废了？哪些跑过的验证要重做？手上这份改动到底能不能交？



**这不是模型不够聪明，是系统缺一份可检查的任务状态。**

这也正是你接下来会遇到的问题：单步查询、短任务，3\.1 的 Loop 就够了；可一旦要做跨模块修复、故障排查、多轮研究这类长程任务，「做到哪了、凭什么说完成」就必须由系统回答，不能靠模型自述。本节要补的就是这份状态。



先记住一句话：**Planning 把任务拆成有完成标准、有依赖关系的子目标，再根据真实证据判断下一步和是否可以交付。底层继续用 3\.1 的 Loop，工程上增加计划状态、计划操作、证据和完成契约。**



而这四样东西，模型都做不了主：计划存在哪里，谁能改，哪些步骤允许开始，什么证据能证明完成。**这就是本节和「写一段更好的提示词」的区别——你要加的是一层工程结构，不是一句更严厉的嘱咐。** 这四件事本节都会落到上一节的代码上。

那怎么证明这层结构真的有用？ 我先运行一下本节的代码，同一份提示词、同一个仓库、同样的工具，分别发给两个 Agent：一个是 3\.1 的 Loop，一个是加上计划层的 Planning Agent。

这里要交代一个前提，**对照组不是 3\.1 原样**——它的 Runtime 同样有 `apply_patch` 和 `run_test`，完成契约也已经从「生成
login\-flow\.md」换成了「当前代码版本上有改动、三个测试范围全通过、有交付说明」。

两者唯一的差别就是计划层，这样多出来的部分才能归因到 Planning。



这一节按四站展开：

|步骤|回答的问题|你要带走的东西|
|---|---|---|
|一、要不要计划|这个任务值得拆成计划吗|三种执行方式的判据，以及不用计划的场景|
|二、计划写成什么样|子目标怎么才算可验收，谁先谁后|`PlanStep` / `Evidence` 结构，`readySteps` 规则|
|三、计划怎么变|结果推翻假设时，改计划还是只改参数|偏差分类，最小修订，修订的工程约束|
|四、怎么落地与验收|怎么接到 3\.1 的 Loop 上，怎么证明有效|最小接线改动，不变量测试，真实运行对照|



注意：每次运行都在 `mkdtemp` 出的临时副本上执行，`fixtures/demo-app`
保持故障态；失败用例使用字面时间戳（`2026-09-11T00:30:00.000Z`），不依赖真实时钟。因此同一个失败每次都稳定复现，结果可预期。

## 一、要不要计划

首先，我们来解决第一个问题：拿到一个任务，到底要不要给它加计划？

前面说了 Planning 的好处，但不是说学了这套东西，以后每个任务都得先列计划。我们先看看，这次加了计划以后到底多了什么，再来判断什么任务值得这样做。

### 1\.1 同一份提示词，两个 Agent 跑出了什么

先看刚才那两份运行结果。两个 Agent 接到的是同一条修复任务，也都能读代码、改代码、跑测试。区别是，一个没有显式计划，一个把任务拆成了有状态的步骤。结果放在一起是这样的：

```Plaintext
codebase.md                     planning.md
执行轮数：8                      执行轮数：17
停止原因：COMPLETED              停止原因：COMPLETED
工具调用记录：38 条               工具调用记录：77 条
                                代码版本：r1
                                计划版本：v1
                                计划修订：0 次
                                步骤状态：
                                  - s1：completed，证据 4 条
                                  - s2：completed，证据 1 条
                                  - s3：completed，证据 1 条
                                  - s4：completed，证据 1 条
                                  - s5：completed，证据 3 条
                                  - s6：completed，证据 1 条
```

你第一眼可能会看轮数：一个跑了 8 轮，另一个跑了 17 轮。那是不是加了 Planning，反而做得更慢了？这次运行确实多用了几轮，我们不能把这个成本忽略掉。但先别只看轮数，还要看看它多做了什么。

看右边，除了最终结果，还多了 s1 到 s6 六个步骤。每一步是什么状态、关联了多少条证据，都单独记了下来。比如这次确认根因的时候，模型手里已经有源码阅读记录，但记录属于前面的阅读步骤。它后来又在根因确认步骤下读了一次源码，补上这一步自己的证据。

这次补读当然也有成本，但它说明了一件事：系统开始区分「做过这件事」和「这件事是在完成哪个步骤」。

所以两者的差别，可以这样理解：Codebase Agent 主要记录做过哪些动作；Planning Agent 在这些动作之外，还记录它们属于哪个子目标，以及这个子目标推进到了哪里。



比如你想知道三个测试范围有没有通过，Codebase Agent 的测试结果和最终报告里也能找到，不是说没有计划就没法验收。Planning 多出来的是步骤这层关系：这些测试是在验证哪一步？这一步现在完成了没有？它用了哪些证据？这些信息不用再靠读整段对话去整理，而是直接保存在计划里。

这才是我们这里要比较的东西：不是谁一定更快，而是任务变长以后，你是否需要这样一份能检查、能追踪的进度记录。



所以别把这个例子理解成「一个会修代码，一个不会」。两边都有修复工具，也都有最终验收要求。我们要看的是，在这个基础上再加计划，能不能把每一步的推进过程管得更清楚。

### 1\.2 三层机制各管什么，落到组件又是谁

看到这里，你可能会问：读完结果再决定下一步，Loop 本来不就在做吗？对，它本来就能做。要把这个问题说清楚，我们先把这三层分开看。

|层次|负责的问题|本节案例里的例子|
|---|---|---|
|Tool Calling|这一次调用哪个工具、传什么参数|读取 session\-policy\.ts|
|Agent Loop|工具结果怎么回写，下一轮怎么继续|读到失败日志后继续查实现|
|Planning|先完成什么、还缺什么、什么时候改变路径|先复现，再确认根因，再修复，再验证|

拿读取文件来说，Tool Calling 负责这次读哪个文件、传什么参数。读完以后，把结果交回模型，让它决定接着做什么，这是 Agent Loop 的事。Planning 关注的则是：这次读取在完成哪个子目标？这个子目标还缺什么？做完以后，哪些步骤可以继续？

所以，没有显式计划，模型一样可以看到测试失败以后换个方向。我们加计划，不是为了让它第一次学会「根据结果行动」，而是为了把多个子目标之间的关系和进度单独管起来。

那到了代码里，这些事情分别交给谁？下面这张表不用急着背名字，先抓住三件事：谁提建议，谁保存和检查状态，谁真正执行。

|对象|主要职责|
|---|---|
|Planner|提出子目标、依赖、下一步和修订建议|
|Plan / PlanStore|保存步骤、状态和修订历史，检查依赖与状态转换|
|pi Agent Loop|调用模型、处理 Tool Call、回写 Tool Result 并继续|
|Harness|装配模型、工具和计划组件，在执行接缝上落实约束|
|Tool Runtime|参数校验、权限检查、超时与工具执行|
|Verifier|检查实际证据是否满足当前验收条件|

还是拿这次修复来说。模型说：「我准备修改会话过期判断了。」这只是一个请求。假如计划要求先复现、再修改，PlanStore 就要先查复现那一步完成没有。检查通过以后，Runtime 还要看这个文件允不允许改。等代码改好了，也不能直接说任务结束，还得检查约定的测试有没有通过。

你可以这样记：模型负责提下一步，程序负责检查能不能做、做完算不算数。Harness 把这些部分接起来，pi 的 Loop 继续负责把一轮轮调用跑下去。有了计划，也不会把原来的权限检查和工具规则替换掉。

### 1\.3 什么时候不需要计划

分工清楚以后，再回头看成本就容易理解了。计划要创建、要更新，证据要关联，步骤状态也要检查，这些都会增加调用和等待时间。如果任务很简单，这一套管理可能比任务本身还重。下面这些情况，就不必急着让模型生成计划：

- 比如查一个订单状态、读一个指定文件，一次工具调用就能拿到结果，不用再拆步骤。

- 比如固定字段抽取、格式转换、通知发送，处理规则已经写清楚了，直接按规则执行就好。

- 比如审批流程，谁先批、谁后批是制度定的，不是让模型临时安排的，适合用固定 Workflow。

- 如果业务特别在意响应速度，而任务又没几步，就要算一算：花时间规划，能不能换来实际收益。

- 如果是高风险操作，不允许模型临时增删步骤，就先把执行流程锁定。这里限制的是模型改路线，不是说这种任务不需要记录进度或检查验收。

所以，不是任务听起来复杂，就一定要上 Planner。你要看：现有的工具调用或者固定流程，能不能把事情管住？如果已经够用了，就先保持简单。如果还需要持续跟踪好几个子目标、它们之间的依赖和各自的完成情况，再考虑显式计划。

### 1\.4 四种执行方式怎么选

那实际接到一个需求，怎么选呢？你可以按下面这张表，从简单的情况往下看。能用前面的方式解决，就没必要为了用 Planning 再多加一层。

|任务特点|优先选择|例子|
|---|---|---|
|一次明确操作就能完成|直接 Tool Calling|查询某个订单状态|
|步骤与异常分支能提前写清|固定 Workflow|固定规则的数据导入|
|下一步取决于执行中获得的信息|Agent Loop|调查登录测试为什么失败|
|还要持续追踪多个子目标、依赖和交付条件|在 Loop 中加入显式计划|跨模块修复并完成分层验证|

我们顺着看一遍。一次操作就有答案，直接调用工具。需要好几步，但步骤和分支都已经确定了，用固定 Workflow。如果必须先拿到结果，才能决定下一步查哪里、做什么，就用 Agent Loop。

到了最后一行，再多问一句：除了让模型继续做事，我是不是还得知道每个子目标做到哪了、谁在等谁、哪些验收还没完成？如果需要，就在 Loop 上加显式计划。它不是把 Loop 换掉，而是给 Loop 里的任务加一份结构化的进度记录。

这里有两个名字容易混。Workflow 不是只能从头走到尾，它也可以有分支、重试，甚至在某一步调用模型。另外，有计划能力，也不代表一定要单独再建一个 Planner Agent。先把计划存好、把操作入口和检查规则接好，同样可以提供显式计划能力。

这几种方式也可以一起用。比如排查故障时，让 Agent Loop 根据日志继续调查；如果排查任务需要跟踪多个子目标，就给它加计划。等修复验证完、准备发布时，再交给固定 Workflow，按既定流程发布。探索可以交给模型，不能省略的发布检查还是由程序控制。

### 1\.5 计划有两种形态，这个案例属于哪一种

好，现在假设我们已经决定用计划。接下来还要分清一件事：这份计划，是一开始基本就能定下来，还是得边做边调整？这就是一次性计划和动态计划的区别。

先说一次性计划。它不是只做一步，而是主要步骤在开始时就能列清楚，后面大多按这个顺序推进。比如上一节的代码理解任务，如果我们要给它列计划，可以先安排搜索入口、读取实现、整理调用关系、生成文档。具体读哪些文件，可能还要搜索之后才知道，但整体要做的事比较稳定。

你可能又会问：那它和 Workflow 有什么不同？区别在于步骤是谁定的。模型根据这次任务临时列出步骤，这是一次性计划；如果每次都做同一套操作，步骤和分支由工程师事先写好，那就直接用固定 Workflow。

当然，一次列好不等于永远不能变。读文件时发现路径变了，就先处理路径问题；如果发现原来的安排已经不适用了，也不能为了照着计划走，继续做错的事。

再看动态计划。本节的修复任务，开始时能确定的是「先查清问题，再修复，再验证」，但还不能确定具体该怎么改。这时计划先写诊断和验证目标，别把猜测直接写成修改结论。等读了源码、跑了测试，再决定后面怎么做。如果新证据让原来的安排不再适用，就申请修订。

这里要区分「允许调整」和「实际调整过」。这次真实运行里，模型读完源码就找到了按日期比较的问题，后面没有替换计划步骤，所以记录里是计划版本 v1、修订 0 次。中间补了一次步骤证据，但那不是改计划。

这也不矛盾。动态计划的意思是，遇到新情况时可以调整，不是每次执行都得改一遍。后面第三站会用确定性测试演示：原来安排的是 modifyPasswordLogic，证据出来以后换成 fixExpiryCheck。那是为了检查修订机制准备的场景，不是这次真实运行走过的过程。

所以回到这个案例，不是说没有 Planning 就修不好——对照组也修好了。我们选择加计划，是因为除了拿到修复结果，还想把阅读、复现、根因确认、修改、测试和交付这几个子目标分别管起来，并且允许后面的安排按证据调整。

这一节你先记住两个问题就够了：下一步是不是要看执行结果才能决定？如果是，Loop 可以解决。除此之外，是不是还要持续跟踪多个子目标、依赖和验收情况？如果也需要，再加显式计划。

到这里，「要不要计划」就判断清楚了。接下来我们不再讨论选哪种方式，而是拿这个修复任务看看：一份真正能用的计划，每一步到底该怎么写。

## 二、计划写成什么样

前面我们已经决定，这个任务值得加计划。接下来要问的是：计划到底怎么写？是不是列上「分析、修改、测试」几个词就够了？

还不够。我们要的是：模型知道每一步要做到什么程度，程序也有办法检查它到底做完没有。这一站就按这个顺序走：先把每一步的结果说清楚，再看这些信息怎么保存，最后确定哪些步骤要等前面做完才能开始。

### 2\.1 为什么「分析、修改、测试」不够

比如计划里写了一步「分析代码」：模型读了一个文件，算不算分析完了？读了十个呢？光看读了多少，说不清楚。因为这句话只说了一个动作，没说最后要拿到什么结果。下面这张表，就是把动作换成能检查的结果。

|模糊动作|可验收子目标|可接受的证据|
|---|---|---|
|分析代码|确认失败入口、相关模块和一个可证伪的假设|文件位置、调用链、失败断言摘要|
|修改代码|完成符合边界的最小修改|受控 Diff、修改理由|
|运行测试|目标用例通过，且没有新增失败|命令、退出码、测试范围|
|查看日志|确认时间、请求 ID、异常类型和调用链|结构化日志字段|
|修复缺陷|原问题消失，并存在防回归验证|修复前后对比、回归结果|

放回这次修复任务就更好理解了。「跑一下测试」只是动作；「目标、边界、回归三个范围都通过」才说清楚了要拿到什么结果。我们把这几个动作对照着改一遍：

|如果写成动作|改成可验收之后|
|---|---|
|「复现失败」|在 `scope=target` 上拿到退出码 1，并保留失败断言的期望值与实际值|
|「修一下」|产生当前代码版本上、允许修改范围内的最小 Diff|
|「跑测试」|`target` / `boundary` / `regression` 三个范围的退出码都为 0|

所以你写一个步骤的时候，可以多问两句：做完以后，我应该知道什么，或者拿到什么？拿什么来证明？这两句答得出来，这一步才有办法验收。否则模型说「我分析完了」，你还是只能相信它的描述。

### 2\.2 一份计划至少装什么

结果和证据说清楚了，接下来要把它们存起来——总不能每次都让模型回头翻聊天记录。代码里因此需要几类对象：Plan 保存整份计划，PlanStep 保存其中一步，Evidence 保存工具执行后留下的证据。下面先看类型，不用逐行背，重点看这些信息分别放在哪里。

```TypeScript
type StepStatus =
  | "pending"      // 等待依赖完成
  | "in_progress"  // 正在执行
  | "completed"    // 证据已通过步骤验收
  | "blocked"      // 权限、预算或外部条件阻塞
  | "skipped"      // 被替换或明确放弃；不等于 completed
  | "failed";      // 尝试失败，等待修订或重试

type EvidenceKind = "tool" | "test" | "diff" | "inspection";

/** 执行层留下的结构化证据。证据只由 Runtime 写入，模型只能引用 id。 */
interface Evidence {
  id: string;
  stepId: string;
  toolCallId: string;
  /** 产生该证据时的代码版本；换版本后旧的测试/改动证据不再能用于交付。 */
  artifactVersion: string;
  kind: EvidenceKind;
  summary: string;
  payload: Record<string, unknown>;
}

interface PlanStep {
  id: string;
  /** 完成后系统应产生的新事实，而不是"做个什么动作"。 */
  objective: string;
  dependsOn: string[];
  /** 事前定义的完成标准；与事后收集的 evidence 分开存放。 */
  successCriteria: string[];
  status: StepStatus;
  evidenceIds: string[];
  attempts: number;
  lastError?: string;
}

interface Plan {
  version: number;
  goal: string;
  constraints: string[];
  steps: PlanStep[];
  revisionCount: number;
  maxRevisions: number;
}

/** 一次修订请求：整体校验通过才提交，失败时原计划保持不变。 */
interface PlanRevision {
  version: number;
  reason: string;
  evidenceIds: string[];
  changes: string[];
}

/** 步骤验收器：返回缺失项；空数组表示证据满足该步骤的完成标准。 */
type StepVerifier = (step: PlanStep, evidence: Evidence[]) => string[];
```

这些字段为什么要分开？你可以带着刚才的修复任务来看：

- objective 说这一步要得到什么，比如「确认根因」，不能只写「分析一下」。

- successCriteria 先定怎么算完成，evidenceIds 等执行完再记下拿到了哪些证据——标准和结果不能混在一起。

- artifactVersion 记这份证据对应哪个代码版本。测试通过以后又改了代码，之前的通过记录就不能直接证明新代码也没问题。

- status 说这一步现在怎么样了。没开始、正在做、被阻塞、已经失败，后面的处理不一样，不能只用「完成或没完成」两个值。

- constraints 保存任务约束，实际限制还要靠执行检查落实；maxRevisions 则限制计划最多修订几次，避免一直改计划却不结束任务。

顺便区分一下：这些类型是我们在应用里加的，不是 pi 自带的 Planner。pi 继续负责循环，我们负责补上任务状态这一层。

### 2\.3 完成标准在事前，证据在事后

现在标准和证据都有了，那怎么判断完成？拿执行结果去对照事先定好的要求。听起来很直接，但有个地方特别容易写错：不能看到退出码是 0 就把所有步骤都算完成，也不能看到非零就把所有步骤都算失败。

比如当前这一步是「复现问题」，我们就是要看到原来的失败断言。如果确实复现了，测试虽然失败，这一步却完成了。可如果当前这一步是「验证修复」，同样的失败结果就说明还没修好。看下面这张表，重点看每份证据能支持多大的结论。

|证据|能证明|不能证明|
|---|---|---|
|scope=target 退出码 1|复现步骤完成（原问题确实存在）|修复完成|
|scope=target 退出码 0，且版本为当前|修复验证完成|边界与回归也通过|
|三个范围退出码都为 0，且版本为当前|本次修复在约定范围内可交付|仓库其它区域没有回归|

所以判断之前，先问「我们正在验收哪一步」。另外，非零退出码本身也不够：如果只是缺依赖，测试根本没跑到原来的断言，那不能叫复现成功。三个测试范围都通过，也只证明约定的测试要求满足了，整个任务还要检查修改和交付说明。

那证据由谁提供？不能让模型自己写一句「测试通过了」，再拿这句话给自己验收。证据要来自真实工具执行，模型只提交它的编号。这次运行里就出过一次证据归属的问题，模型后来自己纠正了。下面是日志里模型的一段说明：

▏ Evidence ev\-4 belongs to s3 \(not s1\)\. Let me reference only s3\-valid evidence\.

这段说明对证据编号的归属讲得有些乱，不要把其中任何一句当成系统返回的错误原文。要抓住的是后续动作：模型在 s3 下重新读了源码，补上根因确认步骤能引用的证据。这里演示的规则是：完成哪一步，就得引用属于哪一步的证据，不能拿别的步骤的记录顶上。

落到程序里：模型申请 complete 时，程序先确认这一步正在执行，再检查它提交的证据。证据这一部分主要看四件事：

1. 证据非空；

2. 引用的证据确实存在；

3. 每条证据的 stepId 与当前步骤一致；

4. test / diff 类证据的 artifactVersion 等于当前代码版本。

这四项检查回答的是：证据拿对了没有。接下来 StepVerifier 才继续判断：拿对的这些证据，够不够证明这一步完成？比如验证修复时，拿到了测试记录还不够，还得检查结果是不是通过。

这里还要把当前实现交代清楚：StepVerifier 可以由应用传进来，但本节真实运行的入口没有额外传入逐步骤的业务验收规则。也就是说，不能看到 successCriteria 存在，就以为程序已经逐条理解并检查了里面的文字。测试里专门传入过一个验收器，用来证明「失败的测试不能完成修复验证」。

那真实任务最后靠什么验收？靠任务级的 CompletionContract：它检查当前版本的修改证据，目标、边界和回归三个范围的通过记录，以及交付说明。你要分清这两层——一步能不能完成，和整个任务能不能交付，不是同一个检查。

### 2\.4 案例的六步拆解

有了这些概念，再看真实计划就不抽象了。这次模型把任务拆成六步：先读实现，再复现，接着确认根因、做修改，最后跑验证、写报告。下面这张表把日志里的步骤和证据条数放在一起，目标和完成标准改用课堂语言整理。

|步骤|目标（完成后产生的新事实）|完成标准|证据条数|
|---|---|---|---|
|s1|确认登录入口、会话实现与允许修改范围|能指出过期判定在 session\-policy\.ts，并说明调用它的位置|4|
|s2|复现目标用例失败|scope=target 退出码为 1，失败断言的期望与实际都有记录|1|
|s3|按证据确认根因|指出具体实现缺陷（slice\(0,10\) 截断到日期），证据来自源码读取而非猜测|1|
|s4|完成允许范围内的最小修复|当前代码版本上产生受控 Diff|1|
|s5|三个测试范围全部通过|target / boundary / regression 各自退出码为 0|3|
|s6|交付修复说明|artifacts/login\-fix\.md 写入成功，且写明未验证项|1|

这张表里有三件事值得留意：

- s1 到 s6 和证据条数来自日志；表里的目标描述是为了讲解整理的，不是完整计划原文。

- s5 是一步，但拿了三个测试范围的证据。这说明一个步骤不一定只调一次工具。你也可以把三个测试范围拆开管理，但讲这次运行时，要按它实际的一步三证据来说明。

- 这里的 s3 是先确认根因，再决定怎么改，不是提前认定密码校验有问题。后面第三站讲步骤替换，会用另外一个确定性测试场景，不要把两次过程混在一起。

这样，每一步做到什么程度算完成，就说清楚了。但光有这六步还不够：模型能不能挑着做？比如还没确认根因就先改代码？这就要接着看步骤之间的依赖。

### 2\.5 依赖决定谁先谁后

你可以把依赖理解成一句话：「这一步要开始，前面必须先拿到什么？」把这句话写清楚，程序才知道现在可以放行哪些步骤。

比如这次修复，我们要求先复现、确认根因，再允许修改。修改以后再跑的测试，才是对这次修改的验证；修改前的测试也有用，但它证明的是原来的状态。实际做工程时，除了这种先后关系，还要考虑输入、权限和资源等条件：

- 前置依赖：没有复现失败，不该贸然动代码；

- 数据依赖：判断根因需要错误栈和代码检索结果；

- 权限依赖：写文件、执行部署前要过策略和审批；

- 验证依赖：修改完成后必须运行目标测试；

- 汇合依赖：目标用例和边界用例都通过才能进入回归；

- 互斥选择：多个候选修复方案只能有一个进入写操作。

这些条件都要考虑，但不要以为写一个 dependsOn 就全解决了。我们这个最小实现只用它表达「必须等哪些步骤完成」；权限仍由 Runtime 检查，多个动作会不会抢同一个资源，也要另外处理。

#### ready 由程序计算，不由模型声明

先看最基本的就绪判断。程序把每一步拿出来，问两件事：它是不是还没开始？它依赖的步骤是不是都完成了？对应的代码就是下面这样：

```TypeScript
readySteps(): PlanStep[] {
return this.plan.steps.filter((step) =>
  step.status === "pending"
  && step.dependsOn.every((id) => this.requireStep(id).status === "completed"),
);
}
```

所以不是模型说「我准备好了」，这一步就真的就绪。假如 fixExpiryCheck 依赖 reproduce，而 reproduce 还没完成，模型即使选中了修复步骤，程序也不能让它开始。

为了知道这次调用在做哪一步，写文件、改代码、跑测试这些动作要带上 planStepId。执行前用这个编号查计划，确认步骤能不能做。依赖的步骤如果根本不存在，也得报错，不能因为查不到就当它已经完成。

#### skipped 不等于 completed

那如果前面的步骤不做了呢？能不能把它标成 skipped，让后面的步骤继续？这里要小心：不做了，不等于做完了。尤其是验证步骤，跳过以后当然不能当作验证通过。

所以本节的 skip\(\) 会先查有没有别的步骤还在等它：有，就拒绝直接跳过。你得先说明这一步为什么不需要了、后面的步骤改成等谁，再通过一次修订一起处理。

比如后面测试场景里的 modifyPasswordLogic 被 fixExpiryCheck 替换了，verify\_target 就不能继续等旧步骤，而要改成等新步骤。旧步骤保留下来记作 skipped，但真正解锁验证的，是新修复步骤完成。这两件事必须一起安排好。

#### 依赖就绪不代表没有冲突

还有一个问题：两步都就绪了，是不是就能同时跑？不一定。读两个互不相关的文件通常没问题，但如果两步都要改同一个文件，就可能互相覆盖。所以依赖检查只回答「前置条件齐不齐」，不能替代并发时的资源检查。

本节先沿用 3\.1 的顺序执行方式，把依赖和验收这条链讲清楚，暂时不展开并行调度。

到这里，你已经能写清每一步要什么结果，也能说明它在等谁。接下来就剩一个很实际的问题：如果执行以后发现原来的安排不对，这份计划要怎么改？

## 三、计划怎么变

前面我们把计划写出来了，但写计划的时候，很多信息还不知道。等真正开始读文件、跑测试，可能就会发现：有的只是参数写错了，有的却是整个方向想错了。这两种情况，显然不能用同一种办法处理。

所以这一站我们顺着三个问题讲：遇到问题先看什么？什么时候才需要改计划？如果确实要改，怎么保证改完以后前后还能接得上？

### 3\.1 收到偏差，先分流再动手

先别一看到报错就让模型重写计划。报错只说明这次执行和预期不一样，至于为什么不一样，还得看结果。我们先把发生了什么记清楚，再判断它有没有影响原来的安排，最后才决定是改参数、重试、改计划，还是停下来。

|新的观察|处置|是否修订计划|
|---|---|---|
|工具参数拼错|局部纠错：改正参数，保留原目标|不需要|
|目标文件不存在|先搜索实际位置；只是路径变了就局部修正，模块结构变了才修订|看情况|
|幂等查询短暂超时|受控重试，且不超出既定预算|不需要|
|测试断言指向到期边界|先补证据，再判断原修复假设是否还成立|前提被推翻时|
|测试缺依赖，断言根本没执行|先恢复测试条件，必要时新增环境准备步骤|需要时新增步骤|
|用户中途补充约束|检查计划与已有 Diff，让冲突步骤和相关验收失效|需要|
|权限拒绝或预算耗尽|记录阻塞或停止原因|不能靠改计划绕过限制|

表里情况不少，我们挑最常碰到的两种说一下：找不到文件，以及测试失败。

先说找不到文件。工具返回 NOT\_FOUND，你现在能确定的只是这个路径没找到，不能直接得出「项目里没有会话功能」。如果只是文件名拼错了，改正参数再读就行；如果你原来以为实现放在这里，搜索后发现它已经拆到了几个模块里，那后面的定位和修改安排就可能要调整。

所以先保留这次调用的路径和错误信息，再搜索实际位置。新位置确认之前，不要继续猜着路径改代码。

你要判断的就是：这一步要做的事没变，只是参数错了；还是当初安排这一步的理由已经不成立了？后者才可能需要动计划。

再说测试失败。拿到一个非零退出码，先别急着改业务代码。测试是跑到了断言但结果不对，还是依赖没装好，根本没开始测？也可能是超时，或者执行环境出了问题。先看运行了什么、测的是哪个代码版本、输出里具体报了什么，再决定往哪查。下面这四类，可以作为排查的起点。

|结果类型|下一步判断|
|---|---|
|assertion|测试到达了业务断言但没满足预期，检查实现、测试预期或根因假设|
|environment|缺少依赖、配置或 fixture，断言根本没执行——先恢复测试条件，不能据此认定业务代码有错|
|timeout|检查卡住的位置与资源限制，区分死锁、慢测试和外部等待|
|infrastructure|执行器或 CI 基础设施失败，记录阻塞并按平台策略处理|

比如本次案例，tests/session\-policy\.test\.ts:10:10 的断言期望 true，实际得到 false。这说明测试确实执行到了过期判断，只是结果和预期不一致，所以我们才继续检查比较逻辑。当然，超时也可能暴露死锁之类的代码问题，不是只有断言失败才值得查代码。关键还是先弄清这次失败证明了什么。

本节的 run\_test 会返回测试范围、退出码、是否通过、文件和代码版本等信息，但不会替你把所有失败都自动分好类。失败类型还要结合输出判断。所以模型说「这是环境问题」，你还得看它指出的是哪条错误，不能只接受这个标签。

如果判断只是短暂故障，也不是所有动作都能直接再来一次。有副作用的操作如果不知道上次到底执行成功没有，要先核对结果，再决定重试，不能一遍遍重复提交。

### 3\.2 什么才算一次修订

分清问题以后，再看要不要修订。这里不要数「已经失败了几次」，而要问：按现在拿到的信息，原来安排的步骤、依赖和后续路径还合不合适？

- 比如测试命令里的路径拼错了，改参数重跑，原来的目标和步骤没变，就不用修订。

- 如果证据推翻了根因判断，原先安排的修改步骤也不该再做了，就要替换步骤、调整依赖，这才是计划修订。

拿刚才的真实运行对照一下，就能看出这两者的区别。

这次运行的记录是计划修订 0 次。模型读完源码，找到了按日期比较的问题：同一天里，即使已经过了具体到期时间，两边的日期还是一样，所以没有被判为过期。原来安排的诊断、修复和验证步骤还能继续用，没有必要替换计划。

中间出过一次步骤证据不匹配，模型后来在 s3 下重新读了源码。注意：它不是把旧证据随便改个归属，也不是换了一份计划，而是补了一条当前步骤能用的新证据。步骤安排没有变，所以这不算计划修订。

所以这份真实日志能说明计划状态和证据关联在工作，但不能拿它来演示「错误假设被替换」。要看这条分支，我们就用下一小节的确定性测试：先安排一个不合适的修改方向，再检查系统能不能按要求替换它。

你也可以用这个办法看一个 Agent 有没有真正调整策略：它是根据新证据改了后面的安排，还是只是把原来的动作又做一遍？重复一次动作，不等于修订了计划。

### 3\.3 一次修订的完整记录

来看测试里准备的场景。初始计划第三步写的是 modifyPasswordLogic，也就是修改密码校验逻辑。这个方向是测试预设的，不是本次真实运行中模型提出的。测试脚本在复现之后安排了一次 revise\_plan 调用，模拟模型申请把修改方向换到会话有效期判断。申请内容如下：

```Plaintext
expectedVersion：1
reason：失败指向会话有效期判断，而不是密码校验
evidenceIds：[ev-3]
replace：modifyPasswordLogic → fixExpiryCheck
objective：修正会话有效期判断
dependsOn：[reproduce]
successCriteria：[按到期时刻比较]
```

这里别只盯着新步骤的名字。模型交上来的是一整份变更申请：基于哪个计划版本、为什么要改、依据哪条证据、旧步骤换成什么。程序收到以后，还不能马上改正式计划，要先过下面这些检查：

1. 版本对齐：expectedVersion 必须等于当前版本，否则 PLAN\_VERSION\_CONFLICT；

2. 预算：revisionCount 必须小于 maxRevisions，否则 PLAN\_MAX\_REVISIONS\_EXCEEDED；

3. 依据：reason 非空、evidenceIds 非空且都真实存在；

4. 在候选副本上应用变更：旧步骤标记 skipped，新步骤插在它后面，所有 dependsOn 指向旧步骤的自动改接到新步骤；

5. 整体校验候选：步骤 ID 唯一、依赖存在、依赖图无环；

6. 提交：版本加一、修订计数加一、追加一条修订记录。

检查通过之后，旧步骤不会消失，它会留下被替换的记录。新步骤接上来，原来等旧步骤的验证步骤改成等它。看下面这段，重点是 skipped、新步骤和 dependsOn 的变化：

```Plaintext
fix（原 modifyPasswordLogic）：skipped（replaced by fixExpiryCheck）
fixExpiryCheck：pending
verify_target.dependsOn：[fixExpiryCheck]
revisions[0].changes：
  replace:modifyPasswordLogic->fixExpiryCheck
  rewire:verify_target.dependsOn=fixExpiryCheck
```

为什么不能让模型直接改一串步骤文字？因为这里有三件事必须由程序守住：不能拿旧计划覆盖新计划，不能只改到一半，也不能无限修订。对应的规则放在这张表里。

|规则|做法|不这么做会怎样|
|---|---|---|
|版本对齐|请求携带 expectedVersion，与当前版本不一致就拒绝|基于旧版本的申请覆盖新计划|
|原子提交|替换、追加、依赖改接在候选副本上一次完成，校验通过才提交|中间状态里旧步骤已跳过、新步骤还没接上，验证步骤误判为就绪|
|预算上限|提交前检查 maxRevisions|失败循环里无限修订，永远不收敛|

这段实现里最值得看的是：先复制一份候选计划，在副本上替换步骤、改接依赖，再检查整份候选计划。如果发现有环、步骤编号重复，或者依赖不存在，就把这次申请拒绝掉，正式计划保持原样。

这样就不用担心「旧步骤改掉了，新步骤却没接好」的半成品状态。即使 skipped 本身不会放行下游，改到一半也可能让计划卡住或者依赖关系不完整。一次校验、一次提交，就是为了不把这种中间状态暴露给执行过程。

所谓最小修订，就是哪里不合适改哪里，不把已经做对的工作全推倒。旧步骤保留着，别人回头看记录，才能知道当时准备做什么、后来为什么换了方向。

本节先把这件事放在一个进程的内存里做。进程中断以后怎么保存和恢复，下一节 3\.3 再接着讲。

### 3\.4 修订只能改路径，不能改标准

最后还要守住一条底线：可以换做法，不能为了早点结束就偷偷把要求改低。比如回归测试一直没通过，模型不能把「回归测试通过」改成「运行过回归测试」，然后给自己打勾。用户要的结果没变，验收底线就不能由模型自行降低。

那如果不是模型想降低标准，而是用户真的补充了新要求呢？这就要按新要求重新检查受影响的工作。举一个课堂例子：

▏ 课堂示例：用户说「不要修改公共 API」。

这时不能只把这句话加进提示词就算处理完了。先记下新约束，再检查已经产生的 Diff：有没有改到公共 API？还没执行的接口改动先停下来；已经改了又不合要求的，就要修正并重新验证。之前测试通过，不代表新加的要求也满足了。

当然，也不是所有步骤都得重做。没有受到影响的结果可以保留，只重新处理有冲突的部分。如果之前已经发出通知或者做了别的不能直接撤销的操作，就把事实说清楚，交给人处理。改掉计划里的文字，不等于现实里的操作也撤销了。

不过，这里讲的是遇到新约束时应该怎么设计。本节代码会在创建计划时保存 constraints，也会把它展示给模型，但还没有运行中更新约束的提交接口。你以后要补这项能力，就要把版本记录、受影响步骤的检查和整体提交一起考虑，不能只让模型改一句话。

回头看，这几部分其实是连在一起的：先写清每一步怎么算完成，再按依赖推进；执行结果让原来的安排不适用时，只修订受影响的部分；最后还是拿证据验收。可以收成下面这一句话：

▏ 子目标给出完成标准，依赖决定执行顺序，观察推动修订，证据决定能否交付。

机制讲完了，下面直接落到代码上。

## 四、怎么落地与验收

前面已经把规则说清楚了。现在我们回到上一节的工程，看看这些规则具体接在哪里。

这一站先做两件事：把计划状态和检查规则接进原来的 Loop，再验证程序能不能拦住模型提出的不合适动作。之后还要跑一次真实模型，看整条链能不能走通。规则测试和真实运行各看一面，不能互相代替。

### 4\.1 改动范围：加计划层，不写第二套 Loop

先把起点说清楚。第一站拿来对比的 Codebase Agent 已经能修改源码、运行测试，也能按修复任务的要求做最终验收。我们不是再教它修代码，而是在这个基础上接进步骤状态、依赖和证据关联。下面这些文件可以按职责看，不用挨个背文件名。

|文件|相对对照组的变化|
|---|---|
|`model.ts`|沿用 Gateway 模型配置，不动|
|`run-context.ts`|增加目标源码、目标用例、边界用例、回归范围|
|`runtime.ts`|工具沿用，新增代码版本计数与证据草稿产出|
|`plan-store.ts`（新增）|保存计划、检查依赖、校验证据、提交修订|
|`plan-tools.ts`（新增）|创建、读取、更新、修订计划的契约与 Handler|
|`completion-contract.ts`（新增）|把对照组硬编码的完成判断提取为可注入契约|
|`planning-prompt.ts`（新增）|运行提示词与每轮替换的计划快照|
|`pi-tools.ts`|增加计划工具注册与 `planStepId` 的 Schema 扩展|
|`loop-guard.ts`|保留轮数与重复保护，增加计划门禁，完成契约改为注入|
|`agent-runner.ts`|装配计划工具、计划状态和运行提示词|
|`main.ts`|启动计划化 Loop，打印计划与证据摘要|

这里要分清哪些是修复任务本来就需要的，哪些是计划层新加的。apply\_patch 和 run\_test 负责真正改代码、跑测试，两边都需要；Planning 要做的是把这些动作产生的结果，关联到对应步骤上。最终测试有没有通过，两边也都要检查，不能把已有的验收能力都算成计划层新增的。

看代码时抓住三个位置就行：工具怎么注册，执行前后在哪里检查，最后在哪里把这些对象组装起来。对应的主要是 pi\-tools、loop\-guard 和 agent\-runner。我们没有重新写一套请求模型、处理工具调用、回写结果的循环，这部分仍然交给 pi。

### 4\.2 第一步：计划数据与计划工具

第一步先别接模型，先把计划本身管起来。比如依赖没完成时能不能开始，没有证据时能不能完成，修订出了问题要不要保留原计划。这些都应该是确定的规则，不应该换一个模型就换一种结果。PlanStore 负责这些状态和检查，计划工具再把操作入口提供给模型。

实现可以交给 AI 编程助手，但你要先把要求说清楚。下面这段提示词，就是把前两站讲过的规则整理成一份实现任务：

```Plaintext
在现有工程（model.ts、run-context.ts、runtime.ts、pi-tools.ts、loop-guard.ts、agent-runner.ts）上增加最小计划能力。
先读这些文件和实际 pi 类型，列出扩展位置，不要引入第二套 Agent Loop。

新增 plan-store.ts：
1. 定义 StepStatus、PlanStep、Plan、Evidence、PlanRevision；
2. PlanStore 提供 readySteps / start / complete / fail / block / skip / revise；
3. 只有依赖全部 completed 才允许开始；skipped、failed 都不满足依赖；
4. complete 必须引用已存在的证据，证据要属于该步骤，并通过 StepVerifier；
5. 测试与改动证据必须产自当前代码版本，旧版本的通过结果不能用于交付；
6. revise 携带 expectedVersion、reason、evidenceIds，整体校验通过才提交；
   替换步骤时保留旧步骤并标记 skipped，下游依赖原子改接到新步骤；
7. 提交前检查修订次数上限；步骤 ID 唯一、依赖存在、依赖图无环；
8. 先实现单进程内存版本。

新增 plan-tools.ts：create_plan / get_plan / update_plan_step / revise_plan 的契约与 Handler。
模型只能提出操作，状态只能由 Handler 修改；complete 只是完成申请。

交付类型、Handler、工具注册，以及覆盖上述规则的测试。
不要修改模型配置，不要新增第二个工具执行入口。
```

AI 把代码写出来以后，不用先纠结类拆得漂不漂亮，先检查关键规则。比如传一个不存在的证据编号，它会不会拒绝？依赖还没完成，步骤能不能被启动？后面 4\.6 会把这些检查整理成验收清单。

### 4\.3 第二步：接进 pi 的四个 Hook

计划层自己能工作以后，第二步才是接进 Loop。接在哪里呢？沿着一次工具调用看就很清楚：执行之前检查步骤，执行之后保存证据，下一轮给模型看最新计划，准备结束时检查交付要求。这四个时机，正好对应下面四个 Hook。

|执行位置|本节增加的行为|
|---|---|
|beforeToolCall|校验动作绑定的步骤是否就绪；继续执行原有重复保护|
|afterToolCall|把 Runtime 的真实结果关联到步骤，形成可引用证据|
|prepareNextTurn|刷新计划版本、就绪步骤和最近证据摘要|
|shouldStopAfterTurn|保留原停止规则，改用注入的完成契约检查交付|

先看模型怎么知道当前进度。prepareNextTurn 会在准备下一轮时更新计划快照，把当前版本、就绪步骤和最近证据放到上下文里。代码是下面这样：

```TypeScript
config.prepareNextTurn = async ({ context }) => ({
context: {
  ...context,
  systemPrompt: composeSystemPrompt(BASE_SYSTEM_PROMPT, session),
},
});
```

这里的 composeSystemPrompt 会把基础规则、规划规则和当前计划快照拼起来。注意第一轮也要准备好这些信息，不能等模型已经开始操作了，才告诉它要先建计划。计划还没创建时，就明确告诉它「尚未创建计划」。

后面每轮更新的是当前快照，不是把旧计划一份份往后贴。否则模型看到好几个版本，既占上下文，也容易拿错当前状态。

接这段代码时，再检查三件事：

- 工具的原始结果仍然要由 pi 回写。计划快照只是帮模型快速看进度，不能把真正的 Tool Result 换没了。

- 仓库文本和工具输出只是待分析的数据。即使摘进了快照，也不能把里面的话当成系统给出的指令。

- planStepId 是用来找计划步骤的，不是业务工具的参数。计划检查用完以后，进 Runtime 之前要把它剥离掉。

把这些接入要求交给 AI 编程助手，可以用下面这段提示词。重点不是让它再写一个循环，而是把检查接到已有入口上：

```Plaintext
把已完成的 PlanStore 接入现有 pi runAgentLoop。

保留流式输出、取消信号、最大轮数、重复调用保护和原工具权限。
1. 给工具 Schema 增加可选 planStepId；写文件、改代码、跑测试必须携带，
  由 beforeToolCall 校验，适配层在调用 Runtime 之前剥离该字段。
2. Runtime 只产出证据草稿；afterToolCall 补全步骤 ID、toolCallId 和当前代码版本后写入 EvidenceStore。
3. prepareNextTurn 每轮刷新计划快照，不重复堆积历史；第一轮就注入规划规则与初始状态。
4. 把 LoopGuard 中硬编码的 login-flow.md 完成判断提取为 CompletionContract：
  保留原代码理解任务的契约；
  为修复任务新增「当前版本有改动 + 目标用例、边界用例、约定回归全部通过 + 有交付说明」。
5. 模型不调用工具不代表完成；证据不足沿用 Follow-up 机制继续。
6. 预算耗尽、取消、阻塞必须输出真实停止原因，不能标为 completed。

依据仓库实际 Hook 类型实现，交付最小 Diff 和验证结果。
```

这里特别看第 4 条：生成说明文档的任务和修复测试的任务，当然不能用同一套完成条件。对照准备时已经把修复验收补上了，接入计划层时还要保留它，不能换成「步骤全部打勾就结束」。最终仍然要检查当前代码版本的修改、测试和交付说明，否则计划看着完成了，实际问题可能还在。

### 4\.4 第三步：运行提示词与任务输入

代码接好了，还要让运行中的 Agent 知道这些入口怎么用。先分清两种提示词：前面两段是给 AI 编程助手的，让它替我们写工程代码；下面这一段才是给业务 Agent 的，告诉它接到任务以后怎么推进。

```Plaintext
你是代码任务 Agent。根据任务规模决定是否使用显式计划：
简单查询直接调用工具；复杂修复先创建或读取计划。

计划步骤描述可验收结果，列出 dependsOn 和完成标准。
未知根因先安排诊断，不把猜测写成已经确认的修改目标。
执行受计划管理的动作时携带对应 planStepId。

每次工具返回后：
- 判断结果支持还是推翻当前假设；
- 条件未变化就继续就绪步骤，局部参数错误先局部修正；
- 假设或约束变化时，引用证据申请 revise_plan；
- 遇到权限或预算限制，报告阻塞，不绕过规则。

申请完成步骤时引用真实 evidenceIds。
不得降低验收标准，不得删除必要验证以提前结束。
最终报告包含改动、实际验证命令、结果和未验证项。
只输出必要判断与行动依据，不要求展开完整思维链。
```

运行规则说的是「遇到这类任务怎么做」，任务输入说的是「这一次具体做什么」。这次输入还是第一站那条修复要求，两者不要混在一起：

```Plaintext
请修复登录模块的会话过期边界问题：先定位登录和会话相关代码，复现失败测试，分析根因，
只修改必要源码，然后运行目标测试、边界测试和回归测试，最后把根因、改动和验证结果
写入 artifacts/login-fix.md。
```

你可能会问：提示词只说了目标测试、边界测试和回归测试，工具怎么知道该跑哪些文件？这些在运行上下文里已经配好了——targetSuite、boundarySuite、regressionSuite 分别对应约定的测试文件，targetSource 指定允许修改的源码，报告写入范围也有限制。不是让模型自己随便选一组容易通过的测试。

所以提示词和程序各有作用：提示词让模型知道应该怎么用这套能力，程序负责检查它有没有越过边界。只写提示词，没有执行检查，模型可能不照做；只有检查，不把规则告诉模型，它又不知道该怎么改正下一步。

### 4\.5 三个容易写错的地方

到这里代码能跑了，但还不能只看一次成功结果就说没问题。验收 AI 写的实现时，我建议先盯住下面三种错误，看看程序会不会放过去。

第一种，有证据就给完成：比如只检查 evidence\.length \> 0，拿到一份测试失败记录也算通过。这就把「有结果」和「结果满足要求」混在一起了。验证修复这一步，必须检查对应的测试要求是否满足。

第二种，把跳过当成完成。前面的验证没做，只是标了 skipped，后面的步骤就被放行了。这样等于绕过验收。你要检查的是：跳过以后依赖有没有正确处理，而不是只看状态是不是从 pending 变成了别的值。

第三种，只在提示词里要求遵守依赖，执行前却不检查。正常运行时模型可能刚好按顺序做，看不出问题。你得故意让它提前调用修复或者验证工具，看看真正的 handler 有没有被拦住。

### 4\.6 验收一：计划层规则

先检查计划层本身，不让真实模型的随机输出干扰判断。plan\-store\.test\.ts 里有 13 个用例，用明确的输入去试这些规则。下面这张表不用背错误码，重点看：不合法的操作有没有被拒绝，拒绝以后原来的状态有没有保住。

|测试|必须观察到的结果|
|---|---|
|依赖未完成时申请开始|PLAN\_STEP\_NOT\_READY；readySteps\(\) 只给出 inspect|
|必要前置被标记 skipped|PLAN\_SKIP\_REQUIRES\_REWIRE；下游仍未就绪|
|没有证据申请完成|PLAN\_COMPLETION\_REQUIRES\_EVIDENCE|
|引用不存在的证据|PLAN\_UNKNOWN\_EVIDENCE|
|证据不属于被完成的步骤|PLAN\_EVIDENCE\_STEP\_MISMATCH|
|证据存在但不满足标准|PLAN\_COMPLETION\_REJECTED，例如修复验证拿到 exitCode=1，步骤留在 in\_progress|
|引用修改前版本的通过结果|PLAN\_EVIDENCE\_STALE，不能用于交付|
|替换修改步骤|旧步骤保留为 skipped，verify\.dependsOn 改接新步骤，changes 记下 replace: 与 rewire:|
|修订产生环|PLAN\_DEPENDENCY\_CYCLE，整次修订被拒，快照与修订前完全相等|
|修订缺理由或缺证据|PLAN\_REVISION\_REQUIRES\_REASON / PLAN\_REVISION\_REQUIRES\_EVIDENCE|
|以旧版本发起修订|PLAN\_VERSION\_CONFLICT，版本不变|
|超过修订预算|PLAN\_MAX\_REVISIONS\_EXCEEDED，版本与步骤状态不变|
|创建计划时依赖不存在|PLAN\_UNKNOWN\_DEPENDENCY|

这里再对应一下前面说的两个细节。skip\(\) 被拒绝，说明请求没有生效，原来的状态应该保留；如果那个前置步骤本来已经完成，下游仍然可能是就绪的，不能一概说它一定没就绪。

另外，测试失败不能完成「修复验证」，不代表它不能完成「复现问题」。真实运行的 s2 就是拿到预期失败以后完成的。业务标准要由对应的验收逻辑检查；把 successCriteria 写进计划，并不会自动生成这些检查。

### 4\.7 验收二：Loop 集成

计划层单独跑没问题，还得检查它有没有真正接进 Loop。比如 PlanStore 本来会拒绝，但工具执行时根本没调用它，那规则等于没用。agent\-runner\.test\.ts 用脚本预先安排模型的返回值，再让完整 Loop 处理这些请求，一共检查下面五种情况。

|测试|必须观察到的结果|
|---|---|
|完整闭环：从初始假设到证据修订|计划版本从 v1 到 v2，modifyPasswordLogic 变 skipped，verify\_regression 依赖改接为目标与边界两项；源码真的被改写；交付说明真的落盘|
|受约束的动作缺少 planStepId|PLAN\_STEP\_REQUIRED，apply\_patch 的 handler 调用次数为 0|
|绑定未就绪步骤的调用|PLAN\_STEP\_NOT\_READY，run\_test 的 handler 调用次数为 0|
|引用不存在的证据申请完成|PLAN\_UNKNOWN\_EVIDENCE，步骤留在 in\_progress|
|证据不足时模型给出 Final|注入 FINAL\_REJECTED Follow\-up 继续；本轮上限用尽后停止原因是 MAX\_TURNS\_EXCEEDED|

这里特别看「缺少 planStepId」和「绑定未就绪步骤」这两行。除了看到错误消息，还要看到 handler 调用次数为 0。只有这样，才说明动作在执行之前就被拦住了，而不是文件已经改了，系统才补一句「你不能这么做」。

再分清测试覆盖的位置。重复调用保护、最大轮数和取消信号，在 3\.1 的 codebase\_agent\_demo/tests/loop\.test\.ts 里有对应用例；本节沿用这些机制，但不能把旧项目的测试直接说成本节所有接线分支都测过了。本节这五个集成用例，重点看计划门禁、证据处理、修订闭环，以及证据不足时继续到轮数上限的行为。

所以当前项目的 npm test 里是 18 个用例：计划层 13 个，Loop 集成 5 个。运行测试用 npm test，检查构建用 npm run build，启动真实任务用 npm start。命令跑过以后，要记录实际结果，不要把用例数量当成全部行为都验证过的证明。

### 4\.8 真实运行怎么留证据

脚本化测试让我们能稳定地检查错误分支，但它毕竟提前安排好了模型会说什么。接下来还要换成真实 Gateway，看看真实模型会不会创建计划、绑定步骤、补证据，最后走到交付。这次运行就别只留一句「成功了」，要把初始计划、工具观察、步骤证据、代码版本、最终测试结果和未验证项一起保存下来。

看结果时也别为了显得能力强，给日志里没发生的事情加戏。这次真实运行修订了 0 次，就如实说 0 次；替换错误假设的过程，是前面那个确定性集成测试演示的。两种材料都保留，但要说清楚各自证明了什么。

最后可以把验证任务也交给 AI 编程助手，但要求它把实际命令、结果和没覆盖的部分说清楚。下面这段就是收尾时的检查要求：

```Plaintext
验证本次计划能力改动：
先运行计划规则的确定性测试：依赖未就绪、证据缺失、证据不属于该步骤、
旧版本证据、有环的修订、旧版本修订、超出修订预算。
再沿用现有 Gateway 真实运行一次登录修复任务，记录实际命令、退出码、计划修订与交付结果。
检查受约束的调用缺少 planStepId 时，handler 是否真的没有执行。

不得为通过验收而删除断言、降低标准或伪造工具结果。
区分已实现、已验证和未验证项；环境阻塞时给出具体原因。
最后说明相较对照组修改了哪些文件，以及这些改动各解决什么问题。
```

### 4\.9 学到什么程度算掌握

学到这里，不是要求你关掉 AI，自己默写一个 Planner。你真正要掌握的是：拿到一个新任务，能不能决定要不要计划；看见一份计划，能不能指出哪里不好验收；执行出了问题，知道该改参数还是改计划；代码交回来，知道用什么反例检查它。对照这四站自查一下：

|站|要能回答|
|---|---|
|一、要不要计划|这个任务该用 Tool Calling、固定 Workflow、Agent Loop，还是加显式计划|
|二、计划写成什么样|子目标怎么写成可验收状态，证据由谁提供，哪些步骤当前就绪|
|三、计划怎么变|哪种失败只需局部纠错，哪种变化必须走修订，修订为什么不能降标准|
|四、怎么落地与验收|怎么在 pi 的接缝上验证拦截、证据关联和完成条件|

以后换一个任务，也可以照这个顺序来：先把目标、边界和完成条件说清楚，再让 AI 补实现，最后主动试那些不该被放行的情况。代码可以交给 AI 写，但什么算做好、什么不能做，以及你实际上验证了什么，这几件事还是要由你把关。

## 本节小结

Planning 给 Harness 提供的是可执行、可验证、可修订的任务状态：子目标要有完成标准，真实存在的依赖要显式表达，完成要由符合条件的证据支撑。

计划表达的是当前的行动假设，而工具结果、测试失败和上下文变化都会推翻旧假设。所以成熟的 Agent
不追求第一次计划就完全正确，它追求的是：遵守当前有效的约束，历史可追踪，证据可验证，用最小修订调整下一步。

到这里，我们能把一个长程目标拆成计划，并在执行中根据证据修订路径。但计划、步骤、工具结果和修订记录目前都放在内存里，进程中断或上下文压缩之后就会丢。下一节进入 State
Machine 与 Checkpoint，把这些执行状态持久化，并解决任务中断、恢复、复现和人工接管。
