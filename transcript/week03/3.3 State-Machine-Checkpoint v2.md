# 3\.3 State\-Machine\-Checkpoint v2

# 3\.3 State Machine 与 Checkpoint

## 序言

大家好，上一节，我们让 Coding Agent 跑通了从拆解任务、执行计划，到根据结果调整下一步的完整闭环。现在，它已经能通过多轮执行，逐步完成任务。

今天，我们继续处理登录模块的会话过期问题，但要增加一个要求：**让 Agent 做到一半停下来，再重新启动，看看它能不能接着往下做。**



这就带来了几个问题：它怎么知道上次做到了哪一步？哪些操作已经完成，哪些还没执行？又该根据什么决定下一步？

这正是本节要解决的问题：**用状态记录任务进度，用检查点保存恢复所需的信息，让 Agent 在中断之后能够继续完成任务。**



接下来，我们分三层展开，先弄清楚：**哪些能力可以直接用，哪些需要写代码串起来，哪些需要我们自己设计。**

- 第一层，**直接使用。** pi 已经提供了现成能力，通过命令和参数就能使用，不需要额外写代码。

- 第二层，**编写代码，把能力串起来。** pi 提供了函数、钩子和事件，我们需要把这些接口接入自己的任务流程。

- 第三层，**根据业务设计规则。** 任务状态怎么保存、中断后何时恢复、哪些操作必须审批，这些需要我们结合业务要求，自己设计并实现。

这样分层，也是为了明确学习重点：现成能力要会用，扩展接口要会接，业务规则要能设计和验证。



我们先从第一层开始，用 pi 自带的能力做一次中断与恢复演示，看看它能帮我们恢复什么，还有哪些问题需要自己解决。

## 一、pi 的原生中断与恢复能力

先看结论：**pi 自带会话持久化和续接能力。我们可以在新进程中找回之前的对话，但任务现场能不能恢复，还需要继续验证。**



这里先做一个小实验，把“会话能保存”这件事看清楚，再回到登录模块的修复任务。

### 1\.1 不写代码，先保存一次会话

【演示 1】启动 pi，并指定会话存档目录：

```Plaintext
pi --session-dir ./demo-sessions "在当前目录创建 notes.txt，内容写一句话：3.3 demo，然后读给我看。"
```

这次任务很简单：创建 `notes.txt`，再读取文件内容。运行结束后，除了这个文件，还要检查会话目录：

```Plaintext
ls demo-sessions/
cat demo-sessions/*.jsonl | head -20
```

目录里的 JSONL 文件就是会话记录。JSONL 的特点是一行一条记录，其中可以包含消息、会话信息以及其他会话条目，并不只是用户和助手的一问一答。



这就是**持久化**：把原本随进程存在的信息写入文件，让进程结束后仍然能读回来。这一步使用的是 pi 的原生能力，我们不需要自己实现存储。



不过，先不要把这份会话记录直接等同于完整的业务 Checkpoint。**会话记录保存了对话相关信息；业务 Checkpoint 还要保存任务进度，以及判断能否继续执行所需的依据。**后面我们会把这两部分接起来。



### 1\.2 换一个进程，验证它还记不记得

【演示 2】结束上一次运行，再打开一个新终端，使用相同的工作目录和会话目录：

```Plaintext
pi --session-dir ./demo-sessions -c "我刚才让你创建的文件叫什么名字？"
```

`-c` 是 `--continue`，用于续接最近的会话。这里已经指定 `./demo-sessions`，因此会从这个会话目录中查找。

如果它能回答 `notes.txt`，就说明历史信息已经被重新放入上下文。你不需要再次交代刚才的任务，新进程也能继续这段对话。

但这次演示只验证了一件事：**它能找回之前聊过什么。**至于文件后来有没有被别人改过、上次工具执行到了哪里，现在还没有验证。

### 1\.3 续接时，pi 实际恢复了什么

从使用者的角度看，续接只是加了一个 `-c`。从框架内部看，需要先读取会话记录，再重建当前分支的上下文，最后才能继续调用模型。

如果会话发生过压缩，重建时会使用压缩摘要和保留下来的消息，而不是把全部历史原样塞回去。这里的“重建上下文”也不意味着删除磁盘上的全部旧记录。

进入底层续跑接口时，还要满足消息链的要求。例如，`runAgentLoopContinue` 不接受空上下文，也不允许直接从最后一条为 `assistant` 的上下文继续。CLI 续接后提交一个新问题，与直接调用这个底层接口，是不同层次的操作，不能混为一谈。

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZWM2YjQ5NTRkY2U2MzNlNjgwNjdkYjFmYjdmNjA2ZTRfYWVhYWFhYzYzMThkOGZhOGUwMjAxNTBmZmI2YjIwMGZfSUQ6NzY4NTc4NDUxNjAxNDcyMjI3M18xNzg5NjE0MTc5OjE3ODk3MDA1NzlfVjM)

这些细节不要求大家背下来。要理解的是：**框架首先要保证送给模型的上下文有效；它不会仅凭这些检查，就知道业务任务的哪一步已经完成。**



如果有多个会话，可以根据需要选择命令：

|命令或参数|用途|
|---|---|
|`-c` / `--continue`|续接最近的会话|
|`-r` / `--resume`|打开会话选择器，选择要恢复的会话|
|`--session-id <id>`|使用精确的项目会话 ID；<br>不存在时会创建，使用前要核对 ID|
|`--fork <path|id>`|从指定会话派生一个新会话|
|`--session-dir <dir>`|指定会话存档目录|
|`--no-session`|关闭会话持久化|

其中，`--fork` 先记住用途即可。它复制的是会话，不会自动替我们还原一份代码工作区。后面讲失败复现时，这个区别还会用到。

到这里，第一层能力已经验证了：会话可以保存，也可以跨进程续接。接下来，我们把中断放到任务执行过程中，看看恢复对话之后，还缺什么。

## 二、能继续对话，不等于能恢复现场

先回答一个大家常问的问题：“既然历史消息还在，直接让 Agent 继续，不就行了吗？”

**如果中断前的记录已经完整保存，工作区没有变化，也没有结果不明的操作，确实可以继续。**问题在于，真实中断未必发生在这样整齐的边界上。

### 2\.1 为什么存档和实际代码可能对不上

回到登录模块的修复任务。按照原示例中 `runtime.ts` 的实现，应用补丁时先修改文件，再更新内存中的版本计数：

```TypeScript
await writeFile(filePath, content.replace(search, replace), "utf8");
this.revisionSequence += 1;
```

工具返回后，业务运行层才会在轮次边界保存下一份 Checkpoint。注意，这是课堂项目选择的保存时机，不是所有 pi 应用都必须采用的规则。

```Plaintext
上次存档：代码 r0，patch 尚未完成
    ↓
补丁已经写进 session-policy.ts
    ↓
进程突然退出，新的版本和执行结果还没存下来
```

这两次写入之间存在一个空当：补丁已经写进 `session-policy.ts`，但新的执行结果和版本信息还没保存，进程就退出了。



恢复时会看到两个不同的事实：磁盘上是修改后的代码，存档里却仍然记录着“补丁尚未完成”。如果直接按旧进度继续，Agent 可能重复打补丁，也可能拿旧测试结果判断新代码。



所以这里要记住：**“存档里没有成功记录”，不等于“动作没有发生”。**恢复不能只读进度，还要核对真实现场。



### 2\.2 做一次中途打断，观察恢复行为

【演示 3】先用一个容易观察的多步任务做实验：

```Plaintext
pi --session-dir ./demo-sessions "逐个读取 src/ 目录下的每个文件，统计总行数，把结果写入 report.md。"
```

等它读取了几个文件、尚未生成报告时，触发中断。课堂上可以尝试 Ctrl\-C，并确认当前模式下任务是否已经停止；按键行为与运行模式有关，验收时要看实际进程和工具状态。

然后重新启动，续接会话：

```Plaintext
pi --session-dir ./demo-sessions -c "继续。"
```

这次重点观察：它有没有重复读取已经读过的文件？有没有遗漏尚未处理的文件？报告是否覆盖了全部目标？



模型可能根据历史消息接着做，也可能重新读取部分文件。**重复读取并不是每次都会发生；即使这一次没有重复，也不能据此认定业务恢复已经可靠。**我们需要的是明确保存的步骤进度和可检查的恢复规则，而不是依赖模型临场推断。



### 2\.3 中断信号能停下什么

前面看到了中断后的现象，再看 pi 如何响应停止请求。



这里主要理解 `AbortSignal`：它把“本次执行需要停止”的信号传给模型调用、循环和工具。相关组件在能够响应的位置检查信号，并结束自己的工作。

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZjM5ZjBlZTcyZGFlNTcwZDlkMDFjZGQxM2JhZjZjY2NfMDc0N2NlODJkNmViMDNiZDM4MTViOGEwZDVmN2Q1ZGJfSUQ6NzY4NTc4NTUyMzE5Mjk5MDkyM18xNzg5NjE0MTc5OjE3ODk3MDA1NzlfVjM)

有三点需要分清：

- **同一个信号一旦中止，就不能恢复为未中止。**启动下一次执行时，需要使用新的信号。

- **停止能否及时生效，取决于执行环节是否支持取消。**把信号传给工具，还需要工具内部配合处理。

- **停止过程需要妥善收尾消息和工具结果。**框架会在相应路径中记录中止或错误结果，但突然断电、强制杀进程时，不能保证这些收尾都已完成。

尤其要注意：**中断不是回滚。**已经写入的文件不会因为发出中断信号就自动恢复，已经启动的子进程也需要明确的终止或隔离策略。

因此，除了会话历史，业务层至少还需要保存或关联四类信息：

|信息|恢复时用来判断什么|
|---|---|
|计划与步骤进度|哪些步骤已经完成，下一步准备做什么|
|工具执行记录与证据|动作是否成功，测试结果是否完整可信|
|工作区标识与代码版本、摘要|现在的代码是否与保存时一致|
|待审批动作与人工决定|哪些动作仍在等待确认，已有批准是否还适用|

保存工作区标识和摘要，不等于把整个工作区备份下来。前者用于核对现场；如果还需要回到旧代码，就要另外准备 Git 提交、快照或独立工作区。



到这里，缺口就明确了：**先核对上次留下的状态，确认可以继续，再让模型进入下一轮。**下面进入第二层，看看这些逻辑该接在哪里。



### 2\.4 通过哪些接口接入业务流程

我们已经有 pi 的循环、模型调用和工具执行机制，接下要做的是找到合适的接口，把业务判断接进去。



这里分四类能力来看：工具执行前的拦截、工具执行后的处理、事件订阅，以及恢复后的续跑。它们并不全是 Hook，但都能为业务层提供接入位置。

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=MDBjMGExNzYxNDJiMWZkZjFmOWY4ODVhY2YxNTljMzFfMGE1ZjYxYzdlYWZiNmU5YjhlYWM1NWUyN2Y5Yjg4MzRfSUQ6NzY4NTc4NjYyMDg1MDkzMjkzNF8xNzg5NjE0MTc5OjE3ODk3MDA1NzlfVjM)

**第一，****`beforeToolCall`****：在执行前决定是否放行。**

下面保留一个最小示例，演示如何拦截 `bash` 工具。`systemPrompt`、`model` 等变量沿用已有 Agent 的配置：

```JavaScript
const agent = new Agent({
  initialState: {
    systemPrompt,
    model,
    tools,
    messages,
  },
  // 参数校验之后、真正执行之前被调用；返回 block 就不放行
  beforeToolCall: async ({ toolCall, args, context }) => {
    if (toolCall.name === "bash") {
      return { block: true, reason: "bash is disabled" };
    }
  },
});
```

这个例子来自 pi 官方 README。它在参数校验之后、工具真正执行之前触发。返回 `{ block: true }`，这次工具调用就不会执行，模型会收到相应的错误结果。



如果你需要实现“停下来等审批”的功能，业务层还需要保存待确认动作、设置 `waiting_approval`，并通过运行控制结束本次执行。在等待期间，其他需要审批的写操作也必须继续被拦住。拦截一次工具调用，不能替代完整的审批流程。



这也帮助我们区分两种人工介入方式：

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZWRmYTMwZjU2ZjMwNGE3MmU3Mjc2MmNmZTExNzA5NGRfMDYxNGVhNWFmODkzMjBiZmM4MDFkNWI5NDdjMWUyNDFfSUQ6NzY4NTc4NzY3OTI1ODA1MzgxOV8xNzg5NjE0MTc5OjE3ODk3MDA1NzlfVjM)

> “插话”（steering）在这里不是日常聊天里打断别人说话，而是指：Agent 还在跑的时候，你又给它发了一条新消息。这条消息不会立刻中止当前动作，而是被收集起来，等下一轮模型调用之前，作为一条 `user` 消息注入上下文，让 Agent 在下一轮“顺势转向”。
> 
> 



|方式|使用场景|需要注意什么|
|---|---|---|
|运行中插话（steering）|Agent 正在执行，希望补充要求或调整方向|消息在循环的接收位置进入上下文，不保证立即停止正在运行的动作|
|暂停等待审批|某个动作执行前必须得到人的批准|业务层保存具体动作并停止推进；批准后重新校验，再恢复执行|



所以，“先别改那个文件”这样的插话可以用于协作，但关键写操作的审批必须落到执行前的确定性规则上。



**第二，****`afterToolCall`****：根据执行结果补充记录。**

这个钩子会收到工具调用、执行结果、错误标志和上下文。我们可以在这里补充审计信息、整理证据，并据此更新步骤记录。

它也支持返回 `terminate` 提示。不过，pi 会检查整个工具批次：该批次所有最终结果都设置了这个提示，才按此机制提前结束。因此，多工具场景下不能把单次返回 `terminate: true` 理解为“整个任务立即停止”。



**第三，事件订阅：把执行过程转成业务状态。**

`agent_start`、`turn_start`、`tool_execution_start`、`tool_execution_end`、`agent_end` 等事件，告诉我们框架运行到了哪里。业务层再把这些事件关联到具体任务和计划步骤。



例如，测试工具开始执行，可以记录为 `waiting_tool`；工具返回后，再根据结果决定下一步。收到 `agent_end` 只说明这次循环结束，并不自动意味着业务任务完成。



**第四，续跑接口：在恢复检查通过后继续调用模型。**

`runAgentLoopContinue` 或 `agent.continue()` 提供的是继续执行的机制。使用前，需要先还原计划、证据、审批状态和运行计数，并完成工作区校验。

这四类能力连起来，分工就清楚了：**pi 提供执行机制，业务层定义使用这些机制的规则。**例如，上一节课堂项目的轮数上限、完成条件，本节的审批条件和恢复规则，都需要接入自己的任务流程。



## 三、业务层需要补齐哪三样东西

接入位置找到了，接下来就要明确：这些接口背后，究竟维护什么数据？

本节集中补齐三样东西：**任务状态机、步骤执行记录，以及业务 Checkpoint。**pi 已有会话和运行相关能力，我们要在此基础上补上当前修复任务的业务含义。

### 3\.1 任务状态机：记录现在到哪了，规定接下来能做什么

前面我们说，恢复任务之前，要先知道任务停在什么地方。那么，程序怎么记住这件事？

最直接的办法，就是给任务加一个 `status` 字段。

比如，Agent 准备修改登录模块，但还没有得到你的批准，我们就记录：

`status = "waiting_approval"`

意思很简单：**这个任务正在等人确认，现在不能执行需要批准的修改。**

你可以把它理解成订单状态。订单有“待付款”“待发货”“已完成”，任务也有“正在执行”“等待工具”“等待审批”“已完成”。

但只有一个状态字段，还不算把状态机设计完整。还要规定：**发生什么事情之后，状态才能改变。**就像订单不能还没付款，就直接进入“待发货”。

我们先沿着修复登录问题的过程走一遍，再看完整的状态表。

**第一步，收到任务。**

用户说：“帮我修复会话过期的问题。”

这时任务刚创建，还没有开始处理，记为 `created`。

Agent 开始拆解任务，准备先定位代码、再复现问题、最后修改和验证，我们把状态改成 `planning`。

计划准备好了，开始分析和执行，进入 `running`。

**第二步，调用工具，等待结果。**

Agent 决定运行测试。测试命令已经发出去，但结果还没回来，这时记为 `waiting_tool`。

为什么要单独记一个“等待工具”？

因为“正在分析下一步”和“正在等测试结束”是两种不同情况。用户问进度时，系统应该能明确回答：“测试还在运行”，而不是一直显示“处理中”。

工具返回了结果，Agent 可以继续分析，就回到 `running`。

**第三步，准备改代码，先等人批准。**

Agent 找到了问题，生成了一份补丁。但我们规定，修改源码之前必须经过人工确认。

这时，任务进入 `waiting_approval`，同时保存待确认的具体补丁。

用户批准后，程序检查这份批准是否仍然适用，通过后再回到 `running`，继续执行。

这里的关键是：\*\*等待审批期间，程序必须拦住未获批准的修改。\*\*如果只是把页面上的文字改成“等待审批”，工具却照常执行，那这个状态就没有起到控制作用。

**第四步，验证通过，结束任务。**

代码修改完成，还不能立刻记为 `completed`。

还要检查：要求的测试是否通过？修复报告是否生成？约定的交付条件是否满足？

这些条件都满足了，程序才把任务记为 `completed`。

走完这个过程，状态机的含义就清楚了：

**状态说明“现在是什么情况”，迁移规则说明“发生什么事以后，允许进入下一种情况”。**

本例使用下面九个状态。大家先理解含义，不需要背英文名称：

|状态|放到修代码的过程里理解|
|---|---|
|`created`|收到修复任务，还没开始处理|
|`planning`|正在建立或整理计划|
|`running`|正在分析结果、决定下一步|
|`waiting_tool`|已发起工具调用，正在等待结果|
|`tool_failed`|某次工具调用失败，需要判断如何处理|
|`waiting_approval`|某个动作尚未获批，等待人工决定|
|`completed`|修复和约定的验证均已完成|
|`failed`|本次任务无法继续，未完成交付|
|`cancelled`|用户决定结束本次任务|

这九个状态不是必须依次走完的九个步骤。比如，不需要审批的任务，就不会进入 `waiting_approval`；一个任务里调用多次工具，也会多次进入和离开 `waiting_tool`。



接下来，有两个容易混淆的地方。

**第一个：工具失败，是不是整个任务就失败了？**

不一定。

比如读取文件时路径写错了，工具返回“文件不存在”。这次工具调用失败，可以先记为 `tool_failed`。

但 Agent 还可以搜索正确路径，再读一次。只要允许继续处理，就可以回到 `running`。只有达到停止条件，例如重试预算耗尽、缺少必要权限且无法解决，才把整个任务记为 `failed`。

还要区分“测试工具执行成功”和“测试通过”。测试命令正常运行，拿到了失败日志，说明我们成功获得了测试结果，但代码仍然有问题。不能因为工具返回了，就宣布任务完成。



**第二个：暂停了，是不是应该记为 ****`cancelled`****？**

也不是。

暂停表示“这次先停，之后还要继续”；取消表示“这个任务不做了”。

本例把这两件事分开记录：

- 任务状态记录中断前处于什么阶段，例如 `running`。

- 停止原因记录这次为什么停下来，例如 `INTERRUPTED`。

所以，看到“任务状态：running，停止原因：INTERRUPTED”时，应该理解为：**任务在执行阶段被打断，目前没有继续运行，但任务还没有结束。**



恢复时，也不是看到 `running` 就立刻调用模型。仍然要先检查存档、工作区和未完成的动作，确认可以继续，才恢复执行。



最后，谁来修改这些状态？

**由程序根据实际事件和业务规则修改。**工具开始执行、工具返回结果、用户批准、验收通过，都是更新状态的依据。模型可以提出下一步建议，但不能仅凭一句“我完成了”，就把任务改成 `completed`。

学到这里，大家能回答三个问题就够了：任务现在是什么状态？什么事件允许它改变状态？处于这个状态时，哪些动作不能执行？

不过，任务状态只能告诉我们“正在等工具”或者“正在等审批”，还不能说明具体是哪一步、哪个工具、哪份补丁。接下来，我们就用步骤执行记录，把这些细节补齐。



### 3\.2 步骤执行记录：哪些工作已经做过

上一小节，我们用任务状态说明了 Agent 当前处于什么阶段。

但如果页面上只显示“正在执行”，你可能还想问：问题找到了吗？代码改了吗？测试跑过了吗？



这些问题，就需要通过步骤执行记录来回答。

**任务状态告诉我们“现在处于什么情况”，步骤执行记录告诉我们“具体做过什么，结果怎么样，还差什么”。**



继续用登录模块的修复任务来看。假设上一节的 Planner 已经把任务分成四步：

这张表已经比一句“正在执行”清楚多了。

但是，只记录“修改代码进行中”，仍然不够。假如这时进程退出，下次启动后，我们还是不知道：补丁已经写进文件了吗？还是刚生成补丁，尚未执行？

所以，每个步骤下面，还需要记录具体的执行过程。我们顺着“修改代码”这一步走一遍。



**第一，记录准备做什么。**

Agent 决定调用 `apply_patch` 修改 `src/auth/session-policy.ts`。

这时要记下：它属于哪个计划步骤、调用哪个工具、传入什么参数。对于补丁工具，参数里就包括目标文件、要查找的内容和替换后的内容。



为什么要保留具体参数？

因为“修改会话判断”只是一个意图，具体补丁才说明它到底准备改什么。后面无论审批、排障还是恢复，都要查看这份具体内容。

同时，每次工具调用还要有自己的调用 ID，也就是 `toolCallId`。你可以把它理解成这次操作的流水号，用来把这次请求和对应结果连起来，避免多次调用之间张冠李戴。



**第二，记录实际发生了什么。**

工具执行后，要保存返回结果。

比如，这次补丁没有应用成功，工具返回：“找不到需要替换的原文。”

我们就要保留这次失败，包括对应参数和失败原因。不能因为后面又试成功了，就把前面的失败记录覆盖掉。



这样，回头排查时才能看清楚：它最初为什么没改成，后来又做了什么调整。



这里还要分清两种情况：

- 工具明确返回“补丁未应用”，这是已知的失败结果。

- 工具发起后进程就退出，没有拿到结果，这是结果不明。

\*\*没有收到结果，不能直接写成“执行失败，所以可以重试”。\*\*文件可能已经改了，只是成功结果还没来得及保存。遇到这种情况，恢复时必须先核对实际文件。



**第三，记录失败后准备怎么办。**

假设工具明确返回了“找不到原文”，Agent 决定先重新读取文件，再生成补丁。

这就需要记录下一步决策：“读取最新内容，确认修改位置，再提交新补丁。”

为什么连下一步也要记？

因为只留一句“补丁失败”，下次恢复时还要重新分析。把已经形成的处理决定保存下来，才能知道原任务准备往哪个方向继续。

不过，这仍然是待执行的决定。恢复时如果文件又变了，就要重新检查，不能不看现场直接照做。



**第四，记录后续尝试与最终结果。**

读完最新文件后，Agent 提交了新的补丁，这次成功了。

我们应该能够从记录中看到：第一次提交为什么失败，随后读取了哪个文件，第二次补丁改了什么，最终是否应用成功。

本例中，同一组工具和参数再次执行，可以记为原动作的重试；修改了参数，则记录为一次新的处理尝试，并关联前一次失败。



名称怎么定义可以根据项目约定，但有一条要守住：**换参数、换工具，都不能把前面的失败次数和已经消耗的预算清零。**



看完这个例子，再看需要记录的信息，就容易理解了：

这里的“完成证据”尤其重要。

比如，补丁工具返回成功，可以作为“修改代码”这一步的依据。但“执行验证”这一步，还需要相应的测试命令、退出结果和测试日志。

**补丁成功，只能说明修改已经应用，不能证明问题已经修好。**每一步都要有自己的完成条件。

还有一个容易混淆的地方：一个步骤，不一定只调用一次工具。

“定位问题”这一步，可能先搜索代码，再读几个文件，最后运行一次测试。它们都是同一步下面的不同执行记录。



所以，我们实际维护的是两层信息：上面是计划步骤和进度，下面是这个步骤中发生的多次工具调用。恢复时，既能看整体还差哪一步，也能查到某次具体操作的结果。

等所有必要步骤完成，再根据整个任务的验收条件，记录任务最终结果：完成、失败或者取消，并附上原因和摘要。这个结论属于整个任务，不需要在每条工具记录里重复保存。本例进入终态后保留原结论；需要重新做，就建立新的运行记录。



学到这里，大家可以用一个问题检查设计是否够用：

**假设换一个人接手，只看这些记录，他能不能知道已经做过什么、哪里出了问题、哪些结果还不确定，以及下一步准备做什么？**



如果还需要翻聊天记录猜测，就说明执行记录还缺少关键信息。



现在，我们已经能把任务进度描述清楚了。但这些记录如果只放在内存里，进程一退出，还是会丢。下一小节，我们就用 Checkpoint 把恢复需要的信息保存下来，让新进程也能接着处理。



### 3\.3 Checkpoint：把恢复所需的信息保存下来

前面两小节，我们已经能说清楚：任务处于什么状态，哪些步骤做过了，每次操作有什么结果。

但还有一个问题：**这些信息如果只保存在内存里，进程一退出，就会丢失。**

比如，Agent 已经找到登录模块的问题，准备修改代码。这时你关掉终端，再次启动程序，之前的计划、步骤进度和执行记录，怎么找回来？

这就需要 Checkpoint，也就是检查点。

你可以把它理解成一份任务存档：**把当前进度和恢复时需要的依据保存下来，让下一个进程知道从哪里接着处理。**

不过，读到存档只是第一步。能不能继续，还要检查存档描述的情况与实际现场是否一致。我们分开看。

**第一，存档里到底要保存什么？**

继续用修复登录问题的例子。

假设任务已经完成诊断，生成了补丁，正在等待人工批准。这时，一份可用于恢复的存档，至少要能回答下面这些问题：

这些数据不一定全部塞进同一个文件。比如，会话记录已经由现有存储保存，Checkpoint 可以记录对应引用。但要保证恢复时能找到，而且引用的记录与这份存档对应得上。

这里尤其要理解为什么保存工作区信息。

假设存档里说“诊断完成，可以应用补丁”，但中断期间有人修改了 `session-policy.ts`。那么，之前生成的补丁和审批决定，可能已经不适用了。

所以，保存工作区位置和文件摘要，是为了让程序检查：**现在要操作的代码，还是保存进度时的那份代码吗？**

文件摘要可以简单理解成根据文件内容计算出的“指纹”，用于判断内容是否变化。但保存指纹不等于备份文件；如果希望恢复旧代码，还需要另外准备 Git 提交或工作区快照。

**第二，什么时候保存？**

最容易想到的是：“等程序退出时，保存一次。”

但如果进程突然崩溃，就没有机会执行退出前的保存。所以，正常运行过程中也要定期留下可用的存档。

本例主要在完整轮次结束后保存；准备停下来等待审批时，也要先把待确认动作和任务状态保存好。

这样，即使后面中断，至少还能找到最近一次成功保存的进度。

这里的取舍是：保存得越频繁，通常能保留越新的进度，但也增加了写入和一致性处理的工作。本节先采用明确的保存边界，不追求任意时刻中断都能原样接上。

尤其要注意：**修改代码和保存 Checkpoint，是两次操作。**

补丁可能已经写进文件，但新的存档还没保存，进程就退出了。因此，即使有 Checkpoint，也不能保证存档永远与实际代码同步。这个空当，需要在恢复时检查。

**第三，怎样避免写出半份存档？**

假如直接覆盖正式存档，写到一半程序退出，原来那份有效记录也可能被破坏。

本例采用的办法是：先把新内容写到临时文件，写完后，再用临时文件替换正式文件。

你可以把它理解成：先准备好新存档，再让它接替旧存档，减少正式文件只写了一半的风险。

同时，存档里还要带上两个信息：

- **格式版本**：说明这份存档使用哪种数据结构，当前程序是否支持读取。

- **校验和**：用于检查存档内容是否损坏。

这两个信息与代码版本不是一回事。代码版本描述工作区里的代码，格式版本描述存档本身的结构。

保存和校验还要遵守同一套数据表示规则。例如，没有值的可选字段，统一省略或统一写成 `null`，不要两边采用不同方式，否则同一份业务数据也可能算出不同的校验结果。

如果新存档保存失败，本例应停止继续推进任务，报告原因，并保留最近一份有效存档。不能一边提示保存失败，一边继续修改代码，让实际进度与存档越差越远。

**第四，读到存档后，能不能马上继续？**

还不能。现在进入恢复流程。

假设我们读到的记录是：“诊断完成，补丁待执行，代码版本为 r0。”

接下来要依次做五件事。

**第一步，检查存档能不能用。**

文件能否正常读取？格式是否支持？关键字段是否齐全？校验是否通过？

这一步不通过，就明确报错，不能拿着不完整的数据启动任务。

**第二步，检查工作区对不对。**

目标目录还在吗？相关文件有没有变化？上次是否留下了结果不明的操作？

如果存档说补丁尚未执行，但文件内容已经变化，就先停下来核查。不能直接认定“没成功记录，所以再执行一次”。

同样，如果存档只记录了测试已经启动，没有完整结果，也不能把测试记为通过。要先确认旧执行的情况，再决定是否重新运行。

**第三步，检查任务是否允许继续。**

已经完成或取消的任务，本例不再续跑。正在等待审批的任务，也不能因为重启就绕过审批。

运行计数和剩余预算同样需要保留。前面已经用掉的轮数和重试次数，不能在恢复时清零。

**第四步，把业务对象还原回来。**

检查通过后，把计划、步骤记录、执行证据、审批信息和运行计数重新加载到程序中。

到这里，业务层才知道：之前发生了什么，哪些进度可信，现在允许做什么。

**第五步，再让 pi 继续执行。**

准备好有效的对话上下文后，才调用 pi 的续跑能力，让模型决定下一步。

所以，整个顺序就是：**先读存档，再核对现场，确认允许继续，还原业务状态，最后启动模型。**

这里的恢复，也不是把程序搬回上次暂停的那一行代码。我们启动的是一个新进程，它根据保存的信息重新判断下一步；上一次测试命令的调用栈或子进程，并不会自动恢复。



最后，我们用这个课堂场景检查一下。

Agent 诊断完成、补丁待审批时退出。重新启动后，系统应该找回诊断证据和具体补丁，确认工作区没有变化，并继续等待批准。它既不需要重新建立整份计划，也不能直接开始修改文件。

如果工作区变了，就说明恢复条件发生变化，应先核查，而不是照着旧记录继续执行。

**Checkpoint 的作用，是为恢复提供依据。真正决定能否继续的，是存档检查、现场核对和业务规则。**

到这里，任务状态、步骤记录和 Checkpoint 就连起来了：状态说明当前阶段，步骤记录说明执行过程，Checkpoint 让这些信息在进程退出后仍然可用。

接下来，我们就把这些要求写成最小规格，接回已有的 Coding Agent，并用中断、审批和异常场景验证它是否真的做到了。



## 四、怎样用最小规格指导开发和验收

前面，我们已经讲清楚三件事：任务状态怎么描述，执行过程怎么记录，恢复所需的信息怎么保存。

接下来就要把这些能力加到上一节的 Coding Agent 上。



但如果直接告诉 AI：“帮我加上状态机、Checkpoint 和人工审批”，它可能很快写出一套代码，你却很难判断这套代码是不是符合要求。

比如，它确实保存了文件，但恢复时清空了重试次数；它确实显示“等待审批”，但补丁已经提前执行了；它确实重新启动了任务，但之前的诊断又全部做了一遍。

所以，开始开发之前，我们先写清楚：**什么情况下，系统应该做什么；什么情况下，必须停下来。**

这就是本节所说的“最小规格”。



### 4\.1 最小规格，要写清楚到什么程度

大家可以把规格理解成开发前约定好的行为要求。

比如，“支持断点续跑”还不够具体。我们把它改成：

> 诊断完成并成功保存后，退出进程。再次恢复时，应保留原计划、诊断结果和证据，从后续步骤继续。
> 
> 

这样，AI 知道要实现什么，我们也知道应该怎么检查。



再比如，“支持人工审批”也不够具体，可以改成：

> 修改源码前，保存具体补丁并等待批准。批准前不能执行，拒绝后不能执行；批准后，如果补丁或相关文件发生变化，需要重新检查授权。
> 
> 

这里没有要求写多少份文档，也没有规定必须设计多少个类。我们只是把容易产生歧义的地方提前说清楚。

**“最小”的意思是只保留影响实现和验收的要求，但关键边界不能省略。**



对本节来说，最重要的就是五件事：进度不能丢，存档要可信，恢复先检查，审批要有效，失败后能排查。

在交给 AI 之前，还要明确哪些能力已经有了，避免它重新实现。

|能力|实现方式|
|---|---|
|模型调用、工具执行、消息回写、事件流|复用 pi 的现有能力|
|对话续接、中断信号、工具前后 Hook|通过 pi 提供的接口接入|
|会话记录持久化|项目已经使用 `Session` / `JsonlSessionRepo` 时继续复用，先核对当前接入方式|
|计划与步骤规则、修复和测试工具|沿用 3\.2 的项目实现|
|任务状态与步骤执行记录|补充业务规则，关联 pi 事件和工具调用|
|业务 Checkpoint 与恢复装配|补充业务数据的保存、校验与还原|
|人工接管与失败排查|补充审批规则、待确认动作、独立重跑和结果对照|

这张表的用途，是告诉 AI：先理解现有项目，再做增量修改。



### 4\.2 怎样把要求交给 AI

现在，我们把前面的内容整理成一份可以直接用于开发的提示词。

它按照四步组织：先读项目，再明确要求，然后列修改计划，最后运行验收。

```Plaintext
任务：在上一节的 Coding Agent 上，补齐任务状态、Checkpoint 和人工接管。  
课堂案例： 修复登录模块的会话过期边界问题， 完成验证后输出 artifacts/login-fix.md。

一、先检查现有项目
  阅读已有的计划、工具、运行入口、会话存储、测试，
  以及项目实际使用的 pi 版本和相关接口。
  列出： 
  1. 已经具备哪些能力。 
  2. 还缺哪些业务逻辑。 
  3. 哪些能力当前不支持，需要说明限制。  
  
  继续复用现有模型接入、pi 的 Loop、工具执行、消息回写、
  中断信号、事件流和已有会话存储。 
  沿用上一节的 Planner、修复工具和测试工具。 
  不要仅凭接口名称推断行为，要核对实际实现。
  
二、按以下最小规格实现  

    R1：任务和步骤记录 
    根据实际执行事件更新任务状态。 
    保存计划进度、工具调用 ID、输入输出、失败原因、 
    重试记录、下一步决策和完成证据。 
    暂停和等待审批不算任务失败。 
    工具返回成功，不等于测试通过或整个任务完成。 
    本例中，已完成、失败或取消的运行不再续跑。  
    
    R2：保存恢复所需的信息 
    保存任务、计划、步骤记录、证据、会话引用或历史、 
    工作区标识、代码版本与摘要、运行计数、 
    待审批动作和人工决定。  
    默认在完整轮次结束后保存； 
    进入等待审批前，保存待确认动作和状态。 
    明确存档格式和校验规则。 
    保存失败时停止推进，保留最近一份有效存档并报告原因。  
    
    R3：先检查，再恢复 先校验存档、工作区和任务状态，再还原业务对象， 
    最后调用 pi 的续跑能力。  
    区分上次动作是已完成、未开始，还是结果不明。 
    结果不明的写操作不得自动重放。 
    无法安全确认时，输出核查信息并停止自动推进。  
    没有完整测试结果，不能把验证步骤记为完成。 
    恢复时保留已有轮数、重试次数和预算消耗。  
    
    R4：人工审批 修改源码前保存具体补丁，进入等待审批状态。 
    批准前不能执行，拒绝后不能执行。 
    等待期间，其他需要审批的写操作也不能绕过检查。  
    批准只适用于对应动作。 
    补丁参数或相关文件内容变化后，重新检查授权。 
    不能因为进程重启，就默认获得批准。  
    
    R5：失败排查 
    允许用原任务输入，在对应初始代码的独立工作区重新执行。 
    保留原运行记录，另存新运行的日志、修改和测试结果。 
    不默认继承危险操作权限。 
    不承诺模型会选择相同路径，也不承诺原错误一定再次出现。  
    
    本次不实现： 
    进程内存或调用栈快照、原测试子进程恢复、 
    任意时刻崩溃后的无损恢复，以及副作用恰好执行一次。 
    不扩展上下文自动压缩和 Sandbox。 
    不额外引入事务或调度框架。

三、列出修改计划，再实现  
    把 R1—R5 对应到现有文件、缺失逻辑和验收场景。 
    按最小增量修改，不重写已有框架能力。  
    
    先准备关键失败场景，再实现对应行为。 
    不能通过清空记录、重置预算或把状态改成成功来绕过问题。 
    对影响业务行为的歧义，先说明取舍。

四、按以下场景验收  
    A1：诊断完成并成功保存后退出进程。 
    恢复后保留计划、诊断与证据，从后续步骤继续。  
    
    A2：补丁已经写入，但下一份存档尚未保存时异常退出。 
    恢复时检测差异或结果不明，阻止重复写入，输出核查信息。  
    
    A3：测试已经启动，但没有完整结果时中断。 
    恢复后不记为通过。 先确认旧执行已结束或被隔离，再决定是否重新测试。  
    
    A4：补丁等待审批。 
    分别验证批准与拒绝： 批准前及拒绝后均不执行，批准后才执行对应补丁。  
    
    A5：批准后，补丁参数或相关文件发生变化。 
    再次执行时，旧授权不能直接放行。  
    
    A6：存档损坏、工作区缺失或任务已经终结。 
    恢复请求被明确拒绝，不启动模型或写工具。  
    
    A7：多次工具失败后暂停。 
    恢复后保留失败记录、运行计数和预算消耗。  
    
    A8：原任务存在失败记录。 
    在独立工作区重跑后，原记录保持不变， 
    能够对照两次运行的日志、修改和测试结果。  
    
    需求与验收对应： 
    R1 → A1、A7 
    R2 → A1、A2、A6 
    R3 → A1、A2、A3、A6、A7 
    R4 → A4、A5 
    R5 → A8

交付： 
最小规格、需求与改动及验证的对应表、 
最小代码改动，以及实际运行证据。  
分别标明“已实现”“已验证”“未覆盖”。 
异常退出实验只在临时工作区进行。 
不能只凭编译通过或模型声称完成，就宣布验收通过。
```

这份提示词里，R 表示需求，A 表示验收场景。编号只是为了方便对应，不需要记住这些字母。

比如，R4 要求“批准前不能执行”，A4 就安排一次实际审批实验，检查文件有没有提前被修改。

这样，开发和验收就连起来了：要求写在哪里，代码改在哪里，用哪个场景证明，都能找到对应关系。

### 4\.2 场景一：中断之后，能不能接上原来的进度

代码补齐后，先验证最基本的恢复能力。

本例把补齐这些能力的课堂项目称为 State Agent。下面沿用原稿中的运行摘录，重点看怎样判断结果；其中的轮数、序号和调用次数，不要求每次运行完全相同。

另外，`--pause-after`、`--auto-approve`、`--resume` 等参数属于课堂项目入口，不能直接当作 pi CLI 参数使用。

先用 `--pause-after 6 --auto-approve` 运行。这里自动批准，是为了先单独观察中断恢复，后面再验证审批。

```JSON
npm start -- --workspace /tmp/state-agent-lab --run-id run-lab2 \
  --pause-after 6 --auto-approve "修复 demo-app 里会话到期边界判断的错误，补上回归测试并写交付说明"
```

暂停后的摘要如下：

```Plaintext

任务状态：running          ← 只是暂停，没有失败

  patch：pending，证据 0 条     ← 代码还没改

任务最终结果：未终结（可从存档继续）
```

这段输出说明：诊断已经完成，补丁还没执行，任务只是暂停，没有被判为失败。

接下来使用项目的恢复入口，观察输出：

```JSON

```

```Plaintext

#54 running -(task_completed)-> completed（COMPLETED）

```

这里首先要检查，恢复的是否还是原任务：任务标识、已有计划、诊断证据和运行计数有没有保留。

然后再看，后续修改和测试是否完成。原稿这次运行中，三个测试范围返回了 `exit=0`，并生成了修复报告。实际验收时，还要查看对应日志和报告，确认运行的是要求的测试。

**状态显示完成，只是一个结果入口；文件改动和验证记录，才是判断它是否完成的依据。**

还可以再做一次异常实验：在补丁写入之后、下一份存档保存之前退出。恢复时应当检测到差异并阻止自动重复写入。这验证的是 A2，不能用前面那次正常暂停代替。

原稿中的运行在修改源码前停了下来：

### 4\.4 场景三：失败以后，能不能留下可对照的证据

最后看失败排查。

假设上一次任务没有修好，我们希望重新执行，看看它会怎么处理。课堂项目中的 `--replay` 就用于组织这类重跑。

```Bash
WS=/tmp/agent-lab-4-4; rm -rf "$WS"; mkdir -p "$WS"
npx tsx scripts/child-run.ts --scenario ac4 --workspace "$WS" --run-id run-bad
npx tsx scripts/child-run.ts --scenario ac4 --workspace "$WS" --resume run-bad --reject
npx tsx scripts/child-run.ts --scenario ac4 --workspace "$WS" --replay run-bad
```

但重跑前，要先准备对应初始代码的独立工作区。如果上次的问题发生在修复之前，这次却拿已经修好的代码重跑，就很难比较。

这里也要区分：pi 的 `--fork` 派生的是会话，课堂项目的重跑还需要自己准备工作区和运行记录。

准备好以后，使用原任务输入重新执行，并保留两组信息：

这样，我们才能比较：两次读取了哪些文件，在哪一步出现差异，修改是否不同，测试结果为什么不同。



模型可能选择另一条处理路径。因此，新运行成功，不代表上次的错误一定能够再次出现；新运行失败，也需要查看具体证据，不能只凭最终状态判断原因。

这里验收的重点是：\*\*原记录没有被覆盖，新运行可以独立查看，两次结果能够对照。\*\*同时，重跑不能默认继承原来的危险操作权限。



到这里，我们就把最小规格用起来了：正常中断验证进度保留，人工审批验证执行控制，独立重跑验证排查依据；再用存档损坏、结果不明、授权变化等场景补齐边界。

写代码可以让 AI 帮忙，但哪些行为算正确、拿什么证据证明，需要工程师判断。接下来，我们再从底层设计看一遍：即使换一个框架，这些中断、恢复和人工接管规则，应该怎样落到执行流程里。

## 五、理解底层设计：换一个框架，哪些判断仍然适用

前面，我们已经把状态记录、Checkpoint 和人工审批接到了 pi 上，也知道应该怎样验收。

这时，大家可能会问：“如果以后项目换了框架，今天学的这些是不是又要重新学？”

**接口用法可能要重新熟悉，但判断系统是否可靠的方法，仍然适用。**

无论用什么框架，都要回答：停止时留下了什么？恢复时检查了什么？没有批准的动作会不会执行？任务完成有没有证据？

下面，我们暂时放下接口名称，从执行过程看这些问题。



### 5\.1 恢复任务，为什么要同时找回对话和业务状态

假设你接手一个做到一半的修复任务。同事给你一份聊天记录，里面说：“问题已经找到了，下一步准备改代码。”

你大概还会问：改哪个文件？补丁执行过没有？测试跑到哪了？这处修改批准了吗？

Agent 恢复时，也面临同样的问题。



它需要两类信息。

第一类是**模型继续思考需要的信息**：用户的目标、之前的分析、工具调用和结果。这些信息通过会话记录或摘要重新放回上下文，让模型知道前面发生过什么。

第二类是**程序决定是否允许继续的信息**：步骤进度、工作区版本、审批记录、剩余预算。这些信息需要有明确的数据和检查规则。



比如，聊天记录里出现“用户同意修改”，程序仍然要核对：批准的是哪份补丁？现在提交的参数有没有变化？

**模型需要知道之前发生了什么，程序需要确认现在可以做什么。**换一个框架，这两个要求仍然存在。



### 5\.2 中断和审批，应该放在执行过程的什么位置

再回到最基本的 Agent Loop。

模型提出工具调用，程序执行工具，把结果交回模型，模型再决定下一步。任务就在这个过程中逐步推进。

现在要增加中断、审批和存档，其实就是在合适的位置加入控制。



继续看修改登录代码的例子：

这里最值得检查的是先后顺序。



审批必须发生在写入之前。补丁已经写进文件，再弹出“是否同意修改”，就失去了审批的作用。

执行结果也必须来自实际运行。不能先把步骤标为完成，再等测试结果回来。

恢复检查同样要放在模型续跑之前。否则模型可能已经发起下一次修改，程序才发现工作区不一致。



因此，阅读一个新框架时，可以先找这些接入位置：**执行前在哪里检查，执行后在哪里记录，停止由谁控制，恢复由谁负责。**

找到了这些位置，再研究具体接口，就知道每个接口是用来解决什么问题的。



### 5\.3 为什么发出停止请求，不等于所有操作都停了

中断看起来像按一下按钮，但底层需要多个环节配合。

假设 Agent 正在运行测试，你点击“停止”。页面不再输出日志了，能不能说明测试已经结束？

不能。也可能只是页面停止等待，后台的测试进程还在运行。



因此，要区分三件事：

- 用户已经请求停止。

- Agent 不再发起新的操作。

- 已经启动的操作确实结束了。

这三件事可能先后发生，不能只完成第一件，就宣布全部停止。



在 JavaScript 中，一个常见做法是用 `Promise.race` 同时等待“操作完成”和“取消发生”。取消先发生时，调用方可以提前结束等待。

但这不会自动停止另一个 Promise 背后的操作。测试子进程可能还在运行，网络请求也可能还没结束。



所以，中断信号还需要传到具体执行环节，并由那个环节处理取消。不能立即取消的操作，要明确记录它的状态，必要时等待结束或进行隔离。

这里不要求大家自己实现一套取消机制，但要能检查：**程序是真的停止了操作，还是只停止了等待结果？**

这个区别会直接影响恢复。如果旧测试还在运行，新进程又启动一遍，就可能出现重复执行或资源冲突。

如果没有结果就记成“失败”，恢复代码可能自动重试；但第一次写入也许已经成功了。

因此，停止时要如实区分“确认失败”和“结果不明”。不能为了让流程看起来完整，随便补一个失败或成功状态。



对话记录也一样。工具调用与结果需要通过调用 ID 对应起来。已知结果要保存，缺失结果要按框架协议妥善处理，同时保留业务上的不确定性，不能伪造成功。

正常中断时，程序可以尽量完成这些收尾。但如果进程被强制结束，收尾逻辑可能根本没有机会运行。



这就是为什么恢复检查不能省略：**我们不能假设上一次总能停得完整，只能根据现有记录和实际现场，判断这一次是否可以继续。**



### 5\.5 工程师应该掌握到什么程度

讲到底层设计，大家不需要给自己增加一个目标：“必须脱离 AI，默写整套 Runtime。”

本节真正希望大家形成的能力，是看到一份实现，能够判断它有没有把关键问题处理好。

比如，AI 写完代码后，你能检查：

- 等待审批时，写工具是否真的被拦住。

- 点击停止后，正在执行的工具是否仍在运行。

- 恢复前，是否检查了工作区和结果不明的动作。

- 恢复后，失败记录和预算是否被保留。

- 标记完成时，是否有对应的测试和交付证据。

如果发现缺口，还能指出应当改在哪个环节，并设计一个场景验证修改是否有效，这就是本节要求的工程能力。

实现时，模型接入、流式处理、工具执行、会话管理等现有能力，继续复用网关和框架。我们重点补充当前业务的状态、审批、恢复和验收规则。

这也帮助大家理解 Harness 的价值：它把模型、工具、消息、会话和运行控制组织起来，为业务逻辑提供接入位置。具体框架已经提供哪些能力，需要检查；哪些规则适用于当前任务，则需要工程师决定。

回到登录修复任务，接口名称可以变化，但要求依然明确：批准前不能改，结果不明不能盲目重试，恢复前要核对现场，完成时要有证据。

能把这些要求落实到代码，并验证它们确实生效，今天学到的能力就能够带到下一个项目中。

## 本节小结

回到开头的场景：Coding Agent 修复登录问题，做到一半停下来，再次启动时，怎样才能接着做？这节课我们看清楚了，pi 的会话续接可以找回之前的对话，而恢复任务还需要业务层补充依据。**任务状态说明现在处于什么阶段，步骤记录说明做过什么、结果怎样，Checkpoint 把这些信息保存下来，供下次恢复时检查。**

这三部分接起来之后，还要守住几条规则：恢复前，先核对存档与实际工作区；没有完整结果的写操作，先确认是否已经发生；需要审批的修改，批准前不能执行，内容变化后还要重新检查授权。最终是否完成，也要看实际改动和验证结果。**有记录，才能判断；检查通过，才能继续。**
