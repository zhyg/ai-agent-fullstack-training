# 3\.1 从 Tool Agent 到 Agent Loop v7

## 序言

大家好，欢迎进入第三章。

经过第二章的铺垫，我们已经搭建起一套可用的工具基础设施：模型能够通过 Function Calling 发起 Tool Call，Tool Runtime 则负责查找工具、校验参数、判断权限、执行对应的 Handler，并将带有原始 `tool_call_id` 的 Tool Result 回写至模型。

不过，上一章的核心问题围绕的是：一次工具调用如何安全、可靠地执行？

到了第三章，我们要把目光投向另一个问题：一个需要搜索、阅读、修改、验证乃至纠错的复杂任务，如何持续地推进，直至完成或主动停止？

这正是本章将要介绍的核心机制 —— Agent Loop。

---

### 是什么业务场景，产生了 Loop？

Chatbot 时代，你问一句，模型答一句，一次调用就结束。没有“下一步”，也就没有循环需要管理。

到了 Agent 时代，模型可能自己连续运行几十步：搜索代码、读取文件、修改实现、运行测试、分析失败，再回到代码继续修改。每一步都依赖上一步的真实结果。你会发现，循环拉得越长，就越容易跑偏、重复、超预算，甚至执行不可逆的操作——因此，我们要对 Agent 施加控制。

控制的前提，是理解控制权发生了什么变化：

控制权从用户移交给了模型，人的工作方式也随之改变。

Peter Steinberger 的一句话把杠杆点说得很直接：

> “You shouldn't be prompting coding agents anymore\. You should be designing loops that prompt your agents\.”
> 
> 

Boris Cherny 的表达更进一步：

> “I don't prompt Claude anymore\. I write loops\.”
> 
> 

这两句话强调的不是“不再需要写提示词了”，而是人的关注点从“逐轮提示”转移到了“设计触发、反馈和验收系统”——杠杆点已经上移了一层。

当然，这种转移是叠加关系，不是替代关系。没有可靠的 Context，Loop 只会更快地误判；没有 Harness 约束，Loop 只会把一次风险放大成几十次风险。Loop 是在 Prompt、Context 和 Harness 之上增加了一个控制层，让系统有能力在连续决策中自我纠偏和收敛，而不是用循环去弥补底层质量的不足。

### LoopEngine 的职责

正因为如此，我们才需要 `LoopEngine` 来承接和约束这个连续的决策过程。它的职责很明确：

> LoopEngine 不负责替模型思考，它负责让模型的连续思考和行动能够启动、反馈、收敛并安全停止。
> 
> 

具体来说，它至少需要管理五件事：组装本轮 Context、调用模型、分发 Tool Call、回写 Tool Result，以及决定继续还是结束。其中，最大轮数、重复动作检测、取消信号和完成契约，都是“决定继续还是结束”这个环节下的具体控制机制。

```Plaintext

    P["Perceive<br/>读取消息与工具结果"] --> D["Decide<br/>模型推理并选择下一步"]
    D -->|"有 Tool Call"| A["Act<br/>分发工具调用"]
    A --> F["Feedback<br/>写回 Tool Result"]

    D -->|"无 Tool Call 或命中停止条件"| X["Finalize<br/>校验并结束"]
```

上图的四段并不是四个独立服务，而是一个 Run 内部不断重复的控制周期：

感知（Perceive）→ 决策（Decide）→ 动作（Act）→ 反馈（Feedback）→ 感知（Perceive）

如果切换到理论叙事的角度，也可以写成：

观察（Observe）→ 思考/规划（Think / Plan）→ 动作（Act）→ 观察（Observe）→ 收束（Finalize）

两种写法没有本质差异——前者更贴近运行时实现，后者更贴近 Agent 的任务行为。



### 什么样的任务适合自主 Loop？

真正适合自主 Loop 的任务，至少满足三个条件：

- 目标清晰：系统知道要交付什么，而不是用运行时长代替任务价值；

- 结果可验证：测试、评分、文件产物或结构化规则能够判断是否完成；

- 过程可收敛：每轮行动能够产生新证据，逐渐逼近目标。



两个真实案例更能说明“可收敛”是什么：

**案例一：规则转 Lint**——把近百条文字代码规范转成 Lint 规则。每轮先扫描仓库，再抽检命中样本；出现误报就调整规则或标记为暂不可实现，然后进入下一轮。停止条件不是“Agent 感觉差不多”，而是“连续三轮抽检零误报”。规则准确率能够随反馈逐轮提高，因此适合 Loop。

**案例二：CLI 迁移**——把 Bun \+ TypeScript CLI 迁移到 Go。迁移前先固定功能清单和验证命令，执行中让 Agent 逐项迁移、编译、运行测试；结束 Hook 检查清单，只要仍有未完成项就拒绝退出。这里真正让长任务跑起来的，不是一段超长 Prompt，而是明确清单、可执行验证和不满足条件时继续工作的机制。

反过来，“把产品做得更高级”“把 UI 做得更好看”都不是合格的自主 Loop 目标。它们需要人的产品语境和品味判断，应先进入开发者反馈循环，不能假装成一个可自动验收的布尔条件。



### Loop 的两层含义

在正式进入实现之前，还需要解释一下 Loop 的双重含义：

- **任务内循环**：指在一次 Agent Run 内部，模型依次进行“观察上下文 → 决定动作 → 执行工具 → 读取结果 → 再次决策”的反复迭代。例如，后面我们将介绍的 `pi` 中的 `runAgentLoop()` 就属于这一层次。

- **任务外循环**：指什么事件会触发一次 Agent Run；一次 Run 结束后，何时再次启动；由谁负责检查目标是否真正达成。例如，`/goal`、`/loop` 指令，以及定时任务和事件触发机制，均归属于这一层次。

本节我们将集中精力实现第一层（任务内循环），同时为第二层（任务外循环）预留停止、Follow\-up 和中断的扩展点（如回调接口或钩子函数）。之所以要明确区分这两层，是因为如果不加区分，很容易一上来就把定时任务、Sub\-agent、Worktree、Memory、Skills 和 Workflow 等全部塞进“Agent Loop”的概念里，结果概念上很啰嗦，代码却无法清晰地说明每一层到底在管理什么。只有先厘清层次，才能让实现有条不紊，也为后续扩展打下扎实的基础。

## 一、先看结果：第一版 Codebase Agent 能完成什么？

为了让你更直观地理解 Loop 在真实任务中如何运转，我们围绕一个具体的代码理解任务展开：

> “帮我找出该项目的登录逻辑，并生成 Markdown 说明文档。”
> 
> 

要求：

1. 找到登录入口；

2. 阅读路由、中间件、Service 和数据库访问代码；

3. 梳理主要调用链；

4. 在 `artifacts/login-flow.md` 中生成说明文档；

5. 最终列出引用过的相关文件路径。



代码理解任务虽然看起来简单，但已经足以完整呈现多轮执行的必要性。整体流程大致如下：

```Plaintext
用户目标
  ↓
list_files：先看项目结构
  ↓
search_code：搜索 login、auth、token 等符号
  ↓
read_file：读取路由
  ↓
read_file：沿调用关系读取 Service
  ↓
read_file：继续读取数据库与认证逻辑
  ↓
write_file：生成 Markdown 说明文档
  ↓
模型读取 Tool Result
  ↓
Final Answer
```

理想化的流程图是一回事，真实的运行轨迹更能说明问题。以这个任务为例，实际执行可能是这样的：

```Plaintext
[turn 1] list_files
         → 找到 src/routes、src/services、src/repositories

[turn 2] search_code
         → 命中 src/routes/login.ts、src/services/auth-service.ts

[turn 3] read_file
         → 路由调用 authService.login()

[turn 4] read_file
         → Service 查询用户并校验密码

[turn 5] search_code
         → 找到 userRepository.findByEmail()

[turn 6] read_file
         → Repository 访问 users 表

[turn 7] write_file
         → artifacts/login-flow.md 写入成功

[turn 8] Final Answer
         → 返回文档位置与相关源码路径
```

这八轮轨迹里，关键模式已经清晰可见：每一次下一步都依赖上一次的真实结果。

模型在第一轮并不知道登录文件叫什么，看到路由以后才知道 Service 名称，看到 Service 以后才知道 Repository 方法，读完证据以后才有资格生成说明文档。

每一步都是上一步的消费者，缺一轮都走不到最终答案。

所以先记住本节第一个核心结论：

**复杂任务需要 Loop，不是因为步骤多，而是因为下一步依赖上一步产生的新事实。**

## 二、Agent Loop 工作时需要从头写吗？

先给结论：不需要。

真实项目中，底层的 Agent 循环通常会复用 `pi`、`codex` 等成熟框架的基础能力。但现有框架不一定能直接适配所有业务场景——当需要与特定的技术栈（如 Java、Golang 等）或内部基础设施对接时，我们就需要在理解 Loop 原理的基础上，用目标语言重新实现一套模型流管理、Tool Call 解析、参数校验、Tool Result 组装和事件派发机制。

不过，在本节中，我们的目标不是“重写一个生产级 Loop”，而是学习怎样使用和约束这些能力。

我们将以 `pi` 的源码为例，带你理解内循环的设计思路——注意，目标是理解，不是背诵。真正掌握本节内容的标准分为三个层次：

|层次|掌握标准|
|---|---|
|能解释|说清 Tool Calling、Tool Runtime 与 Agent Loop 的区别|
|能接入|能使用 pi 把 Tool Result 写回下一轮，并接入第二章 Runtime|
|能验证|能证明最大轮数、完成条件、重复动作和取消确实生效|

这三个层次层层递进：先理解概念，再动手接入，最后用事实验证它没有失控。

说到底，本节不是要求你从零写出一个 Loop。如果 AI 帮你生成了相关代码，而你能清晰地解释执行顺序、审查边界条件、并用测试证明它不会跑偏或超预算——那你就已经达到了本节的目标。

## 三、区分概念

第二章已经讲过 Tool Call，这里继续复用即可。

|对象|负责回答的问题|示例|
|---|---|---|
|Function Calling|模型怎样表达下一步动作？|“调用 `search_code`，搜索 `auth`”|
|Tool Runtime|这一次动作能否执行，怎样执行？|校验路径、权限、超时并运行搜索|
|Agent Loop|Tool Result 回来以后怎么办？|把命中结果交给模型，继续读取文件|
|LoopGuard|整个 Run 还能不能继续？|最大轮数、重复动作、总时间|

一次工具调用的边界是：

```Plaintext
Tool Call
  → Tool Runtime
  → Tool Result
```

一个任务的执行边界是：

```Plaintext
当前 Context
  → LLM Decision
  → Tool Call
      → Tool Runtime
      → Tool Result
  → 更新 Context
  → 下一轮 LLM Decision
```



Loop 是在工具基础上增加了“连续执行”能力，不能因此丢掉第二章已经建立的参数校验、权限、超时、审计和结果治理。

## 四、读懂 pi 的 Agent Loop：真正的循环发生在哪里？

先给结论：pi 负责把“请求模型、执行工具、回写结果、继续请求”连起来。我们要掌握的是这条链怎样运行，以及在哪些位置加上业务判断。

还记得登录分析任务吗？如果每次工具执行完都要你输入“继续读这个文件”，那么下一步仍然由你推动。Agent Loop 接过的第一项工作，就是把刚刚获得的结果交回模型，让它自己决定下一步。

### 4\.1 pi 的最小循环可以怎样理解？

假设模型请求搜索 `login`，工具返回两个文件。如果程序只把搜索结果打印到终端，然后结束请求，模型并没有真正看到这些文件。它既不知道应该读哪个，也无法依据搜索结果修正判断。



所以一次工具执行后，消息历史必须同时保留模型提出的 Tool Call 和对应的 Tool Result。下一次模型请求带上这段历史，观察和行动才闭合起来。



把 `pi@0.83.0/packages/agent/src/agent-loop.ts` 压缩到只剩骨架，核心不到 20 行：

```TypeScript
async function runAgentLoop(context, config) {
  while (true) {
    const assistant = await streamAssistantResponse(context, config);
    context.messages.push(assistant);

    if (["error", "aborted"].includes(assistant.stopReason)) return;

    const calls = assistant.content.filter(x => x.type === "toolCall");
    if (calls.length === 0) return;

    const results = await executeToolCalls(calls, config);
    context.messages.push(...results);

    if (await config.shouldStopAfterTurn?.({ assistant, results })) return;
  }
}
```

这段代码中， Agent Loop 工作过程是：模型提出动作，运行时执行动作，结果回到消息历史，模型再基于新事实继续。所有 Agent 框架都绕不开这个骨架。

你会发现一个反直觉的事实：Agent Loop 的核心骨架极其简单，真正复杂的从来不是“循环”本身，而是长循环中积累的工程细节——流式消息、参数校验、Hook 链、取消信号、并发顺序。

换句话说，`while` 循环不值钱，值钱的是你在循环里放了多少层保护。



### 4\.2 既然骨架这么短，pi 多出来的代码在做什么？



最小循环解释了原理，真实运行还要接住用户输入、流式输出和工具异常。



比如 Agent 正在分析登录逻辑，你补充一句“这次只看移动端入口”。这属于 `steering`，pi 在当前轮次与工具处理结束后的安全边界接收它，影响后续决策。如果你说“分析完再补一份接口清单”，则适合排进 `followUp`：当前工具循环准备停止时，再接着处理。



这就是源码内外两层循环的用途：内层推进工具调用和方向调整，外层在自然停止前检查是否还有追加消息。它们都属于本次执行的消息处理机制，不能与前面讲的定时调度混为一谈。



流式响应也不是每来一个字就新增一条消息。pi 先放入 partial Assistant Message，随后用 text、thinking、toolcall 的增量持续更新，最后替换为完整响应。界面因此可以边生成边展示，而工具执行基于完成后的响应。



工具前后还有两个必须认识的位置：



|位置|pi 做什么|我们接什么规则|
|---|---|---|
|执行前 prepare|找工具、兼容参数、校验 Schema，再调用 `beforeToolCall`|Run 级重复保护；工具权限继续由 Runtime 判断|
|执行后 finalize|调用 `afterToolCall`，允许截断、脱敏或标记错误|从成功结果提取证据|



准备失败会形成错误 Tool Result。若请求提前终止，只有当前批次的所有工具结果都设置 `terminate: true`，才触发批次终止；即使并行执行，回写也按原 Tool Call 顺序组织。模型、Hook 和工具还会收到同一 `AbortSignal`，中断时才能沿整条执行链传播。





### 4\.3  一轮（turn）与一次任务怎样区分？

在 pi 中，一个 Turn 包含一次模型响应，以及它提出的零到多个工具调用；一个 Run 可以包含多个 Turn。所以“用户只问了一次”，并不代表“模型只调用了一次”。：

```Plaintext
turn_start
  → Assistant Message 流式生成
  → 零个或多个 Tool Call
  → Tool 执行
  → Tool Result Message
  → turn_end
```

如果本轮产生 Tool Call，下一轮会再次从 `turn_start` 开始。

典型事件序列是：

```Plaintext
agent_start
  ├─** turn_start**
  ├─ message_start / update / end
  ├─ tool_execution_start
  ├─ tool_execution_end
  ├─ Tool Result message_start / end
  ├─ **turn_end**
  │
  ├─ **turn_start**
  ├─ message_start / update / end
  ├─ **turn_end**
  └─ agent_end
```

这组事件以后会用于 Trace、UI、Checkpoint 和人工接管，但本节只用它完成三件事：

- 统计轮数；

- 记录每次工具动作；

- 判断本轮结束以后是否还允许继续。

---

有了事件之后，意义就不同了。**骨架决定“循环能不能跑起来”，事件决定“循环跑得清不清楚”。**

Run 从 `agent_start` 到 `agent_end`；每轮由 `turn_start/turn_end` 划界，中间发出消息 start/update/end、工具 start/end 和结果消息事件。我们用这些事件统计轮数、记录 Trace；后面再接界面与 Checkpoint。Loop 本身不直接写会话文件，持久化由上层负责，这样更便于测试和复用。



本节使用 `runAgentLoop()` 显露配置和停止位置。`agentLoop()` 提供事件流，`Agent` 封装消息与 `prompt/steer/abort`，Session、Skills 和完整 Harness 装配留到 3\.5。



现在，自动循环解决了“谁来再次调用”。但你原先还在做三个判断：下一步做什么、怎样才算完成、继续是否还有价值。接下来，我们围绕这三个问题，分别安排模型与运行时的职责。

## 五、ReAct：下一步还不知道，任务怎样推进？

先说第一个判断。**ReAct 的核心，是让推理和行动交替发生，每次行动都依据最新观察。** 它适合路径尚不清楚、必须一边探索一边推进的任务。



登录分析就是这样的任务。第一轮还不知道路由在哪里、有没有认证中间件、数据库采用什么访问方式，当然也无法预先列出所有要读取的文件。



模型先搜索认证相关符号，看到路由调用 `authService.login()`，才有理由继续读取 Service；发现 Service 调用了 `userRepository.findByEmail()`，再沿着这个线索读取数据库访问实现。如果它返回的是外部身份服务的调用，下一步就应该转向那条路径，而不是坚持寻找一个不存在的 Repository。



把这个过程对应到课程要求，就是：

|阶段|登录分析中的具体动作|
|---|---|
|Observe|阅读项目结构和已有工具结果|
|Think / Plan|判断缺少哪段调用关系，选择下一步|
|Act|提出搜索、读取或写入请求，由 Runtime 执行|
|Observe|根据结果确认事实，或修正原来的假设|
|Finalize|证据充分后形成说明，并进入完成检查|



所以 ReAct 的价值不在于输出一大段“我正在思考”。真正重要的是：模型有没有看到工具结果，下一步有没有因此发生变化。



比如搜索没有结果，就应调整符号、目录或假设；不能把同一个搜索原样重做，再声称自己进行了新一轮分析。后面讲死循环时，我们还会回来检查这件事。



日志保存可核对的记录即可：



```JSON
{
  "turn": 4,
  "tool_call_id": "call_04",
  "tool_name": "read_file",
  "arguments": {"path": "src/services/auth-service.ts"},
  "result_code": "OK",
  "observation": "AuthService.login 调用 userRepository.findByEmail"
}
```



这条记录能关联动作与结果。配合 Runtime 的授权记录和简短 Decision Summary，我们就能解释为什么继续或停止，无需把模型隐藏推理当作业务状态。



局部决策可以沿线索不断前进。但换成“给函数补测试并修复”，还要确保几个阶段都做到了。这时，计划就有用了。

## 六、Plan\-and\-Execute：何时需要先定路线？



ReAct 关注的是“每一步怎样根据新观察继续行动”——它是一个执行模式，回答的是“这一步往哪走”。

Plan\-and\-Execute 则先问“目标是什么”，再把目标拆成若干子目标，然后由执行器逐一完成——它是一个任务组织模式，回答的是“整体怎么走”。

Plan\-and\-Execute 先把目标拆成子目标，再交给执行器推进；每个子目标内部仍然可以使用 ReAct。\*\*



例如补测试，先安排定位函数与调用方、阅读测试约定、编写失败测试、运行并读取日志、修正测试或实现，最后回归并检查 Diff。计划保证阶段不遗漏，ReAct 负责每个阶段遇到未知信息时怎样行动。



计划也会出错。若原本准备补单元测试，却发现问题来自数据库事务边界，就需要调整验证方式。我们不能为了完成清单而沿着被证伪的假设继续做。



简单任务不必配 Planner；路径稳定的业务流程也可以用固定 Workflow。本节只建立这层区别，结构化子目标、步骤依赖和 Plan Revision 在 3\.2 展开。



计划告诉我们要做哪些事，却不能证明事情做完了。模型把每个步骤都勾上，是否就能交差？这就到了第二个判断：完成标准。

## 七、循环终止：模型说完成，能交差吗？

模型停止调用工具，只能说明它准备结束；业务是否完成，要看证据。\*\*



登录任务里，模型可能只读了路由，就回复“登录流程已经分析完成”。也可能在对话里写了一份说明，却忘记生成用户要求的 Markdown 文件。这两种情况下，pi 都可能走向自然停止，但用户的目标并没有完成。



### 7\.1 怎样把“完成”变成可检查的条件？

我们先约定最低交付门槛：有源码阅读记录，目标文件写入成功。下面仍沿用 Evidence，它由真实工具结果更新：

```Plaintext
function verifyCompletion(e: Evidence): string[] {
  const missing: string[] = [];
  if (e.readFiles.size < 3) {
    missing.push("缺少源码阅读证据");
  }
  if (!e.writtenArtifacts.has("artifacts/login-flow.md")) {
    missing.push("尚未生成说明文档");
  }
  return missing;
}
```

函数返回缺失项，而不是简单地返回“失败”。这样 Host 可以把具体缺口作为 Follow\-up 交回模型，例如“尚未生成说明文档，请完成写入”，驱动下一轮补齐。



但要注意，这只是最低门槛。读三个文件不能证明读对了，写入成功也不能证明内容正确。最终仍要检查路由、中间件、Service、数据库调用链，以及引用路径是否真实。不要把一个容易实现的计数器当作完整业务验收。



如果模型是在询问必须由用户决定的问题，就应该交还控制权；不能把所有最终回答都当作“偷懒”，强行要求继续。



### 7\.2 有了验收，为什么还需要最大轮数？



因为验收可能一直不通过。模型可能反复改写文档，也可能受工具故障影响，始终拿不到证据。因此设置 `maxTurns = 12`，按 `turn_start` 计数，到上限后不再发出新的模型请求。



十二轮是教学配置，不是通用最佳值。真正的用途是限制最坏情况：达到上限就报告 `MAX_TURNS_EXCEEDED`、已完成内容和阻塞点，不能伪装成功。最后一轮恰好完成时，也要依据证据报告成果，不因限额分类把结果丢掉。



时间、Token 和费用预算同样需要限制。尤其是 Follow\-up，虽然增加了新消息，仍然服务于同一个目标，不能因此把计数器清零。



### 7\.3 停止以后，要告诉用户什么？



至少区分三种结果：任务已经完成；需要用户补充信息或审批；由于预算、取消、权限阻断或不可恢复错误而停止。停止自动执行，不等于任务失败，更不等于任务成功。



到这里，我们既防止提前交差，也防止无限运行。不过还有第三个判断：如果十二轮里面后十轮都在重复，真的值得等到上限吗？

## 八、死循环识别：它在工作，还是只是在重复？

**死循环不一定表现为程序卡死，也可能表现为一直有输出，却没有新进展。**



想象一下：Agent 搜索 `login`，得到两个文件；下一轮又搜索 `login`，还是这两个文件；第三轮仍然做同样的事。每次调用单独看都合法，Runtime 没理由禁止搜索，但整个任务已经没有前进。



### 8\.1 怎样在动作执行前发现重复？



最小版本可以把工具名和规范化参数作为动作指纹，再记录出现次数：

```TypeScript
import { createHash } from "node:crypto";

function actionFingerprint(
  toolName: string,
  args: Record<string, unknown>,
): string {
  // canonicalJson 递归排序对象字段，
  // 复用第二章“审批参数摘要”的规范化实现。
  const canonical = canonicalJson({
    toolName,
    args,
  });

  return createHash("sha256")
    .update(canonical)
    .digest("hex");
}
```

这里的 `canonicalJson` 要递归排序对象字段，避免同一组参数仅仅因为字段顺序不同就绕过计数。它可以复用第二章的参数规范化实现。



这段判断放在 `beforeToolCall`。关键不是日志里出现警告，而是第三次请求没有进入真实 handler；停止原因还要交给 Run 控制逻辑，避免后续动作继续执行。



### 8\.2 相同动作一定是死循环吗？



不一定。修改代码前运行测试得到失败，修改后再运行同一条命令得到通过，这正是我们需要的反馈循环。读完文件后人工改了代码，再次读取也有价值。



所以动作指纹只是保守的入门保护，不能直接当作通用无进展检测。真正判断进展，还要看文件版本、测试结果、已验证事实、计划步骤和错误原因有没有变化；也要识别 A、B 两种动作来回切换的振荡。



后续有了 Plan 和 State，就能把这些信号结合起来。确认停滞时先给明确反馈，允许有限次调整策略；如果仍然没有新证据，就结束并报告卡在哪里。无差别地“再试一次”，只会继续消耗预算。



到这里，选路、验收和止损已经有了分工。不过长任务还有一个常见问题：代码刚读完，用户点了停止，回来以后能接着做吗？

## 九、任务中断与恢复：停下来以后，能接着做吗？

中断是停止当前执行；恢复是从可信进度继续。两件事要分开实现。



pi 通过 `AbortSignal` 传递取消。下面展示的是中断接入位置：

```TypeScript
const controller = new AbortController();

const run = runAgentLoop(
  prompts,
  context,
  config,
  emit,
  controller.signal,
  streamFn,
);

// 用户点击停止。
controller.abort();

await run;
```

模型、Hook、工具和下游子进程都要响应这个 signal。仅仅停止界面输出不够，如果测试命令还在运行，任务就没有真正停下来。取消也不能撤销已经完成的文件写入，这是恢复时必须面对的事实。



本节先预留 Snapshot，记录 `runId、messages、turn、evidence、stopCode`，交给 `SnapshotStore.save/load`。可以在轮次边界保存内存快照，但控制台日志不等于持久化 Checkpoint，Set/Map 也要转换成可存储的数据。



恢复时先加载记录，确认最后完成的轮次和待处理调用，再核对工作区。假设文档已经写入，进程却在记录成功前退出，就不能仅凭旧记录断言“没写过”，直接重做。涉及外部副作用时，应先查询结果或核对幂等标识；无法确认的动作交给人处理。



这就是为什么重新发送原 Prompt 不叫恢复：它会重新开始推断，却不知道哪些动作已经发生。正式状态机、持久化、幂等及人工接管续跑在 3\.3 实现。



这些判断只有接到真实执行位置才有效：拦截必须在动作之前，证据必须来自执行之后。pi 的 Hook 正好给我们提供了这些位置。

### 10\.3 `pi-tools.ts`：把 Runtime 工具适配成 pi AgentTool

`pi` 有自己的 `AgentTool` 接口，而阶段二的工具通过 `ToolRuntime.invoke()` 统一执行。两者之间需要一层薄适配。

以 `search_code` 为例，适配层做了四件事：

1. 定义 `TypeBox` 参数 Schema，供 `pi` 校验参数；

2. 在 `execute()` 中调用 `toolRuntime.invoke()`，传入 `toolCallId`、参数和取消信号；

3. 将 `ManagedToolResult` 转换为 `AgentToolResult`；

4. 失败时抛出异常，由 `pi` 归一化为 `isError=true` 的 Tool Result。

```TypeScript
import { Type } from "typebox";
import type {
  AgentTool,
  AgentToolResult,
} from "@earendil-works/pi-agent-core";

import { toolRuntime } from "./runtime.js";
import { executionContext } from "./run-context.js";

const SearchCodeInput = Type.Object(
  {
    query: Type.String({ minLength: 1 }),
    path: Type.String({ minLength: 1 }),
  },
  { additionalProperties: false },
);

function toPiResult(
  result: ManagedToolResult,
): AgentToolResult<Record<string, unknown>> {
  if (!result.ok) {
    // pi 0.83.0 的 AgentTool 约定：执行失败时抛出异常，
    // Loop 会把它归一化为 isError=true 的 Tool Result。
    throw new Error(JSON.stringify({
      code: result.code,
      content: result.modelView,
    }));
  }

  return {
    content: [{
      type: "text",
      text: JSON.stringify(result.modelView),
    }],
    details: {
      code: result.code,
      artifact: result.artifact,
    },
  };
}

export const searchCodeTool: AgentTool<
  typeof SearchCodeInput
> = {
  name: "search_code",
  label: "Search code",
  description: [
    "在代码仓库中搜索文本或符号。",
    "当你还不知道文件位置或调用方时使用。",
  ].join(" "),
  parameters: SearchCodeInput,

  async execute(toolCallId, params, signal) {
    const result = await toolRuntime.invoke({
      toolCallId,
      modelName: "search_code",
      args: params,
      context: executionContext,
      signal,
    });

    return toPiResult(result);
  },
};
```

这层适配保留了第二章的四条不变量：

- `toolCallId` 不丢失；

- 模型参数仍然属于不可信输入；

- 所有工具进入同一个 `invoke()`；

- Tool Result 先治理，再进入模型 Context。

其余三个工具（`listFilesTool`、`readFileTool`、`writeArtifactTool`）按同一模式导出。


### 10\.4 `loop-guard.ts`：只实现本节需要的四项控制

`LoopGuard` 是本节的“停止决策中心”。它不依赖 `pi` 内部状态，而是通过 `pi` 暴露的 Hook 接入：

- `beforeToolCall`：动作指纹去重，连续三次相同动作时阻止执行；

- `afterToolCall`：从工具结果中提取证据（读了哪些文件、写了哪些产物）；

- `afterTurn`：在 Turn 结束时检查最大轮数、完成证据，证据不足时生成 Follow\-up Message；

- `drainFollowUps`：将 Follow\-up Message 注入下一轮。

```TypeScript
import {
  createHash,
} from "node:crypto";
import type {
  AgentMessage,
  AfterToolCallContext,
  BeforeToolCallContext,
  ShouldStopAfterTurnContext,
} from "@earendil-works/pi-agent-core";

export interface Evidence {
  readFiles: Set<string>;
  writtenArtifacts: Set<string>;
}

export interface LoopState {
  runId: string;
  turn: number;
  maxTurns: number;
  stopCode?: string;
  actions: Map<string, number>;
  evidence: Evidence;
}

export class LoopGuard {
  private followUps: AgentMessage[] = [];

  constructor(
    readonly state: LoopState,
  ) {}

  beforeToolCall(
    context: BeforeToolCallContext,
  ): { block?: boolean; reason?: string } {
    const fingerprint = this.fingerprint(
      context.toolCall.name,
      context.args,
    );
    const count = this.state.actions.get(fingerprint) ?? 0;
    this.state.actions.set(fingerprint, count + 1);

    if (count + 1 >= 3) {
      this.state.stopCode = "REPEATED_ACTION";
      return {
        block: true,
        reason: [
          "REPEATED_ACTION：相同工具和参数已出现三次。",
          "本次调用未执行。",
        ].join(" "),
      };
    }

    return {};
  }

  afterTurn(
    context: ShouldStopAfterTurnContext,
  ): boolean {
    if (this.state.stopCode) {
      return true;
    }

    if (this.state.turn >= this.state.maxTurns) {
      this.state.stopCode = "MAX_TURNS_EXCEEDED";
      return true;
    }

    if (context.toolResults.length === 0) {
      const missing = this.verifyCompletion();

      if (missing.length === 0) {
        this.state.stopCode = "COMPLETED";
        return true;
      }

      this.followUps.push({
        role: "user",
        content: [{
          type: "text",
          text: [
            "FINAL_REJECTED：完成证据不足。",
            ...missing.map(item => `- ${item}`),
            "请继续使用工具补齐证据和交付物。",
          ].join("\n"),
        }],
        timestamp: Date.now(),
      });
    }

    return false;
  }

  drainFollowUps(): AgentMessage[] {
    return this.followUps.splice(0);
  }

  observeToolResult(
    context: AfterToolCallContext,
  ): void {
    if (context.isError) return;

    const args = context.args as Record<string, unknown>;

    if (context.toolCall.name === "read_file"
        && typeof args.path === "string") {
      this.state.evidence.readFiles.add(args.path);
    }

    if (context.toolCall.name === "write_file"
        && typeof args.path === "string") {
      this.state.evidence.writtenArtifacts.add(args.path);
    }
  }

  private verifyCompletion(): string[] {
    const missing: string[] = [];
    const evidence = this.state.evidence;

    if (evidence.readFiles.size < 3) {
      missing.push("至少读取三个相关源码文件");
    }
    if (!evidence.writtenArtifacts.has(
      "artifacts/login-flow.md"
    )) {
      missing.push("生成 artifacts/login-flow.md");
    }

    return missing;
  }

  private fingerprint(
    name: string,
    args: unknown,
  ): string {
    return createHash("sha256")
      .update(JSON.stringify(
        this.sortValue({ name, args })
      ))
      .digest("hex");
  }

  private sortValue(value: unknown): unknown {
    if (Array.isArray(value)) {
      return value.map(item => this.sortValue(item));
    }
    if (value && typeof value === "object") {
      return Object.fromEntries(
        Object.entries(value)
          .sort(([left], [right]) =>
            left.localeCompare(right)
          )
          .map(([key, item]) => [
            key,
            this.sortValue(item),
          ])
      );
    }
    return value;
  }
}
```

这段代码只解决四件事：

1. 相同动作第三次出现时阻止；

2. 达到最大轮数时停止；

3. 模型想结束时验证交付证据；

4. 证据不足时生成 `pi` Follow\-up Message。

它没有计划步骤、任务状态机、持久化 Checkpoint 和 Sandbox Policy——这些不是遗漏，而是第三章的教学边界。

```Markdown
- readme 10.1 要求的登录流程说明产物已成功写入；
- 两项同时满足才允许业务完成。
必须提供「返回缺失项列表」的校验能力，而不是只返回布尔值，便于把缺口回传给模型。

【Final 处理规则】
- 模型不再调用工具，只表示协议层准备停止，不等于业务完成；
- 此时必须执行完成校验：
  · 契约满足 → 设置成功停止原因并结束；
  · 契约不满足 → 生成一条用户角色的 Follow-up：包含稳定标识 FINAL_REJECTED、逐项列出缺失证据、
    并要求继续使用工具补齐交付；
- Follow-up 属于同一个 Run，不得重置轮次与动作计数。

【停止判定顺序（不可调换）】
1. 已存在停止原因 → 立即停止；
2. 达到最大轮数 → 以最大轮数原因停止；
3. 本轮无工具结果（模型准备自然结束）→ 执行完成校验；
4. 本轮有工具结果且未命中停止条件 → 允许继续。
停止原因一旦设置，不得被后续覆盖为其它值。

【硬性禁止】
- 不调用模型、不执行工具、不访问文件系统；
- 不实现计划、状态机、Checkpoint、Sandbox；
- 不依赖 pi 内部状态，只依据钩子输入与自身状态作决定。

【验收】
1. 同一动作第三次被阻止；
2. 对应 Runtime handler 实际只执行两次（这是拦截是否真生效的唯一证据）；
3. 参数字段顺序变化无法绕过重复检测；
4. 达到最大轮数后不再发起下一轮模型调用；
5. 缺少源码阅读证据时拒绝 Final；
6. 缺少产物写入证据时拒绝 Final；
7. Follow-up 含具体缺失项且带 FINAL_REJECTED；
8. 补齐证据后能以成功原因结束；
9. 错误工具结果不计入证据；
10. 编译与测试通过。

【只输出】
1. 接入了哪些 pi 钩子、每个钩子负责什么；
2. 全部停止原因清单；
3. 完成契约内容；
4. 重复动作测试中 handler 的真实执行次数；
5. 与 readme 0.83.0 描述的钩子顺序差异（如有）；
6. 编译与测试结果。
```



### 10\.5 agent\-runner\.ts ：把 Guard 接进 pi 原生 Loop

agent\-runner\.ts  是装配点。它的结构很清晰：

1. 创建 `LoopState` 和 `LoopGuard` 实例；

2. 构造 `AgentContext`（System Prompt \+ 工具列表）；

3. 定义用户 Prompt；

4. 实现 `emit` 事件处理（打印 Turn 和工具执行信息）；

5. 装配 `AgentLoopConfig`，将 Guard 的 Hook 接入 `beforeToolCall`、`afterToolCall`、`shouldStopAfterTurn`、`prepareNextTurn`、`getFollowUpMessages`；

6. 调用 `runAgentLoop` 启动。

```TypeScript
import {
  runAgentLoop,
  type AgentContext,
  type AgentEvent,
  type AgentLoopConfig,
  type AgentMessage,
} from "@earendil-works/pi-agent-core";
import { randomUUID } from "node:crypto";

import {
  gatewayModel,
  models,
} from "./model.js";
import {
  codeUnderstandingTools,
} from "./pi-tools.js";
import {
  LoopGuard,
  type LoopState,
} from "./loop-guard.js";

const state: LoopState = {
  runId: randomUUID(),
  turn: 0,
  maxTurns: 12,
  actions: new Map(),
  evidence: {
    readFiles: new Set(),
    writtenArtifacts: new Set(),
  },
};

const guard = new LoopGuard(state);
const controller = new AbortController();

const context: AgentContext = {
  systemPrompt: [
    "你是代码理解 Agent。",
    "先搜索和阅读源码，再形成结论。",
    "不得根据文件名猜测实现。",
    "必须把说明写入 artifacts/login-flow.md。",
    "最终列出引用过的相关源码路径。",
  ].join("\n"),
  messages: [],
  tools: codeUnderstandingTools,
};

const prompt: AgentMessage = {
  role: "user",
  content: [{
    type: "text",
    text: [
      "帮我找出该项目的登录逻辑，",
      "并生成 Markdown 说明文档。",
    ].join(""),
  }],
  timestamp: Date.now(),
};

const emit = async (
  event: AgentEvent,
): Promise<void> => {
  if (event.type === "turn_start") {
    state.turn += 1;
    console.log({
      type: event.type,
      runId: state.runId,
      turn: state.turn,
    });
  }

  if (event.type === "message_update"
      && event.assistantMessageEvent.type === "text_delta") {
    process.stdout.write(
      event.assistantMessageEvent.delta,
    );
  }

  if (event.type === "tool_execution_start") {
    console.log({
      type: event.type,
      toolCallId: event.toolCallId,
      toolName: event.toolName,
    });
  }

  if (event.type === "tool_execution_end") {
    console.log({
      type: event.type,
      toolCallId: event.toolCallId,
      toolName: event.toolName,
      isError: event.isError,
    });
  }

  if (event.type === "turn_end"
      && event.message.role === "assistant"
      && (event.message.stopReason === "error"
          || event.message.stopReason === "aborted")) {
    state.stopCode = event.message.stopReason === "aborted"
      ? "ABORTED"
      : "MODEL_ERROR";
  }
};

const config: AgentLoopConfig = {
  model: gatewayModel,

  convertToLlm: messages =>
    messages.filter(message =>
      message.role === "user"
      || message.role === "assistant"
      || message.role === "toolResult"
    ),

  apiKey: process.env.GATEWAY_API_KEY,
  maxRetries: 0,
  toolExecution: "sequential",

  beforeToolCall: async context =>
    guard.beforeToolCall(context),

  afterToolCall: async context => {
    guard.observeToolResult(context);
    return undefined;
  },

  prepareNextTurn: async ({ context }) => {
    // Evidence 已由 afterToolCall 更新。
    // 3.3 会在这里保存正式 Checkpoint。
    return { context };
  },

  shouldStopAfterTurn: async context =>
    guard.afterTurn(context),

  getSteeringMessages: async () => [],

  getFollowUpMessages: async () =>
    guard.drainFollowUps(),
};

const newMessages = await runAgentLoop(
  [prompt],
  context,
  config,
  emit,
  controller.signal,
  models.streamSimple.bind(models),
);

console.log({
  runId: state.runId,
  turns: state.turn,
  stopCode: state.stopCode,
  newMessages: newMessages.length,
});
```

这里故意使用 `toolExecution: "sequential"`。

第二章已经讲过多个工具什么时候并行。代码理解任务中的动作通常存在前后依赖：先搜索，再根据结果读取。3\.1 不需要再讲一次并发调度。

主流程中有五个位置值得重点读：

第一，底层循环由 `runAgentLoop()` 提供，不自建第二套 Loop。 这是复用成熟框架的核心收益——不用重复实现流式、事件、取消和错误处理。

第二，`beforeToolCall` 只增加 Run 级重复保护；工具本身仍走第二章 Runtime。 职责单一，不越界。

第三，`prepareNextTurn` 是每一轮进入下一次模型调用前更新 Observation 的位置。 本节只更新内存证据，3\.3 再持久化。

第四，`shouldStopAfterTurn` 在完整 Turn 结束后检查上限与完成条件。 这是终止策略的主入口。

第五，`getFollowUpMessages` 把“缺失完成证据”重新注入 `pi`，驱动下一轮，而不是相信模型第一次 Final。



需要注意 pi 0\.83\.0 的实际调用顺序：

```Plaintext
turn_end
  → prepareNextTurn
  → shouldStopAfterTurn
  → getSteeringMessages
  → 如果自然停止，再 getFollowUpMessages
```

因此，Evidence 在 `prepareNextTurn` 更新后，完成校验才能读到本轮最新 Tool Result。

## 十一、换个岗位任务，怎样复用这条 Loop？

换一个任务，先别急着加工具。先看岗位人员原来怎样把事情做完：哪些规则每次都一样，哪些步骤必须看到结果后才能决定，哪些动作需要人确认？登录分析中的定位入口、收集证据、写说明和验收，就可以这样拆开。



|业务内容|Agent 落点|
|---|---|
|必须生成说明并引用源码|Prompt 与 Completion Contract|
|下一步搜索什么、读哪里|模型与 Loop|
|搜索、读取、写入|Tool Runtime|
|轮数和重复动作限制|LoopGuard|
|高风险修改需要确认|HITL|



岗位动作再映射到工具：浏览用 `list_files/read_directory`，定位用 `search_code`，取证用 `read_file`，说明用 `write_file`，修改用 `apply_patch`，验证用 `run_test/run_command`，检查改动用 `git_diff/git_status`。



再沿用户旅程安排协同节点。读取代码通常可以自动完成，生成的文档交给用户审阅；到了源码修改，则根据已有授权策略判断是否需要确认，修改后再做回归。执行中得到的事实保存在任务状态，能够复用的经验以后再沉淀为 Memory。



这样，业务流程和工程组件就对应起来了。不过，配置里写了“需要确认”或“超过上限停止”，不代表执行时真的生效。我们还需要几条测试来证明。

## 十二、TDD 验收：怎样证明规则不是摆设？

概念讲完了，代码也跑通了，但还有一个问题需要回答：你怎么证明 Loop 真的在工作，而不是碰巧跑出了一份文档？

如果只靠最终结果——一个 Markdown 文件被生成——你无法区分以下几种情况：

- 模型真的通过多轮探索找到了登录逻辑；

- 模型靠训练数据“猜”出了登录流程，工具调用只是装饰；

- 工具执行了，但结果没有写回下一轮 Context，模型只是凭记忆续写；

- 最大轮数和重复检测配置了，但从未被触发过，只是摆设。

所以，我们需要一组面向行为的验收测试——不验证内部实现细节，只验证 Loop 的关键机制是否真正生效。

### 12\.1 测试策略：脚本化响应 \+ 真实集成验收

本节采用两层验收策略：

第一层：单元测试层，使用脚本化响应（scripted responses）。在 `pi` 的 `StreamFn` 边界注入预设的模型响应序列，稳定复现终止分支和异常场景。例如，让模型连续三次返回相同的 `search_code` 调用，验证重复拦截是否生效。脚本化响应不替代真实模型，只用于稳定复现那些在真实运行中可能偶发的边界条件。

第二层：集成验收层，使用真实 Gateway 和 DeepSeek 模型。验证端到端流程：从用户输入到文档生成，模型至少经历一次 Tool Call → Tool Result → 下一轮决策的完整闭环。

两类测试缺一不可——脚本化响应验证“机制存在”，真实集成验证“机制在真实环境中有效”。

### 12\.2 Tool Result 会驱动下一轮

第一个要验证的是最基础的闭环：工具执行结果必须回到下一轮模型调用。



```TypeScript
// 测试文件：loop.test.ts
// 验证 Tool Result 是否出现在下一轮 Context 中
it("把 Tool Result 写回后继续请求模型", async () => {
  await runWithScriptedResponses([
    toolCall("search_code", {
      query: "login",
      path: ".",
    }),
    finalMessage("登录入口位于 src/routes/login.ts"),
  ]);

  expect(modelCallCount()).toBe(2);
  expect(secondModelContext()).toContainEqual(
    expect.objectContaining({
      role: "toolResult",
      toolCallId: expect.any(String),
    }),
  );
});
```

测试脚本让模型在第一次调用时返回一个 `search_code` 的 Tool Call，第二次调用时返回 Final Answer。验收标准是：

1. 模型被调用了两次（说明第一轮结束后 Loop 继续了）；

2. 第二次调用的 Context 中包含 `role: "toolResult"` 的消息，且 `toolCallId` 与第一次的 Tool Call 匹配。

如果测试通过，说明 Tool Result 确实写回了消息历史，驱动了下一轮决策——这是 Loop 成立的最底线证据。

### 12\.3 缺少交付证据时拒绝 Final

第二个要验证的是完成条件：模型说“我完成了”时，系统会先验证交付物，而不是盲目接受。

```TypeScript
// 测试文件：loop.test.ts
// 验证模型提前结束但文档未写入时，系统拒绝 Final 并生成 Follow-up
it("没有写文档时不接受 Final", async () => {
  await runWithScriptedResponses([
    finalMessage("登录逻辑已经分析完成"),
    toolCall("write_file", {
      path: "artifacts/login-flow.md",
      content: "# 登录逻辑",
    }),
    finalMessage("文档已经生成"),
  ]);

  expect(modelCallCount()).toBe(3);
  expect(allUserMessages()).toContainEqual(
    expect.stringContaining("FINAL_REJECTED"),
  );
});
```

测试脚本让模型在第一次响应时直接输出 Final Answer（不调用任何工具）。此时 `LoopGuard.afterTurn` 会检查 `evidence.writtenArtifacts`，发现 `artifacts/login-flow.md` 不存在，于是注入一条 `FINAL_REJECTED` 的 Follow\-up Message。

验收标准是：模型被调用了至少三次（第一次 Final → 被拒绝 → 收到 Follow\-up 后再次调用），且用户消息中包含 `FINAL_REJECTED` 或“完成证据不足”等标识。

这个测试还有一个附带价值：它验证了 4\.3 节的核心论断——“没有 Tool Call”只是协议层停止信号，不是业务层完成证据。 测试通过时，这句话就不再是理念，而是可运行的代码事实。



### 12\.4 第三次相同动作不会执行 handler

第三个要验证的是 8\.2 节的重复动作拦截：连续三次相同动作时，第三次不进入真实 Handler。

```TypeScript
// 测试文件：loop.test.ts
// 验证 LoopGuard.beforeToolCall 拦截第三次重复调用
it("阻止第三次相同工具调用", async () => {
  const call = toolCall("search_code", {
    query: "login",
    path: ".",
  });

  await runWithScriptedResponses([
    call,
    call,
    call,
  ]);

  expect(searchHandlerCallCount()).toBe(2);
  expect(lastToolResult()).toMatchObject({
    isError: true,
    content: expect.stringContaining("REPEATED_ACTION"),
  });
});
```

测试脚本让模型连续三次返回相同的 `search_code({"query":"login","path":"."})`。`LoopGuard.beforeToolCall` 在第二次调用后已经将该动作的计数累加到 2，第三次触发时返回 `{ block: true, reason: "REPEATED_ACTION" }`。

验收标准是：

1. `search_code` 的真实 Handler 只执行了两次；

2. 第三次的 Tool Result 是 `isError: true`，内容包含 `REPEATED_ACTION`。

关键断言是 Handler 执行次数为 2，而不是 3。 如果测试只验证“第三次返回了错误”，但 Handler 依然执行了，那拦截就是掩耳盗铃——资源已经消耗、副作用已经产生，“报错”只是事后贴标签。

### 12\.5 最大轮数到达后不再调用模型

第四个要验证的是 7\.2 节的硬限幅机制：达到 `maxTurns` 后，Loop 停止，不再发起新的模型调用。

```TypeScript
// 测试文件：loop.test.ts
// 验证达到最大轮数后停止
it("达到最大轮数后结束", async () => {
  const state = buildLoopState({
    maxTurns: 3,
  });

  await runNeverEndingAgent(state);

  expect(state.turn).toBe(3);
  expect(state.stopCode).toBe(
    "MAX_TURNS_EXCEEDED"
  );
  expect(modelCallCount()).toBe(3);
});
```

测试构造一个“永不结束”的 Agent——每轮都返回 Tool Call，让 Loop 无法自然停止。将 `maxTurns` 设为 3，然后运行。

验收标准是：

1. `state.turn` 恰好等于 3；

2. `state.stopCode` 为 `MAX_TURNS_EXCEEDED`；

3. 模型调用次数恰好为 3（没有第 4 次）。

这个测试的价值在于确认硬限幅机制确实“硬”——它不依赖模型的合作，也不依赖业务条件的满足，纯粹由 Host 配置强制执行。

### 12\.6 用户取消会终止当前 Run

第五个要验证的是 9\.1 节的中断传播：`AbortSignal` 能终止正在运行的模型或工具。

```TypeScript
// 测试文件：loop.test.ts
// 验证取消信号传播到模型流和工具执行
it("取消信号会结束模型或工具等待", async () => {
  const controller = new AbortController();
  const run = startSlowAgent(controller.signal);

  controller.abort();
  await run;

  expect(lastAssistantStopReason()).toBe("aborted");
  expect(toolStartedAfterAbort()).toBe(false);
});
```

测试启动一个执行较慢的 Agent（模拟长耗时工具或流式生成），然后在运行中调用 `controller.abort()`。

验收标准是：

1. 最终消息的 `stopReason` 为 `aborted`；

2. 取消信号发出后，没有新的工具开始执行。

这个测试验证的是中断传播路径的完整性——取消信号是否从 `controller.abort()` 一路传递到模型流和工具执行层。



### 12\.7 真实集成验收

脚本化测试跑通之后，还需要一轮真实集成验收，使用真实的阶段一 Gateway 和 `deepseek-v4-flash` 模型，保持流式输出，完整运行“生成登录逻辑文档”任务。

验收标准：

1. Agent 至少完成一次 Tool Call → Tool Result → 下一轮模型调用的完整闭环；

2. 最终生成 `artifacts/login-flow.md`；

3. 文档中引用的文件路径在仓库中真实存在（不是虚构的）；

如果以上四项都通过，Loop 才真正“成立”。

## 十三、AI 可以外包什么，工程师必须掌握什么？

AI 可以代写实现，不能替工程师定义成功或承担交付责任。\*\*



[Andrew Ng 在 The Batch](https://www.deeplearning.ai/the-batch/issue-359)区分三个反馈尺度：Agent 编码循环以分钟推进，开发者反馈以几十分钟到小时调整规格，外部用户反馈可能持续数小时到数周。他为女儿制作打字应用时，Agent 自行构建检查，但视觉、奖励和用户流程仍由人调整。实现自动化不等于产品判断自动化。



Schema、Adapter、日志、指纹、计数器、Vitest 样板和类型修正可以交给 AI。工程师要识别 SOP 中的动态判断，选择 ReAct、计划或 Workflow，定义证据、预算与中断重放边界，审查 Runtime 是否被绕过，并用测试验证保护。



掌握标准不是背 API：能找到源码里的模型调用、工具执行、回写与退出，能接通已有 Runtime，能证明重复动作被拦、证据不足不算完成，并说明恢复还缺哪些状态。Loop 越快，越不能放弃阅读产物；自动验收不是“不再理解代码”的理由。

## 十四、本节小结：3\.1 为最终项目留下了什么？

回到开头的问题，我们交给 Agent 的不只是一条工具调用，而是一段能够根据结果继续推进的工作过程。阶段一 Gateway 负责模型调用，阶段二 Runtime 负责受控执行，pi Loop 把两者连起来，让搜索和读取获得的事实真正影响下一步。



但能够连续运行，还不等于可以放心交付。模型选择动作，计划组织子目标，完成契约检查证据，LoopGuard 限制空转和预算。用户中途停止时，系统还要分清已经发生的动作与尚未完成的工作，给后续恢复留下可信依据。



下一节我们继续使用这条 pi 执行链，把临时的局部决策升级为可跟踪、可修订的计划。本节先把发动机和停止机制讲清楚，后续再逐步补上持久化恢复、Sandbox 和完整 Harness，最终支撑两个 Codebase Agent 任务。
