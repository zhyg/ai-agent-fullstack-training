# 3.6 LangGraph 与 Agent 编排 v2

## 开场：一张图先放在这里

我们这一节要解决的工程问题是：

> 一个开发者提交一张上线工单（一张发布申请单，上面有服务名、版本号、代码改动内容这些信息），
> 系统怎么自动跑完"构建 / 单测 / 安全扫描 / 依赖审计 →
> 预发环境 → 灰度 10% → 50% → 100%"，并在该停的地方停下来等人批？
> （灰度发布 = 把真实流量一小部分一小部分地切给新版本，边切边观察，没问题再继续放大。）

把这件事画成一张"发布流程图"：

```
START → 受理申请 → [并行 ToolNode×4: 构建/单测/安全扫描/依赖审计]
       → 汇合 → 变更等级路由(L/M/H)
         ├─ L → 自动放行
         ├─ M → Tech Lead 审批 (interrupt)
         └─ H → Tech Lead + Security 双审批 (interrupt ×2)
       → 预发部署 → 冒烟测试 ──失败──┐
                       │成功         │
                       ↓             ↓
                    灰度 10% → SRE 确认 (interrupt) → 监控
                       │异常 ↘                    ↗ 正常
                       │      自动回滚循环 (≤3 次)
                       ↓
                    灰度 50% → 100% → 完成报告 → END
```

这张图就是我们要让 LangGraph 跑起来的东西。它已经覆盖了 LangGraph 的 6 个核心机制：

- **图 / 节点 / 边 / 状态**：每个方框是节点，方框间连线是边，工单本身在节点间流动的数据是状态
- **StateGraph 条件分支与循环**：变更等级路由、冒烟失败回退、灰度异常回滚，3 个分支 2 个循环
- **ToolNode**：四路并行检查的执行体
- **Interrupt**：M/H 审批和每次灰度推进的人工确认
- **Checkpoint**：H 级审批可能跨天，进程也得能停得下来 + 重启接得上
- **调试与可视化**：Mermaid（一种"用文字描述流程图、工具自动画成图"的格式）、`astream` 流式输出、`langgraph dev` 本地 HTTP 服务

下面分 6 步把这张图一步步搭起来。每一步都用一段提示词让 AI 生成代码，
跑测试通过再进下一步。

## 一、概念定位：先把工具生态分清

这一节要用的东西都在 LangGraph 上。但 LangGraph 周边有几个长得很像的工具——
LangChain、AgentScope、Dify、LangSmith——先把它们各自负责什么说清楚，
免得装错、用错：

| 名称                   | 解决什么问题                                  | 不解决什么                                            | 本课用法                 |
| -------------------- | --------------------------------------- | ------------------------------------------------ | -------------------- |
| **LangGraph**        | 用"状态 + 节点 + 边"把流程编排成可执行的图，调度分支/循环/中断/恢复 | 不直接帮你写 Prompt，不做模型抽象                             | **主角**，本章全部能力都靠它     |
| LangChain            | 模型客户端 + 消息类型 + 工具接口的统一封装                | 不管你怎么调度多步骤流程（高层 create_agent 也是建立在 LangGraph 之上） | 配角：用它的 `@tool` 和消息类型 |
| AgentScope           | 另一套独立的 Agent 框架，模型/工具/协作都自己一套           | 与 LangGraph 不是插件关系                               | 知道即可，不装              |
| Dify                 | 可视化搭建 Workflow 的平台，拖拽节点                 | 不适合做"代码内编排 + 跨进程恢复"这种工程化要求高的事                    | 知道即可，不部署             |
| LangSmith / Langfuse | 观测平台，记录每一次调用的 Trace（输入、输出、耗时，方便事后回看）    | 不参与执行；不会让任务具备"中断后继续"的能力                          | 可选接入，本章不依赖           |

表格只给了一句话定位，下面逐个展开：它是什么、谁在用、一般用在什么场景。

**LangGraph**——LangChain 公司开源的"流程编排框架"。你用 Python 代码声明"有哪些步骤、
步骤之间怎么走、中间数据长什么样"，它负责按顺序执行、在分支处选路、在需要人的地方停下、
进程重启后从停下的地方接着跑。它适合**步骤多、有分支、要人工介入、要能中断恢复**的流程，
典型场景：

- 研发与运维：发布审批（就是本课的案例）、故障处置流程、工单自动分派
- 金融与保险：贷款审批、理赔核查——模型先初审，高风险单子转人工复核
- 客服：多轮对话里按意图走不同处理分支，搞不定的转人工坐席
- 企业内部流程：合同审核、采购审批这类"机器先处理、人最后拍板"的流程

**LangChain**——同一家公司更早推出的库，主要做"统一接口"：不管底下接的是 OpenAI、
DeepSeek 还是通义千问，调用方式都一样；另外提供消息类型、工具声明（`@tool`）、
文档加载与检索等现成组件。它的高层 Agent 接口（`create_agent`）内部就是用 LangGraph 实现的。
典型场景：快速做原型、搭 RAG 知识库问答（先从文档库检索相关段落再让模型回答）、
需要在多家模型之间切换的应用。

**AgentScope**——阿里巴巴通义实验室开源的另一套 Agent 框架，和 LangGraph 是
"同类竞品"而不是插件关系：模型接入、工具、记忆、多个 Agent 之间的消息协作，它都自己实现一套。
它的强项是**多个 Agent 互相对话协作**，并对接阿里云生态。
典型场景：多角色协作的任务（比如"产品经理 Agent + 开发 Agent + 测试 Agent"分工）、
群体行为模拟类研究、以阿里云为主的国内企业项目。

**Dify**——一个开源的可视化 AI 应用搭建平台，在网页上拖拽节点就能搭出工作流，
自带知识库、模型管理、对外发布 API，还支持私有化部署（装在企业自己的服务器上）。
它的用户很多不是专职开发者，而是业务和运营人员。
典型场景：企业内部知识库问答、客服机器人、营销文案批量生成、各类"表单进 → 模型处理 → 结果出"的轻量流程。
它的短板是：流程逻辑藏在平台配置里，不好做代码评审、版本管理和精细的中断恢复。

**LangSmith / Langfuse**——两款"观测平台"，本身不执行任何流程，只负责把每一次模型调用、
工具调用的输入、输出、耗时、花了多少 Token 记录下来，供事后排查和评估效果。
LangSmith 是 LangChain 公司的商业产品，和 LangChain/LangGraph 集成最顺；
Langfuse 是开源项目，可以自己部署，数据不出公司，所以在对数据合规要求高的行业更常见。
典型场景：线上 AI 应用出问题时回看"模型当时看到了什么、回答了什么"、
对比两版提示词哪个效果更好、统计调用成本。

**记住两条线**：

1. **Trace 记录发生过什么，Checkpoint（存档）保存接下来怎么继续**。装一个观测 SDK 不等于能恢复任务。
2. **用 LangGraph 不要求你装 LangChain 全家桶**。本章只用 `langchain-openai`/`langchain-deepseek`
   做模型客户端、`langchain-core` 拿消息类型、其余都靠 LangGraph 本体。

把概念认清之后，我们来看怎么把这张图拆成代码。

## 二、业务拆解：先把工单流程想清楚

用 LangGraph 搭流程，真正难的不是 API 怎么调，而是业务步骤有没有拆对：
哪些步骤要串行、哪些可以并行、哪里要分叉、哪里要停下等人。
所以动手写代码之前，我们先把开场那张发布流程图拆成一个个具体步骤：

**7 个业务步骤**（每一步都是一段独立工作，做完就交给下一步）：

1. **受理申请**：校验工单字段，准备上下文
2. **跑前置检查**：构建、单测、安全扫描、依赖审计 —— 这四件**互不依赖可以并行**
3. **变更分级**：根据工单附带的 `patch_diff` 判定风险等级 L / M / H。
   （`patch_diff` 是工单里的一个字段，存放这次发布的代码改动内容，也就是 diff——
   git 对比新旧代码输出的差异文本，哪些行删了、哪些行加了；
   分级只看它的两点：内容里有没有 auth、payment 这类敏感词，改动有多长。
   L = Low 低风险，M = Medium 中风险，H = High 高风险，等级越高审批越严。）
4. **审批**：根据等级决定要不要人介入、几个人介入
5. **预发部署 + 冒烟**：先把新版本发到 staging（预发环境，一个和生产几乎一样的真实运行环境）
   跑冒烟测试（一组最基本的检查：服务起没起来、关键接口通不通），失败就打回修订，从头再来。
6. **灰度推进**：10% → 50% → 100%，每段都要 SRE（Site Reliability Engineer，值班运维工程师）
   确认 + 监控健康度。
7. **完成报告**：把审批记录、各阶段结果汇总写成报告文件，并把工单标记为最终状态（发布成功/被拒/回滚）

把这 7 步映射到 LangGraph 的"对象"概念：

| 业务概念              | LangGraph 对象                                                 |
| ----------------- | ------------------------------------------------------------ |
| 工单本身（贯穿整个流程的共享数据） | **State**：一个随流程一路传递的字典，每个节点从它读数据、把结果写回它（用 TypedDict 声明有哪些字段） |
| 每个步骤              | **节点**（一个 Python 函数）                                         |
| 步骤之间的依赖关系         | **边**（`add_edge` / `add_conditional_edges`）                  |
| 流程总装              | **图**（`StateGraph`）                                          |
| 等待人工输入            | **Interrupt**（`interrupt()` + `Command(resume=...)`）         |
| 跨进程暂停与恢复          | **Checkpoint**（`SqliteSaver` / 顶层工程用 `AsyncSqliteSaver`）     |
| 节点要调用的外部能力        | **ToolNode**（一个"拿着工具清单、负责并发执行工具"的现成节点）                       |

> 这里有一个必须先说清楚的点：**节点 ≠ 一次模型调用**。
> 受理工单的节点是纯函数；变更分级节点在完整工程里会调一次大模型
> （前面几步的教学工程里我们先用规则实现，接不接模型由你定）；前置检查节点会跑 4 个工具。
> 节点 = 业务步骤，里面要不要模型、调几次工具，是节点自己的实现细节。

业务拆清楚了，对象也对齐了。下一步开始用代码搭图——也就是用 `StateGraph`
把上面这些节点一个个注册进去、再用边把它们连起来，得到一张能执行的流程图。
我们**不一次搭完整图**，
而是从主线最小版开始，每跑通一次加一个能力。这样做有两个好处：
**第一**，每一步都有可验证的产物；**第二**，每加一个机制，你都能清楚感觉到
它解决了什么问题、不加它会发生什么。

## 三、主线最小版（P1）

第一步：只搭"主线"。所谓主线，就是从头到尾最直的一条路——工单受理后，
4 项前置检查全部直接通过、不需要任何人审批、每个环节都不失败，一路放行到发布报告：
"受理 → 4 项检查（直接通过）→ 预发 → 冒烟 → 灰度 10% → 50% → 100% → 报告"。
**不含任何分支、不含任何中断**。先把这条最直的路跑通，后面每步再往上加机制。

这一步我们分三个环节走：先把提示词交给 AI 生成代码，再跑测试验证，最后回头读生成了什么。
每份提示词里都带几条 **AC（Acceptance Criteria，验收标准）**——把"怎样才算做对了"
写成可执行的 pytest 测试用例，代码生成后以这些测试全部通过为准。
提示词按 P1…P6 编号，后面每一节各配一份。

### 3.3 这一步的代码里，我们讲清三件事

打开 `demos/01_minimal/state.py`，看 LangGraph 状态对象长什么样：

```python
class ReleaseState(TypedDict):
    ticket_id: str
    ...
    stages_completed: NotRequired[list[str]]
```

**第一件事**：State 用一个**预先声明字段的 TypedDict** 来描述。TypedDict 是 Python 的一种类型标注，
用来声明字典预期有哪些键、每个键对应什么类型，方便编辑器和静态类型检查工具发现拼写或类型错误。
它本身**不会在运行时拦截额外字段**；这里约定所有节点都按这份字段清单读写，是为了让状态结构清楚、便于检查。
`NotRequired` 表示这个字段可以在初始 State 里缺省，后续节点再补上。

打开 `nodes.py`，看节点长什么样：

```python
def deploy_staging(state: ReleaseState) -> dict:
    return {"stages_completed": state["stages_completed"] + ["staging"]}
```

**第二件事**：**节点函数接收整个 State，但只返回要更新的字段**。
比如 `deploy_staging` 只返回 `stages_completed` 一个字段，其他字段它不碰。

为什么不能把整个 State 原样返回？因为 LangGraph 会把节点返回的字段作为本轮更新，再按每个字段配置的合并规则写回 State。
如果多个并行节点都把整个 State 返回，它们就会同时提交同一个字段的更新；对没有 reducer 的普通字段，
LangGraph 会因无法判断如何合并而报并发更新错误，而不是替你挑一个结果。对配置了 reducer 的字段，
返回完整旧列表还可能把已有内容重复合并进去。

这也是 LangGraph 和普通 pipeline（流水线）框架在写法上的一个重要不同。普通 pipeline 的写法
通常是：每一步接收一个完整对象，处理完再返回完整对象，交给下一步——同一时刻只有一个步骤
在改这个对象，所以返回整个对象没问题。LangGraph 的节点可以并行、可以回头重跑、每一步都要存档，
所以节点只报告“我改了什么”（增量），由框架统一决定怎么合并进 State。
正因为是增量，框架才能根据字段的合并规则处理并行分支的结果，也才能在每一步之后清楚地记下“这一步改了什么”。

打开 `graph.py`，看图长什么样：

```python
builder = StateGraph(ReleaseState)
builder.add_node("intake", nodes.intake)
...
builder.add_edge(START, "intake")
builder.add_edge("intake", "deploy_staging")
...
graph = builder.compile(checkpointer=InMemorySaver())
```

**第三件事**：图分两步——**`StateGraph` 是构建器，`compile()` 才得到可调用的对象**。
`compile()` 会做结构检查（孤立节点、缺失边），但不检查业务规则。括号里传的
`InMemorySaver()` 是最简单的 **checkpointer（存档器）**——每执行完一步，
就把当时 State 的快照存一份。它在这一步看起来是多余的，但**编译时就得传进去**。

这是框架层面的技术要求，不是业务要求：后面要用的 interrupt（让图停下来等人）
依赖存档才能恢复——图停下时，LangGraph 得先把当时的 State 存下来，人批完之后再从存档里
取出来接着跑。没有 checkpointer，图虽然也能停，但人工决定送回来时（`Command(resume=...)`）
会直接报错 `Cannot use Command(resume=...) without checkpointer`。所以现在就把它配上，
后面加 interrupt 时不用再改图的编译方式。

主线这一步没有任何"难"的东西。它的价值是：你现在得到了一张**能跑通的图**，
后面每加一个机制，都是往这张图上叠加。下一节我们叠加**第一个机制：条件路由**。

## 四、分支：变更等级路由（P2）

主线跑通了，但现实中"改一行 README"和"改 auth 模块"绝对不能走同一条路。
我们在 `intake` 之后加一步**变更分级**，根据 `patch_diff`（§二 介绍过：工单里存放
代码改动内容的字段）判定风险等级，再按等级决定走哪条审批路径。

这一步只演示**条件路由**。三个审批节点先用占位函数——函数直接返回"已通过"，
图**不会停下来等人**——真正的"暂停等人批"，放在 §6 讲人工审批那一节
（本文用 §N 表示第 N 节，§6 就是"六、中断与恢复"这一节，下文同理）
（这个行业里叫 HITL，Human-in-the-loop，人在回路：流程里专门留给人操作的位置）。
这样做是有意的：先把"分支怎么分"讲透，
再叠加"分支里要等人"这个机制，一次只学一个新概念。

### 4.3 这一步的代码里，我们讲清三件事

打开 `02_routing/graph.py`：

```python
def route_by_level(state: ReleaseState) -> Literal["L", "M", "H"]:
    return state["change_level"]

builder.add_conditional_edges("classify_change", route_by_level, {
    "L": "approval_auto_L",
    "M": "approval_lead_M",
    "H": "approval_dual_H",
})
```

先说这段代码要满足的业务需求：发布风险不同，审批强度就该不同。
改个配置文案这种 L 级变更，没必要找人批，自动放行；改动量大的 M 级，要一位 Tech Lead
（技术负责人）看过；动到登录鉴权、支付这些敏感模块的 H 级，要 Tech Lead 和安全负责人两个人都同意。
`route_by_level` 就是做这个"按等级分流"的函数：它读出上一步 `classify_change` 判好的
`change_level`，原样返回 `"L"`、`"M"` 或 `"H"`，图据此决定下一步去哪个审批节点。

**第一件事**：这一段回答的问题是——条件路由在图上是怎么配置的，
`add_conditional_edges` 的三个参数分别起什么作用。

`add_conditional_edges(source, path_fn, path_map)` 有三个参数：

- `source`（这里是 `"classify_change"`）：**分叉点**。表示"这个节点执行完之后，不是固定走一条边，而是要先做选择"。
- `path_fn`（这里是 `route_by_level`）：**选路函数**。`source` 节点执行完后，LangGraph 调用它，
  传入当前 State；它**只读 State，返回一个字符串**，代表选中的那条路。
- `path_map`（这里是那个字典）：**路名到节点名的对照表**。把 `path_fn` 返回的字符串翻译成
  真正的下一个节点名，比如返回 `"M"` 就去 `approval_lead_M`。

路由函数本身不做任何状态修改——状态变化在节点里完成。

> 这是和 if-else 工作流写法最大的差异。很多刚上手的人会想把"判定 + 改状态"放一起：
> `def route(...) -> state["approver_count"]=...`。**别这么写**。
> 路由函数的职责单一：**选择路径**。要改 state 就专门加一个节点。

**第二件事**：路由函数返回类型用 `Literal[...]` 而不是 `str`。
这不是装饰——它是给 `compile()` 和给 Mermaid 渲染器看的"图元信息"。
你用 `str` 编译能过，但可视化时分支边上的标签就丢了，调试时也别扭。

**第三件事**：三条分支路径在末端**汇合**回 `deploy_staging`。
这靠的是"每个分支节点都各自连一条 `add_edge("approval_xxx", "deploy_staging")`"。
LangGraph 不要求分支必须用某个特定汇合节点——你只要把多条边指向同一个目标，
图上就形成汇合。下一节"4 项检查的并行汇合"在概念上也是汇合，
但机制完全不同：不是多条边汇聚，而是一个 ToolNode 节点**内部**并发执行 4 个工具，
在图上只是一个普通节点。到这里别把两者混为一谈。

分支这一步就讲到这里。下一节我们把"4 项前置检查"从内联函数升级成真正的工具调用，
让它们在图上**并行执行**。

## 五、并行：ToolNode 4 路检查（P3）

到这里图和分支都有了，但"前置检查"还是节点函数里直接 `return True`。
现实中这 4 项各自要查 git、跑测试、扫依赖、调外部 API，互不依赖且耗时。
串行跑就是 4 倍时间。这种"互不依赖的子任务同时开工"的需求，
**LangGraph 给了一个现成的执行器，叫 ToolNode——你把工具清单交给它，它负责并发执行**。

### 5.3 这一步的代码里，我们讲清四件事

打开 `03_toolnode/nodes.py::intake`：

```python
def intake(state: ReleaseState) -> dict:
    fanout = AIMessage(
        content="",
        tool_calls=[
            {"name": "build_service", "args": {...}, "id": "call_build"},
            {"name": "run_unit_tests", "args": {...}, "id": "call_unit"},
            {"name": "security_scan", "args": {...}, "id": "call_scan"},
            {"name": "dependency_audit", "args": {...}, "id": "call_audit"},
        ],
    )
    return {"messages": [fanout], "stages_completed": []}
```

**第一件事**：这一段回答的问题是——"4 路并行"这个行为是从哪来的，ToolNode 靠什么知道该跑哪 4 个工具、结果又写到哪里去。
ToolNode 不看图，只看 `state["messages"]` 末尾那条 AIMessage
（LangChain 里代表"模型回复"的消息类型，里面可以携带 `tool_calls`——一张"要调用哪些工具、
各带什么参数"的清单）。所以"4 路并行"这件事，本质上由**一条 AIMessage 携带 4 个 tool_calls** 表达。
ToolNode 拿到这条消息，自动并发执行 4 个工具，把每个工具返回值包成
一条 ToolMessage（"工具执行结果"消息）追加到 messages 末尾。**这就是 ToolNode 的契约**。

打开 `03_toolnode/graph.py`：

```python
from langgraph.prebuilt import ToolNode
from tools import CHECK_TOOLS

builder.add_node("tool_checks", ToolNode(CHECK_TOOLS))
builder.add_edge("intake", "tool_checks")
builder.add_edge("tool_checks", "collect_checks")
```

**第二件事**：`ToolNode` 是一个**预先实现好的节点对象**，不是要你写函数。
注册到图上后，它**自动**做四件事：① 从 messages 拿最后 AIMessage ② 按 tool_calls
找对应工具 ③ 并发执行 ④ 把结果包成 ToolMessage 写回 messages。

打开 `03_toolnode/nodes.py::collect_checks`：

```python
def collect_checks(state: ReleaseState) -> dict:
    results: list[CheckResult] = []
    for msg in state.get("messages", []):
        if not isinstance(msg, ToolMessage):
            continue
        payload = json.loads(msg.content)
        results.append(CheckResult(...))
    return {"checks": results, "checks_passed": sum(1 for r in results if r["passed"])}
```

**第三件事**：这一段回答的问题是——为什么 `messages` 不能当成一个普通的 list 字段来声明，多出来的那层 `Annotated` 到底在管什么。
`messages` 字段必须声明成 `Annotated[list[AnyMessage], add_messages]`。
这里要解释一个新词：**reducer（合并规则）**——多个节点先后写同一个字段时，
LangGraph 不是简单后者覆盖前者，而是调用这个函数决定"新旧值怎么合并"。
`messages` 指定的合并规则是 `add_messages`，语义是**追加、并按消息 id 去重**。
如果不用这条规则，intake 写入的 AIMessage 会被后面的节点整个覆盖掉。

**第四件事（最容易出错的地方）**：这一段回答的问题是——节点往 `messages` 里写东西时，
到底是"加一条"还是"换一批"。

答案是加一条：`intake` 节点返回 `{"messages": [fanout]}`，LangGraph 会按上面的 `add_messages` 规则，
把 `fanout` 这条 AIMessage **追加到 State 里 messages 列表的末尾**，而不是用它替换掉整个列表。
所以如果后续某个节点还想再发一次 tool_calls，就要注意两点：要么给每个 tool_call 用新的、
不重复的 `id`（否则会被当成同一条消息去重）；要么先把 messages 显式清空
（`{"messages": [RemoveMessage(id=REMOVE_ALL_MESSAGES)]}`）。

我们的工程里，`collect_checks` 处理完结果后**保留**了 messages 里的全部消息，一条都不删。
原因是审计需要：事后要能查到"这张工单调用过哪些工具、每个工具返回了什么"。

到这里我们有了主线 + 分支 + 工具并行。但所有审批节点都还是占位函数。
真正的"暂停等人批"才是 LangGraph 区别于普通 DAG（有向无环图——只能往前走、不能回头）调度器的关键。下一节讲。

## 六、中断与恢复：interrupt 让人审批，Checkpoint 让进程重启后还能找回（P4）

前面三步工程里的审批节点，都是直接 `return {"approver_count": 1}` 假装"批过了"。
现实里这一步要**停下来**：把待批的 diff 摆到审批人面前，进程该退出就退出，
等审批人几小时后点了"同意"，再从**中断的那一点**继续往下跑。

这一步做三件事：① 把三个审批节点改成真正的 `interrupt()`；② 用 `Command(resume=...)`
把人给出的决定送回图里；③ 把 `InMemorySaver` 换成 **SQLite Checkpointer**，
让"暂停—退出—重启—恢复"真的能跨进程发生。

审批规则是这样的（INT-1、INT-2A、INT-2B 是我们给每个"停下来等人"的位置起的编号，
INT 是 interrupt 的缩写，方便在日志和测试里指认是哪一处在等人）：

```
M 级：  approval_m ──(停在 INT-1，等 Tech Lead)──→ 批准 → 预发部署 …
                                                  └→ 拒绝 → finalize（结束）

H 级：  approval_h_lead ──(停在 INT-2A，等 Tech Lead)──→ 批准 ─→
        approval_h_security ──(停在 INT-2B，等安全负责人)──→ 批准 → 预发部署 …
             任一处拒绝 → finalize（结束）
```

举个例子：一张 M 级工单，图跑到 `approval_m` 停下，Tech Lead 批准后才继续部署。
一张 H 级工单要停两次：第一次停在 INT-2A，Tech Lead 批准后，图往前走一步，
又停在 INT-2B 等安全负责人；两人都批准了才去部署。这就是"两段串行"——
第二个人要等第一个人批完才会收到审批请求。任何一处点了"拒绝"，
图直接跳到 `finalize` 记为被拒，后面的部署和灰度都不再执行。

### 6.3 这一步的代码里，我们讲清四件事

打开 `04_hitl/nodes.py::approval_m`：

```python
def approval_m(state: ReleaseState) -> dict:
    decision = interrupt({
        "interrupt_id": "INT-1",
        "role": "tech_lead",
        "ticket_id": state["ticket_id"],
        ...                       # 载荷里还带了 service / version，此处省略
        "diff_preview": state.get("patch_diff", "")[:300],
        "actions": ["approve", "reject"],
    })
    return {"approver_count": 1,
            "approvals": [_as_approval(decision, "INT-1", "tech_lead")]}
```

**第一件事**：这一段回答的问题是——"图停下来等人"这个动作，在代码层面到底发生了什么。
`interrupt(payload)` 会在这里**抛出一个特殊信号**让图停下，
`payload` 就是要给审批人看的、可 JSON 序列化的数据。注意 `decision = interrupt(...)`
下面那行 `return` ——**第一次执行时根本不会跑到它**。图停在节点中间，把 payload 交回宿主。
真正执行 `return` 的，是**恢复之后**——恢复时 `interrupt()` 这一行不再抛信号，而是直接返回
我们用 `Command(resume=...)` 送进来的那个人工决定，于是 `decision` 拿到值、`return` 执行、
审批结果写进 State，图接着往下一个节点走。为什么第一件事值得单独讲？因为它立住了本节
最重要的心智模型：**`interrupt()` 不是"暂停在这一行等"，而是"这一次执行到此为止，
下一次从头再来到这一行"**。记住前半句，第二件事那个"最大的坑"你就能自己推出来。

**第二件事（最大的坑）**：恢复时，LangGraph 是**从这个节点的开头重新执行整个函数**，
不是从 `interrupt()` 那一行"接着往下"。它没有保存 Python 的调用栈，只保存了 State。
所以恢复时 `approval_m` 会从头再跑一遍：重新读 state、重新构造那个 payload dict、
再次走到 `interrupt()`——这次才拿回 `decision` 继续 `return`。
由此得到一条很绝对的规矩：**`interrupt()` 之前绝不能放任何有副作用的操作**（写文件、发请求、扣款、真正应用补丁）。
否则每次 resume 都会把副作用重复执行一次。我们的补丁生成放在**前一个节点**、审批节点只负责
"展示 + 收决定"、写入放在**后一个受控节点**，正是为了守住这条。
（对到我们的代码上：改动内容 `patch_diff` 在 `submit` 入口就写进了 State，`intake`、`classify_change`
这些前序节点只是读它做校验和分级，不对外部世界做任何事；`approval_m` 只展示 diff 摘要、收回人工决定；
真正改动外部系统的操作（部署新版本、切流量、写报告文件）都排在审批通过之后的节点里。）

打开 `04_hitl/checkpointer.py`：

```python
@contextmanager
def open_checkpointer():
    db_path = Path(os.environ.get("CHECKPOINT_DB", "./checkpoints_04.sqlite")).resolve()
    db_path.parent.mkdir(parents=True, exist_ok=True)
    with SqliteSaver.from_conn_string(str(db_path)) as saver:
        yield saver
```

**第三件事**：要让 `interrupt()` 生效，`compile()` 时必须传 checkpointer，调用时必须带
`thread_id`。

先澄清一个容易误会的名字：`thread_id` **不是操作系统里的线程**，和多线程编程没有关系。
它是 LangGraph 给"一次独立任务"起的编号，相当于存档的文件名——同一个 `thread_id` 下的
所有存档属于同一次任务，不同 `thread_id` 之间互不干扰。我们的工程直接拿工单号当 `thread_id`，
一张工单就是一次任务。

`submit` 用 `thread_id="T-042"` 把状态写进
SQLite 文件；换一个进程重新 `open_checkpointer()` 打开**同一个文件**、再拿**同一个
`thread_id`** 去 `get_state()`，就找回了"当时停在哪个节点、待批内容是什么"。
`thread_id` 只是查找键，**不是权限**——谁能 approve、批的是哪一版补丁，仍要在入口自己校验。

打开 `04_hitl/app.py::approve`：

```python

if not snap.next:
    print("该工单没在等待审批。")
    return
graph.invoke(
    Command(resume={"action": action, "actor": actor, "feedback": feedback}),
    config=cfg,

```

接着第一件事往下说，这段回答的问题是：图停了，人工的决定要从哪里、怎么送回去。
看 `approve` 子命令的实现——恢复用的是 `Command(resume=...)`，而不是把原始任务消息再提交一遍。这段必须写在
"收到人工决定"的入口里，**不能紧跟 submit 自动批准**——否则就等于没人真的看过补丁。

**第四件事**：`approvals` 用了 `add` reducer，所以每个审批节点只返回**自己这一条**，
LangGraph 负责把它们**累加**进列表。这带来两个好处：① H 级两段审批各写一条，
最后 `approvals` 自然留下完整审计轨迹（谁、批了哪一步、approve 还是 reject、说了什么）；
② `route_after_approval`（§6.1 提示词里定义的"审批通过后往哪走"的路由函数）直接 `any(a["action"] == "reject" for a in approvals)` 就能判断
"链路里是否已有人否决"，任一 reject 立刻把流程短路到 `finalize`，后面的灰度阶段一个都不跑
（AC-5 验证的就是这条：reject 后 `stages_completed == []`）。

到这一步，我们的图第一次具备了"停下来等人、并且换个进程还能接着跑"的能力。
但发布流水线还差最后一块：灰度阶段发现指标恶化时要能**退回上一步重来**，
审批被打回时要能**回到修订**——这就是循环。下一节讲。

## 七、循环与预算：条件边指回更早的节点，计数兜底防打转（P5）

前面的图，路径整体是"往 END 走"。这一节我们**故意把一条边指回更早的节点**，
让流程能绕回去重跑——这就是循环。但循环最危险的地方是"绕回去出不来"，
所以每个循环都必须配一个**预算计数**：转够了就强制收尾。

这一步加两处循环：

- **循环 A（修订）**：审批人除了 approve / reject，多了 `revise`（打回修订）。
  选 revise → `begin_revision` 把 `revision_count + 1` → 一条普通边退回 `intake`，
  整条检查—分级—审批链路重跑。`revision_count` 触顶则路由判 `stop`，终止并记为 `incomplete`。
- **循环 B（灰度回滚）**：每个灰度阶段部署后拉一次指标。阶段不健康 → `auto_rollback`
  把 `rollback_count + 1`、游标回退 → 条件边退回 `canary_step` 重跑**同一阶段**。
  `rollback_count` 触顶则 `abort`，终止并记为 `rolled_back`。

### 7.3 这一步的代码里，我们讲清四件事

打开 `05_loops/graph.py`：

```python
b.add_edge("begin_revision", "intake")          # 循环 A：普通边指回更早的节点

b.add_conditional_edges("monitor_window", route_after_monitor, {
```

**第一件事**：LangGraph 的循环不需要任何"loop 专用 API"。
`add_edge("begin_revision", "intake")` 就是一条**指向已经走过的节点**的普通边。
图执行时不禁止回边——它只是照着边一步步调度。真正让它"能转"的是：**节点写状态，
路由读状态**，每一圈 `revision_count` 变大，路由函数就能在合适的时机不再选回边。

**第二件事（最关键）**：没有预算上限的循环 = 死循环。
所以每个循环都配一个计数和一个判 `>= max` 的兜底路由：

```python
def route_approval(state: ReleaseState) -> Literal["approve","revise","reject","stop"]:
    last = state.get("approvals", [{}])[-1].get("action")
    if last == "approve": return "approve"
    if last in ("reject", "abort"): return "reject"
    if state["revision_count"] >= state["max_revisions"]:
        return "stop"          # 预算耗尽 → finalize，不再 revise
    return "revise"
```

LangGraph 自身也有一个图执行步数上限（`recursion_limit`）当**安全阀**，
但触发它是抛 `GraphRecursionError`（运行错误），不是"正常收尾"。
业务上"修订 2 次没通过就返回 incomplete"必须**我们自己写成路由**，
不能指望 `recursion_limit` 替你做这个决定。

打开 `05_loops/nodes.py::canary_step`：

```python
def canary_step(state: ReleaseState) -> dict:
    cursor = state["canary_cursor"] + 1        # ← 先算，但不提交
    stage = STAGE_BY_CURSOR[cursor]
    decision = interrupt({"interrupt_id": f"INT-3-{stage}", "role": "sre", ...})
    ...
    return {"canary_cursor": cursor, ...}      # ← 只有 return 时 cursor 才写进 State
```

**第三件事（interrupt 在循环里的坑）**：`canary_step` 就是本节开头看过的那个灰度推进节点——每推进一档都先停下等 SRE 确认——它里面也有一次 `interrupt()`。
而 §6 说过——恢复时节点**从头重跑**。那么 `cursor = canary_cursor + 1` 会不会每恢复一次就 +1，
导致灰度"跳级"？不会。因为 `cursor` 只是个**局部变量**，只有节点 `return` 时才写回 State。
恢复重跑时读到的 `state["canary_cursor"]` 仍是暂停前的旧值，于是**重算得到同一个 cursor**。
这条成立的**前提**是：`interrupt()` 之前没有任何**对外部世界的副作用**（真正部署、写文件）。
我们的 `deploy` 调用放在审批通过之后，回退重跑同阶段时才真正部署一次。一旦把副作用挪到
`interrupt()` 之前，这个循环立刻会"每恢复一次就重复执行一次"——这就是 §6 第二件事
（恢复时节点从头重跑）放进循环场景后的自然延伸。

**第四件事**：回滚为什么能让"同一阶段"重跑，而不是从 10% 重新开始？
先解释 `canary_cursor` 这个字段——它是"灰度游标"，记录当前推进到第几档：
1 = 10%，2 = 50%，3 = 100%。`auto_rollback` 把游标**减 1**，于是下一圈 `canary_step` 又 `+1`
算回**同一个** stage；`stages_completed` 里追加一条 `rolled_back:canary_10` 留痕。
灰度游标 + 回滚计数这两个数字配合，就实现了"原地重试当前灰度档位，最多 N 次，超了就中止"。

到这里，主线 + 分支 + 并行 + 中断 + 循环全部就位。`release_pipeline` 该有的控制流都有了。
可代码一旦长到这个规模，"看图、看每步 state 怎么变"就成了新问题。最后一节我们讲调试与可视化。

## 九、三个实际遇到的工程问题：现象、原因和处理方法

这一节不加新机制，只把做这个工程时实际遇到的三个问题讲清楚。每个问题按同一个顺序说：
先说问题是什么，再说它为什么发生，最后说怎样避免。

### 问题一：恢复时，审批节点会从头再执行

**问题是什么？** 图在 `interrupt()` 处停下后，收到人工决定恢复时，包含 `interrupt()` 的节点函数会从头再执行，
不是从暂停的那一行接着执行。若暂停前已经发请求、部署、写文件或扣款，恢复时这些动作可能再次发生。

**为什么会发生？** LangGraph 保存的是 State 和执行检查点，不是 Python 函数的调用栈。
所以恢复时，它重新调用整个节点函数；State 可以恢复，外部系统已经发生的变化不会自动撤销。

我们在 §七 看过 `canary_step`：`cursor = canary_cursor + 1` 只是局部计算，只有节点返回时才写进 State。
所以暂停后重跑会从相同的旧游标重新算出同一档，不会跳级。危险的是把部署等外部操作放在 `interrupt()` 前面——
它们不会因为节点重跑而自动“撤回”，可能被重复执行。

**怎样避免？** 把有外部副作用的操作放到审批通过后的独立节点；对无法避免重试的外部请求，使用幂等键，
让同一业务操作重复提交也只生效一次。可以在教学环境里于 `interrupt()` 前加 `print` 做观察，
但生产代码不能把“多执行几次也没关系”当作副作用安全策略。

给新人的话：**恢复会重跑代码，不会替你撤销已经发生的外部操作。** 每次写到中断点前，都检查一遍是否已经改了外部系统。

### 问题二：复用旧 checkpoint 会污染测试

**问题是什么？** 带持久化的测试，单独运行可能通过，重复运行或和其他测试一起运行时却出现状态不符合预期。
例如，我们曾看到低风险发布测试中的 `canary_cursor` 停在 1，而预期是 3（1、2、3 分别代表灰度 10%、50%、100%）。

**为什么会发生？** Checkpointer 会把执行状态按 `thread_id` 保存到 SQLite。若测试复用同一个数据库文件和同一个 `thread_id`，
上一轮留下的 checkpoint 可能被下一轮读到；测试以为自己从空白状态开始，实际上读到了旧数据。
问题不是“SQLite 自动把所有调用都续跑”，而是测试没有隔离它所依赖的持久化状态。

**怎样避免？** 每个测试会话使用干净的 checkpoint 数据库，并为不同用例使用不同的 `thread_id`；
在本工程中，`tests/test_acceptance.py` 的 session fixture 会在测试开始前清理 checkpoint 文件和旧报告。
也可以为每次运行使用独立的临时数据库。不要靠手工删库才能让测试变绿，要把隔离方式写进测试设置。

给新人的话：**测试不仅要准备输入，也要准备干净的持久化状态。** 只要测试碰到 checkpoint、缓存或数据库，就要明确它们何时清理、如何隔离。

### 问题三：异步节点里执行阻塞 I/O，会卡住事件循环

**问题是什么？** 命令行测试看似正常，接入 `langgraph dev` 后，`finalize` 写报告时却被 `blockbuster` 报错拦截。
出问题的操作是创建目录和同步写文件（`os.mkdir`、`Path.write_text`）。

**为什么会发生？** `async def` 节点运行在异步事件循环中；同步文件 I/O 会占住当前线程，直到操作完成。
本地短命令里这个阻塞可能不明显，但服务运行时，同一个事件循环还要处理其他请求，阻塞会让它们一起等待。
`langgraph dev` 启用了 `blockbuster` 检测这类用法，所以把问题明确报了出来。

**怎样避免？** 对这种短小的同步文件操作，把节点定义为普通 `def`，LangGraph 会在线程池里运行同步节点；
如果节点必须保持异步，就改用对应的异步 I/O。并在命令行、测试和实际服务运行方式下分别验证。
本工程的 `finalize` 已改为同步函数，详细设计文档也同步更新了签名。

给新人的话：**函数写成 `async def`，不代表函数体里的操作自动变成异步。** 检查异步代码时，逐项确认里面调用的 I/O 是否也不会阻塞事件循环。

## 本章小结：把业务流程变成可执行、可恢复的图

这一章从一条简单的发布主线开始，逐步加上条件分支、ToolNode 并行、人工审批与 Checkpoint、带预算的循环，
最后用 Mermaid、流式事件和状态快照观察流程。记住这几条主线：

1. **State 保存流程共享的数据；节点完成一项工作并返回要更新的字段；边决定下一步去哪。**
2. **条件路由负责选路径，节点负责执行工作。** 先把业务规则想清楚，再把它们映射到图的节点和边。
3. **并行更新和列表累加要明确合并规则。** 像 `messages`、审批记录这样的列表字段，要用合适的 reducer。
4. **`interrupt()` 让流程等待人工决定，Checkpoint 保存流程状态供之后恢复。** 人工决定通过 `Command(resume=...)` 送回去；恢复时节点会从头重跑。
5. **循环要有明确的业务上限。** `recursion_limit` 是防止图执行无限延长的安全限制，不能替代“最多修订几次”这样的业务规则。
6. **运行通过不等于工程可靠。** 还要检查副作用是否会重放、测试状态是否隔离、运行环境里的异步 I/O 是否正确。

六个演示目录按顺序各增加一个主要机制，顶层 `release_pipeline/` 则把这些机制合成完整案例。
复现时从 `demos/01_minimal/` 开始，每一步单独运行对应测试，再观察节点更新和检查点；
最终要能说清楚：这张图为什么这样分支、在哪里等待人工、状态怎样恢复，以及异常时如何安全结束。

## 收尾：哪些工作由 AI 辅助，哪些必须由工程师把关

提示词可以帮助生成 `state.py`、节点、图装配和测试的初稿，但系统边界、验收标准和运行结果仍需要工程师确认：

1. **明确边界**：有哪些 State 字段、节点和工具，哪些事情明确不做。
2. **定义验收标准**：逐条核实 AC 是否覆盖业务规则和拒绝、超限等边界情况。
3. **检查持久化测试**：确保 checkpoint、数据库和报告目录的起点干净，避免旧状态影响断言。
4. **审查中断前后的副作用**：确认恢复重跑时不会重复部署、发消息或提交其他外部操作。
5. **验证实际运行形态**：除了本地命令和 pytest，也要验证服务或 Studio 环境中的运行行为。

AI 可以协助把明确的流程结构写成代码；流程结构是否正确、异常时是否安全、运行结果是否符合预期，
仍要由工程师负责验证。
