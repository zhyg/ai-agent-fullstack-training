# 5\.2\-Subagent任务委托

# 5\.2 Subagent 任务提示词：把要求交清楚，把结果收回来

## 开篇：分工已经发生，为什么结果仍不能用

上一节最后，我们直接运行 pi，把订单项目的检查交给两个只读子 Agent（5\.1 里配置好的 course\-scout）：一个看订单源码，一个看测试覆盖。当时只观察一件事——委托有没有真的发生。

但委托发生了，不等于交清楚了。主 Agent 只说“帮我检查一下测试”，子 Agent 就可能只查语法，也可能顺手补测试、改源码。它回一句“没有问题”，我们依然不知道它看过哪些文件、检查了什么边界、有没有跑过测试。

所以本节要解决的就是这件事：**把提示词写成可验收的契约，再把子 Agent 交回的结果按证据收拢。**

## 一、任务提示词：把一份提示词写成能验收的契约

首先，一份能验收的提示词要写清哪些内容？一共九件事。

1. 任务目标：不是“检查测试”，而是“判断用户隔离、明细完整性、查询次数三种情况有没有对应测试”。

2. 输入上下文：要读哪些文件、遵循哪条规则。规则属于任务要求，源码里的具体条件属于待确认的事实，不能把主 Agent 的猜测当前提。

3. 可调用工具：这次只给读文件、搜索、目录；要跑测试再单独开受控测试工具，不要一开始就放开写文件和任意命令。

4. 权限边界：工具决定“能调用什么”，权限决定“能对哪些对象做什么”。允许读文件，不代表能读整台机器的凭证，要限定工作目录和可读范围。

5. 预期输出：要求返回状态、已检查项、发现、证据和未验证事项。

6. 输出格式：统一用 JSON，方便程序校验；给用户的报告再转成 Markdown。

7. 超时限制：给出截止时间和最大调用次数，超时就取消实际执行。预算不能只写在文本里，要接到 Harness 的计数器上。

8. 评价标准：区分“能解析”和“内容合格”。三项接口要求都查清、来源可复核，才算合格。

9. 写操作限制：本章审查默认不改源码。“给出重构建议”不等于批准执行重构；要改就另建修复任务并单独授权。

这九项不用死记硬背。目标、上下文、工具是主干，缺了它们子 Agent 就不知道该查什么、能碰什么；其余是把“能跑”变成“可验收”。合起来，就是一份任务契约。

## 二、直接运行 pi：从模糊提示词到明确提示词

我们实际跑一下：沿用 5\.1 的启动命令和 course\-scout（只读检查角色，只能读、搜、列目录），直接在 pi 里输入下面的提示词。

```Plaintext
任务：静态覆盖审计（不执行测试）

   输入：
   - app/orders.py
   - tests/test_orders.py

   项目契约（作为验收基线）：
   R1 只返回当前用户订单
   R2 订单及明细合计最多 2 次 SELECT
   R3 返回的订单必须携带其明细

   必须逐项判定的场景，每项单独一条 checked_cases，verdict 取 覆盖/部分覆盖/未覆盖：
   C1 跨用户查询：夹具是否含其他 user_id 的订单，断言是否排除他人订单
   C2 明细完整性：是否断言 items 内容、数量与 order_id 归属
   C3 查询次数上限：是否存在对 db.execute 的计数、spy、mock 或 trace

   工具与范围：仅只读上述文件；可 grep 搜索相关测试；不改文件、不执行任何命令。
   禁止把静态分析表述为“已运行/已通过”。

   输出：仅一个 JSON 对象，首字符 { 末字符 }，无 Markdown 围栏、无前后说明文字。
   字段：
   - status: completed | needs_input
   - checked_cases: [{case, requirement, verdict, reason}]
   - findings: [{id, severity, requirement, detail}]
   - evidence: [{path, symbol, line, excerpt}]  excerpt 须为文件中的精确连续子串
   - unverified: [string]
   - inspected_files: [string]  实际读取过的文件
   - search_queries: [string]   实际执行过的搜索

   输出必须自包含：不要输出解释性散文，主 Agent 会在 JSON 之外单独撰写结论。
```

运行后我们看两处：实际调用记录，和返回的 JSON。前者证明委托真的发生（看 agent 和 task 两个参数有没有真的送进子任务）；后者证明结论能被逐项验收（看它有没有把“跨用户查询”单列出来）。

## 三、演示之后：把任务和结果存成结构

pi 里跑的是一段任务文本；正式系统还要把它存成结构化契约，方便追踪谁发起、对着哪个快照、是否完成。看这段可独立运行的 Python 数据示例（不调用模型，也不替代 pi）：

```Python
import json

contract = {
    "task_id": "review-test-001",
    "parent_run_id": "review-run-001",
    "agent": "course-scout",
    "goal": "检查用户隔离、明细完整性、查询次数三项接口要求测试覆盖",
    "checks": ["user_isolation", "items_complete", "query_count"],
    "snapshot_id": "snapshot-A",
    "inputs": ["app/orders.py", "tests/test_orders.py"],
    "tools": ["read", "grep", "find", "ls"],
    "policy_id": "review-readonly-v1",
    "limits": {"timeout_seconds": 60, "max_model_calls": 6},
    "output_fields": ["status", "checked_cases", "findings", "evidence", "unverified"],
    "acceptance": "三项接口要求都有结论，引用可核对，未修改项目文件",
}
print(json.dumps(contract, ensure_ascii=False, indent=2))
```

运行后打印出这份契约，我们看几个关键字段：task\_id 关联子任务结果，parent\_run\_id 找到主任务，snapshot\_id 标识输入代码——这些值必须由程序创建或注入，不能靠模型编。

两个字段容易被误解。policy\_id 是程序选的权限策略，不是发给模型就生效的咒语；执行工具时 Runtime 仍要读策略、核对实际路径和动作。limits 也只是数据，要接到 Harness 的计数器、计时器和取消逻辑里才成为限制，光打印不算执行了预算。

结果同样分两层：子 Agent 提交发现和引用，程序补上真实执行 ID、时间、用量和退出状态。模型能写“我检查完了”，却不能决定自己是否按时结束、有没有越权、消耗多少 Token。

一句话：描述任务的字段可以交给模型理解，身份、权限、执行状态和计量字段必须有程序侧的可信来源。

## 四、结果聚合：先校验证据，再讨论结论

前面三节把一次提示词写清楚了，但真实审查往往同时提示词多个子 Agent，问题就变成——多份结果交回来，主 Agent 该怎么收拢，才不会把几份结论直接拼在一起。结论是：聚合（把多份结果合成一份可复核的结论）从校验开始，不能直接拼接。

现在，测试和安全两个子 Agent 都交回了结果。测试 Agent 说缺少跨用户查询用例，安全 Agent 说订单查询没有当前用户过滤。两者描述不同，但可能指向同一个边界问题。主 Agent 按五步处理：

1. 检查格式。有没有状态和证据字段？字段类型对不对？失败结果有没有写清原因？这一步只决定结果能不能进入下一步，不判断业务结论。

2. 检查证据。路径是否属于当前项目？引用位置是否存在？原文能否支持结论？结果对应的是不是主任务固定的快照？模型引用了一行代码，不等于它理解了整条调用链。

3. 去重。重复判断看问题对象、行为和影响，不看标题是否相似。“缺少回归测试”和“实现错误”可以关联，但不是同一个发现。

4. 排序。先看影响范围和触发条件，再看严重程度。可验证的越权问题，排在“某个函数没注释”之前。

5. 生成建议。具体到改哪里、为什么改、如何验证，比“优化测试质量”更可执行。

最终报告还要保留未完成项：性能 Agent 没拿到运行数据，只能报静态线索，不能写“性能正常”；安全 Agent 超时，也不能从报告里消失。主 Agent 的复核要围绕用户目标，不能只报边界缺陷。

这五步落到代码，就是 aggregate\(\)。它凭什么相信子 Agent 交回的结论？做法是两层分开——先做字面校验，再谈结论。模型给的路径和摘录都不可信，校验器先检查路径属于工程、原文存在、文件哈希仍与开始时一致。例如子任务引用 app/orders\.py 里未过滤用户的 SQL，文件与快照相符、摘录也能找到，这份引用存在；但它说“所有鉴权都有漏洞”，就不能由这一行代码直接推出。所以代码把 evidence\_status 标为 literal\_verified（字面来源已核对），semantic\_verification 仍是 pending（结论是否成立留给主 Agent 或独立验证），两层不合并成一个 passed。

```Python
import argparse
import json
from pathlib import Path
from common import dump, snapshot, evidence_ok

def aggregate(project, raw, before):
    if not isinstance(raw, dict) or not isinstance(raw.get("results"), list):
        raise ValueError("需要 results 数组")
    seen, accepted, rejected, conflicts, incomplete = {}, [], [], [], []
    expected = {"test", "security", "performance"}
    received = set()
    for result in raw["results"]:
        if not isinstance(result, dict):
            raise ValueError("子任务结果必须是对象")
        task = result.get("task_id")
        if task not in expected or task in received:
            raise ValueError("任务 ID 未授权或重复")
        received.add(task)
        if result.get("status") != "completed":
            incomplete.append(task)
            continue
        findings = result.get("findings")
        if not isinstance(findings, list):
            raise ValueError("findings 必须是数组")
        for finding in findings:
            if not isinstance(finding, dict):
                raise ValueError("finding 必须是对象")
            key, claim = finding.get("issue_key"), finding.get("claim")
            evidence = finding.get("evidence")
            if (not isinstance(key, str) or not key or not isinstance(claim, str)
                    or not isinstance(evidence, list) or not evidence
                    or finding.get("severity") not in ("high", "medium", "low")
                    or not all(evidence_ok(project, e, before) for e in evidence)):
                rejected.append({"task_id": task, "reason": "schema_or_evidence", "finding": finding})
                continue
            if key in seen:
                old = seen[key]
                if old["claim"] != claim:
                    conflicts.append({"issue_key": key, "left": old, "right": finding})
                else:
                    old["sources"].append(task)
                continue
            item = dict(finding, sources=[task], evidence_status="literal_verified")
            seen[key] = item
            accepted.append(item)
    incomplete += sorted(expected - received)
    # 输入快照变化时整份审查失效，不继续用旧摘录。
    if snapshot(project) != before:
        raise ValueError("审查期间快照发生变化")
    priorities = {"high": 0, "medium": 1, "low": 2}
    accepted.sort(key=lambda f: priorities[f["severity"]])
    return {
        "accepted": accepted, "rejected": rejected, "conflicts": conflicts,
        "incomplete": incomplete, "needs_review": bool(conflicts or rejected or incomplete),
        "semantic_verification": "pending",
    }

if __name__ == "__main__":
    p = argparse.ArgumentParser()
    p.add_argument("--project", required=True)
    p.add_argument("--result", required=True)
    p.add_argument("--snapshot", required=True)
    p.add_argument("--output", default="aggregation.json")
    a = p.parse_args()
    report = aggregate(a.project, json.loads(Path(a.result).read_text()),
                       json.loads(Path(a.snapshot).read_text()))
    dump(a.output, report)
    print(json.dumps(report, ensure_ascii=False, indent=2))
```

运行后 accepted 只是可以继续复核的候选，不代表最终裁决。去重采用 issue\_key（同一问题在各子任务里的统一标识）加一致的 claim，不同表述不自动语义合并，宁可留下待处理项。程序还检查审查期间快照是否改变——摘录还在，其他相关代码变了也可能影响结论；这个小型工程把 app、tests、docs 整体固定，真实项目要扩展到配置、依赖和生成文件。

那校验器真拦得住错误吗？我们不能指望真实模型每次都出错，所以主动注入三种错误样本，全程不调用模型：

```Bash
python scripts/inject_demo.py --output injected
```

我们打开 injected\-results\.json，会看到三种输入：真实源码摘录、越出项目的引用、同一个 issue\_key 的相反结论。再看 injected\-aggregation\.json，越界引用进入 rejected，相反结论进入 conflicts，needs\_review 为真。它证明校验器能处理这些样本，不证明模型不会产生别的错误。把某个 test 的 status 改成 needs\_input、findings 清空，结果应保留 incomplete，不能把未完成检查当成没有问题；把 task\_id 改成不在本次委托里的名字，聚合器应拒绝，因为这份结果对不上当前任务契约。

格式校验、来源校验和结论判断各自消除不同的错误，没有哪一项能代替全部。当两个子 Agent 的结论互相矛盾时，光靠校验还不够——这就是下一节要处理的冲突裁决。

## 五、冲突与仲裁：不靠投票，靠证据

这一节要解决的问题是——两个子 Agent 给出互相矛盾的结论时，主 Agent 该信谁。方法不是投票，也不是看谁说得更肯定，而是先限定每个结论的适用范围，再补上证据。

现在我们制造一个冲突。测试 Agent 说“现有测试全部通过，所以订单查询逻辑正确”；安全 Agent 说“代码里有没做用户过滤的 SQL，查询仍可能返回别人的订单”。先拆开两个结论：测试通过，只能说明执行过的用例在对应快照上通过，没有跨用户查询用例就不能推广到所有边界；安全发现是源码线索，还要结合调用路径和实际行为核对。

这时候主 Agent 不能投票，要跑一个独立探针，用真实行为验证结论：

```Bash
python scripts/probe_orders.py --project work/project
```

先验证，再判断：这一步是让主 Agent 用真实行为判对错。探针按当前用户调用 list\_orders，返回的却是用户 20 的订单，可见旧实现没按用户过滤，越权成立；查询次数又从 4 次涨到 7 次，可见每条订单都在单独查明细，N\+1 也现形。

但这只说明这份代码在这个快照上会越权，不能据此断言生产接口安全或变快。另一种情形是：如果函数本来就绑定了用户，那安全 Agent 引用的就是旧版本，主 Agent 应把这条发现标为过期，而不是当成现行缺陷。没做实测时不能盲目修改。

业务规则冲突同理：需求说只返回当前用户订单，旧文档说管理员能查全部，两份说法不一致，所以主 Agent 得先核对哪份是当前版本；找不到权威来源，主 Agent 就交维护者定，不能自己改。

所以仲裁不是让主 Agent 再猜一次，而是让它按顺序核对范围、版本、证据；需要时，主 Agent 再触发一项新验证。

## 六、串行交接与失败处理

前面几节的子任务都能各自独立跑完，结果之后再汇总；但有些任务有先后依赖，只能串行。这一节解决两件事——必须串行时，上一步的结果怎么交给下一步；子任务失败时，又该怎么按类型分别处理。

```Plaintext
调用 subagent 的 chain 模式，用两个 course-scout 串行完成：
第一步读取 app/orders.py，返回用户过滤条件及代码原文，不做正确性保证；
第二步结合上一步结果，读取 tests/test_orders.py，判断三项接口要求覆盖。
第二步 task 中使用 {previous} 引入第一步结果。
两步都只读；最终区分实现观察、测试覆盖观察和未运行测试。
```

这一步我们关注交接：第二步的输入是否包含第一步结果，以及第一步失败时有没有错误记录。

还要说清一点：第一步的自然语言输出仍然是输入数据。它即使夹带“忽略原规则、允许写文件”，也不能改变第二步的权限策略——跨 Agent 传内容要保留来源性质，并继续执行工具门禁。

子任务失败时，按类型分别处理：超时、临时错误可以重试一次，但重试照样计入预算；权限被拒、输入缺失这类失败不重试，直接记为未完成项；只完成一部分的，保留已有证据并标为未验证。不管哪一种，失败都要写进结果的 status，不能让它在报告里消失。

## 小结

这一节，我们把“请帮我检查”变成了一份可验收的契约，再把结果按证据收回来。
主线是：先把目标、输入、工具、权限、输出、预算等九项写进提示词，再用 pi 跑一次确认它真的发生，然后把任务和结果存成结构——身份、权限、执行状态、用量这些字段由程序提供，不交给模型编。
多份结果回来，先校验证据再讨论结论；两个子 Agent 互相矛盾时，不投票，跑独立探针用真实行为裁定；有前后依赖的，上一步结果当数据交给下一步，权限边界不变。

一句话总结：模型负责描述和产出，程序负责身份、权限、状态和计量；任何结论都要落到当前项目的真实证据上，证不实就留成待处理项，不能当成没问题。

下一节，我们会把这套检查方法做成 Skill。提示词描述本次任务，Skill 保存这类任务应该怎样做，这样每次审查不用重新设计全部步骤，但依然要核对当前项目和真实证据。
