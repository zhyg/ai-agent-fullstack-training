# 5\.5 项目演进路线 阶段五：Multi\-Agent \& Evaluation



**项目背景：** 掌握了单 Agent 构建能力后，需要将其升级为可协作、可评测、可迭代的多 Agent 平台，建立 Agent 质量保障体系。



## 一、引言

前面我们已经把单 Agent 的基本能力搭起来了。接下来要做的是让 Agent 能分工、能验收、能留下证据，最后形成一套质量保障机制。

这一节课，我会继续沿用前面做好的 Codebase Agent，带大家完成一次更接近真实工作的软件交付。前面讲过的概念和基本操作，这一节不再单独演示，本节直接放进完整项目里用起来。



这一节课主要解决三个实际问题。

第一，公共 Skills，加上我在项目里沉淀的软件交付 Skills，怎么一起接进项目工作流。

第二，怎么通过 subagent 把一份大任务拆给不同角色的 Agent，让它们分别负责检查、产出和交接，再由主 Agent 汇总信息、做最后决策。

第三，怎么把上一节讲过的评测方法，结合这套 Skills 和多 Agent 协作，真正做成一个可以操作、可以复盘、可以留证据的 Eval Web 平台。



接下来始终围绕这个平台展开。它需要管理题目，调用现有的 Codebase Agent 运行任务，保留模型消息、工具调用、审计记录和评分结果，还要支持查看统计、失败聚类，以及不同版本之间的回归对比。

我们先把公共 Skills 接进来，看看别人总结出来的方法，怎么直接帮助我们检查计划和代码。然后再接入我自己的软件交付 Skills，把需求、设计、开发、测试、验收这条链路真正串起来。最后再把 subagent 接进来，按角色分工，实际组织这个 Eval 平台的开发和审查流程。



等这一轮做完，我们手里拿到的就不只是几段提示词，而是一套能启动、能运行、能回查记录、也能明确说明哪些检查已经通过、哪些还没通过的项目交付结果。

## 二、找对入口

动手之前，先打开 `codebase/src/cli.ts`。

这次重点看两条 Agent 启动路径。不带子命令时，启动 pi 的交互界面；带`agent` 子命令时，调用项目封装的`runManagedAgent()` 。

本节先在 pi 交互入口接 Skills 和 subagent。后面开发 Eval 平台时，再通过 worker 调用现有的受治理运行入口。这里要分清楚：我们用多 Agent 协作开发平台，平台运行评测任务时，复用的是现有 Codebase Agent。



先把这几个文件连起来看：

|文件|具体看什么|
|---|---|
|`src/cli.ts`|pi 怎样启动，配置路径和工作仓库怎样传过去|
|`src/pi/coding-agent-extension.ts`|项目工具怎样注册给 pi，每次调用怎样交给 Runtime，预算检查和审批怎样接进交互流程|

## 三、公共 Skills：把专家经验放进工作的关键步骤

### 3\.1 开始工作之前：先验证计划

我们的主要任务是“开发一个 Eval Web 平台”。如果直接让 Agent 写页面，通常很快就能看到界面，但关键规则可能还没有定义。

比如，模型回答结束是不是就算通过？取消实验以后，本地 worker 停了没有？已经发给模型供应商的请求，是否还能继续产生费用？两条策略是不是用了相同的题目和源码？这些问题如果留到最后处理，前后端都可能返工。

所以，开始工作之前，我会先做三件事：追问方案、安全审计、核实接口。





**先用 ****`/grill-me`**** 追问计划。**

我先给它准备采用的方案，让它问那些会改变方案的问题。比如，第一版真的需要分布式队列吗？能不能先用本地单体？为什么要重新写 Agent Loop？现有 Runtime 能否直接调用？

我的经验是，让它围绕当前方案问具体问题，一次处理一个关键分歧。问题有了结论，就更新方案；现有材料不能确定的，就列为需要调查的事项。



**再用 ****`/audit-ticket`**** ****安全审计。**

`audit-skill` ，做的是安全审计，明确要求检查目标、范围和验收条件。



我会这样给任务：

```Plaintext
/skill:audit-ticket
检查这份 Eval 平台需求是否可以进入开发。
平台用于评测现有 Codebase 的只读源码审查能力。
检查题库、策略、实验、Trace、评分和回归报告是否都有验收条件。
重点找出“完成”“通过”“未知”、取消和费用统计里的歧义。
逐项给出缺口、影响和建议补充的内容。
```

拿到结果以后，我会把真正影响实现的缺口补进需求。比如把“展示运行结果”，改成“分别展示执行状态和验收结论”。这样后面的接口和页面才有明确字段。



**最后用 ****`/deep-research`**** 核实不确定的接口。**

我会让 Agent 先读当前安装包的文档和源码，再给出实现位置和适配建议。输出要能回答“应该改哪个文件、调用哪个接口、还有哪处没有证据”。

如果本地材料不足，再使用 Deep Research 这套调研技能补充外部资料。外部资料也要核对版本，不能拿最新版接口直接套到旧的安装包上。



这三件事不必每次完整跑一遍。需求不清楚，先检查需求；方案存在争议，再追问；接口不确定，再做调查。选择取决于眼前哪一个问题会导致返工。



### 3\.2 提交 PR 之前：先查风险，再查实现，最后收敛代码

平台写出第一版以后，我不会只看页面能不能打开。

先用 **`/security-review`** 看这次变更的边界：服务是否只监听本机，凭据是否留在服务端，Agent 是否仍然只读，源码快照会不会把秘密和参考答案带进去。

给它具体 diff 和相关入口，比一句“全面检查安全”更容易找到可以核对的问题。



接着用 **`/code-review`**** 或 ****`/ultrareview`** 检查实现。

改一个表单字段，先做范围明确的 code\-review。像这次同时涉及 Python、Node worker、前端和评分规则的改造，可以用 ultrareview 组织多个方向检查。

我会特别看：页面显示的状态，是否和后端实际判定一致；程序检查失败以后，人工评分能不能误把它覆盖成通过；worker 超时以后，本地进程有没有退出；取消或超时以后，费用是否被错误地记成零。



最后才用 **`/simplify`** 收敛重复逻辑。

比如前端多个页面都在自己计算成功率，就考虑统一使用 API 返回的统计；多个地方重复判断运行状态，就提取公共逻辑。整理以后，再执行同一组测试，确认状态、错误处理和计价行为没有变化。

这一步的目标是让后续修改更容易。先拿到可工作的实现和验证结果，再整理代码，通常更容易判断哪些逻辑可以合并。



### 3\.3 收到 PR 评论后：逐条处理，给出对应证据

收到评论以后，我会把评论和对应 diff 一起交给 **`/address-pr-comments`**。

先核实评论是否成立，再决定是否修改。评论是需要验证的问题，不是拿到以后就照着改的指令。

比如评论指出：“人工评审不能覆盖程序检查失败。”我会要求它定位当前判定逻辑。如果问题成立，就修改实现、增加对应回归，再给出修改位置和实际结果。如果代码已经拦住了这种情况，也要引用源码和测试说明，而不是为了回应评论再改一遍。



每条评论处理完，都记录：改了什么、依据是什么、怎样验证、还有什么没有解决。

这样我复核时，可以直接从评论回到修改和测试。本项目的代码提交由人工负责，不能因为公共技能里包含提交、推送和关闭评论的步骤，就自动执行这些操作。需要发布的回复先形成草稿，再按团队流程确认。



### 3\.4 定期检查时：找那些会随项目变化而失效的内容

平台持续开发以后，我会在合并较大改造后，或者固定的检查周期里，做下面三类检查。

1. 用`improve-codebase-architecture` 查找模块改造机会。比如 worker 接口越改越多，一个状态变化要同时修改前端、后端和桥接层，就要看看哪些复杂逻辑应该集中到同一个模块里，让调用方少理解一些内部细节。

2. 用`security-review` 检查新增能力带来的边界变化。比如原来只读，后来增加了执行测试，就要重新检查命令范围和工作区隔离。

3. 用`audit-instructions` 检查当前会话里已经加载的指令是否冲突。比如项目要求由人工提交代码，公共技能却要求自动提交，就要明确指出冲突，并按项目规则处理。

文档和实现是否一致，则单独做源码核对。比如 README 还写“事件结束后统一回放”，代码已经改成收到 JSONL 就回调，这种差异应该更新文档，但不是`audit-instructions` 的主要用途。



检查结果先形成待办：具体位置、依据、影响和建议。再根据影响安排修改。如果要定期触发，需要另外配置调度器或 CI；技能本身不会自动定期运行。需要人工选择和确认的步骤，也不能直接当成无人值守任务。



### 3\.5 公共 Skills 的三个最佳实践

第一个，每次调用都给具体对象。审任务给需求，审代码给范围和 diff，处理评论给评论编号和对应文件。调用之前，也先核对技能名称、用途和依赖，不根据目录名字猜它能做什么。

第二个，一次先解决当前最重要的问题。不必把十个技能全部串行跑完，才允许修改一个小函数。

第三个，技能更新以后，用固定任务试跑。比如从同一份源码和 diff 开始，在新会话里审查同一份 worker 变更，比较是否找到了关键问题、证据是否准确、Token 和工具调用增加了多少。不要把上一轮的答案带进去，也不要拿已经修好的代码代替原来的测试对象。



公共 Skills 帮我补检查方法。项目里反复出现的交付要求，我会继续整理到自己的 Skills 里。

## 四、通过自建 Skills，把全栈开发串起来

### 4\.1 安装技能

我整理的这套技能叫`software-delivery` ，围绕需求、设计、开发、测试和交付组织。

它解决的是另一个常见问题：每个环节单看都能产出内容，但前后接不上。需求没有验收条件，开发自己补规则；前后端各写一套字段；换一个执行者，找不到前面的结论。

所以，我把共享流程和交接要求放进`software-delivery-base` ，再让各角色技能读取自己需要的规则和模板。



【操作】课程根目录已经有`skills/` ，下面从`codebase/` 执行，把这套技能复制到 pi 的项目技能目录。除了角色技能，还要把 base 一起接进来。

```Bash
DELIVERY_SKILLS_SRC=../skills
mkdir -p .pi/skills

for skill_dir in "$DELIVERY_SKILLS_SRC"/software-delivery-*
do
  cp -R "$skill_dir" .pi/skills/
done
```

第一次复制可以这样做。如果目标目录里已经有旧版本，先检查再更新，避免新旧文件混在一起。

也可以不复制，启动时直接指定技能目录：

```Python
npm run cli -- --dir "$PWD" \
  --managed-mode plan --managed-roles reviewer \
  --tools list_files,search_code,read_file,read_directory,git_diff,git_status \
  --skill ../skills
```

两种方式选一种，避免同名技能重复加载。进入界面以后，检查启动诊断和`/skill:software-delivery-pm` 是否可用。会话中修改了技能，可以用`/reload` 重新加载。

这套技能里有 PM、架构师、后端、前端、移动端、DBA、测试、运维和反向设计。做这次 Web 平台，先用 PM、架构师、后端、前端和测试，交付时再补启动和运维说明。

还要注意，技术栈也要先对齐。本节平台使用 Python 和 TypeScript；技能里的 Java、Maven、Jacoco 等示例，要换成当前项目的目录和实际命令。交互方式和工具名，同样按当前环境适配。



前面的只读会话可以检查方案，但不能生成工作包文件。开始写需求、设计和代码之前，还要切换到允许对应操作的角色、执行模式和工具范围。加载技能本身不会增加权限。



### 4\.2 先用 PM 技能，把“做个平台”拆成可以交付的工作包

我们继续实现 Eval 平台。

我先给 PM 技能完整目标，让它拆工作包。看下面的任务时，重点看要求有没有同时覆盖功能和验收。

```Plaintext
/skill:software-delivery-pm

为当前 Codebase Agent 规划一个本地 Eval Web 平台。

用户可以管理题目和策略，批量运行任务，查看 Trace，完成程序检查、模型评分和人工评审，比较基线与候选并导出回归报告。

第一版只做可信本地仓库的只读源码审查。复用现有受治理 Agent Loop 和 Runtime；每次运行使用独立工作区和新会话。

执行状态与验收结论分开，失败和未知保留，费用缺失不能填零。程序检查针对回答和工具证据，不执行被评仓库的测试命令。

按数据与评分、Agent 桥接、前端工作台、集成验收拆工作包。每个工作包写清输入、产物、依赖和验收条件。

具体需求参考 @Eval 平台开发需求.pdf
```

这一步要拿到具体任务。

比如“实现实验运行”，至少要说明：接收哪些题目和策略，怎样冻结源码并创建独立副本，怎样保存运行状态，取消以后怎样处理，出现错误时页面显示什么。



这样后端和测试才能围绕同一件事工作。不能让模型自己猜。



### 4\.3 再用架构师技能，先定前后端共同使用的契约

PM 拆完以后，架构师读取工作包和现有 Codebase 入口，核对本地单体方案：Vue 3 前端、Python API、SQLite、独立 Node worker。

这一步我会先看两个结果：运行调用链，以及公共数据契约。



运行调用链要明确：Python 后端怎样启动 Node worker，worker 怎样通过`buildPlatform → runManagedAgent` 调用现有 Agent，哪些配置可以覆盖，模型事件、Trace、审计和 usage 怎样返回。



数据契约则要明确下面几个对象。

|对象|这次要保存什么|
|---|---|
|Task|题目、标签、核心任务标记、程序检查、Rubric 和版本。|
|Strategy|Prompt、模型、API 配置、检索配置和价格。凭据只保存环境变量名，不保存密钥值。|
|Experiment|本次选题、策略、重复次数、预算和进度，并关联固定的输入快照。|
|Run|一次实际执行，包括题目与策略快照、源码哈希、回答、Trace、程序检查和消耗。|
|Review|人工评审者、结论、理由和追加保留的历史。模型 Judge 的结果则单独保存在运行记录里。|

这里提前解决一个容易返工的问题：后端的 `execution_status` 表示执行怎样结束，`outcome` 表示任务怎样验收。前端直接展示这两个字段，不再自己根据“有没有回答”推断通过。



还要提前定好 API 示例、错误格式和边界值。前后端开始实现以后，就按这一份契约对接。



### 4\.4 用研发技能实现工作包，用交接文件保存进度

后端技能读取设计，完成存储、运行调度、检索、评分和 worker 桥接；前端技能读取同一份 API 契约，完成题库、策略、实验、Trace、评审和回归页面。

我的经验是，一次交给一个执行者的任务，要能独立验收。



比如后端这一轮先用固定的 worker 返回和事件，验证一次实验能否正确保存结果；前端先完成“显示运行中、失败、未知和离线状态”。先把接口和状态接通，再接真实模型。

交接时，留下产物位置、实际命令、结果和下一步。共享进度记录可以继续使用`codebaseEval/check/00-env/pipeline-status.md` 。



改成多 Agent 并行以后，我们明确一条适配规则：子 Agent 返回阶段结果，由主 Agent 统一更新共享进度文件，避免多个执行者同时覆盖它。业务代码仍然按工作包划分修改范围。



接手者先读前置文件，再确认能否开工。设计文件还没有确定 API，就先把接口补齐，避免前后端各自发挥。



### 4\.5 用测试技能检查交付，把失败留下来

测试技能读取原来的验收条件，再回到代码、API 和运行记录逐项核对。

比如检查“取消有效”，要看取消以后本地运行中的 worker 是否退出，未开始的任务是否停止。停止本地进程，不等于供应商已经撤销请求，所以收到的用量要保留，无法确认的总费用仍然标为未知。



【操作】下面这些平台检查从`codebaseEval/` 执行，不再沿用技能里的 Maven 示例。

```Python
npm test
npm run test:bridge
npm run test:frontend
npm run check
npm run build
```

这里的测试验证的是评测平台本身，不是让被评 Agent 执行仓库测试。Node worker 的 TypeScript 测试和原 Codebase 检查，还要按各自的运行目录补做。



报告写实际命令和结果。覆盖率没有测，就不填百分比，也不能宣称覆盖率门禁通过；测试没有运行，就说明原因；发现问题，就给出能够复现的步骤。原有失败和本次新增失败分别记录。



到这里，这套 Skills 已经把全栈开发的交接串起来了。接下来，我们把可以独立执行和验收的工作交给子 Agent，让主 Agent 集中处理分工、依赖和最终决策。



## 五、通过 subagent，把单 Agent 改造成多 Agent

### 5\.1 先写分工，再接调度

这次先建立一套七个角色的巡检流程。它既能检查我们正在改造的 Codebase，也能检查后面做出来的 Eval 平台。

这里说的七个角色，是当前主 Agent，加上五个检查专家和一个报告汇总者。

我先把分工写清楚，减少重复检查。需要交叉核对的关键代码，可以由不同专家分别检查，但关注的问题要不同。

|角色|具体负责什么|交回什么|
|---|---|---|
|Supervisor Agent|主 Agent 拆任务、调度、核对结果并做最终决定|任务安排、需要补查的事项和最终结论|
|Architecture Agent|目录结构、模块边界、依赖方向和架构问题|调用关系、边界问题和调整建议|
|Test Agent|测试覆盖率、测试质量和缺失测试|已有测试能证明什么，还缺哪些场景|
|Security Agent|鉴权、注入、敏感信息和权限边界|触发条件、源码依据、影响和修复建议|
|Performance Agent|慢查询、循环、缓存和性能隐患|风险位置、判断依据和测量建议|
|Documentation Agent|文档、注释和知识库内容|与实现不一致、过期或缺失的内容|
|Report Agent|合并结果、处理冲突并生成最终报告|保留来源、优先级和未验证项的报告草稿|

每次派任务，再把这次的重点补上。

比如评审 Eval 平台，架构专家重点看 Python 和 Node 的职责边界；测试专家重点看状态和评分优先级；性能专家重点看快照复制、事件存储和页面刷新。

测试专家没有拿到实际覆盖率报告，就指出缺少数据，不估算百分比。性能专家没有测量结果，就先提交风险和测量方案，不把静态判断写成已经确认的性能问题。

这样主 Agent 才知道下一步需要运行什么检查。



### 5\.2  把角色配置放进项目，任务里给明确范围

【操作】在 `.pi/agents/` 下创建 architecture、test、security、performance、documentation 和 report 六份配置。Supervisor 使用当前主 Agent，不需要再启动一层主管。



下面以 Architecture 为例，重点看三个地方：职责、工具范围和交付要求。

```Markdown
---
name: architecture
description: 分析当前项目的目录结构、模块边界、依赖方向和架构问题。
tools: list_files,search_code,read_file,read_directory,git_diff,git_status
---

根据本次分配的范围执行架构检查。
先通过 read_file 读取任务指定的 Skill，再阅读相关源码和调用者。

检查模块职责、依赖方向、重复实现和跨模块契约。
需要设计方案时，读取 software-delivery-architect 的流程与模板。

返回检查范围、问题、文件行号、源码依据、影响和建议。
保留冲突、待确认和未覆盖内容。
只读检查，不修改文件，不执行仓库命令，不再次委派。
```

其他专家按同样方式配置，替换职责、关注文件和要读取的 Skill。技能路径由调度器解析成明确路径再传给任务，避免切换工作区以后读错目录。



Report 只接收任务正文里的专家结果和证据位置，不读文件、不执行命令、不再次委派。



### 5\.3 先接通一个子任务，再让 Skill 组织巡检

单个架构任务跑通以后，再增加其他角色。

所以这一步先接通一个 Architecture 任务，确认几个结果：子任务用了哪个模型，工作区在哪里，实际启用了哪些工具，调用是否经过 Runtime，结果和消耗能否回到父任务。



单个任务跑通以后，主 Agent 再核对一条实际发现。证据和任务范围都没有问题，再派五个专家。

这时我会让`ultrareview` 按下面的任务组织巡检：

```Plaintext
/skill:ultrareview
对本次改造执行一次多方向巡检，源码版本保持一致。

通过 subagent 的 tasks 模式，
委派 architecture、test、security、performance、documentation
给每个专家明确检查文件和职责，统一返回问题与证据。

等待全部任务结束或失败，再把结果和失败清单交给 report。
报告保留发现来源、冲突和未覆盖项。

主 Agent 核对关键结论，决定补查、修复或接受。
```

Report 汇总以后，主 Agent 还要处理冲突。两个专家对同一处代码判断不同，就回到调用链补查；某个专家超时，就明确保留检查缺口。

如果要完整执行`ultrareview` 的交叉验证流程，还要安排专家核对争议发现。只把五份结果合并起来，不等于已经完成交叉验证。



最终由主 Agent 统一写报告，避免多个专家同时覆盖同一份文件。



### 5\.4 多 Agent 的六条最佳实践

1. 先拆可以独立完成的任务。多个专家读取同一份冻结源码，可以并行；报告依赖专家结果，就放到最后。

2. 每个任务只带它需要的材料。架构任务拿模块和调用关系，测试任务拿验收条件、变更和已有测试。完整运行记录保存在外部，需要时再按任务 ID 和 Trace ID 回查。

3. 预算同时看局部和整体。一个专家在自己的限制内，五个专家加上主 Agent 和 Report，仍然可能超过总预算。

4. 当前单 Agent 的 LoopGuard 不会自动汇总所有子任务消耗。整体配额控制、父子记录关联和实际用量累计，都要在调度层补上。费用数据缺失时保留未知，不能当成零。

5. 失败任务按需要重跑。先看它已经完成了什么，补跑缺失范围；源码变化以后，再判断哪些已有结论需要重新检查。重跑记录单独保留，不覆盖原来的失败证据。

6. 最后看收益。多派几个角色以后，要比较有效发现、重复工作、误报、耗时和费用。小改动用单 Agent 检查更合适，就继续用单 Agent。

## 六、用 Skills 和多 Agent，完成 Eval 平台交付

### 6\.1 先固定这次要交付的平台

现在把前面的做法组合起来。

我们要交付的是一个本机可运行的 Eval 平台。它复用 Codebase 的受治理入口，提供题库、策略、实验、Trace、评审、统计和回归报告。

这次多 Agent 负责平台的开发和审查；平台第一版评测的对象，是现有 Codebase 的单 Agent 只读源码审查能力。

实际调用链沿用现有实现：Python 调度实验，Node worker 调用 `buildPlatform → runManagedAgent`，结果再回到 Python 保存和评分。

先把这条链路和验收标准固定下来，后面各个开发任务都围绕它实现。



### 6\.2 主 Agent 拆工作包，Architecture Agent 定接口

主 Agent 先使用 `software-delivery-pm` 整理需求和工作包。再把工作包、当前代码和技术栈交给 Architecture Agent，让它参考 `software-delivery-architect` 给出设计建议。



我会特别检查四个问题。

第一，每次运行从哪份源码开始？要先冻结实验基线，再为每次运行创建独立工作副本。

第二，什么情况算`completed` ，什么情况算`pass` ？执行状态和验收结论分别保存，不能根据回答是否非空判断通过。

第三，程序检查、Judge 和人工评审怎样共同决定结果？当前平台先检查执行状态，再检查程序结果，最后判断语义评审。有人工评审时，使用最新人工结论，否则使用 Judge 结论；人工通过不能覆盖程序失败或执行错误。

第四，输入不完整、价格未知、运行取消时怎样记录？这些都要进入接口和验收条件，不能在页面上临时补解释。



设计确定以后，主 Agent 保存公共契约，再交给开发任务。后续修改契约，也由主 Agent 协调并通知相关执行者。



### 6\.3 先接通最小闭环，再扩展页面和评分

我会先让第一版跑通一个题目、一个策略和一次实验。

输入是一道源码审查题。平台创建工作副本，调用 worker，保存回答、工具记录和执行状态，再让页面显示这次结果。

这条链路通了，再加重复运行、多策略比较、Judge、人工评审和回归报告。

这样出错时范围更小。比如页面没有 Trace，先查 worker 是否发了事件、Python 是否保存、API 是否返回，最后看前端是否展示。



离线模式可以先验证这条链路。当前离线 worker 会尝试通过真实 Runtime 读取`src/policy.ts` ，再返回明确标记的固定演示回答。读取是否成功，要看审计记录；它不是模型根据题目生成的答案。



离线实验不需要真实模型凭据，最终评测结论保持`unknown` ，不计入真实模型成功率。



### 6\.4 用五个专家审查平台，再由主 Agent 收敛修改

前后端接通以后，启动前面建立的五方向巡检。每个专家的任务都对应平台的具体风险。

|专家|这次检查什么|
|---|---|
|Architecture|Python、worker 与 Runtime 是否各司其职，接口和状态是否一致|
|Test|程序失败、未知、离线、取消、重启和重复评分是否有测试|
|Security|凭据、快照排除、只读工具、输入校验和本机访问边界|
|Performance|快照复制、事件写库、重复检索、页面刷新与并发限制|
|Documentation|安装、启动、目录、模型配置和功能说明是否符合当前代码|

主 Agent 再按影响处理。比如发现程序失败能被人工通过覆盖，就先修判定逻辑；页面的一处措辞问题，可以随后调整。这里说的是检查场景，当前代码已经有程序失败优先的判断，不能把假设的问题讲成现有缺陷。

修完以后，重跑对应测试，再做相关回归。



这时可以用到前面的公共 Skills：关键边界再做`security-review` ，跨模块变更使用接通后的`ultrareview` ，实现和验证稳定以后，再参考`simplify` 收敛重复逻辑。收到评论后，用`address-pr-comments` 逐条核对。



这些技能仍然要受项目权限和交付流程限制，不能因为技能里包含修改、提交或推送，就自动执行。



### 6\.5 运行配套项目，核对页面背后的实际行为

配套平台的目录是`codebaseEval/` ，与`codebase/` 同级。



如果使用分包材料还原项目，先核对包内目录和根配置，不根据“后端包”“前端包”的名字直接覆盖已有文件。还原以后，确认启动脚本、后端模块和前端目录都在对应位置。

【操作】从`codebaseEval/` 执行下面两条命令。第一条安装 Codebase 和前端的锁定依赖，并构建前端；第二条启动 Python API 和静态页面服务。

```Bash
npm run setup
npm start
```

首次运行需要`setup` ，之后通常只需要`npm start` 。默认访问地址是 http://127\.0\.0\.1:8765 。



先打开 Benchmark，检查题目和评分条件；再打开策略，检查模型、Prompt、检索和价格。选择一个题目、两条策略，运行一次`offline` 实验。



已有验收记录中，两次离线运行完成，Trace 展示了 Runtime 读取和审计；最终结论保持`unknown` ，回归门禁为`hold` 。报告请求和内容也做过核对，但没有确认浏览器下载文件实际落盘。

这些记录说明当时验证了哪些链路，不代表当前修改后的版本已经重新验收。



接下来配置真实模型，继续验证实际任务表现。



### 6\.6 验收易错的结果

先看`completed` 。

运行记录中的`execution_status: completed` 表示 Agent 执行正常结束，最终通过还要满足程序检查和语义评审。实验的`status: completed` 则表示整批运行处理结束，其中仍然可能有失败或未知，不能把实验完成当成全部任务成功。



再看 Judge。

当前 Judge 使用被评策略的同一模型、端点和凭据，另发一次请求核对证据。它不是独立模型审查，也不会自己执行仓库测试。重要结论仍然需要人工定标；要使用独立审查模型，再增加单独配置和验证。



再看 RAG。

当前实现对 Markdown、YAML 做关键词或 BM25 检索，不是向量检索。界面展示的召回片段，要能回到对应资料，再与源码核对。



再看 Trace。

页面按运行、轮次、模型消息和工具调用组织记录。这种展示层级不等于真实的多 Agent 父子 Trace。后续评测多智能体时，还要接父子运行关系和用量汇总。



最后看预算和取消。

实验页面的`max_tokens` 用于限制被评 Agent 每次模型响应的输出；累计轮数、工具调用、Token 等限制来自 Codebase 的 LoopGuard。



Judge 使用自己的输出限制和超时控制，消耗会计入平台统计，但不受被评 Agent 同一份累计预算约束，也没有接入实验取消信号。



取消运行中的实验，可以终止当前 Node worker 的进程组。已经开始的 Judge 不会因此立即停止；已经发出的供应商请求是否停止计费，也不能仅凭本地进程退出确认。



这些结果都要按实际代码解释。测试技能、公共审查技能和多专家巡检，就是帮助我们找到实现与预期之间的差异。



【操作】在`codebaseEval/` 验收现有平台，先跑下面几组检查。

```Bash
npm test
npm run test:bridge
npm run test:frontend
npm run check
npm run build
```

Node worker 的 TypeScript 测试，再从`codebase/` 执行。

```Bash
npm exec -- vitest run ../codebaseEval/bridge/worker.test.ts --root ..
npm run check
npm test
```

已有验收记录写明：平台后端 39 项、Python 桥接 4 项、Node worker 8 项、前端 28 项通过，类型检查与生产构建通过。Codebase 当时有 132 项通过，1 项因课程样例目录缺失失败。

当前前端源码已经有 33 个测试声明，但没有本次运行结果，不能直接把它写成“33 项通过”。重新执行以后，再更新验收记录。



这些检查验证的是平台代码和本地行为。真实模型质量，还要继续用固定任务和真实运行评测。



### 6\.7 平台交付以后，把改动变成下一轮实验

现在，我们已经有了一个保存实验和比较结果的地方。

下一次调整 Prompt、模型或检索配置，就先保留基线，再建立候选。当前平台要求在同一个实验里运行两条策略，保持题目快照、源码和评分条件一致，再比较逐题结果和代价。



要比较公共 Skill 更新或 subagent 分工变化，还需要把对应能力接到平台调用的入口，并记录实际生效的版本和父子 Trace。仅仅更新开发环境里的 Skill，不代表平台评测时已经用上它。



做实验时，每轮尽量只改一项。

配套平台的两条默认策略同时改了检索模式和 Prompt，直接比较它们，结论只能对应整套配置。如果要判断 BM25 的作用，就复制同一条策略，只改检索设置。

发现失败以后，回到运行记录，提出一个具体修改，复测原任务，再跑旧任务。确认有效以后，把对应失败场景和验收条件补进回归任务集。



这样，Skills 里的经验会有验证依据，分工策略也能继续调整。

## 七、总结：把一次交付中有效的做法留下来

这一节，我们从接入公共 Skills 开始，把它们放进计划检查、代码审查、评论处理和定期巡检。



再用我自己的交付 Skills，把需求、接口、前后端开发和测试串起来。通过接通并验证的 subagent，把独立任务交给不同执行者，主 Agent 负责依赖、集成和最终决定。



最后，用同一套方法交付 Eval 平台，再把后续修改放进固定任务里验证。



大家可以照这个顺序练习：先接进来，拿一个具体任务用起来；出现遗漏，就补步骤和验收；需要分工，再增加子任务。每完成一轮，都把有效的做法和验证结果留下来。
