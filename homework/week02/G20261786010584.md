# 第二周作业反馈

学员：我是智仔（G20261786010584，记录19452）

**1. 作业等级：优秀（81分）**

**2. 作业优点**

- 教师使用课程原始五项测试独立验收，全部通过；参数注入拒绝、基础权限边界、审批绑定与防重放均有运行证据。
- 四个模拟账户的租户、账号和浮点余额准确；补测确认满额转出成功、缺失目标账户不会先扣款，跨租户账号不会修改其他租户余额。
- 大额转账先等待再扣款，运行时约半秒返回 `TIMEOUT_UNKNOWN`，余额保持不变；交易号正确取调用编号末六位。
- 正常转账结果中的两个账号按要求遮罩；原订单结果的邮箱和令牌字段也能脱敏。

**3. 作业不足**

- 固定的 `PermissionEngine.decide()` 被移除并改写框架；实际链路先消费审批、后做预检，导致未审批的限额和余额不足请求先要求确认，已审批的业务拒绝还会消耗审批。
- 严格参数配置缺少 `strict=True`。金额字符串和布尔值被转换接受，未按要求返回 `INVALID_ARGUMENT`；额外字段禁止仍然有效。
- `canonical_target` 未包含金额，金额不同的转账产生相同目标，不能区分完整业务参数组合；审批摘要绑定本身仍然有效。
- 通用脱敏退化：普通文本和列表中的邮箱、账号可能原样返回；敏感键的值恰为账号时，提前返回账号遮罩而非完整隐藏敏感值。
- 审计只剩阶段和错误码，缺少调用编号、链路、用户及租户关联信息；提交入口也没有打印确认、脱敏结果和关联审计的展示。

**4. 改进方案**

- 恢复附件固定权限引擎，保持业务预检先于审批；复测未审批的 60000 元、余额不足请求直接拒绝，并确认预检拒绝不消费已有审批。
- 恢复严格模型配置且保留 `extra="forbid"`；通过 Runtime 验证字符串、布尔金额与注入字段均被拒绝，合法浮点金额仍能转账。
- 将金额加入规范化目标；分别只改变转出账号、转入账号、金额，验证目标均有区别，同时保留现有审批参数绑定与一次性使用行为。
- 恢复对字符串、嵌套列表和元组的递归脱敏，敏感键优先完整遮罩；复测普通文本邮箱、嵌套账号及敏感键账号值，并回归原订单结果。
- 恢复原审计关联字段，增加离线展示入口，打印确认、模拟人工批准后的脱敏结果及可按调用编号、链路编号关联的审计；最后重跑原始五测和补测。
