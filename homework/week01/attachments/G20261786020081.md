## 验证结果

### 启动

按 README 在干净 venv 安装 `requirements.txt` 后，`./.venv/bin/python main.py` 退出码 1：

```text
ImportError: cannot import name 'ExecutionInfo' from 'langgraph.runtime'
```

原因是 `langchain==1.0.3` 要求 `langgraph<1.1`，解析到的 `langgraph==1.0.10` 又要求 `langgraph-prebuilt>=1.0.8`，pip 装到了 1.0.13。1.0.9 起的 prebuilt 依赖 `ExecutionInfo`，而 langgraph 1.0.10 没有这个符号。仓库没有锁文件。把 prebuilt 固定到 1.0.8 后服务可启动，这只发生在评测环境。

启动后：

- `GET /models` → 200 `{"models":["deepseek","minimax"],"default":"deepseek"}`
- `GET /` → 200

### 两个模型真实调用与协议

提交配置（`app/config/settings.py`）：

| 网关 model | 配置 protocol | 上游模型 | 实际请求 |
| --- | --- | --- | --- |
| `deepseek` | `openai` | `deepseek-flash` | `POST https://api.deepseek.com/chat/completions`，`Authorization: Bearer`，body 含 `messages` |
| `minimax` | `openai` | `MiniMax-M3` | 未发出。`get_api_key` 抛 `RuntimeError: MINI_MAX_API_KEY NOT EXISTS`，HTTP 500 `INTERNAL_ERROR` |

`deepseek` 的 README 示例真实调用成功：HTTP 200，`reply=你好`，usage `prompt 39 / completion 9 / total 48`，`latency_ms=1455`，`attempts=1`。

未知模型 `no-such-model`：HTTP 400 `UNSUPPORTED_MODEL`，没有改走默认模型。

适配器代码本身可以发出第二种协议。评测时把 `AnthropicAdapter` 指到官方 `https://api.deepseek.com/anthropic`、模型 `deepseek-v4-pro`，请求体是顶层 `system` + `messages` + `max_tokens`，鉴权是 `x-api-key` 和 `anthropic-version: 2023-06-01`，路径 `/anthropic/v1/messages`。这与 Chat Completions 的路径、鉴权和请求体都不同。该接线不在学员 `MODEL_CONFIGS` 里，调用方不能通过 `model` 选到它。

官方 `/models` 确认当前可用标识只有 `deepseek-flash` 和 `deepseek-v4-pro`。官方文档确认二者都支持 Chat Completions、Responses（`POST /responses`）和 Anthropic Messages。学员没有 Responses 适配器。

真实调用结果（短提示，官方接口）：

| 协议 | 模型 | 普通 | 流式 | 结构化 |
| --- | --- | --- | --- | --- |
| Chat Completions | `deepseek-flash` | 200，正文「甲」，0.89s | 收到「丙」，0.95s | `{"k":"ok"}`，请求带 `response_format.type=json_object` |
| Anthropic Messages | `deepseek-v4-pro` | 200，正文「乙」，1.92s | 收到「丁」，随后 usage | `{"k":"ok"}`，约束写在 system，无 `response_format` 字段 |

这组调用证明适配器实现能打通两种协议，不证明提交的路由满足「两个模型、两种协议」。

### 未验证

- MiniMax 真实调用。没有 `MINI_MAX_API_KEY`，且作业要求真实模型只用 DeepSeek 官方接口。不把这当成协议错误，也不声称该模型验收通过。
- 无成功终态的 SSE 在超时前是否被标成失败。直接断开后 LangChain 会一直读到 `timeout_seconds`，然后 `ReadTimeout`。短于超时的观察窗口里，指标还没写入。不把「超时前未记录」写成已确认的成功误判。
- Responses 协议只做了官方可达性探测（`POST /responses` 返回 200），学员代码没有这条路径，无需再测。

## 待修复问题

1. 问题与评分项：提交的两个模型实际发送同一种协议。统一接口与适配器 / 双协议。
   - 触发条件：`POST /chat` 分别传 `model=deepseek` 和 `model=minimax`。
   - 预期结果：两个适配器的路径和请求体结构不同。
   - 实际结果：两者 `protocol` 都是 `openai`。deepseek 实际请求 `POST /chat/completions`。minimax 在取密钥时失败，没有第二条协议。Anthropic 适配器未进入 `MODEL_CONFIGS`。
   - 复现：见 `logs/upstream-openai-capture.txt`、`logs/a02-minimax.json`、`app/config/settings.py`。
   - 扣分：双协议 0/4。统一入口 3、路由 4、统一结果 4 保留。不在流式、结构化项再扣「缺第二协议」。

2. 问题与评分项：流式内容被缓冲，终态到达前客户端收不到增量。流式输出 / 真实增量。
   - 触发条件：本地门控上游先发 `FIRST`，2.2 秒后发 `SECOND` 和终态。
   - 预期结果：`FIRST` 在终态之前到达。
   - 实际结果：0.017s 只有 `response.created`；2.203s 才收到 `FIRST-`，2.205s 收到 `SECOND`。`_ThinkFilter` 保留 6 字符前缀，把 `FIRST` 切成 `FIRST-`。
   - 复现：`logs/gated-stream.txt`，`app/adapters/openai_adapter.py` 的 `_ThinkFilter`。
   - 扣分：真实增量 5。SSE 格式、终止与错误、输出后不重试的分数保留。

3. 问题与评分项：SDK 内置重试与外层重试叠加，实际次数超过首次加 3 次。统一错误与重试 / 次数上限。
   - 触发条件：上游持续 500。
   - 预期结果：不超过首次加 3 次，文档写的是最多重试 3 次。
   - 实际结果：一次 `adapter.complete` 就产生 3 次上游请求（OpenAI SDK `max_retries` 默认 2，LangChain 未覆盖）。外层再重试 3 次，合计 12 次。指标只记 `retries=3`。
   - 复现：`logs/retry-always500.json` 旁的 counts、`logs/sdk-retry-isolation.txt`。
   - 扣分：次数上限 3。

4. 问题与评分项：指数退避的正向抖动使等待超过当次 `min(cap, base·2^(n-1))`。统一错误与重试 / 退避。
   - 触发条件：`RetryService.backoff_delay`，base 0.5，cap 8。
   - 预期结果：第 n 次重试前的等待不超过 `0.5 * 2^(n-1)`。
   - 实际结果：200 次抽样全部超过该值。第 1/2/3 次最大约 0.60 / 1.20 / 2.40 秒。实现是 `delay + random.uniform(0, delay * 0.2)`。
   - 复现：`app/services/retry_service.py` `backoff_delay`，`logs/sdk-retry-isolation.txt`。
   - 扣分：退避 4，另扣重试过程 1。没有「同上游对齐的指数退避」，外层看到的成功重试其实是 SDK 在一次调用里完成的。

5. 问题与评分项：上游 4xx 映射成 502。统一错误与重试 / 错误映射。
   - 触发条件：上游返回 400 或 401。
   - 预期结果：明确的 4xx，或至少不伪装成网关 502。
   - 实际结果：HTTP 502 `UPSTREAM_ERROR`，message 里带上游 400/401。只请求 1 次，所以不可重试分保留。缺 `MINI_MAX_API_KEY` 时更是未处理 `RuntimeError`，HTTP 500。
   - 复现：`logs/retry-status400.json`、`logs/retry-status401.json`、`logs/a02-minimax.json`。
   - 扣分：错误映射 1。不在不可重试子项再扣。

6. 问题与评分项：按 README 安装不能启动；验证脚本在第二模型处中断。源码、README 与验证脚本。
   - 触发条件：干净 venv 执行 README 的安装和启动；再跑 `tests/verify.py`。
   - 预期结果：服务可启动；脚本覆盖六项并给出结果。
   - 实际结果：启动退出码 1，`ExecutionInfo` 导入失败。脚本在 minimax 处抛未处理异常，退出码 1。
