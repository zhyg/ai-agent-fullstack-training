### 两个模型真实调用与协议

官方 `GET https://api.deepseek.com/models` 返回 200。当前模型标识：`deepseek-v4-pro`（DeepSeek-V4-Pro）、`deepseek-flash`（DeepSeek-V4.1-Flash）。学员别名 `deepseek-v4-flash` 若把 `upstream_id` 原样发给官方，会打到已退役、仅兼容路由的旧名。本次真实调用把 flash 的 `upstream_id` 配成 `deepseek-flash`。

评测配置（只在评测进程内，未写入学员仓库）：

- `deepseek-v4-pro`：`base_url=https://api.deepseek.com`，协议 `openai_responses`，`POST /v1/responses`，`Authorization: Bearer`
- `deepseek-v4-flash`：`base_url=https://api.deepseek.com/anthropic`，协议 `anthropic_messages`，`POST /v1/messages`，`x-api-key` + `anthropic-version: 2023-06-01`

`adapter.prepare` 确认两条请求的路径、鉴权头和请求体不同：Responses 用 `input` + `max_output_tokens` + `text.format`；Messages 用 `messages` + `max_tokens` + `tools`/`tool_choice`。

## 待修复问题

1. 问题与评分项：统一入口不接受 `response_format`。统一接口与适配器、结构化输出。
   - 触发条件：`POST /v1/chat/completions`，body 含 `response_format: {"type":"json_object"}`。
   - 预期结果：作业要求该字段作为统一入参，由适配器映射到各协议。
   - 实际结果：400 `GW_INVALID_REQUEST`，`response_format` 被当作未知字段。等价字段 `output_schema` 可用，且双协议结构化已验证。
   - 复现命令与证据：`probe/logs/accept-offline.json` 的 `entry-response_format`。入口模型在 `core/types.py` 的 `LLMRequest`，`extra="forbid"`。
   - 扣分：结构化正常流程扣 4。统一接口仍为 15/15。路由、双协议实现、统一结果、成功前校验和失败处理保留。

2. 问题与评分项：空增量被当成首 Token。流式输出。
   - 触发条件：Responses 流先发 `response.output_text.delta` 且 `delta=""`，350 ms 后再发正文。
   - 预期结果：TTFT 计到第一个非空有效内容块。
   - 实际结果：空增量被下发并记入 ttft（1.3 ms），正文约 306 ms 才到。
   - 复现命令与证据：`probe/logs/faults2.json` 的 `empty-delta-ttft`。代码在 `resilience/pipeline.py` 的 `_stream_body`，`text_delta` 不判断文本是否为空。
   - 扣分：2。不在可观测性重复扣。

3. 问题与评分项：上游 4xx 映射成 502。统一错误与重试。
   - 触发条件：mock 上游返回 400；真实 Anthropic 在默认思考模式下拒绝 `tool_choice`。
   - 预期结果：上游参数/能力拒绝应能与网关 5xx 区分，调用方看到明确 4xx 或统一错误结构中的可区分状态。
   - 实际结果：HTTP 502，`GW_UPSTREAM_REJECTED`，body 里保留 `upstream_status: 400`。不重试，这项保留。
   - 复现命令与证据：`accept-offline.json` 的 `F09-400`；`accept-real.json` 的 `REAL-struct-deepseek-v4-flash`。映射在 `upstream/client.py` 的 `raise_for_upstream_status`。
   - 扣分：1。

4. 问题与评分项：README 不能直接启动真实双模型验收。源码、README 与验证脚本。
   - 触发条件：按 README `pip install -r requirements.txt && uvicorn main:app`，不额外改 `config.toml`。
   - 预期结果：启动指南能把两个模型接到可验证的上游，或写明真实接入所需的 Base URL 与模型标识。
   - 实际结果：缺 `MINIMAX_API_KEY` 起不来；配上之后两个 DeepSeek 别名仍指向本机 mock。DESIGN 写明这是纯配置别名。
   - 复现命令与证据：导入失败见 pytest 退出码 4；`config.toml` 中两个 DeepSeek `base_url`。
   - 扣分：2。不把环境阻塞当成协议实现缺陷。真实调用是评测方改配置后完成的，不声称按 README 原样真实验收通过。

## 不另扣分的观察

- `strict=false` 时非法 JSON 返回 200。这是学员在 DESIGN 与测试 `test_contract_strict_false_does_not_fail` 中写明的开关，默认 `strict=true` 会校验。写入评语，不按“成功前校验”再扣 3 分。
- 默认思考模式下 Anthropic `tool_choice` 被官方拒绝。关闭思考后同一适配器真实结构化通过，所以不记为双协议实现缺失，也不在流式/结构化项扣“缺第二协议”。
- 失败调用 usage 记 0，而不是 null。失败记录存在，0 没有被写成真实消耗。不扣失败记录分。
- 重试口径是总尝试 3 次（`config.toml` `max_attempts=3`），实现一致，未超过首次加 3 次。
- 限流键是（调用方，模型），不是只按调用方。A 耗尽不影响 B。
