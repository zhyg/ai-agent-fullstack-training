## 每项扣分的复现、源码及证据

### D1：双协议透传没有统一适配（统一接口与适配器，扣 4）

- 触发：分别访问 Chat 和 Responses，或对 Responses 使用统一 response_format={type:json_object}。
- 预期：调用方只面对统一输入/结果，适配器根据 model 配置选择协议并映射字段。
- 实际：请求路由把固定字符串 chat/responses 传入编排层，路由再据此过滤候选；调用方必须分别传 messages/input、response_format/text.format，并分别解析 choices/output。统一字段在 Responses 被忽略，本地不校验，受控 not json 返回 200。
- 源码：`app/api/routes.py:43–68`；`app/services/router.py:61–106,121–125`；`app/services/structured.py:37–60`；`app/services/gateway.py:167–174`。
- 复现：运行 verify_g197.py；证据 A03-chat、A03-responses、F03-unified-field 的实收请求和响应。
- 统一字段遗漏与返回异构结构同属透传架构根因，只在此扣 4；不再次扣结构化正常流程分。

### D2：流内错误未参与终态判定（流式输出，扣 2）

- 触发：上游先发 partial，再发 error 事件并正常结束 HTTP 传输。
- 预期：客户端能识别失败，网关状态明确为失败，不记录成功完成。
- 实际：原始 error 透传，账本 status=success；`no_end` 对照也记录 success。传输断开路径则能正确 error+DONE、failed，予以保留对应分数。
- 源码：`app/services/gateway.py:259–273,291–302`；只扫描用量，没有协议终态解析。
- 证据：controlled-results.json 中 F01-F02-chat-event_error、F01-F02-responses-event_error 及各自 trace；drop 是通过对照。no_end 是补充建议证据，不另扣分。错误被记成功不再从可观测性重复扣。

### D3：验证提取值、成功仍返回非法原文（结构化输出，扣 3）

- 触发：在 json_object 请求中，上游正文为 Markdown 围栏包裹的对象。
- 预期：成功正文可直接 json.loads；或返回明确失败；允许修复但最终正文仍须合法。
- 实际：本地剥围栏解析成功后丢弃 parsed，返回原 result，HTTP 200 的正文仍有围栏；两协议均复现。bad/empty/truncated/wrong_schema 能 3 次后明确 422，不据此否定全部结构化能力。
- 源码：`app/services/structured.py:120–157` 提取与解析；`app/services/gateway.py:171–174` 返回未清洗 result。
- 证据：F03-F04-chat-fenced、F03-F04-responses-fenced；check_evidence.py 已对返回正文执行 json.loads，确认失败。
- 额外 stream+JSON 返回 partial 无校验留在 extra-results.json；题目未强制组合，不额外扣分。

### D4：账本用量维度丢失（可观测性，扣 2）

- 触发：上游明确返回输入 17、输出 9、总量 26、缓存 7、推理 4。
- 预期：分类按实际能力保存；总量可查，子集不重复加总。
- 实际：HTTP 透传仍保有完整 usage，账本只存 input_tokens/output_tokens，没有 total、cached、reasoning 字段。真实 Responses 也明确返回非零 reasoning，仍丢失。不能用“上游不提供”解释。
- 源码：`app/services/usage.py:15–20`；`app/core/models.py:35–55`；`app/services/gateway.py:372–395`（流用量扫描）。
- 证据：A03-chat、A03-responses 的 response.usage 与 trace 对比，gate 的流式 trace；real-summary.json 与 real-traces.json 对比。修复失败时已知 usage 也丢失，合并为用量采集不完整，不另加扣分。

### D5：TTFT 把心跳当正文（可观测性，扣 2）
