## 每项扣分：触发、预期、实际与源码

以下源码路径均相对于学员固定提交根目录。复现通用入口为 `python probe.py`，以 `controlled-results.json` 的 case 字段定位；完整命令见 `reproduce.md`。每个根因仅扣一次，不按模型数量叠加。

### D01：没有成功终态的断流被当成成功（流式输出，扣 2）

- 触发：`stream-openai-eof`、`stream-anthropic-eof`；上游发非空正文后直接关闭 HTTP body，不发 response.completed / message_stop。
- 预期：客户端能识别失败，账本记 error；不得重放已输出内容。
- 实际：两者均发 `finish_reason=stop`、`[DONE]`，`/v1/requests` 对应 status=ok；上游实际请求均 1 次。不重试部分保留满分。
- 源码：`src/main/java/com/llmgw/ChatController.java:155-200` 初始 finishReason=stop，遍历结束后直接成功发送并记账，未维护“已收到成功终态”；两个适配器的事件解析也未为 EOF 补错误。
- 证据：上述两个 case 及 `/v1/requests?limit=200`；例如 Responses 请求 chatcmpl-338d3d7b9175456cbf9da94a。同一根因的错误成功记录不再扣可观测性。

### D02：JSON 后尾随非法内容仍成功（结构化输出，扣 2）

- 触发：`json-openai-trailing`、`json-anthropic-trailing`，统一 response_format=json_schema，上游正文 `{"answer":"ok"} garbage`。
- 预期：完整正文不是合法 JSON，应返回 invalid_json_output。
- 实际：两者 HTTP 200，content 原样包含 garbage；对照 not json、空串、截断对象均正确 502，保留已实现的基础失败处理分。
- 源码：`ChatController.java:118-120,314-322`，只执行默认 `mapper.readTree(value)`，没有确保解析到整个输入结束；流式也复用此校验。
- 证据：两个 trailing case 与 `assertions.json` 的 reject trailing；不是只检查外层响应能否解析。

### D03：已声明 Schema 能力但不检查类型（结构化输出，扣 1）

- 触发：`json-*-schema-mismatch`，声明 answer 必须 string，上游返回 `{"answer":12}`。
- 预期：按声明 Schema 判断不符合并明确失败，不能把合法语法等同于符合 Schema。
- 实际：两个协议均 200；只验证语法。与 D02 的完整 JSON 读取是两个问题，分别检查不同契约；未强加原题没有要求的额外 Schema 能力，是按 README 的 json_schema 示例和适配器声明验证。
- 源码：`ChatController.java:118-120,314-322` 没有把 schema 传给校验；`adapter/OpenAiResponsesAdapter.java:142-151`、`adapter/AnthropicMessagesAdapter.java:212-226` 仅把 Schema 传上游或工具，未核验最终内容。
- 证据：两个 schema-mismatch case、上游记录中相应 text.format.schema / tools.input_schema；正常 string 对照返回 200。

### D04：Responses 丢失上游缓存分类（可观测性，扣 1）

- 触发：`normal-openai`；外部上游明确返回 input_tokens=11、output_tokens=7、input_tokens_details.cached_tokens=3、reasoning_tokens=2。
- 预期：总量为 18，缓存 3 是输入子集，不另加；缓存与推理分类均保留。
- 实际：总量18和推理2正确，但 prompt_tokens_details=null、账本 cachedTokens=null；Messages 以 11+2+3=16 输入、7 输出、23 总量为正确对照。
- 源码：`adapter/OpenAiResponsesAdapter.java:177-182` 固定向 `Usage.of` 传 cached=null，没有读取 input_tokens_details。
- 证据：`normal-openai`、`normal-anthropic`、`upstream.py` 的 ru/au 固定用量和关联账本。

### D05：JSON 失败后已知 Token 用量被清零（可观测性，扣 1）

- 触发：`json-openai-invalid`、`json-anthropic-invalid`；上游正常 HTTP 200，正文不合法，但同时已提供明确 Token 用量。
- 预期：调用记失败，同时保留已知上游用量，不将已消耗 Token 清为 0。
- 实际：失败记录存在，但两者 promptTokens、completionTokens 都为 0；正确已知值分别应为11/7和16/7。
- 源码：`ChatController.java:117-120` 在拿到 result 后抛校验错误，`140-144` catch 中向 record 传 usage=null，`307-308` 再转为0。
- 证据：失败 case 的 gateway.request_id 与 `/v1/requests?limit=200` join；Responses 示例 chatcmpl-0dec6adbf884467a878bcee6。只扣用量，不因失败已有记录再次扣失败记录分。

### D06：未知模型请求没有失败账本（可观测性，扣 1）

- 触发：`unknown-model`，模型 does-not-exist。
- 预期：明确拒绝且这次调用可按 request_id 查询失败记录。
- 实际：404 和 request_id 正确，但查询200条账本没有该 request_id，本次记录量远低于500容量，不是淘汰所致。
- 源码：`ChatController.java:73-77` config=null 时直接 return error，不调用 record。
- 证据：chatcmpl-cc8a7633148f44efac92c33c；`assertions.json` unknown model logged。路由正确性不重复扣分。

### D07：空增量提前触发首 Token（可观测性，扣 1）

- 触发：`stream-*-empty_delta`，先发空字符串增量，等待250 ms，再发中文正文，最后正常终态。
- 预期：first_token_ms 测到非空有效正文，应该包含这250 ms等待。
- 实际：Responses 首个非空正文客户端约257.5 ms到达，网关报告 first_token_ms=3；Messages 同样提前计时。心跳与 metadata 本身不会计时，这里专门用空内容增量复现。
- 源码：`ChatController.java:170-175` 在检查文本之前，只要 type=delta 就赋值 firstToken；两个适配器会产出空文本 delta。
- 证据：两个 empty_delta case 的逐帧接收时间和最后 gateway.timings；`assertions.json` TTFT excludes empty delta。

### D08：不支持格式的上游400被映射成502（统一错误与重试，扣 1）

- 触发：`unsupported-format-openai`、`unsupported-format-anthropic`；结构化请求遇到受控上游400。
- 预期：保留统一错误结构，向调用方明确返回4xx。
- 实际：HTTP 502、code=upstream_error，错误消息含 upstream 400。不是裸透传，且没有重试，因此统一结构和不可重试处理部分保留。
- 源码：`adapter/OpenAiResponsesAdapter.java:195-204`、`adapter/AnthropicMessagesAdapter.java:268-277` 将普通4xx落入 UPSTREAM_ERROR；`common/GatewayException.java:15` 将其映射502。
- 证据：两个 unsupported-format case。DeepSeek Flash 真实 JSON 同样400→502，仅作补强，不另扣；Pro 首次缺 JSON 单词是评测输入问题，不扣分。

### D09：脚本覆盖范围和断言不足（源码、README 与验证脚本，扣 2）
