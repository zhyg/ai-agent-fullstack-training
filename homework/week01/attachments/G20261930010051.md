## 待修复问题及独立扣分复现

以下复现均使用未改动的学生代码。先按证据包 README 启动受控上游和网关，运行 `controlled_checks.py`；限流、角色、Schema 补测用 `extra_checks.py`，退避等待和正常引用对照用 `boundary_checks.py`。脚本中的替换仅发生于测试进程的 transport/时钟/随机数/睡眠记录器，应用业务函数保持原样；门控、JSON、实际次数的主验证经过 TCP 实收。

### D01：Responses 抹去多轮角色（统一接口 -2）

- 触发：“user:first user → assistant:previous answer → user:next user”。预期上游保留消息数组、角色与顺序。
- 实际：HTTP 200，但实收 input 是 `first user\n\nprevious answer\n\nnext user`，助手输出与用户输入无法区分。
- 证据：`extra-results.json` 的 responses-multiturn，`source/app/adapters.py:86-87` 直接 join 所有 content。只在接口项扣，不再扣路由或脚本分。

### D02：流终态与异常识别不足（流式 -3）

- 触发：门控等待客户端实际收到 FIRST，再分别释放 error 事件、无终态 EOF 或强制传输中断。预期有可识别失败，账本错误且不从头重试。
- 实际：两协议前两者均 `FIRST → DONE`，无错误提示、无成功终态却 success；传输中断客户端可见 RemoteProtocolError，账本仍 success。各场景均只有 1 次上游请求，不扣“输出后避免重试”2 分。
- 证据：`controlled-results.json` 对应八条门控记录及客户端逐行时间、账本；`source/app/adapters.py:117-135,186-209` 不解析 error/failed，`source/app/main.py:333,364-367,396-406` 不检查成功终态，也不捕获流中 httpx 传输错误。
- 同根因导致账本误记 success 已包含在此，不在 D07 再扣。

### D03：校验的是提取结果，返回的却是非法 JSON 原文（结构化 -2）

- 触发：受控两协议持续返回围栏文本 `` ```json\n{"ok":true}\n``` ``，response_format 使用有效 Schema。
- 预期：返回规范 JSON 字符串或明确失败；实际均 200，一次调用即返回围栏原文，`returned_content_valid_json=false`。
- 证据：`F03-F04-*-fenced`；`source/app/structured.py:29-60` 提取校验成功，但 `source/app/main.py:228-253` 丢弃解析数据，`main.py:264` 仍返回 result.text。不是对 NaN 等额外严格性扣分。

### D04：pro 的 json_object 不能在实际官方端点工作（结构化 -2）

- 触发：原模型/协议，`response_format={"type":"json_object"}`，max_tokens=256，要求输出短 JSON。
- 预期：合法 JSON 或合理降级；实际 `extract_schema` 生成仅 `{"type":"object"}`，再映射为 strict json_schema；官方返回 400 “An object with no properties is not allowed”。显式带字段的 Schema 对照真实成功，因此不是凭据、供应商不可用或输出预算问题。
- 证据：`real-results.json` pro-json、`extra-results.json` real-pro-explicit-schema；`source/app/main.py:165-173`、`source/app/adapters.py:90-98`。
- 此处扣请求映射，不因同一个失败再次判整个双协议或全部结构化缺失；其 HTTP 状态误映射是独立错误封装问题，见 D08。

### D05：用量信息丢失且未知值含义不清（可观测性 -3）

- 受控普通结果输入 11、输出 7，额外提供缓存和推理等分类；预期保存已提供分类，实际仅保留输入输出。Responses 已知缓存 3、推理 2；Anthropic 已知缓存读取 3、创建 2 均无对应账本字段。
- 先非法再合法修复两次均各用 11/7，预期已知消耗应为两次合计 22/14，实际只记最终 11/7；修复失败三次均有已知用量却落零。未知与不完整没有说明。
- 无终态时没有官方输出用量，空增量 + FIRST 估为 2 并直接写 output_tokens，既未说明估算也未区分未知；此点只扣计量含义，不重复扣 D02 的终态处理。
- 证据：A02-A03-controlled-*、F03-F04-*-repair/invalid、门控的账本；`source/app/adapters.py:21-30,108-114,177-183`、`source/app/main.py:225-253,376,392-393,418,552-553`、`source/app/store.py:22-35`。分类属于总量子集时不要求再相加。

### D06：空增量提前触发 TTFT（可观测性 -1）

- 触发：先空正文增量，等待 50ms 后发 FIRST，再门控等待终态。预期首 Token 从非空有效内容算。
- 实际：例如 pro 正常 gate 的账本 TTFT=24.28ms，FIRST 实际到达明显在后；两个适配器均将空字符串映射为 delta，网关不判断非空就计时并估计一个 Token。
- 证据：`mock_upstream.py` 的空增量/50ms 间隔、`F01-F02-*-gate` 时间记录及 `source/app/main.py:373-376`。没有将真实模型的推理内容计时口径当缺陷。

### D07：早期失败遗漏，耗尽重试记录为零（可观测性 -2）

- 触发：未知模型或模板/版本/变量缺失；预期失败可关联查询。实际 `ledger_added=0`，即调用未记录。网关本地限流也在记账前抛错（源码核对），不影响这些错误自身正确的 404/422/429 得分。
- 另触发：持续 503/429；上游确实收到 4 次（首次 + 3 次），错误账本却 `retries=0`。等待包含在 total_ms 中，保留相应得分。
- 证据：A04、F05-F06、F07-F09-*-503/429；`source/app/main.py:464-490` 位于记账 try 之前，`main.py:526-542` 在异常路径没有拿到内部 retries。与 D02 的流假成功分开，不再按实际重试上限扣分。

### D08：参数错误状态映射与未封装 Schema 500（统一错误 -2）

- 一：受控上游 400，只收到一次请求，网关返回统一对象但 HTTP 502；官方 pro-json 的 400 同样如此。预期调用参数错误为明确 4xx，而不是服务端故障。扣 1。本地限流与上游限流均可区分程度不足作为同项建议，不追加扣分。
- 二：Schema `{"type":"INVALID"}` 或 `{"$ref":"#/$defs/missing"}`，实际 500 纯文本 Internal Server Error；预期明确参数错误。有效本地引用对照 B03 为 200，未禁用所有引用。扣 1。
- 证据：F07-F09-*-400、extra-results.json 的两个 invalid-schema、boundary-results.json 的 B03；`source/app/main.py:196-203,301-308` 固定 502，`source/app/structured.py:55-59` 仅捕获 ValidationError，不处理 SchemaError/引用错误。
- Schema 500 的日志遗漏不再以同根因追加可观测性扣分。

### D09：加法抖动超出该次指数退避上界（重试 -1）

- 触发：测试进程固定 random.uniform 返回 0.05，记录 asyncio.sleep 的实参，不实际等待；持续 503，普通与建流均实收 4 次。
- 预期按评分标准 F08，第 n 次等待不超过 base·2^(n−1)（此处 base=0.5，无额外 cap）；实际为 0.55、1.05、2.05，超过 0.5、1、2。不是拿 TCP 开销推断睡眠。
- 证据：boundary-results.json 的 F08-F09-recorded-waits、boundary_checks.py；`source/app/main.py:206,311` 使用指数项加 0–0.1 的随机量。README 如实写明该算法，指数增长和有限次数仍给分，只扣抖动上界 1 分。

## 不扣分的边界与限制
