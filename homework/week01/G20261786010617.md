# 第一周作业反馈

学员：G20261786010617（风间，第一次提交）

**1. 作业等级：优秀（88分）**

**2. 作业优点**

- 两套适配器确实使用 Responses 和 Messages 两种协议。替换配置后，DeepSeek Pro、Flash 的普通调用和流式调用都实际成功。
- 双协议均通过门控流式验证：上游尚未发送结束事件时，客户端已经收到正文，不是生成完再一次性返回。
- 提示词新旧版本能分别引用，替换后的文本实际进入上游请求；缺模板、缺版本、缺变量均明确拒绝。
- 实际重试最多三次，等待约半秒、一秒；模型配额独立，超限返回 429，等待后恢复。JDK 17 打包成功，自带脚本在默认模拟配置下 10 项通过。

**3. 作业不足**

- 上游发送正文后直接断流、没有结束事件时，网关仍返回正常结束，调用记录也显示成功，客户端无法识别内容是否完整。
- JSON 基础校验能拒绝非法、空和截断正文，但合法对象后附垃圾文本仍被接受；声明的 Schema 也未拦住字段类型错误。
- 用量和延迟记录还有遗漏：Responses 缓存分类丢失，JSON 校验失败后已知用量被清零，未知模型请求没记录，空增量提前触发首 Token 计时。
- 上游不支持请求格式时，400 被包装成 502。本次 DeepSeek Flash 的强制工具结构化调用因 thinking 模式不兼容而失败，不能视为真实 JSON 验收通过。
- 验证脚本覆盖了六项功能入口，但流式只测一个模型，重试只看响应字段，限流没检查另一模型是否受影响以及配额恢复。

**4. 改进方案**

- 为流式处理保存明确的成功终态；正文后无终态就结束连接时返回错误并记失败，用两个协议的断流用例复验，保持输出后不重试。
- 校验完整正文，拒绝 JSON 后多余内容；请求 Schema 时检查字段类型。补测尾随垃圾、类型不符、空正文和截断正文。
- 保留上游已提供的缓存分类和失败调用用量，补齐未知模型记录；首 Token 只在非空有效正文到达时计时，用延迟空增量对照验证。
- 将不支持格式等上游参数错误映射为统一的 4xx；明确真实供应商的结构化能力边界，补交可用配置及两模型结构化调用证据，不把模拟结果写成真实通过。
- 给两模型补齐流式验证，核对上游实际重试次数和等待，加入模型间配额隔离及恢复断言；保留能明确显示失败的测试结果。
