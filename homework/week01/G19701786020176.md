**2. 作业优点**

- 外部替代配置下，DeepSeek V4 Pro 与 Flash 在 Chat Completions、Responses 两种协议上的普通、流式和 JSON 请求均完成真实调用。原智谱供应商未验证。

**3. 作业不足**

- 当前是双协议透传，调用方仍需选择不同接口、请求字段和结果解析方式；限流按调用方共享，模型 A 耗尽配额会阻塞模型 B，尚未满足统一适配和按模型独立限流要求。
- JSON 校验会提取围栏内的内容，但成功响应仍返回带 Markdown 围栏的原文，调用方直接解析失败。
- 流内错误事件被原样转发后，账本仍记录成功，未形成可靠的成功与失败终态判定。
- 用量账本遗漏总量及缓存、推理分类；心跳被计作首 Token；模板准备失败未入账，修复耗尽时还会少记尝试次数及已知用量。
- 默认重试抖动在指数等待值上向上浮动，可能超过该次退避预算。

**4. 改进方案**

- 增加统一入口与结果抽象，由模型配置选择协议，并统一映射 response_format；限流键纳入模型。验证同一请求结构可访问两种协议，且 A 超限不影响 B。
- 确保最终返回的模型正文就是已校验的 JSON，或明确拒绝不合规原文；增加围栏、前后说明文字、空内容和截断内容的直接解析断言。
- 解析协议终态与错误事件，正确终止并记录失败；保留已有的断流后不重试机制，补测错误事件后不得记成功。
- 在请求入口建立关联记录，按有效内容计时，保留实际提供的用量分类及各次尝试。验证心跳不触发首 Token，失败和修复调用均能准确查账。
- 将抖动限制在每次指数退避上限内，用固定随机种子或注入等待记录检查边界；补齐上述回归测试后重新验收。
