# 第一周作业反馈

学员：G20247585010117

**1. 作业等级：优秀（87分）**

**2. 作业优点**

- 同一调用入口按模型路由到 OpenAI Responses 和 Anthropic Messages。两种协议的真实普通调用和流式调用都返回了正文，上游路径、鉴权头和请求体结构不同。
- 流式响应在终态发出前已经把内容块送到客户端。内容已经输出后，后续上游错误不会再发起一次生成，避免重复正文。
- 模板可以保存多个版本，变量会替换后再进入上游请求，显式指定旧版本时不会被新版本覆盖。缺少模板、版本或变量时返回明确错误。
- 限流按模型分开计数。一个模型达到上限后返回 429 和 Retry-After，另一个模型仍可调用，窗口过后配额恢复。
- README 给出了启动、curl、错误码和配置说明。补齐缺失配置后，提交的验证脚本 24 项和测试 41 项通过；原提交本身还不能直接启动。

**3. 作业不足**

- 按 README 安装依赖后服务不能导入。提交中没有 `app.infrastructure.config`，启动和原有测试都在导入阶段失败。
- 流式连接在发出内容后直接断开、上游没有成功结束事件时，接口仍以成功结束，调用记录也记为成功。
- Anthropic 结构化请求固定使用会被当前官方模型 thinking 模式拒绝的 tool_choice。真实调用返回上游 400，网关再包成 502，没有给出可用的结构化结果。
- 失败调用有记录，但用量被写成 0。上游已经返回的输入和输出 Token 没有保留。
- 指数退避的正向抖动会让本次等待超过该次退避上限。上游参数错误返回 400 时，对外状态也变成 502。这与上面结构化调用被拒绝是两次不同的请求。

**4. 改进方案**

- 把配置模块纳入仓库，使干净环境只按 README 安装依赖就能启动，并用原有测试和验证脚本复验。
- 流式处理要区分正常结束和中途断开。没有成功终态时向客户端返回错误事件，调用记录标为失败，并用中途断流复现。
- Anthropic 结构化输出改为当前官方模型接受的写法，或在不支持时返回明确的请求错误。用两个协议各完成一次真实结构化调用验收。
- 失败记录保留已经拿到的 Token 用量，没有拿到时标明未知，不要把已知用量写成 0。
- 抖动只向下波动或限制在当次退避上限以内。上游 400、401 保持 4xx 语义，并用一次请求确认不会重试。
