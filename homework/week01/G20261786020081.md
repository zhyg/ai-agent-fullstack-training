# 第一周作业反馈

学员：G20261786020081

**1. 作业等级：优秀（80分）**

**2. 作业优点**

- 同一套 `/chat` 入口能按模型名路由，未知模型返回明确的 `UNSUPPORTED_MODEL`，没有静默改走默认模型。
- 提示词可以按版本保存和引用。发布 v2 之后仍能取回 v1，缺模板返回 404，缺变量返回 400，渲染后的正文会进入实际请求。
- 非法、空、截断 JSON 以及不符合 schema 的结果会被拒绝，失败调用也会记入指标，并带上错误码和已知用量。
- 限流按模型分开计数。一个模型配额用尽返回 429 和 `Retry-After` 时，另一个模型仍可调用；窗口过后配额会恢复。
- README 写明了启动步骤、接口和 curl 示例。按文档安装并固定兼容依赖后，服务可以启动，示例请求能返回结果。

**3. 作业不足**

- 当前配置的两个模型都走 OpenAI Chat Completions，调用方不能靠选择模型切到另一种协议。仓库里的 Anthropic Messages 适配器单独接上官方接口可以完成普通、流式和结构化调用，但没有绑定到任何模型，因此这次还不能算双协议验收通过。
- 流式输出会先攒住上游增量，等流结束才一次性下发。门控上游先发出 `FIRST`、两秒后才发 `SECOND` 时，客户端在两秒时才同时收到拼过的内容。
- 重试层数叠加后，持续 500 一次请求会打到上游 12 次。文档写的是最多重试 3 次。退避还带正向抖动，单次等待会超过当次指数上限。上游 400 和 401 会被映射成 502。
- 缺 MiniMax 密钥时，按 README 启动后调用该模型返回 500，而不是统一的上游错误。提交的验证脚本因此在第二个模型处中断，退出码为 1。

**4. 改进方案**

- 把两个模型分别绑到两种不同协议上，例如 Chat Completions 与 Anthropic Messages 或 Responses。用同一入口各做一次真实调用，核对上游路径、鉴权和请求体确实不同。
- 流式路径去掉跨块缓存，或只保留标签识别所需的极短前缀。用先发一块、延迟终态的上游确认第一块在终态之前到达，并确认正文没有被改写。
- 只保留一层重试，把 SDK 内置重试设为 0。持续 5xx 时确认上游收到的次数不超过文档声明；退避不要超过当次指数上限；400 和 401 不要重试，并映射为明确的 4xx。
- 启动时缺密钥应返回统一错误，而不是未处理的 500。补齐第二个模型的可运行配置后，重新跑验证脚本，确认它能跑完并在失败时给出非零退出码。
