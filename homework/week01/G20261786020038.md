# 第一周作业反馈

学员：G20261786020038（Sunny）

**1. 作业等级：优秀（95分）**

**2. 作业优点**

- 在 DeepSeek 官方服务上，Chat Completions 与 Responses 两种协议的普通、JSON 和流式调用均实测成功；协议路径、请求结构和响应解析确有区别。
- 双协议通过门控流式测试：终态释放前已收到正文，输出后断流会报告失败，且不重试生成重复内容。
- 模板新旧版本可分别引用，缺失项会明确报错；按模型限流、HTTP 429 和窗口恢复均通过受控测试。
- 输入、输出、缓存和推理用量及正文首 Token 延迟可关联查询，失败调用也留有记录；自带 28 项离线测试通过，验证脚本能报告注入失败。

**3. 作业不足**

- Chat Completions 非流式结构化结果未检查终止原因：上游标记长度截断时，只要正文仍是合法 JSON，就会返回成功。
- 上游拒绝结构化格式并返回 400 时，网关虽然统一了错误正文，却改成 HTTP 502，未保留明确的客户端错误语义。
- Schema 的本地引用只检查前缀，不确认目标存在；引用不存在的定义时，会先请求模型，再将本地校验异常误报为上游错误。
- 指数退避的正向抖动会突破评分标准的等待上界：基础等待 0.25、0.5 秒时，实测可变成 0.3125、0.625 秒。

**4. 改进方案**

- 在结构化成功返回前结合终止原因校验；补充“正文可解析但 finish_reason=length”的回归用例，确保返回明确失败。
- 为上游不支持的格式等不可重试 4xx 保留恰当状态和统一错误码；模拟上游 400，验证只请求一次且客户端收到 4xx。
- 在请求模型前验证 Schema 本地引用可解析；用正常引用与悬空引用作对照，确认前者通过、后者返回明确入参错误。
- 将抖动限制在指数退避上界内，保留现有次数预算；固定随机值验证每次等待上界，并继续验证两次失败后第三次成功。
