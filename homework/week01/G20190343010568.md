# 第一周作业反馈

学员：王堃（G20190343010568）

**1. 作业等级：优秀（95分）**

**2. 作业优点**

- 统一入口按 model 切换 Responses 与 Messages 协议，两个模型均完成 DeepSeek 官方真实调用，普通、流式和 JSON 输出均有运行证据。
- 原有 10 项 pytest 测试及验证脚本的离线功能检查通过；受控补测确认内容在上游结束前下发，异常 EOF 有错误事件且不会重复生成。
- 提示词能够存储、替换变量并引用旧版本；按模型独立限流、HTTP 429 和窗口恢复均已验证。
- 重试仅针对可重试错误，退避约为 10/20 毫秒，持续失败时共尝试三次；验证脚本能识别注入的错误用量。

**3. 作业不足**

- 上游参数错误 HTTP 400 被统一转换为 502，调用方难以区分请求问题和服务故障。
- Schema 引用不存在的本地定义时返回未封装的 500；有效引用的对照请求则能正常完成。
- Messages 流式处理中忽略 message_start 的输入及缓存用量；当后续事件只含输出用量时会低报总量。本次官方端点返回完整用量的正常请求不受影响。
- JSON 校验触发重新生成时，已知的前两次 Token 消耗没有计入，也没有标明统计范围；三次共 54 Token，最终仅展示 18。
- 未知模型在准备阶段返回明确错误，但没有进入调用记录，失败请求的追踪仍不完整。

**4. 改进方案**

- 对不可重试的上游参数错误保留合理的 4xx 状态，并用注入 400 的请求验证统一错误体和单次尝试。
- 在访问上游前检查本地 Schema 引用，捕获引用解析异常；分别用有效、缺失引用验证明确成功或入参错误。
- 合并 message_start 与 message_delta 的用量，保留输入和缓存分类，并用只在起始事件提供输入量的流进行回归。
- 为多次生成明确计量口径，汇总已知消耗或明确披露各次尝试及统计范围，验证三次生成的用量不会被静默丢弃。
- 将准备阶段失败纳入统一请求生命周期记录，验证未知模型、缺失模板和变量错误均可通过请求标识查询。
