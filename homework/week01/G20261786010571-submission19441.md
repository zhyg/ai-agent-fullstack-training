# 第一周作业反馈

学员：G20261786010571（小目标大成就，第二次提交）

**1. 作业等级：优秀（91分）**

**2. 作业优点**

- 同一 `/v1/llm` 入口只改模型，已实际把 DeepSeek 两个模型分别发到 Responses 和 Chat Completions。普通调用、流式和 JSON 约束都返回了合法结果。
- 已输出内容后断流不再切换备用模型；没有成功终态的连接结束会记为失败。空正文、非法 JSON 和截断 JSON 都不会以成功返回。
- 上游参数错误、鉴权失败和限流能区分，400 与 401 不会在同一上游反复请求。模型配额独立，耗尽后另一个模型仍可调用，窗口过后配额恢复。
- 模板发布新版本后仍能引用旧版，变量替换结果进入了真实上游请求。未知模型、缺模板和缺变量会进入调用审计。
- 按 README 完成安装和启动。离线 179 项测试全部通过；README 中的非流式、流式和兼容入口示例均可运行。

**3. 作业不足**

- 流式失败已经拿到用量，审计却把输入、输出和推理 Token 记成 0，只标用量不完整。已输出内容后断流时，已知用量没有保留。
- 配置写明第 n 次重试等待不超过基值乘以 2 的 n 次方再加抖动，正向抖动却使实际等待超过该上限。
- 自有 `/v1/llm` 不接受作业要求的 `response_format`，调用方必须改用 `response_schema`。兼容入口和 Responses 入口有等价字段，且两种协议的结构化结果可用。
- 示例配置的备用模型未启用 Responses，专用 `/v1/responses` 会拒绝它。本次评测另开该开关后，这个模型的 Responses 普通调用成功，不能算示例配置已通过。

**4. 改进方案**

- 流式失败终态写入已收到的用量，并用 `usage_unknown` 只标记缺失部分。用“首块带用量后断流”核对审计，确认输入、输出和推理 Token 不再被记成 0。
- 让第 n 次重试前的等待不超过配置声明的上限，正向抖动应落在该上限之内。固定随机种子后断言每次等待，再跑一次持续失败用例确认次数不变。
- 让 `/v1/llm` 接受 `response_format`，或在 README 和错误信息中明确它与 `response_schema` 的对应关系。用同一 JSON 约束分别请求两个模型，确认非法 JSON 仍失败。
- 若备用模型要走专用 Responses 入口，示例配置应打开 `supports_responses` 并用真实调用证明。否则在 README 写明该入口只适用于已启用的模型。
