# 第一周作业反馈

学员：G20261786010571（小目标大成就，第一次提交）

**1. 作业等级：优秀（83分）**

**2. 作业优点**

- 已实际启动服务，DeepSeek 两个真实模型的普通、流式及 JSON 调用均成功；另验证了官方 Responses 普通和流式调用。
- 离线验证脚本的 132 项测试全部通过；人为替换错误响应后，原有内容断言能明确报错。
- 模板发布两个版本后，仍能显式引用旧版，变量替换结果确实进入上游请求；缺失模板、版本和变量均有明确错误。
- 模型级配额隔离及补充恢复有效；关闭 SDK 内置重试，受控限流错误按指数退避执行，实际请求数符合配置。

**3. 作业不足**

- 尚未完成统一入口按模型选择不同上游协议：当前两个模型走相同 Chat 协议，使用 Responses 仍需调用方另选入口。
- Responses 入口忽略结构化约束，非法 JSON 仍返回成功；Chat 结构化输出遇空正文时，修复流程产生未处理的内部错误。
- 已输出内容后发生断流，配置备用链时仍会切换模型并重复输出；无成功终态的正常连接结束也未被可靠识别为失败。
- 修复成功只记录最后一次用量，校验失败时把已知用量记零；未知模型、模板缺项等入口失败没有进入调用审计。
- 上游参数错误、鉴权失败和限流最终均变成相同的不可用错误，调用方无法准确区分原因。

**4. 改进方案**

- 在统一模型配置中确定上游协议，由适配器完成请求和响应转换；验证同一入口只改 model 即产生两种不同协议的上游请求。
- 为 Responses 映射并校验结构化约束，或明确拒绝不支持的格式；空正文走统一失败处理，补测非法、空、截断及修复后仍失败的结果。
- 将“已输出内容”作为整条备用链的终止条件，断流后直接发失败事件；只有收到成功终态才能宣告完成，验证不重复生成。
- 累积每次已知用量并标明未知部分，将入口失败纳入统一审计出口；用修复多次、最终失败和模板缺项分别核对账本。
- 保留可识别的上游错误码及合理状态映射；用受控 400、401、429 验证错误可区分，且不可重试错误不会在同一上游反复请求。
