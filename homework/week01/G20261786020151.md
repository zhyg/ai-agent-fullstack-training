# 第一周作业反馈

学员：G20261786020151（nakayama）

**1. 作业等级：优秀（96分）**

**2. 作业优点**

- 两个模型使用不同协议，原配置下的普通、流式和 JSON 六次真实调用都成功，统一接口能正确路由。
- 流式确实逐块下发。受控断流后能报错，不重新生成已输出内容；非法、空和截断 JSON 不会当作成功返回。
- 模板可以保存多个版本、引用旧版并替换变量；模型限流互不影响，窗口到期后能恢复。
- 安装启动可复现，离线脚本实际通过 133 项测试，注入失败后能明确报错；请求关联、失败记录和延迟数据均可查询。

**3. 作业不足**

- Pro 只保留输入、输出和总 Token，上游已有的缓存命中、推理 Token 分类在转换时丢失，明细记录不完整。
- 上游不支持所请求的结构化格式而返回 400 时，网关虽然统一封装错误，却返回 502，调用方不易区分参数问题和服务故障。
- 退避采用指数等待再加正抖动，因此实际等待会超过对应轮次的指数等待上限，未把抖动限制在上限内。

**4. 改进方案**

- 保留 Pro 上报的缓存和推理分类，并写入用量明细；用非零分类同时检查普通、流式响应和查询记录，不要重复加进总量。
- 为上游格式或参数拒绝提供明确的统一 4xx 错误；模拟上游 400，确认只请求一次，响应仍带统一错误码和请求标识。
- 将抖动放进有上限的退避区间；固定随机值核对前三次等待，并继续保持最多四次实收请求及流式输出后不重试。
