**1. 作业等级：优秀（82分）**

**2. 作业优点**

- 在仅调整评测配置、不改业务源码的条件下，DeepSeek 双模型的普通和流式调用成功，实际验证了 Chat Completions 与 Anthropic Messages 两种协议。
- 门控测试确认正文在上游结束前到达；输出后发生网络断流，两种协议都没有重新生成或重复请求。
- 模板发布新版后仍可引用旧版，变量替换结果确实进入上游请求；缺模板、版本和变量都有明确错误。
- 实测前两次失败后第三次成功，退避和次数上限有效；模型 A 超额不影响 B，等待后配额恢复。提交的离线脚本 114 项通过，故意制造失败也能报错。

**3. 作业不足**

- 原配置的 smart、fast 都被原样当作真实模型名发送，官方接口返回 400。双模型接入是在使用真实模型名作为公开名称的替代配置下验证的，不能视为原配置可用。
- json_object 模式不校验正文，非法、空和截断 JSON 仍成功返回；真实 Flash 请求也复现了非法 JSON。Schema 校验虽然能拒绝错误内容，但剥掉围栏后没有同步更新返回正文。
- 心跳会被算作首 Token；上游已提供的推理分类没有记录，部分已知流式用量丢失。流内错误被记成成功，模板预处理失败则没有账本记录。
- README 缺少依赖安装步骤，依赖文件放在 app 目录；按该目录尝试安装又因找不到 README 而失败，需要人工安装依赖才能启动。

**4. 改进方案**

- 发送前使用选中路由的真实模型名，保留公开名称用于路由和记账；用原配置的 smart、fast 分别完成真实普通及流式调用，并核对实际上游请求。
- 对所有结构化模式解析最终返回正文，拒绝非法、空和截断结果；如接受围栏，应返回去围栏后的合法 JSON。补充两种协议的正常、失败及修复后仍失败用例。
- 从首个非空正文开始计时，保留上游已知用量分类；统一记录流内错误和模板预处理失败，并明确未知用量。用心跳延迟、流内错误及缺模板请求核对账本。
- 修正依赖文件与打包路径，补齐可直接执行的安装、配置和启动步骤；在全新虚拟环境按 README 重跑健康检查、curl 示例及验证脚本。
